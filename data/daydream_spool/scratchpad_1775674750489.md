This creates a "cognitive mirror" effect where the model's output is limited by its own internal architecture, potentially poisoning the broader lab architecture if not audited.

### Investigation Progress Update
- **Critical Discovery:** Found `modules/cognitive_dispatcher.py`. This is the heart of the routing logic.
- **The Vulnerability Confirmed:** 
    - The `_llm_triage` method (lines 146-180) uses the **Worker Tier** (a 0.6B model, `Qwen3-0.6B-GGUF`) to classify task complexity.
    - If the 0.6B model fails to correctly identify a `COMPLEX` task (due to "complexity collapse"), the task is routed to the `WORKER` tier instead of the `ARCHITECT` tier.
    - This is exactly what the Epiphany warned about: the small model's inability to synthesize high-level connections leads to a "recursive loop" where it misclassifies its own limitations, causing the system to use a low-parameter model for a high-parameter task.
- **Architectural Flaw:** The triage mechanism itself is subject to the very "complexity collapse" it is meant to guard against. Using a 0.6B model to decide if a task needs a 30B model is a structural circularity.

### Proposed Solution: The "Auditor" Pattern
1. **Upgrade Triage:** Instead of relying solely on the 0.6B model for triage, implement a "High-Parameter Auditor" (the 35B model) to validate ambiguous or high-risk complexity classifications.
2. **Implementation Strategy:**
    - Modify `_llm_triage` in `modules/cognitive_dispatcher.py`.
    - If the 0.6B model returns `MODERATE` or `COMPLEX` (or if the heuristic is ambiguous), trigger a secondary call to the `ARCHITECT` tier (30B/35B) to confirm.
    - This ensures that the "logic kernel" (0.6B) is only used for truly trivial/simple tasks, while the "Auditor" (35B) prevents the "complexity collapse" from poisoning the routing.
