# Apollo Investigation: Cache-to-Weight Ratio vs. Parameter Count
**Timestamp:** 2024-05-22 (Simulated)
**Status:** Initializing Audit

## Epiphany Summary
The subconscious suggests that optimizing for parameter count alone is a fallacy in memory-constrained environments (e.g., 16GB). The "Cache-to-Weight Ratio" is the true metric for stability. Specifically, for 16GB environments, the 7B FP8 threshold is identified as a critical limit to preserve KV cache for context retention.

## Investigation Objectives
1.  **Audit Current Model Deployment Configurations:** Identify if current deployment scripts or configuration files prioritize parameter count over KV cache allocation.
2.  **Analyze Memory Allocation Logic:** Search for logic that calculates VRAM requirements for weights vs. KV cache.
3.  **Verify 7B FP8 Threshold Implementation:** Check if there are existing constraints or if this needs to be codified as a hard limit in the orchestration layer.
4.  **Propose Architectural Shift:** Draft a proposal to implement "Cache-to-Weight Ratio" as a primary optimization metric.

## Initial Hypotheses
- Current deployment logic likely uses a "largest model that fits" approach, which risks OOM (Out of Memory) during long context inference.
- The orchestration layer lacks a formal "Context Buffer" safety margin.
## Findings: Scheduler Analysis
- The `Scheduler` class in `src/orchestrator/scheduler.ts` already contains a `hardware-aware` strategy (lines 36, 174-175).
- However, the `dependency-first` case (line 173) is currently stubbed out to call `scheduleHardwareAware`.
- The `hardware-aware` strategy implementation is partially visible but seems to rely on `hardwareInfo.vram_available` (from grep results in `scheduler.ts` line 346).
- **Critical Gap:** There is no explicit logic for calculating the "Cache-to-Weight Ratio" or enforcing the "7B FP8 threshold" mentioned in the epiphany. The current hardware-aware logic appears to be a simple VRAM availability check rather than a sophisticated ratio-based optimization.

## Proposed Architectural Change
1. **Introduce `CacheToWeightRatio` Metric:**
   - Define a formula: `Ratio = (Total_VRAM - Model_Weights_VRAM) / Context_Window_Size`.
   - Or more simply: `Available_KV_Cache_Capacity / Model_Weight_Size`.
2. **Update `AgentConfig` and `HardwareInfo`:**
   - Ensure `AgentConfig` includes `model_size_gb` and `precision` (e.g., FP8, FP16).
   - Ensure `HardwareInfo` provides `total_vram_gb`.
3. **Refine `hardware-aware` Strategy:**
   - Instead of just checking `vram_available`, the scheduler should calculate the predicted KV cache headroom for a given model size.
   - If `model_size_gb` > 7 (for FP8) and `total_vram_gb` is 16, the scheduler should flag a "High Risk of Context Truncation" and potentially prefer a smaller model or a different agent.
4. **Codify the 7B FP8 Limit:**
   - Add a constant `MAX_STABLE_MODEL_SIZE_16GB = 7.0`.
