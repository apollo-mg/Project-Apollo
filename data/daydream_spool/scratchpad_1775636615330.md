# Investigation Start: Hardware/Driver Stability Pivot
**Timestamp:** 2025-05-22 (Simulated)
**Objective:** Validate the "Epiphany" regarding ROCm/HIP kernel serialization and VRAM management as the root cause of ComfyUI/LLM failures.

## Initial Hypotheses
1. **ROCm/HIP Incompatibility:** The current ROCm version might have known issues with specific kernel serialization patterns used by high-throughput inference engines (vLLM, SGLang).
2. **VRAM Fragmentation/Leakage:** The "illegal memory access" errors are likely symptoms of the driver losing track of memory pages due to aggressive allocation/deallocation cycles in ComfyUI or LLM backends.
3. **Driver/Kernel Mismatch:** A mismatch between the installed `amdgpu` driver and the Linux kernel might be causing non-deterministic memory faults.

## Audit Plan
1. **Check ROCm Version & Status:** Verify current ROCm installation and driver health.
2. **Analyze Error Logs:** Search for "illegal memory access", "HIP error", or "AMD-GPU" related crashes in existing logs.
3. **Review Migration Plans:** Check `ROCM_7.11_MIGRATION_PLAN.md` and `upgrade_rocm.sh` to see if this pivot was already partially considered.
4. **Examine VRAM Management Scripts:** Review `vram_management.py` to see how the system currently handles memory.
## Findings: ROCm/VRAM Status
- **VRAM Usage:** GPU[0] is heavily utilized. Total: ~17.1 GB, Used: ~16.0 GB. This leaves very little headroom (~1.1 GB) for new allocations, which is highly suspicious given the "illegal memory access" errors.
- **Power State:** `rocm-smi` reports the GPU is in a "low-power state". This might be relevant if the driver is aggressively downclocking or entering states that interfere with high-performance kernel execution.
- **Immediate Concern:** The high VRAM utilization suggests that the system is operating at the edge of its capacity. Any sudden spike in allocation (common in ComfyUI workflows) will likely trigger an OOM or an illegal memory access if the driver fails to manage the page table correctly under pressure.

## Findings: Log Analysis
- **OOM Errors:** `apollo-core.log` shows repeated `cudaMalloc failed: out of memory` and `ROCm error: out of memory`. 
- **Note on "cudaMalloc":** Even though this is an AMD system, many libraries (like llama.cpp/ggml) use the CUDA abstraction layer via ROCm/HIP. The error confirms that the system is hitting a hard VRAM limit.
- **Correlation:** The `rocm-smi` output showed ~16GB used out of ~17GB. The logs show attempts to allocate ~857 MiB and ~248 MiB failing. This perfectly aligns with the "unstable foundation" epiphany: the system is constantly redlining its VRAM, leading to allocation failures that manifest as "illegal memory access" or outright crashes when the driver cannot fulfill a request.

## VRAM Management Audit
- The current strategy appears to be "reactive" (trying to allocate and failing) rather than "proactive" (managing a pool or clearing cache before allocation).
- The "illegal memory access" mentioned in the epiphany is likely the result of the driver/HIP attempting to handle these failed allocations or dealing with fragmented memory during these OOM events.
## Findings: Migration Plan & Driver Context
- **Current Version:** The system is running ROCm 7.2.0-2 (based on the recommendation in `ROCM_7.11_MIGRATION_PLAN.md`).
- **Known Issues:** The migration plan highlights that ROCm 7.11 (the preview) has significant regressions, including "illegal instruction" errors and model validation failures for Llama 3.1. While we are on 7.2.0, the "illegal memory access" we are seeing might be a precursor or a symptom of the same underlying memory mapping issues that plague the newer preview.
- **VRAM Management Analysis:** `vram_management.py` exists and attempts to be proactive (`smart_vram_guard`), but the `rocm-smi` output shows we are already at ~16GB/17GB. The `smart_vram_guard` threshold is set to 14.5GB (`VRAM_THRESHOLD_MB = 14500`). 
- **The Gap:** If the system is currently at 16GB, the `smart_vram_guard` *should* have triggered. The fact that we are seeing OOM errors in the logs suggests that either:
    1. The `smart_vram_guard` is not being called frequently enough in the main execution loop.
    2. The `unload_comfy_vram` function is failing to actually release memory (the "kernel cooldown" or "wait for flush" might be timing out).
    3. The memory pressure is spiking faster than the guard can react.

## Conclusion & Proposal
The "Epiphany" is correct. We are fighting a losing battle against VRAM exhaustion. The "illegal memory access" is the driver's way of saying "I can't map this memory because the heap is a mess."

### Proposed Architectural Changes:
1. **Aggressive VRAM Guarding:** Increase the frequency of `smart_vram_guard` calls in all high-level orchestrators (`orchestrator.py`, `fleet_orchestrator.py`).
2. **Enhanced VRAM Monitoring:** Modify `vram_management.py` to include a "Hard Reset" mode. If VRAM doesn't drop below 10GB after a `unload_comfy_vram` call, the system should trigger a graceful restart of the inference service.
3. **Driver Stability:** Monitor for any updates to ROCm 7.2.x that specifically address memory mapping/serialization before attempting the 7.11 migration.
4. **Immediate Action:** Audit the `orchestrator.py` to ensure it is actually utilizing the `smart_vram_guard` before every major inference task.
