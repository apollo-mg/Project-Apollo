### Deep Dive: `vllm_benchmark.py` Analysis
- **Memory Configuration:**
    - `gpu_memory_utilization=0.75`
    - `max_model_len=1024`
    - `dtype="half"` (Note: The model is FP8, but the script forces `dtype="half"`. This might cause an implicit conversion or mismatch, potentially increasing memory pressure or causing inefficient compute).
- **The Bottleneck:**
    - The model is a 14B FP8 model. 14B parameters in FP8 $\approx$ 14GB.
    - Total VRAM is 16GB.
    - `gpu_memory_utilization=0.75` of 16GB = 12GB.
    - **CRITICAL DISCOVERY:** The script is trying to fit a ~14GB model into a 12GB allocation (75% of 16GB).
    - This is the "friction of scarcity" mentioned in the epiphany. The system is likely constantly swapping weights/KV cache between VRAM and RAM because the allocated VRAM (12GB) is smaller than the model weights themselves (14GB). This explains the 6.2s/frame latency—it's not a compute problem, it's a PCIe/RAM-to-VRAM bandwidth problem caused by the mismatch between model size and `gpu_memory_utilization`.

### Conclusion
The epiphany is correct. The performance is limited by memory orchestration. The current configuration is mathematically impossible to run entirely in VRAM without swapping.

### Proposed Architectural Changes
1. **Increase `gpu_memory_utilization`:** Raise it from `0.75` to `0.90` or `0.95` to allow the 14GB model to fit within the 16GB VRAM.
2. **Align `dtype`:** Ensure `dtype` matches the model's native format (FP8) to avoid conversion overhead.
3. **Adjust `max_model_len`:** If memory is still tight, slightly reduce `max_model_len` to prioritize weight residency over context length.
4. **Remove `--lowvram` logic:** If the model can fit in 90% of VRAM, we should disable any automatic offloading mechanisms.
