# Epiphany Investigation: Archeological Architecture vs. Engineering Design

## Initial Assessment
The epiphany suggests that the current architecture is being shaped by "absences" (missing dependencies/modules) rather than intentional design. The actionable insight is to stop reactive patching and instead create a master manifest to formalize environment drift.

## Hypothesis
The project likely suffers from fragmented dependency management, where individual modules or scripts assume certain environments exist without a centralized source of truth. This leads to "whack-a-mole" debugging when new components are introduced.

## Investigation Plan
1.  **Audit Dependency Management:** Search for `requirements.txt`, `pyproject.toml`, `setup.py`, or `conda` environment files to see if a master manifest exists.
2.  **Identify Drift Patterns:** Look for logs or error patterns in `*.log` files that indicate missing modules or environment mismatches.
3.  **Analyze Core Logic:** Examine `apollo.py` and `apollo_heartbeat.py` to understand how they interact with the environment.
4.  **Synthesize Findings:** Determine if a single "Master Manifest" is feasible or if the architecture requires a more fundamental restructuring of how dependencies are declared.

---
## Dependency Audit Findings
The `find` command reveals a highly fragmented dependency landscape. There is no single source of truth. Instead, we have:
1.  **Fragmented Manifests:** Multiple JSON manifests (`guardian_manifest.json`, `provenance_manifest.json`, `model_manifest.json`, `skill_manifest.json`) scattered across different directories (`legacy_vault`, `vault`, `skills`).
2.  **Redundant/Legacy Requirements:** A massive amount of `requirements.txt` files in `legacy_docs`, `tmp`, and `llama.cpp`. This confirms the "archeology" aspect—we are digging through layers of old requirements.
3.  **Environment Drift:** The existence of `setup_voxtral.sh` and various `requirements-openvino.txt` vs `requirements-coreml.txt` suggests that the environment is being tailored per-module rather than being unified.

## Conclusion on "Absence"
The "absences" mentioned in the epiphany are likely the gaps between these disparate manifests. A module might require a dependency defined in `guardian_manifest.json`, but the execution environment is being built using a script that only looks at `requirements.txt` in a `tmp` folder.

## Proposed Action
We need to consolidate these into a single `APOLLO_MASTER_MANIFEST.json` that maps:
- **Module Name**
- **Required Dependencies (Python/System)**
- **Hardware Requirements (OpenVINO/CoreML/CUDA)**
- **Provenance/Version Constraints**

This will transform the process from "patching what's missing" to "deploying what's defined."

---
## Manifest Analysis
- `guardian_manifest.json`: This is a file integrity manifest (hashes of files). It tracks *what* the files are, but not *what they need*.
- `model_manifest.json`: This tracks model metadata (URLs, filenames, types). It tracks *assets*, but not *runtime dependencies*.

## The "Absence" Identified
The architecture is currently split into:
1. **Integrity** (Guardian)
2. **Assets** (Model)
3. **Logic** (Python files)

The **Missing Link** is the **Environment/Dependency Mapping**. There is no manifest that says: "To run `apollo.py`, you need `kokoro_tts` AND `onnxruntime` AND `numpy`." 

This is why we are "excavating": we find a model, then we realize we don't have the runtime, then we find a script that needs a specific library, and we patch it. We are building the map as we walk the terrain.

## Final Proposal Strategy
I will propose a unified `APOLLO_ENVIRONMENT_MANIFEST.json` that bridges the gap between the logic (Guardian) and the assets (Model).
