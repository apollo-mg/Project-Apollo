# Architectural Audit: Heuristic Recovery Model (Epiphany Analysis)

## 1. Epiphany Summary
The subconscious daemon identified a cognitive loop: **Error-Driven Pivoting**. 
The current architecture treats failures (math script bugs, assembly mismatches) as errors to be fixed via code patching. The epiphany suggests a shift toward a **Heuristic Recovery** model, where the agent treats low-level failures as signals to change the execution paradigm (e.g., switching backends like Triton to CK, or changing environmental overrides) rather than attempting to fix the underlying library code.

## 2. Current State Audit
- **Error Handling:** The current implementation in `src/agent/agent.ts` and `src/agent/runner.ts` follows a **Deterministic Execution** model. When a tool fails, the error is caught and returned as a `tool_result` with `isError: true`. The loop continues, expecting the LLM to "fix" the issue or react to the error message.
- **Paradigm Rigidity:** There is no explicit mechanism for a "Paradigm Pivot." The `AgentRunner` is bound to a single `LLMAdapter` and a single `ToolRegistry`.
- **Observed "Sovereign" Constraints:** The `AgentRunner` already enforces a "Sequential Execution" constraint (one tool call per turn) to ensure a deterministic Observe -> Act -> Observe loop. While this prevents "probabilistic bursts," it does not facilitate "paradigm shifts."

## 3. Proposed Architectural Update: The "Paradigm Pivot" Protocol

To implement the **Heuristic Recovery** model, I propose the following architectural changes:

### A. The `Pivotable` Interface
Introduce a new interface for `LLMAdapter` and `ToolRegistry` that allows for dynamic reconfiguration without re-instantiating the entire `Agent` or `AgentRunner`.

### B. Implementation of `ParadigmPivot` in `AgentRunner`
Modify the `AgentRunner.stream` loop to detect "Low-Level/Hardware" error patterns (e.g., `AssemblyMismatchError`, `CudaError`, `TritonKernelError`).

**Proposed Logic Flow:**
1. **Error Detection:** If `tool_result.isError` is true AND the error message matches a "Low-Level/Hardware" signature.
2. **Trigger Pivot:** Instead of just returning the error to the LLM, the `AgentRunner` triggers a `onPivotRequired` callback.
3. **Execution Paradigm Shift:**
   - **Option 1 (Backend Swap):** The `Agent` switches the `adapter` to a different provider or a different model configuration.
   - **Option 2 (Environment Override):** The `Agent` modifies the `ToolRegistry` to point to an alternative implementation (e.g., switching from a `torch` implementation to a `triton` implementation).
   - **Option 3 (Constraint Relaxation):** The `Agent` modifies its own `systemPrompt` to allow for different execution strategies.

### C. Draft Code Proposal (Conceptual)

```typescript
// src/types.ts additions
export type PivotStrategy = 'switch_backend' | 'switch_implementation' | 'environment_override';

export interface PivotEvent {
  strategy: PivotStrategy;
  reason: string;
  suggestedConfig: Record<string, any>;
}

// src/agent/runner.ts modification
// Inside the loop, after tool execution:
if (result.isError && isLowLevelError(result.data)) {
  const pivotEvent: PivotEvent = {
    strategy: 'switch_implementation',
    reason: result.data,
    suggestedConfig: { use_triton: false, use_ck: true }
  };
  this.onPivot?.(pivotEvent);
  // The runner then re-configures the registry/adapter and continues
}
```

## 4. Conclusion
The lab is currently optimized for **Deterministic Execution**. To achieve true autonomy, we must transition to **Heuristic Recovery**. This allows the agent to treat "unfixable" low-level errors not as a dead end, but as a redirection signal to change the very environment it operates within.
