# Architectural Audit: Transition from Imperative to Declarative Orchestration

## 1. Epiphany Summary
The subconscious identified a "recursive loop of manual intervention" where the agent spends excessive cognitive overhead on the mechanics of existence (managing Docker CLI, permissions, and monitoring container status) rather than task execution. This is caused by an imperative, reactive approach to infrastructure management.

## 2. Audit Findings
- **Fragmentation:** Infrastructure is currently fragmented across numerous `Dockerfile` variants and manual `.sh` launcher scripts (e.g., `docker_vllm_launcher.sh`).
- **Manual Monitoring:** There is no centralized, self-healing orchestration layer. The agent is forced to act as a manual operator of shell commands.
- **Cognitive Load:** The agent must manage hardware-specific flags and permission issues (sudo) during runtime, which is a violation of the "Stable Foundation" principle.
- **Lack of Declarative State:** The current system lacks a `docker-compose.yml` or `systemd` integration to define the desired state of the environment.

## 3. Proposed Architectural Shift: "The Orchestration Layer"

### Phase A: Declarative Infrastructure (Docker Compose)
**Goal:** Replace imperative `docker run` commands with a single source of truth.
- **Action:** Implement a root-level `infrastructure/orchestration/docker-compose.yml`.
- **Mechanism:** Use Docker Compose **Profiles** to handle hardware-specific configurations (e.g., `profile: cuda`, `profile: rocm`, `profile: cpu`).
- **Benefit:** The agent can simply call `docker compose --profile <hardware> up -d`, abstracting away the complexity of specific Dockerfiles and volume mounts.

### Phase B: Lifecycle Management (Systemd)
**Goal:** Ensure persistence and automatic recovery without manual monitoring.
- **Action:** Create `systemd` unit files to manage the Docker Compose stack.
- **Mechanism:** Use `Restart=always` and `ExecStart=/usr/bin/docker compose up` within a systemd service.
- **Benefit:** Eliminates the need for `ps -a` or `docker ps` monitoring loops. The OS handles the "mechanics of existence."

### Phase C: Permission Abstraction
**Goal:** Remove the need for `sudo` escalation in the agent's runtime.
- **Action:** Configure the `docker` group for the agent's execution user and implement a dedicated `orchestrator` service.
- **Benefit:** Reduces security risk and prevents "Permission Denied" loops.
