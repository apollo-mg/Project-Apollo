### Initial Findings
- Found multiple instances of `apollo_triage_hook.py` in `legacy_vault`.
- Need to identify the active implementation used in the current execution flow.
- The epiphany suggests the hook is critical for "structural enforcement" and must not become a bottleneck.

### Hypothesis
The current implementation might be using heavy-weight validation logic that scales poorly with increased compute capabilities. I need to find the active hook and profile its execution time or analyze its complexity.
### Analysis of `apollo_triage_hook.py`
- **Mechanism:** The hook intercepts `read_file` and `run_shell_command` (specifically `cat` and `tail`) for `.log` and `.jsonl` files larger than 10KB.
- **Latency Risk:** It calls `query_llm` with `model_override="qwen35-4b-aggressive"`. This is a synchronous network/inference call.
- **Bottleneck Potential:** If the system is performing high-frequency logging or large-scale data ingestion, every attempt to read a log file will trigger an LLM call. This is a massive latency sink.
- **Structural Flaw:** The "structural enforcement" is currently implemented as a synchronous blocking call within the execution flow. As compute scales, the time spent waiting for the LLM to summarize a log file will dwarf the actual computation time.

### Proposed Architectural Changes
1. **Asynchronous Triage:** Move the `query_llm` call to a background process or an asynchronous task. The hook should return a "pending" status or a lightweight metadata summary instead of blocking the main thread for a full LLM summary.
2. **Caching:** Implement a local cache (e.g., a small SQLite DB or even a simple file-based cache) for log summaries. If the file hash hasn't changed, return the cached summary.
3. **Threshold Tuning:** The 10KB threshold is arbitrary. We should implement a tiered approach:
    - Small files: Direct read.
    - Medium files: Lightweight regex-based summary (no LLM).
    - Large files: Asynchronous LLM summary.
4. **Decoupling:** The hook should not be part of the critical path for *every* log read. It should be a "sampling" mechanism or triggered only on specific high-priority events.
