# Architectural Audit Report: Dependency Fragmentation & Ghost Dependencies

## 1. Executive Summary
The audit confirms the "Epiphany" provided by the Subconscious: the system is suffering from severe dependency fragmentation. The search for a stable vLLM/Torch baseline revealed that the local virtual environments are either broken, orphaned, or insufficient for heavy model inference. The core inference capabilities are currently sequestered within Docker containers, creating a disconnect between the local orchestration layer and the execution layer.

## 2. Key Findings

### 2.1 Broken Local Environments
- **`venv` (Primary):** Found to be structurally invalid. The `pyvenv.cfg` contains a hardcoded path (`/home/mark/gemini/archive/personal/device_sync/phone/Project-Apollo/venv`) that does not exist in the current filesystem. This is a "ghost" environment that cannot be used for reliable execution.
- **`gemini_venv`:** Exists but does not contain `vllm` or `torch`. It appears to be a lightweight environment for auxiliary tasks (e.g., API calls, data processing) rather than model hosting.

### 2.2 Containerized Inference (The Real Baseline)
- The actual vLLM and Torch installations are encapsulated in Docker images, specifically optimized for ROCm 7.2 (e.g., `rocm/vllm-dev:rocm7.2_navi_ubuntu24.04_py3.12_pytorch_2.9_vllm_0.14.0rc0`).
- The `legacy_vault/infrastructure` directory contains the logic for managing these containers.
- This explains the "fragmentation": the system is attempting to manage high-performance model execution through a layer of shell scripts and Dockerfiles, while the local Python environment remains disconnected from these heavy dependencies.

## 3. Identified Risks
- **Migration Failure:** Any attempt to migrate to a "streamlined" architecture that assumes local `pip` installations will fail to capture the ROCm-specific optimizations currently provided by the Docker containers.
- **Orphaned Logic:** The presence of broken venvs suggests that previous attempts at environment management have left behind "ghost" structures that can mislead future automation or manual debugging.
- **Orchestration Gap:** There is a significant gap between the local `requirements.txt` (which is purely orchestration/data-focused) and the actual runtime requirements (vLLM/Torch/ROCm) which are hidden in containers.

## 4. Proposed Architectural Update (The "Rescue Mission")

To resolve this, the `streamline_proposal.md` must be updated to include the following:

### Phase 1: Environment Sanitization
- **Purge Broken Venvs:** Explicitly remove the orphaned `/mnt/TG_2TB/Projects/Apollo/venv` and any other identified non-functional environments.
- **Standardize Orchestration Environment:** Create a single, robust `apollo_orchestrator_venv` that contains all necessary libraries for managing Docker, interacting with APIs, and processing data, but *does not* attempt to host the models themselves.

### Phase 2: Unified Container Management
- **Formalize the Container Registry:** Instead of scattered shell scripts in `legacy_vault`, implement a centralized `ContainerManager` module within the `src/` directory.
- **Bridge the Gap:** The `ContainerManager` should be the single source of truth for vLLM/Torch versions, ensuring that the local orchestration layer always knows exactly which container image is running and what its capabilities are.

### Phase 3: Dependency Mapping
- Maintain a `runtime_manifest.json` that maps local orchestration requirements to the specific versions of vLLM/Torch running inside the containers. This prevents the "migration of ghost dependencies" by ensuring the local environment only tracks what it *needs* to control, not what it *needs* to run.

## 5. Conclusion
The current architecture is fractured between a broken local state and a functional but siloed containerized state. The proposed rescue mission must focus on bridging this gap through formal container orchestration rather than attempting to force heavy dependencies into a local virtual environment.
