## Findings: The "Hardware-Aware" Loop
The `scheduleHardwareAware` method in `src/orchestrator/scheduler.ts` (lines 325-359) confirms the existence of the logic described in the Epiphany. 

While the current implementation is a "simulated" version (lines 332-333), the comments explicitly state:
`// In a real implementation, we would query the OS/ROCm for current VRAM usage.`

The Epiphany's warning about "the act of asking—the constant interrogation of the CUDA state—is where the system stalls" directly maps to the intended production implementation of this `hardware-aware` strategy. If the `Scheduler.autoAssign` or `Scheduler.schedule` methods are called frequently (e.g., in a tight loop within the `Orchestrator`), and each call triggers a synchronous OS/GPU query to determine `vram_available`, the overhead of these queries will scale linearly with the number of tasks and agents, creating a recursive performance bottleneck.

## Proposed Architectural Update
To resolve this, we must decouple the hardware state interrogation from the scheduling logic.

### 1. Implement a `HardwareMonitor` Singleton
Instead of querying the OS/ROCm directly within the `Scheduler`, we should introduce a `HardwareMonitor` service.
- This service will run as a background process (or a periodic `setInterval` in the event loop).
- It will poll the hardware state (VRAM, GPU utilization, etc.) at a fixed, configurable interval (e.g., every 500ms or 1s).
- It will cache the latest state in a thread-safe/atomic manner.

### 2. Update `Scheduler` to use Cached State
The `scheduleHardwareAware` method will be updated to read from the `HardwareMonitor`'s cache rather than performing a fresh query.

### 3. Threshold-Based Updates (Optional)
If the `HardwareMonitor` detects a significant change in state (e.g., >5% change in VRAM), it can trigger an event, but the `Scheduler` will always rely on the cached value to ensure $O(1)$ access time during the scheduling phase.

## Implementation Plan (Draft)
1. **Create** `src/utils/hardware_monitor.ts`.
2. **Modify** `src/orchestrator/scheduler.ts` to import and use `HardwareMonitor.getLatestState()`.
3. **Update** `AgentConfig` or the `hardware_info` object to be populated by the monitor.
4. **Ensure** the `HardwareMonitor` is initialized during the `Orchestrator` startup.

## Conclusion
The epiphany is valid. The current "stubbed" implementation avoids the problem, but the planned "real" implementation contains a fundamental architectural flaw: synchronous, high-frequency hardware polling within the critical path of task scheduling. Moving to an asynchronous, cached monitoring model is required.
