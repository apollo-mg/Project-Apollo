# Architectural Proposal: VRAM Topology Protocol for Sovereign Swarm

## 1. Executive Summary
The current VRAM management in the Apollo architecture is **reactive** (threshold-based cleanup). To realize the "Sovereign Swarm" epiphany, the architecture must transition to a **proactive topological allocation** model. This ensures that the high-reasoning Supervisor's context window is mathematically guaranteed to coexist with the high-velocity Worker fleet within the 16GB VRAM limit of the RX 9070 XT.

## 2. Current State Audit
- **Monitoring:** `vram_management.py` successfully utilizes `rocm-smi` for real-time telemetry.
- **Mechanism:** `smart_vram_guard` triggers `unload_comfy_vram` when usage exceeds 14.5GB.
- **Deficiency:** There is no logic to prevent the Supervisor and Workers from being loaded simultaneously in a way that causes OOM. The system "reacts" to the crash/threshold rather than "architecting" the space.

## 3. Proposed Protocol: "VRAM Topology"

### 3.1 Mathematical Model
Let $V_{total}$ be the total available VRAM (16,384 MB).
Let $V_{buffer}$ be the reserved safety margin (1,536 MB, ~10%).
Let $V_{available} = V_{total} - V_{buffer} = 14,848 \text{ MB}$.

We define the **Asymmetry Ratio ($\alpha$)** based on the Supervisor's parameter scale:
- **High-Reasoning Core (Supervisor):** $V_{sup} = \alpha \cdot V_{available}$
- **Worker Fleet (Workers):** $V_{workers} = (1 - \alpha) \cdot V_{available}$

### 3.2 Implementation Strategy
1. **Model Manifest Update:** Update `model_manifest.json` to include `vram_footprint_estimate` and `context_window_vram_scaling_factor` for every model.
2. **Orchestrator Logic Update:** Modify `fleet_orchestrator.py` (or a new `swarm_orchestrator.py`) to:
    - Calculate the required $\alpha$ based on the selected Supervisor model.
    - Validate that the sum of (Supervisor VRAM + $N \times$ Worker VRAM) $\le V_{available}$.
    - Reject deployment if the topology is invalid.
3. **Dynamic Context Scaling:** Implement a mechanism where the Supervisor's context window is capped to ensure its memory footprint does not exceed $V_{sup}$.

## 4. Recommended Code Changes (Draft)

### A. `vram_management.py`

### C. `swarm_orchestrator.py` (New Module)
A new orchestrator that sits above `fleet_orchestrator.py`, specifically managing the ratio of Supervisor-to-Worker parameters.

## 5. Conclusion
By implementing this protocol, we move from a system that *survives* VRAM pressure to a system that *optimizes* it, allowing for a single high-reasoning core to effectively command a massive, low-parameter fleet without risking kernel panics or context truncation.
