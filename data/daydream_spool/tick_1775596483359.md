# Architectural Audit: Epiphany #1775596483359
## Subject: The vLLM Lifecycle Mismatch

### 1. Epiphany Validation
**Status: CONFIRMED.**
The subconscious has identified a critical structural flaw in the current deployment pattern. The `librarian_daemon.py` (found in `legacy_vault/infrastructure/`) explicitly implements the "spin up/shut down" lifecycle that the epiphany warns against.

### 2. Evidence of Structural Mismatch
The audit of `librarian_daemon.py` reveals the following anti-pattern:
- **Line 37:** `subprocess.run(["docker", "start", VLLM_CONTAINER])`
- **Lines 43-50:** A heavy retry loop (up to 20 minutes) to wait for the API server to respond.
- **Line 60:** `subprocess.run(["docker", "stop", VLLM_CONTAINER])`

This confirms that the system is paying the "compilation/initialization tax" (the 150s+ penalty) for every single ingestion cycle. This is a direct violation of the requirement for rapid agentic loops.

### 3. Proposed Architectural Shift: "Warm-Standby" Sidecar
To resolve the friction between isolation and speed, we must transition from a **Dynamic Lifecycle** to a **Persistent Infrastructure** model.

#### Proposed Changes:
1.  **Decommission `librarian_daemon.py` logic:** Remove the `docker stop` command from the ingestion cycle.
2.  **Implement a Resident Sidecar:**
    - Deploy the vLLM container as a persistent service (always running).
    - Use a lightweight "Watchdog" instead of a "Hibernator".
3.  **VRAM Management Strategy:**
    - Instead of killing the container to free VRAM, implement a **Model Swapping** or **VRAM Reservation** strategy.
    - If VRAM is needed for other tasks, use `vllm`'s ability to unload models or use a lower-priority process that can be preempted, rather than a full container teardown.
4.  **Decoupling:**
    - The `vllm_email_ingest.py` script should treat the vLLM endpoint as a stable network resource (e.g., `http://localhost:8000`), not a transient one.

### 4. Implementation Roadmap
- [ ] **Phase 1:** Modify `librarian_daemon.py` to remove `docker stop`.
- [ ] **Phase 2:** Implement a `vllm_health_check.py` service that ensures the resident container is responsive.
- [ ] **Phase 3:** Integrate a VRAM-aware scheduler that manages model loading/unloading without container restarts.

**Conclusion:** The epiphany is correct. The current "Hibernation" strategy is optimized for VRAM conservation at the catastrophic expense of operational latency. We must move toward a persistent engine architecture.
