# Architectural Proposal: Gatekeeper Semantic Hardening

## 1. Problem Statement
The current Gatekeeper implementation in `apollo_team.ts` relies on `gemma-4-26b`. While high-capacity, there is a risk of "semantic drift" where the model provides syntactically correct routing decisions that fail to capture the underlying intent of the user request, leading to incorrect agent dispatching.

## 2. Proposed Change
Transition the `gatekeeper` agent from `gemma-4-26b` to `qwen-3.5-4b-gguf`. 

**Rationale:**
- **Semantic Density:** Qwen 3.5 4B (GGUF) is optimized for high-density instruction following and schema adherence.
- **Triage Efficiency:** For a routing layer, a smaller, highly specialized model reduces latency and provides more predictable schema enforcement than a larger, more "creative" model.
- **Error Prevention:** Prevents the propagation of "structurally valid but logically useless" data to downstream specialists (Architect, Sysadmin, Archivist).

## 4. Verification Plan
1. **Unit Test:** Run the `runApollo()` function with a set of "ambiguous" prompts (e.g., "Check my system logs for errors" - which could be Sysadmin or Archivist).
2. **Schema Validation:** Ensure the Gatekeeper's output strictly adheres to the expected routing schema without hallucinating new agent names.
3. **Latency Check:** Verify that the transition to the 4B model reduces the time-to-first-token for the routing decision.

## 5. Conclusion
This change moves the architecture from a "large-model-as-default" approach to a "specialized-model-per-role" approach, increasing the overall robustness of the agentic loop.
