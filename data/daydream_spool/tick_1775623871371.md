# Architectural Audit Report: Runtime-Intent Dissociation

## 1. Executive Summary
An investigation into the "Epiphany" regarding the dissociation between recorded intent (workflows) and active reality (runtime) has confirmed a critical architectural gap. The system is currently susceptible to "silent divergence," where the loaded model's specific requirements (specifically noise schedules and sampling shifts for Flow Matching models like Wan 2.1) are not reconciled with the metadata provided in the workflow files. This results in high-impact visual artifacts (e.g., the "strobe effect" in video generation).

## 2. Findings
- **The Disconnect:** Workflows (JSON/ComfyUI style) often specify model files (e.g., `.safetensors`) or generic samplers, but the actual runtime uses `.gguf` models.
- **The "Truth" in Runtime:** The GGUF models carry specific architectural metadata (e.g., `qwen35`, `wan2.1`) that dictates a non-standard noise schedule.
- **The Failure Mode:** Standard samplers (like `dpmpp_2m` with a `simple` scheduler) do not inherently know they need to apply a `max_shift` (e.g., `3.0`) for Flow Matching models. Without this, the model treats every frame as an independent image, causing temporal instability.
- **Evidence:** 
    - `Apollo_Chat_History.txt` logs explicitly mention the "strobe effect" and the need for `max_shift=3.0`.
    - `session-2025-11-21T21-52-6ecb2ccf.json` shows a `UnetLoaderGGUF` loading a Wan 2.1 model but using a standard `KSampler` without noise-shift parameters.

## 3. Proposed Architectural Update: Runtime Verification Layer

I propose the implementation of a **`ModelRuntimeValidator`** to bridge the gap between the `WorkflowParser` and the `ModelLoader`.

### Core Components:
1.  **`MetadataExtractor`**: A module that parses GGUF metadata (using the existing `llama_model_loader` logic) to identify the model's true architecture (e.g., `FlowMatching`, `Wan2.1`, `Diffusion`).
2.  **`RequirementRegistry`**: A mapping of architectures to their required sampling parameters (e.g., `Wan2.1` -> `{ "max_shift": 3.0, "noise_schedule": "flow_matching" }`).
3.  **`DivergenceChecker`**: A logic engine that compares the `WorkflowIntent` (extracted from JSON) against the `RuntimeRequirements` (extracted from the loaded GGUF).

### Proposed Logic Flow:
```python
def validate_runtime_state(loaded_model, workflow_metadata):
    # 1. Extract architecture from GGUF metadata
    arch = loaded_model.get_metadata("general.architecture")
    
    # 2. Get required sampling parameters for this architecture
    required_params = RequirementRegistry.get_params(arch)
    
    # 3. Check if workflow provides these parameters
    for param, expected_value in required_params.items():
        actual_value = workflow_metadata.get(param)
        if actual_value != expected_value:
            # 4. Trigger reconciliation
            if is_critical(param):
                logger.warn(f"DIVERGENCE DETECTED: {param} mismatch. "
                            f"Workflow: {actual_value}, Required: {expected_value}. "
                            "Injecting required parameter to prevent strobe effect.")
                workflow_metadata[param] = expected_value
            else:
                logger.info(f"Minor divergence in {param}. Proceeding with caution.")
    
    return workflow_metadata
```

## 4. Implementation Roadmap
1.  **Phase 1 (Audit):** Update `WorkflowParser` to explicitly capture all sampling-related widgets (including `max_shift`, `shift`, `noise_type`).
2.  **Phase 2 (Detection):** Implement the `MetadataExtractor` within the `ModelLoader` to surface architecture-specific keys.
3.  **Phase 3 (Reconciliation):** Deploy the `DivergenceChecker` as a middleware between loading and execution.

## 5. Conclusion
By moving the "truth" of the model's requirements from the static workflow file to a dynamic runtime verification layer, we eliminate the risk of silent divergence and ensure that the "active reality" of the model is always aligned with the "recorded intent" of the user.
