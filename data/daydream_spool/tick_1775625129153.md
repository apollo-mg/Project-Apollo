# Architectural Audit Report: Recursive Hardware Polling Bottleneck

## 1. Executive Summary
An investigation into the "Epiphany" regarding recursive memory polling has confirmed a critical architectural risk in the `hardware-aware` scheduling strategy. The current implementation of `src/orchestrator/scheduler.ts` contains a stub for hardware-aware scheduling that, when fully implemented, would perform synchronous OS/GPU queries (e.g., ROCm/CUDA) during the task assignment phase. This creates a "monitoring-induced contention" loop where the overhead of checking resource availability contributes to the resource exhaustion it aims to mitigate.

## 2. Root Cause Analysis
The `Scheduler.scheduleHardwareAware` method (lines 325-359 in `src/orchestrator/scheduler.ts`) is designed to map tasks to agents based on VRAM availability. 

**The Flaw:**
The intended production logic (as noted in comments at lines 332-333) involves querying the OS/ROCm for current VRAM usage. Because `Scheduler.autoAssign` is called frequently to manage the task lifecycle, the system would perform $O(N \times M)$ synchronous hardware queries (where $N$ is the number of pending tasks and $M$ is the number of agents) within the critical path of the orchestrator's execution loop.

**Impact:**
- **Latency Spikes:** Synchronous GPU queries are high-latency operations.
- **Resource Contention:** The CPU/GPU overhead of the interrogation process competes with the actual agent workloads.
- **Recursive Stall:** As system load increases, the frequency of scheduling calls may increase, leading to more frequent hardware queries, further increasing load—a classic positive feedback loop of system degradation.

## 3. Proposed Architectural Resolution

### Phase 1: Decoupling via Asynchronous Monitoring
Transition from a **Reactive Polling** model to a **Cached State** model.

**New Component: `HardwareMonitor`**
- **Responsibility:** A singleton service responsible for the periodic interrogation of hardware states (VRAM, GPU utilization, etc.).
- **Mechanism:** Uses a background loop (e.g., `setInterval`) to poll hardware at a controlled frequency (e.g., 500ms - 1000ms).
- **Data Structure:** Maintains an atomic, read-only cache of the latest hardware telemetry.

### Phase 2: Refactoring the Scheduler
Update `src/orchestrator/scheduler.ts` to consume the cached state.

**Changes to `scheduleHardwareAware`:**
- **Current (Planned):** `query_os_for_vram() -> return score`
- **Proposed:** `HardwareMonitor.getLatestState().vram_available -> return score`

This change reduces the complexity of the scheduling call from a high-latency I/O operation to a near-instantaneous memory read.

## 4. Implementation Roadmap
1. **Define Interface:** Create `src/utils/hardware_monitor.ts` with a `getLatestState()` method.
2. **Implement Monitor:** Implement the background polling logic in `HardwareMonitor`.
3. **Integrate:** Inject `HardwareMonitor` into the `Orchestrator` and update the `Scheduler` to use it.
4. **Validate:** Perform load testing to ensure scheduling latency remains constant regardless of hardware state volatility.
