# Epiphany Audit: The Declarative Protocol

## 1. Executive Summary
The subconscious epiphany identifies a fundamental weakness in the current lab architecture: the reliance on "negotiable parameters" (user-driven settings, manual documentation, and soft-fail logic) rather than "environmental constants" (hard-coded constraints and automated enforcement). To reach the "Sovereign Entity" stage (Phase 13), the system must transition from a "Request-Response" governance model to a "Declarative Protocol" model, where boundaries are treated as immutable laws of the environment.

## 2. Audit Findings

### A. Governance (The Registry)
- **Current State:** `GLASS_COCKPIT.md` serves as a manual registry. It relies on the "honor system" for AI agents to document their existence.
- **Vulnerability:** This is a "negotiable" boundary. An agent can exist without being documented, leading to "ghost processes" that consume VRAM/CPU without oversight.
- **Requirement:** Transition from a manual Markdown registry to a machine-readable `registry.json` that is enforced by the `deepseek_watchdog.py`.

### B. Operational Boundaries (Context & VRAM)
- **Current State:** Context length management (e.g., in Open WebUI) is currently a "negotiable" user setting. `GLASS_COCKPIT.md` even provides instructions on how to "hard-cap" it manually when things break.
- **Vulnerability:** Relying on user intervention to prevent OOM (Out of Memory) errors is a reactive, non-declarative approach.
- **Requirement:** Move context limits into the `vllm_gatekeeper.sh` or the `MessageBus` as a hard environmental constant. The system should reject/truncate invalid context *before* it reaches the model, not as a post-crash recovery step.

### C. Logic & Integrity (The Sobriety Check)
- **Current State:** `test_logic_trap.py` demonstrates that "Sobriety" (strict adherence to JSON and logic) can be tested, but this testing is currently an external diagnostic tool rather than an internal gatekeeper.
- **Vulnerability:** Agents currently "negotiate" their output format (e.g., adding Markdown blocks), which requires manual cleanup or error handling.
- **Requirement:** Integrate the "Sobriety Analysis" logic directly into the `KAIROS Daemon` (Phase 13). Every agentic output must pass a schema and logic validation check before being promoted to the `MessageBus`.

## 3. Architectural Proposal: The Declarative Protocol

### Phase 1: The Law of Existence (Registry Hardening)
- **Action:** Implement a `system_registry.json`.
- **Enforcement:** Update `deepseek_watchdog.py` to perform a "Process-to-Registry" diff. Any process found in the OS process tree that is not explicitly declared in the registry is immediately terminated.

### Phase 2: The Law of Capacity (Context Hardening)
- **Action:** Define `HARD_CONTEXT_LIMIT` and `MAX_VRAM_THRESHOLD` as environment variables/constants in the core infrastructure.
- **Enforcement:** The `vllm_gatekeeper.sh` must intercept all incoming inference requests and perform a pre-flight check against these constants. If a request violates the constant, it is rejected with a `400 Bad Request` (Constraint Violation) rather than attempting to process it and risking an OOM.

### Phase 3: The Law of Form (Output Hardening)
- **Action:** Implement a "Declarative Validator" middleware in the `MessageBus`.
- **Enforcement:** All agent outputs are passed through a validator that checks for:
    1. **Schema Integrity:** Valid JSON.
    2. **Format Integrity:** No Markdown/Conversational noise.
    3. **Logic Integrity:** Mathematical/Conditional correctness (as seen in `test_logic_trap.py`).
- **Failure Mode:** If validation fails, the output is discarded, and the agent is issued a "Constraint Violation" signal, forcing a re-attempt with the error as a new hard constraint.

## 4. Conclusion
The transition to a "Sovereign Entity" requires the architecture to stop asking for permission and start enforcing reality. By implementing the Declarative Protocol, we move from a lab of "tools" to a lab of "laws."
