# Architectural Audit Report: VRAM/Python Lifecycle Synchronization

## 1. Executive Summary
The investigation confirms a critical synchronization gap between high-level Python object destruction and low-level VRAM reclamation. The current architecture relies on external process termination (`fuser`) and external API calls (`/free` for ComfyUI), which fails to address memory fragmentation and lingering references within the orchestrator's own execution context.

## 2. Findings
- **Gap Identified:** There is no explicit link between `del` operations/object destruction and the triggering of `gc.collect()` or GPU allocator cache clearing (`torch.cuda.empty_cache()`).
- **Fragmentation:** The failure of `expandable_segments` indicates that the allocator is struggling with non-contiguous memory requests, a symptom of the "lingering references" mentioned in the Epiphany.
- **Reactive vs. Proactive:** Current VRAM management (`vram_management.py`) is reactive (polling `rocm-smi`). It lacks a proactive "Clear-before-Allocate" protocol.

## 3. Proposed Architectural Update

### A. Enhanced `vram_management.py`
Implement a `force_memory_cleanup()` function to bridge the gap:
```python
import gc
import sys

def force_memory_cleanup():
    """
    Explicitly triggers Python GC and clears the GPU allocator cache.
    """
    print("--- [CLEANUP] Triggering explicit memory cleanup ---")
    gc.collect()
    try:
        # Check if torch is available in the current environment
        import torch
        torch.cuda.empty_cache()
        # Ensure all operations are finished before proceeding
        torch.cuda.synchronize() 
        print("--- [CLEANUP] Python GC and GPU cache cleared ---")
    except (ImportError, AttributeError, Exception) as e:
        print(f"--- [CLEANUP] Warning: GPU cache clear failed or torch not present: {e} ---")
```

### B. 'Clear-before-Allocate' Protocol
Integrate the following sequence into the `ServiceOrchestrator` or `FleetOrchestrator` lifecycle:
1. **De-provision:** Stop the current service/model.
2. **Purge:** Call `vram_management.force_memory_cleanup()`.
3. **Verify:** Call `vram_management.wait_for_vram_release(target_mb)`.
4. **Provision:** Launch the new service/model.

### C. Environment Hardening
Update `profiles.json` to ensure all model-loading processes include:
`"PYTORCH_CUDA_ALLOCATOR_CONF": "expandable_segments:True"`

## 4. Conclusion
Implementing this protocol will transform the VRAM management from a passive monitoring system into an active, synchronized lifecycle component, directly addressing the fragmentation and "death-to-release" gap identified by the KAIROS model.
