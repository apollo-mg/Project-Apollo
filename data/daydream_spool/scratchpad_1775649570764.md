# Epiphany Investigation: SGLang Native Deployment for RDNA 4 (gfx1201)
## Timestamp: 2025-05-22 (Simulated)
## Status: Investigating

### Hypothesis
The current deployment strategy relies heavily on containerization (Docker/Podman) or generic vLLM wrappers which may introduce an abstraction layer that prevents Triton kernels from optimizing specifically for the RDNA 4 (gfx1201) architecture. 

The "Epiphany" suggests that SGLang, when deployed natively, can act as the "gun" (inference orchestrator) to fire the "bullets" (Triton/ROCm/RDNA 4).

### Investigation Plan
1. **Audit ROCm/Triton Status:** Check if ROCm 7.1.1 and Triton are correctly installed and recognizing the gfx1201 hardware.
2. **Analyze Current Orchestration:** Look for existing SGLang or vLLM deployment scripts in the codebase to see if they are containerized.
3. **Check for Hardware-Specific Kernels:** Search for any existing Triton kernel implementations or optimizations for gfx1201.
4. **Evaluate 'Abstraction Tax':** Identify where Docker/Containerization is currently used for inference.
### Findings: Hardware Verification
- `rocminfo` confirms the presence of `gfx1201` and `amdgcn-amd-amdhsa--gfx12-generic`.
- The hardware is correctly recognized by the ROCm stack.
### Findings: SGLang Status
- A log file `legacy_vault/logs/sglang_install.log` shows a failed attempt to install SGLang using a ROCm 6.2 index (`https://download.ai-infra.nvidia.com/sglang/rocm62`).
- This is a critical mismatch: the system is running ROCm 7.1.1 (as per the Epiphany and `rocminfo`), but the previous attempt tried to pull from a ROCm 6.2 repository.
- This explains why the "gun" (SGLang) is missing: previous installation attempts were targeting the wrong ROCm version, likely leading to dependency hell or silent failures.
- The "abstraction tax" mentioned in the Epiphany is validated by the fact that we are currently struggling with version mismatches that could be bypassed by a clean, native installation tailored to ROCm 7.1.1.
### Findings: Abstraction Tax (Docker)
- The `legacy_vault/infrastructure/` directory contains numerous scripts (`docker_vllm_launcher.sh`, `vllm_gatekeeper.sh`, `librarian_daemon.py`) that rely heavily on Docker to run vLLM.
- This confirms the "Epiphany": the current inference orchestration is heavily containerized, which likely masks the specific hardware capabilities of the RDNA 4 (gfx1201) architecture from the Triton kernels.
- Moving to a native SGLang deployment would bypass this containerization layer, allowing for direct hardware-to-kernel interaction.
