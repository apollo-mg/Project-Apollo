# Apollo Investigation: Resurrection Tolerance vs. Stable Vectors

## Epiphany Summary
The system oscillates between causal certainty (stable vectors) and performance (TTL). The risk is "zombie data" (re-animation of deleted keys).

## Investigation Goals
1. Locate TTL and Vector Clock implementations.
2. Identify how deletions are handled (Tombstones vs. immediate purge).
3. Evaluate the risk of clock skew/late writes causing data re-animation.
4. Propose a Resurrection Tolerance threshold.

## Findings

### 1. Current State of Memory Management
- **Storage Mechanism**: The primary in-memory store (`InMemoryStore`) uses a standard JavaScript `Map`.
- **Deletion Strategy**: Deletion is immediate and destructive (`this.data.delete(key)`). There is no concept of "tombstones" (markers indicating a key was deleted) or "versioned deletions".
- **Causal Consistency**: There is no implementation of vector clocks or stable vectors in the current `MemoryStore` or `SharedMemory`. The system relies on `createdAt` timestamps, but these are only used for metadata/provenance, not for resolving conflicts or ordering events.
- **TTL/Purging**: There is currently **no** TTL-based purging mechanism implemented in the core `InMemoryStore`. The "TTL" mentioned in the Epiphany appears to be a missing feature or a conceptual tension rather than an existing implementation.

### 2. The "Zombie Data" Risk
The risk of "zombie data" is high in the current architecture. Because `delete` is an immediate removal from the `Map`:
1. **Scenario**: Agent A writes `key: value`. Agent B deletes `key`. Agent C (due to network latency or clock skew) writes `key: value_old` with a slightly older timestamp or a delayed arrival.
2. **Result**: The `Map` will simply accept the late-arriving write from Agent C as a new entry. The "deleted" state is lost.
3. **Implication**: The system cannot distinguish between a "new write" and a "resurrected write" because there is no historical record of the deletion.

### 3. Architectural Tension
- **Stable Vectors (Causal Certainty)**: Would require storing a history of operations or versioned entries. This would prevent resurrection but increase memory overhead and complexity in `get()`/`list()` operations.
- **TTL/Purging (Efficiency)**: Would allow the system to prune old data, but without tombstones, it exacerbates the zombie data problem.

## Proposed Architectural Direction

### Resurrection Tolerance Threshold
I propose a **"Tombstone Window"** approach. Instead of immediate deletion, the system should transition to a "Tombstone" state for a configurable duration.

**Proposed Threshold**: `TOMBSTONE_TTL = 24h` (or configurable per team).

### Implementation Plan
1. **Update `MemoryEntry`**: Add a `deletedAt?: Date` field.
2. **Modify `MemoryStore.delete`**: Instead of `this.data.delete(key)`, set `deletedAt = new Date()` and update the entry.
3. **Modify `MemoryStore.get`**: If `deletedAt` is present, return `null` (simulating a deletion) unless the caller explicitly requests "historical" data.
4. **Implement Purge Worker**: A background process that performs a hard `Map.delete()` only on entries where `deletedAt` is older than the `TOMBSTONE_TTL`.
5. **Conflict Resolution**: In `set()`, if an entry has a `deletedAt` timestamp, compare the new write's timestamp (if provided) against the `deletedAt` timestamp. If the write is "older" than the deletion, reject it to prevent resurrection.

## Conclusion
The current architecture favors **efficiency of the present** (simple `Map`) but is highly vulnerable to **zombie data**. To achieve the "causal certainty" required for complex multi-agent coordination, we must implement a tombstone-based deletion mechanism.
