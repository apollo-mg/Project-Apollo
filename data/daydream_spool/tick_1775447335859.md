# Architectural Audit: Unified Boundary Condition Strategy

**Epiphany**: The architecture treats resource exhaustion (VRAM limits) and data absence (FileNotFoundError) as the same class of boundary condition: 'The Edge'—where the system must decide whether to offload, fail, or persist. Both memories reveal the lab cannot distinguish between 'cannot be held' (physical constraint) and 'does not exist' (logical failure), treating both as the same containment boundary requiring explicit handling.

## Current State Analysis

### 1. VRAM Exhaustion (Physical Constraint)
**Location**: `vram_management.py`, `librarian_daemon.py`

**Current Handling**:
- **Proactive Offloading**: `smart_vram_guard()` triggers when usage > 14.5GB threshold
- **Blocking Synchronization**: `wait_for_vram_release()` blocks until VRAM flushes (30s timeout)
- **Resource Reclamation**: `unload_comfy_vram()` explicitly frees 14GB VRAM via ComfyUI API
- **Threshold-Based**: Hard-coded constants (`IDLE_THRESHOLD_VRAM_MB = 2000`)

**Pattern**: Physical resource exhaustion is treated as a **blocking condition** requiring explicit cleanup and wait loops.

### 2. FileNotFoundError (Logical Failure)
**Location**: `generate_image.py`, `whisper.cpp` bindings, `vllm_registry_backup.py`

**Current Handling**:
- **Bare Exception Catches**: `except FileNotFoundError:` with bare returns or print statements
- **Scattered**: No centralized handling; ad-hoc per-file
- **No Graceful Degradation**: Hard failures with no fallback strategies

**Pattern**: Logical resource absence is treated as **terminal failure** with no containment strategy.

## Architectural Gap

The system currently distinguishes between:
- **"Cannot be held"** (VRAM exhaustion) → **Explicit handling** with offloading, thresholds, and blocking waits
- **"Does not exist"** (FileNotFound) → **Terminal failure** with no containment strategy

**Both are the same boundary condition**: The Edge where the system must decide whether to offload, fail, or persist.
