# Epiphany Investigation: Reasoning Buffer & MLA Principles
## Timestamp: 2025-02-27
## Status: Initializing Audit

### Hypothesis
The "Epiphany" suggests that the system's memory structure is mirroring the model's internal reasoning traces (CoT). The actionable insight is to implement a 'reasoning buffer' within the orchestration layer, inspired by Multi-head Latent Attention (MLA), to prioritize CoT traces over raw token history to prevent Sysmem spills.

### Investigation Plan
1. **Identify the Orchestration Layer:** Locate the primary orchestration/management scripts (e.g., `orchestrator.py`, `fleet_orchestrator.py`, `task_manager.py`).
2. **Analyze Memory Management:** Search for how the system handles context, token history, and memory (e.g., `vram_management.py`, `prune_memories.py`, `Memory/`).
3. **Search for 'Reasoning' or 'CoT' handling:** Determine if there is existing logic that distinguishes between raw tokens and reasoning traces.
4. **Audit for 'Sysmem Spills':** Look for logs or code related to memory pressure or context overflow.
### Analysis of `orchestrator.py`
`orchestrator.py` is a high-level service manager (launching/stopping processes). It does *not* handle the actual data flow or memory management of the models. It is a process-level orchestrator, not a data-level orchestrator.

### Identifying the Data Orchestration Layer
The "reasoning buffer" and "MLA principles" must be implemented where the model's context and memory are managed. 

Potential candidates:
1. `vram_management.py`: Likely handles GPU memory allocation.
2. `prune_memories.py`: Likely handles the logic for what to keep in long-term/short-term memory.
3. `llm_interface.py`: Likely the bridge between the system and the model, where CoT vs. raw tokens might be distinguished.
4. `task_manager.py`: Might manage the lifecycle of a reasoning task.
5. `Memory/` directory: Contains the actual memory storage logic.

### Analysis of `llm_interface.py`
`llm_interface.py` is the primary interface for interacting with LLM endpoints. 

**Key Findings:**
1. **Reasoning Handling:** Lines 125-129 explicitly strip reasoning tags (`<|channel>thought...` and `[[...]]`) from assistant history. This is a crucial point of contact for the "Epiphany".
2. **Reasoning Extraction:** Lines 192-198 handle `reasoning_content` from the API response, wrapping it in `[[...]]` tags.
3. **The "Mirroring" Effect:** The system is currently *stripping* reasoning traces from the history to keep the context clean, but the "Epiphany" suggests that these traces are being imprinted on the system's memory.

### Proposed Architectural Change: The Reasoning Buffer
Instead of simply stripping reasoning traces or treating them as raw text, we should implement a "Reasoning Buffer" logic within `llm_interface.py` or a new orchestration module.

**Implementation Strategy:**
1. **Identify Reasoning vs. Content:** Use the `reasoning_content` field from the API (if available) or regex to distinguish between CoT and the final answer.
2. **Implement MLA-inspired Prioritization:**
   - When the context window or VRAM is near capacity (detected via `vram_management.py`), the system should prioritize keeping `reasoning_content` (the "latent" reasoning) over the raw token history of the conversation.
   - This "Reasoning Buffer" would act as a compressed representation of the model's logic, allowing the model to maintain its "thinking" state even if the raw conversation history is pruned.
3. **Integration with `prune_memories.py`:** The pruning logic should be updated to recognize "reasoning traces" as high-importance entities that are resistant to the standard biological decay formula.
