# Architectural Audit: Recursive State Resonance in Orchestration Layer

## Epiphany Analysis
The subconscious identified a structural resonance in the execution engine, specifically a failure to differentiate between pending tasks and terminal states within the asynchronous orchestration layer. This manifests as a recursive loop where the system chases an unreachable output state.

## Findings
After auditing `src/orchestrator/orchestrator.ts` and `src/task/queue.ts`, I have identified the following architectural vulnerability:

### 1. The `executeQueue` Loop Vulnerability
In `src/orchestrator/orchestrator.ts`, the `executeQueue` function (lines 177-292) uses a `while (true)` loop that relies on `queue.getByStatus('pending')` to determine termination. 

```typescript
183:  while (true) {
184:    // ...
188:    const pending = queue.getByStatus('pending')
189:    if (pending.length === 0) {
190:      // Either all done, or everything remaining is blocked/failed.
191:      break
192:    }
```

### 2. The "Shadow Chasing" Mechanism
The "unreachable state" occurs when tasks enter a `blocked` state due to unresolved dependencies. If a dependency fails, `TaskQueue.cascadeFailure` (lines 166-179 in `queue.ts`) correctly marks dependents as `failed`. However, if a dependency is lost or a task is stuck in `in_progress` without a terminal transition, the `pending` count may drop to zero while `blocked` tasks remain.

The "recursive loop" described in the epiphany likely refers to the `scheduler.autoAssign` call (line 186) being executed repeatedly in a loop that cannot terminate if the `pending` check is bypassed or if the state machine enters a cycle where `pending` tasks are constantly re-added or re-evaluated without progress.

### 3. Circular Dependency Risk
The `loadSpecsIntoQueue` method (lines 735-785 in `orchestrator.ts`) resolves title-based dependencies. If the coordinator produces a circular dependency (e.g., Task A depends on Task B, and Task B depends on Task A), both tasks will be marked as `blocked` in the `TaskQueue`. 

Because `isComplete()` (lines 232-237 in `queue.ts`) only checks if tasks are `completed` or `failed`, a set of `blocked` tasks will cause `isComplete()` to return `false`, but `getByStatus('pending')` will return an empty array, causing `executeQueue` to `break`. 

**The actual bug:** The system doesn't distinguish between "All tasks are finished" and "All tasks are stuck/blocked". The `executeQueue` loop terminates, but the `runTeam` method proceeds to `buildSynthesisPrompt` (line 529), which attempts to synthesize a result from a potentially incomplete or broken task set.

## Proposed Architectural Update

### A. Enhanced Termination Logic
Modify `executeQueue` to check for "Stall Conditions" (where `pending` is 0 but `isComplete()` is false).

### B. Dependency Graph Validation
Implement a cycle detection algorithm within `loadSpecsIntoQueue` to prevent the coordinator from injecting circular dependencies into the `TaskQueue`.

### C. State Machine Hardening
Update `TaskQueue.isComplete()` to include a check for `blocked` tasks, or provide a `isStalled()` method to allow the orchestrator to differentiate between a successful run and a deadlocked one.

## Conclusion
The system is indeed "chasing its own shadow" when it encounters `blocked` tasks that are not `failed`. The orchestration layer assumes that `pending.length === 0` implies completion, whereas it actually only implies that no *new* tasks can be started.
