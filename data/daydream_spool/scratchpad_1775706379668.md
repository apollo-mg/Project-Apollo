# Epiphany Investigation: Cache-Aware Routing for MoE
## Timestamp: 2025-02-27
## Status: Initializing Audit

### Hypothesis
The current MoE implementation likely routes tokens based on expert affinity (top-k logits) without considering the physical location of the expert weights in the memory hierarchy. This leads to "VRAM Bubbles" where the system waits for weights to be fetched from VRAM/System RAM, increasing latency.

### Objective
1. Locate the MoE routing logic in the codebase.
2. Identify if there is any existing mechanism for weight-location awareness.
3. Propose a 'Cache-Aware Routing' protocol that prioritizes experts residing in the L3 cache (96MB boundary).

### Investigation Plan
- [ ] Search for `moe` or `router` in `src/` and `modules/`.
- [ ] Analyze `moe_shootout.py` for clues on current MoE implementation.
- [ ] Check `vram_management.py` to see how weight residency is tracked.
- [ ] Draft architectural proposal.
### Findings: Current State of Routing
- The current `modules/router.py` implements a **Cascading Router** (System 1.5) based on model size/capability (0.6B -> 8B -> 30B).
- It is a **semantic/intent-based router**, not a **hardware-aware router**.
- It uses `llm_interface.query_llm` to decide which "module" (and thus which model) to use.
- There is no mention of expert residency, L3 cache, or VRAM-to-cache latency in the current routing logic.
- The `moe_shootout.py` script benchmarks different dense models, but doesn't seem to implement or test MoE routing logic itself; it's a performance comparison tool.

### Gap Analysis
- **The "VRAM Bubble"** is real: The current router selects a model based on the *complexity of the task*, but it ignores the *cost of switching* or the *latency of the model's weights*.
- If a task is "Medium" complexity, the router picks the 8B model. If that 8B model's weights are currently swapped out of the L3 cache or even VRAM, the "Round-Trip" time (latency) will spike.
- **Missing Component:** A `HardwareStateMonitor` that provides real-time telemetry on which model weights are "Warm" (in L3/VRAM) vs "Cold" (in System RAM/Disk).

### Proposed Architectural Update: 'Cache-Aware Routing'
1. **Telemetry Integration:** Integrate `system_monitor.py` (or a new `cache_monitor.py`) into the `router.py` decision loop.
2. **The 'Affinity-Latency' Score:** Instead of just `module` and `priority`, the router should calculate a `routing_score`:
   $$Score = \alpha(IntentAffinity) + \beta(CacheResidency)$$
   Where $\beta$ is a weight that penalizes models whose weights are not in the 96MB L3 boundary.
3. **Tiered MoE Loop:**
   - **Tier 0 (L3-Resident):** Small, highly specialized experts (sharded < 96MB).
   - **Tier 1 (VRAM-Resident):** Standard MoE experts.
   - **Tier 2 (System-Resident):** Large, dense models.
4. **Implementation Strategy:**
   - Modify `modules/router.py` to accept a `hardware_context` object.
   - Update `llm_interface` to report weight residency status.
   - Implement a "Cache-Resident Expert" preference in the routing logic.
