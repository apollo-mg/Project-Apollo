# Epiphany Investigation: Modular Workflow Conversion Template

## Initial Assessment
The epiphany suggests a shift from viewing workflows as static JSON files to viewing them as modular systems of node substitutions. Specifically, it highlights the transition from monolithic loaders (like `CheckpointLoader`) to a decoupled triad (`UnetLoaderGGUF`, `CLIPLoader`, `VAELoader`) to accommodate new architectures like Wan 2.1.

## Investigation Goals
1. Identify the codebase responsible for workflow management or node definitions.
2. Locate existing implementations of `CheckpointLoader` or similar monolithic loaders.
3. Search for any existing "Wan" or "Wan 2.1" related code to understand the current state of support.
4. Map the "triad" substitution logic.
## Findings

### 1. Workflow Context
The codebase contains references to ComfyUI-style JSON workflows, specifically in `/mnt/TG_2TB/Projects/Apollo/chat_history/local/`. A recent session log (`session-2025-11-22T03-38-f96c20d8.json`) contains a workflow for `wan_2.2_t_2_v_working.json`.

### 2. Node Architecture Analysis
The identified workflow uses a modular approach rather than a monolithic one:
- `CLIPLoaderDisTorch2MultiGPU` (mapped to `CLIPLoader`)
- `VAELoader`
- `UNETLoader`
- `ModelSamplingSD3`

This confirms the epiphany's observation: the system is already moving towards (or requires) a decoupled architecture where the UNet, CLIP, and VAE are loaded separately.

### 3. Identified Gap
There is no centralized "Modular Conversion Template" or "Substitution Map" within the `Apollo` project. Currently, adapting a workflow for a new model (like Wan 2.1) requires manual inspection of the JSON structure and manual node replacement.

### 4. Proposed Solution: Modular Conversion Template
Instead of a script that attempts to "fix" JSONs (which is error-prone), I propose a structured **Mapping Schema**. This schema would define:
- **Source Node Type:** (e.g., `CheckpointLoader`)
- **Target Node Triad:** (e.g., `[UnetLoaderGGUF, CLIPLoader, VAELoader]`)
- **Input/Output Mapping:** How the `MODEL`, `CLIP`, and `VAE` wires must be re-routed.
- **Parameter Mapping:** Which widgets (e.g., `weight_dtype`) need to be carried over.

This template can serve as a "wiring diagram" for both human architects and automated agents.
