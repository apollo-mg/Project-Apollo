# Epiphany Audit: Shift from Hardware Brute-Force to Systemic Evolution

## Summary
The investigation confirms that while the framework possesses the necessary hooks for high-fidelity data collection (via `AgentRunner` and `ToolExecutor`), the current data schema is insufficient for "systemic evolution." The system currently captures *what* happened (tool calls, tokens, duration) but fails to capture the *contextual state* (memory snapshots, reasoning traces, and hardware stability metrics) required to inform a post-RDNA 4 architecture.

## Audit Findings

### 1. The Foundry (Data Collection)
- **Status:** Functional but "low-fidelity."
- **Observation:** `ToolCallRecord` in `src/types.ts` captures `toolName`, `input`, `output`, and `duration`. This is sufficient for debugging but insufficient for architectural learning.
- **Gap:** It lacks a semantic link to the `MemoryStore` state at the time of execution and the specific `AgentState` (message history) that triggered the call.
- **Requirement:** To transcend hardware constraints, the Foundry must record the "Environmental State" alongside the "Action Result."

### 2. The Dispatcher (Orchestration & Scheduling)
- **Status:** Reactive to concurrency, but blind to hardware stability.
- **Observation:** The `AgentPool` uses a `Semaphore` to manage concurrency, which mitigates resource exhaustion. However, the `Scheduler` is purely logic-driven (capability matching).
- **Gap:** There is no feedback loop between hardware stability (e.g., vLLM/RDNA 4 kernel errors) and the `Scheduler`.
- **Requirement:** The `Scheduler` must evolve from a "Task Dispatcher" to a "Resource-Aware Orchestrator" that can throttle execution based on real-time hardware telemetry.

## Architectural Proposals

### Proposal A: High-Fidelity Observation Schema
Update `src/types.ts` to expand `ToolCallRecord` into an `ObservationRecord`:
```typescript
export interface ObservationRecord {
  readonly toolCall: ToolCallRecord;
  readonly memorySnapshot?: Record<string, string>; // Relevant memory keys/values
  readonly reasoningTrace?: string;               // Extracted from assistant text
  readonly hardwareTelemetry?: {
    gpu_temp?: number;
    vllm_status?: 'stable' | 'unstable' | 'error';
  };
}
```

### Proposal B: Stability-Aware Scheduling
Modify `src/orchestrator/scheduler.ts` to incorporate a `StabilityMonitor`. The scheduler will adjust the `maxConcurrency` of the `AgentPool` dynamically based on the frequency of `isError: true` results in the `ToolResultBlock`.

## Conclusion
The transition to "systemic evolution" requires moving from logging *events* to logging *states*. By enriching the Foundry with environmental context, we create the dataset necessary to design an architecture that is inherently resilient to the hardware constraints we are currently battling.
