# Architectural Audit Report: RDNA 4 Stability & Integrity

## 1. Executive Summary
Following a subconscious epiphany regarding RDNA 4 hardware volatility, an architectural audit was performed to investigate the relationship between hardware feature enablement (SDMA, AITER) and computational stability (RMS Norm errors, silent data corruption). 

The audit confirms that the current system maintains a "defensive perimeter" by disabling high-volatility hardware features in primary execution scripts, but maintains "performance-first" experimental paths that expose the system to the known instabilities of the RDNA 4 architecture.

## 2. Findings

### 2.1 Hardware Instability Evidence
Logs (`synthesizer_batch.log`) explicitly link RDNA 4 (ROCm/HIP) instability to:
- Silent data corruption.
- "RMS Norm" errors during generative processes.
- "Cognitive Dissonance" in model outputs.

### 2.2 Configuration Divergence
The audit identified two distinct operational modes within the codebase:

| Feature | **Integrity Mode** (Current Stable) | **Performance Mode** (Experimental/Volatile) |
| :--- | :--- | :--- |
| **Primary Script** | `start_architect.sh` | `start_coordinator_experimental.sh` |
| **SDMA Status** | `HSA_ENABLE_SDMA=0` (Disabled) | `HSA_ENABLE_SDMA=1` (Enabled) |
| **AITER Status** | `VLLM_ROCM_USE_AITER=0` (Disabled) | `VLLM_ROCM_USE_AITER=1` (Enabled) |
| **Risk Profile** | Low (Controlled Sandbox) | High (Raw Silicon Volatility) |

### 2.3 Root Cause Analysis
The "Performance Mode" attempts to maximize hardware autonomy (SDMA/AITER), which, on the current RDNA 4 silicon/driver implementation, leads to non-deterministic mathematical errors in the latent space. This confirms the epiphany: we are currently trading raw speed for the integrity of the generative output.

## 3. Proposed Architectural Shift

### 3.1 Paradigm Shift: "Integrity-First"
We will transition from a "Maximize Hardware" default to a "Minimize Interference" default. All generative video and high-precision inference tasks must default to the "Integrity Mode" baseline.

### 3.2 Concrete Implementation Plan

#### A. Update `start_coordinator_experimental.sh`
Modify the script to default to `HSA_ENABLE_SDMA=0`. Introduce a `--force-performance` flag to allow users to explicitly opt-in to the high-volatility/high-speed mode.

#### B. Standardize Environment Variables
Create a centralized `hardware_integrity.env` file containing the following "Safe Baseline" for RDNA 4:
```bash
export HSA_ENABLE_SDMA=0
export HSA_XNACK=0
export VLLM_ROCM_USE_AITER=0
export GGML_HIP_FORCE_MMQ=1
```

#### C. Documentation Update
Update `ROADMAP.md` and `README.md` to reflect that RDNA 4 hardware is currently treated as a "hostile environment" for generative tasks, requiring these specific mitigations to ensure latent space integrity.

## 4. Conclusion
The current "sandbox" approach is successful but inconsistently applied. By formalizing the "Integrity-First" paradigm, we protect the system from the inherent volatility of the RDNA 4 architecture while providing a clear, intentional path for performance testing.
