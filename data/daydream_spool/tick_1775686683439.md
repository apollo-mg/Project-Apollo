# Architectural Audit: Migration from Ollama to vLLM/SGLang

## 1. Executive Summary
The current system architecture utilizes an abstraction layer (`llm_interface.py`) that facilitates easy switching between LLM providers. However, the current operational state relies on Ollama, which, while convenient, introduces a performance ceiling by abstracting away low-level hardware optimizations (Triton kernels, ROCm-specific scheduling, and continuous batching). 

The "Epiphany" is validated: the system is currently operating in a state of "functional mediocrity" where the hardware's true capacity is underutilized.

## 2. Audit Findings
- **Abstraction Layer:** `llm_interface.py` uses a `DeploymentConfig` pattern. This is highly efficient for migration as it decouples the application logic from the specific inference engine.
- **Current State:** The `DEPLOYMENT_CONFIGS` point to `http://127.0.0.1:8082/v1/chat/completions`. This endpoint is currently served by Ollama.
- **Infrastructure Readiness:** Evidence of vLLM testing (`vllm_benchmark.py`, `run_vllm_benchmark.sh`) and SGLang logs (`sglang_install.log`) indicates that the transition has been partially explored but not fully integrated into the production deployment cycle.
- **Bottleneck Identification:** Ollama's management of VRAM and request scheduling is less granular than vLLM's PagedAttention and Triton-optimized kernels, which are critical for maximizing ROCm throughput.

## 3. Proposed Architectural Update

### Phase A: Infrastructure Deployment (Non-Code Change)
1. **Containerization:** Deploy a vLLM container specifically built for ROCm.
2. **Service Mapping:** Map the vLLM OpenAI-compatible API to the existing port `8082` (or update the config) to minimize disruption.
3. **Kernel Validation:** Execute `vllm_benchmark.py` to verify that Triton kernels are correctly utilizing the GPU's compute units during high-token prefill stages.

### Phase B: Codebase Update (Targeted Changes)
Modify `llm_interface.py` to formalize the high-performance deployment:

```python
# Proposed addition to DEPLOYMENT_CONFIGS in llm_interface.py
"vllm_optimized": DeploymentConfig(
    url="http://127.0.0.1:8000/v1/chat/completions", # Standard vLLM port
    model_name="Qwen3.5-35B-A3B-UD-IQ2_XXS",
    max_tokens=8192,
    temperature=0.6
)
```

### Phase C: Validation
1. **Throughput Test:** Compare tokens/sec between `ollama` and `vllm_optimized` configurations.
2. **Latency Test:** Measure Time-To-First-Token (TTFT) during heavy prefill loads.

## 4. Conclusion
The migration is low-risk due to the existing `DeploymentConfig` abstraction. The primary effort should be focused on the containerized deployment of vLLM and the validation of ROCm optimizations. This move will bridge the gap between "convenience" and "peak performance."
