# Apollo Investigation Scratchpad
## Epiphany Analysis
- **Core Issue:** Friction between C++ template abstractions and ROCm 7.2 macro requirements.
- **Symptom:** Boundary violations/scope pollution in kernel headers.
- **Proposed Solution:** 'Clean-Slate' protocol (Master Restore + Atomic Application).

## Detailed Findings
- **Code Analysis (`ggml-cuda/sum.cu`):** 
    - Line 19 explicitly notes: `// For AMD there is rocPRIM which could be used as a drop-in replacement via hipcub but this would require C++11 -> C++14.`
    - This confirms the "friction" between high-level abstractions (C++11/14) and the specific requirements of the ROCm/HIP ecosystem (rocPRIM/hipcub).
    - The current implementation uses a fallback (`sum_rows_f32_cuda`) instead of the optimized `rocPRIM` path because of the C++ versioning constraint.
- **Code Analysis (`ggml-cuda/mmq.cu`):**
    - Uses heavy template usage (`mul_mat_q_case<GGML_TYPE_Q4_0>(...)`) which is exactly what the epiphany warns about.
    - The `switch` statement (lines 6-68) is a manual dispatch mechanism that likely suffers from the "scope pollution" or "macro-translation" issues when trying to support multiple architectures (NVIDIA vs AMD/CDNA) within the same template-heavy framework.
- **Architectural Audit:**
    - The current approach is "incremental patching" of kernel logic via `switch` statements and `#ifdef` blocks.
    - The epiphany suggests that when these template/macro boundaries fail, we should not try to patch the existing files, but rather perform a "Master Restore" and apply all fixes atomically.
- **Conclusion:** The epiphany is highly relevant. The `ggml-cuda` (and likely `ggml-hip`) implementation is a prime candidate for the 'Clean-Slate' protocol. The friction is real: the code is trying to bridge the gap between generic C++ templates and hardware-specific ROCm/HIP requirements, and the current "patch-as-you-go" method is causing scope/macro leakage.
