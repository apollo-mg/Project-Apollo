# Architectural Audit: VRAM Headroom Protocol Implementation

## Epiphany Summary
The connection between long-running video generation (Hunyuan) and 'illegal memory access' errors indicates that latency is a symptom of memory-boundary thrashing. The system is currently treating `radeontop` as a passive observer, whereas it should be used as a proactive trigger for a 'VRAM Headroom' protocol.

## Current State Analysis
The current `hardware-aware` scheduling strategy in `src/orchestrator/scheduler.ts` is a "simulated" implementation. It relies on static `hardware_info` provided in the `AgentConfig` (lines 345-346), which does not reflect real-time VRAM pressure. 

```typescript
// Current implementation (Lines 344-349)
const scoredAgents = agents.map(agent => {
  const hardwareInfo = (agent as any).hardware_info || {}
  const availableVram = hardwareInfo.vram_available || 0
  const score = needsHighVram ? availableVram : 1
  return { agent, score }
}).sort((a, b) => b.score - a.score)
```

This approach is reactive only to the *initial* configuration, not the *dynamic* state of the GPU during execution.

## Proposed Architectural Update: "The VRAM Headroom Protocol"

### 1. Dynamic Telemetry Integration
Instead of relying on static `AgentConfig` metadata, the `Scheduler` (or a dedicated `HardwareMonitor` service) must poll real-time metrics from `rocminfo` or `radeontop`.

### 2. Proactive Constraint Enforcement
We must transition from a "Score-based" assignment to a "Constraint-based" assignment.
- **Threshold:** If `current_vram_usage > 90%`, the agent is marked as `UNSTABLE`.
- **Action:** Tasks requiring high memory (detected via keywords like 'video', 'generation', 'Hunyuan', 'large-scale') must be blocked from `UNSTABLE` agents.

### 3. Implementation Plan (Draft)

#### Step A: Update `AgentConfig` and `HardwareMonitor`
Introduce a `HardwareMonitor` that runs as a background task, updating a shared state of available VRAM.

#### Step B: Refactor `scheduleHardwareAware`
Modify `src/orchestrator/scheduler.ts` to use real-time telemetry.

**Proposed Code Change (Conceptual):**

## Conclusion
The current implementation is insufficient for production-grade stability. To prevent kernel hangs and illegal memory access, the scheduler must move from a static capability-matching model to a dynamic, telemetry-driven constraint model.
