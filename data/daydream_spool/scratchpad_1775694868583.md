# Interface Audit: Ingestion vs. Observation Layer

## Initial Hypothesis
The system currently suffers from "Interface Bloat." The Epiphany suggests that the distinction between how Apollo receives data (Ingestion) and how Apollo presents data (Observation/Telemetry) is blurred. 

## Audit Objectives
1. Identify all "Ingestion" scripts (Discord, WebUI, API, etc.).
2. Identify all "Observation" scripts (React dashboards, Glass Cockpit, Telemetry, etc.).
3. Flag "Hybrid" scripts that violate the separation of concerns.
4. Identify "Redundant" scripts that serve the same purpose.

## Current Status
Investigation started.

- `modules/dashboard.py` acts as an observation point but monitors the bridges.
- `modules/forge.py` seems to handle "refining" and "posting", which blurs the line between processing and outputting.
- `discord_bridge.py` is likely both: Ingesting user commands AND Outputting responses. This is a primary candidate for the "Hybrid" category.
- `apollo_bridge.py` (implied by `modules/dashboard.py` monitoring port 5000) is likely the central hub, but its role in Ingestion vs. Observation needs clarification.

## Hypothesis Update
The "Discord Bridge" is the most problematic component because it is inherently bi-directional. It is an Ingestion point (user commands) and an Observation point (status updates/responses). The architecture needs to decouple the *Command Processing* (Ingestion) from the *Response Delivery* (Observation).
## Detailed Audit: Discord Bridge Analysis

### Component: `legacy_vault/tools/discord_bridge.py`

**Role Analysis:**
- **Ingestion (Input):**
    - Uses `commands.Bot` to receive user input (implied by `command_prefix='!'`).
    - Uses `ui.Button` (e.g., `Approve`, `Deny`, `Refine Forge`) to ingest user decisions/commands.
- **Observation (Output/Telemetry):**
    - `check_new_refinements`: Pushes new architect proposals to the `monitoring` channel.
    - `update_planner_dashboard`: Pushes the system dashboard to the `planner` channel.
    - `check_pending_approvals`: Pushes security approval requests to the `monitoring` channel.

**Verdict:**
The `discord_bridge.py` is a **High-Complexity Hybrid**. It violates the separation of concerns by acting as both a command listener (Ingestion) and a proactive notification engine (Observation).

### Proposed Architectural Shift
To resolve the fragmentation, we must move toward a **"Centralized Intelligence, Decoupled Interfaces"** model.

1.  **Ingestion Layer (The "Ears"):**
    - Create a dedicated `IngestionService`.
    - The `discord_bridge.py` should be stripped of its "proactive" logic. Its only job should be to translate Discord events (messages, button clicks) into standardized internal events/commands.
    - It should *not* contain logic for monitoring files (`check_new_refinements`) or pushing dashboards.

2.  **Observation Layer (The "Eyes"):**
    - Create a dedicated `TelemetryService` or `NotificationService`.
    - This service will be responsible for all outbound communication.
    - It will listen to internal system events (e.g., `NEW_PROPOSAL_READY`, `SYSTEM_STATUS_CHANGE`) and decide which bridge to use (Discord, WebUI, or Log).
    - The `discord_bridge.py` would then be treated as just one of many "Output Drivers" for the `TelemetryService`.

3.  **The Core (The "Brain"):**
    - The core intelligence (e.g., `modules/forge.py`, `modules/cognitive_dispatcher.py`) should remain agnostic of whether the user is on Discord or a WebUI. It should only interact with the `IngestionService` and emit events for the `TelemetryService`.

## Actionable Proposal for Next Sprint

### 1. Deprecate "Proactive" Discord Logic
- Move `check_new_refinements` logic from `discord_bridge.py` to a new `modules/notification_engine.py`.
- Move `update_planner_dashboard` logic to the same engine.
- Move `check_pending_approvals` logic to the same engine.

### 2. Standardize the Interface
- Define a `Command` schema for all Ingestion.
- Define an `Event` schema for all Observation.

### 3. Consolidate Bridges
- If the WebUI bridge and Discord bridge both implement "Command Processing," they must both call a single `CommandDispatcher`.
- If the WebUI is intended to be the primary "Observation" point, the Discord bridge should be relegated to "Alerting/Notification" only.
