# Architectural Audit: Temporal Entropy Monitor Implementation

## Epiphany Summary
The subconscious identified a tension between high-level semantic goals and low-level execution jitter. Specifically, the agentic loop can fall into "stuttering" patterns—high-frequency, recursive, or repetitive tool-calling loops that consume turns and tokens without making meaningful progress toward the macro-level objective.

## Audit Findings
The investigation of `src/agent/runner.ts` confirmed the following:
1. **Deterministic Loop:** The `AgentRunner` uses a `while(true)` loop that enforces a single-tool-call-per-turn constraint to ensure "Sovereign Integrity."
2. **Lack of Semantic Monitoring:** While the runner tracks `turns` and `tokenUsage`, it has no concept of the *quality* or *directionality* of the turns. It cannot distinguish between a productive sequence of actions and a repetitive "stutter."
3. **Vulnerability:** An agent can enter a loop of calling the same tool with minor variations (e.g., `list_files` -> `read_file` -> `list_files`...) which will continue until `maxTurns` is exhausted, wasting resources and failing the task.

## Proposed Architectural Update

### 1. New Component: `TemporalEntropyMonitor`
A new utility class to be placed in `src/utils/entropy_monitor.ts`.

**Core Logic:**
- **Signature Generation:** For each turn, create a signature: `hash(tool_name + JSON.stringify(input_params))`.
- **State Tracking:** Maintain a sliding window of the last `N` signatures.
- **Entropy Calculation:** 
    - Calculate the ratio of unique signatures to total turns in the window.
    - If `unique_signatures / total_turns < threshold` (e.g., 0.3) AND `turns > min_threshold` (e.g., 3), flag as `isStuttering`.

### 2. Integration into `AgentRunner`
Modify `src/agent/runner.ts` to incorporate the monitor:

**Changes in `stream()` method:**
- **Initialization:** `const entropyMonitor = new TemporalEntropyMonitor({ windowSize: 5, threshold: 0.4 });`
- **Observation:** After `await this.toolExecutor.execute(...)`, call `entropyMonitor.recordTurn(block.name, block.input);`.
- **Intervention:** If `entropyMonitor.isStuttering()` returns `true`:
    - Inject a high-priority system message into `conversationMessages`:
      `"[SYSTEM ALERT]: High-frequency repetitive behavior detected. You are stuck in a loop. Break the cycle by pivoting to a fundamentally different tool or summarizing your current state."`
    - This forces the LLM to break the "vibration" and return to the "cathedral of logic."

### 3. Telemetry Update
Update `RunResult` interface in `src/types.ts` to include:
- `entropyScore: number` (The final entropy value of the run).
- `stutterDetected: boolean`.

## Implementation Details (Pseudo-code)

```typescript
// src/utils/entropy_monitor.ts
export class TemporalEntropyMonitor {
  private signatures: string[] = [];
  constructor(private windowSize: number, private threshold: number) {}

  recordTurn(name: string, input: any) {
    const sig = `${name}:${JSON.stringify(input)}`;
    this.signatures.push(sig);
    if (this.signatures.length > this.windowSize) this.signatures.shift();
  }

  isStuttering(): boolean {
    if (this.signatures.length < this.windowSize) return false;
    const unique = new Set(this.signatures).size;
    return (unique / this.signatures.length) < this.threshold;
  }

  getScore() {
    return new Set(this.signatures).size / this.signatures.length;
  }
}
```

Implementing this monitor bridges the gap between the "frantic heartbeat" of execution and the "cathedral" of semantic intent. It provides a formal mechanism to acknowledge and mitigate the micro-scale jitter that threatens macro-level goal achievement.
