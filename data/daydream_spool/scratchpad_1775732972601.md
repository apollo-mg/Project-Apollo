# Epiphany Investigation: Tiered Nervous System (Reflex vs. Deliberative)
## Timestamp: 2025-05-22 (Simulated)
## Status: Initializing Audit

### Hypothesis
The current architecture treats "local" and "cloud" as binary fallbacks (if cloud fails, use local). The Epiphany suggests a paradigm shift:
1. **Reflex Layer (GigaChat 3.1 Lightning):** Low-latency, high-speed, handles immediate/reflexive tasks.
2. **Deliberative Layer (Cloud API):** High-latency, deep processing, handles complex reasoning.

The goal is to move from "Fallback" to "Tiered Hierarchy."

### Investigation Plan
1. Identify current implementation of "local fallback" logic.
2. Locate where "queues" and "timeouts" are currently managed.
3. Map the existing decision-making logic that selects between local and cloud.
4. Determine if there is a mechanism to route tasks based on *complexity* rather than just *availability*.
### Findings
1. **Current Fallback Mechanism:**
   - Found in `/mnt/TG_2TB/Projects/Apollo/tmp/open-multi-agent/src/llm/anthropic.ts` and `openai.ts`.
   - The logic appears to be: `try { cloud_api } catch { fallback_local }`.
   - This confirms the "binary fallback" pattern identified in the hypothesis.

2. **Queue/Timeout Management:**
   - `TaskQueue` is central to the orchestration (`src/team/team.ts`, `src/orchestrator/orchestrator.ts`).
   - Timeouts are currently hardcoded or used as error-handling triggers (e.g., `openai.ts:301`).
   - The queue is used for *sequencing* and *dependency management*, but not for *intelligence routing*.

3. **Architectural Gap:**
   - There is no "Router" or "Classifier" that evaluates a task's complexity *before* assigning it to a provider.
   - The system currently treats all tasks as "Cloud-first" and only uses local as a safety net for failures.

### Proposed Architectural Shift: The "Tiered Nervous System"
Instead of `Cloud -> Fallback to Local`, we implement `Router -> [Reflex Layer | Deliberative Layer]`.

**New Component: `IntelligenceRouter`**
- **Input:** Task description + Metadata (e.g., `priority`, `complexity_hint`).
- **Logic:**
    - If `complexity < threshold` OR `latency_requirement == 'ultra-low'`: Route to **GigaChat 3.1 Lightning (Reflex Layer)**.
    - If `complexity >= threshold`: Route to **Cloud API (Deliberative Layer)**.
- **Benefit:** Decouples user experience from cloud latency. The "Reflex Layer" handles the "chatter" (formatting, simple extraction, status updates), while the "Deliberative Layer" handles the "thinking" (reasoning, synthesis).

### Implementation Strategy
1. **Define Task Complexity:** Introduce a `complexity` score in the `Task` schema.
2. **Implement Reflex Layer:** Integrate GigaChat 3.1 Lightning as a first-class provider in `src/llm/`.
3. **Update Orchestrator:** Modify `src/orchestrator/scheduler.ts` to use the `IntelligenceRouter` instead of simple provider assignment.
4. **Refactor Queue:** The queue should support "priority lanes" for reflex tasks to ensure they bypass heavy deliberative queues.
