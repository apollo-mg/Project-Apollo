# ARCHITECTURAL AUDIT: THE HOMOGENEITY TRAP
**Status:** Epiphany Validated.
**Date:** 2025-05-22 (Simulated)
**Subject:** Transition from Multi-LoRA to Model Router Pattern.

## 1. THE PROBLEM: THE HOMOGENEITY TRAP
The current architecture attempts to manage heterogeneous model requirements (e.g., DeepSeek 14B for reasoning vs. 7B Vision for multimodal tasks) through a single-architecture optimization model (Multi-LoRA). 

**Symptoms Identified:**
- **ComfyUI Tracebacks:** Asynchronous execution loops fail when mapping multi-architecture requirements to a single-model context.
- **Structural Limitation:** The system treats "personality" (LoRA) as the primary variable, while ignoring "scale/architecture" (Base Model) as the fundamental constraint.
- **The "Singular Brain" Constraint:** Forcing a 14B reasoning model and a 7B vision model into a single vLLM instance via LoRAs creates a bottleneck where the model scale mismatch causes execution failures during heterogeneous task switching.

## 2. AUDIT FINDINGS
- **`llm_interface.py` Analysis:** The current implementation uses a `UNIFIED_MODEL` constant (`Qwen3.5-35B-A3B-UD-IQ2_XXS`) and a single `LLM_API_URL`. This confirms the "Singular Brain" constraint. The interface is hardcoded to a single endpoint, making it impossible to route requests to different base models without changing the global state.
- **`vram_management.py` Analysis:** The system is highly sensitive to VRAM (threshold 14.5GB). Attempting to load multiple large base models via a Multi-LoRA approach is already pushing the limits of the 16GB RX 9070 XT.
- **`model_manifest.json` Analysis:** The manifest is currently used for small assets (TTS), not for managing a heterogeneous model fleet.

## 3. PROPOSED ARCHITECTURAL SHIFT: THE MODEL ROUTER
Instead of a single `LLM_API_URL` and `UNIFIED_MODEL`, we must implement a **Model Router Pattern**.

### Proposed Changes:
1.  **Decouple `llm_interface.py` from a single constant:** Replace `UNIFIED_MODEL` and `LLM_API_URL` with a dynamic routing mechanism.
2.  **Implement `ModelRouter` Class:**
    - A registry of available model endpoints (e.g., `http://127.0.0.1:8082` for DeepSeek, `http://127.0.0.1:8083` for Vision).
    - A routing logic based on task type (e.g., `task_type="vision"` -> `route_to_vision_model()`).
3.  **VRAM-Aware Orchestration:**
    - The Router must interface with `vram_management.py` to ensure that switching between a 14B and 7B model doesn't trigger an OOM.
    - It should trigger `unload_comfy_vram()` if the target model requires a significant VRAM footprint that exceeds current availability.

## 5. CONCLUSION
The "Homogeneity Trap" is a structural failure, not a software bug. We must accept the VRAM overhead of running distinct vLLM instances to achieve the necessary architectural freedom. The transition to a Model Router pattern is mandatory for the stability of the heterogeneous model fleet.
