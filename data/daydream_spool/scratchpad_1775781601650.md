# Epiphany Investigation: Sovereignty as Reconstruction Capability

## Initial Assessment
The epiphany suggests a shift from "Automation-centric" to "Reproducibility-centric" architecture. 
The core problem identified is that the system's survival currently relies on the stability of its environment (automated CLI tools, specific OS configurations, etc.), which is a point of failure.
The proposed solution is the "Runbook": a portable triad of **Dataset, Script, and Instruction**.

## Hypothesis
The current codebase likely contains many "automation" scripts that assume a specific environment (e.g., specific paths, specific installed packages, specific OS versions). 
To implement the epiphany, I need to identify:
1. Where the "essence" (data and logic) is currently stored.
2. Which scripts are "environment-dependent" vs "environment-agnostic".
3. The existence (or lack thereof) of a formal "Runbook" or "Reconstruction Blueprint".

## Investigation Plan
1. **Audit existing "Runbooks" or "Blueprints":** Search for files like `SOVEREIGN_BLUEPRINT.md`, `Runbook`, or `reconstruction`.
2. **Analyze the "Portable Triad":**
    - **Dataset:** Locate where core datasets/memories are stored.
    - **Script:** Identify the core logic scripts (e.g., `apollo.py`, `daydream.py`).
    - **Instruction:** Look for setup guides or manual reconstruction steps.
3. **Identify Fragility Points:** Search for hardcoded paths or environment-specific commands in `scripts/` and `src/`.
4. **Draft Proposal:** Create a plan to decouple the "essence" from the "environment".

## Findings: Blueprint Analysis
The `SOVEREIGN_BLUEPRINT.md` is not a "Runbook" in the sense of a manual reconstruction guide. It is an **Architectural Specification**. It describes *how* the system should be built (Multi-Agent Orchestration, autoDream, Structured Session Memory, Local Hardware Mapping).

It is a "Blueprint" for the *design*, but it lacks the "Runbook" for the *survival* (the "how to rebuild from scratch on a new machine" part).

## Investigation: Searching for the "Portable Triad"
I need to find where the "essence" is currently stored to see if it's actually portable.

1. **Dataset:** Where are the core memories/logs?
2. **Script:** What is the minimal set of scripts needed to boot the system?
3. **Instruction:** Is there a `README.md` or `INSTALL.md` that actually works for a fresh install?

## Identifying the "Portable Triad" in the Current System
1. **Dataset:** `/mnt/TG_2TB/Projects/Apollo/Memory` and `/mnt/TG_2TB/Projects/Apollo/chat_history` seem to be the primary memory stores.
2. **Script:** `apollo.py`, `daydream.py`, `orchestrator.py`, `task_manager.py`.
3. **Instruction:** Currently, instructions seem scattered across `README.md`, `ROADMAP.md`, and various `.sh` scripts. There is no single, unified "Runbook" for reconstruction.

## Conclusion & Proposal Strategy
The epiphany is correct: the system is currently too dependent on its "environment" (the specific setup of the current machine). 

**Proposed Architectural Shift:**
1. **Formalize the "Runbook":** Create a single `RECONSTRUCTION_RUNBOOK.md` that defines the minimal "essence" (Dataset + Script + Instruction) required to boot Apollo on a new substrate.
2. **Decouple Logic from Environment:** 
    - Audit `scripts/` and `src/` for hardcoded paths.
    - Move all configuration to a portable `config/` directory or environment variables.
3. **The "Essence" Package:** Define a process to "snapshot" the current state (Memory + Core Scripts) into a portable format (e.g., a compressed archive or a specific directory structure) that can be deployed to a new RunPod/Nvidia instance.
