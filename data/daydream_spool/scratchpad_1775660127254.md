# Dependency Stress Test: Sovereign Autonomy Audit
## Timestamp: 2025-03-27 (Simulated Pre-Shift)
## Objective: Identify implicit dependencies on external connectivity, cloud telemetry, or centralized orchestration that would fail in an air-gapped/decoupled environment.

## Initial Hypothesis:
The MoE (Mixture of Experts) architecture is designed for VRAM efficiency, but the orchestration layer might rely on external APIs for model routing, weight loading, or telemetry. If the "March 31st shift" occurs, any dependency on `huggingface.co`, `openai.com`, or centralized telemetry servers will break the swarm.

## Investigation Plan:
1. **Orchestration Audit**: Examine `orchestrator.py`, `fleet_orchestrator.py`, and `task_manager.py` for external API calls or remote weight fetching.
2. **Telemetry Audit**: Examine `telemetry_layer.py` and `foundry_logger.py` for cloud-based logging or external telemetry sinks.
3. **Weight Loading Audit**: Search for `huggingface`, `download`, `requests`, or `urllib` in scripts related to model provisioning (`model_provisioner.sh`, `model_manifest.json`).
4. **Dependency Audit**: Check `requirements.txt` for cloud-native SDKs.
## Findings:
- **Localhost usage**: Most `http://` hits in the core logic (e.g., `shop_bridge.py`, `moe_shootout.py`, `test_27b.py`) are targeting `127.0.0.1` or `localhost`. This is a positive sign for autonomy; the system is communicating with local services (Ollama, ComfyUI, etc.).
- **Potential Risk**: `shop_bridge.py` uses `KLIPPER_IP`. If this IP is a remote device that becomes unreachable, the bridge fails.
- **External Dependencies**: The `venv` contains many external URLs (GitHub, MDN, etc.), but these are likely for documentation or package metadata, not runtime logic.
- **Missing Audit**: I haven't yet checked `model_provisioner.sh` or `model_manifest.json` for remote weight downloading (e.g., `huggingface_hub`).
## Critical Vulnerability Identified:
- **Model Provisioning Dependency**: The `llama.cpp` and `whisper.cpp` scripts (found in `legacy_vault`) rely heavily on `huggingface.co` for downloading weights and configs. While these are in `legacy_vault`, any future deployment or automated scaling that uses these scripts will fail in an air-gapped environment.
- **Build-time Dependencies**: `bootstrap_apollo.sh` and several `legacy_vault` scripts attempt to download PyTorch and other packages from external indices (`download.pytorch.org`, `wheels.vllm.ai`).
- **Runtime Autonomy**: The core Python logic (`shop_bridge.py`, `moe_shootout.py`) appears to be correctly targeting `localhost` or `127.0.0.1`, which is excellent for local autonomy. However, the *initialization* of the swarm (getting the weights onto the machine) is currently a "connected" process.

## Proposed Architectural Changes (Sovereign Resilience):
1. **Local Model Registry**: Implement a local `model_registry` directory that acts as a "Sovereign Reserve." All model weights, tokenizers, and configs must be mirrored here before the system is considered "deployment-ready."
2. **Offline-First Provisioning**: Modify `model_provisioner.sh` to check for local existence before attempting any network calls. If a model is missing, it should fail gracefully or trigger a "Sync Required" state rather than attempting a failed `wget`.
3. **Containerized/Bundled Dependencies**: Move away from `pip install` during runtime/bootstrap. Use pre-built wheels or a local `pip` mirror to ensure that the environment can be reconstructed without internet access.
4. **Telemetry Decoupling**: Ensure `telemetry_layer.py` has a "Local-Only" mode where logs are written to a local SQLite database or flat files, with no attempt to push to external endpoints.
