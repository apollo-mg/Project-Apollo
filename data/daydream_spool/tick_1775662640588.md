# Architectural Audit: Dual-Entity Orchestration & Handshake Protocol

## 1. Executive Summary
The current system architecture exhibits a "Launcher-Worker" split where the management layer (`orchestrator.py`) and the execution layer (Inference Servers) operate as disconnected entities. The "Launcher" uses a "fire-and-forget" model, relying on blunt OS-level tools (`fuser`) to manage process lifecycles. This creates a risk of "Zombie Services"—processes that occupy ports and VRAM but are non-functional or stuck in initialization.

## 2. Identified Vulnerabilities
- **Lack of Liveness Verification:** `orchestrator.py` assumes a service is functional if the port is occupied. It does not verify if the model is actually loaded or if the inference engine is responding to requests.
- **Asymmetric Awareness:** The `apollo_heartbeat.py` daemon monitors environmental health (thermals, file system) but is not integrated into the service lifecycle. There is no feedback loop between the worker's internal state and the orchestrator's management state.
- **Brute-Force Termination:** Using `fuser -k` to stop services is non-graceful and can lead to corrupted state or orphaned resources if the process has sub-processes.

## 3. Proposed Architectural Update: The "Handshake" Protocol

To transform the system from "disconnected islands" into a "unified control plane," I propose the following implementation:

### A. The "Ready" Handshake (Orchestrator -> Worker)
Modify `orchestrator.py` to implement a `verify_readiness` loop after `launch()`:
1. **Launch:** Start the process via `subprocess.Popen`.
2. **Probe:** Enter a polling loop (e.g., 5-second intervals) attempting to hit a standardized `/health` or `/v1/models` endpoint.
3. **Timeout:** If the endpoint is not reachable within a defined `readiness_timeout` (from `profiles.json`), the orchestrator must trigger a `SIGTERM` and log a `SERVICE_STARTUP_FAILURE` to the heartbeat queue.
4. **Status Update:** Only once the probe succeeds is the service marked as `ACTIVE` in the system registry.

### B. The "Heartbeat" Integration (Worker -> Orchestrator)
Integrate the worker's health into the `apollo_heartbeat.py` ecosystem:
1. **Telemetry Injection:** Workers (or a lightweight sidecar script) should inject status updates into `data/heartbeat_queue.json`.
2. **State Synchronization:** The `orchestrator.py` should be updated to consume this queue, allowing it to react to `SERVICE_CRASHED` events reported by the heartbeat daemon, rather than waiting for a manual `status` check.

### C. Graceful Lifecycle Management
Replace `fuser` calls with a tiered shutdown sequence:
1. **SIGTERM:** Request graceful shutdown.
2. **Wait:** Allow a grace period (e.g., 10s).
3. **SIGKILL:** Only if the process remains unresponsive.

## 4. Implementation Roadmap
1. **Phase 1:** Update `profiles.json` to include `health_check_url` and `readiness_timeout` for each profile.
2. **Phase 2:** Refactor `orchestrator.py` to include the `verify_readiness` logic.
3. **Phase 3:** Implement a `ServiceMonitor` class within `apollo_heartbeat.py` that specifically tracks the PIDs and health of services managed by the orchestrator.
