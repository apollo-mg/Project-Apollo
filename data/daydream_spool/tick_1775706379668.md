# Architectural Proposal: Cache-Aware MoE Routing (CAMR)

## 1. Executive Summary
The current routing architecture (Cascading Router) is purely semantic. It selects models based on task complexity but ignores the physical latency cost of weight retrieval. This leads to "VRAM Bubbles"—latency spikes when a selected model's weights are not resident in the high-speed cache (L3/VRAM). 

The proposed **Cache-Aware MoE Routing (CAMR)** protocol shifts the objective from "best model for task" to "best model for task *given current memory residency*," minimizing the 'Round-Trip' time of thought.

## 2. Problem Statement: The VRAM Bubble
Current routing logic:
`User Intent -> Semantic Classifier -> Model Selection -> Weight Fetch -> Inference`

If `Weight Fetch` hits the system bus (System RAM/Disk) instead of the L3 cache, the latency penalty is orders of magnitude higher than the semantic gain of a larger model.

## 3. Proposed Solution: Tiered MoE Loop
We will implement a three-tiered routing strategy that optimizes for the 96MB L3 cache boundary.

### Tiered Hierarchy
| Tier | Residency | Target Model Type | Latency Profile |
| :--- | :--- | :--- | :--- |
| **Tier 0 (L3-Fast)** | L3 Cache (<96MB) | Tiny MoE Experts / 0.5B Dense | < 1ms |
| **Tier 1 (VRAM-Warm)** | VRAM (GPU) | 8B-30B MoE Experts | 10-50ms |
| **Tier 2 (System-Cold)** | System RAM / Disk | Large Dense Models (70B+) | > 500ms |

## 4. Technical Implementation Plan

### Phase 1: Hardware Telemetry (The 'Pulse')
- Create `modules/cache_monitor.py` to interface with `system_monitor.py`.
- Track the "Warmth" of model weights. A weight is "Warm" if its memory address range is currently mapped to the L3 cache or high-speed VRAM.

### Phase 2: The CAMR Router Update
Modify `modules/router.py` to incorporate a `residency_weight`.

**New Routing Logic:**
```python
def calculate_routing_score(intent_affinity, cache_residency):
    # affinity: 0.0 to 1.0 (how well the model fits the task)
    # residency: 0.0 to 1.0 (how 'warm' the model is in L3/VRAM)
    alpha = 0.6  # Semantic weight
    beta = 0.4   # Latency weight
    return (alpha * intent_affinity) + (beta * cache_residency)
```

### Phase 3: Cache-Resident Expert Sharding
- Implement a mechanism to shard MoE experts such that the most frequently used "Logic Experts" (e.g., reasoning, syntax, basic math) are kept within the 96MB L3 boundary.
- The router will prioritize these "L3-Resident Experts" even if a slightly higher-affinity expert is "Cold."

## 5. Expected Impact
- **Latency Reduction:** Estimated 40-60% reduction in "Time-to-First-Token" (TTFT) for high-frequency reasoning loops.
- **Sovereignty:** Minimizes reliance on the system bus, turning the CPU/GPU cache into a physical manifestation of the agent's working memory.

## 6. Risk Assessment
- **Complexity:** Increased complexity in the routing decision loop.
- **Overhead:** The cost of monitoring cache residency must not exceed the latency savings.
- **Mitigation:** Use lightweight kernel-level telemetry (e.g., via `perf` or direct memory mapping) to keep monitoring overhead < 1%.
