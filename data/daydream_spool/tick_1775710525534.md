# Architectural Audit: Intelligence-as-Infrastructure Transition

## 1. Executive Summary
The current architecture of the Apollo system is fundamentally designed around the "Intelligence-as-a-Service" paradigm. It relies on high-level abstractions (`LLMAdapter`) that wrap remote API calls to Anthropic and OpenAI. While this provides ease of use, it creates a critical vulnerability: total dependency on centralized providers and the erosion of data sovereignty.

To align with the "Post-Bubble" reality, the architecture must pivot toward "Intelligence-as-Infrastructure," treating local model weights as a primary, sovereign resource rather than a fallback.

## 2. Current State Analysis
- **Provider Model:** Hardcoded to `anthropic` and `openai` in `src/llm/adapter.ts`.
- **Orchestration:** The `Orchestrator` manages agents that are essentially proxies for remote API requests.
- **Hardware Abstraction:** Non-existent. There is no logic to detect or utilize local compute (RDNA, CUDA, etc.) for inference.
- **Data Sovereignty:** Zero. Every reasoning step requires an outbound network request to a third-party provider.

## 3. Proposed Architectural Shift: "The Defensive Perimeter"

### Phase 1: Local Provider Integration
Introduce a `local` provider to the `SupportedProvider` type. This provider will not call an API but will interface with a local inference engine.

**Proposed Changes:**
- **`src/llm/adapter.ts`**: Update `SupportedProvider` to include `'local'`.
- **`src/llm/local.ts` (New)**: Implement a `LocalAdapter` that interfaces with a local inference server (e.g., Ollama, llama.cpp server, or a direct binding to a local MoE runner).
- **`src/llm/config.ts`**: Add configuration for `local_model_path` and `local_inference_endpoint`.

### Phase 2: Hardware-Aware Orchestration
The `Orchestrator` should be upgraded to prioritize local inference for sensitive tasks or when "Sovereignty Mode" is enabled.

**Proposed Changes:**
- **`src/orchestrator/orchestrator.ts`**: Implement a routing logic that selects the provider based on a `SovereigntyPolicy`.
  - *Policy A (Efficiency):* Use `openai`/`anthropic`.
  - *Policy B (Sovereignty):* Force `local` for all reasoning and tool-calling.

### Phase 3: The "Model Hoard" Integration
Transform the concept of a "model library" into an active component of the system.
- Implement a `WeightManager` module that handles the loading, unloading, and lifecycle of local weights (GGUF/Safetensors) to optimize consumer-grade VRAM usage.

## 4. Implementation Roadmap (Draft)

| Task | Description | Priority |
| :--- | :--- | :--- |
| **`LLMAdapter` Expansion** | Add `local` to `SupportedProvider` and create `LocalAdapter` interface. | Critical |
| **Ollama/Llama.cpp Bridge** | Implement the first concrete `LocalAdapter` using a local HTTP inference endpoint. | High |
| **Sovereignty Mode** | Add a global flag to the `Orchestrator` to bypass all remote providers. | High |
| **Hardware Detection** | Add utility to detect RDNA/NVIDIA/Apple Silicon to optimize local loading. | Medium |

## 5. Conclusion
The transition from "accessing models" to "orchestrating local weights" is not merely a feature update; it is a fundamental re-engineering of the system's trust model. By implementing these changes, Apollo moves from being a consumer of intelligence to a sovereign orchestrator of infrastructure.
