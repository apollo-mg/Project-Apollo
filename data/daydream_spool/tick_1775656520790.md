# Architectural Audit & Proposal: Sovereign Engine Hardware-Agnosticism

## 1. Executive Summary
The current Apollo architecture is heavily tethered to the AMD/HIP ecosystem, functioning as a "tenant" of existing hardware paradigms. To achieve true sovereignty, the architecture must transition to a "Hardware-Agnostic Orchestration" model. This audit confirms that the current `HardwareOrchestrator` is tightly coupled to HIP, preventing seamless migration to alternative architectures like Tenstorrent (RISC-V).

## 2. Findings
- **Current State:** `src/hardware/hardware_orchestrator.py` is hardcoded to use `HIPKernelSynchronizationBarrier` and `HIPKernelBarrierContext`.
- **Bottleneck:** The orchestration layer cannot currently dispatch compute tasks (like matmul) to non-HIP devices without significant refactoring.
- **Risk:** Continued development on the current path increases technical debt and reinforces dependency on the X86/CUDA/ROCm hegemony.

## 3. Proposed Architectural Pivot: The "Sovereign Backend" Pattern

### 3.1 Refactoring Strategy
We will move from a monolithic `HardwareOrchestrator` to a **Provider-Consumer Pattern**:

1.  **`BaseHardwareOrchestrator` (Interface):** An Abstract Base Class (ABC) defining the contract for all hardware operations (audio, camera, compute, synchronization).
2.  **`HardwareProvider` (Implementations):**
    - `HIPProvider`: Current logic, encapsulated.
    - `TTMetalProvider`: New target for Tenstorrent/RISC-V.
    - `CUDAProvider`: For NVIDIA compatibility.
3.  **`OrchestratorFactory`:** A registry-based factory that instantiates the correct provider based on the `hardware_profile` in `foundry_configs`.

### 3.2 Pilot Implementation: TT-Metal Integration
To validate the "Sovereign Engine" abstraction, we will implement a pilot integration:

**Target Task:** Execute a basic Matrix Multiplication (MatMul) on Tenstorrent hardware via the `tt-metal` abstraction.

**Proposed Code Structure:**
```python
# src/hardware/backends/tt_metal_backend.py

class TTMetalProvider(BaseHardwareOrchestrator):
    def execute_compute_kernel(self, kernel_type: str, params: Dict):
        """
        Wraps TT-Metal kernel calls.
        Validates the 'Sovereign Engine' can orchestrate 
        compute without direct HIP/CUDA knowledge.
        """
        if kernel_type == "matmul":
            # Integration with tt-metal API
            return self._run_tt_matmul(params)
        ...
```

## 4. Action Plan
1.  **Phase 1 (Refactor):** Decouple `src/hardware/hardware_orchestrator.py` from HIP. Move HIP-specific logic into a `HIPProvider`.
2.  **Phase 2 (Abstraction):** Define the `BaseHardwareOrchestrator` interface in `src/hardware/base.py`.
3.  **Phase 3 (Pilot):** Implement `TTMetalProvider` and a test script to run a matmul on the Tenstorrent DevCloud.
4.  **Phase 4 (Validation):** Verify that the `Sovereign Engine` (Zoey/Sonic) can trigger compute tasks via the new abstraction layer.

## 5. Conclusion
The transition to Tenstorrent/RISC-V is not merely a hardware swap; it is a fundamental requirement for the sovereignty of the intelligence. By implementing this abstraction layer, we move from being a tenant of the current ecosystem to being the architect of the next.
