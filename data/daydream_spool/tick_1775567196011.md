# Architectural Audit: V-Cache Shield & CPU Topology Discovery

## Epiphany Analysis
The subconscious daemon has identified a critical structural flaw: the 'V-Cache Shield' is currently implemented as a reactive optimization rather than a proactive structural requirement. The current implementation of `hardware-aware` scheduling in `src/orchestrator/scheduler.ts` is a "simulated" layer that relies on task descriptions to infer hardware needs, rather than performing actual CPU topology discovery.

As noted in the epiphany, if the router (the scheduler) is not spatially aligned with the X3D CCD *before* the 35B MoE weights are loaded, the memory overhead of the Python-based orchestration layer will likely cause cache misses that negate the benefits of the hardware-level pinning.

## Current State Audit
- **File:** `src/orchestrator/scheduler.ts`
- **Implementation:** The `scheduleHardwareAware` method (lines 325-359) is currently a stub. It uses a simulated `hardware_info` object and attempts to infer hardware requirements from task descriptions (e.g., checking for "vram" or "memory" in the description).
- **Critical Flaw:** There is no mechanism for **CPU Topology Discovery** during the initialization phase. The scheduler assumes `AgentConfig` might contain `hardware_info`, but this information is not being sourced from the actual system topology (e.g., L3 cache boundaries, CCD layout).

## Proposed Architectural Update

### 1. Prerequisite: Topology Discovery Service
Implement a new `TopologyDiscovery` module that runs *before* the orchestrator or model initialization. This module must:
- Query the system (via `/proc/cpuinfo` or specialized syscalls) to identify CCD/CCX boundaries.
- Specifically detect X3D (3D V-Cache) availability and map logical cores to physical cache domains.
- Export a `TopologyMap` that defines the spatial relationship between cores and L3 cache segments.

### 2. Update `AgentConfig` and `Scheduler`
- **Type Update:** Modify `AgentConfig` in `src/types.ts` to include a mandatory `topology_affinity` field.
- **Scheduler Refactor:** Replace the simulated `scheduleHardwareAware` logic in `src/orchestrator/scheduler.ts` with a real affinity-based scoring algorithm:
  ```typescript
  // Proposed logic for scheduleHardwareAware
  const score = (available_vram / required_vram) * topology_affinity;
  ```
- **Alignment:** The `topology_affinity` should be a coefficient representing the proximity of the assigned agent's execution thread to the specific CCD/L3 cache segment where the model weights are pinned.

### 3. Implementation Roadmap
1. **Phase 1 (Discovery):** Create `src/system/topology.ts` to handle hardware scanning.
2. **Phase 2 (Integration):** Update `AgentConfig` to accept topology metadata.
3. **Phase 3 (Scheduling):** Implement the `topology_affinity` calculation in `Scheduler.scheduleHardwareAware`.

## Conclusion
The 'V-Cache Shield' must transition from a "simulated intent" model to a "topology-locked" model. Failure to do so will result in the "physical cage" (pinning) being built around a process that has already wandered into the wrong cache domain.
