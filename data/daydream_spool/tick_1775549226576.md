# Architectural Audit: Cognitive Noise Decoupling

## Epiphany Analysis
The subconscious has identified a critical cognitive bottleneck: **Environmental Noise (Systemic Telemetry) vs. Functional Signal (API/Logic Failures).** 

In the current architecture, specifically within the `bash` tool execution, `stderr` is treated as a monolithic stream. When hardware-level initializations (like ALSA or driver warnings) emit to `stderr`, they are interleaved with actual functional errors. This creates "cognitive tax," where the agent must parse through environmental noise to find the structural fracture (the actual error).

## Audit Findings
- **Current State:** The `bashTool` in `src/tool/built-in/bash.ts` captures `stdout` and `stderr` via `spawn`. It then uses `buildOutput` to concatenate them.
- **The Problem:** There is no distinction between "Environmental/Systemic Noise" (e.g., `ALSA lib ...: warning: ...`) and "Functional/Logic Errors" (e.g., `command not found` or `permission denied`).
- **Impact:** High-level reasoning models (Architects) are forced to process raw `stderr` strings, increasing token usage and the probability of misinterpreting a system warning as a logic failure, or vice versa.

## Proposed Architectural Update: The "Signal-to-Noise" Interceptor

I propose implementing a two-tier error reporting mechanism within the `bash` tool.

### 1. Implementation Strategy: `stderr` Categorization
Instead of a simple string concatenation, the `bash` tool should implement a regex-based or heuristic-based interceptor that classifies `stderr` into:
- **`SYSTEM_TELEMETRY`**: Known patterns of hardware/OS noise (ALSA, driver warnings, kernel logs).
- **`FUNCTIONAL_ERROR`**: Actual execution failures (exit codes > 0, command errors).

### 2. Draft Code Changes (Conceptual)

**File:** `src/tool/built-in/bash.ts`

**Proposed Modification to `runCommand` / `buildOutput`:**

```typescript
// New classification constants
const NOISE_PATTERNS = [
  /ALSA lib/,
  /driver warning/,
  /kernel:.*:/,
  /hardware error/i, // Note: This might be ambiguous, requires careful tuning
];

function classifyStderr(stderr: string): 'SIGNAL' | 'NOISE' {
  for (const pattern of NOISE_PATTERNS) {
    if (pattern.test(stderr)) return 'NOISE';
  }
  return 'SIGNAL';
}

// Updated buildOutput to support structured reporting
function buildOutput(stdout: string, stderr: string, exitCode: number): string {
  const classification = classifyStderr(stderr);
  
  let output = stdout;
  
  if (stderr.length > 0) {
    const header = classification === 'NOISE' ? '--- environmental noise ---' : '--- functional error ---';
    output += `\n${header}\n${stderr}`;
  }
  
  // ... rest of logic
}
```

### 3. Integration with Cognitive Escalation
This decoupling allows the `CognitiveEscalation` module (as identified in `coordinator_test.log`) to:
1. **Ignore `NOISE`** during standard worker-tier execution.
2. **Trigger Deep Reasoning** only when a `SIGNAL` (Functional Error) is detected, or when a specific threshold of `NOISE` suggests hardware instability.

## Conclusion
The epiphany is valid. The current "flat" error reporting is a source of entropy. By implementing a telemetry-aware interceptor, we reduce the cognitive load on the agent and increase the precision of the error-to-model feedback loop.
