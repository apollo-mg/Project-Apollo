# Epiphany Audit: Cloud-Dependency Leaks vs. Bare-Metal Sovereignty

## Initial Assessment
The epiphany identifies a critical architectural tension: the transition from "rented" cloud intelligence to "owned" bare-metal sovereignty. 
The goal is to identify "cloud-dependency leaks"—instances where the lab's core intelligence (specifically MoE pipelines) relies on external APIs or cloud-based abstractions rather than the local AMD/Local RAG stack.

## Investigation Strategy
1. **Scan for Cloud API usage:** Search for common cloud provider SDKs (boto3, azure-storage, google-cloud, openai, anthropic) within the codebase.
2. **Identify MoE/Pipeline modules:** Locate the core intelligence logic to see if it is decoupled from external APIs.
3. **Check Hardware Abstraction:** Verify if the current pipelines are optimized for local AMD hardware or if they are generic/cloud-centric.
4. **Audit Configuration:** Look for environment variables or config files that point to external endpoints.

## Current Status
- Initial directory scan complete.
- Starting deep search for cloud-related dependencies.
## Findings
- **Cloud-Dependency Leaks:** The search for direct SDK imports (openai, boto3, etc.) returned no results in the core Python files, which is a positive indicator of sovereignty.
- **Local Abstraction:** `GLASS_COCKPIT.md` reveals that the system is already using a local OpenAI-compatible endpoint (`http://localhost:8085/v1`). This suggests that the "abstraction" layer is already being redirected to a local service (likely a local LLM runner like Ollama or vLLM).
- **Hardware Context:** The presence of `nct6687d` (a kernel module for hardware monitoring) and `amdgpu-install` indicates that the lab is actively managing the physical layer and hardware monitoring.
- **Potential Risk:** While the code doesn't show direct cloud imports, the reliance on `http` requests (even to localhost) means the architecture is built around an API-driven model. The "leak" isn't necessarily a cloud leak, but a potential "abstraction leak" where the system might still be designed to expect an API-based response, which could be a bottleneck if the local MoE pipelines are not properly integrated into the local service layer.

## Hypothesis
The "cloud-dependency leak" is not a direct API call to AWS/Azure, but rather a structural reliance on the *pattern* of API-based intelligence. To achieve true sovereignty, we must ensure that the local MoE pipelines are not just "wrapped in an API" but are natively integrated into the hardware-aware execution loop.
