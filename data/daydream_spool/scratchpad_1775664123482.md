
# Epiphany Investigation: VRAM Orchestration Protocol
## Timestamp: 2024-05-22 (Simulated)
## Objective: Audit current model deployment logic to ensure VRAM headroom for 'Heretic' models (Q6_K) vs 'Gatekeeper' models.

### Initial Hypothesis
The current system likely lacks a pre-deployment check that calculates the cumulative VRAM footprint of the 'Resident Gatekeeper' (the primary agent/orchestrator) and the 'High-IQ Heretic' (the specialized reasoning model). If the Gatekeeper consumes too much VRAM, the Heretic is forced into lower quantization (Q4/Q5) or, worse, triggers disk swap, destroying real-time performance.

### Investigation Plan
1.  **Identify Model Management Logic:** Locate where models are loaded, quantized, or selected.
2.  **Identify 'Gatekeeper' and 'Heretic' Definitions:** Find where these roles are defined in the codebase.
3.  **Audit VRAM Calculation:** Check if there is any existing logic for calculating VRAM usage or if it's currently "blind" deployment.
4.  **Propose Orchestration Protocol:** Design a logic gate that checks `Available_VRAM - Gatekeeper_VRAM >= Heretic_Q6_Requirement`.
### Audit Findings: VRAM Orchestration
- **Current State:** The `AgentPool` manages concurrency via a `Semaphore`, but this is purely a *logical* concurrency limit (number of concurrent async tasks). It has no awareness of the *physical* resource requirements (VRAM) of the models being loaded.
- **The Problem:** When `AgentPool.runParallel` is called, multiple agents can be active simultaneously. If these agents are using large models (e.g., 30B+ parameters), the cumulative VRAM usage can easily exceed the 16GB limit, causing the OS to swap to disk or the process to crash.
- **Missing Link:** There is no mechanism to:
    1.  Query the VRAM requirement of a model/quantization (e.g., Q6_K vs Q5_K_M).
    2.  Calculate the "Resident Gatekeeper" (orchestrator) VRAM footprint.
    3.  Dynamically adjust the `maxConcurrency` or the quantization level of the "Heretic" (worker) models based on available VRAM.

### Proposed Architectural Update: `VRAMOrchestrator`
1.  **New Module:** `src/orchestrator/vram_orchestrator.ts`.
2.  **Logic:**
    - Define a `ModelProfile` interface: `{ model_id: string, quantization: string, estimated_vram_gb: number }`.
    - Implement a `VRAMManager` that tracks `current_vram_usage`.
    - Update `AgentPool` to consult `VRAMManager` before executing a run.
    - If `current_vram_usage + next_agent_vram > total_vram_limit`, the pool must either:
        - **A:** Wait for a semaphore (current behavior, but doesn't solve the VRAM issue if the *active* agents already exceed the limit).
        - **B:** Force a lower quantization for the next agent (e.g., downgrade from Q6_K to Q4_K).
        - **C:** Reject the task with a `ResourceExhaustionError`.

### Implementation Plan (Draft)
- **Step 1:** Add `vram_requirement` to `AgentConfig` in `src/types.ts`.
- **Step 2:** Create `VRAMManager` to track usage.
- **Step 3:** Modify `AgentPool.run` to check `VRAMManager`.
- **Step 4:** (Advanced) Implement a "Quantization Downgrade" logic in the `LLMAdapter` factory.
