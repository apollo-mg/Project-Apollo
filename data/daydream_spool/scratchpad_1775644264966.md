# Epiphany Investigation: Mathematical Scale vs. Physical Constraint
## Timestamp: 2025-05-22 (Simulated)
## Status: Investigating

### Hypothesis
The "Epiphany" suggests that model deployment failures are occurring because the infrastructure (disk/VRAM) is not being pre-validated against the model's weight requirements. I need to find where models are provisioned or started and check if there is any logic that calculates required space vs. available space.

### Target Files for Investigation
1. `model_provisioner.sh` - Likely handles downloading/preparing models.
2. `model_manifest.json` - Might contain model size metadata.
3. `start_*.sh` scripts - To see how models are launched.
4. `vram_management.py` - To see if VRAM is being checked.
5. `foundry_configs` - To see if there are default infrastructure settings.
6. `scripts/` - General scripts for deployment.
7. `src/` - Core logic.

### Initial Search Strategy
- Search for "VRAM", "disk", "size", "GB", "MB", "capacity", "requirement" in the codebase.
- Look for `model_provisioner.sh` content.
- Look for `model_manifest.json` content.
### Findings: `model_provisioner.sh` and `model_manifest.json`
- `model_provisioner.sh` is a simple downloader. It iterates through `model_manifest.json` and uses `curl` to download files.
- **Critical Flaw:** There is **zero** validation of disk space or VRAM before downloading. It blindly attempts to download whatever is in the manifest.
- `model_manifest.json` currently only contains small files (Kokoro ONNX/Voices), but the architecture is designed to scale. If a large LLM (e.g., 70B parameter model) were added to this manifest, the script would attempt to download it without checking if `/mnt/TG_2TB/Projects/Apollo/models` has sufficient capacity.
- The "Epiphany" is highly relevant here. The current provisioning logic is "optimistic" rather than "pre-flighted".

### Next Steps
1. Check `vram_management.py` to see if VRAM is checked during *runtime* (which is too late, as the epiphany suggests).
2. Search for other deployment scripts (e.g., `start_*.sh`) to see if they assume the model is already present and valid.
3. Investigate if there are any "default" infrastructure configurations in `foundry_configs` or `defaults` that might be causing the "collision" mentioned in the epiphany.
