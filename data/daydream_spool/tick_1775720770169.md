# Architectural Audit: Transition to Silicon-Centric Optimization (GFX1201/RDNA 4)

## 1. Executive Summary
The current orchestration layer implements a "Hardware-Aware" scheduling strategy that is fundamentally limited to resource allocation (VRAM/Memory availability). This audit confirms that the "Epiphany" regarding the GFX1201/RDNA 4 bottleneck is valid: the system lacks a "translation layer" that maps model mathematical requirements (GEMM shapes) to hardware-native optimal configurations.

## 2. Current State Analysis
- **Location of Logic:** `src/orchestrator/scheduler.ts` (Lines 325-359).
- **Current Heuristic:** `scheduleHardwareAware` uses a simple VRAM-based score: `score = needsHighVram ? availableVram : 1`.
- **Identified Gap:** There is no mechanism to align the model's computational "dialect" (GEMM shapes, FP8 precision patterns) with the specific architectural strengths of the RDNA 4 (GFX1201) silicon. The scheduler is currently "Hardware-Aware" in terms of *capacity*, but "Hardware-Agnostic" in terms of *computation*.

## 3. Proposed Architectural Evolution: The 'Tuning Map' Pipeline

To transition from 'Model-Centric' to 'Silicon-Centric', I propose the implementation of a closed-loop optimization pipeline.

### Phase A: The Tuning Map Library (Foundational Layer)
We will introduce a new module, `src/modules/tuning_map.ts`, to act as the central repository for hardware-optimized shapes.

**Proposed Data Structure:**
```typescript
/**
 * Maps hardware-specific identifiers to optimal kernel configurations
 * based on GEMM shapes and precision.
 */
export interface TuningMap {
  [chipId: string]: {
    [precision: string]: {
      [shapeKey: string]: {
        optimal_block_size: number;
        preferred_tiling: string;
        kernel_variant: string;
      };
    };
  };
}
```

### Phase B: Refactoring the Scheduler
The `scheduleHardwareAware` method in `src/orchestrator/scheduler.ts` will be refactored to use **Shape-Affinity Scoring**.

**New Logic Flow:**
1. **Identify Task Intent:** Extract expected model precision (e.g., `FP8`) and approximate tensor shapes from the task/agent metadata.
2. **Query Tuning Map:** Retrieve the optimal `KernelConfig` for the agent's `chip_id` and the task's required precision.
3. **Calculate Affinity Score:** 
   $$\text{Score} = \text{TopologyAffinity} \times \text{ShapeMatchPercentage}$$
4. **Assign Agent:** Prioritize agents whose hardware-native "dialect" matches the task's mathematical requirements.

### Phase C: The Closed-Loop Pipeline
1. **Sweep:** A new utility `src/modules/sweeper.ts` will execute automated kernel benchmarks on GFX1201 hardware.
2. **Map:** Results are serialized into the `TuningMap`.
3. **Quantize/Fine-Tune:** Model weights are quantized specifically to align with the optimal shapes discovered in the sweep, ensuring the "translation layer" is seamless.

## 4. Implementation Roadmap
1. **[Immediate]** Update `src/types.ts` to include `chip_id` and `hardware_capabilities` in `AgentConfig`.
2. **[Short-term]** Implement `src/modules/tuning_map.ts` with a basic JSON-based provider.
3. **[Mid-term]** Refactor `src/orchestrator/scheduler.ts` to integrate the `TuningMap` lookup.
4. **[Long-term]** Develop the `sweeper` module to automate the generation of the `TuningMap`.

## 5. Conclusion
By implementing this transition, we move from merely *running* models on hardware to *remastering* them for the silicon. This turns the GFX1201 from a generic target into a bespoke, high-performance intelligence engine.
