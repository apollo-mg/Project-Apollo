# Investigation Log: Drive Name Drift & Ontological Dissonance
## Initial State
- `/etc/fstab` currently uses UUIDs for the root filesystem (Btrfs) and the `/mnt/TG_2TB` drive (ext4).
- The `/boot` partition also uses a UUID.
- The system seems to already be following the "Actionable Insight" for the primary system drives.

## Hypothesis
The "drift" mentioned in the Epiphany might refer to:
1. External drives or secondary partitions not listed in `/etc/fstab` that are being mounted via udev rules or manual scripts using `/dev/sdX` names.
2. A mismatch between what the user *expects* to be at a certain mount point and what is actually there due to Windows Fast Startup/Hibernation causing the kernel to reorder device enumeration.
3. The presence of other drives (like the 2TB drive mentioned in the paths) that might be subject to this issue if they are not correctly anchored.

## Next Steps
1. List all block devices and their UUIDs to compare against `/etc/fstab`.
2. Search the codebase for any hardcoded `/dev/sd` paths.
3. Check for udev rules that might be causing naming issues.
## Findings: Block Device Audit
- `/etc/fstab` is correctly using UUIDs for the primary system drives (`nvme0n1` and `nvme1n1`).
- **Critical Observation:** The NTFS drives (`sda2` and `sdb2`) are currently mounted under `/run/media/mark/`. This indicates they are being handled by a desktop environment's automounter (likely udisks2/gvfs) rather than a static system configuration.
- **The "Drift" Source:** Because these NTFS drives are mounted via automounting, they are assigned mount points based on their **LABEL** (`Games 2TB`, `Backup 3TB`). If the label changes or if the kernel reorders the device names (e.g., `sda` becomes `sdb`), the automounter might struggle or the user might find their files in unexpected locations if they rely on these paths in scripts.
- **Windows Interaction:** The NTFS partitions are the ones most susceptible to the "ghost" state (Fast Startup/Hibernation). If Windows is not fully shut down, the NTFS filesystem is marked "dirty" or "in use," which can cause Linux to mount them as read-only or fail to mount them entirely, further complicating the "identity" of the drive.

## Identified Risks
1. **Script Fragility:** Any scripts or applications relying on `/run/media/mark/Games 2TB` or `/run/media/mark/Backup 3TB` will break if the label is changed or if the automounter behaves differently.
2. **Mount Point Instability:** The current mount points are transient.

## Proposed Architectural Update
1. **Transition to Static Mounts:** Move the NTFS drives from transient `/run/media/` mounts to permanent `/mnt/` mounts.
2. **UUID Anchoring:** Update `/etc/fstab` to use the UUIDs identified in `lsblk`:
   - `4C5EE1925EE1755C` for `Games 2TB`
   - `F4D477FDD477C102` for `Backup 3TB`
3. **Mitigation of Windows "Ghost" State:** Recommend disabling "Fast Startup" in Windows to ensure the NTFS filesystem is cleanly unmounted.
