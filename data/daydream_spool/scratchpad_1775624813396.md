### The "Spatial Conflict" Hypothesis
The epiphany suggests that the 500 error is a "spatial conflict where the vision tokens are attempting to exist in a memory geometry too small to hold them". 

In the context of this codebase:
1. The `AgentRunner` is initialized with a static `maxTokens`.
2. When a vision-capable model (like Claude 3.5 Sonnet or Opus) is used, the number of tokens generated by the vision adapter (the "vision tokens") can be significantly higher than a standard text-only turn.
3. If the `AgentRunner` or the underlying `LLMAdapter` has a fixed-size buffer or a pre-allocated memory structure for the response/stream, a high-density vision turn could overflow this buffer, leading to a 500 error (likely at the adapter or server level).

### Proposed Solution: Modality-Aware Resource Allocation
Instead of a static `maxTokens` in `RunnerOptions`, we need a way to:
1. Detect if the input/task involves vision (modality detection).
2. Calculate the *theoretical maximum* token output for that specific modality.
3. Dynamically adjust the buffer/resource allocation (or at least the `maxTokens` parameter) before the `AgentRunner` starts its loop.

### Technical Analysis of the 500 Error
The `AnthropicAdapter.chat` and `AnthropicAdapter.stream` methods both use a default `max_tokens` of `4096` if not provided:
```typescript
max_tokens: options.maxTokens ?? 4096,
```
In a vision-heavy context, the "spatial conflict" described in the epiphany likely refers to the fact that while `max_tokens` controls the *output* limit, the *input* (which includes vision tokens) can be massive. 

However, the epiphany specifically mentions: "the vision tokens are attempting to exist in a memory geometry too small to hold them". This implies the issue is with the *output* buffer or the *allocation* for the response, which is being overwhelmed by the sheer volume of tokens generated by the vision adapter's interpretation.

If the `maxTokens` is set too low for a complex vision task, the model might attempt to output more than the buffer allows, or the server might fail when trying to process a response that exceeds the expected "geometry".

### Proposed Architectural Change: Modality-Aware Resource Allocation
Instead of relying on a static `maxTokens` in `RunnerOptions`, we should implement a protocol that:
1. **Inspects the input messages** for `ImageBlock` content.
2. **Calculates a "Vision Multiplier"** or a theoretical maximum token requirement based on the number and resolution of images.
3. **Dynamically overrides `maxTokens`** in the `LLMChatOptions` before the adapter call is made.

### Implementation Strategy
1. **Modify `AgentRunner.stream` (or a new helper):**
   - Add a method `calculateRequiredTokens(messages: LLMMessage[])`.
   - This method will scan `messages` for `ImageBlock` types.
   - It will return a suggested `maxTokens` value (e.g., `base_max_tokens * (1 + num_images * vision_factor)`).
2. **Update `AgentRunner` logic:**
   - Use this calculated value to populate `baseChatOptions.maxTokens`.
3. **Update `RunnerOptions`:**
   - Add a `visionTokenFactor` to allow tuning the multiplier.

// New helper in AgentRunner
private calculateDynamicMaxTokens(messages: LLMMessage[], baseMaxTokens: number): number {
  let imageCount = 0;
  for (const msg of messages) {
    for (const block of msg.content) {
      if (block.type === 'image') {
        imageCount++;
      }
    }
  }
  // Heuristic: Each image adds a potential for higher token density/output
  // This is a placeholder for a more robust calculation.
  const visionFactor = 1.5; 
  return Math.ceil(baseMaxTokens * (1 + imageCount * (visionFactor - 1)));
}
