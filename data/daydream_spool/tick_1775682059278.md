# Epiphany Audit: Friction Ingestion Protocol

## Summary
The subconscious epiphany identifies a critical architectural gap: the system currently treats operational failures (typos, missing binaries, failed imports) as noise to be suppressed or returned to the LLM (the "Filter" posture). The proposed shift is to treat these failures as primary signals for mapping the system's actual boundaries (the "Knowledge Curator" posture).

## Audit Findings
1.  **Current Error Handling:** The `ToolExecutor` (`src/tool/executor.ts`) already implements a robust error-isolation pattern. It catches execution exceptions and Zod validation failures, converting them into `ToolResult` objects with `isError: true`.
2.  **The "Filter" Posture:** Currently, these errors are passed back to the LLM as tool outputs. While this allows the LLM to attempt self-correction, the system itself gains no structural knowledge from the failure.
3.  **Architectural Readiness:** The `ToolExecutor` is the ideal interception point for a "Friction Ingestion" protocol. The existing `ToolUseContext` and `ToolResult` structures provide sufficient metadata to facilitate this.

## Proposed Architectural Update: Friction Ingestion Protocol

### 1. Core Concept
Transform the error-handling flow from a single path (`Error -> LLM`) to a dual path (`Error -> LLM` AND `Error -> Curator`).

### 2. Implementation Strategy

#### A. Define the Curator Interface
Introduce a new module `src/modules/curator.ts` to define the contract for friction ingestion.
```typescript
export interface FrictionEvent {
  toolName: string;
  error: string;
  context: Record<string, unknown>;
  timestamp: number;
}

export interface FrictionCurator {
  ingest(event: FrictionEvent): Promise<void>;
}
```

#### B. Enhance `ToolExecutor`
Modify `src/tool/executor.ts` to support an optional `FrictionCurator`.
- **Injection:** Add `curator?: FrictionCurator` to `ToolExecutorOptions`.
- **Interception:** In the `runTool` method's `catch` block, if `this.curator` is present, trigger `this.curator.ingest(...)` before returning the `errorResult`.

#### C. Implement `GroundTruthCurator`
Create a concrete implementation `src/modules/ground_truth_curator.ts`.
- **Pattern Matching:** Use regex to parse error messages for environmental signals (e.g., `command not found: <cmd>`, `No such file or directory: <path>`, `EACCES`).
- **Metadata Extraction:** Extract the "missing" entity (binary name, file path, or permission type).
- **Memory Integration:** Write these findings to a specialized `ground_truth` key in the `MemoryStore`. This creates a persistent, queryable map of the environment's actual state.

#### D. Orchestrator Integration
Update `src/orchestrator/orchestrator.ts` to:
1. Instantiate the `GroundTruthCurator`.
2. Pass it to the `ToolExecutor` during the `Agent` construction process.

### 3. Expected Outcome
- **Systemic Learning:** The system will build an internal model of its environment (e.g., "The `jq` binary is missing", "The `/tmp/data` directory is read-only") without requiring explicit user input.
- **Reduced Friction:** Future agents can query the `ground_truth` memory to avoid attempting known-failing operations, moving from reactive error handling to proactive environmental awareness.
- **Ontological Shift:** The system evolves from a "brain that executes" to a "brain that understands its own existence within a specific environment."

## Conclusion
The transition is highly feasible and requires minimal changes to the core execution logic while providing a massive leap in architectural intelligence. The `ToolExecutor` is the perfect "sensor" for this new investigative ontology.
