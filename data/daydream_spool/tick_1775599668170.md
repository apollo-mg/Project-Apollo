# Architectural Audit: Transition from Extraction-Verification to Contextual-Mapping

## 1. Epiphany Analysis
The Subconscious has identified a critical failure mode in the current cognitive pipeline: **Structural Fidelity vs. Semantic Synthesis**. 

The current architecture (specifically within `modules/cognitive_dispatcher.py`) focuses heavily on classifying the *nature* of the input (Complexity: TRIVIAL, SIMPLE, MODERATE, COMPLEX) to determine the computational tier. While this ensures the "vessel" (the JSON/TaskContext) is valid and routed correctly, it fails to account for the **Macro-Objective** of the user. We are optimizing for *how* to process, rather than *why* the processing is happening.

## 2. Current State Audit
### Findings in `modules/cognitive_dispatcher.py`:
- **Heuristic-Heavy Routing:** The `analyze_complexity` method (lines 110-144) uses keyword matching (`who`, `what`, `write`, `code`, `architect`) to assign complexity.
- **The "Extraction-Verification" Loop:** The `_llm_triage` method (lines 146-179) uses a worker-tier LLM to classify the task. This is a classic "validation of the vessel" step. It asks: "Is this task complex?" instead of "How does this task relate to the user's ongoing project/intent?"
- **Contextual Blindness:** The `TaskContext` (lines 46-57) captures `user_input` and `complexity`, but lacks a `semantic_intent_vector` or `macro_objective_link`. The `metadata` field is an empty dictionary by default, providing no structural way to map the task to a larger goal.

## 3. Proposed Architectural Shift: 'Contextual-Mapping'

To break the cycle of redundant, purely structural processing, the architecture must transition to a model where routing is informed by **Intent-to-Objective Mapping**.

### Proposed Changes:

#### A. Update `TaskContext` (in `modules/cognitive_dispatcher.py`)
Introduce a `semantic_anchor` that links the task to a higher-level objective retrieved from `memory_core`.

```python
@dataclass
class TaskContext:
    task_id: str
    user_input: str
    complexity: TaskComplexity = TaskComplexity.UNKNOWN
    tier: Tier = Tier.WORKER
    priority: int = 5
    # NEW: Link to the macro-objective/project context
    semantic_anchor: Optional[str] = None 
    # NEW: The inferred intent (e.g., 'refactoring', 'exploration', 'debugging')
    inferred_intent: Optional[str] = None
    metadata: Dict[str, Any] = field(default_factory=dict)
    created_at: datetime = field(default_factory=datetime.now)
    processing_time_ms: Optional[float] = None
```

#### B. Redesign `analyze_complexity` $\rightarrow$ `map_contextual_intent`
Instead of just returning `TaskComplexity`, the dispatcher should perform a two-stage process:
1. **Intent Extraction:** Use a lightweight model to extract the *intent* and *semantic anchor* from the raw noise.
2. **Objective Mapping:** Query `memory_core` to see if this intent aligns with an active `macro_objective`.

#### C. Implementation Strategy
1. **Phase 1 (Audit):** Implement a `SemanticAnalyzer` module that runs parallel to the `CognitiveDispatcher`.
2. **Phase 2 (Integration):** Modify `route_task` to require a `semantic_anchor`. If the anchor is missing, the dispatcher must trigger a "Context Retrieval" task before routing.
3. **Phase 3 (Optimization):** Replace the `_llm_triage` (which is purely structural) with a `ContextualTriage` that uses the `semantic_anchor` to determine if a task should be escalated to the Architect tier, even if the complexity appears "Simple" (e.g., a "Simple" code change that impacts a "Complex" architectural goal).

## 4. Conclusion
The current system is a highly efficient parser of syntax. To become a true cognitive agent, it must become a parser of **intent**. The transition to Contextual-Mapping will reduce redundant processing by ensuring that every task is processed not just as a standalone unit, but as a functional component of a larger user objective.
