# Architectural Audit: Ingestion Layer Fragmentation

## 1. Executive Summary
The current ingestion architecture is fragmented into specialized, standalone scripts (`librarian_ingest.py` and `ingest_chats.py`). This "one script per format" approach creates technical debt, inconsistent metadata schemas, and high maintenance overhead. To support the `daydream.py` synthesis engine, the ingestion layer must transition to a polymorphic, strategy-based architecture.

## 2. Current State Analysis
### 2.1 Identified Fragmentation
- **`librarian_ingest.py`**: Focuses on static documents (PDFs) and web content (URLs). Uses `file_hash` and `url_id` for deduplication.
- **`ingest_chats.py`**: Focuses on conversational history (JSON). Uses `timestamp` and `filename` for context.
- **Inconsistency**: There is no unified metadata schema. `daydream.py` relies on retrieving memories, but the lack of a standardized schema makes cross-format reasoning (e.g., "How does this PDF relate to this chat?") more difficult for the LLM.

### 2.2 Technical Debt
- **Code Duplication**: Both scripts implement their own loops, error handling, and vector store interaction logic.
- **Scalability Bottleneck**: Adding a new data source (e.g., Obsidian notes, email logs) requires a full script implementation rather than a simple parser module.

## 3. Proposed Architectural Refactor: `UnifiedIngestionEngine`

### 3.1 Design Pattern: Strategy Pattern
Implement a central `IngestionEngine` that delegates parsing logic to specialized `Parser` modules.

**Proposed Directory Structure:**
```text
modules/
└── ingestion/
    ├── __init__.py
    ├── engine.py          # The central controller
    ├── base.py            # Abstract Base Class (ABC) for Parsers
    ├── registry.py        # Maps file extensions/types to Parsers
    └── parsers/           # Concrete implementations
        ├── pdf_parser.py
        ├── url_parser.py
        ├── chat_parser.py
        └── markdown_parser.py
```

### 3.2 Unified Metadata Schema
All ingested documents must be normalized to a standard schema before being committed to ChromaDB:
- `source`: (string) Original file path or URL.
- `content_type`: (string) `document`, `chat`, `web`, or `code`.
- `ingested_at`: (float) Unix timestamp of ingestion.
- `fingerprint`: (string) SHA-256 hash of the content/source for deduplication.
- `metadata`: (dict) Format-specific key-value pairs (e.g., `author`, `role`, `url_id`).

### 3.3 Implementation Workflow
1. **Detection**: `Engine` receives a path/URL and queries `ParserRegistry` to find the appropriate parser.
2. **Parsing**: The `Parser` extracts text and generates the `UnifiedDocument` object.
3. **Normalization**: The `Engine` applies the standard metadata schema and calculates the `fingerprint`.
4. **Commitment**: The `Engine` performs a single, unified batch write to the Vector Store.

## 4. Action Plan
1. **Phase 1**: Create `modules/ingestion/base.py` defining the `BaseParser` interface.
2. **Phase 2**: Implement `ChatParser` and `DocumentParser` (covering PDF/URL) as the first set of strategies.
3. **Phase 3**: Develop `engine.py` to orchestrate the process.
4. **Phase 4**: Deprecate existing scripts and migrate existing ingestion logic into the new engine.
