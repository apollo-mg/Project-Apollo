# Epiphany Investigation: Latency-Gated Routing
## Timestamp: 2025-05-22 (Simulated)
## Status: Initializing Audit

The epiphany suggests a shift from accuracy-centric routing to latency-centric routing. 
The goal is to treat the 3D V-Cache (reflexive layer) as an autonomic nervous system.
The primary metric: 'sub-microsecond' execution profile to avoid PCIe/RAM penalties.

### Hypothesis
The current routing logic likely resides in `orchestrator.py`, `task_manager.py`, or a specialized dispatcher in `src/`. 
I need to find where the decision to route a request to a specific model (GPU vs CPU/V-Cache) is made.

### Search Strategy
1. Search for "router", "dispatch", "route", or "decision" in `src/` and the root directory.
2. Look for logic that selects between different model tiers or hardware backends.
3. Check `test_cognitive_dispatcher.py` for clues on how dispatching is currently tested.
### Findings: Current Routing Architecture
The current `CognitiveDispatcher` (in `modules/cognitive_dispatcher.py`) uses a two-stage approach:
1. **Heuristic Analysis**: Fast, keyword-based checks (lines 121-141).
2. **LLM Triage**: If heuristics fail, it calls `_llm_triage` (lines 146-179), which uses `query_llm` with the `_worker_config`.

### Critical Flaw Identified
The `_llm_triage` method, while intended to be a "fast path," is a potential latency bottleneck. 
- It performs a full LLM inference call (`query_llm`) to classify complexity.
- Even with a small model (Worker Tier), this involves:
    - Network/IPC overhead.
    - Tokenization/De-tokenization.
    - Inference time.
- This violates the "sub-microsecond" requirement of the epiphany. The decision-making process itself is currently "deliberative" (using an LLM) rather than "reflexive" (using a sub-microsecond mechanism).

### Proposed Architectural Update: 'Latency-Gated' Routing
To align with the epiphany, we must move the triage from an LLM-based process to a "reflexive" process that avoids the PCIe/RAM penalty of a full model call where possible.

**Proposed Changes:**
1. **Reflexive Triage Layer**: Implement a lightweight, non-LLM-based "Reflexive Router" that uses:
    - High-speed regex/keyword matching (already partially implemented).
    - A tiny, local, C-based or highly optimized Python-based classifier (e.g., a small SVM or a simple decision tree) that runs in the same process space as the dispatcher, avoiding IPC/Network overhead.
2. **Latency-Gated Routing Logic**:
    - Introduce a `latency_budget_ms` threshold.
    - If the heuristic/reflexive layer cannot decide within `X` microseconds, it defaults to a "safe" tier (Worker) rather than waiting for a slow LLM triage.
3. **Hardware-Aware Routing**:
    - Ensure the `Worker Tier` is explicitly mapped to the 3D V-Cache/CPU-local memory space to minimize latency.
    - The `Architect Tier` remains the GPU-bound "prefrontal cortex".

### Implementation Plan (Draft)
- **Step 1**: Refactor `analyze_complexity` to include a `ReflexiveRouter` class.
- **Step 2**: Implement a `latency_gate` decorator or context manager to monitor and enforce the sub-microsecond profile.
- **Step 3**: Update `_llm_triage` to be a "last resort" only, triggered only when the reflexive layer reports high uncertainty AND the latency budget allows.
