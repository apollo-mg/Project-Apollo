# Epiphany Investigation: Dual-Core Orchestration Layer
## Timestamp: 2025-05-22 (Simulated)
## Status: Initializing Audit

### Hypothesis
The current system architecture likely suffers from VRAM contention because it attempts to run heavy multimodal models (DeepSeek V4) and stability-focused models (Ministral 3) without a dedicated orchestration layer to partition the RX 9070 XT's VRAM. 

### Investigation Plan
1. **Identify Model Management:** Locate where models are provisioned and loaded (e.g., `model_manifest.json`, `model_provisioner.sh`, `orchestrator.py`).
2. **Analyze VRAM Management:** Check `vram_management.py` and `system_monitor.py` to see how current VRAM usage is tracked and if there's any existing logic for partitioning.
3. **Examine Orchestration Logic:** Look at `orchestrator.py` and `fleet_orchestrator.py` to see if there is a mechanism to switch between or concurrently run models based on task type.
4. **Audit Configuration:** Check `lab.json` or `foundry_configs` for existing model deployment settings.
5. **Verify Hardware Constraints:** Check `system_monitor_v2.py` to understand the current telemetry regarding the RX 9070 XT.

### Findings: Current Orchestration State
- **Profiles Analysis:**
    - `architect`: Uses a 27B Qwen model (Q2_K) on port 8082.
    - `turbo`: Also uses port 8082 (Conflict detected in `profiles.json`!). It uses a Gemma 4 26B model.
    - `whisper`: Port 8080.
    - `bonsai`: Port 8083.
- **VRAM Contention Risk:** The `architect` and `turbo` profiles both target port 8082, which is a configuration error. More importantly, both are heavy models (26B-27B) that likely compete for the same VRAM space.
- **Missing Tiered Logic:** There is no profile for a "stable edge" model (like Ministral 3) or a "multimodal reasoning" model (DeepSeek V4) as suggested by the Epiphany. The current `orchestrator.py` is a simple process launcher and lacks the intelligence to partition VRAM or route tasks based on complexity.

### Proposed Architectural Shift: Dual-Core Orchestration
1. **New Profile Definitions:**
    - `reasoning_core`: DeepSeek V4-14B (High VRAM allocation, high context).
    - `stability_core`: Ministral 3 (Low VRAM allocation, low latency).
2. **VRAM Partitioning Strategy:**
    - Implement a `vram_management.py` update that calculates the available VRAM on the RX 9070 XT and assigns fixed `ngl` (number of layers to offload) or `cache_ram` limits to each profile to prevent OOM (Out of Memory) crashes.
3. **Orchestration Layer Upgrade:**
    - Modify `orchestrator.py` to include a `route_task` method. This method will act as a proxy/router that inspects incoming requests (or task metadata) and decides whether to hit the `reasoning_core` or the `stability_core`.

### Final Audit Summary: VRAM Contention & Orchestration
- **Current State:** The system uses a single-model deployment model via `orchestrator.py` and `profiles.json`. There is a critical configuration error where `architect` and `turbo` both claim port 8082.
- **VRAM Management:** `vram_management.py` provides telemetry via `rocm-smi` and a `smart_vram_guard` that interacts with ComfyUI. However, it is reactive (triggered by thresholds) rather than proactive (partitioning resources).
- **The Bottleneck:** The RX 9070 XT (16GB VRAM) is being over-leveraged by attempting to run large MoE models (26B-27B) without a tiered hierarchy. This leads to high latency and potential OOMs when ComfyUI/Vision tasks are active.

### Proposed Architectural Update: Dual-Core Orchestration Layer

#### 1. Update `profiles.json`
Introduce a tiered model hierarchy to replace the current monolithic/conflicting profiles.
- **`reasoning_core` (DeepSeek V4-14B):** High-capacity multimodal reasoning.
- **`stability_core` (Ministral 3):** Low-latency, high-frequency stability tasks.
- **`vision_core` (ComfyUI/Flux):** Reserved VRAM headroom.

#### 2. Enhance `orchestrator.py`
Transform the `ServiceOrchestrator` from a simple process launcher into a **Tiered Intelligence Router**.
- **Logic:** Implement a `route_request(task_type)` method.
- **Routing Rules:**
    - `task_type == 'reasoning' | 'multimodal'` $\rightarrow$ `reasoning_core`
    - `task_type == 'control' | 'stability' | 'chat'` $\rightarrow$ `stability_core`
- **VRAM Partitioning:** Use the `vram_management.py` logic to enforce `ngl` (number of layers) limits during the `launch` phase, ensuring `reasoning_core` and `stability_core` never collectively exceed the available headroom required for `vision_core`.

#### 3. Refine `vram_management.py`
- Implement **Proactive Partitioning**: Instead of just waiting for a threshold, the orchestrator should query `get_gpu_stats()` before launching a new profile to determine if the requested model's VRAM footprint will cause a collision.
