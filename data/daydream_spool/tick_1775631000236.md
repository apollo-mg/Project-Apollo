# Architectural Proposal: Action Tag Interpreter

## 1. Executive Summary
The current Sovereign Engine architecture relies on manual tool orchestration (e.g., `bash`, `file_edit`) to perform system-level tasks. This is error-prone and lacks semantic abstraction. We propose the implementation of **Action Tags**: a semantic layer that maps high-level LLM intents to predefined, safe, and optimized OS/hardware-level functions.

## 2. Problem Statement
- **High Cognitive Load:** The Foreman must manually construct complex `bash` commands for routine system tasks (e.g., restarting services, managing processes).
- **Safety Risk:** Manual `bash` execution is prone to syntax errors and unintended side effects.
- **Lack of Agency:** The system is currently a "passive observer" that uses tools to fix its environment, rather than an "active agent" that uses semantic commands to control its environment.

## 3. Proposed Solution: The Action Tag System

### 3.1 Semantic Schema (`action_tags.json`)
A centralized registry defining the available actions.
```json
{
  "tags": {
    "SERVICE_RESTART": {
      "description": "Restarts a specific system service.",
      "parameters": { "service_name": "string" },
      "handler": "exec_systemctl_restart"
    },
    "PROCESS_PAUSE": {
      "description": "Pauses a running process using SIGSTOP.",
      "parameters": { "pid": "number" },
      "handler": "exec_kill_stop"
    },
    "MEMORY_PURGE": {
      "description": "Clears system cache to free up VRAM/RAM.",
      "parameters": {},
      "handler": "exec_sys_cache_purge"
    }
  }
}
```

### 3.2 The Action Interpreter
A new component within the `ToolExecutor` (or a dedicated `ActionInterpreter` class) that:
1. **Detects:** Uses regex to identify `<tag:NAME(args)>` patterns in the LLM's output stream.
2. **Validates:** Checks the tag and arguments against the `action_tags.json` schema.
3. **Executes:** Maps the tag to a hardcoded, tested, and safe internal function (e.g., a Python method that wraps a specific `subprocess` call).

### 3.3 Integration Workflow
1. **Daydreamer/Foreman** generates a proposal: `[ACTION_TAG: SERVICE_RESTART(service_name="apollo_bridge")]`.
2. **Action Interpreter** intercepts the tag.
3. **Interpreter** executes the underlying system command safely.
4. **Result** is returned to the Agent as a `tool_result`.

## 4. Implementation Roadmap

### Phase 1: Schema & Registry (Immediate)
- Create `/mnt/TG_2TB/Projects/Apollo/src/action_tags.json`.
- Implement `ActionRegistry` class to load and validate tags.

### Phase 2: Interpreter Core (High Priority)
- Integrate `ActionInterpreter` into the `ToolExecutor` within the `open-multi-agent` framework.
- Implement the regex-based detection logic.

### Phase 3: Hardware/OS Mapping (Expansion)
- Populate the registry with core system functions (Process management, Service management, Memory management).
- Bridge the gap between semantic strings and physical execution.

## 5. Conclusion
Implementing Action Tags transitions the Sovereign Engine from a tool-using agent to a system-controlling entity. This provides the "nervous system" required for true autonomy and predictable agency.
