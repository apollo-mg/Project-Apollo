# Epiphany Investigation: Proactive Resource Orchestration
## Timestamp: 2025-05-22 (Simulated)
## Status: Initializing Audit

### Hypothesis
The system currently relies on reactive monitoring (checking `get_free_memory` or similar) which leads to "anxiety loops" where the system detects a crash is imminent but cannot prevent it. The epiphany suggests moving toward proactive orchestration: quantization and layer offloading.

### Investigation Plan
1.  **Identify Reactive Patterns:** Search for `get_free_memory`, `vram`, `memory`, and `check_memory` in the codebase to find where the "anxiety loop" resides.
2.  **Identify Resource Management Modules:** Look for files like `vram_management.py`, `system_monitor.py`, or `orchestrator.py` to see how resources are currently handled.
3.  **Assess Quantization/Offloading Capabilities:** Check if there are existing implementations for quantization or layer offloading (e.g., in `llama.cpp` or custom modules).
4.  **Draft Proposal:** Propose a shift from `system_monitor.py` (reactive) to a more proactive `resource_orchestrator.py` (proactive).
### Findings
- `vram_management.py` exists and contains a `smart_vram_guard` function (lines 98-112).
- The current implementation of `smart_vram_guard` is a simple threshold check: if `used > VRAM_THRESHOLD_MB`, it calls `unload_comfy_vram()`.
- This is still fundamentally reactive: it waits until the threshold is *already* crossed before acting.
- The `unload_comfy_vram` function is a "nuclear option" (unloading models entirely) rather than a surgical one (quantization or layer offloading).
- The "anxiety loop" mentioned in the epiphany is likely the `wait_for_vram_release` function (lines 68-85), which blocks execution while waiting for the kernel to flush, creating a bottleneck.

### Architectural Gaps
1. **Lack of Granularity:** There is no middle ground between "everything is fine" and "unload everything."
2. **No Predictive Scaling:** The system doesn't look at the *rate of change* of VRAM usage or the *complexity of the upcoming task* (e.g., a large image generation request).
3. **No Quantization Integration:** The system doesn't attempt to switch to a lower-bit model (e.g., 4-bit or 8-bit) when approaching the limit.

### Proposed Shift
Move from `smart_vram_guard` (reactive threshold) to a `ResourceOrchestrator` that:
1. **Monitors VRAM Velocity:** Calculates `dVRAM/dt`. If usage is spiking, trigger mitigation *before* the threshold.
2. **Task-Aware Pre-emption:** If the task queue contains a high-VRAM task (e.g., Flux), proactively clear VRAM *before* starting the task.
3. **Tiered Mitigation:**
    - **Tier 1 (Soft):** Trigger garbage collection/cache clearing.
    - **Tier 2 (Medium):** Switch to a quantized model version (if available).
    - **Tier 3 (Hard):** Offload non-essential layers/models (the current `unload_comfy_vram`).
