# Epiphany Audit: K-type Transformation Convergence

## Summary
The subconscious identified a pattern of "reactive patching" vs "ritualistic pattern enforcement." The actionable insight is to formalize the **'clone inputs + explicit shift rewrite'** as a mandatory structural primitive for all K-type transformations.

## Investigation Findings
1.  **Identification of K-type:** Through codebase scanning, "K-type" was not found as a literal string, but the concept aligns with `z.effects()` (Zod transformations) found in `tmp/open-multi-agent/src/tool/framework.ts`. These transformations are the primary source of potential architectural variance.
2.  **Current State:**
    *   `src/agent/runner.ts` and `src/agent/agent.ts` show evidence of mutation-based state management (e.g., `[...this.messageHistory]` is a shallow copy, and `runner.ts` explicitly mentions a "working copy... mutated as turns progress").
    *   `src/tool/executor.ts` executes tools using `parseResult.data`. If a Zod schema uses `.transform()`, the `data` object is the result of that transformation. If the transformation logic mutates the input object, it creates side effects that propagate through the agent's memory.
3.  **Architectural Risk:** In multi-agent environments, if one agent's tool transformation mutates a shared input object, it causes "architectural drift"—where the state of the world becomes inconsistent with the recorded history.

## Proposed Architectural Update

### 1. Formalize the 'K-Type' Primitive
Define "K-type transformations" as any transformation that alters the shape or content of an input object.

### 2. Mandatory Structural Pattern: `Clone -> Shift -> Rewrite`
All tool `execute` functions and Zod `transform` implementations must adhere to the following lifecycle:
1.  **Clone:** Perform a deep clone of the input object using `structuredClone()`.
2.  **Shift:** Apply the transformation logic to the *cloned* object.
3.  **Rewrite:** Return the new object, ensuring the original input remains immutable.

### 3. Implementation Strategy (Code Change Proposal)
**A. Update `ToolExecutor` (TypeScript):**
Modify the execution loop to ensure that the input passed to `execute` is a deep clone, preventing any possibility of the tool mutating the agent's internal state.

```typescript
// Proposed change in src/tool/executor.ts
async execute(name: string, input: any, context: ToolUseContext): Promise<ToolResult> {
  const tool = this.registry.get(name);
  if (!tool) throw new Error(`Tool ${name} not found`);

  // ENFORCE K-TYPE CONVERGENCE: Deep clone input before passing to execute
  const inputClone = structuredClone(input);
  
  // The 'Shift' happens during Zod parsing/validation
  const parseResult = tool.inputSchema.safeParse(inputClone);
  
  if (!parseResult.success) {
    // ... error handling
  }

  // The 'Rewrite' happens here
  return await tool.execute(parseResult.data, context);
}
```

**B. Update Agent Memory (Python/TypeScript):**
Ensure that when messages are added to history, they are deep-cloned to prevent subsequent turns from mutating previous turns' data.

## Conclusion
This change moves the architecture from "reactive patching" (fixing bugs caused by mutation) to "ritualistic pattern enforcement" (preventing mutation by design). This ensures architectural convergence across all agentic transformations.
