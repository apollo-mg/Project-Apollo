# Apollo Investigation: Blueprint-First Migration Strategy
## Epiphany Context
The subconscious identifies a risk of losing "context" (workflows/data) while preserving "logic" (patches/instructions). The goal is to decouple environmental configurations from the data they operate on.

## Investigation Goals
1. Identify current methods of managing environmental configurations (ROCm, kernel, drivers).
2. Check for existing version control of these configurations.
3. Assess the coupling between logic (scripts/patches) and data (large datasets/workflows).
## Initial Findings
- Found `upgrade_rocm.sh`: This is a prime candidate for a "Blueprint" module. It likely contains the logic for driver/ROCm updates.
- Found `foundry_configs`: This directory likely contains environmental configurations.
- Found `patched_commander.py` and `patched_commander_v2.py`: These suggest "logic" (patches) is being applied to the "commander" component.

## Hypothesis
The current system manages environment adaptation through scripts (`upgrade_rocm.sh`) and potentially manual configuration files, but these are not structured as "independent, lightweight modules." They are likely scattered or coupled to the specific execution environment.
## Deep Dive: `upgrade_rocm.sh`
- The script is a monolithic procedural script.
- It performs high-risk operations: stopping services (`mbsync.timer`, `ollama`), killing processes (`background_chronicler.py`), and installing system-level packages.
- **Risk:** If this script fails halfway, the system is left in an inconsistent state (services stopped, but ROCm not upgraded).
- **Coupling:** The script is tightly coupled to specific process names (`background_chronicler.py`, `discord_bridge.py`). If these processes change, the "blueprint" (the upgrade script) breaks.
- **Lack of Versioning:** There is no mechanism to version the *state* of the environment before or after the upgrade.

## Investigation Update
- `foundry_configs` is currently empty. This is a critical finding. It suggests that "foundry configurations" are either not being used or are being stored elsewhere, reinforcing the "lost context" epiphany.
- The absence of a structured configuration directory means that environmental tweaks are likely being applied ad-hoc or are hardcoded into scripts like `upgrade_rocm.sh`.

## Proposed Architectural Shift: The "Blueprint" Module
Instead of monolithic scripts, I propose a modular "Blueprint" system:
1. **`blueprints/env/`**: Version-controlled YAML/JSON files defining the desired state (ROCm version, kernel parameters, driver versions).
2. **`blueprints/drivers/`**: Modularized installation logic (e.g., `rocm_7_2.sh`, `nvidia_550.sh`) that accepts the state files as input.
3. **`blueprints/services/`**: A registry of services that must be managed during environment transitions, decoupling the upgrade logic from specific process names.
4. **`blueprints/snapshots/`**: A mechanism to capture the current system state (package versions, kernel version) before any "destructive" upgrade.

This ensures that the "logic" (the blueprint) is independent of the "weight" (the actual installed packages and data).
