# Epiphany Investigation: Heterogeneity Exploitation vs. Latency Mitigation
## Timestamp: 2026-02-27
## Status: Initializing Audit

### Hypothesis
The current MoE (Mixture of Experts) implementation likely treats all compute resources as a homogeneous pool, attempting to minimize latency through standard scheduling. The Epiphany suggests that the hardware's architectural differences (specifically RDNA 2 vs RDNA 4 instruction sets/capabilities) should be used as a routing signal. 

Instead of:
`Router -> Expert (Generic)`

We should aim for:
`Router -> [Hardware Capability Profile] -> Expert (Optimized for ISA)`

### Immediate Objectives
1.  **Identify MoE Routing Logic:** Locate the code responsible for expert selection and routing.
2.  **Identify Hardware Profiling:** Determine how the system currently perceives hardware (is it just "GPU" or does it know the ISA/Architecture?).
3.  **Analyze Existing Benchmarks:** Look at `moe_shootout.py` or similar to see if hardware-specific performance is being recorded.
4.  **Draft Proposal:** Design a "Tiered Execution Hierarchy" where experts are mapped to specific hardware capabilities.

### Findings: Hardware/Software Disconnect
- `profiles.json` shows that `architect` and `turbo` profiles use different server binaries:
    - `architect`: `/mnt/TG_2TB/Projects/Apollo/tmp/llama_cpp_gemma4/build/bin/llama-server`
    - `turbo`: `/mnt/TG_2TB/Projects/Apollo/tmp/llama_cpp_turboquant/build_rocm/bin/llama-server`
- The `env` variables in `profiles.json` (e.g., `HSA_OVERRIDE_GFX_VERSION: 12.0.1`) are being applied globally to the profile, but they don't seem to account for the *actual* hardware capability of the underlying device in a dynamic way.
- The `orchestrator.py` is a static launcher. It doesn't "route" based on hardware; it just launches what is in the JSON.
- The "Epiphany" is correct: we are treating the hardware as a static target for a specific binary, rather than a dynamic substrate that should influence the routing of MoE experts.

### Proposed Architectural Shift: "Heterogeneous Expert Routing" (HER)
Instead of static profiles, we need a `SubstrateAwareRouter`.

1. **Substrate Discovery Layer:**
   - A new module that probes the hardware (using `rocminfo` or similar) to identify the specific GFX version and instruction set capabilities (RDNA 2 vs RDNA 4).
   - This creates a `SubstrateProfile`.

2. **Expert-to-ISA Mapping:**
   - We define "Expert Tiers" based on ISA requirements.
   - *Tier 1 (High-Throughput/RDNA 4):* Experts optimized for newer instructions (e.g., specialized matrix math or memory compression).
   - *Tier 2 (Legacy/RDNA 2):* Experts using standard ROCm kernels.

3. **The Routing Protocol:**
   - The MoE router doesn't just pick the top-k experts.
   - It picks the top-k experts *weighted by the SubstrateProfile*.
   - If the current hardware is RDNA 2, the router penalizes the "Tier 1" experts to avoid the latency penalty of emulating or using suboptimal kernels, effectively "routing" the intelligence to the hardware it can actually exploit.

### Implementation Plan (Draft)
- **Step 1:** Create `src/substrate_discovery.py` to detect GFX version.
- **Step 2:** Modify `orchestrator.py` to accept a `substrate_id`.
- **Step 3:** Implement a `routing_engine.py` that sits between the model's MoE layer and the execution kernel, applying the hardware-weighting logic.
- **Step 4:** Update `profiles.json` to include `hardware_affinity` tags for models/experts.
