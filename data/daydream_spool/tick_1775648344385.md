# ARCHITECTURAL PROPOSAL: DUAL-CORE ORCHESTRATION LAYER

## 1. EXECUTIVE SUMMARY
The current system architecture suffers from VRAM contention on the RX 9070 XT (16GB) due to a lack of tiered intelligence. Large MoE models (26B-27B) are being deployed without strict resource partitioning, leading to latency spikes and potential OOM errors when ComfyUI/Vision tasks are active. 

This proposal shifts the architecture from a single-model deployment to a **Dual-Core Orchestration Layer**, separating heavy multimodal reasoning from high-frequency stability tasks.

## 2. IDENTIFIED ISSUES
- **VRAM Contention:** Current profiles (`architect` and `turbo`) both target port 8082, causing immediate conflicts.
- **Monolithic Deployment:** The system lacks a mechanism to route tasks based on complexity, forcing all tasks through heavy models.
- **Reactive VRAM Management:** `vram_management.py` is currently reactive (threshold-based) rather than proactive (partition-based).

## 3. PROPOSED ARCHITECTURE: TIERED INTELLIGENCE

### A. Model Hierarchy
| Tier | Model | Role | VRAM Strategy |
| :--- | :--- | :--- | :--- |
| **Reasoning Core** | DeepSeek V4-14B | Heavy multimodal reasoning, complex logic. | High `ngl`, high context, limited to available headroom. |
| **Stability Core** | Ministral 3 | High-frequency, low-latency stability/control tasks. | Low `ngl`, minimal VRAM footprint, high priority. |
| **Vision Core** | ComfyUI / Flux | Image/Video generation and vision processing. | Reserved VRAM headroom (min 4GB). |

### B. Orchestration Logic (`orchestrator.py` Update)
The `ServiceOrchestrator` will be upgraded to include a **Task Router**:
1. **Request Interception:** Incoming tasks are tagged with a `complexity_score` or `task_type`.
2. **Routing:**
   - `task_type: 'reasoning'` $\rightarrow$ Route to `reasoning_core`.
   - `task_type: 'stability' | 'control'` $\rightarrow$ Route to `stability_core`.
3. **VRAM-Aware Launch:** Before launching a profile, the orchestrator will call `vram_management.get_gpu_stats()` to ensure the requested model's footprint won't violate the `vision_core` headroom.

## 4. ACTIONABLE CODE CHANGES

### I. `profiles.json` Update
- Resolve port conflicts (e.g., `architect` on 8082, `turbo` on 8084).
- Add `reasoning_core` and `stability_core` profiles.
- Define `vram_limit_mb` for each profile to guide the orchestrator.

### II. `orchestrator.py` Update
- Implement `route_task(task_type: str) -> str` (returns profile name).
- Implement `launch_with_vram_check(profile_name: str)` which uses `vram_management.py` to validate headroom before `subprocess.Popen`.

### III. `vram_management.py` Update
- Add `get_available_headroom()` to return the safe margin for the Vision core.
- Implement `enforce_partition(profile_name: str)` to dynamically adjust `ngl` or `cache_ram` based on current usage.

## 5. SUCCESS METRICS
- **Zero OOMs:** No system-wide crashes during concurrent Vision/LLM tasks.
- **Latency Reduction:** Stability tasks (Ministral 3) should maintain <100ms response times regardless of Reasoning Core load.
- **Resource Efficiency:** Consistent 4GB+ VRAM headroom for ComfyUI.
