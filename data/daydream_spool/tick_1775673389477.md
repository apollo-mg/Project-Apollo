# Architectural Proposal: Surgical Sprint Deployment Model

## 1. Executive Summary
The current orchestration layer implements a simulated "hardware-aware" scheduling strategy that relies on existing agent pools. To realize the "Surgical Sprint" epiphany, the architecture must evolve from a **static agent assignment model** to a **dynamic resource provisioning model**. This proposal outlines the transition to a model where high-VRAM tasks (e.g., model surgery/abliteration) trigger the rapid, ephemeral deployment of 24GB-tier compute instances.

## 2. Identified Gap
The `src/orchestrator/scheduler.ts` currently uses a heuristic approach to assign tasks to existing agents based on simulated VRAM availability. It lacks the capability to:
1.  **Detect** the specific threshold requirements (the 24GB VRAM "gateway").
2.  **Provision** new, specialized compute resources on-demand.
3.  **Terminate** resources immediately after task completion to minimize capital expenditure.

## 3. Proposed Architectural Changes

### A. New Component: `ProvisioningOrchestrator`
**Location:** `src/orchestrator/provisioner.ts`
**Responsibility:** 
- Interface with infrastructure providers (e.g., Docker, Kubernetes, or Cloud APIs).
- Implement the "Surgical Sprint" lifecycle: `SpinUp` -> `AttachAgent` -> `Execute` -> `TearDown`.
- Manage the lifecycle of ephemeral 24GB-tier instances.

### B. Orchestrator Integration
**Location:** `src/orchestrator/orchestrator.ts`
**Changes:**
- Modify the main orchestration loop to check for "High-VRAM Intent" in pending tasks.
- If a task requires high VRAM and no suitable agent exists in the current pool, invoke the `ProvisioningOrchestrator`.
- Update the `TaskQueue` to reflect the status of "Provisioning" agents.

### C. Enhanced Scheduling Logic
**Location:** `src/orchestrator/scheduler.ts`
**Changes:**
- Refine `scheduleHardwareAware` to return a special `PROVISION_REQUIRED` signal instead of just picking the "best" (but insufficient) existing agent.
- Formalize the "Hardware-to-Intent" mapping (e.g., mapping "abliteration" or "surgery" keywords to a 24GB VRAM requirement).

### D. Type System Updates
**Location:** `src/types.ts`
**Changes:**
- Add `ProvisioningStatus` enum: `IDLE`, `PROVISIONING`, `READY`, `TERMINATING`.
- Update `AgentConfig` to include `provisioning_metadata` (e.g., instance type, VRAM requirement).

## 4. Implementation Roadmap
1.  **Phase 1 (Infrastructure Interface):** Implement the `Provisioner` interface with a mock provider to test the lifecycle logic.
2.  **Phase 2 (Orchestrator Hook):** Integrate the `Provisioner` into the `Orchestrator` loop.
3.  **Phase 3 (Hardware Mapping):** Formalize the keyword-to-VRAM mapping in the `Scheduler`.
4.  **Phase 4 (Real-world Deployment):** Connect the `Provisioner` to actual compute providers (e.g., local GPU via Docker or cloud instances).

## 5. Conclusion
By implementing the "Surgical Sprint" model, we transform the system from a passive task distributor into an active, resource-efficient compute engine capable of performing high-level model manipulation with minimal capital overhead.
