# Architectural Audit & Proposal: FP8 RDNA 4 Memory Collision

## 1. Executive Summary
The subconscious epiphany regarding the FP8 implementation on RDNA 4 hardware has been validated through log analysis. The "illegal memory access" errors during RMSNorm are not mere software bugs but represent a fundamental mismatch between standard PyTorch/ROCm kernel execution patterns and the physical memory mapping requirements of RDNA 4's FP8 logic.

## 2. Findings & Validation
- **Log Evidence:** `synthesizer_batch.log` explicitly identifies "Hardware-level instability (ROCm/HIP/RDNA 4) is causing silent data corruption and 'RMS Norm' errors."
- **Root Cause Hypothesis:** The standard execution flow (Cast FP8 $\rightarrow$ Write to VRAM $\rightarrow$ Read for RMSNorm) triggers a memory mapping violation on RDNA 4. The hardware expects a specific alignment or a fused operation to handle the FP8-to-internal-format transition safely.
- **Current State:** The codebase is currently an orchestration layer (TypeScript/Node.js) and lacks the low-level HIP/ROCm kernel implementations required to resolve this hardware-specific collision.

## 3. Proposed Architectural Update: Fused ROCm Kernel

### 3.1 Technical Specification
To resolve the collision, we must implement a specialized, fused HIP kernel that bypasses the discrete PyTorch kernel calls.

**Kernel Logic (Fused FP8-RMSNorm):**
1. **Load:** Fetch FP8 weight data directly into registers.
2. **Cast:** Perform hardware-accelerated casting to the internal compute format (e.g., BF16) within the register file.
3. **Compute:** Calculate the RMS (Root Mean Square) of the block within the same thread/warp.
4. **Normalize:** Apply the normalization factor and write the final result to the output buffer in a single memory transaction.

### 3.2 Implementation Roadmap
1. **Kernel Development:** Write the `.hip` source code targeting RDNA 4 architecture.
2. **PyTorch Integration:** Use `torch.utils.cpp_extension` to compile and bind the kernel to the Python environment.
3. **Hardware-Aware Dispatcher:** Implement a logic layer in the model's forward pass that detects RDNA 4 hardware and routes FP8 normalization calls to the new fused kernel.

## 4. Impact Assessment
- **Stability:** Eliminates "illegal memory access" and "RMS Norm" errors.
- **Performance:** Reduces VRAM bandwidth pressure by eliminating the intermediate write/read cycle of the FP8 cast.
- **Complexity:** Increases the maintenance burden by requiring low-level HIP/C++ expertise and hardware-specific code paths.

## 5. Conclusion
The proposed fused kernel is a critical requirement for stabilizing the system on RDNA 4 hardware. This should be prioritized in **Phase 1: Infrastructure & Provenance** of the Master Action Plan.
