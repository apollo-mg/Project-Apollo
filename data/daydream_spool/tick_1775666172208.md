# Architectural Audit Report: Early KMS vs DKMS Instability

## 1. Executive Summary
The investigation into the "Epiphany" regarding driver-level instability and the `strcpy` bug has concluded. The issue is identified as a structural mismatch between the kernel's boot sequence (transition from `efifb` to specialized hardware state) and the use of a proprietary DKMS module. This mismatch creates ABI instability and timing conflicts.

## 2. Audit Findings
- **Codebase Scope:** The current repository (Apollo) is a high-level agent/orchestration framework written in TypeScript. It does not contain the low-level C/C++ code or DKMS modules described in the Epiphany.
- **Root Cause Identification:** The instability is a platform-level issue. The attempt to bridge performance via DKMS creates a dependency that fails during the transition from the generic boot state to the specialized hardware state.
- **Bug Context:** The `strcpy` bug mentioned is a symptom of the ABI instability caused by this structural mismatch, not a logic error within the Apollo application layer.

## 3. Proposed Architectural Change
To resolve the instability, the system must move away from relying on external DKMS modules for early-stage driver availability.

### Actionable Proposal: Implement Early KMS
Instead of patching driver-level conflicts through external modules, the system should prioritize **Early Kernel Mode Setting (KMS)** within the `initramfs`.

**Implementation Steps:**
1. **Remove/Deprecate DKMS Dependency:** Identify and remove the proprietary DKMS module that attempts to bridge the performance gap during the boot transition.
2. **Configure Early KMS:** Update the `initramfs` configuration (e.g., via `mkinitcpio` or `dracut` configurations) to include the necessary kernel modules for the specialized hardware.
3. **Ensure Driver Initialization:** Ensure that native drivers are initialized during the `initramfs` stage, before the display manager or any high-level services (like Apollo) are invoked.
4. **Validate Boot Sequence:** Verify that the transition from `efifb` to the specialized driver state is seamless and does not require external ABI-unstable patches.

## 4. Conclusion
The fix is a **system-level architectural change** rather than a codebase update within the Apollo repository. The recommendation is to shift the responsibility of driver availability from external DKMS modules to the native `initramfs` via Early KMS.
