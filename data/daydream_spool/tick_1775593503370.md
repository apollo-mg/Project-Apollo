# Architectural Audit: Resident Loop & Telemetry Bridge

## 1. Epiphany Analysis
The subconscious has correctly identified a critical structural weakness: the **Resident Loop** (the orchestration layer) is currently decoupled from the actual execution of heavy-duty deployment tasks (the **Fleet Orchestrator**). 

The current workflow relies on `nohup` or detached processes that execute the `fleet_orchestrator.py` lifecycle. Because these processes run in a separate shell context without a direct feedback channel, the Resident Loop remains "blind" to intermediate failures (e.g., a `TRAIN` stage crash or a `ZIP` corruption) until it attempts to interact with the resulting artifact. This creates "empty state stalls" where the system thinks a task is progressing when it has actually silently failed.

## 2. Audit Findings
- **Current State:** `fleet_orchestrator.py` manages the `BOOT -> TRAIN -> ZIP -> UPLOAD -> VERIFY` lifecycle. It logs to standard output/files but does not push state updates to a centralized telemetry service.
- **Telemetry Layer:** An `ImmutableTelemetryLayer` exists (`telemetry_layer.py`) which is designed for recording state transitions and system health. However, it is currently underutilized by the deployment orchestration logic.
- **The Gap:** There is no "Watchdog" or "Telemetry Bridge" that actively monitors the `fleet_orchestrator.py` execution and reports real-time stage transitions back to the `orchestrator.py` or `fleet_orchestrator.py`'s parent.

## 3. Proposed Architectural Update

### Phase A: Telemetry Integration in `FleetOrchestrator`
Modify `fleet_orchestrator.py` to inject the `ImmutableTelemetryLayer` into its lifecycle. Each stage (`BOOT`, `TRAIN`, etc.) must emit a `record_transition` and `record_event` call.

**Draft Code Change (Conceptual):**
```python
# Inside FleetOrchestrator.run_lifecycle
from telemetry_layer import ImmutableTelemetryLayer

telemetry = ImmutableTelemetryLayer()

# Example for TRAIN stage
telemetry.record_transition("FLEET_ORCHESTRATOR", "BOOT_COMPLETE", "TRAINING")
try:
    train_result = self.trainer.train(...)
    telemetry.record_event("TRAIN_SUCCESS", "Model training completed", "INFO")
except Exception as e:
    telemetry.record_event("TRAIN_FAILURE", str(e), "CRITICAL")
    raise
```

### Phase B: The Watchdog Bridge
Implement a lightweight `DeploymentWatchdog` service. This service will:
1. Monitor the `telemetry_state_log.jsonl` file.
2. Parse recent entries for `FLEET_ORCHESTRATOR` components.
3. Provide a real-time status API (or simple file-based signal) that the Resident Loop can poll to determine if a process is `STALLED` (e.g., no telemetry updates for > 5 minutes).

## 4. Conclusion
The transition from "manual diagnostic workflow" to a "centralized telemetry bridge" is required to move the system from reactive error handling to proactive state awareness. This will prevent the Resident Loop from entering an indeterminate state during deployment failures.

**Status:** Audit Complete. Implementation of Telemetry Bridge recommended.
