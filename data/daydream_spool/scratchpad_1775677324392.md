# Epiphany Investigation: Semantic Collision (Content vs Intent)
- **Hypothesis:** DeepScaler's routing logic is misclassifying technical data as 'ENGINEER' because it uses 'Complexity-to-Role' instead of 'Purpose-to-Role'.
- **Goal:** Audit the taxonomy and system prompts to decouple technical complexity from the Engineer role and implement a 'Telemetry/Hardware Monitoring' override.
- **Status:** Initializing investigation.
- **Observation:** `modules/cognitive_dispatcher.py` uses a `TaskComplexity` enum (TRIVIAL, SIMPLE, MODERATE, COMPLEX) and a `_llm_triage` method.
- **Problematic Heuristics:** 
    - Lines 130-132: `['write', 'code', 'script', 'python', 'bash']` -> `SIMPLE`.
    - Lines 139-141: `['architect', 'refactor', 'system', 'design', 'cad']` + `['complex', 'deep', 'structural', 'entire', 'comprehensive']` -> `COMPLEX`.
- **The "Semantic Collision":** The `_llm_triage` prompt (Lines 148-157) defines complexity based on *what* the task is (e.g., "deep architecture, CAD") rather than the *intent* or *purpose*. If a user asks for "telemetry data for the GPU", the LLM might see "GPU" and "telemetry" as technical/complex and classify it as `COMPLEX` or `MODERATE`, even if the intent is just a simple status check (which should be `TRIVIAL` or `SIMPLE`).
- **Proposed Fix:** 
    1. Update `TaskComplexity` or add a `TaskIntent` layer.
    2. Modify `_llm_triage` prompt to prioritize *Intent* (e.g., "Monitoring/Status" vs "Design/Creation").
    3. Add a specific override for "Telemetry/Hardware Monitoring" to ensure it stays in the `WORKER` tier unless explicitly requested otherwise.
- **Next Step:** Find where the `SYSTEM_PROMPT` for the `UTILITY` role is defined to implement the override.
