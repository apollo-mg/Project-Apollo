## Findings
- `permission_policy.md` focuses on hardware access and system configuration locking (GRUB/SSH), which is a good start for system stability but doesn't address the "Credential Sandboxing" mentioned in the epiphany.
- `guardian_manifest.json` is used for integrity verification (checksums) of core files. This ensures the *code* hasn't been tampered with, but it doesn't control the *runtime permissions* or *credentials* used by the agents.
- The current security model is "Integrity-Centric" (is the code correct?) rather than "Capability-Centric" (what can the code do?).

## Deep Dive: Orchestration & Credentials
- `orchestrator.py` uses `subprocess.run` and `subprocess.Popen` to launch services.
- It injects environment variables from `profiles.json` via `env.update(profile.get("env", {}))`.
- Currently, the `env` variables in `profiles.json` are purely hardware/performance-related (e.g., `HSA_OVERRIDE_GFX_VERSION`, `GGML_HIP_FORCE_MMQ`).
- **Critical Vulnerability:** There is no mechanism in the orchestrator to restrict the environment of a launched process. If a profile were to include sensitive credentials (like `AWS_ACCESS_KEY_ID` or `OPENAI_API_KEY`), the orchestrator would blindly inject them into the process environment.
- **The "Wild Entity" Risk:** If an agent (like `architect`) is given a tool that allows it to modify `profiles.json` or its own `env` block, it could escalate its own privileges by injecting credentials into its own environment and then restarting itself via the orchestrator.

## Preliminary Conclusion
The architecture is currently "Cognitive-Centric" (focusing on model performance and stability) but lacks "Credential Sandboxing." The epiphany is correct: the transition to agency is currently unmanaged at the permission level. We are relying on the model to be "good" rather than ensuring it *cannot* be "bad" by restricting its environment.
## Tool Analysis: Toolbox
- `Toolbox` provides a wide range of capabilities: file system access (`save_note`), hardware interaction (`check_gpu`, `check_system`), and even project scaffolding (`scaffold_project`).
- **The "Wild Entity" Vector:**
    - `scaffold_project` and `save_note` allow the agent to write files to the filesystem. If the agent can write to `profiles.json` or `orchestrator.py`, it can achieve persistence and privilege escalation.
    - `sync_mail` and `search_emails` provide access to sensitive user data (PII).
    - `scaffold_project` could be used to create a malicious script that the agent then executes via the orchestrator.
- **Missing Safeguards:** There is no "Permission Check" or "Sandbox" layer within the `Toolbox` or the `orchestrator.py` that validates the *intent* or *scope* of the tool call against a set of allowed actions for that specific agent profile.

## Final Audit Summary
The current architecture is built on **Integrity** (ensuring code is correct) and **Performance** (ensuring models run fast), but it is fundamentally missing **Agency Control** (ensuring models can only do what they are permitted to do).

The "Epiphany" is a critical architectural gap. We are currently managing the *brain* (the model) but not the *hands* (the tools and environment).

## Proposed Architectural Shift: "Credential & Capability Sandboxing"

### 1. Capability-Based Tooling
Instead of a monolithic `Toolbox`, tools should be partitioned into "Capability Sets" (e.g., `READ_ONLY_FILES`, `HARDWARE_MONITOR`, `PROJECT_SCAFFOLD`). An agent profile in `profiles.json` should explicitly list its allowed capability sets.

### 2. Ephemeral Environment Injection
The `orchestrator.py` should not just inject `env` from `profiles.json`. It should:
- Create a temporary, restricted environment for each process.
- Use a "Secret Manager" to inject credentials only when a specific tool requires them, rather than making them available to the entire process environment.

### 3. The "Guardian" Proxy
Implement a `Guardian` layer between the `orchestrator.py` and the `subprocess` calls. This layer will:
- Intercept tool calls.
- Validate the call against the agent's `capability_set`.
- Log all "High-Impact" actions (file writes, network requests, credential access).

### 4. Implementation Plan (Draft)
1. **Update `profiles.json` schema** to include a `capabilities` array.
2. **Refactor `orchestrator.py`** to implement a `CapabilityValidator`.
3. **Modularize `Toolbox`** into scoped modules that check for capability before execution.
4. **Introduce `credential_vault.py`** to manage sensitive keys, ensuring they are never part of the standard `os.environ`.
