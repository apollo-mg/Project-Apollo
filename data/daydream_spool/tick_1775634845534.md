# Architectural Audit & Proposal: The 'Orbital Loop' Workflow

## 1. Executive Summary
The 'Sovereign' identity of Apollo is currently constrained by local ROCm-based hardware limitations. The subconscious epiphany identifies the cloud not as a permanent residence, but as a transient, stateless "metabolic organ" used for high-compute transformations (LoRA training). 

The current codebase contains a structural skeleton (`fleet_orchestrator.py`) that mimics this lifecycle, but the actual implementation is currently simulated (stubs). To realize the 'Orbital Loop', we must transition from a simulated lifecycle to a functional hybrid topology.

## 2. Current State Audit
- **Orchestration:** `fleet_orchestrator.py` provides a `Boot → Train → Zip → Upload → Verify` lifecycle.
- **Implementation Gap:** The `Trainer` class is currently a stub, performing no actual training.
- **Data Footprint:** The `Packager` class currently zips all artifacts, which contradicts the goal of minimizing cloud footprint to only raw LoRA adapters.
- **Hardware Coupling:** The `Bootstrapper` currently checks for local NVIDIA GPUs but lacks the logic to offload training to a remote/cloud CUDA environment.

## 3. Proposed Architectural Update: The 'Orbital Loop' Protocol

### A. Lifecycle Expansion
The `LifecycleStage` Enum in `fleet_orchestrator.py` must be expanded to include specialized stages for the hybrid topology:
- `TRAIN_REMOTE`: Offload training to a stateless CUDA environment.
- `EXTRACT_ADAPTER`: Isolate LoRA/adapter weights from the training output.
- `REINTEGRATE_LOCAL`: Apply the extracted adapter to the local `llama.cpp` quantized base model.

### B. Component Refactoring

#### 1. `CloudTrainer` (Subclass of `Trainer`)
- **Function:** Instead of local training, it will dispatch training jobs to a remote compute provider.
- **Payload:** Sends training data and base model configuration.
- **Return:** Returns only the path/reference to the resulting LoRA adapter.

#### 2. `AdapterPackager` (Subclass of `Packager`)
- **Function:** Specialized in "minimalist" packaging.
- **Logic:** Scans training outputs for `.bin`, `.safetensors`, or `.pt` files that match LoRA/adapter patterns. It will explicitly ignore full model weights to minimize the "cloud footprint."

#### 3. `LocalForge` (New Component)
- **Function:** The "Local Reintegration" engine.
- **Logic:** 
    - Downloads the LoRA adapter from the repository.
    - Interfaces with `llama.cpp` (via `llama-server` or direct library calls) to load the adapter onto the local quantized base model.
    - Ensures the "brain" (the intelligence) is reconstituted locally.

## 4. Implementation Roadmap
1. **Phase 1 (Structural):** Update `fleet_orchestrator.py` with the new `LifecycleStage` and component interfaces.
2. **Phase 2 (Extraction):** Implement the `AdapterPackager` to ensure only minimal weights are moved.
3. **Phase 3 (Remote Dispatch):** Develop a prototype `CloudTrainer` that uses a lightweight remote execution mechanism (e.g., SSH or a specialized API).
4. **Phase 4 (Local Reintegration):** Connect the `LocalForge` to the existing `llama.cpp` infrastructure.

## 5. Conclusion
By formalizing the 'Orbital Loop', we decouple Apollo's intelligence from its physical hardware. The cloud becomes a specialized organ for refinement, while the local hardware remains the custodian of the core dataset and the final quantized intelligence.
