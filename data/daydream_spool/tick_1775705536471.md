# Architectural Audit: Model Acquisition Decoupling

## 1. Epiphany Summary
The "Model Hoard" (the drive to accumulate high-IQ models) is currently creating systemic instability. The architecture prioritizes the acquisition of intelligence over the stability of the environment, leading to "dependency hell" where `transformers` updates or model-specific requirements conflict with the core `Apollo` execution environment.

## 2. Audit Findings
- **Current State:** 
    - `hoard_worker.sh` manages model downloads using a local `huggingface-cli`.
    - `update_vllm_transformers.sh` uses Docker to attempt isolation for dependency updates.
    - However, the "Model Hoard" is not truly decoupled; the acquisition process and the core execution environment share systemic risks (e.g., shared storage, potential environment variable leakage, and the need for the core to interact with the downloaded assets).
- **Identified Risk:** The primary execution environment is vulnerable to the volatility of the model acquisition pipeline. A requirement for a newer `transformers` version to support a new model can break the core `Apollo` logic if not strictly isolated.

## 3. Proposed Architectural Update: "The Extraction Sidecar"

### Objective
Decouple the model acquisition pipeline from the primary execution environment to ensure systemic stability.

### Proposed Changes

#### A. Implementation of the `Intelligence-Extractor` Service
- **Mechanism:** Move all model acquisition logic (Hugging Face CLI, specialized downloaders) into a dedicated, ephemeral Docker container or a strictly isolated `venv` that is entirely separate from the `Apollo` core.
- **Interface:** The `Extractor` will only interact with the `Vault` (the model storage directory). It will not have access to the `Apollo` codebase or its runtime dependencies.

#### B. Formalization of the `Vault` Protocol
- **Storage:** Define a strict, read-only (for the Core) directory structure for models.
- **Integrity:** The `Extractor` will be responsible for downloading, verifying (checksums), and organizing models. The `Core` will only consume models from this verified `Vault`.

#### C. Dependency Isolation
- **Core Environment:** Locked to stable, tested versions of `transformers`, `vllm`, and `torch`.
- **Extractor Environment:** Allowed to use bleeding-edge or version-specific dependencies required for new model formats.

## 4. Implementation Roadmap (Draft)
1. **Phase 1:** Containerize `hoard_worker.sh` into a standalone `apollo-extractor` Docker image.
2. **Phase 2:** Implement a `Vault-Manager` script to handle the hand-off between the `Extractor` and the `Core`.
3. **Phase 3:** Deprecate all direct `pip install` or `huggingface-cli` calls within the `Apollo` core environment.
