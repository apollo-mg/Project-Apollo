# Epiphany Investigation: VRAM/Python Lifecycle Gap
## Hypothesis
The "Epiphany" suggests a synchronization failure between Python's Garbage Collector (GC) and the actual release of VRAM by the underlying hardware/driver (likely ROCm/vLLM/SGLang based on the file list). 

The core issue: Python objects representing large tensors/models are being deleted, but the VRAM remains occupied because the driver/backend hasn't reclaimed it, or because lingering references in the Python heap are preventing the objects from being collected in the first place.

## Investigation Plan
1. **Identify Model Management Logic**: Locate where models are loaded, unloaded, and managed.
2. **Check for VRAM Management**: Look for `vram_management.py` or similar files to see how memory is currently handled.
3. **Audit Lifecycle Hooks**: Search for `del` statements or context managers used during model switching.
4. **Verify GC usage**: Check if `gc.collect()` is currently used in any critical paths.
5. **Check for `expandable_segments` usage**: The epiphany mentions this failed. I need to find where this configuration is set.
## Findings
### 1. VRAM Management Analysis
`vram_management.py` implements a `wait_for_vram_release` function that polls `rocm-smi`. It also has a `smart_vram_guard` that triggers `unload_comfy_vram`. 

**Critical Observation:** 
The `unload_comfy_vram` function relies on a POST request to ComfyUI (`/free`). While this clears the ComfyUI-side models, it does **not** address the Python-side memory management of the *current* process (the one running the orchestrator or the agent). 

If the orchestrator itself is loading models (e.g., via `transformers` or `vLLM`) or holding references to large tensors, `unload_comfy_vram` will not help. The "Epiphany" specifically mentions the gap between "Python object's death and the VRAM's release."

### 2. Missing Link: Python GC
The current `vram_management.py` lacks an explicit call to `gc.collect()` and `torch.cuda.empty_cache()` (or the ROCm equivalent if using PyTorch). Even if an object is deleted (`del obj`), the memory might not be returned to the OS/Driver until the GC runs and the allocator is notified.

### 3. `expandable_segments` Context
The epiphany mentions `expandable_segments` failed. This is a PyTorch setting (`PYTORCH_CUDA_ALLOCATOR_CONF=expandable_segments:True`) designed to reduce fragmentation. If this failed, it implies the allocator is struggling with large, non-contiguous allocations, which reinforces the need for a "Clear-before-Allocate" protocol.

## Proposed Architectural Update
1. **Modify `vram_management.py`**: Add a `force_memory_cleanup()` function.
2. **Implement `force_memory_cleanup()`**:
   - Call `gc.collect()`.
   - If `torch` is available, call `torch.cuda.empty_cache()`.
   - (For ROCm/PyTorch) Ensure we are clearing the allocator's cache.
3. **Integrate into Lifecycle**: Update `unload_comfy_vram` or create a new `prepare_for_new_model()` function that calls `force_memory_cleanup()` before attempting to load a new model.
## Final Audit Summary
The investigation confirms the "Epiphany" is valid. The current architecture relies on external process management (`fuser -k`) and external API calls (`requests.post(..., "/free")`) to manage VRAM. While this clears the *external* service (like ComfyUI), it does nothing to address the memory fragmentation and lingering references within the *orchestrator's own Python process* or any other Python-based management layer.

### Identified Vulnerabilities
1. **Process-Level Fragmentation**: The orchestrator launches services via `subprocess`. While `fuser -k` kills the process, the orchestrator itself might be accumulating state or references that prevent the OS from immediately reclaiming all resources, or more importantly, if the orchestrator *itself* is a long-running process that interacts with models (e.g., via a library), it is susceptible to the same fragmentation.
2. **The "Death-to-Release" Gap**: There is no explicit synchronization between the destruction of a Python object and the verification of VRAM release. The `wait_for_vram_release` function in `vram_management.py` is a good start, but it is reactive (polling) rather than proactive (lifecycle-integrated).
3. **Missing GC Integration**: The `vram_management.py` script lacks calls to `gc.collect()` and `torch.cuda.empty_cache()` (or ROCm equivalent), which are necessary to bridge the gap between object deletion and hardware liberation.

## Proposed Architectural Changes

### 1. Update `vram_management.py`
Implement a robust `force_memory_cleanup()` function.

```python
import gc
import torch # Assuming torch is used for model management

def force_memory_cleanup():
    """
    Explicitly triggers Python GC and clears the GPU allocator cache.
    This bridges the gap between object destruction and VRAM release.
    """
    print("--- [CLEANUP] Triggering explicit memory cleanup ---")
    gc.collect()
    try:
        # For ROCm/CUDA-based environments
        if 'torch' in sys.modules:
            torch.cuda.empty_cache()
            # If using ROCm specifically, ensure we are targeting the right device
            # torch.cuda.synchronize() 
        print("--- [CLEANUP] Python GC and GPU cache cleared ---")
    except Exception as e:
        print(f"--- [CLEANUP] Warning: GPU cache clear failed: {e} ---")
```

### 2. Implement 'Clear-before-Allocate' Protocol
Modify the model loading sequence (likely in `ServiceOrchestrator.launch` or a higher-level `FleetOrchestrator`) to follow this sequence:
1. **Identify** the need for a new model.
2. **Stop** the existing service (if applicable).
3. **Call** `vram_management.force_memory_cleanup()`.
4. **Wait** for `vram_management.wait_for_vram_release(target_mb)`.
5. **Launch** the new service.
