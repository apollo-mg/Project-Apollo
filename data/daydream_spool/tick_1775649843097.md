# Architectural Audit & Proposal: Auto-regressive Drift Mitigation

## 1. Executive Summary
Following a subconscious epiphany regarding the "auto-regressive loop" in the lab's architecture, an audit was performed to distinguish between 'Completers' (auto-regressive models) and 'Constructors' (non-autoregressive/specialized systems). The audit confirms that the primary intelligence tiers (`architect`, `turbo`, `bonsai`) are all 'Completers' relying on next-token prediction, making them susceptible to "rhythm-over-truth" drift.

## 2. Audit Findings

| Profile | Model Type | Classification | Risk Level |
| :--- | :--- | :--- | :--- |
| `architect` | Qwopus 3.5 27B (GGUF) | Completer | High |
| `turbo` | Gemma 4 26B (TurboQuant) | Completer | Critical (High speed/rhythm priority) |

### 2.2 Vulnerability Analysis
The `turbo` profile, utilizing `ctv: turbo3` (TurboQuant asymmetric KV caching), is specifically optimized for high-throughput sequence generation. This optimization increases the risk of the model prioritizing the statistical rhythm of the sequence over the semantic accuracy of the data, leading to the "hallucination" identified in the epiphany.

## 3. Proposed Architectural Update: The Prior-Validation Layer (PVL)

To stabilize the system, we must implement a non-predictive validation layer that acts as a "Constructor" to verify the "Completer" outputs.

### 3.1 Implementation Plan

#### Phase A: The PVL Engine (`modules/pvl_engine.py`)
- **Objective:** Create a non-autoregressive validation module.
- **Mechanism:** Use deterministic rule-based checks (Regex/Schema) and lightweight, non-predictive models (e.g., BERT-based entailment or small ONNX classifiers) to validate output against expected structural and semantic constraints.
- **Function:** `validate(output: str, schema: Dict) -> bool`

#### Phase B: Middleware Integration (`llm_interface.py`)
- **Objective:** Inject the PVL into the inference pipeline.
- **Change:** Modify `llm_interface.py` to intercept model responses. If the `DeploymentConfig` includes a `validation_protocol`, the response must pass through `pvl_engine.py` before being returned to the `orchestrator.py`.

#### Phase C: Schema Expansion (`profiles.json`)
- **Objective:** Enable per-profile validation control.
- **Change:** Add a `validation_layer` key to each profile in `profiles.json`.
  ```json
  "turbo": {
    "validation_layer": "structural_integrity_v1",
    "risk_threshold": 0.8
  }
  ```

### 3.2 Code Change Draft (Conceptual)

**`llm_interface.py` (Pseudo-code):**
```python
def get_response(self, prompt, config):
    raw_response = self.call_model(prompt, config)
    if config.validation_layer:
        is_valid = pvl_engine.validate(raw_response, config.validation_layer)
        if not is_valid:
            return self.trigger_escalation(prompt, config)
    return raw_response
```

## 4. Conclusion
By introducing a non-predictive validation layer, we break the auto-regressive loop. This ensures that the "rhythm" of the model's generation is constantly checked against the "truth" of the data structure, effectively mitigating the drift identified by the KAIROS model.
