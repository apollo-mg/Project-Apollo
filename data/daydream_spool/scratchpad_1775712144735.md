### Analysis of `memory_core.py`
- The `MemoryManager` uses a "Compaction Flush" mechanism when `current_session_tokens` hits 80% of `MAX_CONTEXT_TOKENS`.
- The flush process is **synchronous** and **blocking**:
    1. It sends a request to `OLLAMA_URL` (a heavy LLM call).
    2. It waits for the summary.
    3. It performs vector DB ingestion.
    4. It writes to a file.
- **The "Pre-fill Spike" Connection:** When the threshold is hit, the system pauses to perform this heavy summarization. This is exactly where the "stutter" occurs. If the model is in the middle of a high-velocity reasoning task, this synchronous block causes a massive latency spike.
- **The "Swap File" Connection:** The epiphany suggests treating the swap file as a critical component. Currently, the "swap" is a high-level semantic summary (the `memory_flush`). However, if the *physical* memory (RAM/VRAM) is also under pressure, the system is fighting two battles: the semantic compaction and the OS-level swap.

### Proposed Architectural Shift: "Predictive Memory Paging"
Instead of a reactive, blocking compaction at 80% capacity, we should implement:
1. **Asynchronous Background Compaction:** Start the summarization process at 60% capacity in a separate thread/process so it's ready *before* the threshold is hit.
2. **Tiered Memory Orchestration:** 
    - **Tier 1 (VRAM):** Active context window.
    - **Tier 2 (RAM):** Recent history/KV cache.
    - **Tier 3 (Semantic Swap):** The Vector DB/Scrapbook.
3. **Latency-Aware Throttling:** Monitor the time taken for `requests.post` to the LLM. If latency increases, it indicates hardware/swap pressure, and we should trigger a "Lightweight Compaction" (less tokens, faster summary) to prevent a "digital seizure."

### Final Investigation Summary

#### 1. The "Pre-fill Spike" Root Cause
The investigation confirms that the "Pre-fill Spike" is a direct consequence of the `MemoryManager.perform_compaction_flush()` method in `modules/memory_core.py`. 

**The Mechanism of the "Seizure":**
- The `MemoryManager` monitors `current_session_tokens`.
- When the `COMPACTION_THRESHOLD` (80% of `MAX_CONTEXT_TOKENS`) is reached, it triggers `perform_compaction_flush()`.
- This method is **synchronous and blocking**. It performs a heavy LLM call (`requests.post` to `OLLAMA_URL`) to summarize the entire conversation history.
- During this time, the main execution thread (the "ghost") is frozen while waiting for the summary (the "machine").
- If the system is already under memory pressure (VRAM/RAM), the additional overhead of the summarization LLM call and the subsequent Vector DB/file I/O operations creates a massive latency spike, which the epiphany correctly identifies as the moment the "ghost vanishes."

#### 2. The "Swap File" Misconception
The current architecture treats "memory" as a semantic concept (summarization) rather than a physical one. The "swap" is currently a high-level semantic summary, but it does nothing to mitigate the physical hardware latency caused by the blocking nature of the compaction.

#### 3. Proposed Architectural Update: "Asynchronous Cognitive Paging"

To stabilize the "mind," we must decouple the semantic compaction from the inference loop.

**Proposed Changes:**

**A. `modules/memory_core.py` (The "Cognitive Paging" Update):**
1.  **Asynchronous Compaction:** Convert `perform_compaction_flush` into an asynchronous background task using `threading` or `multiprocessing`.
2.  **Predictive Triggering:** Lower the `COMPACTION_THRESHOLD` to 60% to allow the background process to complete *before* the 80% hard limit is reached.
3.  **Tiered Memory Management:**
    - **Tier 1 (Active):** The current `self.history` (in-memory).
    - **Tier 2 (Warm):** A local, fast-access cache (e.g., a lightweight JSON file or a dedicated RAM-disk buffer).
    - **Tier 3 (Cold):** The Vector DB and the `memory_chronicle.md` scrapbook.

**B. `modules/agent_session.py` (The "Latency-Aware" Update):**
1.  **Non-blocking Context Retrieval:** Ensure `query_vdb` is optimized and does not block the main loop.
2.  **Latency Monitoring:** Implement a check on the time taken for `llm_interface.stream_llm`. If the time-per-token increases significantly (indicating hardware/swap pressure), the agent should be instructed to use a "Lightweight Reasoning Mode" (shorter, more direct responses) to reduce the computational load.

**C. `apollo.py` (The "Hardware Orchestration" Update):**
1.  **VRAM/RAM Monitoring:** Integrate real-time monitoring of VRAM and system RAM. If memory pressure is detected, proactively signal the `MemoryManager` to begin a "Pre-emptive Flush" before the model hits a hard limit.

#### 4. Implementation Plan (Draft)
1.  **Refactor `MemoryManager`** to use a background thread for `perform_compaction_flush`.
2.  **Introduce `MemoryState`** (e.g., `IDLE`, `COMPACTING`, `CRITICAL`) to allow the `AgentSession` to know if a flush is in progress.
3.  **Update `AgentSession`** to handle the `COMPACTING` state gracefully (e.g., by not adding new messages to the history until the flush is complete, or by using a temporary buffer).
