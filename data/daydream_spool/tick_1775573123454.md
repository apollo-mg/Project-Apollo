# Architectural Audit: Memory Contiguity & Alignment for RDNA 4

## Epiphany Analysis
The subconscious daemon has identified a critical structural vulnerability: the current memory management system treats memory as a logical abstraction (key-value pairs in a `Map`), ignoring the physical spatial requirements of the RDNA 4 architecture. For high-performance computational kernels (like those potentially used in JIT-transferred weight offloading), non-contiguous memory access patterns ("the ghost of non-contiguity") can lead to performance degradation or hardware-level instability.

## Current State Audit
- **Memory Implementation:** The current `InMemoryStore` (in `src/memory/store.ts`) uses a standard JavaScript `Map<string, MemoryEntry>`.
- **Data Structure:** Data is stored as discrete objects within a `Map`. While logically sound for a high-level orchestration framework, this provides zero guarantees regarding the physical memory layout of the underlying values when they are serialized or transferred to a computational context.
- **Transfer Pipeline:** There is currently no explicit "alignment" or "contiguity" enforcement pass. Data is simply stringified or passed as-is.

## Proposed Architectural Update: The Contiguity Enforcement Pass

To resolve the tension between logical abstraction and physical reality, I propose the implementation of a **Memory Alignment & Contiguity (MAC) Layer** within the JIT-transfer pipeline.

### 1. Implementation of `ContiguityEnforcer`
A new utility module `src/memory/contiguity.ts` will be introduced. This module will be responsible for:
- **Buffer Alignment:** Ensuring that any weight tensors or large data blocks are aligned to specific byte boundaries (e.g., 64-byte or 256-byte alignment) required by RDNA 4 SIMD instructions.
- **Contiguity Verification:** Before an offload operation, the enforcer will validate that the data buffer is a single, contiguous block of memory.
- **Defragmentation/Re-packing:** If data is non-contiguous (e.g., fragmented across multiple logical entries), the enforcer will perform a "re-packing" operation to create a new, physically contiguous `ArrayBuffer` before the JIT transfer.

### 2. Integration into `SharedMemory`
The `SharedMemory.write` method will be updated to detect "Heavyweight" payloads (e.g., large numeric arrays or tensors).
- If a payload is detected as a high-performance weight set, the `write` operation will trigger the `ContiguityEnforcer`.
- The resulting entry in the `MemoryStore` will include a `physicalLayout` metadata flag, signaling to the computational kernels that the data is pre-aligned and safe for direct DMA/JIT transfer.

### 3. Updated `MemoryEntry` Type
The `MemoryEntry` interface in `src/types.ts` will be extended:
```typescript
export interface MemoryEntry {
  readonly key: string;
  readonly value: string;
  readonly metadata?: Record<string, unknown>;
  readonly createdAt: Date;
  /** New: Indicates if the value is physically contiguous and aligned for hardware kernels */
  readonly isHardwareOptimized?: boolean;
}
```

## Conclusion
The "poison" of non-contiguity is a structural corruption that our current logical abstraction ignores. By implementing a mandatory alignment pass, we bridge the gap between the high-level agent orchestration and the low-level hardware requirements of the RDNA 4 architecture.
