# Architectural Audit: The 'Silence' Gap & Attention Dispatcher Proposal

## 1. Epiphany Validation
The subconscious epiphany is **highly valid**. Current notification logic is fragmented and reactive. 
- `discord_bridge.py` is currently acting as a monolithic "bridge" that handles both Discord logic and specific business logic (like checking `FORGE_REFINED_PATH` or `PENDING_PATH`).
- This creates a "tight coupling" where adding a new notification type (e.g., SMS, Telegram, or a local siren) requires modifying the core bridge or adding more specialized loops.
- The system is "silent" because there is no unified way for a module to say: *"I have a high-priority event that requires human attention."*

## 2. Current State Audit
- **Fragmented Logic:** `discord_bridge.py` contains hardcoded paths to `modules/approvals/pending.json` and `modules/forge.py`.
- **Polling Inefficiency:** The bridge uses `tasks.loop` to poll files/directories. This is a "pull" model that is inherently delayed and resource-intensive.
- **Lack of Multi-modality:** There is no abstraction for "Alerts." If we wanted to add an audible beep via `aplay` or a mobile push, we would have to write new logic inside the bridge.

## 3. Proposed Architecture: The 'Attention Dispatcher'

Instead of modules talking to `discord_bridge.py`, they will talk to a centralized `AttentionDispatcher`.

### A. The Dispatcher Service (`services/attention_dispatcher.py`)
A singleton service that manages a queue of `AttentionEvent` objects.
- **Event Types:** `CRITICAL_SECURITY`, `HUMAN_IN_THE_LOOP`, `SYSTEM_DEGRADATION`, `INFO_ONLY`.
- **Severity Levels:** `LOW`, `MEDIUM`, `HIGH`, `EMERGENCY`.
- **Dispatch Logic:** Based on severity and event type, the dispatcher routes the event to registered "Handlers."

### B. Multi-Modal Handlers
- **`DiscordHandler`**: Sends embeds/messages to specific channels.
- **`AudioHandler`**: Triggers local system sounds (e.g., `beep`, `aplay`) for `EMERGENCY` events.
- **`MobileHandler`**: (Future) Integration with Pushover/NTFY.
- **`VisualHandler`**: (Future) Updates the `GLASS_COCKPIT.md` or a dynamic canvas.

### C. Implementation Workflow
1. **Define the Interface:**
   ```python
   # Example usage in a module
   from services.attention_dispatcher import AttentionDispatcher
   
   async def handle_security_breach():
       await AttentionDispatcher.dispatch(
           event_type="SECURITY_BREACH",
           severity="EMERGENCY",
           message="Unauthorized access attempt detected in vault.",
           metadata={"ip": "192.168.1.50"}
       )
   ```
2. **Decouple `discord_bridge.py`**: 
   - Convert `discord_bridge.py` from a "logic provider" to a "subscriber" of the `AttentionDispatcher`.
   - It will simply listen for `AttentionEvent` objects and format them for Discord.

## 4. Immediate Action Plan
1. **Phase 1 (Foundation):** Create `services/attention_dispatcher.py` and a base `AttentionEvent` class.
2. **Phase 2 (Migration):** Move the logic currently in `discord_bridge.py` (the loops for `check_new_refinements` and `check_pending_approvals`) into specialized modules that *emit* events to the Dispatcher.
3. **Phase 3 (Expansion):** Implement the `AudioHandler` to break the "silence" using local system calls.

**Status:** *Architectural Gap Identified. Transitioning from Patching to Orchestration.*
