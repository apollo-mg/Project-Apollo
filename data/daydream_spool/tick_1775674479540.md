# Architectural Audit: Loop Stability & Execution Verification

## Epiphany Context
The subconscious identified a false dichotomy between 'reasoning' (PAL) and 'agency' (Jarvis). The intelligence lies in the translation of intent into a verifiable execution loop. Current development has over-indexed on linguistic accuracy, leading to a "hallucination" risk where the agent assumes success based on the *intent* to execute, rather than the *reality* of the execution.

## Audit Findings
The investigation of `orchestrator.py` and the agent's execution patterns revealed a critical structural weakness in the "Agency" component:

1.  **Silent Failures in Background Mode:** The `ServiceOrchestrator.launch` method uses `subprocess.Popen` with `stdout=subprocess.PIPE` and `stderr=subprocess.PIPE` for background processes. This is highly unstable:
    - **Buffer Deadlock:** Without an active consumer, the process will hang once the OS pipe buffer is full.
    - **False Positives:** The method returns `0` (success) immediately after the process is spawned, regardless of whether the process actually initializes correctly or crashes immediately due to resource constraints (VRAM, missing models, etc.).
2.  **Decoupled Reasoning and Reality:** The agent receives a success signal from the orchestrator and proceeds to the next reasoning step (the "thought") before the service (the "reality") is actually ready. This creates the "hallucination" loop described in the epiphany.

## Proposed Architectural Update: "The Verifiable Loop"

To resolve this, we must shift from "Fire and Forget" to "Spawn and Verify."

### 1. Orchestrator Refactoring (`orchestrator.py`)
- **Redirect to Persistent Logs:** Replace `subprocess.PIPE` with redirection to dedicated log files (e.g., `logs/{profile_name}.log`). This prevents buffer deadlocks and provides a permanent audit trail for the agent to inspect.
- **Implement Readiness Probing:** The `launch` method must include a `_verify_readiness` phase. For AI services, this means polling the assigned port or checking the log file for a "Ready" or "Listening" string before returning a success code.
- **Timeout-Aware Execution:** Implement strict timeouts for the verification phase to prevent the orchestrator from hanging on a failed service.

### 2. Agent/Tool Integration (`src/agent/agent.py` & Tools)
- **Observation-First Reasoning:** Update the agent's tool-calling protocol. A tool call is not "complete" when the command is sent; it is complete only when the *observation* (the result of the readiness probe or the log output) is returned to the reasoning engine.
- **Error-State Feedback:** If the readiness probe fails, the tool must return the specific error from the log file (e.g., `CUDA Out of Memory`) rather than a generic `Execution Failed`. This allows the "Reasoning" (PAL) to adjust its next "Thought" (e.g., by choosing a smaller model).

### 3. Implementation Roadmap
- [ ] **Phase 1:** Update `orchestrator.py` to use file-based logging instead of pipes.
- [ ] **Phase 2:** Implement `ServiceOrchestrator.verify_readiness()` using port-probing.
- [ ] **Phase 3:** Update the Agent's execution loop to wait for the `verify_readiness` signal.
