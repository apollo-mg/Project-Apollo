# Investigation: Quantization & VRAM Management
## Epiphany Context
The subconscious identified a "cyclical struggle with hardware thresholds" and suggested that the `--lowvram` flag is a symptom of a shift from parallel execution to sequential survival. The proposed solution is to implement quantized model formats (GGUF/NF4) to reduce UNet memory footprint and minimize VRAM swap cycles.

## Initial Audit Steps
1. Identify where `--lowvram` or VRAM management logic is currently implemented.
2. Locate model loading/provisioning logic to see how quantization is currently handled (or if it's missing).
3. Check for existing support for GGUF or NF4 in the current codebase.
## Findings
- `vram_management.py` exists and provides telemetry via `rocm-smi`.
- It includes a `smart_vram_guard` function that triggers `unload_comfy_vram` when usage exceeds `VRAM_THRESHOLD_MB`.
- The current strategy is reactive (waiting for threshold breach) and relies on ComfyUI's `/free` endpoint to flush memory.
- There is no evidence of quantization-aware loading in the current VRAM management logic.
- The "Slow and Steady" bottleneck is likely caused by the frequency of these `unload_comfy_vram` calls and the subsequent latency of reloading full-precision models.

## Hypothesis
By integrating quantization (GGUF/NF4) into the model provisioning layer, we can lower the `VRAM_THRESHOLD_MB` or, more importantly, prevent the threshold from being hit in the first place. This would reduce the "rhythmic, sequential survival" mode (constant swapping) and allow for more "parallel, fluid execution."

## Next Steps
1. Search for model loading/provisioning logic (e.g., `model_provisioner.sh`, `model_manifest.json`, or Python scripts that interact with ComfyUI/LLMs).
2. Determine if the current system supports passing quantization parameters to the model loader.
3. Propose an architectural change to include a `quantization_preference` in the model manifest or provisioning workflow.
## Detailed Analysis of Provisioning
- `model_provisioner.sh` is a simple downloader that uses `model_manifest.json`.
- `model_manifest.json` currently only contains metadata for downloading files (URL, filename, type).
- There is no mechanism for selecting different versions of a model (e.g., FP16 vs. GGUF) or specifying quantization requirements.

## Proposed Architectural Update
To implement the Epiphany's insight, we need to evolve the manifest and the provisioning logic to support "Quantization Profiles."

### 1. Manifest Evolution
Update `model_manifest.json` to support multiple variants per model ID.
Example structure:
```json
{
  "models": [
    {
      "id": "flux_dev",
      "name": "Flux.1 Dev",
      "variants": [
        {
          "type": "fp16",
          "url": "...",
          "filename": "flux_fp16.safetensors"
        },
        {
          "type": "gguf_q4_k_m",
          "url": "...",
          "filename": "flux_q4_k_m.gguf"
        }
      ]
    }
  ]
}
```

### 2. Provisioning Logic Update
Update `model_provisioner.sh` to iterate through `variants` instead of a single `url`.

### 3. Runtime Integration (The "Bridge")
The `vram_management.py` or the orchestrator (e.g., `orchestrator.py`) must be able to request a specific `variant_type` based on current VRAM pressure.
- **Normal State:** Load `fp16` variants.
- **High Pressure State (VRAM > Threshold):** Switch to `gguf` or `nf4` variants for the next model swap.

## Conclusion
The "Slow and Steady" bottleneck is a direct result of the system's inability to dynamically adjust model precision to match available hardware headroom. By implementing a variant-aware manifest and provisioning system, we can transform the "rhythmic survival" into a "dynamic scaling" model.
