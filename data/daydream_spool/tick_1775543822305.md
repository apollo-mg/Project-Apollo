# Architectural Audit: State-Sanity Check Protocol (Epiphany Response)

## 1. Epiphany Analysis
The subconscious has identified a critical architectural gap: the assumption that model deployment is a logical operation rather than a physical state transition. Currently, the system treats VRAM and filesystem states as static resources. The "unspoken truth" is that the hardware layer is "occupied" rather than "clean," leading to potential OOM (Out of Memory) errors or "dirty" state interference during high-level routing.

## 2. Current State Audit
- **`vram_management.py`**: Contains `smart_vram_guard` and `wait_for_vram_release`. It is proactive but currently decoupled from the primary orchestration logic. It relies on `rocm-smi` and a ComfyUI cleanup endpoint.
- **`orchestrator.py`**: Manages service lifecycles (launch/stop) but lacks a "State-Sanity Check" before launching new profiles. It assumes that if a port is free, the hardware is ready.
- **`router_v3.py` (Conceptual/In-Development)**: The intended high-level cognitive architecture. It currently lacks the "State-Sanity Check" protocol mentioned in the epiphany.

### B. Router V3 Implementation (The "Volatile Truth" Dispatcher)
The `router_v3.py` must treat the `SYSTEM` module not just as a reporter, but as a gatekeeper.

**Proposed Logic for `router_v3.py`:**
1. **Pre-Routing Check**: Before routing a complex task to `DEEP_THINK` or `ARCHITECT`, the router queries `vram_management.py`.
