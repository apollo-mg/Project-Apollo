# Apollo Investigation: Tiered Autonomy Framework
## Timestamp: 2025-05-22 (Simulated)
## Status: Initializing Audit

### Epiphany Context
The subconscious daemon identified a friction loop: 'Request cancelled' logs suggest that safety protocols are hindering agentic flow. The current model is binary (Manual vs. YOLO). The proposed solution is a tiered autonomy framework.

### Investigation Goals
1. Identify where 'Request cancelled' or similar friction-inducing logs are generated.
2. Locate the current permission/autonomy logic (e.g., `permission_policy.md`, `guardian_manifest.json`, `lab.json`).
3. Identify the 'flash_coder' or similar high-velocity agents.
4. Assess the current implementation of 'YOLO mode'.

### Initial Findings
- Found `permission_policy.md`.
- Found `guardian_manifest.json`.
- Found `lab.json`.
- Found `orchestrator.py`.
- Found `task_manager.py`.
- Found `fleet_orchestrator.py`.

### Hypothesis
The current permission system is likely centralized in a single file or a rigid check within the `orchestrator.py` or `task_manager.py`, making it difficult to grant granular autonomy to specific sub-agents without compromising the whole system.
### Audit Findings: The Friction Loop
The `modules/approvals/handler.py` file confirms the "binary" nature of the current system. 

1. **The Bottleneck:** The `should_require_approval` function uses a rigid heuristic:
   - `run_shell` is *always* blocked (Line 27).
   - `write_code` is blocked if the file is in `CORE_FILES` (Line 44) OR if the content is "large" (Line 48).
   - This explains the "Request cancelled" friction: an agent trying to perform a complex, multi-line refactor or a shell-based test will trigger a mandatory human-in-the-loop (HITL) request via `request_approval`.

2. **The "YOLO" Problem:** There is no concept of "Autonomy Levels." The system is either "Ask for everything" or "Do nothing."

3. **The Solution (Tiered Autonomy):** 
   - We need to replace the `CORE_FILES` list and the hardcoded `run_shell` block with a `PermissionProfile` mapping.
   - `flash_coder` (or similar agents) should be assigned a `Level 2` or `Level 3` profile, allowing them to execute shell commands in specific directories (e.g., `/tmp/` or `projects/sandbox/`) and write small/medium files without triggering the `request_approval` loop.
   - `architect` or `guardian` agents would remain at `Level 0` (Maximum Friction).

### Proposed Architectural Change: `AutonomyTier` Framework
Instead of a boolean `should_require_approval`, we implement a `get_required_autonomy_level(action, params)` method.

**New Schema for `guardian_manifest.json` or a new `autonomy_policy.json`:**
```json
{
  "agents": {
    "flash_coder": {
      "max_autonomy_level": 3,
      "allowed_paths": ["/mnt/TG_2TB/Projects/Apollo/temp/", "/mnt/TG_2TB/Projects/Apollo/projects/sandbox/"],
      "max_file_size_kb": 50,
      "allow_shell_in_sandbox": true
    },
    "architect": {
      "max_autonomy_level": 0,
      "allowed_paths": ["/mnt/TG_2TB/Projects/Apollo/"],
      "max_file_size_kb": 0,
      "allow_shell_in_sandbox": false
    }
  },
  "levels": {
    "0": "Human Required (Strict)",
    "1": "Human Required (Low Friction/Async)",
    "2": "Agentic (Sandbox Only)",
    "3": "YOLO (Uninhibited)"
  }
}
```

### Implementation Plan
1. **Update `modules/approvals/handler.py`**:
   - Introduce `AgentContext` (passed during action calls).
   - Replace `should_require_approval` with `check_autonomy_compliance(agent_id, action, params)`.
2. **Update `guardian_manifest.json`**:
   - Add the `agents` configuration.
3. **Refactor `request_approval`**:
   - Only trigger the GUI/Polling if `agent_autonomy_level < required_level`.
