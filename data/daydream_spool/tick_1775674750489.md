# Architectural Audit Report: Complexity Collapse & Routing Integrity

## 1. Executive Summary
An investigation triggered by a subconscious epiphany has identified a critical structural vulnerability in the **Cognitive Dispatcher (CDP)**. The current routing mechanism relies on a low-parameter "logic kernel" (0.6B model) to classify task complexity. This creates a "complexity collapse" loop: the small model lacks the structural capacity to recognize high-level complexity, leading to the misclassification of complex tasks as simple/moderate. This results in high-parameter tasks being routed to low-parameter workers, causing reasoning degradation and "poisoning" the broader lab architecture.

## 2. Findings
### 2.1 Root Cause Analysis
- **Location:** `modules/cognitive_dispatcher.py`, method `_llm_triage`.
- **Mechanism:** The `_llm_triage` function uses `self._worker_config` (a 0.6B model) to perform task classification.
- **Failure Mode:** When a user provides a prompt that requires deep architectural reasoning (e.g., "Refactor the entire VFS layer to support multi-tenant isolation"), the 0.6B model may fail to recognize the depth of the request, returning `SIMPLE` or `MODERATE`. The dispatcher then routes the task to the `WORKER` tier, which is fundamentally incapable of executing the request, leading to a failure loop.

### 2.2 Impact Assessment
- **Systemic Risk:** High. The "intelligence" of the Sovereign Engine is gated by a gatekeeper that is itself prone to the limitations it is meant to manage.
- **Data Integrity:** Medium. Misrouted tasks can lead to hallucinated code or incorrect system state updates.

## 3. Proposed Architectural Update: The "Auditor" Pattern

### 3.1 Implementation Plan
We will implement a secondary validation step within the `CognitiveDispatcher`. Instead of a single-pass triage, we will introduce a "High-Parameter Auditor" (the 35B model) to validate ambiguous or high-risk classifications.

### 3.2 Code Change Proposal (Target: `modules/cognitive_dispatcher.py`)

**Current Logic:**
```python
def _llm_triage(self, user_input: str) -> TaskComplexity:
    # ... (Uses worker_config to classify)
```

**Proposed Logic:**
```python
def _llm_triage(self, user_input: str) -> TaskComplexity:
    # 1. Attempt fast triage with Worker Tier (0.6B)
    try:
        response = query_llm(
            prompt=prompt,
            system_message="You are a task classifier. Return ONLY the complexity level.",
            config=self._worker_config,
            max_tokens=100
        )
        
        # 2. Identify "Ambiguous" or "High-Risk" results
        # If the worker suggests MODERATE or if the prompt contains high-complexity keywords
        is_ambiguous = any(word in user_input.lower() for word in ['architect', 'refactor', 'system', 'design'])
        
        if is_ambiguous or response in ["MODERATE", "COMPLEX"]:
            # 3. Trigger the Auditor (35B) to validate
            audit_response = query_llm(
                prompt=f"Validate if this task is COMPLEX: {user_input}",
                system_message="You are a High-Parameter Auditor. Confirm if the task requires deep reasoning. Return ONLY 'COMPLEX' or 'NOT_COMPLEX'.",
                config=self._architect_config,
                max_tokens=50
            )
            if "COMPLEX" in audit_response:
                return TaskComplexity.COMPLEX
        
        # ... (rest of existing logic)
```

## 4. Conclusion
By implementing the Auditor pattern, we decouple the *classification* of complexity from the *execution* of the task, ensuring that the 35B model acts as a structural safeguard against the "complexity collapse" of the 0.6B logic kernel.
