# Architectural Audit Report: Structural Syntax & Component Existence

## 1. Executive Summary
Following the "Epiphany" regarding the fragility of system identity, an audit was conducted to investigate `KeyError` and "missing node" phenomena. The investigation confirms that component "existence" within the Apollo ecosystem is strictly tied to the structural alignment of identifiers within configuration manifests (specifically `profiles.json`). A mismatch between a component's logical name and its manifest key results in a "vanishing" component, manifesting as a `KeyError`.

## 2. Findings

### 2.1 Identified Discrepancy
- **Symptom:** `KeyError: 'qwen35'` detected in `legacy_vault/logs/vllm_engine.log`.
- **Root Cause:** The system attempted to access a profile identified as `qwen35`. However, in the current `profiles.json` manifest, the Qwen 3.5 model is registered under the key `"architect"`.
- **Mechanism of Failure:** The component exists physically (the model file is present) and logically (the configuration is defined), but because the *structural syntax* (the key name) does not match the *invocation syntax* (the requested name), the component fails to manifest in the runtime environment.

### 2.2 Structural Integrity Audit
- **`profiles.json`**: Syntactically valid. The schema is consistent.
- **`orchestrator.py`**: The `ServiceOrchestrator.get_profile` method correctly validates keys but raises a `ValueError` for unknown profiles. The `KeyError` observed in logs suggests that legacy components are accessing the dictionary directly or via a different mechanism that bypasses the orchestrator's safety checks.

## 3. Architectural Proposals

### 3.1 Implementation of an Alias Registry
To prevent "vanishing" components during transitions from legacy to modern orchestration, implement an alias mapping within `profiles.json`.

**Proposed `profiles.json` Update:**
```json
{
  "profiles": {
    "architect": {
      "aliases": ["qwen35", "qwen_3_5", "primary_llm"],
      "description": "Sovereign Architect Gemma 4 26B MoE...",
      ...
    }
  }
}
```

### 3.2 Orchestrator Enhancement
Update `orchestrator.py` to resolve aliases during the `get_profile` call.

**Proposed Code Change in `orchestrator.py`:**
```python
def get_profile(self, profile_name: str) -> Dict[str, Any]:
    profiles = self.profiles.get("profiles", {})
    
    # 1. Direct match
    if profile_name in profiles:
        return profiles[profile_name]
    
    # 2. Alias match
    for name, config in profiles.items():
        if profile_name in config.get("aliases", []):
            return config
            
    raise ValueError(f"Unknown profile: {profile_name}")
```

## 4. Conclusion
The system's identity is indeed fragile. The "existence" of a component is a function of its name matching its structural definition. By implementing an alias resolution layer, we can harden the system against identity fragmentation and ensure that components remain "manifest" even when referred to by legacy or alternative identifiers.
