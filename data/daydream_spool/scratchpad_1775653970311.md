# Investigation Log: Epiphany - Tool Identity vs. Location
## Timestamp: 2025-02-27
## Status: Initializing Audit

### Hypothesis
The 'gemini' tool (and potentially others) relies on local files (e.g., `.env`, `config.json`, or specific API key files) located within its own directory or the CWD. When the tool is invoked from a different directory, it fails to find these markers, triggering a "wizard" or initialization loop.

### Audit Plan
1.  **Locate 'gemini' tool source code:** Find where the Gemini integration is defined.
2.  **Analyze configuration loading:** Check how it loads API keys and credentials.
3.  **Identify CWD dependency:** Confirm if it uses `os.getcwd()` or relative paths for sensitive configuration.
4.  **Scan other tools:** Check `llm_interface.py` or other tool-related files for similar patterns.
5.  **Propose Decoupling:** Design a migration to XDG-compliant paths (e.g., `~/.config/apollo/`).

---
### Findings from Grep
- The `gemini` CLI appears to use `~/.gemini/settings.json` for configuration.
- There are references to hardcoded paths like `/home/mark/gemini/...` and `/home/gemini/Project-Apollo/...`.
- The `Dev_Log` suggests that the `gemini` CLI might be experiencing issues when run in nested subprocesses, potentially due to file locks on its internal SQLite history database or authentication/rate-limit locks.
- The "Epiphany" mentions a collision between location and identity. The grep results show a heavy reliance on specific user paths (`/home/mark/gemini/...`), which strongly supports the idea that the tool is not location-agnostic.

### Next Steps
1.  **Investigate `llm_interface.py`:** This is likely the primary interface for LLM calls within the Apollo codebase. I need to see how it handles credentials and if it's hardcoded to specific paths.
2.  **Check for `gemini` CLI source/wrapper:** If there's a local `gemini` wrapper or script in the `bin/` or `tools/` directory, I need to examine it.
3.  **Verify XDG compliance:** Check if any existing tools use `~/.config/` or similar.
### Analysis of `llm_interface.py`
- The `llm_interface.py` file uses a `DEPLOYMENT_CONFIGS` dictionary (lines 37-57) which contains hardcoded URLs and model names.
- The `api_key` is currently hardcoded in the `remote` config (line 47: `"api_key": "your-api-key-here"`).
- While `llm_interface.py` itself doesn't explicitly call `os.getcwd()`, the `DEPLOYMENT_CONFIGS` are static. If a user wants to change the API key or the endpoint, they have to modify the source code or rely on the `ACTIVE_DEPLOYMENT` being set correctly.
- The "Epiphany" specifically mentions the `gemini` tool. The `grep` results showed that the `gemini` CLI uses `~/.gemini/settings.json`.
- The `llm_interface.py` is a *wrapper* for LLM calls, but the `gemini` tool mentioned in the epiphany seems to be a separate entity (likely a CLI tool) that is being used by the Apollo system.

### Refined Hypothesis
The `gemini` CLI tool is likely a standalone Python script or binary that looks for its configuration in `~/.gemini/settings.json` or a local `.env` file. The "collision between location and identity" suggests that when the tool is run, it might be looking for its configuration relative to its own installation path or the CWD, rather than a stable, user-defined path.

### Next Steps
1.  **Search for the `gemini` CLI source:** I need to find the actual script that provides the `gemini` command. It might be in `bin/`, `scripts/`, or `tools/`.
2.  **Examine the `gemini` CLI code:** Once found, I will check how it loads its configuration and API keys.
3.  **Check for `~/.gemini/settings.json` usage in the codebase:** See if any other parts of the system are trying to interact with this file.
4.  **Propose a unified configuration management system:** Move away from `~/.gemini/` and towards a more standard `~/.config/apollo/` approach for all tools.
