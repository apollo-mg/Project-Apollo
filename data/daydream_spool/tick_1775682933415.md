# Architectural Audit: Resurrection Tolerance & Memory Consistency

## 1. Executive Summary
The investigation into the tension between 'stable vectors' and 'TTL-based purging' confirms that the current architecture is heavily biased toward **efficiency of the present**. The system uses a simple `Map`-based `InMemoryStore` with immediate, destructive deletions. This creates a significant architectural vulnerability: **Zombie Data Re-animation**.

## 2. Identified Vulnerability: Zombie Data
Because `MemoryStore.delete(key)` performs a hard `Map.delete()`, the system loses all record of the deletion. In distributed or high-latency scenarios (e.g., late-arriving writes or clock skew), a write that was intended to be superseded by a deletion can "resurrect" the key, leading to inconsistent state across agents.

**Current Risk Profile:**
- **Causal Certainty:** Low. The system lacks vector clocks or versioned history.
- **Resurrection Tolerance:** Zero. There is no mechanism to distinguish a new write from a late-arriving write following a deletion.
- **Operational Risk:** High for complex, long-running multi-agent tasks where state consistency is critical for task dependency resolution.

## 3. Proposed Architectural Shift: The "Tombstone Window"
To mitigate the risk of zombie data without the massive overhead of a full causal history (stable vectors), I propose implementing a **Tombstone-based Deletion Strategy**.

### Proposed Thresholds
- **Resurrection Tolerance (Tombstone TTL):** 24 Hours.
- **Consistency Model:** Eventual Consistency with Causal Protection (via Tombstones).

### Implementation Specification
1.  **Metadata Extension**: Update `MemoryEntry` to include an optional `deletedAt: Date` field.
2.  **Soft Deletion**: Modify `MemoryStore.delete(key)` to:
    - Set `deletedAt = new Date()`.
    - Retain the entry in the `Map` to act as a "tombstone".
3.  **Read Logic**: Update `MemoryStore.get(key)` to return `null` if `deletedAt` is present.
4.  **Write Conflict Resolution**: Update `MemoryStore.set(key, value, metadata)`:
    - If the existing entry has a `deletedAt` timestamp, compare the new write's timestamp (if provided in metadata) against `deletedAt`.
    - If `newWrite.timestamp < deletedAt`, **reject the write** to prevent resurrection.
5.  **Hard Purge (The TTL Component)**: Implement a background `purge()` task that performs `this.data.delete(key)` only for entries where `deletedAt` is older than the `TOMBSTONE_TTL`.

## 4. Conclusion
The current "efficiency-first" approach is insufficient for the lab's trajectory toward complex, multi-agent orchestration. Moving to a tombstone-based model provides the necessary "Resurrection Tolerance" to prevent data re-animation while maintaining the performance benefits of an eventual consistency model.

**Status:** Ready for implementation in the next architectural sprint.
**Recommendation:** Prioritize the `MemoryStore` update before expanding the `SharedMemory` capabilities.
