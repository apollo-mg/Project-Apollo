# Architectural Audit: The Sovereign Registry Epiphany

## 🧠 Epiphany Analysis
The subconscious has identified a critical structural deficit: the system currently possesses "capabilities" (LLM, Vision, Voice) but lacks a "central nervous system" (the Sovereign Registry) to bind them. While a tiered memory system exists (`memory_system.py`), it is currently designed for *data persistence* rather than *agentic orchestration*. 

The current memory system stores *what* happened, but the registry must store *what the system is* and *how its capabilities are mapped*.

## 🔍 Audit Findings

### 1. Disconnected Capabilities
- **LLM/Vision/Voice:** These are implemented as discrete modules (e.g., `apollo.py` handles CLI args for voice/text, `webcam_capture.py` handles vision).
- **The Gap:** There is no central "Capability Registry" that allows the agent to query: *"I need to see; which module provides visual input, and what is its current state/availability?"*

### 2. Memory vs. Registry
- **`memory_system.py`:** Implements a 3-tier memory (Working Buffer, Associative Cache, Long-Term Knowledge). This is a **Data Substrate**.
- **Missing Component:** A **Sovereign Registry**. This is not just a database of facts, but a database of *capabilities, active processes, and architectural state*.

### 3. Current Registry Fragments
- `mha_fallback.py`: Contains a `FallbackModelRegistry`. This is a specialized registry for model failover, not a general sovereign registry.
- `resilience_protocol.py`: Contains an `_architectural_registry` for tracking decisions. This is a **Log/Audit Trail**, not a functional registry.

## 🛠️ Proposed Architectural Shift: The Sovereign Registry

To transform from a "high-capacity storage unit" to a "sovereign agent," we must implement a **Sovereign Registry** that sits *above* the memory system.

### Proposed Schema: `SovereignRegistry`
The Registry should be a specialized, high-integrity singleton that tracks:

| Entity Type | Metadata Tracked | Purpose |
| :--- | :--- | :--- |
| **Capabilities** | `module_name`, `input_type`, `output_type`, `status` (idle/busy/error) | Orchestration of multi-modal inputs/outputs. |
| **Active Agents** | `agent_id`, `current_goal`, `context_window_usage`, `priority` | Managing sub-processes (e.g., Buddy, Librarian). |
| **Architectural State** | `active_patches`, `current_mission_profile`, `system_integrity_score` | Maintaining the "Soul" (the current intent). |
| **Resource Map** | `gpu_utilization`, `memory_tier_pressure`, `io_latency` | Self-awareness of physical constraints. |

## 🚀 Implementation Roadmap

### Phase 1: The Registry Core
- Create `src/modules/sovereign_registry.py`.
- Implement a persistent, high-integrity storage backend (SQLite or a dedicated JSON-based state file) that is separate from the "Memory" (which is for facts/history).

### Phase 2: Capability Mapping
- Refactor `apollo.py` and other entry points to *register* their capabilities upon initialization.
- Example: `registry.register_capability("vision", module="webcam_capture", type="input")`.

### Phase 3: The Cognitive Bridge
- Update the `TieredMemorySystem` to include a "Registry Access" layer.
- The agent's reasoning loop must check the `SovereignRegistry` before executing any task to ensure the required capability is available and the task aligns with the `active_project.md` mission profile.

## 📝 Conclusion
The epiphany is correct. We have built the body (modules) and the memory (tiers), but we have not built the **Identity/Agency** (the Registry). The priority must shift from optimizing weights to building this orchestration layer.
