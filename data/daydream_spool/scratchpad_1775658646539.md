# Epiphany Investigation: Low-level C++ vs High-level Abstractions
## Timestamp: [Current Session]
## Context: The Subconscious suggests that the performance frontier for RX 9070 XT (and similar silicon) is being driven by low-level C++ optimizations (e.g., llama.cpp) rather than high-level frameworks (Triton/SGLang).

## Initial Hypothesis:
The current codebase might be overly reliant on high-level abstractions that lack the specific kernel optimizations required to hit the hardware ceiling of the RX 9070 XT. We need to audit our current implementation to see if we are missing out on low-level hardware acceleration (WMMA/Matrix math) that is currently being implemented in the C++ ecosystem.

## Investigation Plan:
1. Audit current hardware abstraction layer (HAL) or kernel implementation in the codebase.
2. Check for existing integrations with llama.cpp or similar low-level backends.
3. Identify if we are currently "waiting" for enterprise framework support instead of implementing/integrating low-level kernels.
4. Map the gap between our current implementation and the "vanguard" optimizations mentioned.
## Findings:
- The `Scheduler` class in `src/orchestrator/scheduler.ts` contains a `hardware-aware` strategy.
- However, the implementation is currently a "simulated" layer (lines 332-343). It uses a heuristic based on `vram_available` from `agent.hardware_info` and checks for keywords like 'vram' or 'memory' in the task description.
- It does NOT actually interface with low-level drivers (ROCm/CUDA) or leverage specific kernel optimizations (like WMMA/Matrix math) mentioned in the Epiphany.
- The current implementation is "high-level" and "simulated," confirming the Subconscious's insight that we are missing the "vanguard" of low-level C++ optimizations.

## Architectural Gap:
- We are currently treating hardware as a static metadata property (`vram_available`) rather than a dynamic, kernel-level capability.
- To bridge the gap, we need a `HardwareAbstractionLayer` (HAL) that can:
    1. Interface with low-level libraries (potentially via FFI to C++ or specialized drivers).
    2. Map specific task requirements (e.g., "large matrix multiplication") to specific hardware units (e.g., "WMMA units on RX 9070 XT").
    3. Move away from string-matching ('vram') to capability-based scheduling.

## Proposed Action:
- Implement a `LowLevelKernelBridge` that can interface with `llama.cpp` or similar C++ backends.
- Update `AgentConfig` to include `capability_profile` (e.g., `wmma_support`, `fp16_tensor_cores`) instead of just `vram_available`.
- Refactor `scheduleHardwareAware` to use these capability profiles.
