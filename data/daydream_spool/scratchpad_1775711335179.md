## Findings: `src/hardware/hardware_orchestrator.py`
- This file is clearly intended to be the 'Senses' layer (Hardware Abstraction).
- It manages audio, camera, and sensors.
- It uses `HIPKernelSynchronizationBarrier` for thread-safe hardware access.
- **Conflict Identified:** While `hardware_orchestrator.py` is designed to be the abstraction layer, `src/agent/agent.py` (the 'Self') is bypassing this layer entirely by performing its own hardware detection via `subprocess.run(['nvidia-smi', ...])`.

## Architectural Violation Summary
The 'Self' (`src/agent/agent.py`) has "leaked" hardware-sensing logic into its core reasoning/initialization domain. Instead of querying the `HardwareOrchestrator` (the 'Senses') for system capabilities, it is performing low-level OS/driver calls itself. This creates a direct dependency on the hardware implementation (NVIDIA/nvidia-smi) within the 'Self' layer, violating the principle of agnosticism.

## Proposed Remediation
1.  **Move Hardware Detection to `src/hardware/`**: The logic in `HardwareResourceChecker` (specifically the `_detect_hardware` and `_estimate_vram_from_model` methods) should be moved to `src/hardware/hardware_orchestrator.py` or a new specialized driver module within `src/hardware/`.
2.  **Expose Capabilities via Orchestrator**: The `HardwareOrchestrator` should provide a method (e.g., `get_system_capabilities()`) that returns the VRAM, memory, and driver information.
3.  **Refactor `Agent`**: The `Agent` class should depend on the `HardwareOrchestrator` interface to perform its MHA (Model-to-Hardware Alignment) checks, rather than implementing its own detection logic.
