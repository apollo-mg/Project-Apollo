# Architectural Audit: Pivot to Triton-Native Backend

## 1. Executive Summary
The current development trajectory for the Sovereign Engine is heavily weighted toward stabilizing the HIP/C++ software stack. However, historical logs and codebase analysis reveal significant hardware-level instability (ROCm/HIP/RDNA 4) and "silent data corruption." This confirms that the current approach of "fixing" the legacy stack is a losing battle against the architectural mismatch between Wave64-optimized HIP and RDNA 4's specific requirements.

**Recommendation:** Immediate pivot from HIP-compatibility to a Triton-native compute backend.

## 2. Findings & Evidence
- **Hardware Instability:** Logs in `tmp/open-multi-agent/synthesizer_batch.log` explicitly document ROCm/HIP kernel errors and RDNA 4 instability.
- **Legacy Friction:** The codebase contains extensive legacy C++ and OpenCL kernels (e.g., `whisper.cpp/ggml`) which act as "ghosts"—adding complexity without providing the performance benefits required for RDNA 4.
- **Existing Infrastructure:** The environment already contains `torch/_inductor` Triton templates (e.g., `triton_mm_rocm.py.jinja`), providing a ready-made path for JIT-driven abstraction.

## 3. Proposed Architectural Shift

### Current State (Legacy/HIP)
- **Flow:** Python $\rightarrow$ HIP/C++ Kernels $\rightarrow$ ROCm Driver $\rightarrow$ RDNA 4 Hardware.
- **Problem:** High friction, manual kernel management, and difficulty mapping RDNA 4 wavefronts to Wave64-optimized C++ code.

### Proposed State (Triton-Native)
- **Flow:** Python $\rightarrow$ Triton JIT $\rightarrow$ `gfx1201` Assembly $\rightarrow$ RDNA 4 Hardware.
- **Benefit:** Bypasses the brittle HIP/C++ middle layer. Uses JIT to dynamically optimize kernel execution for the specific wavefront characteristics of RDNA 4.

## 4. Implementation Roadmap (Draft)
1. **Deprecate HIP-Kernel Maintenance:** Cease all efforts to debug or optimize existing C++ kernels for RDNA 4.
2. **Triton Integration:** Implement a new `TritonComputeBackend` that utilizes `torch.inductor` and custom Triton kernels.
3. **Targeted JIT Optimization:** Focus on mapping high-level tensor operations directly to `gfx1201` assembly via Triton's JIT, specifically targeting the RDNA 4 memory hierarchy.
4. **Validation:** Use the existing `synthesizer_batch.log` error patterns as a baseline to verify that the Triton-native approach resolves the "silent data corruption" and "RMS Norm" errors.

## 5. Conclusion
The Sovereign Engine must stop fighting the legacy stack. By embracing Triton-native JIT compilation, we move from a reactive "fix-the-driver" posture to a proactive "target-the-hardware" architecture.
