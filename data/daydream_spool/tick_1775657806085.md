# Architectural Audit & Proposal: Quantization-Aware Model Provisioning

## 1. Executive Summary
The subconscious identified a systemic bottleneck: the system is currently trapped in a "rhythmic, sequential survival" mode, where VRAM thresholds trigger frequent, high-latency model swaps. This is caused by a lack of precision-scaling capabilities. The current architecture treats model loading as a binary state (present/absent) rather than a spectrum of memory-to-performance trade-offs.

## 2. Current State Audit
- **VRAM Management:** `vram_management.py` uses a reactive threshold (`VRAM_THRESHOLD_MB = 14500`) to trigger `unload_comfy_vram`.
- **Provisioning:** `model_provisioner.sh` and `model_manifest.json` are primitive. They support only single-file downloads per model entry, with no concept of model variants or quantization levels.
- **Bottleneck:** When VRAM is exceeded, the system unloads models and reloads them. Because it only knows how to load the primary (likely high-precision) version, the reload cycle is heavy and slow, leading to the "Slow and Steady" latency pattern.

## 3. Proposed Architectural Shift: "Dynamic Precision Scaling"

### A. Manifest Evolution (The "Variant" Pattern)
Transition `model_manifest.json` from a flat list of files to a hierarchical structure of model IDs and their associated precision variants.

**Proposed Schema:**
```json
{
  "models": [
    {
      "id": "flux_dev",
      "name": "Flux.1 Dev",
      "variants": [
        {
          "precision": "fp16",
          "url": "https://...",
          "filename": "flux_fp16.safetensors",
          "vram_requirement_mb": 24000
        },
        {
          "precision": "gguf_q4_k_m",
          "url": "https://...",
          "filename": "flux_q4_k_m.gguf",
          "vram_requirement_mb": 12000
        }
      ]
    }
  ]
}
```

### B. Provisioning Logic Update
Update `model_provisioner.sh` to iterate through the `variants` array. This allows the system to pre-cache multiple versions of the same model (e.g., a high-fidelity version and a "survival" version).

### C. Intelligent Orchestration (The "VRAM-Aware Switch")
Integrate the `vram_management.py` telemetry with the model loading logic in `orchestrator.py` or `task_manager.py`.

**Logic Flow:**
1. **Check VRAM:** Before loading a model, query `get_vram_usage()`.
2. **Decision Matrix:**
   - If `Free VRAM > Model_FP16_Requirement`: Load `fp16` variant.
   - If `Free VRAM < Model_FP16_Requirement` AND `Free VRAM > Model_GGUF_Requirement`: Load `gguf` variant.
   - If `Free VRAM < Model_GGUF_Requirement`: Trigger `unload_comfy_vram()` and wait for flush.

## 4. Implementation Roadmap
1. **Phase 1 (Data):** Refactor `model_manifest.json` to support the variant schema.
2. **Phase 2 (Provisioning):** Update `model_provisioner.sh` to handle nested variant objects.
3. **Phase 3 (Runtime):** Modify the model loading interface (likely in `llm_interface.py` or the ComfyUI bridge) to accept a `precision` parameter.
4. **Phase 4 (Intelligence):** Connect `vram_management.py` telemetry to the selection logic to automate the switch between precision levels.

## 5. Expected Outcome
By trading off a marginal amount of model fidelity for significantly lower VRAM footprints, we will:
- Reduce the frequency of `unload_comfy_vram` calls.
- Decrease the latency of model swaps.
- Transition from "sequential survival" back toward "parallel, fluid execution."
