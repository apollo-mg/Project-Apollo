# Architectural Proposal: Mitigating the "Translation Tax"

## 1. Executive Summary
The transition from general-purpose GPU stacks (ROCm/HIP) to specialized AI accelerators (Tenstorrent) shifts the engineering bottleneck from **environment stability** to **mathematical translation**. This proposal outlines a framework to quantify and manage this "Translation Tax" through a formal Hardware Abstraction Layer (HAL).

## 2. Problem Statement
Current architectural focus is on high-level agent orchestration. However, as we move toward specialized hardware, the complexity of mapping high-level model operators to specific hardware primitives (e.g., TT-Buda) becomes a primary source of friction. Without a formal assessment mechanism, we risk committing to hardware that requires prohibitive engineering effort for "operator legalization."

## 3. Proposed Solution: The Translation Tax Framework

### A. Primitive Registry (`src/hardware/primitive_registry.ts`)
A centralized registry that defines the "Geometry" of the target hardware.
- **Standard Operators**: The set of mathematical operations required by target models (e.g., `Conv2D`, `Attention`, `GELU`).
- **Hardware Primitives**: The atomic operations supported by the target compiler (e.g., `TT-Buda` primitives).
- **Mapping Matrix**: A lookup table defining how standard operators are decomposed into primitives.

### B. Legalization Engine (`src/hardware/legalization_engine.ts`)
A service that performs a "Translation Tax Assessment" on a given computational graph.
- **Input**: A model graph (ONNX, TorchScript, etc.).
- **Process**:
    1. Traverse the graph.
    2. For each node, query the `Primitive Registry`.
    3. Calculate the "Tax" based on:
        - **Direct Match**: 0 tax.
        - **Decomposition Required**: Moderate tax (complexity of the decomposition).
        - **Unsupported/Custom Kernel Required**: High tax (requires manual kernel writing).
- **Output**: A `TranslationTaxReport` containing a complexity score and a list of "High-Friction Operators."

### C. Integration into Deployment Pipeline
The `LegalizationEngine` will be integrated into the pre-deployment phase. Before a model is committed to a specific hardware target, the system will run a simulation to predict the engineering labor required for legalization.

## 4. Implementation Roadmap

| Phase | Task | Description |
| :--- | :--- | :--- |
| **Phase 1** | **Registry Definition** | Define the first set of primitives for Tenstorrent/TT-Buda. |
| **Phase 2** | **Engine Development** | Implement the graph traversal and tax calculation logic. |
| **Phase 3** | **Validation** | Run the engine against existing model architectures to validate the "Tax" accuracy. |

## 5. Conclusion
By formalizing the "Translation Tax," we transform a qualitative engineering risk into a quantitative architectural metric. This allows for data-driven hardware selection and prevents "Complexity Migration" from becoming an unmanaged bottleneck.
