# Architectural Audit: Precision Baseline Protocol

## Epiphany Analysis
The subconscious daemon has identified a critical tension in our current operational model: the conflict between **acoustic/model precision** and **VRAM constraints (16GB ceiling)**. 

Currently, the system risks "Cognitive Dissonance" (instability/OOM) by attempting to negotiate hardware limits through quantization or low-precision optimizers, which degrades the model's "voice" (output quality).

## Audit Findings
1.  **Hardware-Aware Scheduling:** The `Scheduler` class in `src/orchestrator/scheduler.ts` already contains a `hardware-aware` strategy. However, it is currently a simulation/stub that relies on `(agent as any).hardware_info`.
2.  **Precision Gap:** There is no explicit logic in the current codebase to enforce a "Precision Baseline." The system treats VRAM as a scheduling constraint but does not explicitly protect the optimizer precision (e.g., forcing 32-bit Adam) when datasets are small/manageable.
3.  **Risk Vector:** The `hardware-aware` strategy (lines 325-359) uses a heuristic based on `task.description` containing "vram" or "memory". This is fragile and prone to the "noise of quantization" mentioned in the epiphany.

## Proposed Architectural Update: Precision Baseline Protocol

### 1. Implementation of `PrecisionBaseline` Logic
We must move away from purely heuristic-based VRAM management. I propose a new configuration layer within the `AgentConfig` or a global `OrchestratorConfig` that defines the `PrecisionBaseline`.

**Proposed Change to `AgentConfig` (in `src/types.ts`):**
```typescript
export interface AgentConfig {
  // ... existing fields
  /** 
   * If true, the system will prioritize 32-bit precision for optimizers 
   * and modulate batch size to fit within VRAM constraints, 
   * rather than defaulting to lower-precision (FP16/BF16) optimizers.
   */
  enforcePrecisionBaseline?: boolean;
}
```

### 2. Refined Hardware-Aware Scheduling
The `scheduleHardwareAware` method in `src/orchestrator/scheduler.ts` should be updated to prioritize agents capable of maintaining the `PrecisionBaseline`.

**Proposed Logic Update:**
Instead of just checking for "vram" in the description, the scheduler should:
1.  Identify if the task/agent requires `enforcePrecisionBaseline`.
2.  Calculate the `required_vram_for_fp32` (which is significantly higher than `fp16`).
3.  If `available_vram < required_vram_for_fp32`, the scheduler must **not** simply assign the task to a lower-precision agent; it must instead **throttle the batch size** or **queue the task** until sufficient VRAM is released.

### 3. Actionable Code Change (Draft)
In `src/orchestrator/scheduler.ts`, update the `scoredAgents` calculation:

```typescript
// PROPOSED REPLACEMENT FOR LINES 344-349
```

## Conclusion
The "ritual of stability" requires us to treat VRAM as a hard boundary for **batch size modulation** rather than a trigger for **precision degradation**. By implementing the `PrecisionBaseline` protocol, we ensure that the model's voice remains uncompromised by the noise of quantization.
