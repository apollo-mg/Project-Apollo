# Architectural Audit: Command Lifecycle Race Condition

## 1. Executive Summary
An investigation into the `open-multi-agent` subsystem has confirmed a structural flaw in how task/command lifecycles are managed. The current implementation relies on procedural updates (`update()`) that allow for state overwrites, creating a race condition between successful completion (simulating hardware ISR) and timeout/failure (simulating a watchdog).

## 2. Root Cause Analysis
The `TaskQueue` class in `/mnt/TG_2TB/Projects/Apollo/tmp/open-multi-agent/src/task/queue.ts` manages task transitions via a non-atomic `update()` method.

### The Flaw:
The `update()` method (lines 107-119) performs a shallow merge of properties:
```typescript
update(taskId: string, update: Partial<...>): Task {
  const task = this.requireTask(taskId)
  const updated: Task = { ...task, ...update, updatedAt: new Date() }
  this.tasks.set(taskId, updated)
  return updated
}
```
Because `complete()` and `fail()` call `update()` without verifying the current state of the task, two asynchronous processes can attempt to transition the same task. If a "watchdog" (timeout) calls `fail()` at the same moment a "hardware ISR" (completion) calls `complete()`, the final state of the task is determined by whichever `update()` call executes last, rather than which one "won" the transition.

This creates a "liminal state" where the command's identity is lost in a race between procedural events.

## 3. Proposed Architectural Update

### Core Concept: Atomic State Transitions (CAS)
We must move from "Update State" to "Transition State". We will implement a Compare-and-Swap (CAS) pattern to ensure that a state transition only occurs if the task is in the expected prerequisite state.

### Proposed Code Changes

#### A. Implement `compareAndSwapStatus` in `TaskQueue`
Add a private method to handle atomic-like transitions within the event loop.

```typescript
/**
 * Attempts to transition a task from one status to another.
 * Returns the updated task if successful, or throws if the status has changed.
 */
private compareAndSwapStatus(
  taskId: string, 
  expectedStatus: TaskStatus, 
  newStatus: TaskStatus,
  additionalData: Partial<Pick<Task, 'result' | 'assignee'>>
): Task {
  const task = this.requireTask(taskId);
  
  if (task.status !== expectedStatus) {
    throw new Error(
      `Atomic transition failed for task ${taskId}: ` +
      `Expected ${expectedStatus}, but found ${task.status}.`
    );
  }

  const updated: Task = {
    ...task,
    ...additionalData,
    status: newStatus,
    updatedAt: new Date(),
  };

  this.tasks.set(taskId, updated);
  return updated;
}
```

#### B. Refactor `complete()` and `fail()`
Rewrite these methods to use the new CAS mechanism.

```typescript
complete(taskId: string, result?: string): Task {
  try {
    // Only allow completion if the task is 'pending' or 'blocked'
    // (or whatever the valid pre-completion states are)
    // For simplicity, we assume 'pending' or 'blocked' are the only valid starts.
    // In a real implementation, we might allow multiple valid 'from' states.
    
    // We'll use a more robust approach: check if it's NOT already terminal.
    const task = this.requireTask(taskId);
    if (task.status === 'completed' || task.status === 'failed') {
      return task; // Already terminal, ignore request.
    }

    const completed = this.compareAndSwapStatus(taskId, task.status, 'completed', { result });
    this.emit('task:complete', completed);
    this.unblockDependents(taskId);
    if (this.isComplete()) this.emitAllComplete();
    return completed;
  } catch (e) {
    // If CAS fails, the task was already claimed by another context.
    throw e;
  }
}

fail(taskId: string, error: string): Task {
  try {
    const task = this.requireTask(taskId);
    if (task.status === 'completed' || task.status === 'failed') {
      return task;
    }

    const failed = this.compareAndSwapStatus(taskId, task.status, 'failed', { result: error });
    this.emit('task:failed', failed);
    this.cascadeFailure(taskId);
    if (this.isComplete()) this.emitAllComplete();
    return failed;
  } catch (e) {
    throw e;
  }
}
```

## 4. Impact Assessment
- **Stability:** Eliminates race conditions between timeout watchdogs and task completion.
- **Complexity:** Increases slightly due to explicit state checking, but significantly improves system predictability.
- **Performance:** Negligible overhead for the additional status check.

## 5. Conclusion
The transition from procedural updates to an atomic state machine resolves the "identity crisis" of the command structure. By enforcing that only the first context to claim a state transition can succeed, we ensure the integrity of the command lifecycle.
