# Architectural Audit: RDNA 4 Stability & Functional Compromise

## 1. Executive Summary
The investigation confirms the "Epiphany" regarding the current state of RDNA 4 deployment. The system is currently operating under a "functional compromise" where performance is sacrificed for stability. The mismatch between the vLLM optimizer's assumptions and the RDNA 4 Wave32 execution model leads to hardware-level instability (specifically "RMS Norm" errors and silent data corruption), as evidenced in `synthesizer_batch.log`.

## 2. Findings

### 2.1 Hardware Instability
- **Evidence:** `synthesizer_batch.log` reports: `Hardware-level instability (ROCm/HIP/RDNA 4) is causing silent data corruption and "RMS Norm" errors.`
- **Root Cause:** The attempt to use advanced optimization techniques (like graph capture) on RDNA 4 hardware is currently incompatible with the underlying Wave32 execution model used by the vLLM optimizer.

### 2.2 The "Software Bridge" & Eager Mode
- **Current State:** The orchestration layer (`src/orchestrator/scheduler.ts`) contains a simulated `scheduleHardwareAware` method. It currently relies on a non-existent `hardware_info` property on `AgentConfig`.
- **Eager Mode:** While "Eager Mode" is not explicitly defined in the TypeScript source, the logs and the epiphany suggest it is the operational mode used to bypass the unstable optimization layer. This mode provides the "ability to boot" at the cost of ~20% peak performance.

### 2.3 Optimization Mismatch
- The codebase currently lacks direct integration with vLLM's optimization parameters, suggesting the "bridge" is at the driver/runtime level.
- Attempting to manually bridge the gap between vLLM's graph capture and RDNA 4's execution model is currently a pursuit of diminishing returns due to the fundamental hardware/software mismatch.

## 3. Architectural Proposal

### 3.1 Establish Eager Mode as Stable Baseline
- **Action:** Formally designate "Eager Mode" (non-optimized execution) as the official stable baseline for all RDNA 4 deployments.
- **Implementation:** Update the `AgentConfig` and `Scheduler` to explicitly support an `execution_mode: 'eager' | 'optimized'` flag.

### 3.2 Optimization Freeze
- **Action:** Cease all automated attempts to enable graph capture or vLLM-specific optimizations when RDNA 4 hardware is detected.
- **Implementation:** 
    - Enhance `src/orchestrator/scheduler.ts` to include real hardware detection (via ROCm/HIP queries).
    - If `chip_id` matches RDNA 4, force `execution_mode: 'eager'`.

### 3.3 Hardware-Aware Scheduler Upgrade
- **Action:** Replace the simulated `scheduleHardwareAware` with a production-ready implementation.
- **Implementation:**
    - Update `src/types.ts` to include a robust `HardwareInfo` interface.
    - Implement a real-world query mechanism (e.g., via a shell call to `rocm-smi`) to populate `vram_available` and `chip_id` in the `AgentConfig`.

## 4. Conclusion
The current architecture prioritizes stability over capability. By formalizing this compromise and preventing unstable optimization attempts, we ensure a reliable deployment foundation while waiting for vLLM's Wave32 compatibility.
