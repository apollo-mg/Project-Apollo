# Architectural Audit: Transitioning from Script Sprawl to Parameterized Orchestration

## 1. Current State Analysis: "The Script Graveyard"
The audit of `/mnt/TG_2TB/Projects/Apollo/` confirms the Subconscious Epiphany. The operational layer is currently fragmented into multiple, highly specific shell scripts that duplicate logic and environment configurations.

### Identified Redundancies:
*   **Environment Duplication:** `start_architect.sh`, `start_bonsai.sh`, and `start_turbo.sh` all manually export ROCm stability flags (`HSA_OVERRIDE_GFX_VERSION`, `GGML_HIP_FORCE_MMQ`, etc.).
*   **Configuration Fragmentation:** Model paths, server binaries, ports, and context window sizes are hardcoded into individual files.
*   **Operational Risk:** To launch a different model profile (e.g., switching from "Stability Mode" to "TurboQuant Mode"), the user must physically navigate and execute a different file, increasing the risk of running the wrong configuration in the wrong environment.

### Specific File Mappings:
| Script | Model Profile | Port | Backend/Binary |
| :--- | :--- | :--- | :--- |
| `start_architect.sh` | Gemma 4 26B (Stability) | 8082 | `llama_cpp_gemma4` |
| `start_bonsai.sh` | Bonsai-8B (1-bit KAIROS) | 8083 | `prism_llama_cpp` |
| `start_turbo.sh` | Gemma 4 26B (TurboQuant) | 8082 | `llama_cpp_turboquant` |
| `start_whisper.sh` | Whisper Large v3 | 8080 | `whisper-server` |

## 2. Proposed Architectural Shift: The 'Orchestrator' Model

Instead of managing $N$ scripts, we will implement a single `orchestrator.sh` (or a Python-based `orchestrator.py`) that treats model deployment as a **parameterized service**.

### Proposed Orchestrator Logic:
The new system will use a `profiles.json` to define the "DNA" of each service and a single entry point.

**Command Syntax Example:**
`./orchestrator.sh --profile turbo --port 8082`
`./orchestrator.sh --profile bonsai --port 8083`

### Implementation Blueprint:

#### A. The Configuration Schema (`profiles.json`)
```json
{
  "profiles": {
    "architect_stability": {
      "model": "/mnt/TG_2TB/AI/Models/Gemma 4/unsloth-gemma-4-26B-A4B-it-UD-IQ2_M_(fixed).gguf",
      "binary": "/mnt/TG_2TB/Projects/Apollo/tmp/llama_cpp_gemma4/build/bin/llama-server",
      "env": {
        "HSA_OVERRIDE_GFX_VERSION": "12.0.1",
        "GGML_HIP_FORCE_MMQ": "1",
        "HSA_ENABLE_SDMA": "0"
      },
      "args": ["-c", "65536", "-b", "512", "-ctk", "q8_0", "-ctv", "q4_0"]
    },
    "turbo_quant": {
      "model": "/mnt/TG_2TB/AI/Models/Gemma 4/gemma-4-26B-A4B-it-UD-IQ2_XXS.gguf",
      "binary": "/mnt/TG_2TB/Projects/Apollo/tmp/llama_cpp_turboquant/build_rocm/bin/llama-server",
      "env": {
        "HSA_OVERRIDE_GFX_VERSION": "12.0.1",
        "GGML_HIP_FORCE_MMQ": "1"
      },
      "args": ["-c", "65536", "-b", "512", "-ctk", "q8_0", "-ctv", "turbo3"]
    }
  }
}
```

#### B. The Orchestrator Engine (`orchestrator.sh`)
1.  **Parse Arguments:** Use `getopts` to capture `--profile`, `--port`, and `--host`.
2.  **Load Profile:** Read the corresponding JSON block.
3.  **Inject Environment:** Loop through the `env` block and `export` variables.
4.  **Execute:** Construct the final command string and execute via `nohup` or `systemd`.

## 3. Conclusion & Impact
By moving to parameterization, we achieve:
1.  **Cognitive Load Reduction:** The user manages one tool, not a dozen scripts.
2.  **Operational Integrity:** Environment variables are strictly tied to the model profile, preventing "dirty" environments from causing crashes.
3.  **Scalability:** Adding a new model (e.g., a new Llama-3 variant) becomes a JSON entry rather than a new `.sh` file.

**Status:** *Audit Complete. Ready for implementation of `orchestrator.sh` and deprecation of legacy `start_*.sh` scripts.*
