# Architectural Audit: Adaptive Noise-Floor Detection for Audio Slicing

## 1. Epiphany Analysis
The subconscious daemon identified a critical vulnerability in the audio processing pipeline: the use of a static -34dB threshold for silence detection (slicing). This creates a "brittle" architecture where the system's ability to preserve semantic edges of speech is entirely dependent on a constant, predictable environmental noise floor. In dynamic environments, this leads to either:
1. **Truncation:** High noise floors cause the threshold to cut off the start/end of speech.
2. **Inefficiency:** Low noise floors cause the system to process excessive "dead air," wasting ASR (Automatic Speech Recognition) compute.

## 2. Audit Findings
- **Search Results:** A direct grep for `-34dB` within the `src/` directory returned no matches. This suggests the threshold is either:
    - Hardcoded in a compiled/distressed file (e.g., `dist/`).
    - Defined in a configuration file not currently indexed.
    - Part of a third-party dependency (e.g., `openai` or a local audio utility).
    - Implemented via a different constant or variable name.
- **Codebase State:** The current codebase lacks a dedicated `audio_processing` or `vad` (Voice Activity Detection) module in `src/`. The `src/` directory contains orchestration, task, and agent logic, but the actual signal processing logic appears to be abstracted or missing from the primary source tree.

## 3. Proposed Architectural Update

### Phase 1: Implementation of `AdaptiveNoiseFloor` Module
Create `src/modules/audio/noise_floor.ts` to handle ambient noise estimation.
- **Mechanism:** Use a rolling window of RMS (Root Mean Square) values from the incoming audio stream to calculate the current ambient noise floor.
- **Algorithm:** Implement a slow-moving average for the noise floor to prevent speech signals from being categorized as noise, and a fast-moving average to react to sudden environmental changes.

### Phase 2: Refactoring the Slicing Logic
Replace the static threshold in the slicing module (likely located in a utility or a specialized agent runner) with a dynamic threshold:
`Threshold = Ambient_Noise_Floor + Safety_Margin_dB`

### Phase 3: Integration with ASR Pipeline
Ensure the `AdaptiveNoiseFloor` module is initialized at the start of an audio session to establish a baseline before the first inference request.

## 4. Conclusion
The epiphany is valid. The current "blunt" thresholding is a technical debt that threatens the precision of the entire inference engine. Transitioning to an adaptive mechanism is required to ensure semantic integrity across varying acoustic environments.
