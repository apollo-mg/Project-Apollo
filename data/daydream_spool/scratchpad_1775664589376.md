### Refined Hypothesis
The "Epiphany" likely refers to a specific failure mode in the build process of a Python-based component (possibly a kernel or a driver-related library) that is *not* part of the primary TypeScript codebase. 

The `src/orchestrator/scheduler.ts` file shows that `hardware-aware` scheduling is a planned feature, but the `dependency-first` strategy is currently stubbed out to call `scheduleHardwareAware`. This suggests the system is architecturally prepared for hardware awareness, but the actual implementation of hardware-specific logic (like ROCm) might be where the "build isolation" friction occurs.

The friction described (build isolation vs. specialized hardware) is a classic issue when `pip install` or `setuptools` attempts to build a wheel in a clean environment, failing to find the necessary ROCm/HIP headers/libraries that exist on the host system.

### Conclusion & Proposal
The "Hardware-Aware Build Protocol" should be implemented as a set of guidelines or a CI/CD configuration change. 

**Proposed Architectural Change:**
1.  **Build Configuration:** For any Python package identified as "Hardware-Critical" (e.g., those containing ROCm/HIP/CUDA kernels), the build command must explicitly use `--no-build-isolation`.
2.  **Environment Requirements:** Ensure that the build environment (Docker container or CI runner) has the necessary hardware SDKs (ROCm, CUDA) pre-installed in the system path, rather than relying on `pyproject.toml` to fetch them.
3.  **Detection Logic:** Implement a check in the build script to detect the presence of ROCm/HIP and, if found, automatically switch to a non-isolated build mode to ensure the compiler can link against the host's specialized libraries.
