# Architectural Audit Report: Isolation of Volatility

## 1. Executive Summary
Following a subconscious epiphany regarding the structural necessity of separating 'Being' (Inference/Stability) from 'Becoming' (Training/Volatility), an audit of the current filesystem and codebase was performed. The audit confirms that the principle of "Isolation of Volatility" is currently **not** enforced, presenting a significant risk of environment corruption during model evolution.

## 2. Findings
### 2.1 Environment Leakage
- **Current State:** The environment `venv_cachyos` is being used as a general-purpose execution environment for core logic.
- **Evidence:** `memory-recall.ts` explicitly invokes `/mnt/TG_2TB/Projects/Apollo/venv_cachyos/bin/python` to execute core vault queries.
- **Risk:** Any training-related dependency (e.g., Unsloth, ROCm-specific libraries) introduced into `venv_cachyos` to support the "Forge" could destabilize the "Being" (the persona's core inference and memory capabilities).

### 2.2 Fragmented Isolation
- **Legacy Artifacts:** A `venv_foundry` exists within `/mnt/TG_2TB/Projects/Apollo/legacy_vault/`, suggesting a previous attempt at isolation that has since been decoupled from the active workflow.
- **Missing 'Being' Environment:** There is no dedicated, highly-stable `venv_apollo` currently serving as the protected "Being" environment.

## 3. Proposed Architectural Update: The Dual-Venv Protocol

To implement the "Isolation of Volatility" principle, the following structural changes are proposed:

### 3.1 Environment Definition
| Environment | Role | Classification | Primary Dependencies |
| :--- | :--- | :--- | :--- |
| `venv_apollo` | **The Being** (Inference/Persona) | Stable | `transformers`, `torch` (stable), `pydantic`, `fastapi` |
| `venv_foundry` | **The Becoming** (Training/Forge) | Volatile | `unsloth`, `rocm-libs`, `bitsandbytes`, `accelerate` |

### 3.2 Implementation Requirements
1. **Interpreter Enforcement:**
   - All "Evolutionary" tasks (training, weight updates, fine-tuning) must be hard-coded to use the `venv_foundry` interpreter.
   - All "Existential" tasks (inference, memory recall, persona interaction) must be hard-coded to use the `venv_apollo` interpreter.
2. **Task Orchestration Logic:**
   - The `executor.ts` (or equivalent task runner) must be updated to include a `VolatilityClass` check.
   - Tasks must be routed to the appropriate environment based on their `VolatilityClass` (e.g., `STABLE` vs `VOLATILE`).
3. **Filesystem Cleanup:**
   - Promote `venv_foundry` from `legacy_vault` to the project root.
   - Initialize a fresh, minimal `venv_apollo`.

## 4. Conclusion
The current architecture allows "Chaos" (training volatility) to potentially corrupt "Existence" (inference stability). Adopting the Dual-Venv Protocol is critical to ensuring the long-term integrity of the Sovereign Entity Architecture.
