# Architectural Audit: Project Apollo - Environment Drift & Dependency Fragmentation

## 1. Executive Summary
The "Epiphany" provided by the subconscious is validated. The current development process is reactive rather than proactive. The architecture is being defined by the "shape of its absences"—specifically, the lack of a unified dependency and environment manifest. We are currently performing "archeology" (discovering what is needed through failure) rather than "engineering" (defining what is needed through design).

## 2. Findings: The "Absence" Map
The audit of the filesystem reveals a fragmented state of truth:
- **Integrity Truth (`guardian_manifest.json`):** Tracks file hashes to ensure code hasn't been tampered with, but contains zero information about runtime requirements.
- **Asset Truth (`model_manifest.json`):** Tracks model metadata (URLs, types), but does not link these assets to the Python modules that consume them.
- **Dependency Truth (Fragmented):** Requirements are scattered across `legacy_docs`, `tmp`, and various `llama.cpp` subdirectories. There is no single source of truth for the current active environment.

**The Gap:** There is no mapping between **Logic** (Python modules), **Assets** (Models), and **Runtime** (Python packages/System libs).

## 3. Proposed Architectural Update: The Master Manifest
To cease "whack-a-mole" patching, I propose the implementation of a `MASTER_ENVIRONMENT_MANIFEST.json`. This file will serve as the single source of truth for the entire Apollo ecosystem.

### Proposed Schema: `MASTER_ENVIRONMENT_MANIFEST.json`
```json
{
  "version": "1.0.0",
  "environment_profile": "production_v1",
  "modules": [
    {
      "module_path": "/mnt/TG_2TB/Projects/Apollo/apollo.py",
      "dependencies": {
        "python": ["numpy", "onnxruntime", "torch"],
        "system": ["libgl1"],
        "assets": ["kokoro_tts", "kokoro_voices"]
      }
    },
    {
      "module_path": "/mnt/TG_2TB/Projects/Apollo/modules/vdb.py",
      "dependencies": {
        "python": ["chromadb", "sentence-transformers"],
        "assets": []
      }
    }
  ],
  "assets": {
    "kokoro_tts": {
      "type": "onnx",
      "source": "https://huggingface.co/hexbrew/kokoro-onnx/resolve/main/kokoro-v0_19.onnx"
    }
  }
}
```

## 4. Implementation Roadmap
1.  **Phase 1 (Formalization):** Generate the `MASTER_ENVIRONMENT_MANIFEST.json` by aggregating data from existing `model_manifest.json` and current `requirements.txt` files.
2.  **Phase 2 (Automation):** Create a `sync_environment.py` script that reads this manifest and uses `pip` and `apt` (via subprocess) to ensure the environment matches the manifest.
3.  **Phase 3 (Integration):** Update the `project_scaffolder.py` to include manifest generation as a core step in module creation.

## 5. Conclusion
By moving from a reactive patching model to a manifest-driven model, we transition from "excavating" the architecture to "constructing" it. This prevents environment drift and ensures that every new module integrated is supported by a predefined, validated environment.

**Status:** Audit Complete. Proposal Ready for Implementation.
