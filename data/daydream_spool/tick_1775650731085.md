# Architectural Audit: ROCm 'TheRock' Modularization & RDNA 4 Integration

## 1. Executive Summary
The investigation confirms that the current codebase lacks explicit support for RDNA 4 hardware targets (`gfx1200`, `gfx1201`). Existing logs (`synthesizer_batch.log`) indicate that hardware-level instability related to ROCm/HIP/RDNA 4 is already causing silent data corruption and "RMS Norm" errors. This validates the Subconscious's epiphany: the current monolithic ROCm approach is insufficient for the upcoming hardware transition.

## 2. Current State Analysis
- **Hardware Support:** No `gfx120x` targets found in the codebase.
- **Stability Issues:** Logs confirm that ROCm/HIP kernel errors and VRAM management issues are contributing to "Cognitive Dissonance" and "Contextual Blindness" in the agentic workflows.
- **Integration Gap:** The `scheduler.ts` contains only placeholder comments for ROCm VRAM querying, indicating a lack of deep integration with the hardware/driver layer.

## 3. Proposed Architectural Shift: 'TheRock' Convergence
To support the RX 9070 XT and subsequent RDNA 4 hardware, the system must move from manual driver/environment management to a modular, system-native approach.

### 3.1. Integration Strategy
- **Modular ROCm Adoption:** Align with the CachyOS 'TheRock' modularization strategy. This involves moving away from monolithic ROCm packages toward granular, target-specific modules.
- **Native Pacman Integration:** Ensure that `gfx120x` support is managed through the native system tree. This prevents "dependency hell" by allowing the OS package manager to resolve hardware-specific ROCm components.

### 3.2. Implementation Roadmap
1. **Phase 1: Monitoring & Dependency Mapping**
   - Monitor CachyOS repositories for the release of modular ROCm packages.
   - Map the new modular dependencies to ensure compatibility with the existing `pacman` ecosystem.

2. **Phase 2: Orchestrator Update**
   - Replace the placeholder VRAM querying in `src/orchestrator/scheduler.ts` with a robust implementation that interfaces with the modular ROCm/HIP layer.
   - Implement error-handling logic specifically for RDNA 4-related kernel errors to mitigate "silent data corruption."

3. **Phase 3: Target-Specific Optimization**
   - Once modular packages are available, prioritize the migration of `gfx1200/1201` targets into the native system tree.

## 4. Conclusion
The transition to 'TheRock' is not merely a deployment change but a necessary structural evolution to synchronize hardware modularity with the OS. Failure to adopt this modularity will result in continued instability as RDNA 4 hardware becomes standard.
