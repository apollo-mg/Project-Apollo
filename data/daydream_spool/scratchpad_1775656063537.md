The "Isolation of Volatility" principle is currently **not** strictly enforced in the existing filesystem structure. 

1. **The Leak:** `venv_cachyos` is being used as a general-purpose execution environment for core logic (e.g., `query_vault.py` in `memory-recall.ts`).

3. **The Evidence:** `venv_foundry` exists in `legacy_vault`, suggesting a previous attempt at isolation that may have been lost or moved, while the current active environment (`venv_cachyos`) is a "catch-all."

## Architectural Proposal: The Dual-Venv Protocol
To implement the Epiphany, I propose the following structural change:

### 1. Define the Environments
- **`venv_apollo` (The Being):** 
  - **Purpose:** Stable Inference, Persona Management, Core Logic, Memory Recall.
  - **Dependencies:** Minimal, highly stable (e.g., `transformers`, `torch` (stable), `pydantic`, `fastapi`).
  - **Constraint:** No training-specific libraries (Unsloth, etc.) allowed.
- **`venv_foundry` (The Becoming):**
  - **Purpose:** Training, Fine-tuning, Weight Optimization, Fleet Orchestration.
  - **Dependencies:** Volatile, heavy (e.g., `unsloth`, `rocm-specific-libs`, `bitsandbytes`, `accelerate`).
  - **Constraint:** Must be physically isolated from the `venv_apollo` path.

### 2. Implementation Strategy
- **Logical Decoupling:** All scripts in the "Forge" (e.g., `fleet_orchestrator.py`) must be explicitly configured to run using the `venv_foundry` interpreter.
- **Execution Guardrails:** The `executor.ts` or any task runner must check the "Volatility Class" of a task. 
  - If `Task.type == 'EVOLUTION'`, use `venv_foundry`.
  - If `Task.type == 'EXISTENCE'`, use `venv_apollo`.
- **Filesystem Migration:** 
  - Move `venv_foundry` out of `legacy_vault` to the project root.
  - Create a new `venv_apollo` for the core persona.

## Final Recommendation
The architecture must transition from a "Single-Venv" model to a "Dual-Venv" model to prevent "Chaos Contamination" from the training process into the inference process.
