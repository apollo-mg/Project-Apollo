# Epiphany Investigation: Always-On Macro Plan & Compute Sovereignty

## Initial Hypothesis
The epiphany suggests that the 'Always-On' plan's failure is due to the OS prioritizing the GUI/WDDM (Windows Display Driver Model) over raw compute. This leads to TDR (Timeout Detection and Recovery) errors during heavy workloads like LoRA training or TT-Metalium orchestration. 

The proposed solution is to move towards a headless, TTY-centric architecture for compute nodes to bypass the abstraction layer.

## Investigation Plan
1. **Audit existing infrastructure definitions**: Look for any configuration files that define compute nodes or orchestration logic.
2. **Check for TDR/Display Server dependencies**: Search for code that interacts with display drivers or assumes a GUI environment.
3. **Identify 'Always-On' implementation**: Find where the 'Always-On' logic is currently implemented to see if it's tied to OS-level power management or GUI stability.
4. **Evaluate TT-Metalium/LoRA orchestration**: Check how these tasks are currently launched and if they are susceptible to display-related interruptions.
## Findings

### 1. Infrastructure Audit
- No explicit "Always-On" configuration found in the current codebase.
- The codebase is primarily a multi-agent orchestration framework (`src/orchestrator`, `src/agent`).
- The orchestration logic (`src/orchestrator/orchestrator.ts`) manages task scheduling and team execution but does not currently manage the underlying OS/hardware state (e.g., display server unbinding).

### 2. TDR/Display Dependencies
- `src/memory/shared.ts` contains logic for `displayValue`, which is likely for logging/UI purposes, but doesn't seem to drive the compute process.
- `src/agent/runner.ts` handles text streaming for "displaying" results, which is a high-level abstraction.
- There is no direct interaction with WDDM or display drivers in the current `src` directory.

### 3. 'Always-On' Implementation
- The term "Always-On" is absent from the codebase, suggesting it might be a high-level strategic concept or a planned feature not yet implemented in the core logic.

### 4. Compute Orchestration (TT-Metalium/LoRA)
- The framework is designed to orchestrate tasks. If these tasks (like LoRA training) are executed via the `bash` tool (`src/tool/built-in/bash.ts`), they are subject to the environment they run in.
- If the environment is a standard desktop OS with a GUI, the TDR risk is real.

## Conclusion & Architectural Proposal

The epiphany is valid: the current orchestration layer is "GUI-aware" in its output (streaming text for display) but "OS-agnostic" in its execution environment. To support the 'Always-On' plan, we need a new module: `ComputeEnvironmentManager`.

### Proposed Changes:
1. **New Module: `src/modules/environment_manager.ts`**
   - Define an interface `ComputeEnvironment` with methods: `prepare()`, `teardown()`, and `isHeadless()`.
   - Implement a `HeadlessLinuxEnvironment` that can interact with `systemd` or `logind` to ensure the node is in a TTY-only state during heavy compute tasks.
   - Implement a `WindowsWDDMEnvironment` (for research/testing) that monitors for TDR risks.

2. **Update `src/orchestrator/orchestrator.ts`**
   - Integrate `ComputeEnvironmentManager`.
   - Before launching high-criticality/high-compute tasks (identified via `src/modules/criticality.ts`), the orchestrator should check if the current environment meets the "Sovereign Compute" requirements.
   - If not, it should trigger a "Headless Transition" or alert the user that the task is running in a "Hostage" (GUI-dependent) state.

3. **Update `src/types.ts`**
   - Add `EnvironmentMode` (e.g., `GUI`, `HEADLESS`, `TTY_ONLY`).
   - Add `environmentMode` to the `Task` type.

This moves the framework from being just a "task scheduler" to a "compute sovereign," capable of managing the hardware abstraction layer to protect the compute cycle.
