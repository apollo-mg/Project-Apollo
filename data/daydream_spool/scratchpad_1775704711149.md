# Epiphany Investigation: Feedback Paradox in Graph Execution
## Timestamp: 2024-05-22 (Simulated)
## Status: Initializing Audit

### Hypothesis
The subconscious daemon suggests a structural flaw in the current graph architecture. Specifically, the system is attempting to perform a recursive update on a primitive value (likely the prompt or state) within a single execution pass of a Directed Acyclic Graph (DAG). This creates a logical impossibility where a node attempts to redefine its own input/origin, leading to a "feedback paradox."

### Objective
1. Identify the code responsible for prompt generation and state management.
2. Locate the "Logic Gate" or similar nodes that handle prompt transformations.
3. Determine if the current implementation attempts to overwrite the `original_prompt` within the same execution cycle.
4. Propose a decoupling mechanism using a State Manager or an Iteration Controller.

### Investigation Plan
1. Search for "prompt", "original_prompt", and "new_prompt" in the codebase to find the logic responsible for these transformations.
2. Examine the graph definition/orchestration logic to see how iterations are handled.
3. Look for patterns where a node's output is being fed back into its own input without a stateful buffer.
### Findings
1. **Orchestration Logic**: The `OpenMultiAgent.runTeam` method (lines 455-544) follows a linear, three-step process:
   - **Decomposition**: A coordinator agent breaks the goal into tasks.
   - **Execution**: `executeQueue` runs tasks in a DAG-based loop.
   - **Synthesis**: A coordinator agent synthesizes the final answer.

2. **The "Feedback Paradox"**: The epiphany suggests that the system is attempting to "redefine its own birth." In the context of `runTeam`, the `goal` (the "birth") is passed into `buildDecompositionPrompt` and `buildSynthesisPrompt`. 

3. **Potential Issue**: If a task's output is intended to *become* a new goal for a subsequent run, the current architecture requires a manual external trigger. There is no internal mechanism for a task to say "this is not a task, this is a new goal for a new orchestration cycle."

4. **Architectural Constraint**: The `executeQueue` loop (lines 177-292) is strictly bounded by the `TaskQueue`. It cannot spawn new `runTeam` calls or modify the `goal` variable of the current execution.

### Proposed Solution: The Iteration Controller
To allow for "biological recursion" (self-improving or self-evolving goals), we need to decouple the execution from the goal definition.

**Proposed Changes:**
1. **Introduce `IterationController`**: A new component that monitors `TeamRunResult`. If a result contains a specific "Evolution Signal" (e.g., a new goal in the synthesis output), the controller initiates a *new* `runTeam` call with the updated goal.
2. **State Manager Node**: Instead of agents writing directly to shared memory, they write to a `StateStore`. This store can distinguish between "Task Results" and "Evolutionary Directives."
3. **Decoupling**:
   - `original_goal` $\rightarrow$ `current_goal` (in a State Manager).
   - `current_goal` $\rightarrow$ `Decomposition` $\rightarrow$ `Execution` $\rightarrow$ `Synthesis`.
   - `Synthesis` $\rightarrow$ `Evolutionary Directive` $\rightarrow$ `Iteration Controller` $\rightarrow$ `New current_goal`.

### Implementation Plan (Draft)
- **Step 1**: Define a new `EvolutionaryResult` type that extends `TeamRunResult`.
- **Step 2**: Modify `OpenMultiAgent` to optionally accept an `IterationController`.
- **Step 3**: Implement a loop in the CLI or a high-level runner that handles the transition from `Iteration N` to `Iteration N+1`.

### Conclusion
The epiphany is correct. The current DAG is too rigid for self-referential evolution. We are attempting to achieve recursion within a single pass of a finite state machine. We must move the recursion to the *orchestrator level* rather than the *graph level*.
