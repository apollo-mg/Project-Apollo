2.  **Active Reality (The Runtime):** The runtime executes the GGUF model. However, if the runtime's implementation of the `KSampler` or the scheduler doesn't automatically detect that the loaded GGUF is a "Wan 2.1" model and apply the necessary `max_shift` or "High/Low" noise pass logic, the output will be visually broken (the "strobe effect").
3.  **The "Truth":** The truth is not just the model file, but the **interaction** between the model's architecture (GGUF) and the sampling parameters (Noise Schedule/Shift) applied at runtime.

## Proposed Architectural Update: Runtime Verification Layer

I propose a `ModelRuntimeValidator` that sits between the `WorkflowParser` and the `ModelLoader`.

### Logic Flow:
1.  **Parse Workflow:** Extract model type and intended sampling parameters from the JSON.
2.  **Load Model:** Load the actual file (e.g., `.gguf`).
3.  **Inspect Metadata:** Extract the model architecture from the GGUF metadata (e.g., `general.architecture = qwen35` or similar for Wan).
4.  **Reconcile:**
    - **IF** `model_architecture` is `Wan2.1` (or similar Flow Matching architecture).
    - **AND** `workflow_sampling_params` does **NOT** include `max_shift` or the correct `noise_schedule`.
    - **THEN** Trigger a `DivergenceWarning` or automatically inject the required `max_shift` parameter into the runtime execution.
5.  **Verification:** Ensure the "High/Low" noise pass logic is correctly applied if the workflow indicates a multi-stage process.
