# Architectural Proposal: Declarative Hardware-Software Bridge Optimization

## 1. Problem Statement
Current model deployment relies on manual environment variable configuration within individual shell scripts (e.g., `start_qwen_35b_moe.sh`). This approach is error-prone, lacks scalability, and fails to account for the specific memory-handling requirements of high-parameter architectures on ROCm backends.

## 2. Proposed Solution: The `BridgeOptimizer` System
Transition from imperative shell-based environment management to a declarative, architecture-aware optimization layer.

### 2.1 Component: `bridge_config.json`
A centralized registry mapping model architectures to optimized ROCm/PyTorch parameters.
**Example Schema:**
```json
{
  "architectures": {
    "wan_2_1": {
      "PYTORCH_HIP_ALLOC_CONF": "expandable_segments:True",
      "PYTORCH_TUNABLEOP_ENABLED": "1",
      "PYTORCH_TUNABLEOP_TUNING": "0"
    },
    "qwen_moe": {
      "PYTORCH_HIP_ALLOC_CONF": "max_split_size_mb:512",
      "PYTORCH_TUNABLEOP_ENABLED": "1"
    }
  }
}
```

### 2.2 Component: Enhanced `model_manifest.json`
The manifest must be expanded to include architectural metadata to allow the optimizer to perform lookups.
**Proposed Update:**
```json
{
  "models": [
    {
      "id": "qwen_35b_moe_v1",
      "architecture": "qwen_moe",
      "parameters": "35B",
      "type": "moe"
    }
  ]
}
```

### 2.3 Component: `src/bridge_optimizer.py`
A Python utility that performs the following logic:
1. **Identify**: Receives a `model_id`.
2. **Lookup**: Queries `model_manifest.json` for the associated `architecture`.
3. **Resolve**: Fetches the corresponding environment variables from `bridge_config.json`.
4. **Inject**: Returns a dictionary of environment variables to be used by the process launcher.

## 3. Implementation Roadmap

### Phase 1: Data Foundation
- Update `model_manifest.json` to include `architecture` fields.
- Create `bridge_config.json` with baseline optimizations for known architectures.

### Phase 2: Logic Implementation
- Develop `src/bridge_optimizer.py`.
- Implement unit tests for the lookup logic.

### Phase 3: Orchestration Integration
- Refactor `orchestrator.py` to use `bridge_optimizer.py` when spawning model processes.
- Deprecate manual `export` statements in `start_*.sh` scripts in favor of a unified `run_model.py` wrapper.

## 4. Expected Impact
- **Reliability**: Eliminates OOM errors caused by suboptimal memory allocation settings.
- **Performance**: Ensures `TUNABLEOP` is correctly enabled for high-throughput workloads.
- **Maintainability**: Centralizes hardware-specific tuning, allowing for global updates via a single JSON file.
