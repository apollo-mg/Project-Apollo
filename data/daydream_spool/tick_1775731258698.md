# Architectural Proposal: Feasibility Engine Integration

## 1. Executive Summary
The "Feasibility Engine" is proposed as a new specialized layer within the Apollo ecosystem to bridge the gap between idealized design (DesignMind) and real-world procurement constraints (Procurement Mind). By leveraging the semantic delta between CAD-based design intent and the real-world constraints extracted from historical email data (via the `vllm_email_ingest.py` pipeline), the engine will provide predictive feedback to the design process.

## 2. Architectural Overview

### 2.1 Core Components
- **FeasibilityEngine (New Module):** Located in `src/modules/feasibility_engine.ts`. This module acts as a semantic validator.
- **Constraint Vector Store:** The existing vector database (populated by `vllm_email_ingest.py`) serves as the primary source for "Real-World Constraints."
- **Design Intent Interface:** A standardized way for `DesignMind` agents to express their requirements (e.g., part specifications, material types, lead-time tolerances).

### 2.2 Data Flow
1. **Design Generation:** `DesignMind` agent generates a design concept/specification.
2. **Constraint Query:** `FeasibilityEngine` intercepts the concept and performs a semantic search in the vector store using the design's key entities (e.g., "Aluminum 6061", "NEMA enclosure").
3. **Delta Analysis:** The engine compares the design requirements against retrieved "Real-World Constraints" (e.g., "Aluminum 6061 lead times increased to 24 weeks due to supplier X shortage").
4. **Feedback Loop:** 
    - **Success:** If constraints are met, the design proceeds.
    - **Failure/Warning:** If a conflict is detected, the engine generates a `FeasibilityWarning` which is fed back into the `DesignMind` agent's context, forcing a recursive redesign.

## 3. Implementation Roadmap

### Phase 1: Schema Definition
- Define `Constraint` and `FeasibilityReport` interfaces in `src/types.ts`.
- Implement a `ConstraintMapping` logic to translate email-extracted entities into design-relevant constraints.

### Phase 2: Module Development
- Implement `src/modules/feasibility_engine.ts`.
- Integrate with `src/memory/store.ts` to enable semantic querying of the email-derived vector space.

### Phase 3: Orchestration Integration
- Update `src/orchestrator/orchestrator.ts` to include a `FEASIBILITY_CHECK` stage in the task pipeline.
- Ensure that `training_success.jsonl` is used to fine-tune the engine's ability to distinguish between "minor delays" and "critical procurement failures."

## 4. Conclusion
This integration transforms the Lab from a collection of tools into a self-correcting synthetic organism, where the "genetic material" of past successes and failures directly informs the evolution of future designs.
