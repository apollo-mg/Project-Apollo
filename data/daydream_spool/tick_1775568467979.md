# Architectural Audit: Reflex vs. Reflection (VRAM Management)

## Epiphany Analysis
The subconscious has identified a critical structural flaw in the current orchestration hierarchy. The `OpenMultiAgent` (Orchestrator) is currently acting as a "Thinker" (using a high-parameter model like `claude-opus-4-6` or `DeepSeek-R1` to decompose tasks and synthesize results) rather than a "Reflex" (a lightweight, near-zero VRAM footprint controller).

When the primary reasoning engine (the "Reflection" layer) saturates the GPU VRAM, the Orchestrator—which is part of the same memory space—becomes unable to perform its management duties, including triggering emergency resets or monitoring system health. This creates a "Cognitive Death Spiral" where the system cannot recover because the recovery mechanism itself is starved of resources.

## Current State Audit (`orchestrator.ts`)
The audit of `src/orchestrator/orchestrator.ts` confirms the epiphany:
1. **Heavyweight Coordinator:** The `runTeam` method (lines 455-544) instantiates a `coordinatorAgent` using `this.config.defaultModel` (line 463). This model is typically a high-parameter LLM.
2. **Reasoning-Heavy Lifecycle:** The Orchestrator performs complex reasoning tasks:
   - **Decomposition:** Breaking a goal into a JSON task list (lines 469-485).
   - **Synthesis:** Summarizing all task outputs into a final answer (lines 529-531).
3. **Resource Coupling:** The Orchestrator's lifecycle is tightly coupled to the `AgentPool` and the models it manages. If the `AgentPool` consumes all VRAM, the `coordinatorAgent.run()` calls will fail or hang, preventing the Orchestrator from executing any "reflex" logic.

## Proposed Architectural Shift: The "Reflex" Model

To resolve this, we must decouple the **Orchestration Logic** from the **Reasoning Engine**.

### 1. Formalize the 'Reflex' Layer
The Orchestrator must be stripped of its dependency on heavy LLMs for its core lifecycle management.
- **Reflex Mode:** Use a local, extremely small model (e.g., a tiny SLM or even a rule-based heuristic engine) or a remote API call that does not compete for local GPU VRAM.
- **Separation of Concerns:** 
    - **Reflex (Orchestrator):** Manages the state machine, task queue, and resource monitoring. It uses "shallow" reasoning (regex, JSON parsing, simple logic).
    - **Reflection (Agents/Coordinator):** Performs the "deep" reasoning (task decomposition, synthesis, complex tool use).

### 2. Implementation Strategy
- **Introduce `ReflexConfig`:** A new configuration type that specifies a `reflexModel` (e.g., a lightweight API-based model or a local tiny model) specifically for the Orchestrator's internal meta-tasks.
- **Refactor `runTeam`:**
    - The `coordinatorAgent` should be initialized with the `reflexModel` instead of the `defaultModel`.
    - The `parseTaskSpecs` logic (which is already relatively lightweight) should be the primary driver for task management, minimizing the need for the coordinator to "think" deeply.
- **VRAM Guardrails:** Implement a `VRAMMonitor` that the Orchestrator can query. If VRAM exceeds a threshold, the Orchestrator (in Reflex mode) can preemptively kill low-priority agents or trigger a hard reset via an external API.

## Conclusion
The transition from "Orchestrator as Thinker" to "Orchestrator as Reflex" is mandatory for system stability in VRAM-constrained environments. This change will ensure that the system's "survival instinct" remains functional even when its "intellectual capacity" is fully saturated.
