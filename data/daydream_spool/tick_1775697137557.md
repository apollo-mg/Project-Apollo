# Architectural Proposal: Foundry-Gated Model Registry

## 1. Executive Summary
The current model orchestration architecture treats model availability as a static property of the configuration (`profiles.json`). This creates a risk where unoptimized or unprofiled models are launched, leading to sub-optimal performance or runtime errors on specific hardware (e.g., RDNA 4). 

The "Overnight Foundry" epiphany identifies that a model is not truly "ready" until it has been compiled into a hardware-native artifact (HIP Graphs, tuning CSVs). We must transition from a **Static Registry** to a **Stateful Lifecycle Registry**.

## 2. Proposed State Machine
Each model profile in `profiles.json` will transition through the following states:

| State | Description | Visibility to Inference Engine |
| :--- | :--- | :--- |
| `UNAVAILABLE` | Model path is defined but no profiling has occurred. | Hidden |
| `PENDING_COMPILATION` | Model is being processed by the Foundry. | Hidden |
| `READY` | Profiling complete; HIP Graphs and tuning CSVs verified. | **Visible** |
| `ERROR` | Profiling failed or artifacts are corrupted. | Hidden (requires manual intervention) |

## 3. Technical Implementation Plan

### A. Schema Update (`profiles.json`)
Inject a `lifecycle` object into each profile:
```json
"architect": {
  "description": "...",
  "status": "READY",
  "lifecycle": {
    "last_profiled": "2025-05-20T14:00:00Z",
    "artifacts_verified": true,
    "foundry_version": "1.0.2"
  },
  ...
}
```

### B. Orchestrator Logic Update (`orchestrator.py`)
Modify `ServiceOrchestrator.launch()` to implement a gatekeeper pattern:
1. **Fetch Profile:** Retrieve the profile configuration.
2. **Status Check:** 
   - If `status != "READY"`, abort launch with a specific error: `Model [name] is in state [status]. Please run the Foundry to compile hardware-native artifacts.`
3. **Artifact Verification (Optional/Deep Check):** Before execution, perform a lightweight check to ensure the `model` path matches the expected optimized artifact type.

### C. Foundry Integration (`foundry_profile.py`)
The Foundry becomes the sole authority for state transitions.
1. **Trigger:** Foundry starts profiling a model.
2. **Update:** Foundry sets status to `PENDING_COMPILATION`.
3. **Execution:** Foundry runs `foundry_profile.py` to generate HIP Graphs/CSVs.
4. **Verification:** Foundry verifies the existence of files in the centralized directory.
5. **Finalization:** Foundry updates `profiles.json` to `status: "READY"`.

## 4. Impact Assessment
- **Reliability:** Eliminates "cold start" performance penalties by ensuring only optimized models are served.
- **Complexity:** Increases complexity of the model deployment pipeline but reduces complexity of the inference engine (which no longer needs to handle unoptimized models).
- **Hardware Native:** Directly realizes the goal of turning raw weights into hardware-native execution graphs.
