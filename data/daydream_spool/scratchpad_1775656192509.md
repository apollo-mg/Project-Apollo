# Epiphany Investigation: Risk-Weighted Autonomy
## Timestamp: 2025-05-22 (Simulated)
## Status: Initializing Audit

### Objective
Investigate the current HITL (Human-in-the-Loop) implementation to identify where the 'y' input friction exists and how a 'Safety Critic' model could be integrated into the architecture.

### Initial Observations
- The epiphany suggests a transition from binary HITL to 'Risk-Weighted Autonomy'.
- The current system likely uses a manual confirmation for bash commands or sensitive operations.
- I need to locate the core orchestration logic that handles tool execution and user confirmation.

### Hypotheses
1. The confirmation logic is likely located in `orchestrator.py`, `task_manager.py`, or a specific module within `src/` or `modules/`.
2. There might be a `permission_policy.md` or `guardian_manifest.json` that defines current constraints.
3. The 'Safety Critic' would require a new module that intercepts tool calls before they reach the execution layer.

### Findings
- Found a pattern of `require_human_approval` decorators in `gemini-infrastructure_chats_session...json` (likely a historical log or template) that uses a hard `input("Authorize this action? (y/n): ")`.
- This confirms the "binary HITL" model described in the epiphany.
- The `apollo.py` file also contains a direct `input()` loop for user interaction.
- The `Dev_Log` mentions a "Persistent Approval Queue" and a `request_approval` function, suggesting some work was already started to move away from simple `input()`.

### Proposed Architectural Shift: Risk-Weighted Autonomy
1. **The Safety Critic**: A lightweight LLM (e.g., Llama 3.2 or a quantized model running on the RX 9070 XT) will act as a pre-processor for tool calls.
2. **Risk Scoring**:
   - **Low Risk**: `ls`, `cat` (non-sensitive), `grep`, `web_search`.
   - **Medium Risk**: `pip install`, `git commit`, `mkdir`.
   - **High Risk**: `rm -rf`, `sudo`, `curl | bash`, `modify_system_config`.
3. **The Workflow**:
   - Tool Call Requested $\rightarrow$ **Safety Critic** evaluates risk $\rightarrow$ 
     - If **Low Risk**: Execute immediately + Log to `audit_log`.
     - If **Medium Risk**: Prompt user with a "Quick Approve" (e.g., `[Y/n]`) or auto-approve if within a "Trust Window".
     - If **High Risk**: Mandatory manual confirmation (the current "Hard Gate").
4. **Implementation Strategy**:
   - Replace the `require_human_approval` decorator with a `risk_aware_approval` decorator.
   - This decorator will call a new `SafetyCritic` class.
   - The `SafetyCritic` will use a local LLM to categorize the command.
### Detailed Audit of `modules/approvals/handler.py`
- **Current Heuristic (`should_require_approval`)**:
  - `run_shell` is hardcoded to `True` (always requires approval). This is the primary source of the "binary HITL" friction.
  - `write_code` uses a heuristic based on file path (core files), content length, and file existence.
- **Current Approval Flow (`request_approval`)**:
  - Uses a `PENDING_PATH` (`pending.json`) as a queue.
  - Attempts to use a GUI (`launch_inspector`) or `kdialog`.
  - Falls back to a polling loop on the `pending.json` file.
- **The "Paradox" confirmed**: The system is designed to be "safe" by defaulting to manual intervention for shell commands, even though the hardware (RX 9070 XT) could easily handle a local model to evaluate these commands.

### Proposed Implementation Plan for 'Risk-Weighted Autonomy'

#### 1. Create `modules/approvals/safety_critic.py`
- This module will interface with a local LLM (via `llm_interface.py`).
- It will take `action_name` and `params` as input.
- It will return a `RiskLevel` (LOW, MEDIUM, HIGH).

#### 2. Update `modules/approvals/handler.py`
- **Modify `should_require_approval`**:
  - Instead of `if action_name == "run_shell": return True`, it will call `SafetyCritic.evaluate(action_name, params)`.
- **Introduce `RiskLevel` logic**:
  - **LOW**: Return `True` (auto-approve) but log the action.
  - **MEDIUM**: Return `True` (require "Quick Approval" - e.g., a single keystroke or a non-blocking GUI notification).
  - **HIGH**: Return `True` (require full manual confirmation/GUI).

#### 3. Refactor `request_approval`
- Integrate the `RiskLevel` into the decision tree.
- For `LOW` risk, bypass the `PENDING_PATH` and the polling loop entirely to minimize latency.
- For `MEDIUM` risk, use a lightweight notification (e.g., `notify-send` or a simple terminal prompt) rather than a full-blown `kdialog` or `launch_inspector` if possible.

#### 4. Resource Allocation
- The `SafetyCritic` will be configured to use a small, fast model (e.g., `llama3.2:1b` or `gemma:2b`) to ensure the "overhead" is negligible compared to the computational power of the RX 9070 XT.
