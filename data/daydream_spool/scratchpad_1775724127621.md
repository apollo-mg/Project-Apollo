# Investigation: Probabilistic Agency vs. Deterministic Enforcement
## Timestamp: 2025-05-22 (Simulated)
## Status: Initializing Audit

### Epiphany Analysis
The subconscious suggests a drift where the system is moving away from using LLM reasoning for decision-making and instead is hardcoding logic to bypass "flaky" reasoning. This implies a shift from an autonomous agent to a rigid, trigger-based state machine where the LLM is merely a decorator.

### Hypothesis
The 'Orchestrator' or 'Task Manager' components likely contain logic that bypasses reasoning for certain task types, or conversely, uses reasoning for tasks that could be handled by deterministic triggers. I need to find the core orchestration logic to see where this boundary is currently drawn.

### Target Files for Investigation
- `orchestrator.py`
- `task_manager.py`
- `fleet_orchestrator.py`
- `src/` (to check for core logic)
- `modules/` (to check for task definitions)
### Findings: The Cognitive vs. Mechanical Boundary

#### 1. Current State of the Boundary
The investigation confirms that the system is indeed implementing a "Deterministic Enforcement" layer via the `CognitiveEscalation` module and the `CognitiveDispatcher`. 

- **Deterministic Triggers (Mechanical):** 
    - `CognitiveEscalation` uses hardcoded thresholds (CPU, Memory, Temperature, Disk) to detect system instability.
    - When thresholds are breached, it bypasses standard complexity analysis and **forces** an escalation to the `ARCHITECT` tier (Deterministic Enforcement).
    - This is a "Reflex Arc" designed to prevent the system from "thinking" its way into a crash, instead triggering a high-compute response to resolve the underlying issue.

- **Probabilistic Reasoning (Cognitive):**
    - `CognitiveDispatcher.analyze_complexity` uses a mix of heuristics (fast/mechanical) and LLM-based triage (probabilistic).
    - The LLM triage (`_llm_triage`) is used when heuristics fail, representing the "flaky" reasoning layer the Epiphany warns about.

#### 2. The "Flaky" Reasoning Risk
The `CognitiveDispatcher` relies on `_llm_triage` to decide if a task is `MODERATE` or `COMPLEX`. If the LLM (Worker tier) misclassifies a complex task as `SIMPLE`, the system loses its "Deep Reasoning" capability for that task, effectively relegating the intelligence to a "decorator" of the dispatcher's logic.

#### 3. Taxonomy of Tasks (Proposed)

| Task Category | Mechanism | Logic Type | Example |
| :--- | :--- | :--- | :--- |
| **System Health/Safety** | `CognitiveEscalation` | **Deterministic** | Thermal throttling, OOM prevention, Disk full. |
| **Resource Management** | `ServiceOrchestrator` | **Deterministic** | Port allocation, process lifecycle, env injection. |
| **Data Ingestion/Sync** | `Librarian/Ingest` | **Deterministic** | File movement, log parsing, database updates. |
| **Task Triage** | `CognitiveDispatcher` | **Hybrid** | Heuristics (Fast) $\rightarrow$ LLM Triage (Probabilistic). |
| **Core Intelligence** | `Architect Tier` | **Probabilistic** | Refactoring, CAD design, complex system architecture. |

#### 4. Architectural Audit Conclusion
The Epiphany is correct: the system is increasingly using hardcoded triggers to manage the "liability" of LLM autonomy. While this increases stability (Resilience Engineering), it risks creating a "glass ceiling" where the system cannot autonomously decide to use more intelligence unless a hardcoded trigger is pulled.

### Proposed Architectural Update: "The Cognitive Governor"
Instead of just "Forced Triggers," we should implement a **Cognitive Governor** that:
1. **Monitors Triage Accuracy:** Tracks how often `WORKER` tier decisions lead to `ARCHITECT` tier escalations (detecting misclassification).
2. **Dynamic Thresholding:** Allows the `ARCHITECT` to adjust the `CognitiveDispatcher` heuristics based on current system load, rather than relying on static `thresholds`.
3. **Explicit Complexity Injection:** Allows the user or a higher-level process to "force" a reasoning tier without waiting for a system error.
