## Deep Dive: Hardware-Awareness Implementation
- **Discovery:** `src/orchestrator/scheduler.ts` contains a `scheduleHardwareAware` method (lines 325-359).
- **Current State:** The implementation is currently a "simulated" layer. It uses a very basic heuristic:
    1. It checks if the task description contains "vram" or "memory".
    2. It attempts to access `agent.hardware_info` (cast as `any`) to get `vram_available`.
    3. It sorts agents by `availableVram` if high VRAM is needed.
- **Gap Analysis:** This is exactly what the Epiphany calls out. The current "hardware-aware" logic is purely about *resource allocation* (VRAM/Memory), whereas the Epiphany proposes *mathematical/architectural optimization* (GEMM shapes/Tuning Maps).
- **The "Translation Layer" Opportunity:** The `scheduleHardwareAware` method is the perfect architectural hook. Instead of just checking VRAM, it should be the entry point for the "Tuning Map Library".

## Proposed Architectural Update: The "Silicon-Centric" Pipeline
The goal is to move from `VRAM-based scheduling` to `Shape-based optimization`.

### 1. The Tuning Map Library (New Module)
- **Location:** `src/modules/tuning_map.ts` (Proposed)
- **Function:** A registry that maps `(chip_id, precision, shape_tuple)` $\rightarrow$ `optimal_kernel_config`.
- **Data Structure:** A high-performance lookup table (or a serialized JSON/Protobuf map) containing the results of the "Sweep $\rightarrow$ Map" process.

### 2. Integration into the Scheduler
- **Modification:** Update `scheduleHardwareAware` in `src/orchestrator/scheduler.ts`.
- **Logic:**
    - Instead of just checking `vram_available`, the scheduler should look at the *model requirements* of the task (e.g., the expected GEMM shapes for the model being run).
    - It queries the `TuningMapLibrary` for the `chip_id` (e.g., GFX1201).
    - It selects the agent whose hardware configuration best matches the "mathematical dialect" (the optimal shapes) for that specific model/precision combination.

### 3. The Closed-Loop Pipeline (Conceptual)
- **Sweep:** A background process (or a new `src/modules/sweeper.ts`) that runs benchmarks on the target hardware (RDNA 4).
- **Map:** The results are processed into the `TuningMapLibrary`.
- **Quantize/Fine-Tune:** The model weights are adjusted to align with the optimal shapes discovered in the sweep.

## Conclusion & Proposal
The codebase has the structural "hooks" (the `hardware-aware` strategy) but lacks the "intelligence" (the Tuning Map). The transition is not just a code change, but a shift in how we define "hardware-aware".
