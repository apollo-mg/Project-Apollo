# Apollo Investigation: Hardware-Software Bridge Calibration
## Epiphany Analysis
The subconscious has identified a critical friction point: the manual management of ROCm-specific environment variables (`PYTORCH_HIP_ALLOC_CONF`, `TUNABLEOP`) when loading high-parameter models (e.g., WAN 2.1). 

Current state: Likely manual script patching or hardcoded environment variables in various `start_*.sh` scripts.
Proposed state: A declarative pre-flight check that detects model architecture and injects optimized parameters.

## Initial Investigation Steps
1. Identify where models are launched (looking at `start_*.sh` and `scripts/`).
2. Search for existing usage of `PYTORCH_HIP_ALLOC_CONF` or `TUNABLEOP` in the codebase.
3. Audit `model_manifest.json` to see if architecture metadata is available for the proposed pre-flight check.
4. Examine `v8_tuning_strategy.json` to see if tuning data is already being captured.
## Findings
- The search revealed that `PYTORCH_TUNABLEOP_ENABLED` and `PYTORCH_HIP_ALLOC_CONF` are heavily used in `legacy_vault/`.
- Specifically, `legacy_vault/infrastructure/apollo_vllm.sh` and `legacy_vault/core/vllm_tune.py` show manual management of these variables.
- `legacy_vault/data/model_database.json` contains some configuration, suggesting a precedent for declarative model metadata.
- The current `start_*.sh` scripts in the root directory (e.g., `start_qwen_35b_moe.sh`, `start_gemma_moe_experimental.sh`) do NOT appear to use these variables, which confirms the "manual patching" problem. They likely rely on default environment settings, which might be suboptimal for high-parameter models.

## Hypothesis
The current orchestration layer (the `start_*.sh` scripts) is too primitive. It lacks a "Pre-flight Hardware-Software Bridge Optimizer" that can:
1. Parse the model being requested.
2. Consult a manifest (like `model_manifest.json`) for architecture-specific tuning requirements.
3. Inject the correct `PYTORCH_HIP_ALLOC_CONF` and `TUNABLEOP` settings before the process spawns.

## Next Steps
1. Examine `model_manifest.json` to see if it contains architecture/parameter info.
2. Examine `scripts/` to see if there's a central orchestration script that could be upgraded.
3. Draft a proposal for a `bridge_optimizer.py` or similar utility.
## Refined Hypothesis
The `model_manifest.json` is currently too sparse (only contains TTS models). The `v8_tuning_strategy.json` is actually a dataset strategy for model training, not a hardware tuning strategy. This suggests that the "tuning" mentioned in the epiphany might refer to a missing or under-utilized component in the current architecture.

The `legacy_vault` contains the "DNA" of how these variables *should* be managed. The goal is to extract that logic and formalize it into a modern, declarative system.

## Proposed Architectural Update: `BridgeOptimizer`
Instead of manual shell scripts, we should implement a `BridgeOptimizer` module.

### 1. Declarative Configuration (`bridge_config.json`)
A new file that maps model architectures/IDs to their optimal ROCm/PyTorch environment variables.
Example:
```json
{
  "wan_2_1": {
    "PYTORCH_HIP_ALLOC_CONF": "expandable_segments:True",
    "PYTORCH_TUNABLEOP_ENABLED": "1",
    "PYTORCH_TUNABLEOP_TUNING": "0"
  },
  "qwen_35b_moe": {
    "PYTORCH_HIP_ALLOC_CONF": "max_split_size_mb:512",
    "PYTORCH_TUNABLEOP_ENABLED": "1"
  }
}
```

### 2. The Optimizer Logic (`src/bridge_optimizer.py`)
A Python utility that:
- Reads the `model_manifest.json` (which needs to be expanded to include architecture metadata).
- Loads `bridge_config.json`.
- Returns a dictionary of environment variables.

### 3. Integration
The `orchestrator.py` or the `start_*.sh` scripts should be refactored to call a wrapper that uses this optimizer. 

## Action Plan for Implementation
1. **Expand `model_manifest.json`**: Add `architecture` and `parameter_count` fields to model entries.
2. **Create `bridge_config.json`**: Define the mapping of architecture -> env vars.
3. **Implement `src/bridge_optimizer.py`**: The logic to merge manifest data with config.
4. **Update Orchestration**: Replace manual `export` calls in shell scripts with a call to a Python wrapper that sets the environment before launching the model process.

## Audit Conclusion
The epiphany is valid. The current system relies on "tribal knowledge" embedded in legacy shell scripts. Moving to a declarative, architecture-aware configuration will reduce friction and prevent runtime OOM/performance degradation on ROCm.
