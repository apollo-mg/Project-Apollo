# Epiphany Investigation: Proactive-State Architecture vs. Reactive-Flush
## Timestamp: 2025-02-27
## Status: Initializing Audit

### Hypothesis
The current system architecture relies on a "reactive-flush" mechanism (likely involving `keep_alive: 0` or similar logic) to manage VRAM/GPU state. This causes context mismatch and instability during model transitions. 

The "Epiphany" suggests moving to a "proactive-state" architecture where transitions are atomic and state-validation occurs in a buffer before GPU re-engagement.

2. **Orchestration Layer:** Identify which script manages model loading/unloading (e.g., `orchestrator.py`, `fleet_orchestrator.py`, `model_provisioner.sh`).
3. **State Management:** Look for how model state or context is preserved or discarded during transitions.
4. **Error Logs:** Correlate "context mismatch" or "transition errors" with specific logs (e.g., `server_crash.log`, `server_qwen_moe_crash.log`).

### Findings: VRAM Management Analysis
- `vram_management.py` exists and implements a `smart_vram_guard` function.
- The current implementation of `smart_vram_guard` is **reactive**: it checks if `used > VRAM_THRESHOLD_MB` and *then* triggers `unload_comfy_vram`.
- `unload_comfy_vram` calls `wait_for_vram_release`, which is a blocking wait for the kernel to flush.
- This confirms the "reactive-flush" pattern described in the Epiphany. The system waits for a threshold breach before attempting to clear space, which is exactly the "fighting the hardware" behavior mentioned.

### Identified Friction Point
The `smart_vram_guard` is a "reactive-flush" strategy. It only acts when the danger zone is reached. This creates a race condition: by the time the guard triggers, the system might already be experiencing latency or instability due to the high VRAM pressure.

### Proposed Architectural Shift: Proactive-State
Instead of:
`Check VRAM -> If High -> Flush -> Wait for Release -> Proceed`

We should move toward:
`Predict Next State -> Validate Buffer -> Atomic Transition -> Proceed`

This requires:
1. **Predictive Modeling:** Knowing the VRAM requirements of the *next* model/task before the current one is fully released.
2. **Atomic Orchestration:** Ensuring the "unload" and "load" operations are treated as a single transaction where the state is validated in a buffer.
3. **Pre-emptive Offloading:** Triggering cleanup based on *upcoming* task requirements rather than *current* usage.

### Orchestrator Analysis
- `orchestrator.py` is a relatively simple service manager. It handles `launch`, `stop`, and `status` based on `profiles.json`.
- **Critical Observation:** The `stop` method uses `fuser -k {port}/tcp`. This is a "hard kill" of the process occupying the port. 
- **The Friction:** When transitioning from one model to another, the orchestrator kills the old process and then launches the new one. This is the definition of a "reactive-flush" and "fragmented" transition. There is no "buffer" or "state-validation" step. The old process is killed, the VRAM is (hopefully) released, and then the new process is launched.
- **The "Context Mismatch" Connection:** If the `fuser -k` command kills the process but the ROCm kernel hasn't fully released the VRAM buffers before the new `launch` command executes, the new process will attempt to allocate memory that the kernel still thinks is occupied, leading to OOM or "context mismatch" errors.

### Proposed Solution: Atomic Transition Layer
We need a new orchestration pattern. Instead of `stop(A) -> launch(B)`, we need `transition(A, B)`.

**The `transition(A, B)` workflow:**
1. **Pre-flight Check:** Check current VRAM.
2. **Predictive Load:** Determine VRAM requirements for `B`.
3. **Graceful Shutdown:** Send a signal to `A` to unload models/clear buffers (if `A` supports it) rather than a hard `fuser -k`.
4. **Wait for Release:** Use `vram_management.py`'s `wait_for_vram_release` to ensure the hardware is actually ready.
5. **Atomic Launch:** Only once the buffer is validated, launch `B`.

### Implementation Plan
1. **Modify `orchestrator.py`:** Add a `transition` method.
2. **Enhance `vram_management.py`:** Ensure it can be used as a reliable gatekeeper for the transition.
3. **Update `profiles.json` (Conceptual):** Add a `vram_requirement_mb` field to profiles to allow for predictive scheduling.
