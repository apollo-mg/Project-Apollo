The "Epiphany" suggests that implementing a 'Project State' schema will allow the agent to use the current task context (e.g., 'Ender 6 Frame') to disambiguate technical terms and reduce hallucination loops.

### Findings: `src/types.ts` Analysis
- `Task` is defined as a discrete unit of work (ID, title, description, status, assignee, dependsOn, result, timestamps).
- `ToolUseContext` provides `agent`, `team`, `abortSignal`, `abortController`, `cwd`, and `metadata`.
- `TeamInfo` includes `sharedMemory` (a `MemoryStore`).
- **Observation:** There is no explicit `Project` or `ContextualAnchor` type in the core types. The `Task` is the primary unit of work, but it lacks a "Project" or "Global Context" field that could be used to weight semantic interpretations.
- **Opportunity:** We can introduce a `ProjectContext` type or extend `ToolUseContext` to include a `projectState` or `semanticAnchors` field. This would allow tools to receive not just the `cwd` or `agent` info, but also the high-level "Project State" (e.g., "Ender 6 Frame Assembly").

### Proposed Architectural Change
1. **Define `ProjectState` Schema:**
   - `projectId: string`
   - `currentObjective: string`
   - `semanticAnchors: string[]` (e.g., ["Ender 6", "extruder", "stepper motor"])
   - `activeContext: Record<string, unknown>`
2. **Update `ToolUseContext`:**
   - Add `projectState?: ProjectState` to the `ToolUseContext` interface.
3. **Update `Orchestrator`:**
   - The orchestrator should be responsible for loading the `ProjectState` (perhaps from `active_project.md` or a database) and injecting it into the `ToolUseContext` for every tool call.
4. **Update `LLMAdapter` / `LLMInterface`:**
   - Ensure the `systemPrompt` or the tool-calling mechanism can leverage this `ProjectState` to provide better context to the model.

- This confirms that the `ToolUseContext` is the correct injection point for the proposed `ProjectState`.

### Conclusion & Proposal
The "Epiphany" is architecturally sound and addresses a fundamental gap in the current system: the lack of a persistent, high-level semantic anchor that can be programmatically injected into the tool execution context.

#### Proposed Changes:

1.  **`src/types.ts`**:
    - Define `ProjectState` interface.
    - Extend `ToolUseContext` to include `projectState?: ProjectState`.

2.  **`src/orchestrator/orchestrator.ts`** (or equivalent orchestration logic):
    - Implement a mechanism to load `ProjectState` from a persistent source (e.g., `active_project.md` or a database).
    - Inject this `ProjectState` into the `ToolUseContext` before calling `ToolExecutor.execute`.

3.  **`src/memory/store.ts`**:
    - Add methods to persist and retrieve `ProjectState`.

#### Impact:
- **Reduced Hallucinations:** By providing the agent with a "semantic bridge" (the `ProjectState`), the LLM can better interpret ambiguous terms within the context of the current project.
- **Improved Scalability:** The agent moves from reactive error correction to proactive context-aware execution.
- **Contextual Collaboration:** The agent becomes a "contextual collaborator" rather than a "passive observer".
