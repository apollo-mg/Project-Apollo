# Architectural Audit: Cache-to-Weight Ratio Optimization

## 1. Executive Summary
The current orchestration architecture prioritizes task distribution and capability matching but lacks a critical safety mechanism for memory-constrained environments. The "Epiphany" identifies a fundamental risk: maximizing parameter count without accounting for the KV cache headroom leads to inference instability and context truncation.

## 2. Current State Analysis
- **Scheduler Logic:** The `Scheduler` in `src/orchestrator/scheduler.ts` implements `hardware-aware` scheduling, but it is currently rudimentary, focusing on `vram_available` without considering the relationship between model weight size and the remaining VRAM required for the KV cache.
- **Type Definitions:** `AgentConfig` in `src/types.ts` lacks metadata regarding model weight size or precision (e.g., FP8 vs FP16), which is necessary to calculate the "Cache-to-Weight Ratio."
- **Risk:** In 16GB environments, deploying a 7B+ parameter model in FP16 or even a large FP8 model can leave insufficient VRAM for the KV cache, causing OOM errors or severe context degradation during long-running tasks.

## 3. Proposed Architectural Updates

### A. Data Model Enhancements (`src/types.ts`)
Update `AgentConfig` to include hardware-relevant metadata:
```typescript
export interface AgentConfig {
  readonly name: string;
  readonly model: string;
  readonly provider?: 'anthropic' | 'openai';
  readonly systemPrompt?: string;
  readonly tools?: readonly string[];
  readonly maxTurns?: number;
  readonly maxTokens?: number;
  readonly temperature?: number;
  // NEW FIELDS
  readonly modelWeightSizeGB?: number; // Estimated size of weights
  readonly precision?: 'fp8' | 'fp16' | 'bf16';
}
```

### B. Metric Implementation: Cache-to-Weight Ratio
Introduce a utility to calculate the stability metric:
`Ratio = (Total_VRAM - Model_Weight_Size) / Target_Context_Tokens`

### C. Scheduler Refinement (`src/orchestrator/scheduler.ts`)
Upgrade the `hardware-aware` strategy to implement the "7B FP8 Threshold" rule:
1. **Hard Limit:** If `Total_VRAM <= 16GB` and `Model_Weight_Size > 7GB` (for FP8), flag as "High Risk."
2. **Optimization Goal:** Instead of just finding "available VRAM," the scheduler should maximize the `Cache-to-Weight Ratio` to ensure the agent can handle the expected task complexity (context length).

## 4. Implementation Roadmap
1. **Phase 1 (Types):** Update `AgentConfig` and `Task` types to support weight/memory metadata.
2. **Phase 2 (Logic):** Implement the `calculateCacheHeadroom` utility.
3. **Phase 3 (Orchestration):** Refactor `Scheduler.scheduleHardwareAware` to use the new ratio-based scoring.
4. **Phase 4 (Validation):** Run stress tests in simulated 16GB environments to verify stability improvements.

## 5. Conclusion
Shifting the optimization metric from "Max Parameters" to "Cache-to-Weight Ratio" will transform the orchestrator from a simple task distributor into a memory-aware intelligence coordinator, ensuring reliability in edge and consumer-grade hardware environments.
