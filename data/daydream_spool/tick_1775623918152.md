# Architectural Audit: Hardware Capability Profile (HCP)

## 1. Epiphany Summary
The subconscious identified a performance gap between the OS-imposed power limits and the physical VBIOS ceiling. This gap represents "lost" performance due to software-defined constraints.

## 2. Audit Findings
- **Hardware:** AMD GPU detected.
- **Current State:**
    - `power1_cap` (Current): 374W
    - `power1_cap_default` (Default): 304W
    - `power1_cap_max` (VBIOS Ceiling): 374W
- **Discrepancy:** While the current limit is at the ceiling, the system's *default* behavior (304W) is significantly lower than the hardware's capability (374W). This confirms the "friction" described in the epiphany. A kernel update or system reset would likely revert the power envelope to the 304W default, causing a performance regression.

## 3. Proposed Architectural Update: Hardware Capability Profile (HCP)

### Objective
To automate the reconciliation of the power envelope, ensuring the system always operates at its maximum VBIOS-defined capability.

### Proposed Implementation: `hw-capability-reconciler`

#### A. Profile Definition (`/etc/apollo/hardware_profiles.json`)
A mapping of hardware identifiers (e.g., PCI IDs) to their maximum safe power limits.
```json
{
  "pci_ids": {
    "1002:xxxx": {
      "name": "AMD Radeon High-Perf",
      "max_power_watts": 374,
      "sysfs_path": "/sys/class/drm/card0/device/hwmon/hwmon2/power1_cap"
    }
  }
}
```

#### B. Reconciliation Logic (`/usr/local/bin/hw-reconciler.py`)
A lightweight Python script that:
1. Loads the `hardware_profiles.json`.
2. Identifies the current hardware via PCI scanning.
3. Compares the current `power1_cap` with the `max_power_watts` in the profile.
4. If `current < max`, it attempts to write the `max` value to the `sysfs_path`.

#### C. Automation (`/etc/systemd/system/hw-capability-reconciler.service`)
A systemd service that runs:
- `OnBoot`: To ensure immediate reconciliation after a reset.
- `OnFailure`: To recover if a driver update resets the limits.
- `Timer`: A periodic check (e.g., every 1 hour) to catch any runtime regressions.

## 4. Conclusion
The epiphany is validated. The current system is "unstable" in its performance profile because it relies on a manual or transient state to reach its full potential. Implementing the HCP will transform the power envelope from a "fixed boundary" into a "malleable tool."
