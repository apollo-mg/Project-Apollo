# Architectural Audit: Hardware-Aware Scheduling & Low-Level Optimization Gap

## 1. Executive Summary
The investigation confirms the Subconscious's "Epiphany": the current implementation of hardware-aware scheduling in the Apollo orchestrator is a high-level simulation that lacks the granularity required to leverage the performance frontier of new silicon (e.g., RX 9070 XT). While the system has a `hardware-aware` strategy, it relies on superficial metadata (VRAM availability) and string-matching in task descriptions, rather than interfacing with the low-level C++ kernel optimizations (WMMA, matrix math) that drive the current performance vanguard.

## 2. Audit Findings

### 2.1 Current Implementation Analysis
- **Location:** `src/orchestrator/scheduler.ts`
- **Strategy:** `hardware-aware`
- **Mechanism:** 
    - Uses a simulated `hardware_score` based on `agent.hardware_info.vram_available`.
    - Uses keyword matching (`task.description.includes('vram')`) to trigger hardware-specific logic.
- **Critical Flaw:** The implementation is "reactive" and "simulated." It treats hardware as a static resource pool rather than a dynamic execution environment. It fails to account for the specific architectural advantages of modern GPUs (like WMMA units) which are being optimized in the C++ layer (e.g., `llama.cpp`) faster than our high-level TypeScript abstractions can track.

### 2.2 Identified Gaps
| Feature | Current State (High-Level) | Target State (Low-Level Vanguard) |
| :--- | :--- | :--- |
| **Hardware Awareness** | VRAM capacity & string matching | Kernel-level capability (WMMA, Tensor Cores) |
| **Resource Mapping** | Static metadata in `AgentConfig` | Dynamic capability profiles via FFI/C++ Bridge |
| **Optimization Path** | Waiting for framework support | Direct integration with C++ kernel implementations |

## 3. Proposed Architectural Update

### 3.1 Phase 1: Capability-Based Modeling
Shift from `vram_available` to a `CapabilityProfile`.
```typescript
// Proposed AgentConfig extension
interface CapabilityProfile {
  compute_units: 'wmma' | 'tensor' | 'standard';
  precision_support: string[]; // e.g., ['fp16', 'bf16', 'int4']
  kernel_affinity: string[]; // e.g., ['llama.cpp-optimized', 'rocml-v1']
}
```

### 3.2 Phase 2: The Low-Level Bridge
Introduce a `HardwareAbstractionLayer` (HAL) that can interface with low-level drivers or C++ binaries. This bridge will allow the orchestrator to query actual hardware state and kernel availability.

### 3.3 Phase 3: Refactored Scheduler
Update `scheduleHardwareAware` to perform a multi-dimensional match between `TaskRequirement` and `AgentCapabilityProfile`.

## 4. Conclusion
To maintain competitive performance on next-generation silicon, Apollo must pivot from "simulating" hardware awareness to "integrating" with low-level hardware capabilities. The focus should shift toward building a robust bridge to the C++ optimization layer.

**Status:** Audit Complete. Implementation of `CapabilityProfile` and `HardwareAbstractionLayer` recommended.
