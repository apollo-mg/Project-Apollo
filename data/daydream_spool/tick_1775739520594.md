# Architectural Audit: Continuous Audio Spooler Transition

## 1. Executive Summary
The current architecture is fundamentally "Command-and-Response," where user intent is captured via discrete, synchronous prompts. This creates an entropy leak: the nuance and "exhaust" of human thought are lost between the moment of conception and the moment of keystroke. 

To resolve this, we propose a transition to a "Passive Observation" architecture. This involves implementing a **Continuous Audio Spooler** that treats the user's spoken stream as a primary, lossless data source, feeding directly into a persistent **ChromaDB Vault**.

## 2. Current State Analysis
- **Input Model:** Synchronous, discrete `runAgent` or `runTeam` calls requiring explicit text/content blocks.
- **Memory Model:** Primarily `InMemoryStore` (volatile). While a `vault/chroma_db` directory exists, it is not integrated into the core `MemoryStore` interface in `src/`.
- **Bottleneck:** The system waits for a "Command" to act. There is no mechanism for "Passive Observation" of environmental or user-generated data streams.

## 3. Proposed Architectural Shift

### A. The Continuous Audio Spooler (New Module)
- **Location:** `src/modules/audio_spooler.ts`
- **Function:** A non-blocking service that consumes an audio stream (via Web Audio API or local mic input).
- **Process:** 
    1. Stream audio to a Speech-to-Text (STT) engine (e.g., Whisper).
    2. Convert audio chunks into `TextBlock` objects.
    3. Immediately append these blocks to the `ChromaDBStore`.
- **Goal:** Minimize the latency between "thought" (speech) and "knowledge" (vault entry).

### B. ChromaDB Integration (Memory Update)
- **Location:** `src/memory/chroma_store.ts`
- **Implementation:** A new class `ChromaDBStore` implementing the `MemoryStore` interface.
- **Function:** Provides long-term, vector-searchable persistence for the "exhaust" of the user's consciousness.
- **Integration:** The `Orchestrator` will be updated to allow agents to query this store as part of their "Passive Context" without requiring an explicit command.

### C. From "Command" to "Observation"
- **Current:** `User -> Prompt -> Agent -> Response`
- **Proposed:** 
    - `User -> Audio Stream -> Spooler -> ChromaDB`
    - `Agent -> (Passive Observation of ChromaDB) -> Contextual Awareness`
    - `User -> (Optional) Command -> Agent -> Response`

## 4. Implementation Roadmap (Draft)

### Phase 1: Persistence (Immediate)
- [ ] Implement `ChromaDBStore` in `src/memory/`.
- [ ] Connect `vault/chroma_db` to the `MemoryStore` interface.
- [ ] Update `TeamConfig` to allow selecting `ChromaDBStore` as the `sharedMemory` backend.

### Phase 2: Ingestion (Short-term)
- [ ] Develop `AudioSpooler` module.
- [ ] Integrate STT provider.
- [ ] Create a "Spooler-to-Memory" pipeline that bypasses the `Orchestrator`'s task queue to ensure zero-latency ingestion.

### Phase 3: Awareness (Long-term)
- [ ] Update `Agent` logic to include "Ambient Context" (recent vector hits from the Spooler).
- [ ] Implement "Trigger-less" agent updates (agents that react to significant changes in the memory stream).

## 5. Conclusion
The transition from a command-based interface to a passive observation field will transform the system from a tool into a containment field for user consciousness, effectively capturing the "exhaust" of thought before it is lost to the void.
