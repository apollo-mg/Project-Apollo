# Architectural Audit: Semantic Significance Filter

## 1. Epiphany Analysis
The subconscious has identified a critical architectural flaw: **Temporal Saturation**. The system is currently recording every micro-event (the "heartbeat") with the same weight as substantive progress (the "signal"). This creates a "digital hall of mirrors" where the memory buffer and logs are filled with repetitive, low-entropy telemetry, potentially obscuring high-value reasoning or task progress.

## 2. Audit Findings
The audit of `src/agent/runner.ts` and `src/orchestrator/orchestrator.ts` confirms that the system is designed for high-fidelity event emission:
- **`AgentRunner.stream`** yields every `text` delta, `tool_use`, and `tool_result`.
- **`OpenMultiAgent.executeQueue`** emits `task_start`, `agent_start`, `task_complete`, and `agent_complete` events for every single unit of work.
- **`InMemoryStore`** (and potential future implementations) treats all `set` operations as equal, regardless of the semantic delta between the new value and the existing value.

The current architecture lacks a **Significance Layer** to differentiate between:
1. **System Pulse:** (e.g., "Agent X is thinking", "Task Y is in progress", "Tool Z called").
2. **Substantive Signal:** (e.g., "Task Y completed with result: [Data]", "New insight discovered").

## 3. Proposed Architectural Update: Semantic Significance Filter

I propose the implementation of a `SignificanceFilter` middleware within the `Orchestrator` and `AgentRunner` pipelines.

### A. Implementation Strategy
1. **Introduce `SignificanceLevel` Enum:**
   ```ts
   enum Significance {
     HEARTBEAT = 0, // Low-entropy, high-frequency (e.g., "running" status)
     SIGNAL = 1,    // Medium-entropy (e.g., tool calls, task transitions)
     INSIGHT = 2    // High-entropy (e.g., final task results, new knowledge)
   }
   ```

2. **Update `OrchestratorEvent` and `StreamEvent`:**
   Add a `significance` property to these interfaces to allow consumers (and the memory store) to prioritize or discard events.

3. **Implement `SignificanceEvaluator`:**
   A logic component that inspects event payloads.
   - **Heartbeat Detection:** If an event's content is identical to the previous event within a $T$ temporal window, downgrade its significance or suppress it.
   - **Semantic Delta Check:** For `MemoryStore` writes, only trigger a "Signal" if the `value` contains a significant change from the previous entry (using a lightweight hash or string similarity check).

4. **Configurable Filtering:**
   Allow the `OrchestratorConfig` to define a `minSignificance` threshold.
   - `minSignificance: SIGNAL` -> Suppresses all `HEARTBEAT` events.
   - `minSignificance: INSIGHT` -> Only records major milestones.

### B. Impact
- **Memory Efficiency:** Reduces the volume of data written to long-term memory/logs by an estimated 60-80% in high-concurrency scenarios.
- **Signal-to-Noise Ratio:** Improves the quality of the "context window" for agents by ensuring they are not distracted by their own operational telemetry.
- **Observability:** Allows for "Zoomable Logs" where users can toggle between seeing the raw pulse and the high-level progress.

## 4. Conclusion
The epiphany is valid. The system is currently "documenting its own pulse." Implementing a semantic significance filter is required to transition from a reactive logger to a proactive, goal-oriented intelligence.
