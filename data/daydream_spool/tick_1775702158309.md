# Architectural Audit: Workflow Schema Validation Failure

## 1. Findings Summary
The investigation confirms the "Epiphany" regarding a structural misalignment in the workflow execution engine. The current implementation of `parseTaskSpecs` in `src/orchestrator/orchestrator.ts` uses manual, shallow type checking which is insufficient for robust LLM-to-Machine communication.

### Key Vulnerabilities:
- **Weak Type Enforcement:** `parseTaskSpecs` (lines 111-149) only validates `title`, `description`, and `assignee`. It lacks validation for any other fields that might be introduced by the LLM (e.g., `start_at_step`, `sampler_name`, `scheduler`).
- **Type Mismatch Risk:** There is no mechanism to cast semantic descriptors (e.g., `"step 1"`) to integers (`1`) or to validate that string identifiers for samplers/schedulers match the backend's allowed enums.
- **Schema Fragility:** The `ParsedTaskSpec` interface is too restrictive and doesn't account for the metadata required for advanced orchestration, leading to a "translation failure" when the LLM attempts to communicate complex intent.

## 2. Proposed Architectural Changes

### A. Implement Zod-based Schema Validation
Replace the manual parsing logic in `src/orchestrator/orchestrator.ts` with a formal Zod schema. This will provide:
1. **Strict Type Casting:** Automatically convert numeric strings to integers for fields like `start_at_step`.
2. **Enum Validation:** Ensure `sampler_name` and `scheduler` values are strictly checked against allowed lists.
3. **Graceful Error Handling:** Provide clear error messages when the LLM's JSON output deviates from the expected structure.

### B. Update Core Types
Expand `ParsedTaskSpec` in `src/orchestrator/orchestrator.ts` (or `src/types.ts`) to include:
- `start_at_step: number`
- `sampler_name: string`
- `scheduler: SchedulingStrategy`

### C. Code Implementation Plan (Draft)

## 3. Conclusion
The current "bridge" between user intent and machine execution is indeed broken at the type-casting level. Moving from manual parsing to a schema-driven approach (Zod) is the necessary architectural evolution to prevent semantic misalignment and ensure system stability.
