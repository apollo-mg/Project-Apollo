# Epiphany Investigation: Dual-Layered Haunting
## Timestamp: 2025-05-22 (Simulated)
## Status: Initializing Audit

### Hypothesis
The system is experiencing a "shadow identity" issue where:
1. **Process Level:** Dead or zombie processes are holding onto resources or causing `OSError`.
2. **Filesystem/Module Level:** Duplicate directories or inconsistent paths are causing `sys.modules` to load stale or incorrect versions of modules, specifically affecting GGUF detection logic.

### Investigation Plan
1. **Audit Filesystem Structure:** Look for duplicate directory structures or redundant project copies that could lead to path ambiguity.
2. **Audit Process State:** Check for lingering processes related to the project.
3. **Audit Module Loading Logic:** Inspect how the system handles imports and path resolution, specifically looking for GGUF-related logic.
4. **Identify 'Shadow' Modules:** Check if multiple versions of the same module exist in the search path.

---
### Filesystem Audit Findings
- **Redundancy Detected:** Found `legacy_vault/infrastructure/` which contains several shell scripts and python files that seem to be older versions of deployment/infrastructure logic (e.g., `vllm_gatekeeper.sh`, `build_qwen35_sandbox.sh`).
- **Potential Shadow Identity:** The presence of `apollo.py` and `apollo.py.old` in the root directory suggests a manual versioning pattern that could easily lead to `sys.modules` confusion if the execution environment isn't strictly controlled.
- **Ambiguity:** The `legacy_vault` directory structure might be being inadvertently added to the `PYTHONPATH` or being imported by newer scripts, leading to the "shadow identity" described in the epiphany.

### Next Steps
1. Search for GGUF detection logic in the codebase to see if it's pulling from `legacy_vault` or the root.
2. Check for any scripts that modify `sys.path` or `PYTHONPATH`.
3. Check for running processes that might be "ghosts".
### GGUF Detection & Path Ambiguity Findings
- **Path Fragmentation:** GGUF models are scattered across multiple mount points:
    - `/mnt/TG_2TB/Projects/Apollo/models/`
    - `/mnt/TG_2TB/AI/Models/Qwen 3.5/...`
    - `/media/mark/AI_Fast/Models/GGUF/`
    - `/run/media/mark/Games 2TB/APOLLO_COLD_STORAGE/GGUF/`
- **Shadow Identity Risk:** The `forge_manager.py` script uses hardcoded paths to `/media/mark/AI_Fast/...`, while other scripts use `/mnt/TG_2TB/Projects/Apollo/models/...`. If a deployment script relies on one but the environment is configured for another, the "truth" of the model location is lost.
- **The "Ghost" Connection:** The `OSError` mentioned in the epiphany likely stems from a process attempting to access a model file on a mount point that has been unmounted or changed (e.g., `/media/mark/...` vs `/mnt/TG_2TB/...`), or a process holding a file descriptor to a model that was moved/replaced.

### Conclusion on "Shadow Identity"
The "shadow" is the discrepancy between the *intended* model path in the configuration and the *actual* filesystem state. When `sys.modules` loads a module that expects a specific path, and that path is actually a symlink or a different mount point, the module becomes a "shadow" that doesn't reflect the current system state.

### Proposed Architectural Fix
1. **Canonical Model Registry:** Implement a single `registry.json` that maps model IDs to absolute, verified paths.
2. **Environment Sanitization:** Before any deployment, a `pre_flight_check.sh` must:
    - Kill all processes matching the project signature.
    - Clear `__pycache__` and `venv` directories.
    - Verify all paths in the `registry.json` are currently mounted and accessible.
3. **Path Injection:** Use a single source of truth for `PYTHONPATH` and model paths, injected via environment variables rather than hardcoded strings in scripts.
