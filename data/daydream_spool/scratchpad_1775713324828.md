# Apollo Investigation: Warp Size Divergence (32 vs 64)

## Initial Hypothesis
The software abstraction layer (C10) defines `C10_WARP_SIZE` as 32. However, the hardware reality is 64. This discrepancy creates a "shadow divergence" where indexing logic (e.g., `threadIdx.x / 32`) will fail to account for the full hardware warp, leading to synchronization gaps or memory corruption in shared memory/shuffles.

## Investigation Update: Discovery of Divergence Mechanism
- Found evidence of the 32/64 divergence in `legacy_vault/infrastructure/compile_pytorch.sh` and `legacy_vault/SOVEREIGN_ENGINE_BUILD_LOG.md`.
- **The Mechanism:**
    - The build script `compile_pytorch.sh` performs a dual-patch:
        1. It forces `C10_WARP_SIZE` to `32` in `Macros.h` (the software abstraction).
        2. It forces `shared[C10_WARP_SIZE]` to `shared[64]` in normalization kernels (the hardware reality).
- **The Risk:**
    - This is a "brute-force" patch. While it fixes the `__shared__` memory allocation size (which requires a constant expression), it creates a massive logical gap.
    - Any kernel that uses `C10_WARP_SIZE` for indexing (e.g., `threadIdx.x / C10_WARP_SIZE` or `blockIdx.x * C10_WARP_SIZE`) will assume a warp is 32 threads.
    - If the hardware actually executes in 64-thread warps, the indexing will be off by a factor of 2, leading to:
        - **Synchronization Mismatches:** `__syncwarp()` or `__shfl_sync()` might operate on the wrong thread subsets.
        - **Memory Corruption:** Indexing into shared memory using a 32-based logic while the hardware expects 64-based alignment.
- **Conclusion:** The "Epiphany" is correct. This is not just a compilation fix; it is a manual divergence management that introduces significant risk of silent data corruption or synchronization failures in any kernel relying on `C10_WARP_SIZE` for anything other than array sizing.
