# Architectural Audit Report: Intelligence Location (DSP vs. Distributed)

## 1. Executive Summary
The subconscious epiphany identified a critical strategic tension: whether audio intelligence should reside in a dedicated, isolated DSP (Hardware-as-a-Service) or within a flexible, networked ecosystem (Software-defined-Hardware). 

An audit of the current codebase reveals that the repository is currently a high-level **Orchestration and Agent Framework**. It lacks any direct implementation of audio processing, hardware drivers, or signal processing modules. This confirms that the "conflict" is not yet present in the code, but is a **latent architectural risk** for any upcoming audio-centric features.

## 2. Audit Findings
- **Codebase Scope:** The repository focuses on LLM orchestration (`src/llm`), task management (`src/task`), and multi-agent coordination (`src/team`).
- **Missing Layer:** There is no `audio` or `hardware` module. The system is currently "hardware-agnostic" by omission, which is dangerous if developers begin assuming a specific ingestion model (e.g., assuming a local Linux audio pipeline is always available).
- **Risk Assessment:** Without a defined `Intelligence Location` strategy, future modules may inadvertently couple agent logic to a specific hardware paradigm (e.g., writing code that expects a local USB stream vs. code that expects a networked ESP32 stream).

## 3. Proposed Architectural Update
To resolve the tension identified in the epiphany, I propose the introduction of a **Processing Paradigm Configuration** within the system's core types.

### Proposed Change: `src/types.ts`
Introduce a `ProcessingParadigm` type to allow agents and orchestrators to adapt their behavior based on the hardware environment.

```typescript
/**
 * Defines the location and nature of intelligence for hardware-dependent tasks.
 */
export enum ProcessingParadigm {
  /** 
   * Dedicated, isolated DSP (e.g., XMOS USB array). 
   * Intelligence is local, low-latency, and "Black Box".
   */
  BLACK_BOX_DSP = 'BLACK_BOX_DSP',

  /** 
   * Flexible, networked ecosystem (e.g., ESP32/ESPHome). 
   * Intelligence is distributed, scalable, and "Software-defined".
   */
  DISTRIBUTED_NODE = 'DISTRIBUTED_NODE'
}

export interface HardwareContext {
  paradigm: ProcessingParadigm;
  latencyRequirement: 'ultra-low' | 'standard' | 'flexible';
  connectivity: 'local_bus' | 'networked';
}
```

## 4. Implementation Strategy
1. **Phase 1 (Definition):** Update `src/types.ts` with the `ProcessingParadigm` enum.
2. **Phase 2 (Contextualization):** Update the `Agent` and `Task` definitions to include an optional `HardwareContext`.
3. **Phase 3 (Execution):** When implementing audio-related tools (e.g., `src/tool/built-in/audio_stream.ts`), the tool must check the `HardwareContext` to decide whether to attempt a local device grab (USB) or a network request (MQTT/ESPHome).

## 5. Conclusion
The epiphany is a proactive warning. By formalizing the "Intelligence Location" in our type system now, we prevent the technical debt of choosing between "Black Box" and "Distributed" models mid-implementation.
