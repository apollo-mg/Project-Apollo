# Architectural Audit: Epiphany 1775546043874
## Subject: Transition from Package-Based Deployment to Atomic Node Validation

### 1. Epiphany Validation
The subconscious daemon's epiphany is **CORRECT**. 
The filesystem audit confirms that even within a ROCm-optimized environment (`venv_cachyos`), the dependency tree is heavily saturated with `torch.cuda` calls. Specifically, the `triton` package (a critical component for high-performance kernels) contains significant logic branches that explicitly check for `torch.cuda` availability and capability.

### 2. Audit Findings
- **Hard-coded CUDA Dependencies:** The `triton` package, which is essential for the performance of models like SAM2, contains deep-seated logic for NVIDIA drivers (`triton/backends/nvidia/driver.py`). While ROCm support exists, the "gravitational pull" of CUDA-centric code paths in these libraries creates overhead and potential failure points when the environment is not perfectly aligned.
- **The '6GB Choke' Mechanism:** The audit suggests that the "choke" is likely caused by libraries attempting to initialize CUDA-specific contexts or memory allocators (via `torch.cuda.synchronize()` or `torch.cuda.Event`) even when running on ROCm. This initialization can trigger unexpected memory allocations or driver-level handshakes that exceed the available 16GB partition's headroom before the actual model weights are even loaded.
- **Monolithic Assumption:** Current deployment patterns treat the entire stack (SAM2 + Impact Pack + Triton + PyTorch) as a single unit. When one node (e.g., a specific Triton kernel) attempts a CUDA-centric operation, it compromises the entire node's stability on RDNA 4.

### 3. Proposed Architectural Shift: Atomic Node Validation (ANV)
To prevent the '6GB choke' cycle, we must move away from monolithic environment loading.

#### Phase A: Dependency Decomposition
Instead of a single `requirements.txt` or monolithic environment, we will implement a **Node Manifest System**.
- Each functional component (e.g., `sam2_inference_node`, `impact_pack_processor`) will have its own `node_manifest.json`.
- This manifest will list required capabilities (e.g., `requires_rocm: true`, `max_vram_usage: 4GB`).

#### Phase B: Pre-Flight Atomic Audit
Before a workflow is dispatched to the 16GB partition, a **Validation Kernel** will:
1. **Scan for CUDA-Hardcoding:** Use a lightweight static analysis tool to scan the specific dependency sub-tree of the node for `torch.cuda` or `cuda` strings.
2. **Simulate Memory Footprint:** Calculate the theoretical VRAM footprint of the node's dependencies.
3. **Reject/Redirect:** If a node contains high-risk CUDA-centric calls that cannot be shimmed by ROCm, the node is flagged for "Emulation Mode" or rejected before it can cause a system-wide OOM/Choke.

### 4. Implementation Roadmap
1. **Immediate:** Create a `validation_shim.py` that intercepts `torch.cuda` calls and redirects them to `torch.hip` or returns `False` to prevent accidental CUDA context initialization.
2. **Short-term:** Implement the `Atomic Node Validation` script to audit `venv_cachyos` for high-risk patterns.
3. **Long-term:** Transition all workflow deployments to the Manifest-based system.
