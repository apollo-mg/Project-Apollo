### Investigation Progress
- Analyzed `server_qwen_moe_crash.log`.
- **Finding:** The log shows a successful model load of `Qwen3.5-35B-A3B-Base.i1-IQ2_M_mradermacher.gguf` (10.73 GiB) into 16GB VRAM.
- **Observation:** The model fits with ~4GB of free VRAM remaining (`llama_params_fit_impl: will leave 4161 >= 1024 MiB of free device memory`).
- **Risk:** While the *load* was successful, the "crash" mentioned in the filename suggests that during *inference* (especially with long context or high-throughput requests), the VRAM is likely exhausted. The context length is set to 262,144, which is massive and will definitely cause VRAM thrashing/OOM if the KV cache isn't managed or offloaded.

### Hypothesis
The "crash" is not a loading error, but a runtime OOM caused by the KV cache expansion or the MoE expert switching overhead during inference. The gap between the 10.7GB model and the 16GB VRAM leaves only ~5GB for the KV cache and activation buffers, which is insufficient for a 262k context window.

### Investigation Progress
- Analyzed `run_vllm_benchmark.sh`.
- **Finding:** The script explicitly sets `gpu_memory_utilization=0.80` to leave room for HIP graph capture. This confirms that memory management is a known concern for the current hardware (16GB VRAM).
- **Observation:** The use of `vllm` with `gpu_memory_utilization` suggests that the team is already aware of the need to cap memory usage to prevent crashes during graph capture or other overheads.
- **Gap:** There is no evidence of a *dynamic* or *standardized* offloading protocol. The current approach is "static capping" (leaving 20% free). This is a reactive strategy, not a proactive architectural one.

### Conclusion & Proposal
The "Epiphany" is correct: the gap between model scale and silicon capacity is a systemic issue. The current strategy of using `gpu_memory_utilization=0.80` is a "safe workflow" in a narrow sense, but it doesn't solve the problem of running models that *require* more than 80% of VRAM or managing multiple models.

**Proposed Architectural Update: The "Apollo Memory Orchestrator" (AMO)**
1. **Standardized Offloading Protocol:** Implement a tiered memory management system (VRAM -> System RAM -> NVMe) using `torch.device` and `accelerate`'s `device_map`.
2. **Dynamic KV Cache Management:** Instead of static capping, implement a protocol that scales the KV cache based on the available VRAM headroom, allowing for larger context windows when the model is small, and smaller windows when the model is large.
3. **Model-Aware Memory Profiles:** Define "Memory Profiles" for each high-parameter model (T5, CLIP, Wan, Qwen) that specify their optimal VRAM footprint and offloading thresholds.
4. **Pre-emptive Offloading:** Develop a background daemon (part of the `apollo_heartbeat.py` or similar) that monitors VRAM and proactively offloads inactive model weights to system RAM before an OOM occurs.
