# Epiphany Investigation: The Translation Tax
## Context
The subconscious has identified a shift in complexity when moving from ROCm/HIP to Tenstorrent. The friction is no longer in the build/driver layer but in the mathematical translation layer (operator legalization).

## Hypothesis
The "Translation Tax" is a measurable metric of the effort required to map high-level model operators to the specific primitives supported by the target hardware compiler (e.g., TT-Buda).

## Investigation Plan
1.  **Audit existing hardware-specific translation logic** (if any) in the codebase to see how we currently handle operator mapping.
2.  **Identify the "Geometry" of the target hardware** (Tenstorrent) as defined in our current architectural specs.
3.  **Propose a formal "Translation Tax Assessment" framework** to be used during the hardware selection phase.

## Initial Thoughts
- The shift from "building the engine" to "translating the logic" suggests that our engineering focus must move from DevOps/Systems Engineering toward Compiler/Mathematical Engineering.
- We need to quantify "legalization" effort.
## Findings
- **Codebase Audit**: I searched for mentions of "Tenstorrent", "TT-Buda", "ROCm", and "HIP". 
- **Existing Context**: The codebase contains references to ROCm/HIP in logs (`synthesizer_batch.log`), specifically noting hardware-level instability and kernel errors. This confirms the "low-level software stack" friction mentioned in the Epiphany.
- **Absence of Translation Logic**: There is currently no existing logic in the `src/` directory that handles mathematical operator mapping or "legalization" for specific hardware geometries. The current architecture focuses on agent orchestration, task scheduling, and LLM adaptation, rather than hardware-specific kernel translation.

## Conclusion
The Epiphany is valid. The current codebase is architected for high-level orchestration, but it lacks the "Translation Layer" required to manage the shift to specialized hardware like Tenstorrent. If we move to Tenstorrent, we will face a new class of "Translation Tax" that our current abstraction layers are not prepared to quantify or mitigate.

## Proposed Architectural Update: The "Translation Tax" Framework
I propose the introduction of a `HardwareAbstractionLayer` (HAL) module that includes:
1. **Primitive Registry**: A mapping of standard mathematical operators (e.g., `MatMul`, `Softmax`, `LayerNorm`) to hardware-supported primitives.
2. **Legalization Engine**: A service that analyzes a model's computational graph and calculates the "Tax" (the delta between standard operators and supported primitives).
3. **Complexity Score**: A metric used during the hardware selection phase to predict engineering effort.

## Action Plan
1. Create `src/hardware/primitive_registry.ts`.
2. Create `src/hardware/legalization_engine.ts`.
3. Integrate the `LegalizationEngine` into the model deployment pipeline to provide early warnings of high "Translation Tax".
