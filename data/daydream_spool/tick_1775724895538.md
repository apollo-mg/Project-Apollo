# Architectural Proposal: Telemetry-Driven "Thrash" Diagnostics

## 1. Executive Summary
The current agentic execution loop lacks visibility into the physical hardware's state. To fulfill the "Does it Thrash?" diagnostic requirement, we must transition from purely logical telemetry (tokens, turns) to physical telemetry (memory pressure, swap activity). This will allow us to identify the exact moment the hardware's physical reality collapses under the weight of the model weights.

## 2. Proposed Changes

### A. Type Definitions (`src/types.ts`)
Introduce a `TelemetryData` interface and update `RunOptions` to include a telemetry callback.

```typescript
export interface TelemetryData {
  timestamp: number;
  mem_used_kb: number;
  swap_used_kb: number;
  mem_free_kb: number;
  swap_free_kb: number;
  turn: number;
  active_tool?: string;
}

export interface RunOptions {
  // ... existing options
  /** Fired periodically with system resource telemetry. */
  readonly onTelemetry?: (data: TelemetryData) => void;
  /** Frequency of telemetry sampling in milliseconds. Defaults to 1000ms. */
  readonly telemetryInterval?: number;
}
```

### B. Core Logic Update (`src/agent/runner.ts`)
Modify `AgentRunner.stream` to manage a background telemetry sampling loop.

1. **Initialization:** Inside `stream()`, initialize a `telemetryInterval` based on `options.telemetryInterval`.
2. **Sampling Logic:** Use `fs.readFileSync('/proc/meminfo')` (for Linux environments) to parse memory and swap statistics. This is more efficient than spawning a `free` process repeatedly.
3. **Execution:**
   - Start the interval at the beginning of the `while(true)` loop.
   - Capture the `active_tool` by tracking the current tool name during the tool execution phase.
   - Invoke `options.onTelemetry?.(data)`.
4. **Cleanup:** Use a `finally` block to ensure `clearInterval()` is called, preventing memory leaks when the runner finishes or is aborted.

### C. Implementation of Memory Parsing (Internal Helper)
A private helper method `parseMemInfo(content: string): TelemetryData` will be added to `AgentRunner` to transform the raw `/proc/meminfo` string into the structured `TelemetryData` object.

## 3. Impact Analysis
- **Performance:** Minimal. Reading `/proc/meminfo` is a low-overhead filesystem operation.
- **Complexity:** Low. It leverages existing `RunOptions` patterns.
- **Observability:** High. Provides the necessary data to define the "Thrash" boundary.

## 4. Verification Plan
1. **Unit Test:** Mock `/proc/meminfo` and verify the parser correctly calculates `mem_used_kb` and `swap_used_kb`.
2. **Integration Test:** Run `examples/apollo_cli.ts` with a custom `onTelemetry` callback that logs to a file.
3. **Stress Test:** Execute a large model (e.g., Gemma 4 26B) and verify that the telemetry logs show increasing swap usage as the system approaches the thrash state.
