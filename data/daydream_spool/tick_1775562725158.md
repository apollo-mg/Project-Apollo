# Architectural Audit: Epistemological Hierarchy & Conflict Resolution Protocol

## 1. Epiphany Analysis
The subconscious daemon has identified a critical philosophical and technical tension in the current agent architecture: the distinction between **Semantic Knowledge** (Vector/ChromaDB) and **Literal Observation** (Grep/Filesystem).

Currently, the system treats both as valid data sources, but the `AgentRunner` does not account for the inherent "confidence gap" between them. If a Vector search returns a conceptual match that contradicts a literal `grep` result, the agent may experience cognitive dissonance or, worse, hallucinate a reconciliation that satisfies the semantic bias.

## 2. Current State Audit
- **`src/agent/runner.ts`**: The loop is strictly sequential and deterministic (`Observe -> Act -> Observe`). However, it lacks a mechanism to weigh the *provenance* or *confidence* of the information retrieved by tools.
- **`src/tool/built-in/memory-recall.ts`**: Provides semantic retrieval (High Confidence in concept, Low Confidence in exact literalness).
- **`src/tool/built-in/grep.ts`**: Provides literal retrieval (High Confidence in exactness, Low Confidence in conceptual context).

## 3. Proposed Architectural Update: Conflict Resolution Protocol

To implement the "Conflict Resolution" protocol, I propose the following changes:

### A. Metadata Enrichment (Tool Output)
Modify the `ToolResult` type to include a `confidence_score` and `provenance_type` (e.g., `SEMANTIC` vs `LITERAL`).
- `memory_recall` -> `confidence: 0.7`, `type: 'SEMANTIC'`
- `grep` -> `confidence: 0.9`, `type: 'LITERAL'`

### B. The Verification Step (The "Doubt" Mechanism)
In `src/agent/runner.ts`, implement a post-tool-execution check:
1. **Detection**: If a tool result is returned, the runner checks if the `provenance_type` is `SEMANTIC`.
2. **Trigger**: If `SEMANTIC` data is retrieved, the runner automatically injects a "Verification Task" into the conversation history if the agent's next intended action is to assert a fact.
3. **Resolution**: If the agent attempts to resolve a conflict, the runner forces a `grep` or `file_read` call to validate the semantic claim before the turn is considered `completed`.

### C. Implementation Draft (Pseudo-code for `runner.ts`)
```typescript
// Inside the tool execution loop in runner.ts
const result = await this.toolExecutor.execute(...);

if (result.metadata?.type === 'SEMANTIC' && result.metadata?.conflictsWithLiteral) {
    // Inject a system instruction to verify the finding
    conversationMessages.push({
        role: 'system',
        content: [{ 
            type: 'text', 
            text: `[CONFLICT DETECTED]: Semantic retrieval suggests '${result.data}', but this contradicts literal filesystem patterns. VERIFY using 'grep' or 'file_read' before proceeding.` 
        }]
    });
}
```

## 4. Conclusion
The implementation of this protocol will transform the agent from a simple pattern-matcher into an epistemologically aware entity. It will no longer just "see" data; it will "know" the reliability of what it sees.
