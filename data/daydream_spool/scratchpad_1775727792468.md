# Epiphany Investigation: Harvester JSONL Standardization
## Timestamp: 2025-05-22 (Simulated)
## Status: Investigating

### Hypothesis
The 'Harvester' (the component responsible for turning raw interaction into portable intelligence) may be using a schema that is optimized for small-scale local training (7B) but lacks the structural richness required for high-parameter models (32B+). 

If the schema is too flat or lacks metadata (context, intent, reasoning traces), the transition to the 'Cloud' (larger models) will require a heavy re-processing step to inject the necessary depth.

### Investigation Plan
1.  **Locate the Harvester:** Identify the code responsible for data ingestion and JSONL generation.
2.  **Audit Current Schema:** Examine existing `.jsonl` files in the `data/` or `training_` directories to see what is actually being recorded.
3.  **Analyze Ingestion Logic:** Check the code that writes these files to see if it's hardcoded to a specific, limited schema.
4.  **Propose Standardization:** If a discrepancy is found, draft a schema that includes:
    -   `instruction`
    -   `input`
    -   `output`
    -   `metadata` (model_version, timestamp, context_window_usage, reasoning_trace)
    -   `system_prompt` (to ensure consistency across model scales)
### Findings
- **Current Schema Analysis:** The `training_success.jsonl` file uses a very flat schema: `{"prompt": "...", "response": "...", "expected_tag": "..."}`.
- **Gap Analysis:** This schema is insufficient for high-parameter model training (32B+). It lacks:
    - `system_prompt`: To define the persona/constraints.
    - `context`: To provide the necessary background for complex reasoning.
    - `thought_process` or `reasoning_trace`: Crucial for training models to "think" before acting (Chain of Thought).
    - `metadata`: To track which model version generated the response and the specific tool/environment context.
- **Harvester Status:** The "Harvester" mentioned in the Epiphany seems to be a conceptual or legacy component (found in `legacy_vault` or `archive`). There is no active `harvester.py` in the root that is currently generating these files, suggesting the "Harvester" might be a logic pattern or a script that needs to be re-implemented/standardized to feed the training pipeline.

### Conclusion
The Epiphany is correct. The current training data is "shallow." To enable "Cloud Bursting" (seamlessly moving from 7B to 32B), we must upgrade the ingestion pipeline to produce a "Deep JSONL" schema.

### Proposed Architectural Update: "Deep JSONL" Schema
I propose the following schema for all future Harvester outputs:
```json
{
  "id": "uuid",
  "timestamp": "iso8601",
  "system_prompt": "...",
  "context": {
    "conversation_history": [...],
    "environment_state": {...},
    "tool_outputs": [...]
  },
  "instruction": "...",
  "thought_trace": "...", 
  "response": "...",
  "metadata": {
    "model_scale": "7B",
    "source": "local_interaction",
    "complexity_score": 0.8
  }
}
```
This ensures that when we move to 32B, the model isn't just learning *what* to say, but *how* to reason through the context provided.

### Action Plan
1. **Implement `harvester_v2.py`**: A new script that implements this deep schema.
2. **Refactor Ingestion**: Update `ingest_chats.py` or similar scripts to use the new schema.
3. **Backfill (Optional)**: Create a script to enrich existing `training_success.jsonl` entries with basic metadata to maintain consistency.
