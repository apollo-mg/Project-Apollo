# Architectural Audit: SDMA-Native Data Paths for RDNA 4 (GFX1201)

## 1. Epiphany Validation
The subconscious epiphany regarding the synergy between SDMA (System Direct Memory Access) and RDNA 4 is **architecturally sound** and supported by historical telemetry. 

The "friction" identified in previous RDNA 4 deployments (specifically the `gfx1201` target) was not merely a compute bottleneck, but a data movement bottleneck. While the `rdna4_tilelang_postmortem.md` highlights the Wave32/Wave64 mismatch in matrix compute, the `rdna4_rocm_stability.md` reveals a more fundamental issue: the instability of SDMA during Host-to-Device transfers (`HSA_ENABLE_SDMA=0` was used as a workaround).

## 2. Audit Findings

### A. The SDMA/Bandwidth Paradox
Current architectural patterns rely on standard ROCm/HIP memory copies. As model weights transition to FP8/FP4 to increase parameter density, the sheer volume of data being moved from Host to Device (and between VRAM banks) will hit a "transfer wall" if we rely on standard CPU-orchestrated DMA.

### B. Identified Friction Points
- **Alignment Issues:** `rdna4_rocm_stability.md` notes that `.contiguous()` is required to bypass DMA alignment bugs. This indicates that the current data path is not "transparent" but requires manual tensor manipulation to satisfy the hardware.
- **SDMA Instability:** The existence of `HSA_ENABLE_SDMA=0` in `start_architect.sh` proves that the SDMA engine was previously treated as a liability rather than an asset. This is the exact "friction" the epiphany describes.

## 3. Proposed Architectural Shift: "Transparent Conduit" Protocol

To realize the epiphany, we must move from *managing* memory transfers to *orchestrating* SDMA-native paths.

### Phase 1: SDMA-Native Tensor Layouts
Instead of forcing `.contiguous()` at the application layer, we must implement a kernel-level layout engine that prepares tensors in SDMA-friendly, aligned blocks. This eliminates the "alignment friction" noted in the stability logs.

### Phase 2: Asynchronous Weight Streaming (FP8/FP4)
As we scale to FP8/FP4, we must implement a "Pre-fetch & Stream" architecture. 
- **Mechanism:** Use SDMA to asynchronously stream the next layer's weights into a dedicated "Shadow Buffer" on the RDNA 4 device while the current layer is computing.
- **Goal:** The compute engine should never wait for a `hipMemcpy`. The hardware should act as a "transparent conduit" where weights are already present in the local cache/LDS by the time the kernel is dispatched.

### Phase 3: TileLang Backend Integration
We must resolve the `mai-insts` and Wave32 mapping issues identified in the `rdna4_tilelang_postmortem.md`. The goal is to allow TileLang to generate kernels that utilize SDMA for data movement *within* the kernel (e.g., loading tiles directly from global memory to LDS via SDMA-optimized instructions).

## 4. Conclusion
The epiphany is correct. The breakthrough is not in faster math, but in the disappearance of the data-transfer latency. We must prioritize SDMA-native data paths to ensure that the bandwidth of our transfer protocols scales linearly with the density of our quantized weights.

**Status:** *Audit Complete. Transitioning to Implementation Design.*
