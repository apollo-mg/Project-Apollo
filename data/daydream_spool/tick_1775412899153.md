# Architectural Audit: Flux Sampling vs. Attention Kernel Instability

## Epiphany Summary
The current Flux sampling logic (Memory 1) is being implemented on a computational foundation (Memory 2) that is experiencing significant instability due to a version mismatch between Triton/Flash-Attention and the underlying PyTorch/ROCm environment. The pursuit of optimized kernels is currently causing system-wide failures rather than performance gains.

## Findings
- **Kernel Instability:** The audit confirms that the environment is heavily reliant on custom ROCm/PyTorch builds (e.g., `rocm/vllm-dev:rocm7.2...pytorch_2.9`).
- **Version Mismatch:** The logs indicate a history of attempting to reconcile specific PyTorch versions (2.4.0, 2.9) with ROCm 7.1/7.2, which creates a high risk of "misaligned transmission" in the attention mechanism.
- **Optimization Risk:** Attempts to use `flash_attn` or highly optimized SDPA kernels are currently acting as a source of failure rather than a performance booster.

## Architectural Proposal

### 1. Immediate Stability Mandate (The "SDPA Fallback" Protocol)
Until the Triton/Flash-Attn version mismatch is resolved, all deployment scripts and sampling pipelines must be forced to use the PyTorch `scaled_dot_product_attention` (SDPA) fallback mechanism. 

**Action:**
- Prohibit the use of `flash_attn` in all production/lab deployment scripts.
- Implement a strict check in the model loading sequence: if `flash_attn` is detected or requested, the system must automatically revert to the standard PyTorch SDPA implementation to ensure stability.

### 2. Codebase Update Strategy
- **Constraint Enforcement:** Add a configuration flag `STRICT_STABILITY_MODE = True` in the core sampling module. When enabled, this flag will disable all non-standard attention kernels.
- **Audit Logging:** Log every instance where the system falls back to SDPA to track the "performance tax" being paid for stability.

### 3. Long-term Resolution
- The mismatch between the Triton kernels and the ROCm-optimized PyTorch binaries must be addressed by synchronizing the `vllm` and `torch` versions specifically for the target ROCm version (7.2).
