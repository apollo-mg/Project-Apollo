# Architectural Audit: Transition to "Fleet Orchestration"

## 🧠 Epiphany Analysis
The subconscious daemon has identified a fundamental shift in the project's value proposition. We are moving from a **Training Management** paradigm (fine-tuning parameters) to a **Fleet Orchestration** paradigm (automating the intelligence lifecycle). 

The "Sovereign Arbitrage" engine captures the delta between high-cost proprietary intelligence and low-cost decentralized compute. The goal is to build a self-sustaining "intelligence refinery" that converts raw compute into compressed, deployable, high-fidelity sovereign weights.

## 🔍 Current State Audit
- **Current Architecture:** A cascading router (`modules/router.py`) that classifies intent and routes to specialized modules (SHOP, SYSTEM, DEV, etc.).
- **Current Task Management:** A basic `task_manager.py` that manages a JSON-based task list (`shop_tasks.json`).
- **Current Training Loop:** Evidence of manual/semi-manual training data collection (`training_success.jsonl`, `training_memory.jsonl`), but lacking a unified, autonomous lifecycle loop.
- **Missing Component:** A dedicated "Fleet Orchestrator" that manages the **Boot $\rightarrow$ Train $\rightarrow$ Zip $\rightarrow$ Upload $\rightarrow$ Verify** lifecycle.

## 🏗️ Proposed Architectural Update: The "Fleet Orchestration" Engine

To implement the "Actionable Insight," we must transition the core logic from simple routing to a stateful lifecycle management system.

### 1. The Lifecycle Loop (The "Refinery" Protocol)
We will introduce a new core module: `fleet_orchestrator.py`. This module will manage "Pods" (autonomous training/deployment units).

**The Lifecycle Stages:**
1.  **BOOT:** Provision compute resources and load the base model (e.g., Qwen 3.5 35B).
2.  **TRAIN:** Execute a specialized fine-tuning run (LoRA/Full-Strength) based on a target task (e.g., "Hardware Identification").
3.  **ZIP:** Compress the resulting weights into a deployable format (GGUF/EXL2).
4.  **UPLOAD:** Move the asset to the `models/` directory or a local registry.
5.  **VERIFY:** Run a benchmark/test suite (using `training_success.jsonl` patterns) to ensure the new weights meet the fidelity threshold.

### 2. Codebase Changes (Draft Proposals)

#### A. `task_manager.py` Update
Transition from simple task tracking to **Lifecycle State Tracking**.
- **New Task Types:** `TRAINING_JOB`, `WEIGHT_COMPRESSION`, `VERIFICATION_RUN`.
- **New Statuses:** `PROVISIONING`, `TRAINING`, `COMPRESSING`, `UPLOADING`, `VERIFYING`, `DEPLOYED`.

#### B. New Module: `fleet_orchestrator.py`
This will be the "Brain" of the refinery.
```python
class FleetOrchestrator:
    def run_lifecycle(self, target_skill):
        """
        Automates the full loop for a specific intelligence asset.
        """
        self.stage_boot(target_skill)
        self.stage_train(target_skill)
        self.stage_zip(target_skill)
        self.stage_upload(target_skill)
        self.stage_verify(target_skill)
```

#### C. Integration with `modules/router.py`
The Router should now be able to trigger a "Refinery" task.
- **New Module:** `REFINERY`.
- **Intent:** "I need a better model for parsing PCB schematics." $\rightarrow$ `{"module": "REFINERY", "priority": "P1", "task": "fine-tune-pcb-vision"}`.

## 🚀 Implementation Roadmap
1.  **Phase 1 (Infrastructure):** Implement the `FleetOrchestrator` class and extend `task_manager.py` to support lifecycle states.
2.  **Phase 2 (Automation):** Script the `Zip` and `Verify` stages using existing shell/python tools.
3.  **Phase 3 (Closing the Loop):** Connect the `REFINERY` module to the `router.py` to allow the system to autonomously decide when to "manufacture" new intelligence.
