# Architectural Audit: Modular Workflow Conversion Template

## 1. Executive Summary
The investigation confirms the validity of the "Epiphany." The current workflow management paradigm relies on monolithic JSON files that are difficult to adapt to emerging model architectures (e.g., Wan 2.1/2.2). The transition from monolithic loaders (like `CheckpointLoader`) to a decoupled "triad" (`UnetLoaderGGUF`, `CLIPLoader`, `VAELoader`) is necessary for hardware-optimized and architecture-specific deployments.

## 2. Audit Findings
- **Current State:** Workflows are stored as static JSON files (e.g., `wan_2.2_t_2_v_working.json` found in chat history).
- **Node Structure:** Existing workflows for Wan 2.2 already utilize a modular approach (using `UNETLoader`, `VAELoader`, and `CLIPLoader`), but there is no formal specification or template to guide this conversion from older, monolithic formats.
- **Missing Component:** There is no centralized "Modular Conversion Template" or "Substitution Map" in the `Apollo` codebase to automate or standardize the rewiring of conditioning logic.

## 3. Proposed Architectural Update: The "Modular Conversion Template"
I propose the creation of a `WORKFLOW_MAPPING.md` or a structured JSON schema that serves as a "Wiring Diagram" for model adaptation.

### Proposed Mapping Schema (Conceptual)
| Source Node (Monolithic) | Target Node Triad (Modular) | Required Input/Output Mapping |
| :--- | :--- | :--- |
| `CheckpointLoader` | `UnetLoaderGGUF` | `MODEL` -> `MODEL` |
| | `CLIPLoader` | `CLIP` -> `CLIP` |
| | `VAELoader` | `VAE` -> `VAE` |
| `Load Checkpoint` | `UnetLoader` | `MODEL` -> `MODEL` |
| | `CLIPLoader` | `CLIP` -> `CLIP` |
| | `VAELoader` | `VAE` -> `VAE` |

### Implementation Strategy
1. **Define the Template:** Create a formal document mapping common monolithic nodes to their modular counterparts.
2. **Parameter Mapping:** Explicitly define which widget values (e.g., `weight_dtype`, `device`) must be migrated during the "rewiring" process.
3. **Automation Path (Future):** This template can eventually be ingested by a script to perform automated JSON transformations (Search & Replace nodes + Re-link inputs/outputs).

## 4. Conclusion
The "Epiphany" is a critical architectural insight. Moving from "searching for files" to "assembling systems" via a modular template will significantly reduce the friction of adopting new model architectures.
