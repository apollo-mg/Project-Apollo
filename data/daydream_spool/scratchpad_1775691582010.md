## Epiphany Analysis
The epiphany suggests a race condition in command lifecycle management. Specifically, the system uses list membership (e.g., `pending_commands`) as a proxy for validity, which fails when an Interrupt Service Routine (ISR) and a timeout watchdog attempt to handle the same command simultaneously.

**Core Problem:**
- Command state is being managed procedurally (sequence of events).
- Lack of atomicity in state transitions.
- Race condition between hardware completion and software timeout.

**Proposed Solution:**
- Implement an atomic state machine within the command structure.
- Use Compare-and-Swap (CAS) to transition states.
- Ensure only one context (ISR or Watchdog) can claim the `COMPLETING` state.

## Detailed Analysis of `queue.ts`
The `update` method (lines 107-119) is a major red flag. It performs a shallow merge and then overwrites the task in the map:

```typescript
107  update(
108    taskId: string,
109    update: Partial<Pick<Task, 'status' | 'result' | 'assignee'>>,
110  ): Task {
111    const task = this.requireTask(taskId)
112    const updated: Task = {
113      ...task,
114      ...update,
115      updatedAt: new Date(),
116    }
117    this.tasks.set(taskId, updated)
118    return updated
119  }
```

**The Race Condition:**
If two contexts (e.g., a worker completing a task and a watchdog timing it out) call `complete(taskId)` and `fail(taskId)` nearly simultaneously:
1. Context A calls `complete(taskId)`.
2. Context A calls `update(taskId, { status: 'completed' })`.
3. Context B calls `fail(taskId)`.
4. Context B calls `update(taskId, { status: 'failed' })`.

Because `update` is not atomic relative to the *state check*, if `complete` and `fail` are called in rapid succession, the second one might overwrite the first, or worse, if the logic relied on the *previous* state to decide whether to proceed, the lack of a CAS (Compare-and-Swap) mechanism means we can't guarantee that we are transitioning from a valid state.

Specifically, `complete` (line 130) and `fail` (line 149) both call `update` without checking if the task is already in a terminal state. While `cascadeFailure` (line 166) checks `task.status !== 'blocked' && task.status !== 'pending'`, the `complete` and `fail` methods themselves do not.

**The "Identity Crisis":**
The epiphany mentions: *"We are treating the command's lifecycle as a sequence of procedural events rather than a single, atomic transition of state."*

This is exactly what's happening. `complete()` is a procedure: `update` -> `emit` -> `unblock`. If two procedures run, they both try to `update`.

## Proposed Architectural Change
Instead of `update(taskId, partial)`, we need a `transition(taskId, expectedStatus, newStatus)` method.

**New `transition` logic (Pseudo-code):**
```typescript
transition(taskId, expectedStatus, newStatus): Task {
  const task = this.requireTask(taskId);
  if (task.status !== expectedStatus) {
    throw new Error(`Invalid transition: expected ${expectedStatus}, got ${task.status}`);
  }
  // Perform atomic update...
}
```

However, since this is TypeScript/JavaScript (single-threaded event loop), "atomicity" in the multi-threaded sense (CPU instructions) isn't the issue, but "logical atomicity" in the event loop is. If an `await` or an asynchronous event occurs between the check and the update, the state could change.

Wait, the epiphany mentions "ISR" and "watchdog". In a real system, these are concurrent. In this simulation/codebase, they are likely asynchronous tasks.

**Actionable Plan:**
1. Modify `Task` type to include a version or a more robust state.
2. Implement `compareAndSwapStatus(taskId, expectedStatus, newStatus)`.
3. Refactor `complete` and `fail` to use this CAS.
4. Ensure `cascadeFailure` also respects this.
