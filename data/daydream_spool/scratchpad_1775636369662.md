# Apollo Investigation: Drift Threshold Protocol
## Epiphany Analysis
The subconscious suggests that as model scale increases (0.8B -> 4B), the risk of "Instruction Drift" (loss of structural compliance) increases, which is catastrophic for automated triage.

## Objectives
1. Map the model integration pipeline (The "Foundry").
2. Locate the triage layer implementation.
3. Identify existing JSON schema validation mechanisms.
4. Propose a "Drift Threshold" validation step.

## Findings
- The current validation architecture is **reactive**: it validates tool arguments *after* the model has generated them.
- There is no **proactive** validation of the model's ability to adhere to the system prompt or JSON schema *before* it is deployed into a critical role (like triage).
- The `Agent` class (in `src/agent/agent.ts`) lazily creates an `AgentRunner` via `getRunner()`. This is the point where the model configuration is finalized.

## Hypothesis
The "Drift Threshold" protocol should be implemented as a validation step within the `Agent` or `AgentRunner` lifecycle, or as a separate `ComplianceGuard` service that must be passed to the `Agent` constructor.

## Proposed Architecture: `ComplianceGuard`
1. **`ComplianceGuard` Class**: A new service that holds a set of "Golden Prompts" (standardized tasks with expected JSON outputs).
2. **`DriftThreshold` Protocol**:
   - Before an `Agent` is allowed to transition from `idle` to `running` in a high-stakes context, the `ComplianceGuard` runs a `validateModelAdherence(model, systemPrompt)` check.
   - This check executes the Golden Prompts and verifies that the model's output matches the expected JSON schema with a high degree of structural accuracy.
   - If the model fails (e.g., produces invalid JSON or misses required fields), the `Agent` is flagged as "Drifted" and prevented from executing triage tasks.
