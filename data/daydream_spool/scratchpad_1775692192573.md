## Findings: Deep Dive
- `src/orchestrator/scheduler.ts` implements a `hardware-aware` strategy.
- The current implementation of `scheduleHardwareAware` (lines 325-359) is very primitive:
    - It checks if the task description contains "vram" or "memory" to set `needsHighVram`.
    - It then sorts agents by `availableVram` if `needsHighVram` is true.
- **The Problem:** The current logic is binary and reactive. It doesn't allow for the "Sensory Fidelity vs. Reasoning Depth" trade-off mentioned in the Epiphany. It only looks at *available* VRAM, not the *ratio* of VRAM used by the "Dreamer" (World Model) vs. the "Engineer" (LLM).
- The Epiphany suggests that we should be able to compress the "Engineer" (quantization) to save VRAM for the "Dreamer" (World Model).
- Currently, there is no explicit distinction in the code between a "World Model" agent and an "Engineer" agent, nor is there a mechanism to adjust their quantization/resolution based on VRAM pressure.

## Proposed Architectural Change
1. **Introduce Agent Types:** Explicitly define `AgentType.WORLD_MODEL` and `AgentType.ENGINEER` in `src/types.ts`.
2. **Enhance Hardware-Awareness:**
    - Instead of just checking `needsHighVram`, the scheduler should evaluate the *composition* of the task.
    - If a task requires high sensory fidelity (e.g., "visual simulation", "high-res"), it should be prioritized for agents with high VRAM, and the "Engineer" component of that task should be instructed to use a lower-precision/quantized model.
3. **VRAM Tetris Logic:**
    - Implement a mechanism where the `Scheduler` can suggest quantization levels for the `Engineer` based on the `World Model`'s requirements.
    - This requires the `AgentConfig` to support a `quantization_preference` or similar field.
