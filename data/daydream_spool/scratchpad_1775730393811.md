The system is experiencing a "Heisenberg" failure mode where the telemetry mechanism (likely CUDA memory polling) is being executed within the same context/thread as the primary workload. During high VRAM pressure, the overhead of the telemetry call triggers a context switch or a synchronization point that causes a CUDA OOM or a timeout, which then triggers a traceback, which then triggers more telemetry, creating a loop.

## Investigation Findings: The "Observer Effect" Confirmed

### Root Cause Analysis
The `CognitiveEscalation` module (`modules/cognitive_escalation.py`) implements a monitoring loop that uses `psutil` and `subprocess.run(['ping', ...])` to gather system health metrics. 

**The Recursive Failure Loop:**
1. **Trigger:** A system error occurs (e.g., VRAM pressure or a CUDA OOM).
2. **Detection:** The `CognitiveEscalation` module's `_get_system_health` method is called.
3. **The Observer Effect:** 
    - `psutil.cpu_percent(interval=1)`: This call **blocks the thread for 1 second**. In a high-pressure environment, this blocking call can cause timeouts in other critical threads (like the orchestrator or the model's inference loop).
    - `subprocess.run(['ping', ...])`: This spawns a new process. Spawning a process during high VRAM/CPU pressure adds significant overhead and context-switching latency.
    - `psutil.virtual_memory()`: While relatively lightweight, it still requires a syscall.
4. **The Loop:** The overhead of these monitoring calls (especially the 1-second block and the process spawning) contributes to the very instability (latency/timeouts) that triggers the "Critical Error" detection, leading to a recursive loop of monitoring-induced failures.

### Architectural Flaw
The telemetry is **synchronous and blocking**. It is integrated into the same execution flow that handles error detection and escalation. When the system is under stress, the act of checking the stress makes the stress worse.

## Proposed Architectural Update

### 1. Decouple Telemetry (Asynchronous Monitoring)
- Move `_get_system_health` to a dedicated, low-priority background thread or a separate process.
- Use a non-blocking "Shared State" (e.g., a `multiprocessing.Value` or a simple thread-safe singleton) where the monitor writes the latest metrics and the `CognitiveEscalation` module only **reads** the last known state.

### 2. Implement Predictive Memory-Budgeting
- Instead of polling `psutil` or `torch.cuda` during a crisis, the system should maintain a "Running Budget" based on:
    - `Estimated_Allocation = Current_Usage + Next_Task_Requirement`
- This allows the `CognitiveDispatcher` to reject or reroute tasks *before* the OOM occurs, rather than reacting to it.

### 3. Replace Heavyweight Probes
- Replace `subprocess.run(['ping', ...])` with a lightweight socket-based latency check.
- Replace `psutil.cpu_percent(interval=1)` with a non-blocking `psutil.cpu_percent(interval=None)` call that calculates the delta since the last call, avoiding the 1-second block.
