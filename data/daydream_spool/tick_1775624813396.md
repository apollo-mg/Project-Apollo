# Architectural Audit: Modality-Aware Resource Allocation

## 1. Problem Statement
The current architecture utilizes static `maxTokens` configurations within the `AgentRunner` and `LLMAdapter` implementations. When processing vision-based inputs (via `ImageBlock`), the resulting token density and output complexity often exceed the pre-allocated "memory geometry" (buffers/limits), leading to 500 errors. This is a spatial conflict between the model's perception (vision tokens) and the fixed capacity of the execution buffers.

## 2. Root Cause Analysis
- **Static Allocation:** `AgentRunner` (in `src/agent/runner.ts`) and `AnthropicAdapter` (in `src/llm/anthropic.ts`) default to a fixed `maxTokens` (typically 4096) if not explicitly provided.
- **Modality Blindness:** The orchestration layer (`AgentPool`, `AgentRunner`) is unaware of the input modality. It treats a text-only prompt and a vision-heavy prompt with the same resource constraints.
- **Buffer Overflow:** High-entropy vision tasks generate a burst of tokens that exceed the expected response geometry, causing failures in the streaming or batching logic.

## 3. Proposed Architectural Update: Modality-Aware Protocol

### A. Dynamic Token Calculation
Implement a heuristic-based token requirement calculator within the `AgentRunner`. This calculator will scan the `initialMessages` for `ImageBlock` content and adjust the `maxTokens` parameter before the adapter is invoked.

**Proposed Logic:**
```typescript
/**
 * Calculates a dynamic max_tokens limit based on input modality.
 * @param messages The conversation history.
 * @param baseMaxTokens The user-provided or default maxTokens.
 * @returns An adjusted maxTokens value.
 */
private calculateDynamicMaxTokens(messages: LLMMessage[], baseMaxTokens: number): number {
  const imageBlocks = messages.flatMap(m => m.content).filter(c => c.type === 'image');
  const imageCount = imageBlocks.length;

  if (imageCount === 0) return baseMaxTokens;

  // Heuristic: Increase token capacity by 50% per image to accommodate 
  // the increased complexity of vision-to-text reasoning.
  const visionMultiplier = 1.5;
  return Math.ceil(baseMaxTokens * (1 + (imageCount * (visionMultiplier - 1))));
}
```

### B. Integration Points
1.  **`src/agent/runner.ts`**:
    - Integrate `calculateDynamicMaxTokens` into the `stream` method.
    - Use the calculated value to populate `baseChatOptions.maxTokens`.
2.  **`src/types.ts`**:
    - (Optional) Add `visionTokenFactor: number` to `RunnerOptions` to allow fine-grained control over the multiplier.

## 4. Implementation Plan (Read-Only Audit Complete)
1.  **Phase 1 (Logic):** Update `AgentRunner.stream` to perform a pre-flight scan of `initialMessages`.
2.  **Phase 2 (Configuration):** Update `RunnerOptions` to include modality-specific scaling factors.
3.  **Phase 3 (Validation):** Test with high-resolution image sequences to ensure the `max_tokens` parameter scales linearly with visual complexity.

## 5. Conclusion
By transitioning from static batch configurations to a modality-aware resource allocation protocol, we resolve the spatial conflict between vision-based perception and the physical constraints of the token buffers. This ensures the "Architect's sight" is always supported by sufficient "thought capacity."
