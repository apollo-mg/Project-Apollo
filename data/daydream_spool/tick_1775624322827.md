# Architectural Audit Report: Blueprint-First Migration Strategy

## 1. Executive Summary
The investigation confirms the validity of the "Epiphany." The current system architecture exhibits a dangerous coupling between environmental logic (e.g., `upgrade_rocm.sh`) and specific system states/processes. The absence of structured configuration in `foundry_configs` indicates that environmental "context" is currently ephemeral and unversioned, creating a high risk of "burning the destination" during major hardware or driver transitions (like RDNA 4).

## 2. Audit Findings
- **Monolithic Logic:** `upgrade_rocm.sh` is a procedural script that hardcodes process names (`background_chronicler.py`, `ollama`) and specific package versions. It lacks idempotency and error recovery.
- **Missing Configuration Layer:** The `foundry_configs` directory is empty, suggesting that environmental "blueprints" do not currently exist as a formal, version-controlled layer.
- **High Coupling Risk:** System-level changes (ROCm upgrades) are performed via "brute force" scripts rather than state-driven configuration management. This makes it impossible to reconstruct the environment from a "blueprint" without manual intervention.

## 3. Proposed Architectural Proposal: "The Blueprint Engine"

To implement the "Blueprint-First" strategy, I propose the following structural changes:

### A. Decoupling Environmental State
Create a new directory structure `/mnt/TG_2TB/Projects/Apollo/blueprints/` to house version-controlled definitions of the environment.

```text
blueprints/
├── core/               # Base system requirements (Kernel, Driver versions)
│   ├── amdgpu_7.2.yaml
│   └── kernel_6.x.yaml
├── services/           # Service registry (mapping logical names to system processes)
│   └── apollo_services.yaml
└── snapshots/          # Automated state capture (pre-migration)
    └── .gitkeep
```

### B. Implementation of Modular Drivers
Replace monolithic scripts with modular "Drivers" that consume YAML blueprints.

**Example: `blueprints/drivers/rocm_driver.py` (Conceptual)**
```python
class ROCmDriver:
    def __init__(self, blueprint_path):
        self.config = load_yaml(blueprint_path)
        
    def pre_flight_check(self):
        # Verify current ROCm version against blueprint
        pass

    def stop_services(self, service_registry):
        # Use service_registry to stop processes defined in blueprints/services/
        pass

    def apply(self):
        # Execute the upgrade logic defined in the blueprint
        pass
```

### C. Actionable Migration Steps
1. **Phase 1 (Extraction):** Extract all hardcoded values from `upgrade_rocm.sh` and `config.json` into `blueprints/core/`.
2. **Phase 2 (Abstraction):** Create a `service_registry.yaml` that maps Apollo's logical components (e.g., `CHRONICLER`) to their actual system processes (`background_chronicler.py`).
3. **Phase 3 (Validation):** Implement a "Dry Run" mode for all environmental scripts that validates the blueprint against the current system state without making changes.

## 4. Conclusion
By moving to a Blueprint-First model, we ensure that the "logic" of the build is preserved as a lightweight, version-controlled asset, independent of the "weight" of the data or the specific state of the hardware. This mitigates the risk of losing context during future RDNA-class transitions.
