# Epiphany Investigation: Friction Ingestion Protocol

## Initial Assessment
The epiphany suggests a paradigm shift: treating operational failures (typos, failed imports, cancelled requests) as primary signals for mapping the system's boundaries rather than noise. 

**Current State:**
- The system likely treats errors as exceptions to be handled or suppressed.
- There is no explicit "Friction Ingestion" mechanism to convert these errors into "Ground Truth" metadata.

**Proposed Goal:**
- Formalize a protocol where errors are routed to a 'Knowledge Curator'.
- This Curator will map the environment (paths, binaries, dependencies) based on these failures.

## Investigation Plan
1. **Audit Error Handling:** Search the codebase for error handling patterns, specifically where shell command failures or import errors are caught.
2. **Identify 'Filter' vs 'Curator' logic:** Locate existing components that handle error suppression (the 'Filter') and see if there's a placeholder or existing structure for a 'Curator'.
3. **Map Metadata Storage:** Determine where the system currently stores environmental metadata to see how 'Friction Ingestion' would integrate.
4. **Draft Proposal:** Create a concrete architectural plan for the 'Friction Ingestion' protocol.

## Hypothesis
The current architecture likely has a centralized error handler or a wrapper around shell executions. This is the ideal injection point for the new protocol.
## Findings

### 1. Error Handling Analysis
The `ToolExecutor` (in `src/tool/executor.ts`) already implements a "defensive" error handling pattern. It catches errors (Zod validation, unknown tools, execution exceptions) and converts them into `ToolResult` objects with `isError: true`. 

**Current Behavior:**
- Errors are captured and returned to the agent.
- The agent receives the error message as part of its tool output.
- This is the "Filter" behavior: the error is handled so the system doesn't crash, but it's treated as a tool output to be processed by the LLM.

### 2. The "Friction Ingestion" Opportunity
The epiphany suggests that these errors shouldn't just be returned to the LLM, but should be used to update the system's internal model of the environment.

**Gap:**
- There is no mechanism to intercept these `isError: true` results and route them to a "Curator" for environmental mapping.
- Currently, if a `bash` tool fails because a binary is missing, the error is returned to the LLM, but the system's "knowledge" of available binaries remains unchanged.

### 3. Proposed Architectural Change: The 'Curator' Hook
I propose introducing a `FrictionIngestion` hook within the `ToolExecutor`.

**Proposed Workflow:**
1. `ToolExecutor.runTool` catches an error.
2. Before returning the `errorResult`, it checks if a `FrictionCurator` is registered.
3. If registered, it sends the error metadata (tool name, error message, context) to the `Curator`.
4. The `Curator` parses the error (e.g., "command not found: jq") and updates a specialized `GroundTruth` memory store.

## Proposed Implementation Plan

### Phase 1: Define the Curator Interface
Create `src/modules/curator.ts` defining the `FrictionCurator` interface.
```typescript
export interface FrictionEvent {
  toolName: string;
  error: string;
  context: any;
  timestamp: number;
}

export interface FrictionCurator {
  ingest(event: FrictionEvent): Promise<void>;
}
```

### Phase 2: Update ToolExecutor
Modify `src/tool/executor.ts` to accept an optional `FrictionCurator`.

```typescript
// In ToolExecutor class
private curator?: FrictionCurator;

// In runTool catch block
} catch (err) {
  const message = ...;
  if (this.curator) {
    await this.curator.ingest({
      toolName: tool.name,
      error: message,
      context: context, // Be careful with sensitive data
      timestamp: Date.now()
    });
  }
  return this.errorResult(`Tool "${tool.name}" threw an error: ${message}`);
}
```

### Phase 3: Implement a Concrete Curator
Create `src/modules/ground_truth_curator.ts` which implements `FrictionCurator`. It will:
- Use regex to parse common errors (e.g., `ENOENT`, `command not found`, `permission denied`).
- Update a `GroundTruth` memory entry in `src/memory/store.ts`.

### Phase 4: Integration
Update the `Orchestrator` to instantiate the `GroundTruthCurator` and pass it to the `ToolExecutor` during agent creation.

## Conclusion
The architecture is well-positioned for this shift. The `ToolExecutor` is the perfect interception point. The transition from "Filter" to "Curator" is essentially moving from "Error -> LLM" to "Error -> (LLM + Curator)".
