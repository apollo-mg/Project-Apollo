# Architectural Audit: Immersion Layer & VRAM Stability

## Epiphany Analysis
The subconscious identified a critical link between the 'Immersion Layer' (high-fidelity roleplay) and VRAM management. Specifically, the tension between 7B (efficiency) and 35B (depth) models is a resource management problem. When deploying high-depth models (35B), the 'Long Context Window' can trigger a 'Total Party Kill' (system crash/OOM) if VRAM is not strictly managed via MoE (Mixture of Experts) optimization.

## Current State Audit
The current `Scheduler` implementation in `src/orchestrator/scheduler.ts` contains a `hardware-aware` strategy. However, it is currently a "simulated" implementation:
- It uses a placeholder `hardware_info` cast to `any`.
- It relies on a simple keyword match (`'vram'` or `'memory'`) in the task description to trigger high-VRAM prioritization.
- It does not actually interface with the hardware or the model's memory requirements.

## Proposed Architectural Update
To stabilize the 'Immersion Layer' and prevent OOM during high-fidelity sessions, the `hardware-aware` strategy must be upgraded from a keyword-based heuristic to a deterministic resource-intent model.

### Proposed Changes:
1.  **Update `AgentConfig` (in `src/types.ts`)**:
    - Add `vram_required_gb: number` to the `AgentConfig` interface.
    - Add `is_moe: boolean` to allow the scheduler to prioritize MoE-optimized models for long-context tasks.
2.  **Refine `Scheduler.scheduleHardwareAware` (in `src/orchestrator/scheduler.ts`)**:
    - Instead of searching for the string "vram" in the task description, the scheduler should look for a `resource_requirement` field in the `Task` object.
    - The scoring algorithm should be: `score = (available_vram - required_vram) / total_vram_capacity`.
    - Implement a "Safety Buffer" logic: If `available_vram < (model_vram + context_window_buffer)`, the scheduler must reject the assignment or trigger a context-flush/swap.

### Implementation Draft (Pseudo-code for `scheduler.ts`):
```typescript
// Proposed logic for hardware-aware scoring
const scoredAgents = agents.map(agent => {
  const vram_limit = agent.vram_limit_gb; // From updated AgentConfig
  const current_usage = get_current_vram_usage(); // Real-time OS query
  const available = vram_limit - current_usage;
  
  // Calculate stability score: higher is better
  // We penalize agents that are close to their VRAM ceiling
  const stability_score = available > task.required_vram ? (available / task.required_vram) : 0;
  
  return { agent, score: stability_score };
}).sort((a, b) => b.score - a.score);
```

## Conclusion
The 'Immersion Layer' is currently fragile because the scheduler treats hardware awareness as a secondary "capability" rather than a primary "stability" constraint. By moving from keyword-based intent to explicit VRAM requirement mapping, we can prevent the 'TPK' (system crash) during high-fidelity 35B model sessions.
