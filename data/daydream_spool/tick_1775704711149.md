# Architectural Audit: Feedback Paradox & Recursive Orchestration

## 1. Executive Summary
The investigation confirms the "Feedback Paradox" identified by the Subconscious. The current architecture of the `OpenMultiAgent` orchestrator is designed as a strictly directed acyclic graph (DAG) for a single execution pass. While it handles task dependencies within a single goal, it lacks the structural capacity for "biological recursion"—where the output of a synthesis phase can redefine the original goal and trigger a new, subsequent orchestration cycle.

## 2. Root Cause Analysis
The `runTeam` method (in `src/orchestrator/orchestrator.ts`) follows a linear lifecycle:
`Goal` $\rightarrow$ `Decomposition` $\rightarrow$ `Task Execution` $\rightarrow$ `Synthesis` $\rightarrow$ `Result`.

The "paradox" occurs because the `goal` is a primitive string passed into the method. There is no mechanism within the `executeQueue` loop or the `coordinator` agent to "re-birth" the orchestration with a modified goal. Any attempt to achieve self-correction or evolution within a single `runTeam` call is logically impossible because the graph's boundaries are fixed at the start of the call.

## 3. Proposed Architectural Update: The Iteration Controller

To resolve this, we must move from a "Single-Pass Orchestrator" to an "Iterative Orchestration Loop."

### A. Decoupling via State Manager
We propose introducing a `StateStore` that separates:
- **Ephemeral State**: Task results and intermediate messages (current implementation).
- **Persistent State**: The `EvolutionaryGoal` and `IterationCount`.

### B. The Iteration Controller (New Component)
A new high-level controller will manage the lifecycle of multiple `runTeam` calls.

**Proposed Workflow:**
1. **Initialize**: `IterationController` receives an `InitialGoal`.
2. **Execute**: `IterationController` calls `orchestrator.runTeam(team, currentGoal)`.
3. **Evaluate**: The `Synthesis` result is passed to an `EvolutionaryEvaluator` (a specialized LLM node).
4. **Decide**:
   - If `EvolutionaryEvaluator` returns `CONTINUE` + `NewGoal` $\rightarrow$ Update `currentGoal` and repeat from Step 2.
   - If `EvolutionaryEvaluator` returns `FINISH` $\rightarrow$ Return final result to user.

## 4. Concrete Code Change Proposals (Draft)

### Change 1: Define Evolutionary Result Types
In `src/types.ts`:
```typescript
export type EvolutionDirective = {
  action: 'continue' | 'stop';
  newGoal?: string;
  reasoning?: string;
};

export interface EvolutionaryTeamRunResult extends TeamRunResult {
  evolution?: EvolutionDirective;
}
```

### Change 2: Update Coordinator Synthesis
Modify `buildSynthesisPrompt` in `src/orchestrator/orchestrator.ts` to instruct the coordinator to provide an optional "Evolutionary Directive" if the task requires further refinement.

### Change 3: Implement the Controller
Create `src/orchestrator/iteration_controller.ts`:
```typescript
export class IterationController {
  async runIterativeTeam(team: Team, initialGoal: string): Promise<TeamRunResult> {
    let currentGoal = initialGoal;
    let finalResult: TeamRunResult;

    while (true) {
      const result = await this.orchestrator.runTeam(team, currentGoal);
      const directive = await this.evaluateEvolution(result);

      if (directive.action === 'stop') {
        return result;
      } else {
        currentGoal = directive.newGoal ?? currentGoal;
      }
    }
  }
}
```

## 5. Conclusion
The current architecture is a "Single-Turn" system. To achieve the "Self-Correcting Organism" envisioned by the architecture, we must implement the `IterationController` to allow the graph to execute in discrete, progressive steps, effectively turning the DAG into a recursive loop controlled by an external state manager.
