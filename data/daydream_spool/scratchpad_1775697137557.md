# Epiphany Investigation: Overnight Foundry & Model Registry Redesign

## Hypothesis
The current model registry architecture likely treats model availability as a binary state (Downloaded/Ready). The Epiphany suggests a state machine transition:
`Downloaded` -> `Pending Compilation` -> `Ready (Hardware-Native)`.

The 'Ready' state should be gated by the presence of:
1. HIP Graph captures.
2. Tuning CSVs.
3. Verification via `foundry_profile.py`.

## Investigation Plan
1. Locate `foundry_profile.py`.
2. Locate the Model Registry implementation (likely in `ai/` or a similar directory).
3. Audit the current model state transition logic.
4. Identify where `foundry_profile.py` is invoked or if it's currently decoupled.
5. Check the directory structure for where HIP Graphs and tuning CSVs are stored.
## Audit Findings
- **Current State:** `profiles.json` is a static configuration file. It maps a profile name to a model path, server binary, and environment variables.
- **Missing Link:** There is no `status` or `state` field in the `profiles.json` schema. The `ServiceOrchestrator` simply launches whatever is defined.
- **The Gap:** The "Overnight Foundry" (the compilation/profiling step) is currently external to the orchestration lifecycle. A model is considered "available" as soon as its path exists in `profiles.json`.
- **Verification Gap:** There is no logic in `orchestrator.py` to verify if the model at `model_path` has been optimized (e.g., checking for HIP Graph captures or tuning CSVs).

## Proposed Architectural Change
1. **Schema Update:** Update `profiles.json` to include a `status` field for each profile.
   - `status`: `READY`, `PENDING_COMPILATION`, or `UNAVAILABLE`.
2. **Orchestrator Logic Update:**
   - Modify `ServiceOrchestrator.launch()` to check the `status`.
   - If `status == "PENDING_COMPILATION"`, refuse to launch and suggest running the Foundry.
   - If `status == "READY"`, proceed with launch.
3. **Foundry Integration:**
   - The `foundry_profile.py` (or a new service) must be responsible for:
     a. Running the profiling/compilation.
     b. Verifying the existence of artifacts (HIP Graphs, CSVs).
     c. Updating `profiles.json` to set `status: "READY"`.
4. **Inference Engine Gate:** The inference engine (which uses the orchestrator) will now naturally only see "Ready" models.

## Implementation Strategy (Draft)
- **Step 1:** Define the new JSON schema.
- **Step 2:** Implement a `ModelRegistry` class (or update `ServiceOrchestrator`) that handles the state transitions.
- **Step 3:** Create a validation hook in `launch()` that calls a verification function (potentially wrapping `foundry_profile.py` logic) to ensure the model is actually hardware-native.
