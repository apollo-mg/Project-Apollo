# Epiphany Investigation: Tiered Cognitive Architecture
## Timestamp: 2025-05-22 (Simulated)
## Status: Initializing Audit

### Hypothesis
The current system architecture likely treats all LLM requests with a uniform priority/latency profile, or lacks a sophisticated routing mechanism that distinguishes between "high-frequency/low-latency" (coding/debugging) and "low-frequency/high-depth" (complex reasoning) tasks. 

The "friction" mentioned in the epiphany refers to the overhead of loading large weights into VRAM or the latency of PCIe transfers when switching between models.

### Investigation Plan
1. **Identify Orchestration Logic:** Locate the core component responsible for dispatching tasks to models (e.g., `orchestrator.py`, `fleet_orchestrator.py`, `task_manager.py`).
2. **Analyze Model Management:** Check how models are provisioned and loaded (`model_provisioner.sh`, `model_manifest.json`, `vram_management.py`).
3. **Audit Task Routing:** Determine if there is any existing logic that categorizes tasks by type or complexity.
4. **Assess Latency/Throughput Data:** Look for logs or benchmarks that indicate model switching overhead or PCIe bottlenecks (`vllm_results.log`, `bonsai_bench.log`).
### Findings: Current State of Orchestration
- `orchestrator.py` is a service manager that launches pre-defined profiles from `profiles.json`.
- `profiles.json` defines:
    - `architect`: High-complexity (27B MoE, Q2_K).
    - `turbo`: High-context (26B MoE, IQ2_XXS).
    - `whisper`: Audio processing.
    - `bonsai`: Low-latency/Small (8B).
- **The Problem:** The current `orchestrator.py` is a *service launcher*, not a *task router*. It manages the lifecycle of the servers, but it does not sit in the middle of the request stream to decide *which* server should handle a specific task based on task metadata (e.g., "coding" vs "reasoning").
- **The Gap:** There is no "Cognitive Dispatcher" layer that inspects the intent of a request and routes it to the appropriate port (8083 for Bonsai, 8082 for Architect/Turbo).

### Proposed Architectural Update: The "Cognitive Dispatcher"
1. **New Component:** `cognitive_dispatcher.py`.
2. **Functionality:**
    - Acts as a proxy/router for all incoming agent requests.
    - **Classification Engine:** Uses a lightweight heuristic (or a very fast call to `bonsai`) to classify the task.
    - **Routing Logic:**
        - `TaskType.ITERATIVE` (Code, Debug, Chat) $\rightarrow$ `bonsai` (Port 8083).
        - `TaskType.DEEP_REASONING` (Architecture, Planning, Complex Logic) $\rightarrow$ `architect` (Port 8082).
    - **Latency Management:** If `bonsai` is overloaded or fails, it can fallback to `turbo`.
3. **Integration:**
    - Update `fleet_orchestrator.py` to ensure the Dispatcher is part of the standard boot sequence.
    - Update `task_manager.py` to send requests to the Dispatcher instead of directly to model ports.
