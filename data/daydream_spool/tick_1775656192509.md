# Architectural Proposal: Transition to Risk-Weighted Autonomy

## 1. Executive Summary
The current Human-in-the-Loop (HITL) model is binary: any `run_shell` action triggers a mandatory manual approval, creating significant operational friction. This proposal outlines a transition to a **Risk-Weighted Autonomy** model, leveraging the excess computational capacity of the RX 9070 XT to run a local 'Safety Critic' that pre-approves low-risk operations.

## 2. Current State Analysis
- **Bottleneck**: `modules/approvals/handler.py` currently implements a hard gate for `run_shell` actions:
  ```python
  if action_name == "run_shell":
      return True # Shell commands are always risky
  ```
- **Friction**: This forces a manual `y/n` or GUI interaction for even trivial commands (e.g., `ls`, `pwd`, `grep`), causing cognitive dissonance between the system's high-performance hardware and its restricted agency.

## 3. Proposed Architecture: The Safety Critic

### 3.1 Component: `SafetyCritic`
A new module, `modules/approvals/safety_critic.py`, will be introduced. It will utilize a lightweight, high-speed LLM (e.g., Llama 3.2 1B or Gemma 2B) to evaluate the intent and risk of a proposed action.

### 3.2 Risk Categorization Logic
The `SafetyCritic` will classify actions into three tiers:

| Risk Level | Criteria | Action |
| :--- | :--- | :--- |
| **LOW** | Read-only operations (`ls`, `cat`, `grep`), non-destructive system queries, or web searches. | **Auto-Approve**: Execute immediately and log to `audit_log.json`. |
| **MEDIUM** | File creation in non-core directories, `pip install` (non-system), or `git` operations. | **Quick-Approve**: Use a non-blocking notification (e.g., `notify-send`) or a single-key terminal prompt. |
| **HIGH** | `rm`, `sudo`, modification of `CORE_FILES`, or system-level configuration changes. | **Hard Gate**: Maintain current `kdialog`/`launch_inspector` workflow. |

## 4. Implementation Plan

### Phase 1: The Critic Module
- Implement `modules/approvals/safety_critic.py`.
- Integrate with `llm_interface.py` to ensure the critic uses a dedicated, low-latency model instance.

### Phase 2: Refactoring the Handler
- Update `modules/approvals/handler.py`:
  - Replace the hardcoded `run_shell` check in `should_require_approval` with a call to `SafetyCritic.evaluate()`.
  - Modify `request_approval` to branch based on the returned `RiskLevel`.
  - Implement a "Fast Path" for `LOW` risk actions to bypass the `PENDING_PATH` polling loop.

### Phase 3: Audit & Logging
- Ensure all auto-approved `LOW` risk actions are recorded in a new `audit_log.json` for retrospective review, maintaining the "Zero-Trust" integrity through observability rather than constant interruption.

## 5. Impact Assessment
- **Pros**: Drastically reduces human friction; maximizes hardware utility; maintains security through intelligent filtering.
- **Cons**: Introduces a small amount of latency for the initial risk assessment (mitigated by the RX 9070 XT's performance).
- **Risk Mitigation**: The `SafetyCritic` itself is subject to the `guardian_manifest.json` to prevent it from being compromised or modified autonomously.
