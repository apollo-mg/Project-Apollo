# Investigation: Identity and Permission-First Deployment
**Timestamp:** 2024-05-22 (Simulated)
**Status:** Initiated

## Hypothesis
The "Epiphany" suggests that migration failures in the system are not due to data corruption or transfer errors, but due to insufficient filesystem permissions (identity/authority) when services attempt to access external mounts. 

## Initial Audit Plan
1.  **Identify External Mounts:** Locate where external storage (like `/mnt/TG_2TB/`) is mounted.
2.  **Permission Audit:** Check the ownership and permission bits of critical service directories and model paths.
3.  **Service Identity Check:** Determine the user/group under which core services run and verify their ability to traverse the target paths.
4.  **Codebase Search:** Look for hardcoded paths or deployment scripts that might be assuming local filesystem permissions.

## Filesystem Audit Results
- **Mount Point:** `/mnt/TG_2TB` is an `ext4` filesystem on `/dev/nvme1n1p1`.
- **Permissions:** 
    - `/mnt/TG_2TB` is owned by `mark:mark` with `drwxr-xr-x` (755).
    - `/mnt/TG_2TB/Projects/Apollo/data/daydream_spool/` is owned by `mark:mark` with `drwxr-xr-x` (755).
- **Observation:** The current user `mark` has full access. However, if a service runs under a different user (e.g., `root`, `www-data`, or a dedicated `service_user`), it will only have read/execute access (due to the `r-x` for others). If the service needs to write to these directories, it will fail.
## Critical Vulnerability Identified
- **Hardcoded Absolute Paths:** Multiple scripts (e.g., `moe_shootout.py`, `modules/voice.py`, `deep_sleep_triage.py`) use hardcoded absolute paths starting with `/mnt/TG_2TB/Projects/Apollo`.
- **The "Identity" Problem:** While the paths are correct for the current user `mark`, any service or containerized process that does not have the exact same mount point structure or user permissions will fail to "see" its own logic or models.
- **Model Path Risk:** `moe_shootout.py` references `/mnt/TG_2TB/AI/Models/Gemma 4/...`. This is outside the project root, increasing the risk of permission mismatches if the AI model directory has different ownership/ACLs than the project directory.

## Proposed Architectural Changes
1.  **Environment-Aware Path Resolution:** Replace hardcoded absolute paths with relative paths or environment-variable-based paths (e.g., `APOLLO_ROOT`).
2.  **Permission-First Deployment Script:** Implement a pre-flight check in the deployment pipeline that:
    - Validates the existence of all required paths.
    - Verifies `access` (R/W/X) for the service user on all critical paths.
    - Logs a "Permission Audit" report before service start.
3.  **Configuration Injection:** Move model paths and system paths into a `.env` or `config.yaml` file that is injected at runtime.
