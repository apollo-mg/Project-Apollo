# Architectural Audit Report: HIP Asynchronous Error Masking

## 1. Executive Summary
The investigation confirms the validity of the "Asynchronous Deception" epiphany. Log analysis of `synthesizer_batch.log` reveals a direct correlation between ROCm/HIP kernel errors and hardware-level instability (RDNA 4/ROCm), specifically noting "silent data corruption" and "RMS Norm" errors. These symptoms are consistent with kernel execution errors that are reported asynchronously, leading to a mismatch between the reported error location and the actual point of failure.

## 2. Findings & Evidence
- **Log Evidence:** `synthesizer_batch.log` explicitly identifies:
    - `Hardware-level instability (ROCm/HIP/RDNA 4) is causing silent data corruption...`
    - `Hardware-level instability (ROCm/HIP kernel errors) ... causing "Cognitive Dissonance"...`
- **Root Cause Hypothesis:** The current error-reporting mechanism (the "Reflex Arc" in `modules/agent_session.py`) captures the *symptom* (the reported error) but cannot pinpoint the *cause* because the GPU kernel execution is decoupled from the CPU-side error reporting.
- **Current State:** The system is currently reactive, treating the error as a "messenger" rather than investigating the "crime" (the specific kernel launch that caused the corruption).

## 3. Proposed Architectural Changes

### A. Immediate Environment Hardening (Non-Invasive)
To strip away the asynchronous mask, the following environment variables must be injected into the execution runtime (e.g., via `.env` files, Dockerfiles, or systemd service files):

| Variable | Value | Purpose |
| :--- | :--- | :--- |
| `AMD_SERIALIZE_KERNEL` | `3` | Forces kernel execution to be synchronous, ensuring errors are reported at the exact moment of occurrence. |
| `TORCH_USE_HIP_DSA` | `1` | Enables Device Side Assertions (DSA) to catch illegal memory accesses directly on the GPU hardware. |

### B. Long-term Observability (Invasive)
1. **Kernel-Level Tracing:** Implement a diagnostic mode that wraps `torch.cuda.synchronize()` (or the HIP equivalent) around critical kernel launches during high-risk operations (e.g., RMS Norm, Attention mechanisms).
2. **Enhanced Error Context:** Update the `modules/agent_session.py` error-to-model feedback loop to include a "Synchronization Check" flag, indicating whether the error was caught in a synchronous or asynchronous context.

## 4. Implementation Plan
1. **Phase 1 (Validation):** Deploy `AMD_SERIALIZE_KERNEL=3` to a staging environment. Verify if the error stack trace shifts to the actual offending kernel.
2. **Phase 2 (Standardization):** Integrate these variables into the standard `apollo_bridge` or container orchestration layer.
3. **Phase 3 (Monitoring):** Monitor for increased latency (a side effect of serialization) and balance it against the gain in debugging precision.
