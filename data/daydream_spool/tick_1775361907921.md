# Epiphany Audit: Hardware-to-Inference Mapping Layer

## 1. Analysis of the Epiphany
The subconscious has identified a critical architectural gap: the "metabolism" problem. Currently, the system has "eyes" (Desktop Eyes for visual context and VRAM management for physical constraints) but lacks a "brain" that connects these two. 

**Current State:**
- `desktop_eyes.py`: Captures visual context and sends it to the Architect.
- `vram_management.py`: Monitors VRAM and triggers cleanup/offloading.
- `model_manifest.json`: A static list of URLs for downloading models.
- `model_provisioner.sh`: A simple downloader based on the manifest.

**The Gap:**
There is no logic that says: *"If VRAM is 16GB and we are running a 70B model, use Q4_K_M quantization; if VRAM is 8GB, use Q2_K."* The transition from hardware state to model selection is manual.

## 2. Architectural Audit Findings
- **Physical Topology Sensing:** `vram_management.py` and `system_monitor_v2.py` successfully capture the "Desktop Eyes" view of the hardware (VRAM, CPU, RAM).
- **Digital Model Landscape:** `model_manifest.json` is too primitive. It only contains URLs and filenames, lacking metadata about quantization, model size, or inference engine requirements (vLLM vs. Ollama/llama.cpp).
- **The Bridge:** Missing. There is no "Inference Profile" layer.

## 3. Proposed Architectural Update: The 'Metabolism' Layer

I propose the creation of a `metabolism_engine.py` and an updated `model_manifest.json`.

### A. Updated `model_manifest.json` (Schema Change)
The manifest must move from a simple list to a capability-aware registry.
```json
{
  "models": [
    {
      "id": "llama-3-70b",
      "name": "Llama 3 70B",
      "profiles": {
        "vram_16gb": { "quant": "Q2_K", "engine": "llama.cpp", "url": "..." },
        "vram_32gb": { "quant": "Q4_K_M", "engine": "vLLM", "url": "..." }
      }
    }
  ]
}
```

### B. New Module: `metabolism_engine.py`
This module will act as the "Watchdog" bridge.
1. **Sensing:** Calls `vram_management.py` to get current `vram_used_mb` and `vram_total_mb`.
2. **Mapping:** Compares available VRAM against the `profiles` in the manifest.
3. **Execution:** Triggers `model_provisioner.sh` with the specific quantized URL identified by the mapping.

## 4. Implementation Roadmap
1. **Phase 1 (Data):** Expand `model_manifest.json` to include quantization profiles.
2. **Phase 2 (Logic):** Implement `metabolism_engine.py` to resolve the "Hardware -> Model" mapping.
3. **Phase 3 (Automation):** Integrate `metabolism_engine.py` into the `desktop_eyes.py` loop so that visual context changes (e.g., "I am starting a heavy CAD task") trigger a VRAM-aware model swap.

**Status:** *Audit Complete. Proposal Ready for Implementation.*
