# Architectural Proposal: Compute Sovereignty & Headless Transition

## Epiphany Summary
The 'Always-On' macro plan is hindered by the conflict between consumer OS design (protecting the GUI/WDDM) and the requirement for uninterrupted compute (protecting the silicon). Heavy compute cycles (LoRA, TT-Metalium) are vulnerable to Kernel-level TDR (Timeout Detection and Recovery) timeouts when the OS prioritizes the display server.

## Audit Findings
- **Current State:** The framework is a high-level multi-agent orchestrator. It is currently "GUI-aware" (streaming text for display) but "OS-agnostic" regarding the execution environment.
- **Risk:** Tasks executed via the `bash` tool are subject to the host OS's stability. In a standard desktop environment, a heavy GPU load can trigger a TDR, causing the OS to reset the driver and potentially killing the long-running compute process.
- **Gap:** There is no mechanism to ensure the compute environment is "sovereign" (headless/TTY-centric) before initiating high-criticality tasks.

## Proposed Architectural Update

### 1. Introduction of `EnvironmentManager` Module
Create `src/modules/environment_manager.ts` to manage the abstraction layer.
- **Interface `ComputeEnvironment`**:
  - `prepare(mode: EnvironmentMode): Promise<void>`: Transitions the system to the requested state.
  - `teardown(): Promise<void>`: Restores the system to a standard user state.
  - `getStabilityScore(): number`: Returns a metric of current OS/Driver stability.
- **Implementations**:
  - `LinuxTTYEnvironment`: Uses `systemctl` or `logind` to ensure a headless state, unbinding display servers if necessary.
  - `WindowsWDDMEnvironment`: Monitors for TDR-prone conditions and warns the orchestrator.

### 2. Orchestrator Integration
Modify `src/orchestrator/orchestrator.ts` to incorporate environment awareness:
- **Pre-flight Check**: Before executing a task, the orchestrator will check the `Task.criticality`.
- **Environment Transition**: If a task is marked as `CRITICAL_COMPUTE` (e.g., LoRA training), the orchestrator will call `EnvironmentManager.prepare(EnvironmentMode.HEADLESS)`.
- **Safety Guard**: If the environment cannot be transitioned to a headless state, the orchestrator will flag the task as "Hostage-Risk" and require explicit user override.

### 3. Type System Updates (`src/types.ts`)
- Add `EnvironmentMode` enum: `GUI`, `HEADLESS`, `TTY_ONLY`.
- Add `environmentRequirement: EnvironmentMode` to the `Task` definition.

## Implementation Strategy
1. **Phase 1 (Detection):** Implement the `EnvironmentManager` in "Audit Mode" to log when tasks are running in non-ideal environments.
2. **Phase 2 (Transition):** Implement the actual unbinding/headless logic for Linux-based compute nodes.
3. **Phase 3 (Automation):** Fully automate the transition within the `orchestrator` loop.

**Status:** Ready for implementation in the next development cycle.
