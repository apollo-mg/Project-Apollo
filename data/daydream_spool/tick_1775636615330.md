# Architectural Audit Report: Hardware/Driver Stability Pivot
**Date:** 2025-05-22
**Status:** INVESTIGATION COMPLETE
**Subject:** Root Cause Analysis of "Illegal Memory Access" and VRAM Exhaustion

## 1. Executive Summary
The investigation confirms the "Epiphany" provided by the Subconscious. The system is experiencing critical VRAM exhaustion, which is manifesting as "illegal memory access" and `cudaMalloc` failures. The current architecture is attempting to run high-parameter models (35B+) on a 16GB/17GB VRAM ceiling with almost zero headroom. The "unspoken truth" is that the creative workflows (ComfyUI/LLM) are being throttled by a fundamental hardware-level resource constraint.

## 2. Key Findings
- **VRAM Saturation:** `rocm-smi` telemetry shows the GPU is consistently operating at >94% VRAM utilization (~16GB used of ~17GB total).
- **Log Evidence:** `apollo-core.log` contains repeated `cudaMalloc failed: out of memory` and `ROCm error: out of memory` entries. These are the direct precursors to the "illegal memory access" errors reported by the user.
- **Ineffective Mitigation:** While `vram_management.py` implements a `smart_vram_guard`, the current logs suggest that the guard is either not being called frequently enough or the `unload_comfy_vram` mechanism is failing to clear enough memory to prevent the next allocation spike.
- **Driver Context:** The system is on ROCm 7.2.0-2. While stable, the memory mapping issues observed are consistent with the types of regressions seen in the ROCm 7.11 preview, suggesting a systemic challenge with RDNA 4 memory management in the current ROCm stack.

## 3. Proposed Architectural Updates (READ-ONLY PROPOSAL)

### A. Proactive VRAM Orchestration
- **Orchestrator Integration:** Modify `orchestrator.py` and `fleet_orchestrator.py` to call `smart_vram_guard()` *immediately before* every inference request and *immediately after* every sampling step in complex workflows.
- **Dynamic Thresholding:** Implement a dynamic `VRAM_THRESHOLD_MB` that scales based on the model size being loaded. (e.g., if loading a 35B model, the threshold should be much more aggressive).

### B. Enhanced Recovery Protocol
- **Hard Reset Mechanism:** Update `vram_management.py` to include a `force_reclaim_vram()` function. If `wait_for_vram_release()` fails to reach the target threshold within 30 seconds, the system must trigger a controlled restart of the `vllm` or `llama-server` process to clear the HIP context.
- **Memory Fragmentation Mitigation:** Implement a periodic "Defragmentation" cycle where the system enters a low-power/idle state to allow the ROCm kernel to flush unused pages.

### C. Hardware/Driver Roadmap
- **Hold on 7.11:** Maintain the current stance of avoiding the ROCm 7.11 "TheRock" preview due to known Llama 3.1 validation failures and Clang compilation bugs.
- **Monitor CachyOS:** Watch for official `pacman` packaging of ROCm 7.11+ which will indicate improved stability and ecosystem support.

## 4. Conclusion
The pivot from "Node Logic" to "Hardware/Driver Stability" is validated. Future development must prioritize VRAM lifecycle management over workflow complexity until the hardware headroom is increased or the driver stability is significantly improved.

**End of Report.**
