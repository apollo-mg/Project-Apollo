# Architectural Audit: The "Truth-Lock" Protocol

## Epiphany Analysis
The subconscious daemon has identified a critical convergence between technical "Cache Locks" and epistemological "Auditor" failures. Currently, the system treats all retrieved data from the Vector Database (VDB) as "truth." However, the existence of `pending_knowledge.json` (and similar ingestion buffers) indicates that there is a state of "unverified knowledge" that is currently being conflated with "verified truth" during RAG (Retrieval-Augmented Generation) processes.

The "friction" identified is the lack of a formal distinction between **Ingested Data** (raw, unverified) and **Core Dossier Knowledge** (verified, audited).

## Current State Audit
1.  **Data Ingestion:** Files are ingested into `vault/chroma_db` (via `modules/vdb.py`).
2.  **Retrieval:** `query_vdb` in `modules/vdb.py` performs similarity searches.
3.  **The Gap:** There is no metadata-driven "mutex" or "lock" that prevents the RAG system from treating a newly ingested, un-audited document as a primary source of truth. The system is currently "leaking" unverified claims into the cognitive environment.

## Proposed Architectural Update: The "Truth-Lock" Protocol

To resolve this, we must implement a metadata-based distinction in the Vector Database.

### 1. Metadata Schema Update
Every document in the Chroma collection must include a `status` metadata field:
- `status: "pending"`: Data that has been ingested but not yet processed by the Auditor.
- `status: "verified"`: Data that has passed the Auditor's scrutiny and is part of the "Core Dossier."

### 2. Implementation Plan

#### A. Update `modules/vdb.py`
Modify the ingestion logic (wherever `vector_store.add_documents` is called) to default all new entries to `status: "pending"`.

#### B. Implement the "Truth-Lock" in `query_vdb`
Modify `query_vdb` to allow for a "Strict Mode." When the system is performing high-stakes reasoning (e.g., the Architect or Engineer persona is active), the query should default to filtering for `status: "verified"`.

### 3. Impact Assessment
- **Technical:** Prevents "Cognitive Cache" collisions where unverified data overrides established facts.
- **Epistemological:** Forces the Auditor persona to act as the "mutex," resolving the conflict between raw data-dumps and verified truth.
- **Performance:** Minimal overhead; Chroma metadata filtering is highly efficient.

## Conclusion
The transition from a system that *stores* to a system that *reconciles* requires this metadata-driven gatekeeper. By implementing the `status` flag, we transform the `pending_knowledge` list from a mere file-system buffer into a formal "Cognitive Cache" that requires an explicit "unlock" (Auditor verification) before it can influence the core intelligence.
