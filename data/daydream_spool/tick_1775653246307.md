# Architectural Audit Report: VRAM Bottleneck & Offloading Protocols

## 1. Executive Summary
The "Epiphany" regarding the systemic gap between model scale and silicon capacity is validated. Current investigations into the `server_qwen_moe_crash.log` and `run_vllm_benchmark.sh` reveal that while the system attempts to manage memory through static capping (e.g., `gpu_memory_utilization=0.80`), it remains highly vulnerable to OOM (Out of Memory) errors during inference, particularly when dealing with large context windows (e.g., Qwen 3.5 with 262k context) or MoE expert switching.

## 2. Findings
- **Current State:** Memory management is reactive and static. We use fixed utilization rates to leave headroom for overhead (like HIP graph capture), but this does not account for the dynamic memory demands of varying context lengths or model architectures.
- **Identified Risk:** The mismatch between model size (e.g., 10.7GB for a quantized Qwen 3.5) and available VRAM (16GB) leaves insufficient headroom for the KV cache required for high-context tasks.
- **Systemic Symptom:** The "crash" in the Qwen MoE server is likely a runtime OOM caused by the expansion of the KV cache or activation buffers during inference, not a loading error.

## 3. Proposed Architectural Update: Apollo Memory Orchestrator (AMO)
To transition from "reactive capping" to "proactive negotiation" with hardware, I propose the implementation of the **Apollo Memory Orchestrator (AMO)**.

### Core Components:
1. **Tiered Memory Management:**
   - Implement a standardized protocol for weight offloading across three tiers: **VRAM (L1) $\rightarrow$ System RAM (L2) $\rightarrow$ NVMe (L3)**.
   - Utilize `accelerate`'s `device_map` and `bitsandbytes` for seamless weight distribution.

2. **Dynamic KV Cache Scaling:**
   - Replace static `gpu_memory_utilization` with a dynamic allocator that calculates the maximum permissible context window based on the current VRAM headroom.
   - Implement "KV Cache Offloading" to system RAM for long-context scenarios where VRAM is exhausted.

3. **Model-Specific Memory Profiles:**
   - Define a registry of `MemoryProfile` objects for all high-parameter models (T5, CLIP, Wan, Qwen).
   - Profiles will include: `optimal_vram_footprint`, `offload_threshold`, and `max_safe_context`.

4. **Proactive Memory Daemon:**
   - Integrate a monitoring loop into `apollo_heartbeat.py` that tracks VRAM pressure.
   - When VRAM exceeds a critical threshold (e.g., 90%), the daemon will trigger an immediate offload of non-essential model layers or KV cache segments to L2/L3 memory.

## 4. Implementation Roadmap
- **Phase 1 (Audit):** Complete the mapping of all high-parameter models to their respective `MemoryProfile`.
- **Phase 2 (Core):** Develop the `MemoryManager` class and integrate it into the model loading pipeline.
- **Phase 3 (Integration):** Update deployment scripts (`run_vllm_benchmark.sh`, etc.) to utilize the AMO.
- **Phase 4 (Validation):** Stress-test the system with long-context inference to ensure stability under VRAM pressure.
