# Epiphany Investigation: Matryoshka Tiered Retrieval

## Hypothesis
The current RAG pipeline likely processes multimodal (visual + text) embeddings at full dimensionality during the initial retrieval phase. This causes high latency and computational overhead. Implementing a Matryoshka-based "pre-attentive" layer (using truncated embeddings) should significantly speed up candidate filtering before full-dimensional reasoning.

## Investigation Plan
1. Identify the core RAG/Embedding logic in the codebase.
2. Check if current embeddings are Matryoshka-compatible (i.e., if they support truncation).
3. Locate the retrieval function to see where the dimensionality bottleneck occurs.
4. Draft a proposal for a two-stage retrieval process.
## Findings
- `Tier2AssociativeCache` uses SQLite to store vectors as BLOBs.
- `semantic_search` in `Tier2AssociativeCache` is currently a placeholder (returns by timestamp).
- `Tier3LongTermKnowledge` is also a placeholder for ChromaDB.
- The `MemoryEntry` dataclass includes a `vector` field.
- The current architecture is already "tiered" in terms of storage (Working Buffer -> Associative Cache -> Long-Term Knowledge), but the *retrieval* process itself is not tiered by dimensionality.

## Proposed Architectural Change: Matryoshka Tiered Retrieval
Instead of just tiering by *storage* (frequency/persistence), we will tier by *dimensionality* (computational cost).

1. **Update `MemoryEntry`**: Ensure it can handle multiple vector representations or at least be aware of dimensionality.
2. **Implement Matryoshka-aware `semantic_search` in `Tier2AssociativeCache`**:
    - Store a low-dimensional "pre-attentive" vector (e.g., 128-dim) alongside the full-dimensional vector.
    - The `semantic_search` will first perform a fast dot-product/cosine similarity on the low-dim vectors to find the top $N$ candidates.
    - It will then perform a high-precision search on the full-dim vectors only for those $N$ candidates.
3. **Update `TieredMemorySystem`**: Add a method `search_with_matryoshka` that orchestrates this two-stage process.

## Implementation Details
- **Vector Storage**: Modify `Tier2AssociativeCache._init_db` to include a `vector_low_dim` BLOB column.
- **Ingestion**: When `put` is called, truncate the provided vector to a lower dimension (e.g., 128) and store it.
- **Retrieval**:
    - Stage 1: `SELECT id, vector_low_dim FROM memories` -> Fast similarity check.
    - Stage 2: `SELECT vector FROM memories WHERE id IN (...)` -> High-precision check.
