## Detailed Findings

### 1. Current Implementation of "Sensory Input"
The current implementation of `<sensory_input>` in `modules/agent_session.py` (lines 187-190) is used exclusively for **error reporting**. When a tool fails, the error is wrapped in this tag:
```python
self.messages.append({
    "role": "user",
    "content": f"<sensory_input type='tool_error'>\n{e}\n</sensory_input>\n\nDIAGNOSTIC: A tool execution failed..."
})
```
This confirms the epiphany's observation: the model treats "sensory input" as an *event* (an error) rather than a *state* (the ground truth).

### 2. System Prompt & Ground Truth
The `_prepare_system_prompt` method (lines 25-58) attempts to provide context by:
- Loading the "Soul" (personality/identity).
- Injecting the current inventory state via `Toolbox.get_inventory_detail()`.
- Injecting retrieved memory via `query_vdb`.

However, there is a critical gap: **Physical/Sensor Ground Truth is missing from the system prompt.** 

While the prompt says:
`"You have direct vision capabilities. If an image is provided, you can see it perfectly."` (lines 51-52),
it does **not** provide a baseline of what the model *should* be seeing or what the current physical state of the environment is (e.g., "The webcam is currently pointing at the workbench, and the light level is high").

### 3. The "Gap" Identified
The epiphany states: *"The breakthrough wasn't just making an argument optional; it was the realization that for Apollo to 'see' correctly, the 'ground truth' must be part of its internal consciousness (system context) rather than an external lookup."*

In the current code:
- To know the inventory, the model calls `get_inventory_detail`.
- To know the camera state, the model would likely have to call a tool (if one existed) or rely on the image provided in the message.
- There is no "System State" or "Environmental Baseline" injected into the prompt that describes the *expected* state of the physical world.

## Proposed Architectural Update

### Phase 1: Grounding the Context (System Prompt)
Instead of just providing the `inv_state` (digital truth), we should introduce an `env_state` (physical/sensor truth) into the system prompt.

**Proposed Change in `_prepare_system_prompt`:**
1.  **Implement a `get_environmental_baseline()` method** in `Toolbox` or a new `SensorManager`.
2.  **Inject this baseline into the system prompt.**

```python
# Proposed addition to _prepare_system_prompt
env_baseline = Toolbox.get_environmental_baseline() # Returns e.g., "Webcam: Active, Location: Workbench, Lighting: Normal"

# New section in json_mandate/system_prompt
"""
ENVIRONMENTAL BASELINE (Ground Truth):
{env_baseline}

CURRENT INVENTORY (Digital Truth):
{inv_state}
...
"""
```

### Phase 2: Refined Tooling
Once the model has the baseline, tools like `visual_inventory_audit` should be designed to compare the *actual* image against the *baseline* provided in the prompt, rather than just describing the image in isolation.

## Conclusion
The epiphany is correct. The current architecture treats sensor data as a "tool result" (an external event). To achieve true "vision," the model needs the environmental baseline to be part of its "internal consciousness" (the system prompt).
