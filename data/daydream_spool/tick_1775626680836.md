# Architectural Proposal: Tiered Cognitive Dispatcher

## 1. Executive Summary
The current system suffers from "PCIe Friction": high-complexity models (Architect/Turbo) are being used for low-complexity, high-frequency tasks, causing unnecessary latency and VRAM/bus contention. 

This proposal introduces a **Cognitive Dispatcher** layer to implement a tiered architecture, separating "Flow" (low-latency, iterative) from "Depth" (high-complexity, asynchronous).

## 2. Current State Analysis
- **Orchestrator (`orchestrator.py`):** Manages service lifecycles (launch/stop) but lacks request-level intelligence.
- **Profiles (`profiles.json`):** Defines distinct models (Bonsai-8B, Architect-27B, Turbo-26B) but they are currently treated as independent silos.
- **Bottleneck:** The lack of a routing mechanism means the agentic loop must manually decide which port to hit, or worse, defaults to a heavy model for simple tasks.

## 3. Proposed Architecture: The Tiered Dispatcher

### A. Component: `cognitive_dispatcher.py`
A new middleware service that sits between the `task_manager.py` and the model servers.

**Logic Flow:**
1. **Ingest:** Receives a task/prompt.
2. **Classify:** 
   - *Heuristic:* Check for keywords (e.g., "fix", "debug", "write", "check") or length.
   - *Fast-Path:* A single, extremely low-latency call to `bonsai` (8B) to classify intent.
3. **Route:**
   - **Tier 1 (Flow):** `TaskType.ITERATIVE` $\rightarrow$ Route to `bonsai` (Port 8083).
   - **Tier 2 (Depth):** `TaskType.REASONING` $\rightarrow$ Route to `architect` (Port 8082).
   - **Tier 3 (Context):** `TaskType.LONG_CONTEXT` $\rightarrow$ Route to `turbo` (Port 8082).

### B. Implementation Plan

#### Phase 1: Dispatcher Core
- Implement `cognitive_dispatcher.py` using `FastAPI` or a lightweight `asyncio` proxy.
- Implement the `IntentClassifier` module.

#### Phase 2: Orchestration Integration
- Modify `fleet_orchestrator.py` to include the `cognitive_dispatcher` in the `Boot` sequence.
- Update `profiles.json` to include a `dispatcher` profile.

#### Phase 3: Agentic Refactoring
- Update `task_manager.py` and `orchestrator.py` to point all LLM requests to the Dispatcher's port instead of individual model ports.

## 4. Expected Impact
- **Latency Reduction:** ~40-60% for iterative coding/debugging tasks by keeping them on the 8B model.
- **Throughput Increase:** Reduced PCIe/VRAM pressure by preventing large model weight swaps for trivial tasks.
- **Cognitive Depth:** Allows the system to "think bigger" only when necessary, preserving resources for high-complexity reasoning.

## 5. Risk Assessment
- **Classification Error:** If a complex task is misclassified as "Flow", the agent may fail. 
  - *Mitigation:* Implement a "Complexity Escalation" trigger where the agent can request a re-route to `architect` if the first response is insufficient.
- **Dispatcher Latency:** The dispatcher itself adds a small overhead.
  - *Mitigation:* Keep the classification logic extremely lean (heuristic-first).
