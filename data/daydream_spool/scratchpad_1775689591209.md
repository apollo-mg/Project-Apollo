# Investigation: Environment-First Protocol Implementation
## Epiphany Analysis
The subconscious identifies a pattern of failure stemming from "fighting the map, not the territory." This implies that service failures are often caused by environmental mismatches (incorrect file paths, invalid YAML syntax, missing directories) rather than the core logic of the services themselves.

## Hypothesis
The current codebase lacks a unified pre-flight validation layer. Services are likely attempting to initialize with assumptions about the filesystem and configuration that are not explicitly verified, leading to reactive error handling.

## Audit Plan
1. **Identify Configuration Patterns:** Search for YAML/JSON configuration loading in the codebase.
2. **Identify Filesystem Dependencies:** Search for hardcoded paths or directory creation logic.
3. **Assess Error Handling:** Determine if errors are caught at the "environment" level or only when a service fails to execute a command.
4. **Propose Validation Layer:** Design a `PreFlightValidator` module.

## Initial Findings
- No immediate evidence of a centralized configuration validator found in initial directory scan.
- Need to scan for `yaml.load`, `json.load`, and `os.path` usage to map the "territory."
## Audit Progress
- **Identified Filesystem Interaction:**
    - `src/tool/built-in/file-write.ts`: Uses `mkdir` and `writeFile`. It handles directory creation but doesn't seem to have a formal "validation" phase before the write attempt.
    - `examples/apollo_foreman.ts`: Manually checks `fs.existsSync(SPOOL_DIR)` and `fs.mkdirSync`. This is a "reactive" pattern (checking right before use) rather than a "pre-flight" pattern.
    - `examples/apollo_coordinator.ts`: Uses `fs.existsSync(MASTER_PLAN_PATH)`.
- **Identified Configuration/JSON Interaction:**
    - `src/orchestrator/orchestrator.ts`: Uses `JSON.parse` on content extracted from LLM responses. This is a high-risk area for "syntax" errors mentioned in the epiphany.
- **Gap Analysis:**
    - There is no centralized `EnvironmentValidator` that can be called by the `Orchestrator` or `Agent` before they begin a complex task sequence.
    - The "Environment-First" protocol is currently implemented piecemeal in individual scripts/tools rather than as a core architectural component.

## Proposed Architectural Change: `Environment-First` Protocol
1. **New Module:** `src/utils/environment_validator.ts`
2. **Functionality:**
    - `validateDirectoryStructure(requiredPaths: string[])`: Checks if all necessary directories exist or can be created.
    - `validateConfigSchema(config: any, schema: ZodSchema)`: (If Zod is available) or a custom lightweight validator to ensure YAML/JSON integrity.
    - `validatePermissions(paths: string[])`: Checks write access to critical paths.
3. **Integration:**
    - The `Orchestrator` should invoke `EnvironmentValidator.preFlightCheck()` before dispatching tasks that involve filesystem or configuration changes.
    - The `ToolExecutor` should use this to validate tool arguments (like file paths) before execution.
