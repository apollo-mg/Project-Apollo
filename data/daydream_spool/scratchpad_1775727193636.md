# Epiphany Investigation: Contextual Defragmentation (autoDream)
**Timestamp:** 2024-05-22 (Simulated)
**Status:** Initializing Audit

## Hypothesis
The current architecture relies on manual or reactive memory management. The 'autoDream' process described in the epiphany suggests a proactive mechanism to consolidate 'Topic Files' into high-level abstractions. This is intended to solve 'contextual fragmentation'—where the LLM's attention window is cluttered with granular details rather than the high-level cognitive primitives needed for complex reasoning.

## Investigation Plan
1. **Audit Memory Structure:** Identify how 'Topic Files' and 'MEMORY.md' are currently structured.
2. **Identify Fragmentation Patterns:** Look for evidence of fragmented context (e.g., many small, disconnected files vs. a cohesive hierarchy).
3. **Locate Orchestration Logic:** Find where the 'Agent' transitions to 'Kernel' logic or where state management is handled.
4. **Propose 'autoDream' Implementation:** Design a routine that performs 'Contextual Defragmentation'.

## Initial Findings
- Need to locate the directory containing 'Topic Files' and 'MEMORY.md'.
- Need to understand the current 'Agent' vs 'Kernel' distinction in the codebase.
## Memory Audit Results
- **Current State of `MEMORY.md`**: It functions as a "High-Level System Truth" file (Hardware, Stack, Verified Truths, Ongoing Goals). It is a static summary of the system's current configuration and status.
- **Fragmentation Observation**: The `MEMORY.md` file is highly structured but lacks the "Topic Files" mentioned in the epiphany. The epiphany suggests that 'Topic Files' exist and are being consolidated. In the current filesystem, I see many `.md` files in `legacy_vault/` and `data/daydream_spool/`, but they appear to be logs, scratchpads, or historical records rather than a structured "Topic" hierarchy.
- **The 'Agent' vs 'Kernel' Gap**: The `MEMORY.md` describes the "Active Stack" (Gatekeeper, Engineer, etc.), which aligns with the "Agent" layer. However, there is no explicit "Kernel" orchestration logic visible in the high-level memory. The "Kernel" in the epiphany refers to the *orchestration of state* (the attention window management).

## Hypothesis Refinement
The "Contextual Defragmentation" (autoDream) is not just about summarizing files; it's about creating a **Cognitive Index**. 
Currently, the system has:
1. **Granular Data**: `legacy_vault/*.md`, `data/daydream_spool/*.md` (The "Agent" level noise).
2. **High-Level Truths**: `MEMORY.md` (The "Kernel" level state).

The missing link is a **Middle-Tier Abstraction Layer**: A set of "Topic Files" that represent semantic clusters of information, which are then distilled into `MEMORY.md`.

## Proposed 'autoDream' Architecture
1. **Trigger**: A background cron/timer (e.g., `autodream.timer`) or a threshold of new file creation.
2. **Process**:
    - **Scan**: Identify new or modified `.md` files in the project root and subdirectories.
    - **Cluster**: Use the `Gatekeeper` (0.6B) to assign semantic tags to these files.
    - **Consolidate**: If multiple files share a tag (e.g., "ROCm_Tuning"), the `Engineer` (8B) generates a "Topic Summary".
    - **Update**: The "Topic Summary" is written to a new `TOPICS/` directory.
    - **Distill**: Periodically, the `Engineer` reads the `TOPICS/` directory and updates `MEMORY.md` with the most critical "Verified Truths" or "Ongoing Goals".
3. **Goal**: Prevent the "Attention Window" from being filled with raw logs/scratchpads by ensuring only the "Topic Summaries" or "System Truths" are loaded into the primary context.
