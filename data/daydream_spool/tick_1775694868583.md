# Architectural Audit Report: Interface Fragmentation

## 1. Executive Summary
The audit confirms the "Epiphany": the system suffers from architectural fragmentation where the distinction between the **Ingestion Layer** (how Apollo hears) and the **Observation Layer** (how Apollo is seen) is blurred. The primary offender is the `discord_bridge.py`, which functions as a high-complexity hybrid, performing both command ingestion and proactive telemetry broadcasting.

## 3. Root Cause Analysis
The current architecture allows "Bridges" to contain business logic for *when* and *how* to notify the user. This creates a "Mirroring" effect where every new interface (Discord, WebUI, etc.) must reimplement its own monitoring loops, leading to redundant code and inconsistent system states.

## 4. Proposed Architectural Redesign

### Phase 1: Decoupling (The "Ears" vs. "Eyes" Split)
- **The Ingestion Layer (Ears):** Refactor all bridges (`discord_bridge.py`, `webui_bridge.py`) to be "dumb" translators. Their sole responsibility is to convert external signals (Discord buttons, WebUI clicks) into internal `Command` objects and pass them to the `CognitiveDispatcher`.
- **The Observation Layer (Eyes):** Implement a centralized `TelemetryService`. This service will subscribe to internal system events (e.g., `EVENT_PROPOSAL_READY`, `EVENT_SYSTEM_CRITICAL`). 
- **The Notification Engine:** The `TelemetryService` will then dispatch these events to registered "Output Drivers" (Discord, WebUI, Terminal).

### Phase 2: Refactoring `modules/forge.py`
- Remove the `posted_to_discord` flag and the direct dependency on Discord from the refinement logic.
- Instead, `forge.py` should emit a `PROPOSAL_REFINED` event. The `TelemetryService` will catch this event and decide to push it to the Discord `monitoring` channel.
