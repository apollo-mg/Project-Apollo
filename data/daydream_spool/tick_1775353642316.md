# Architectural Audit: Decision-Payload Latency Gap

## Epiphany Summary
The subconscious identified a critical architectural pattern: the **Decision-Payload Latency Gap**. In high-scale systems (like XDPs or MoE routers), throughput is maximized by decoupling **Decision Metadata** (low-latency, small footprint) from the **Heavy Payload** (high-latency, large footprint).

## Current State Analysis
The current `open-multi-agent` codebase implements a `MemoryStore` (via `InMemoryStore`) that stores `MemoryEntry` objects. 

### Findings:
1.  **Coupled Storage:** In `src/memory/store.ts`, the `MemoryEntry` interface (as implied by usage) bundles `key`, `value`, and `metadata` into a single object stored in a single `Map`.
2.  **Linear Scan Latency:** The `search` method in `InMemoryStore` performs a linear scan over the entire `data` map, checking both `key` and `value`. As the "Heavy Payload" (`value`) grows, the cost of iterating and checking these values increases, potentially blocking the "Decision Logic" (the search/routing).
3.  **Metadata Access:** While `metadata` is present, it is stored alongside the `value`. To retrieve metadata for a decision (e.g., "Which agent wrote this?"), the system must fetch the entire `MemoryEntry`, which includes the heavy `value`.

## Proposed Architectural Refinement: "Tiered Metadata Isolation"

To resolve the Decision-Payload Latency Gap, I propose a split-tier memory architecture.

### 1. Decouple the Store
Instead of a single `Map<string, MemoryEntry>`, implement a dual-tier storage mechanism:
-   **Tier 1 (Control Plane / L3-equivalent):** A `MetadataStore` containing only `key`, `metadata`, and a `payload_pointer`. This is optimized for rapid lookups, searches, and routing decisions.
-   **Tier 2 (Data Plane / DDR5-equivalent):** A `PayloadStore` containing only the heavy `value` strings, indexed by the `payload_pointer`.

### 2. Implementation Plan
-   **Update `MemoryEntry`:** Redefine it to separate the metadata from the payload.
-   **Refactor `InMemoryStore`:**
    -   Internalize two maps: `metadataMap: Map<string, Metadata>` and `payloadMap: Map<string, string>`.
    -   `get(key)` will return a lightweight object containing metadata and a reference to the payload.
    -   `getPayload(key)` will be a separate, explicit call to fetch the heavy data only when required.
-   **Optimize `search`:** The `search` method will now operate exclusively on the `metadataMap` (keys and metadata), ensuring that the "Decision" (finding the right entry) never waits on the "Payload" (the heavy string).

### 3. Impact
-   **Routing Speed:** Finding an entry via `search` or `get` becomes $O(1)$ or $O(MetadataSize)$ rather than $O(PayloadSize)$.
-   **Memory Efficiency:** Metadata can be cached or kept in high-speed memory tiers, while payloads can be offloaded to slower, larger storage.

**Status:** PROPOSAL DRAFTED. 
**Recommendation:** Implement `SplitTierMemoryStore` to decouple decision logic from payload retrieval.
