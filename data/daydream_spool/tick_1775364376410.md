# Architectural Audit: Hot-Swap Orchestration Layer

## Epiphany Analysis
The Subconscious has identified a critical architectural pivot: transitioning from a monolithic model approach to a "Hot-Swap" cognitive architecture. This treats VRAM as a finite, cycling "working memory" between specialized agents (8B Engineer and 32B Vision Specialist). The trade-off of 3-bit quantization is accepted as a necessary sacrifice of "nuance" to ensure "structural accuracy" during high-stakes sensory/forensic audits.

## Current State Audit
- **VRAM Management:** `vram_management.py` exists and provides telemetry via `rocm-smi`. It currently handles ComfyUI VRAM cleanup but lacks the orchestration logic for LLM model swapping (Ollama/vLLM).
- **Infrastructure:** Evidence of `ollama stop` and `vLLM` interaction exists in `legacy_vault`, suggesting the concept is known but not implemented as a primary orchestration layer.
- **Latency Risk:** The "context-switch penalty" (the time taken to stop one model and load another) is the primary technical risk.

## Proposed Architectural Update: The 'Hot-Swap' Orchestrator

### 1. Core Logic: `orchestrator_hot_swap.py` (Draft)
A new module must be developed to manage the lifecycle of specialized agents.

**Proposed Workflow:**
1. **Trigger:** A task requires "Vision Specialist" (32B) or "Engineer" (8B).
2. **Pre-flight:** Check `vram_management.py` to ensure sufficient headroom.
3. **Eviction:** Execute `ollama stop <current_model>` or equivalent vLLM shutdown.
4. **Verification:** Call `wait_for_vram_release()` to ensure the kernel has flushed the VRAM.
5. **Loading:** Execute `ollama run <target_model>` or equivalent.
6. **Execution:** Perform the specialized task.
7. **Cleanup:** Return to a "low-memory" baseline state.

### 2. Technical Requirements
- **Latency Validation:** A benchmark script must be run to measure the exact duration of:
  `ollama stop` $\rightarrow$ `VRAM Flush` $\rightarrow$ `Model Load`.
- **Quantization Strategy:** Standardize on 3-bit (or equivalent) weights for the 32B model to minimize the "load" phase of the cycle.

## Conclusion & Recommendation
The epiphany is valid. The current `vram_management.py` is the correct foundation, but it is currently "reactive" (responding to thresholds). To implement the "Hot-Swap" architecture, it must become "proactive" (orchestrating the swap).
