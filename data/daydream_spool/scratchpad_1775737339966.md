### Hypothesis
The current architecture relies on hard context limits (2048/4096) to maintain stability. This "Perfect Cascade" is actually a suppression mechanism. The "Heretic" (likely a larger/uncensored model) is being throttled by these limits rather than being managed by resource awareness. 

The proposed shift is to move from **Static Context Capping** to **Predictive Resource Orchestration**. 
This requires:
1. **VRAM Debt Calculation**: Estimating the memory footprint of a request (KV cache + model weights + activation buffers) before execution.
2. **Telemetry-Driven Feedback**: Using real-time GPU/VRAM telemetry to decide whether to escalate a request to the 9B model or keep it at the 4B Gatekeeper level.
3. **Driver Safety**: Preventing hard crashes on `gfx1201` (likely RDNA3/AMD hardware) by ensuring the VRAM ceiling is never breached.

### Findings: `vram_management.py`
- **Current State**: It is a *reactive* guard. `smart_vram_guard` checks if `used > VRAM_THRESHOLD_MB` and then triggers `unload_comfy_vram`.
- **The Flaw**: It only acts *after* the threshold is breached. It does not predict the impact of the *next* request. It is a "safety net" (as the Epiphany suggested), not an "orchestrator."
- **Missing Component**: There is no logic to calculate the "VRAM Debt" of an incoming request (e.g., `request_vram_cost = model_size + (context_length * kv_cache_per_token)`).

- **The "Heretic" Connection**: The `architect` and `turbo` profiles use massive 64k contexts. If a request is escalated from `bonsai` (4k) to `architect` (64k), the VRAM jump will be massive.

### Synthesis of the Problem
The current system is a "High-Wire Act":
1. `bonsai` (Gatekeeper) handles the initial triage with a small 4k context.
2. If the request is complex, it's escalated to `architect` or `turbo`.
3. **The Crash Vector**: The jump from 4k context to 64k context in a 27B model creates a massive "VRAM Debt" (KV cache expansion). 
4. `vram_management.py` only reacts *after* the memory is already used, which is too late to prevent a `gfx1201` driver crash if the allocation happens mid-inference.

### Proposed Architectural Update: "Predictive Resource Orchestration"
Instead of `smart_vram_guard` being a reactive check, we need a `VRAMDebtCalculator` that sits in the `orchestrator.py` or a new middleware layer.

**New Workflow:**
1. **Request Arrival**: `bonsai` receives a request.
2. **Intent Analysis**: `bonsai` determines if the request requires "Heretic" level intelligence.
3. **Debt Calculation**:
    - `debt = model_weights_mb + (target_context_length * kv_cache_per_token_mb)`
4. **Pre-flight Check**:
    - `if (current_vram_used + debt) > VRAM_TOTAL_MB`:
        - **Action**: Trigger `unload_comfy_vram()` *before* the escalation.
        - **Action**: Or, force the request to stay in `bonsai` with a truncated context.
5. **Execution**: Escalate to `architect` only after VRAM is guaranteed.

### Draft Proposal for `VRAMDebtCalculator`
```python
class VRAMDebtCalculator:
    def __init__(self, model_manifest):
        self.manifest = model_manifest

    def estimate_debt(self, profile_name, context_length):
        profile = self.manifest[profile_name]
        # Base weight (from manifest)
        base_weight = profile['weight_mb']
        # KV Cache estimation (simplified formula)
        # kv_cache = context * layers * heads * head_dim * bytes_per_element
        kv_cache = context_length * profile['kv_per_token_mb']
        return base_weight + kv_cache
```
