# Architectural Audit: Apollo Bridge Stability & Request Cancellation

## 1. Executive Summary
The investigation confirms a fundamental friction between the Controller (MoE/Pi 5) and the Executor (Dense/Workstation). The "Request cancelled" loops identified in the Epiphany are not mere errors but symptoms of a "Hard-Kill" orchestration pattern. When the Dense model enters high-entropy reasoning phases, the resulting latency or resource spikes (RAM/VRAM) trigger the Controller's `AbortSignal`, causing immediate task cancellation. This creates a feedback loop of cancellations and retries, destabilizing the "bridge."

## 2. Root Cause Analysis
- **Mechanism of Failure:** The `AgentRunner` and `ToolExecutor` rely on `AbortSignal` for lifecycle management. This is a binary state (Running vs. Aborted).
- **The Entropy Spike:** High-entropy workloads (Dense model reasoning) correlate with increased System RAM usage and decreased Tokens Per Second (TPS). 
- **The Friction:** The Controller perceives this latency/resource spike as a failure or a hang and issues an `abortSignal`. Because the bridge lacks a "buffer" or "pressure-aware" state, the task is killed mid-turn, preventing the model from ever completing its reasoning phase.

## 3. Proposed Architectural Update: "The Pressure-Aware Bridge"

### A. Transition from "Hard-Kill" to "Pressure-Aware" Orchestration
Replace the binary `AbortSignal` logic with a tiered `PressureSignal` system.

**New Type Definition (`src/types.ts`):**
```typescript
export enum PressureLevel {
  NORMAL = 'normal',
  ELEVATED = 'elevated', // Reduce concurrency, prioritize existing tasks
  CRITICAL = 'critical'  // Signal model to "summarize and conclude"
}
```

### B. Implementation of the "Reflex Arc" (Decoupling Layer)
1.  **Resource Monitor (`src/utils/resource_monitor.ts`):**
    - A background process monitoring System RAM, VRAM, and TPS.
    - Emits `PressureLevel` updates based on thresholds.
2.  **Pressure-Aware `AgentRunner` (`src/agent/runner.ts`):**
    - Instead of immediately aborting, the runner receives the `PressureLevel`.
    - **At `ELEVATED`:** The runner restricts new tool calls and increases the frequency of "status check" messages to the LLM.
    - **At `CRITICAL`:** The runner injects a system instruction: `[SYSTEM: RESOURCE PRESSURE HIGH. CONCLUDE CURRENT THOUGHT AND PROVIDE SUMMARY ONLY.]`
3.  **Backpressure-Enabled `AgentPool` (`src/agent/pool.ts`):**
    - The pool will refuse to dispatch new tasks if the `ResourceMonitor` reports `CRITICAL` pressure, preventing the "spillover" that triggers the controller's kill switch.

## 4. Concrete Code Change Proposal (Draft)

### Change 1: `src/agent/runner.ts`
- **Current:** `if (this.options.abortSignal?.aborted) break;`
- **Proposed:** 
  ```typescript
  const pressure = this.options.pressureSignal?.currentLevel ?? PressureLevel.NORMAL;
  if (pressure === PressureLevel.CRITICAL) {
    // Inject instruction to wrap up
    conversationMessages.push({ role: 'system', content: [{ type: 'text', text: 'RESOURCE PRESSURE: Summarize and end turn.' }] });
  }
  ```

### Change 2: `src/agent/pool.ts`
- **Current:** Dispatches tasks based on `maxConcurrency`.
- **Proposed:** 
  ```typescript
  async run(agentName: string, prompt: string): Promise<AgentRunResult> {
    if (this.resourceMonitor.getPressure() === PressureLevel.CRITICAL) {
      throw new Error("System pressure too high to dispatch new task.");
    }
    // ... existing logic
  }
  ```

## 5. Conclusion
The "Apollo Bridge" requires a transition from a reactive, signal-based architecture to a proactive, pressure-aware nervous system. By implementing this decoupling, we allow the "Dense" engine to survive high-entropy phases without triggering the "Controller's" kill switch, thereby stabilizing the handshake and preventing the cancellation loops.
