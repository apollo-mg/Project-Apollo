# Investigation: Guardian Watchdog Monitoring Overhead
## Initial Findings
- Identified `buddy_guardian.py` as the primary implementation of the Guardian.
- Identified `test_gpu.py` and `stress_test_buddy.py` as potential testing candidates.
- The Epiphany suggests that the Guardian's own resource consumption (monitoring RDNA 4) might trigger the very hardware thresholds it is meant to prevent.
- Need to audit `buddy_guardian.py` to see how it monitors and if it tracks its own footprint.
- Need to check if existing smoke tests/stress tests include resource overhead checks.

## Plan
1. Read `buddy_guardian.py` to understand the monitoring mechanism.
2. Read `test_gpu.py` and `stress_test_buddy.py` to see current testing coverage.
3. Propose a new test case/metric for 'monitoring overhead'.
## Audit Progress
- `buddy_guardian.py` analyzed. It contains:
    - `SovereignGuardian.audit_plan`: LLM-based alignment check.
    - `SovereignGuardian.check_system_integrity`: Hash-based file integrity check.
    - `scan_content`/`redact_content`: Secret scanning.
- **Observation:** The current `buddy_guardian.py` does *not* monitor hardware (RDNA 4) or resource consumption. It is a logic/integrity guardian, not a hardware/resource guardian.
- The "Guardian Watchdog" mentioned in the Epiphany might be a separate component or a planned evolution.
- I need to check if there are other files related to hardware monitoring or if `test_gpu.py` implements a version of this.
