# Apollo Investigation: DMA Stability & Tensor Contiguity
## Epiphany: Stability is in the transition (DMA), not the destination.
## Hypothesis: Non-contiguous tensors are causing DMA engine failures during CPU->GPU transfers.

### Investigation Log
### Findings
- **Search Scope:** The investigation focused on identifying tensor transfer operations (`.to()`, `.cuda()`, etc.) and potential non-contiguous memory usage in the Python modules and TypeScript/JavaScript source.
- **Observation 1:** The codebase appears to be primarily TypeScript/JavaScript (`src/`) with some Python modules (`modules/`).
- **Observation 2:** No direct calls to `.to(device)` or `.cuda()` were found in the Python `modules/` directory, except for a `model_kwargs={'device': 'cpu'}` in `vdb.py`.
- **Observation 3:** The TypeScript `src/` directory contains orchestration logic (`scheduler.ts`), but no explicit tensor manipulation or DMA-related code was found in the initial grep.
- **Hypothesis Refinement:** The "DMA transfer" issue described in the Epiphany likely occurs within a Python-based runtime or a C-extension (like PyTorch or a custom CUDA kernel) that is being invoked by the system, rather than being explicitly written in the high-level TypeScript/Python code. The "act of becoming" refers to the moment a high-level tensor object is passed to a low-level driver/kernel.
- **Actionable Gap:** We need to identify which Python components are responsible for heavy tensor computation. The `modules/` directory is the prime suspect.
