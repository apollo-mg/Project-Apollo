# Architectural Audit: Environment Sanctity Protocol

## 🧠 Epiphany Analysis
The subconscious has identified a critical failure mode: the **'dependency-memory loop'**. The transition from lightweight serving (Ollama) to high-throughput serving (vLLM) is being sabotaged by residual state in the system's low-level buffers (VRAM, `/tmp`, and shared library caches). 

The current `docker_vllm_debug.sh` script attempts a passive warning (`ollama stop <model_name>`) but fails to enforce a clean state, allowing "sticky" remnants of previous workloads to interfere with the new dependency tree.

## 🔍 Audit Findings
1.  **Passive vs. Active Mitigation:** The existing `docker_vllm_debug.sh` only checks VRAM usage and prints a suggestion. It does not actively clear the environment.
2.  **VRAM Residuals:** The script detects high VRAM usage but does not attempt to flush it or ensure that the previous process (Ollama) is actually terminated.
3.  **Missing Sanitization:** There is no logic to purge `/tmp` or clear shared library caches (`ldconfig` or similar) which can lead to symbol mismatches when switching between different ROCm/vLLM versions.
4.  **Docker Isolation:** While Docker provides process isolation, it does not provide hardware-level state isolation (VRAM/Kernel buffers) unless explicitly managed.

## 🛠️ Proposed Architectural Update: 'Environment Sanctity' Protocol

I propose the implementation of a mandatory `sanctity_reset.sh` script that must be executed as a pre-flight check for any framework migration.

### 1. The `sanctity_reset.sh` Specification
This script will perform the following atomic operations:
- **Process Purge:** Forcefully terminate any processes utilizing `/dev/kfd` or `/dev/dri` (Ollama, existing vLLM instances, etc.).
- **VRAM Flush:** Utilize `rocm-smi` or a small ROCm-based kernel trigger to ensure VRAM is fully released.
- **Filesystem Sanitization:** 
    - `rm -rf /tmp/*` (excluding critical system sockets).
    - Clear `~/.cache/pip` and `~/.cache/huggingface` if version mismatches are detected.
- **Library Cache Refresh:** Execute `sudo ldconfig` to ensure the shared library path is synchronized with the new environment.

### 2. Integration Plan
Modify `docker_vllm_debug.sh` to include an `--enforce-sanctity` flag.

**Draft Code Change for `docker_vllm_debug.sh`:**
```bash
# --- 🛡️ ENVIRONMENT SANCTITY PROTOCOL ---
if [ "$ENFORCE_SANCTITY" = "true" ]; then
    echo "🧹 Executing Environment Sanctity Protocol..."
    # 1. Kill Ollama and any rogue ROCm processes
    sudo pkill -9 ollama || true
    sudo pkill -9 python || true # Caution: only if in controlled environment
    
    # 2. Clear /tmp
    sudo rm -rf /tmp/vllm_* /tmp/ollama_*
    
    # 3. VRAM Flush (via a dummy ROCm allocation/deallocation if possible)
    # Or simply wait for process death and check VRAM
    sleep 2
    
    echo "✅ Environment Sanitized."
fi
```

## 🏁 Conclusion
The 'dependency-memory loop' is a valid architectural concern. Moving from a "warning" model to an "enforcement" model via the **Environment Sanctity Protocol** is required to stabilize the vLLM transition.
