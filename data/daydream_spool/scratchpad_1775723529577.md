# Investigation Log: Planar Screen Architecture Audit

## 1. Current State Analysis
The "Planar Screen" architecture is currently implemented as a decoupled, data-driven system using a JSON file (`data/ui_state.json`) as the bridge between the Logic Engine and the Visual Feedback Engine.

### Components:
- **Logic Engine (`adventure.py`):**
    - Acts as a "UI Generator".
    - It doesn't just update state; it constructs a complete UI layout tree (VBox, HBox, Label, etc.) and writes it to the JSON file.
    - It uses an LLM to generate game state, which it then maps into a UI structure.
- **Visual Feedback Engine (`dynamic_canvas.py`):**
    - Acts as a "UI Renderer".
    - It polls the JSON file every 500ms.
    - It recursively builds a PyQt6 widget tree based on the `root` node in the JSON.
    - It supports specific node types: `VBox`, `HBox`, `Label`, `Button`, and `VideoFeed`.

## 2. Identified Architectural Risks
- **Tight Coupling of Logic and Layout:** `adventure.py` is responsible for both game logic AND the specific UI layout structure. If the UI requirements change (e.g., adding a new widget type), the logic engine must be updated.
- **Implicit Schema:** There is no formal JSON schema. The "contract" is currently implicit in the code of both files. Any deviation in the JSON structure (e.g., a typo in a `type` field) will cause rendering errors or silent failures in `dynamic_canvas.py`.
- **Lack of Validation:** There is no validation step when writing to the state file. If the LLM or the logic engine produces malformed JSON or an invalid UI tree, the canvas might crash or display nothing.
- **Scalability Issues:** As more "Logic Engines" are added, they all must reimplement the complex UI tree construction logic, leading to code duplication and inconsistent UI experiences.

## 3. Proposed Solution: Formalized State Contract
To decouple the engines properly, we should move from a "UI Layout" model to a "State-Driven UI" model.

### Proposed Schema Change:
Instead of the Logic Engine sending a UI tree, it should send a **State Object**. The Visual Engine should then interpret that state using a predefined mapping.

**Current (UI-Driven):**
```json
{
  "root": {
    "type": "VBox",
    "children": [
      { "type": "Label", "text": "LOCATION: Engineering Bay" }
    ]
  }
}
```

**Proposed (State-Driven):**
```json
{
  "version": "1.0",
  "timestamp": "2023-10-27T10:00:00Z",
  "game_state": {
    "location": "Engineering Bay",
    "vitals": {
      "health": 90,
      "oxygen": 85
    },
    "alert_level": "WARNING"
  },
  "metadata": {
    "engine": "adventure_v1"
  }
}
```

### Implementation Plan:
1. **Define a JSON Schema:** Create a formal `.json` schema file that defines the `game_state` structure.
2. **Update Logic Engines:** Modify `adventure.py` to write only the `game_state` to the file.
3. **Update Visual Engine:** Modify `dynamic_canvas.py` to include a "UI Template" that maps `game_state` fields to specific widget layouts.
4. **Introduce a Validation Layer:** Use a lightweight validation step (e.g., `jsonschema` library) in both engines to ensure contract compliance.
