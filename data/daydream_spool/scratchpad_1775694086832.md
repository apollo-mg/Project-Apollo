# Epiphany Investigation: Shift from Hardware Brute-Force to Systemic Evolution (Foundry Focus)

## Context
The subconscious daemon has identified a strategic pivot: moving away from attempting to fix low-level hardware/kernel instability (vLLM/RDNA 4) and instead focusing on the 'Foundry'—the system responsible for high-fidelity data collection and architectural refinement.

## Objective
1. Audit the 'Foundry' component to ensure it is capable of capturing the high-fidelity data required for future architectural evolution.
2. Verify if the 'Dispatcher' is correctly interfacing with the Foundry to manage the current hardware constraints.
3. Determine if the current data collection schema is sufficient to inform a post-RDNA 4 architecture.

## Initial Hypotheses
- The Foundry might be collecting raw logs but lacks the semantic metadata required for "systemic evolution."
- The Dispatcher might be too tightly coupled to hardware stability, potentially discarding "useful" failure data that could inform the next architecture.
- The data schema in the Foundry needs to be audited for "high-fidelity" capabilities.
## Findings: Foundry & Dispatcher Audit

### 1. Foundry (Data Collection) Analysis
- **Current State:** The "Foundry" is not a single monolithic component but rather an emergent property of the `AgentRunner` and `ToolExecutor` interaction.
- **Data Capture:** `AgentRunner.run` and `AgentRunner.stream` accumulate `ToolCallRecord`s (including duration, input, and output) and `TokenUsage`.
- **Gap Identified:** While `ToolCallRecord` captures the *what* and *how long*, it lacks the *why* (semantic intent) and the *contextual state* (the state of the world/memory at the time of the call).
- **Recommendation:** To support "systemic evolution," the `ToolCallRecord` or a new `ObservationRecord` must be expanded to include:
    - A snapshot of relevant `MemoryStore` keys/values.
    - The `AgentState` (specifically the message history leading up to the call).
    - A "Reasoning Trace" if the model provides one (though currently, we only capture the `text` block).

### 2. Dispatcher (Orchestrator/Scheduler) Analysis
- **Current State:** The `Scheduler` and `TaskQueue` manage dependencies and task distribution.
- **Hardware Constraint Handling:** The `AgentPool` uses a `Semaphore` to limit concurrency, which is a direct response to hardware/resource constraints.
- **Gap Identified:** The `Scheduler` is currently "capability-match" based. It does not yet account for "hardware health" or "stability thresholds."
- **Recommendation:** The `Scheduler` should be updated to accept a `HardwareHealth` signal. If the RDNA 4/vLLM stability threshold is breached, the `Scheduler` should automatically transition to a "Conservative Mode," increasing the gap between tasks or reducing concurrency to prevent kernel panics.

### 3. Architectural Proposal: The "Evolutionary Loop"
To bridge the gap between current hardware limitations and future architectural needs:
1. **Enhanced Telemetry:** Modify `src/types.ts` to include `ObservationMetadata` in `ToolCallRecord`.
2. **Foundry Persistence:** Implement a `FoundryStore` (likely a SQLite-backed implementation of `MemoryStore`) that specifically logs these enriched `ObservationRecord`s.
3. **Feedback Loop:** The `Orchestrator` should consume these logs to adjust the `Scheduler`'s aggressiveness.

## Conclusion
The shift from "brute force" to "systemic evolution" is technically feasible by upgrading the telemetry from simple logs to high-fidelity observations. The current codebase has the hooks (`onToolCall`, `onToolResult`), but the data being passed through them is too thin for true architectural learning.
