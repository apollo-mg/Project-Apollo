# Architectural Audit: Tool Matrix & System 2 Integration

## Epiphany Summary
The current architecture treats 'Tool Matrix' (metadata) and 'System 2' (safety/validation) as separate concerns. The epiphany suggests that tool metadata (Security/Reliability scores) should be used to proactively scale the Engineer's skepticism level by injecting this risk profile directly into the System Prompt *before* tool execution.

## Findings
1.  **Current State**: 
    - `src/tool/framework.ts` defines `ToolDefinition` and `ToolRegistry`, but currently lacks fields for `securityScore` or `reliabilityScore`.
    - `src/agent/runner.ts` constructs the `systemPrompt` by appending a static `enforcementPrompt` (the "ENGINEER MODE" mandate).
    - The `AgentRunner` currently uses a binary enforcement: either the prompt is appended or it isn't, based on whether tools are present. It does not differentiate between a "safe" tool (e.g., `echo`) and a "risky" tool (e.g., `shell_exec`).

2.  **Architectural Gap**:
    - There is no mechanism to map specific tool risk profiles to the intensity of the `systemPrompt` instructions.
    - The "Safety First" mandate is reactive (handled in the loop) rather than proactive (handled in the prompt).

## Proposed Architectural Update

### 1. Update `ToolDefinition` (src/types.ts)
Add metadata fields to the `ToolDefinition` interface to capture the risk profile.
```typescript
export interface ToolDefinition<TInput = Record<string, unknown>> {
  readonly name: string
  readonly description: string
  readonly inputSchema: ZodSchema<TInput>
  readonly securityScore: number // 0-10 scale
  readonly reliabilityScore: number // 0-10 scale
  execute(input: TInput, context: ToolUseContext): Promise<ToolResult>
}
```

### 2. Update `ToolRegistry` (src/tool/framework.ts)
Modify `register` and `toToolDefs` to handle the new metadata.

### 3. Dynamic Prompt Injection (src/agent/runner.ts)
Modify the `AgentRunner.stream` loop to calculate a "Risk Density" for the current toolset. Instead of a static enforcement prompt, inject a dynamic instruction based on the average risk of the available tools.

**Proposed Logic for `AgentRunner.ts`**:
```typescript
const toolRiskProfile = toolDefs.map(d => {
  const meta = this.toolRegistry.get(d.name)?.metadata; // Assuming metadata is added
  return (meta.securityScore + meta.reliabilityScore) / 2;
}).reduce((a, b) => a + b, 0) / toolDefs.length;

const dynamicSafetyMandate = toolRiskProfile < 5 
  ? "\n[SYSTEM]: Tools are low-risk. Standard execution applies."
  : "\n[SYSTEM]: CRITICAL. High-risk tools detected. You are in ENGINEER MODE. Validate all inputs with extreme skepticism.";

const baseChatOptions: LLMChatOptions = {
  // ...
  systemPrompt: (this.options.systemPrompt ?? "") + dynamicSafetyMandate,
}
```

## Conclusion
By moving the risk assessment from the execution phase (reactive) to the prompt construction phase (proactive), we transform the Engineer from a passive validator into a context-aware architect. This reduces the likelihood of "hallucinated" tool usage or unsafe command generation by setting the model's "temperature of skepticism" based on the actual tool environment.
