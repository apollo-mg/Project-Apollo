### Step 3: Analysis of `email_ingest.py`
- **The Bottleneck is Confirmed:** The script processes emails one by one in a single-threaded loop (`for key in new_keys:`).
- **Latency Source:** Inside the loop, it calls `assess_email_importance` (line 182), which invokes `query_llm` (line 125).
- **Artificial Throttling:** Line 203 (`time.sleep(2)`) explicitly adds a 2-second delay between *every* email to "prevent VRAM spikes." This is a massive throughput killer.
- **Inefficient State Management:** It re-loads and re-saves the entire `processed_ids` JSON list (lines 141, 200) inside the loop for *every single email*. This is $O(N^2)$ complexity relative to the number of processed emails.
- **The "Straw" Problem:** The script is designed for a trickle, not a flood. It's a sequential, synchronous, and artificially slowed-down process.

### Step 4: Proposed Architectural Pivot (System 2 Scaling)
1. **Implement Multi-threading/Concurrency:** Use a `ThreadPoolExecutor` to allow multiple LLM queries to run in parallel, saturating the available VRAM/GPU capacity rather than waiting for one to finish.
2. **Batch Processing:** Instead of processing one by one, pull a batch of `new_keys`, process them in parallel, and then update the state.
3. **Optimize State Management:** Use a more efficient way to track processed IDs (e.g., a local SQLite DB or at least only saving the JSON once per batch).
4. **Remove/Optimize Sleep:** Replace the hard `time.sleep(2)` with a more intelligent semaphore-based approach or a rate-limiter that respects the LLM's capacity without idling the CPU.
5. **Decouple Acquisition from Ingestion:** Ensure the `mbsync` (System 1) can run independently and that the ingestion engine (System 2) can "drain" the `new/` directory as fast as the LLM allows.
