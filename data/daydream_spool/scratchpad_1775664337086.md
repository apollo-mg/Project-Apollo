## Proposed Architectural Update: "The Orchestration Layer"
Instead of the agent executing `docker run` or `bash scripts` to launch models, we should implement a declarative orchestration system.

### 1. Implementation of `orchestrator.yml` (Docker Compose)
- Create a root-level `docker-compose.yml` that defines the standard environment (vLLM, Whisper, TTS, etc.).
- Use `profiles` in Docker Compose to allow the agent to "activate" specific hardware-optimized containers (e.g., `docker compose --profile cuda up -d`).
- This abstracts the `Dockerfile` selection and hardware-specific flags away from the agent's primary logic.

### 2. Systemd Integration for Persistence
- For long-running background tasks (like the TTS engine or heavy training), use `systemd` unit files that manage the Docker containers.
- This provides automatic restart policies and centralized logging via `journalctl`, removing the need for the agent to manually monitor `ps -a` or `docker ps`.

### 3. Permission Abstraction
- Implement a dedicated `docker-orchestrator` service running with the necessary privileges, communicating with the agent via a controlled API or a socket, rather than the agent needing `sudo` access to the host.
