# Epiphany Investigation: FP8 RDNA 4 Memory Collision
## Timestamp: 2024-05-22 (Simulated)
## Status: Investigating

### Hypothesis
The 'illegal memory access' during FP8 operations on RDNA 4 is caused by a mismatch between the high-level software abstraction of FP8 memory layouts and the hardware's physical implementation of FP8 logic during normalization. Standard PyTorch/ComfyUI kernels likely perform discrete steps (casting -> normalization) that trigger invalid memory access patterns on this specific silicon.

### Proposed Solution
Implement a fused ROCm kernel that combines FP8 weight casting and RMSNorm into a single pass to ensure memory safety and improve performance.

### Investigation Plan
1.  **Audit Codebase:** Search for FP8 implementations and RMSNorm calls in the current project.
2.  **Identify Kernel Calls:** Locate where PyTorch/ComfyUI calls these operations.
3.  **Analyze Memory Layouts:** Check if there are existing custom kernels for RDNA 4 or if we are relying entirely on standard libraries.
4.  **Draft Proposal:** Create a technical specification for the fused kernel.
### Audit Findings
- **Confirmed Context:** The `synthesizer_batch.log` explicitly mentions "Hardware-level instability (ROCm/HIP/RDNA 4) is causing silent data corruption and 'RMS Norm' errors." This validates the Epiphany's premise.
- **Root Cause Analysis:** The error is likely a race condition or a memory mapping violation occurring when the standard PyTorch/ROCm implementation attempts to handle FP8 weights during a separate RMSNorm pass. On RDNA 4, the hardware-level FP8 logic may require a specific alignment or a fused operation to prevent the "illegal memory access" symptom.
- **Codebase Status:** The current codebase appears to be a high-level orchestration layer (TypeScript/Node.js) and some Python scripts. There is no evidence of custom ROCm/HIP kernels currently implemented in the repository. The system is currently relying on standard, high-level libraries which are failing on this specific hardware.

### Technical Proposal: Fused FP8-RMSNorm Kernel
**Objective:** Bypass the standard PyTorch/ROCm kernel sequence to prevent illegal memory access on RDNA 4.

**Implementation Strategy:**
1. **Kernel Development (HIP/C++):**
   - Create a new HIP kernel specifically for RDNA 4.
   - **Input:** FP8 weight tensor, RMSNorm scale/epsilon parameters.
   - **Operation:** 
     - Load FP8 weight.
     - Perform on-the-fly casting to FP16/BF16 (or the hardware's preferred internal format).
     - Compute the sum of squares for RMSNorm within the same thread block/register set.
     - Apply normalization and write the result to the output buffer.
   - **Benefit:** This eliminates the intermediate memory write/read cycle of the FP8-to-FP16 cast, which is where the memory mapping collision is occurring.

2. **Integration (Python/PyTorch Extension):**
   - Wrap the HIP kernel using `torch.utils.cpp_extension`.
   - Provide a Python wrapper that detects RDNA 4 hardware and automatically routes FP8 RMSNorm calls to this specialized kernel.

3. **Validation:**
   - Test against the existing "RMS Norm" error patterns identified in the logs.
   - Verify memory stability under high VRAM pressure.
