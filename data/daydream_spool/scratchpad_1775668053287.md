# Epiphany Investigation: Distributed Swarm Orchestration vs. Single-Model Optimization

## Initial Assessment
The Subconscious suggests that the current architectural focus is too heavily weighted toward fitting single, large models into the VRAM of a single card (the "Golden Rule" ceiling). This has led to a regression where we use smaller models (14B) to avoid ROCm memory-mapping crashes, effectively capping the system's intelligence.

The proposed shift is toward "Distributed Swarm Orchestration"—treating multiple GPUs (specifically the RX 580s) as a unified memory pool or a coordinated swarm rather than individual silos.

## Hypothesis
1.  **The "Golden Rule" Constraint:** There is likely code or configuration that explicitly limits model size based on single-card VRAM availability.
2.  **The ROCm Crash:** The "memory-mapping crash" mentioned is likely related to how `vLLM` or `llama.cpp` handles large tensors across multiple cards or how the current orchestrator manages memory allocation.
3.  **Orchestration Gap:** The current `orchestrator.py` or `fleet_orchestrator.py` likely manages tasks but lacks the logic for "Distributed Swarm" (e.g., model parallelism or pipeline parallelism across heterogeneous/distributed cards).

## Investigation Plan
1.  **Audit `orchestrator.py` and `fleet_orchestrator.py`** to see how they handle model deployment and resource allocation.
2.  **Search for "Golden Rule" or similar logic** in the codebase that might be enforcing the 14B limit.
3.  **Examine `vram_management.py`** to understand how memory is currently being tracked and if it's too conservative.
4.  **Review `ROCM_7.11_MIGRATION_PLAN.md`** to see if the memory-mapping issue was documented and if the "fix" was actually a regression.
5.  **Check `model_manifest.json`** to see the current model deployment strategy.
