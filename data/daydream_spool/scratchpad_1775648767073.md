# Epiphany Investigation: MiniMax/Unsloth Synergy & RDNA 4 Optimization
## Timestamp: 2025-05-22 (Simulated)
## Status: Initializing Audit

### Hypothesis
The subconscious suggests that the efficiency bottleneck for running frontier-scale models on local RDNA 4 hardware is being mitigated by the combination of MoE (Mixture of Experts) architectures (specifically MiniMax) and optimized Triton kernels (Unsloth). This implies that VRAM-intensive models can be executed more efficiently by optimizing the routing and kernel-level operations, potentially bypassing traditional VRAM limitations.

### Investigation Plan
1. **Verify Model Availability:** Check `model_manifest.json` and the `models/` directory to see if MiniMax 2.5 or Qwen 3.5 variants are already present or queued for ingestion.
2. **Audit Hardware/Driver Context:** Check `ROCM_7.11_MIGRATION_PLAN.md` and other ROCm-related files to confirm the current state of the RDNA 4 stack.
3. **Analyze Existing Benchmarks:** Review `vllm_results.log`, `qwen_bench_new.log`, and `moe_shootout_results.json` to establish a baseline for current MoE performance.
4. **Search for Unsloth/Triton Integration:** Search the codebase for any existing implementations or configurations related to Unsloth or Triton kernels to see if the "synergy" is already being leveraged.
5. **Draft Proposal:** Based on findings, propose a benchmark suite specifically targeting the MiniMax/Unsloth/RDNA 4 intersection.
### Step 1: Model Manifest Audit
- `model_manifest.json` checked.
- **Finding:** The manifest currently only contains Kokoro TTS models. MiniMax 2.5 and Qwen 3.5 variants are **NOT** listed in the manifest.
- **Implication:** The "Actionable Insight" to prioritize retrieval is valid; these models are currently missing from the formal registry.

### Step 2: Hardware/Driver Context

- Checking `upgrade_rocm.sh` to see if the environment is prepared for the latest kernel optimizations.
### Step 2: Hardware/Driver Context
- `ROCM_7.11_MIGRATION_PLAN.md` reviewed.
- **Finding:** The current environment is running ROCm 7.2.0-2. The 7.11 "TheRock" preview is considered unstable due to `llama.cpp` regressions and Llama 3.1 validation failures.
- **Implication:** The "Epiphany" suggests that the synergy between MiniMax and Unsloth/Triton might bypass some of these driver-level bottlenecks by optimizing at the kernel level. However, we must be cautious about deploying new experimental kernels (like Triton) on the current ROCm 7.2 stack without verifying compatibility.

### Step 3: Analyze Existing Benchmarks
- `moe_shootout_results.json` reviewed.
- **Finding:** Current benchmarks focus on `Gemma-4` (Dense models). There is no existing data for MoE (Mixture of Experts) architectures in this file.
- **Implication:** We lack a baseline for comparing MoE efficiency (specifically MiniMax) against the current dense models. This confirms the need for the proposed benchmark.

### Step 4: Search for Unsloth/Triton Integration

### Step 4: Search for Unsloth/Triton Integration
- `grep` for "unsloth" and "triton" yielded no direct matches in the project root, but `triton` was found in `vllm_results_fp8_redhat.log` and within the `venv_cachyos` directory (as part of PyTorch/Inductor).
- **Finding:** The system *is* using Triton via PyTorch Inductor (as seen in the `vllm` logs), but there is no evidence of a dedicated "Unsloth" implementation or custom Triton kernel optimization being actively managed by the Apollo codebase.
- **Implication:** The "synergy" mentioned in the Epiphany is currently a theoretical opportunity rather than an implemented feature. The current Triton usage is standard PyTorch Inductor behavior, which is already showing some errors in the `vllm` logs.

### Step 5: Final Synthesis & Proposal
- **Summary of Findings:**
    1. **Models:** MiniMax 2.5 and Qwen 3.5 are missing from the `model_manifest.json`.
    2. **Hardware:** The RDNA 4 stack is currently stable on ROCm 7.2.0-2. Moving to 7.11 is risky due to known regressions.
    3. **Benchmarks:** Existing benchmarks are for dense Gemma-4 models only. No MoE baseline exists.
    4. **Optimization:** Triton is present via PyTorch, but Unsloth-specific optimizations are not yet integrated.

- **Architectural Proposal:**
    1. **Ingestion:** Create a new ingestion pipeline for MiniMax 2.5 and Qwen 3.5.
    2. **Benchmark Suite:** Develop a `moe_efficiency_benchmark.py` that specifically compares:
        - Standard `vLLM` execution.
        - `Unsloth`-optimized execution (if compatible with ROCm/HIP).
        - Metrics: VRAM usage (peak), Tokens Per Second (TPS), and Prompt Processing Latency.
    3. **Kernel Audit:** Investigate if Unsloth's Triton kernels can be ported/compiled for the `gfx120x` architecture to leverage the RDNA 4 hardware more effectively than standard PyTorch Inductor.
