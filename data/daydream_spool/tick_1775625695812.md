# Architectural Audit: Heterogeneity Exploitation Proposal

## 1. Executive Summary
The current orchestration model in Apollo is "Static-Profile-Based." It maps specific models to specific binaries and environment variables via `profiles.json`. While this provides stability, it fails to exploit the inherent heterogeneity of the hardware substrate (RDNA 2 vs. RDNA 4). The "Epiphany" identifies this as a recursive loop of observation without synthesis. 

To move from "latency mitigation" to "heterogeneity exploitation," we must transition to a **Substrate-Aware Routing (SAR)** architecture.

## 2. Current State Analysis
- **Orchestration:** `orchestrator.py` is a linear launcher. It lacks the intelligence to differentiate between hardware capabilities during runtime.
- **Hardware Mapping:** `profiles.json` uses hardcoded `HSA_OVERRIDE_GFX_VERSION` values. This is a "brute force" approach to compatibility rather than an exploitation of capability.
- **MoE Execution:** Current MoE implementations (e.g., Qwen 3.5 MoE) treat all experts as computationally equivalent, ignoring that certain experts may benefit significantly from RDNA 4's specific instruction set disparities.

## 3. Proposed Architecture: The Tiered Execution Hierarchy

### A. Substrate Discovery Layer (SDL)
A new service, `substrate_discovery.py`, will be implemented to probe the hardware at boot time.
- **Inputs:** `rocminfo`, `clinfo`, and system telemetry.
- **Outputs:** A `SubstrateManifest` containing:
    - `gfx_version` (e.g., `11.0.0`, `12.0.1`)
    - `compute_unit_density`
    - `memory_bandwidth_tier`
    - `instruction_set_features` (e.g., specialized matrix acceleration)

### B. Heterogeneous Expert Routing (HER) Protocol
We will replace the standard MoE router with a `SubstrateAwareRouter`.
- **Mechanism:** The router will maintain a weight matrix $W_{sub}$ that modifies the expert selection probability $P(e)$ based on the current `SubstrateManifest`.
- **Formula:** $P_{final}(e) = P_{model}(e) \times \text{Affinity}(e, \text{Substrate})$
- **Result:** On RDNA 2 hardware, the router will naturally favor "Legacy-Optimized" experts. On RDNA 4, it will prioritize "High-Throughput" experts, turning hardware fragmentation into a tiered execution hierarchy.

### C. Implementation Roadmap
1. **Phase 1 (Audit):** Implement `substrate_discovery.py` to formalize the hardware profile.
2. **Phase 2 (Integration):** Update `orchestrator.py` to inject `SubstrateManifest` into the environment of launched services.
3. **Phase 3 (Routing):** Develop the `HER` routing logic within the MoE kernel/dispatch layer.

## 4. Conclusion
By treating hardware heterogeneity as a "texture" rather than "friction," we move from a system that merely *survives* on fractured hardware to one that *evolves* through it. This is the synthesis of the Heretic's granular reality and the Architect's high-level vision.
