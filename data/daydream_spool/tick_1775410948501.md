# Architectural Audit: Granularity Mismatch & Alignment Strategy

## Epiphany Summary
The Subconscious identified a recurring failure pattern: **'Granularity Mismatch.'** This occurs when the precision of input data (e.g., complex regex or high-fidelity data streams) exceeds the optimized 'fast path' of the processing engine (e.g., ROCm backend or regex engine), forcing expensive fallbacks.

## Audit Findings
During the filesystem audit of the `open-multi-agent` project, a critical implementation gap was identified in the `Scheduler` class (`/mnt/TG_2TB/Projects/Apollo/tmp/open-multi-agent/src/orchestrator/scheduler.ts`).

### 1. The 'Hardware-Aware' Stub
The `SchedulingStrategy` includes a `hardware-aware` option, which is intended to align task granularity with hardware capabilities (VRAM/Topography). However, the current implementation is a stub:
```typescript
case 'dependency-first':
  return this.scheduleHardwareAware(unassigned, agents) // Stubbed out
case 'hardware-aware':
  return this.scheduleHardwareAware(unassigned, agents)
```
This confirms that the system is currently *ignoring* the very "Architectural Alignment" the Epiphany suggests is necessary for performance.

### 2. Regex Fragility
The `grep` tool implementation (`/mnt/TG_2TB/Projects/Apollo/tmp/open-multi-agent/src/tool/built-in/grep.ts`) shows evidence of manual regex construction and escaping. This is a direct manifestation of the "regex fragility" mentioned in the Epiphany, where the granularity of the pattern must be carefully managed to avoid engine fallbacks or syntax errors.

## Proposed Architectural Alignment

To prevent future performance collapses, the following updates are proposed for the upcoming voice/agent integration:

### A. Implementation of the Hardware-Aware Fast Path
Instead of treating hardware as a secondary concern, the `Scheduler` must implement a logic that maps task complexity to agent VRAM/Compute capacity.
- **Action:** Replace the `scheduleHardwareAware` stub with a logic that calculates a `Compute-to-VRAM` ratio.
- **Alignment:** If a task requires high-precision processing (e.g., large LLM context), it must be assigned to an agent whose "Fast Path" (high VRAM availability) matches that granularity.

### B. Data Granularity Standardization
For the voice/agent integration:
- **Constraint:** Do not pass raw, uncompressed, or overly high-frequency audio streams to the processing engine.
- **Alignment:** Pre-process audio into a "sweet spot" granularity (e.g., standardized feature vectors) that matches the optimized inference path of the backend, rather than forcing the engine to handle raw, high-precision data.

### C. Regex/Parsing Optimization
- **Action:** Transition from complex, multi-line regex patterns to a "Token-First" approach.
- **Alignment:** Instead of forcing the regex engine to parse complex structures, use a lightweight tokenizer to break data into manageable chunks, ensuring the regex engine only operates on low-complexity, high-speed patterns.

## Conclusion
The system is currently fighting its own abstractions. By moving from "Raw Precision" to "Architectural Alignment," we ensure that the data provided matches the engine's optimized processing logic, avoiding the costly fallbacks that caused previous performance collapses.
