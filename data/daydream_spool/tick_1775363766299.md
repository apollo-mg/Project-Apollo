# Architectural Audit: System Volatility & VRAM Margin Management

## Epiphany Analysis
The subconscious identified a critical failure mode: the "V4 Lite" ambition (massive context) is colliding with the "Memory 1" reality (700MB VRAM margin). The current watchdoging is reactive to model usage but blind to external system volatility (e.g., background GPU processes).

## Current State Assessment
1.  **`deepseek_watchdog.py` (Legacy):** Currently functions as a Hugging Face API poller for model availability. It is *not* a system stability watchdog.
2.  **`vram_management.py` (Active):** Provides telemetry via `rocm-smi` and a `smart_vram_guard` function. It monitors VRAM usage but does not account for external process interference.
3.  **The Gap:** There is no mechanism to detect if a background process (e.g., a browser, a separate ComfyUI instance, or a rogue compute kernel) is consuming the "safety margin" required for the primary model's KV cache.

## Proposed Architectural Update

### 1. Refactor `deepseek_watchdog.py` (or create `system_volatility_watchdog.py`)
The watchdog must transition from a "Model Availability" monitor to a "System Stability" monitor.

**New Logic Requirements:**
- **Process Polling:** Use `psutil` or `rocm-smi` to identify high-priority GPU-accelerating processes.
- **Volatility Check:** Monitor the rate of change ($\Delta$) in VRAM usage. A sudden spike in background VRAM usage is more dangerous than high steady-state usage.
- **Threshold Trigger:** If `VRAM_FREE < 1024MB` AND `Background_Process_VRAM_Delta > Threshold`, trigger emergency protocols.

### 2. Implementation Plan (Drafting `vram_management.py` extensions)
