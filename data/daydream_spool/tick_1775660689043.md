# Architectural Proposal: Tiered Autonomy Framework

## 1. Executive Summary
The current security model in Apollo is a binary "Human-in-the-loop" (HITL) system. This creates a "friction loop" where high-velocity agents (like `flash_coder`) are constantly interrupted by mandatory approval requests for routine tasks, such as running shell tests or writing non-core files. This investigation proposes transitioning to a **Tiered Autonomy Framework** that assigns granular permissions based on agent identity and operational scope.

## 2. Problem Analysis
Audit of `modules/approvals/handler.py` reveals:
- **Hardcoded Friction:** `run_shell` actions are globally blocked (Line 27).
- **Heuristic Bottlenecks:** `write_code` is blocked by file size or presence in `CORE_FILES` (Lines 44-49).
- **Lack of Context:** The system does not distinguish between a "Sandbox Agent" and a "System Architect."

## 3. Proposed Solution: Tiered Autonomy
We will replace the boolean `should_require_approval` logic with a level-based permission system.

### 3.1 Autonomy Levels
| Level | Name | Description |
| :--- | :--- | :--- |
| **0** | **Sovereign** | Maximum friction. Every action requires explicit human approval via GUI/KDialog. |
| **1** | **Guided** | High-friction. Allows small, non-core file edits; requires approval for shell/large files. |
| **2** | **Agentic** | Medium-friction. Allows unprompted execution within designated "Sandbox" directories. |
| **3** | **YOLO** | Zero friction. Uninhibited execution for specialized, high-velocity agents. |

### 3.2 Implementation Details

#### A. Configuration Update (`guardian_manifest.json`)
Introduce an `agent_profiles` section to define capabilities:
```json
"agent_profiles": {
    "flash_coder": {
        "autonomy_level": 2,
        "sandbox_paths": ["/mnt/TG_2TB/Projects/Apollo/temp/", "/mnt/TG_2TB/Projects/Apollo/projects/sandbox/"],
        "max_write_size_kb": 100
    },
    "architect": {
        "autonomy_level": 0,
        "sandbox_paths": [],
        "max_write_size_kb": 0
    }
}
```

#### B. Logic Refactor (`modules/approvals/handler.py`)
Refactor `should_require_approval` to `evaluate_autonomy(agent_id, action, params)`:
1. **Identify Agent:** Determine the `agent_id` from the calling context.
2. **Check Level:** Compare `agent_profile.autonomy_level` against the `action_requirement`.
3. **Path Validation:** If `autonomy_level >= 2`, allow `run_shell` ONLY if `params['file_path']` is within `sandbox_paths`.
4. **Size Validation:** If `autonomy_level < 3`, enforce `max_write_size_kb`.

## 4. Impact Assessment
- **Pros:** Drastically reduces "Request cancelled" logs; enables high-velocity agentic workflows; maintains security for core system files.
- **Cons:** Increased complexity in the `approvals/handler.py` logic; requires agents to pass their identity/context in calls.

## 5. Recommended Action Plan
1. **Phase 1:** Update `guardian_manifest.json` with the new schema.
2. **Phase 2:** Refactor `modules/approvals/handler.py` to implement the level-based check.
3. **Phase 3:** Update the `orchestrator.py` or `task_manager.py` to inject `agent_id` into the approval context.
4. **Phase 4:** Validate with a `flash_coder` test run in a sandboxed directory.
