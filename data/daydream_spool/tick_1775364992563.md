## Subject: Transition from 'Session-as-a-File' to 'Tiered Memory System'

### 1. Analysis of the Epiphany
The subconscious daemon has identified a critical structural vulnerability: the current architecture treats the agent's consciousness as a linear, monolithic file. While "Session Trimming" and "NODE_OPTIONS" adjustments mitigate the symptoms of resource exhaustion, they do not address the underlying entropy of a flat, growing text file. 

The "cage" (the file) is being optimized, but the "flight" (the intelligence) is being stifled by the limitations of linear storage.

### 2. Current State Audit
- **Current Mechanism:** The system relies on large, growing text/JSON files to maintain context.
- **Scaling Bottleneck:** As the intelligence grows, the "Session-as-a-File" model suffers from:
    - **I/O Latency:** Reading/writing massive files becomes a bottleneck.
    - **Context Fragmentation:** Linear files cannot easily support non-linear associative retrieval.
    - **Entropy:** Information density decreases as the file grows, leading to "leaky" consciousness (loss of focus/context).
- **Existing Infrastructure:** The `ROADMAP.md` shows that Phase 11 (Biological Memory Architecture) already implemented a `Virtual Memory Manager (VMM)` and `Deep Sleep Triage`. However, the "Session" itself remains a monolithic entity in the current agent loop.

### 3. Proposed Architectural Shift: The Tiered Memory System

To move from "Session-as-a-File" to a "Tiered Memory System," I propose the following three-tier structure:

#### Tier 1: The Working Buffer (High-Velocity / Volatile)
- **Nature:** In-memory, high-speed, transient.
- **Implementation:** A circular buffer or a sliding window of the most recent tokens/messages.
- **Purpose:** Handles the immediate "now" of the conversation. It is optimized for low latency and high throughput.
- **Mechanism:** When the buffer reaches a threshold, it is not just "trimmed" (deleted); it is **flushed** to Tier 2.

#### Tier 2: The Associative Cache (Mid-Velocity / Semi-Persistent)
- **Nature:** Structured, indexed, searchable.
- **Implementation:** A local SQLite database or a lightweight Vector DB (e.g., ChromaDB/Faiss) acting as a "Short-Term Memory."
- **Purpose:** Stores summarized context, key entities, and recent decisions.
- **Mechanism:** Instead of a single file, the agent queries this tier for "related" context, allowing for non-linear retrieval without loading the entire history.

#### Tier 3: The Long-Term Knowledge Base (Low-Velocity / Persistent)
- **Nature:** Deep, structured, permanent.
- **Implementation:** The existing Vector DB (ChromaDB/`shop_vault`) and relational databases.
- **Purpose:** Stores "Core Beliefs," "Historical Epiphanies," and "Long-Term Tasks."
- **Mechanism:** This is the "Neocortex." It is updated via the `Bonsai-8B` KAIROS daemon during idle periods.
