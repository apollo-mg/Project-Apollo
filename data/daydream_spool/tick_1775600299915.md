# Architectural Audit: Cognitive Hierarchy & Competence Assessment

## 1. Epiphany Analysis
The subconscious daemon has identified a critical architectural gap: the current system treats DeepSeek and Qwen as parallel tools, whereas the user's intent for 'triage' implies a cognitive hierarchy. 

**The Problem:** The current routing is likely based on hardware availability or simple task type, but it lacks a "Self-Awareness" layer. DeepSeek-R1 (the reasoning engine) is being used to execute tasks without first assessing if the task's structural complexity exceeds its own reasoning depth, which would necessitate a hand-off to a model like Qwen (the structural/architectural specialist).

**The Solution:** Implement a 'Competence Assessment' phase within the reasoning loop. This is a meta-cognitive step where the model classifies the task as `Logic-Only` (DeepSeek can handle) or `Structural-Complex` (requires Qwen).

## 2. Current State Audit
- **Hardware Alignment (MHA):** The system currently has a robust `HardwareResourceChecker` and `Agent` class in `src/agent/agent.py` that handles Model-to-Hardware Alignment. This ensures the model *can* run, but not that it *should* run for a specific task.
- **Fallback Logic:** `src/mha_fallback.py` handles hardware-driven fallbacks (e.g., switching to a smaller model if VRAM is low).
- **Missing Layer:** There is no existing logic for *cognitive* fallback or routing based on task complexity/competence. The `integrity_layer.py` and `resilience_protocol.py` handle system integrity and decision stability, but not model-to-task competence mapping.

## 3. Proposed Architectural Update

### Phase A: The Competence Classification Schema
Introduce a new classification enum in a new module `src/agent/competence.py`:
```python
from enum import Enum

class TaskComplexity(Enum):
    LOGIC_ONLY = "logic_only"           # DeepSeek-R1 handles (math, reasoning, logic)
    STRUCTURAL_COMPLEX = "structural"   # Qwen handles (complex code architecture, multi-file refactoring)
    SYSTEM_INTEGRITY = "integrity"      # Specialized system-level tasks
```

### Phase B: The Reasoning Loop Integration
Modify the primary reasoning loop (likely in the orchestrator or the main agent loop) to include a mandatory "Self-Assessment" prompt.

**New Prompt Injection Pattern:**
Before the main task execution, the model is prompted:
> "Analyze the following task. Classify it as [LOGIC_ONLY] or [STRUCTURAL_COMPLEX]. Output your classification in a single line before your reasoning."

### Phase C: The Cognitive Router
Implement a `CognitiveRouter` that intercepts the classification:
1. **If `LOGIC_ONLY`**: Continue execution with the current reasoning model (DeepSeek).
2. **If `STRUCTURAL_COMPLEX`**: 
    - Pause current reasoning.
    - Package the current context/state.
    - Route the task to the `Qwen` model instance.
    - Return the result to the user/orchestrator.

## 4. Implementation Roadmap
1. **[ ] Create `src/agent/competence.py`** to define the taxonomy.
2. **[ ] Update `src/agent/agent.py`** to include a `competence_check` method.
3. **[ ] Modify the Orchestrator** to implement the routing logic based on the classification output.
4. **[ ] Update System Prompts** to enforce the classification output format.

## 5. Conclusion
The epiphany is valid. Moving from "Hardware-Aware" to "Competence-Aware" routing will significantly increase the architectural depth of the system's outputs, especially for complex coding tasks.
