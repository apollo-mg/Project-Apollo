# Architectural Audit: Semantic Conflict Resolution Readiness

## 1. Epiphany Analysis
The subconscious daemon has identified a critical phase shift: the transition from **retrieval** (finding a document) to **disambiguation** (filtering conflicting technical specifications). 

Current state: The RAG pipeline (via `memory_recall` tool and `query_vault.py`) performs a standard similarity search using `Chroma`. This is effective when semantic competition is low. However, as the library scales to 450GB, the probability of "semantic collisions"—where multiple documents contain similar technical terms but contradictory values (e.g., different voltage tolerances for the same component)—increases exponentially.

## 2. Current Architectural Audit

### A. Retrieval Mechanism (`src/tool/built-in/memory-recall.ts` & `query_vault.py`)
- **Mechanism:** Uses `vector_store.similarity_search(q, k=k)`.
- **Limitation:** Similarity search is inherently "fuzzy." It retrieves the most semantically similar chunks but lacks a mechanism to weigh them against metadata (e.g., version numbers, timestamps, or document authority).
- **Conflict Risk:** If two documents are semantically similar but technically contradictory, the current pipeline will return both, potentially confusing the LLM or providing outdated information.

### B. Metadata Utilization (`modules/vdb.py`)
- **Mechanism:** `query_vdb` supports a `filter_dict` using Chroma's filtering syntax (e.g., `{"type": {"$ne": "email"}}`).
- **Limitation:** While filtering is possible, the current `memory_recall` tool does **not** expose metadata-based filtering to the agent. The agent can only provide a text `query`. It cannot say "Find me the specs for Component X, but only from documents where `version >= 2.0`."

### C. Context Window Reasoning (`src/types.ts`)
- **Mechanism:** The `LLMResponse` and `AgentRunResult` structures allow for multi-turn reasoning.
- **Limitation:** The current pipeline relies on the LLM to "self-correct" by seeing multiple results in the `formattedMemories` block. This is a "passive" resolution strategy.

## 3. Proposed Architectural Update: The 'Semantic Conflict Test'

To prepare for the 450GB scale, I propose the following updates to the architecture:

### Phase 1: Metadata-Aware Retrieval (Immediate)
**Update `src/tool/built-in/memory-recall.ts`:**
- Expand the `inputSchema` to include an optional `metadata_filter` object.
- This allows the agent to explicitly disambiguate by passing constraints (e.g., `{"version": "2.0"}`) directly to the vector store.

**Update `query_vault.py`:**
- Modify the CLI interface to accept a JSON string representing the metadata filter.
- Pass this filter into `vector_store.similarity_search(q, k=k, filter=filter_dict)`.

### Phase 2: Conflict Detection Logic (Long-term)
**Implement a 'Discrepancy Detector' in the Orchestrator:**
- When the RAG pipeline returns multiple high-confidence results that contain conflicting numerical or boolean values, the system should flag a `SemanticConflictWarning`.
- This warning would be injected into the `LLMMessage` history, prompting the agent to perform a "Verification Step" before proceeding with technical tasks.

## 4. Conclusion
The current architecture is optimized for **discovery**, not **validation**. To scale to 450GB, we must transition from a "Search-and-Return" model to a "Search-Filter-Verify" model. The implementation of metadata-aware tool calls is the highest priority to enable this transition.
