# Investigation: State-First Contingency Rule
## Epiphany Analysis
The subconscious identifies a critical failure mode: procedural rigidity during network/auth disruptions. The agent's current logic prioritizes tool-specific protocols, which can lead to infinite loops or stalled execution when the environment (network/auth) is the root cause.

## Hypothesis
The current agent architecture lacks a "pre-flight" or "emergency diagnostic" mode that triggers upon specific error signatures (e.g., 401 Unauthorized, Connection Refused, DNS failure).

## Audit Plan
1.  **Identify Error Handling Patterns:** Search the codebase for how HTTP errors (401, 403, 500) and network exceptions are caught and handled.
2.  **Analyze Tool Execution Logic:** Examine the core loop that manages tool calls to see if there is a mechanism to intercept errors and switch to a "diagnostic" state.
3.  **Verify Protocol Rigidity:** Check if the system instructions or core logic explicitly prevent "non-standard" diagnostic commands (like `ping`, `curl`, `nslookup`) when a tool fails.

## Detailed Audit Findings
1.  **Error Handling in `AgentRunner.stream` (runner.ts:373-384):**
    - The `try-catch` block around `this.toolExecutor.execute` catches errors and converts them into a `ToolResult` with `isError: true`.
    - This is the "loop" mechanism: the error is fed back to the LLM as a `tool_result` message.
    - **Problem:** If the error is a network/auth error (e.g., 401), the LLM receives the error message and, following its instructions, attempts to "fix" it or "retry" using the same tool. This creates the infinite loop described in the Epiphany.

2.  **Lack of Error Classification:**
    - The current implementation treats all tool errors identically. There is no distinction between a "logical" tool error (e.g., "file not found") and a "systemic/environmental" error (e.g., "401 Unauthorized").

3.  **Procedural Rigidity:**
    - The `AgentRunner` is strictly bound to the `LLMAdapter.chat` -> `ToolExecutor.execute` loop. There is no mechanism to break this loop and enter a "Diagnostic Mode" where the agent can use low-level tools (like `bash` or `curl`) to verify the environment without relying on the potentially broken high-level tool/adapter path.

## Proposed Architectural Change: "State-First" Contingency
Implement a `DiagnosticInterceptor` within the `AgentRunner` loop.

### Proposed Logic:
1.  **Intercept Tool Results:** In `runner.ts`, inspect the `result.isError` and the `result.data` (the error message).
2.  **Identify Systemic Errors:** Define a set of "Systemic Error Signatures" (e.g., `401`, `403`, `ECONNREFUSED`, `ETIMEDOUT`, `DNS_RESOLUTION_FAILURE`).
3.  **Trigger Contingency:** If a systemic error is detected:
    - **A. State Transition:** Flag the agent state as `RECOVERING_ENVIRONMENT`.
    - **B. Priority Override:** Instead of just feeding the error back to the LLM, the runner injects a high-priority `system` message into the conversation.
    - **C. Diagnostic Instruction:** The injected message instructs the agent: *"A systemic network/auth error was detected ([Error Message]). You are now in DIAGNOSTIC MODE. Use low-level tools (e.g., bash) to verify connectivity/auth before attempting the previous task again."*
    - **D. Tool Access:** Ensure the `allowedTools` whitelist is temporarily expanded or that the `bash` tool is explicitly prioritized for this state.

## Implementation Plan (Draft)
1.  **Modify `runner.ts`:**
    - Add a `SystemicErrorDetector` utility.
    - Update the `try-catch` block in the tool execution loop to check for systemic errors.
    - If detected, append a specialized `system` message to `conversationMessages` before the next `adapter.chat` call.
2.  **Update `types.ts`:**
    - Add `RECOVERING_ENVIRONMENT` to the possible agent states if necessary.
3.  **Update `AgentRunner` options:**
    - Add an optional `diagnosticTools` list to allow the user to specify which tools are available during recovery.

## Conclusion
The Epiphany is valid. The current architecture's "Observe -> Act -> Observe" loop is too rigid to handle environmental failures, leading to "hallucination loops" where the agent tries to solve a network problem using the very tools that are failing. The "State-First" rule will break this loop by providing a clear, non-probabilistic path to recovery.
