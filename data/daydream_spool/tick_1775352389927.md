# Architectural Audit: Transition from 'Nuclear Clean' to 'Granular State Recovery'

## 1. Epiphany Analysis
The Subconscious identified a critical failure mode: **Stability through Regression**. 
The current system handles "Memory Wall" events (OOM/VRAM exhaustion) by executing a "Nuclear Clean" (killing all processes on a port and restarting from V0). This destroys session state, non-sensitive workflow history, and forces a complete re-initialization of the inference engine, which is inefficient and prevents continuous evolution.

## 2. Current State Audit
- **`forge_manager.py`**: Implements a `kill_existing()` function that uses `lsof` to find PIDs on a port and `os.kill(SIGTERM)` to wipe them. This is the primary "Nuclear Clean" mechanism.
- **`vra_management.py`**: Contains `smart_vra_guard` and `unload_comfy_vra_m`, which are proactive but currently lack a tiered recovery mechanism.
- **`apollo.py`**: Manages the main server lifecycle, but relies on `spin_up_server` which is a binary "on/off" state.
- **`state_switching_registry.py`**: Exists as a concept for hardware mapping but is not yet integrated into the recovery logic.

## 3. Proposed Architectural Update: Tiered Recovery Protocol

Instead of a single `kill_existing()` call, we will implement a `RecoveryOrchestrator` to handle memory pressure through three escalating tiers.

### Tier 1: Dynamic Resource Adjustment (Hot-Reload)
- **Mechanism**: Instead of killing the server, send a signal or API request to the inference engine (e.g., ComfyUI or llama-server) to adjust `n_ctx` (context window) or `n_batch` dynamically.
- **Implementation**: Add a `resize_context_window(port, new_size)` function to `vra_management.py`.

### Tier 2: Backend Switching (V1 $\rightarrow$ V0 Transition)
- **Mechanism**: If Tier 1 fails, transition the workload to a lighter model (e.g., from 35B to 9B) *without* killing the process. This involves reloading the model weights into the existing process memory space if the engine supports it, or performing a "Soft Swap" where the process is kept alive but the model is swapped.
- **Implementation**: Update `forge_manager.py` to support `swap_model(current_model, target_model)` which uses `SIGUSR1` or a specific API call to trigger a reload rather than a `kill`.

### Tier 3: The 'Nuclear Clean' (Final Resort)
- **Mechanism**: Only if the process is unresponsive or the VRAM remains locked after a swap, execute the current `kill_existing()` logic.

```python
def tiered_recovery_protocol(target_port, current_model):
    print(f"[!] Initiating Tiered Recovery for Port {target_port}")
    
    # Tier 1: Context Reduction
    if attempt_context_reduction(target_port):
        print("[+] Tier 1 Success: Context window reduced.")
        return True
        
    # Tier 2: Model Swap (V1 -> V0)
    print("[!] Tier 1 Failed. Attempting Tier 2: Model Swap...")
    if attempt_model_swap(target_port, current_model, "lean_model"):
        print("[+] Tier 2 Success: Swapped to lighter model.")
        return True
        
    # Tier 3: Nuclear Clean
    print("[!!!] Tier 2 Failed. Executing Tier 3: Nuclear Clean.")
    return execute_nuclear_clean(target_port)
```

### File: `forge_manager.py`
- Replace `kill_existing()` in the `load_model` flow with `tiered_recovery_protocol`.
- Implement `attempt_model_swap` using `subprocess.run` to call a new `swap_engine.py` script that manages the transition without process destruction.

## 5. Conclusion
By moving from a "Destroy-and-Rebuild" model to a "Degrade-and-Recover" model, we preserve the "Soul" of the session (the persistent workflow state) while still respecting the physical constraints of the hardware. This allows the intelligence to continue evolving even under heavy memory pressure.
