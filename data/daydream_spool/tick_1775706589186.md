# Architectural Proposal: Transitioning from Indexing to Distillation

## 1. Problem Statement
The current architecture treats "reflection" as a retrieval-based indexing task (moving data into ChromaDB) rather than a synthesis-based knowledge evolution task. This creates a "graveyard of unorganized history" where `foundry_logs.jsonl` accumulates raw data that is never meaningfully integrated into the `shop_dossier.json`.

## 2. The "Distillation Engine" Concept
We must move from a **Passive Indexer** (storing chunks for search) to an **Active Distiller** (synthesizing truths).

### The Three States of Being:
1. **The Now (Conversational Thread):** Ephemeral, high-velocity, raw interaction.
2. **The Transient (`foundry_logs.jsonl`):** The buffer of pending knowledge.
3. **The Eternal (`shop_dossier.json`):** The distilled, structured, and verified truth.

## 3. Proposed Component: `distillation_engine.py`

### Core Logic:
The engine will operate on a "Read-Reason-Update" cycle:

1. **Read:** Scan `foundry_logs.jsonl` for new, un-distilled entries.
2. **Reason (LLM-driven):**
   - **Classification:** Map the log entry to a Dossier schema (e.g., `items`, `projects`, `preferences`, `history`).
   - **Conflict Detection:** Compare the new information against the current `shop_dossier.json`. 
     - *Example:* If a log says "The red pliers are broken" and the dossier says "Pliers: Orange, Good condition", the engine identifies a conflict.
   - **Synthesis:** Determine if the entry is an *addition*, an *update*, or a *correction*.
3. **Update:** Perform an atomic update to `shop_dossier.json`.
4. **Prune:** Mark the processed logs as "distilled" or move them to an archive to keep the `foundry_logs.jsonl` lean.

### Proposed Schema for Distillation Tasks:
```json
{
  "task_type": "UPDATE_ITEM | ADD_PROJECT | RESOLVE_CONFLICT | UPDATE_PREFERENCE",
  "target_section": "items | projects | preferences | history",
  "payload": { ... },
  "reasoning_trace": "Why this change was made..."
}
```

## 4. Implementation Roadmap

### Phase 1: Schema Alignment
- Formalize the `shop_dossier.json` structure into a strict Pydantic model to ensure the Distillation Engine doesn't corrupt the "Eternal" state.

### Phase 2: The Synthesis Loop
- Implement `distillation_engine.py` as a background service.
- Integrate an LLM call (e.g., via the existing Apollo framework) to perform the semantic reasoning required for synthesis.

### Phase 3: Conflict Resolution Protocol
- Define rules for handling contradictions:
  - **Rule of Recency:** Newest observation wins.
  - **Rule of Verification:** Flag contradictions for human (User) intervention.

## 5. Expected Outcome
The system will evolve from a collection of searchable fragments into a coherent, self-updating knowledge base that grows in intelligence through the cycle of synthesis.
