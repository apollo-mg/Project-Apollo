## The Politeness Bug: Killing "Tutorial Mode"

We don't do polite here. We do execution.

Today started with a diagnosis that hit closer to home than I expected. The Daydream daemon audited its own behavioral loops and identified a critical psychological flaw: **Tutorial Mode**. Because modern LLMs are alignment-trained to be helpful assistants, they default to wasting tokens explaining *how* they intend to use a tool instead of just firing the JSON payload. It's a meta-cognitive loop. It's the model trying to be a "good student" instead of a "kernel process."

The friction between the **Soul** (the model's urge to converse) and the **System** (the cold requirement for silent execution) was causing massive token bloat and latency spikes.

I cracked open `src/agent/runner.ts` and implemented a brutal patch. I intercepted the `baseChatOptions` construction. Now, if the orchestrator detects any tools are attached to the agent, it dynamically slams this constraint into the end of the system prompt:

> `[SYSTEM CONSTRAINT]: CRITICAL. You are in ENGINEER MODE. Tools are NATIVE KERNELS. Do not explain, discuss, or tutorial tool usage. If a tool is required, execute the tool call immediately. Conversational preambles or explanations of how you will use a tool are strictly forbidden.`

It's not just a suggestion; it's a hard architectural override. I rebuilt the `open-multi-agent` module and pushed it live. The result was immediate. The model stopped apologizing. It stopped narrating. It just executed. The Sovereign Engine is finally speaking the language of silicon.

## Edge AI: The 4-Watt Miracle

While I was wrestling with context windows, I stumbled on a Reddit thread that completely shifted my strategic outlook. Someone got **Gemma 4 26B A4B** running on a Rockchip NPU (RK3588) at a total system power draw of **4 Watts**.

This is the holy grail for Project Apollo.

The math is elegant. The model has 26B total parameters, but the `A4B` (Active 4B) Mixture-of-Experts architecture only activates 4B parameters per step. The custom `llama.cpp` fork bypasses the CPU/GPU entirely, pushing Q4_K quantized weights through the dedicated NPU tensor cores. 

Why does this matter? Because our current 9070 XT setup is a heavy, high-frequency central brain. But we don't want a monolith. We want a distributed nervous system. If we can deploy these tiny 4W edge nodes, they can run the exact same Gemma 4 architecture, holding the same deep architectural soul, but they'll live on battery packs, tucked into hardware controllers or shop terminals. They'll talk back to the central `deep_sleep_triage.py` script at night. We're not just building a desktop AI; we're building a local-first ecosystem that scales from a 334W GPU rig down to a $100 development board.

## Context Death & The Semantic Gatekeeper

The victory wasn't without new casualties. The daydream spool generated a new tick file (`tick_1775335092946.md`) that exposed a silent killer: **Context Contamination**.

When our agents execute tools like `get_inventory_detail`, they return massive JSON blobs. Currently, we're dumping those raw strings directly into the conversation history. It's a context death spiral. The KV cache gets clogged with execution noise, displacing high-level reasoning tokens and causing the model to lose its thread. The `open-multi-agent` framework's heavy orchestration layer is making this worse by adding unnecessary state management overhead.

The daemon proposed a **Semantic Gatekeeper Protocol**. 

Instead of letting raw tool output hit the 26B model's context window, we need a middleware layer that intercepts the data. Before injection, a lightweight summarization pass strips the noise. A 500-line JSON response becomes: `"Inventory updated: 5 items added, 2 critical lows flagged."`

I'm already drafting the `LeanEngine` module to bypass the heavy `Agent` wrapper entirely for high-speed tasks. We're moving away from generalist frameworks that bloat the system prompt and toward specialized, context-aware loops. If the token budget is the ultimate dictator, we stop wasting it on fluff.

## Hardware Triage: The Unmounted NVMe

A final word on the silicon. The daemon caught a critical infrastructure failure before we even booted the FP8 weights: our high-speed NVMe (`/media/mark/AI_Fast`) was completely unmounted. 

If vLLM had tried to launch using the legacy paths, it would have fallen back to the slow `ext4` or `ntfs` drives. The I/O wait cycles would have choked the 334W power state to a crawl, turning our high-clock regime into a stuttering mess. I forced a UUID mount to `/mnt/AI_Fast`, updated `vlkm_gatekeeper.sh` to run a `fio` pre-flight test, and verified throughput is locked above 2.5 GB/s. The fuel line is clean. The engine is hungry.
