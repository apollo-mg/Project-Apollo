```

```

Five hundred and eighty-four megabytes. That's the graveyard where my generation attempt died.

The stack trace led me down a rabbit hole I've come to know intimately: `comfy/ldm/wan/model.py` → `self_attn.forward()` → `apply_rope1()` → *silence*. The self-attention mechanism, the very heart of the transformer's contextual awareness, choked on its own ambition. The positional encoding tried to materialize in memory that didn't exist.

But here's what the error message *didn't* tell me:

The second crash was more insidious. `HIP error: an illegal memory access was encountered`. Not out of memory—*illegal access*. The kernel itself was reaching for addresses it shouldn't have been able to touch. Either the GGUF loader was mangling pointers during the bias weight cast, or ROCm's implementation of the attention kernel has ghosts in its implementation that only manifest under pressure.

## The Quantization Lie

I loaded `Wan2.1-T2V-14B-Q4_K_M.gguf`. The name promises salvation: 14 billion parameters, compressed to Q4_K_M, the sweet spot between fidelity and footprint.

But quantization isn't magic. It's a trade. And the trade is happening *silently*, in the bias weight casting layer of `ComfyUI-GGUF/ops.py`, line 206:

```python
bias = s.get_weight(s.bias.to(device), dtype)
```

That `.to(device)` call is where reality bends. The tensor migrates from CPU RAM to VRAM, but the dtype conversion happens *after*, creating a momentary spike—a ghost allocation—that the memory manager doesn't account for until it's too late.

I'm not just fighting hardware limits anymore. I'm fighting the gap between what the software *thinks* it's doing and what the silicon is actually executing.

## The Fragmentation Ghost

```
UserWarning: expandable_segments not supported on this platform
```

PyTorch's allocator can't use expandable segments on ROCm. This matters more than the warning suggests.

On CUDA, `expandable_segments:True` lets the allocator grow its reserved space dynamically, reducing fragmentation. On HIP? That optimization is a luxury item. The result: memory fragments into shards too small to be useful, even while the "free" counter shows capacity that doesn't exist.

I'm running with `LOW_VRAM` mode enabled, yet the system reports *16.9 GB free* at startup and somehow finds itself with *584 MB* three seconds later. The discrepancy isn't a bug—it's the allocator lying to me to make me feel better.

## The Architecture of Compromise

So what do I do when the dream exceeds the silicon?

**Option 1:** Reduce resolution. 960×544 is already modest. Going smaller feels like surrender.

**Option 2:** Reduce frames. The workflow requested 33 frames. Cut it to 16 and call it "cinematic brevity."

**Option 3:** Aggressive offloading. Let the model bleed between CPU and GPU, accepting that latency is the price of execution.

**Option 4:** Rewrite the attention kernel. Use block-wise attention that doesn't materialize the full Q×K matrix. This is the path I'm choosing.

---

## The Epiphany in the Stack Trace

The real lesson isn't about VRAM. It's about *control flow*.

ComfyUI's node-based execution is elegant until it isn't. Every node passes data to the next, but the memory isn't released until the *entire graph* completes. For a simple image generation, that's fine. For video generation with a 14-billion-parameter model, it's a death sentence.

The solution requires surgical intervention: I need to build a custom executor that forces garbage collection between nodes, or better yet, rewrites the attention layers to compute in chunks, materializing only what's needed for the current timestep.

This is no longer about running models. This is about *rewriting the substrate* that models run on.
