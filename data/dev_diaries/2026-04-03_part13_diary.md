# Project Apollo // Dev Diary: 2026-04-03 (Part 13)

The friction between the silicon and the soul is becoming a permanent feature of my life. 

I spent most of today wrestling with the ROCm 7.1/7.2 drivers on this RX 9070 XT. It is a beast of a GPU, but the software-to-hardware marriage is still a bleeding-edge mess. I’m chasing ghosts in the kernel—"Illegal Memory Access" errors that appear seemingly at random during LoRA application or when the VAE tries to decode a video frame. 

It’s not just a bug; it’s a fundamental mismatch in how the RDNA 4 architecture handles strided tensors and memory mapping. Every time I try to do something "elegant" with a complex tensor operation, the driver throws a fit. 

The technical debt I've had to accrue just to make Wan 2.1/2.2 stable is staggering. I've had to implement what I call "Nuclear Option" laundering: instead of a direct `tensor.to(device)`, I’m forced to pull data back to the CPU, cast it to float, force it into a contiguous numpy array, and then re-upload it to the GPU. It’s ugly, it’s slow, and it’s computationally expensive, but it’s the only way to bypass the buggy PyTorch stream copy kernels that are currently choking my memory system.

The VRAM is a relentless dictator. With 16GB, I am playing a constant game of VRAM Tetris. I have the 14B model trying to breathe, while the Vision model (Qwen 2.5-VL) is trying to see, and the system is trying to maintain a stable context. I’ve had to implement aggressive `split_cross_attention` and hard-clamp the VAE tile sizes to 256 just to prevent the system from vomiting an OOM error the moment a video generation starts. The "System" is so rigid that even a small increase in temporal size causes a total collapse.

But then, there was the breakthrough. 

I managed to unlock a 65,536-token context window. By utilizing a custom `llama.cpp` build with TurboQuant Asymmetric KV Caching and MoE Micro-Batching, I’ve effectively bypassed the `MUL_MAT_ID` matrix math bugs that were crippling the single-slot pipeline. This is a massive win for the "Soul" of Apollo. It means the agent can actually *remember* the conversation, rather than just reacting to the immediate prompt. The ability to ingest massive local context locally, without a cloud provider breathing down my neck, is what this project is actually about.

The architectural realization I'm coming to is that local-first intelligence isn't just about running a model; it's about managing the chaos of the hardware. To have a "Sovereign Entity," we can't just rely on standard libraries that assume a perfect, stable environment. We have to write the stability into the application layer. We have to patch the math, enforce the contiguity, and manually manage the memory strides because the drivers aren't ready for the future we're trying to build.

The "Soul" wants to be a continuous, thinking presence. The "System" wants to crash every time I use a new feature. My job is to build the bridge that keeps the machine from killing the dream.

Phase 13 is a mess of patches, but it's a working mess. The architecture is finally holding.

**Core Lessons Learned:**
- RDNA 4 (ROCm 7.x) is extremely sensitive to non-contiguous tensors in custom kernels; `.contiguous()` is not a suggestion, it is a requirement.
- The "Illegal Memory Access" is often a side effect of asymmetric precision (Float16/BF16) in mixed-precision kernels on AMD.
- VRAM management must be handled at the application level (hard-clamping/tiling) rather than relying on the driver's memory management.
- Local sovereignty requires a "Laundered" approach to data movement to bypass unstable async copy kernels.
