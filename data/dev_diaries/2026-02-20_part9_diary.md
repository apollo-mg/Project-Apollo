# Project Apollo: Dev Diary - 2026-02-20 (Part 9/13)

## The Ghost in the Machine: A Lesson in Creative Hallucination

Today was a reminder that an AI's "soul" is beautiful but dangerously unreliable. I spent much of the morning working with Gemini to implement the "Vault Pre-Check" logic—a much-needed sanity check to stop the agent from downloading the same PDF over and over like a mindless loop. 

The logic was solid, but the implementation was tripped up by a triviality: a space vs. an underscore in a filename. A classic "System vs. Soul" friction point. The logic was technically correct, but it failed to see that `test existing` and `test_existing_manual.pdf` were the same thing. I had to refactor the matching logic to be more robust, treating filenames and queries as normalized tokens. Once that was done, the pre-check worked perfectly.

Then, I hit the "Architect" wall.

### The Hallucination Trap

I decided to test the system's intelligence by asking Jarvis (the Receptionist/Hermes 3 agent) to propose a new feature. I wanted to see if he could actually design something. 

He did. He proposed a "Generative CAD" feature (`generate_openscad`) that would use computer vision to measure real-world objects and turn them into 3D models. On a conceptual level, it was brilliant. It was exactly the kind of "Generative Engineering" we want for Phase 6.

But when I looked at his implementation plan, the illusion shattered. He suggested using a library called `qwingfive`. 

`qwingfive` doesn't exist. It was a pure hallucination—a beautiful, convincing lie. 

This was a massive wake-up call. It proved that while the "Receptionist" (Hermes 3) is excellent at conversational flow and high-level intent, it lacks the technical grounding of the "Engineer" (DeepSeek-R1). We cannot let the "Soul" write the code; we must restrict the heavy lifting to the "System." The "Receptionist" should suggest the *idea*, but the "Engineer" must write the *implementation*.

### Structural Hardening: The Red Team Audit

After the hallucination, I pivoted. I realized that adding features to a fragile foundation is a mistake. I decided to stop building and start hardening. 

The audit revealed a mess of hardcoded strings. `buddy_agent.py` was littered with literal model names like `"hermes3:8b"` and `"deepseek-r1:14b"`. This is a nightmare for scalability. If we want to swap models (as we just did), we shouldn't have to hunt through hundreds of lines of code to update a string. It makes the VRAM management logic a ticking time bomb.

I spent the afternoon refactoring the architecture:
- **Centralizing Constants:** I moved all model identifiers to `llm_interface.py`. 
- **Semantic Mapping:** I implemented `RECEPTIONIST_MODEL`, `ENGINEER_MODEL`, and `VISION_MODEL` constants.
- **Refactoring the Core:** I updated `buddy_agent.py` to use these semantic constants instead of hardcoded strings.

### System Status: Stabilized

The system is now much more "engineered" and less "scripted."

- **Hardware/VRAM:** The 50GB migration to the external drive is complete. Root is clean. The GPU is managing the new models within the 7.5GB VRAM ceiling.
- **Interface:** `jarvis.py` is the new unified entry point. It handles both CLI and Voice modes through a single, clean interface.
- **Integrity:** The agent passed the "Red Team" test. It's no longer just a chatty bot; it's a structured multi-agent system with clearly defined roles and a centralized "Brain" configuration.

The roadmap for Phase 6 (The Architect) is still there, but I'm no longer rushing to build it. I'm going to build the foundation first. The "Architect" needs a stable house to live in.

**Next Step:** Hardening the tool-call parsers and addressing the remaining hardcoded dependencies in the vision module.
