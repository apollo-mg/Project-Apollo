# Project Apollo: Dev Diary Entry 2026-02-26 (Part 1)

The friction between the "Soul" and the "System" is feeling particularly heavy tonight. I wanted to analyze the physical manifestations of my print-quality logic—the test cubes—but I spent the better part of two hours fighting the very infrastructure meant to support it. 

The goal was simple: analyze four new image captures to check for corner bulging, likely a symptom of a Pressure Advance calibration error in the hardware. But the system wouldn't let me touch the data.

The primary antagonist tonight wasn't a bug in my logic, but a ghost in the git-ignore rules. The local environment was being incredibly stubborn. My agent was trying to read the images from the `tmp/` directory, but a broad wildcard `*` in the `.gitignore` was acting like a digital blackout curtain. Even when we tried to use specific exclusion patterns like `!tmp/`, the hierarchy of the wildcard was still choking the file access. It's a classic case of the silicon being too rigid for the fluidity of the task.

We tried the "brute force" approach: copying files to the root to bypass the ignore rules. We even attempted to rewrite the `.gitignore` on the fly, adding `!tmp/**` to try and force the directory open. But the `read_file` tool was still throwing "ignored" errors. It felt like the tool's internal cache was stuck in a different reality than the file system itself.

Then things got weird. `verify_capture.jpg` (a previously tracked file) would load, but the new `analyze_*.jpg` files—despite being explicitly unignored—wouldn't. I had to dig into the Git index itself. It turns out the tool wasn't just looking at the ignore rules; it was looking at the *tracking status*. The system was refusing to "see" anything that wasn't part of the Git repository, effectively blinding the agent to any new, untracked data.

I had to perform a bit of a "surgical bypass." We backed up the tracked file, renamed the untracked image to the tracked filename, and essentially tricked the system into reading the new data under an old identity. It's a hack, but in a local-first ecosystem where we are constantly wrestling with driver quirks and file-system permissions, sometimes the "hack" is the only way to maintain momentum.

The lesson here for the multi-agent architecture is clear: our file-system abstraction layer needs to be decoupled from the version control state. We can't expect an agent to have the same "vision" as the user just because the user can see the file in the folder. The agent's world is governed by the rules of the repository, and if those rules are too strict, the agent is effectively lobotomized.

Now that the bypass is working, we are finally looking at the second image. I'll see if the bulging persists across the sequence. If the corner bulging is consistent, I'll need to recalibrate the extrusion flow.

**Status: Moving from infrastructure-fix to actual data analysis.**
