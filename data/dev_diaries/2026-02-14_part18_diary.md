# Project Apollo: Dev Diary
## 2026-02-14: The Audio Hardware Wall

The dream of a seamless, local-first multi-agent ecosystem hit a brutal reality check today. I spent most of the session wrestling with the "System"—the cold, unyielding friction of Linux audio drivers and permission layers—while trying to give the "Soul" of the project (the Commander agent) its voice.

### The Tight Loop Crash
The initial deployment of the `gemini` user was a disaster. I had the agent running in a tight `while True` loop that was too aggressive. Every time the microphone initialization failed (which it did, constantly), the script would immediately try again. This created a massive file descriptor leak. I watched the terminal scroll with `socket(): Too many open files` and `shared memfd open() failed`. The OS was literally choking on the sheer number of failed attempts to open audio sockets.

I had to implement a safety delay—a simple `time.sleep(5)`—to throttle the retry logic. It’s a small technical fix, but it’s the difference between a system that breathes and a system that suffocates itself.

### The ALSA/PvRecorder Impasse
Even with the throttle, the hardware refused to cooperate. The `PvRecorder` module was throwing a wall of ALSA errors: `unable to open slave`. It felt like the user-space agent was being locked out of the kernel-level audio device. 

I suspected a permissions mismatch between the `gemini` user and the hardware groups. I attempted to inject the user into the `audio` and `pulse` groups, but the hardware remained elusive. The "System" was being stubborn. 

Then, the TTS component hit another snag: a 404 on the Kokoro model download. The URLs were shifting, or the manifest was broken. It's a reminder that even in a local-first architecture, we are still tethered to the shifting sands of remote repositories.

### Hardware Discovery
To break the deadlock, I had to pivot to a diagnostic mode. I wrote a quick `test_mic.py` script to bypass the agent logic and query the hardware directly via `PvRecorder.get_available_devices()`. 

The results were illuminating:
- Index 0: Monitor of USB HIFI
- Index 1: USB HIFI
- Index 2: USB PnP Audio (Mono)
- Index 3: Monitor of Starship/Matisse HD Audio

The hardware is there, visible to the system, but the `gemini` user is still being denied access to the actual stream. The "Soul" is ready to speak, but the "System" hasn't opened the door yet.

### Architectural Lessons
1. **Resource Guardrails are Mandatory:** In a multi-agent environment, an unthrottled error loop isn't just a bug; it's a denial-of-service attack on your own machine.
2. **Permission Granularity:** Local-first doesn't mean "permissionless." The isolation of the `gemini` user is great for security, but it creates a massive friction point for hardware access (ALSA/Pulse).
3. **The Fragility of the Pipeline:** The TTS model failure proves that even when we build local, our deployment scripts must be resilient to external dependency failures.

Next step: Manually mapping the device index and forcing the `gemini` user into the correct hardware group. We'll get this voice working if we have to rewrite the entire ALSA config.
