# Dev Diary: 2026-02-21 (Part 5/10)

## The VRAM Tetris and the RDNA 4 Crash

Today was a brutal reminder that no matter how much "Soul" we pour into the architecture, the "System" is a cold, unforgiving master. I spent the first half of the session fighting a ghost in the machine—a driver crash that felt like a physical seizure of the hardware.

We were attempting to optimize the model-switching logic, but the interaction between the new VRAM management scripts and the RX 9070 XT’s RDNA 4 architecture was fundamentally unstable. The system was trying to load the 14B DeepSeek-R1 model while the Qwen Vision model was still hanging on in the VRAM. The driver simply couldn't handle the contention. It wasn't just a software error; it was a "device wedged" situation where the GPU command processor literally froze. 

I had to reboot the entire machine. It’s frustrating. We're building a multi-agent ecosystem that's supposed to be seamless, but the silicon is currently a bottleneck of memory fragmentation and slow driver flushes.

## Hardening the Core

We couldn't just "fix" it; we had to harden the entire pipeline. I realized our `vram_management.py` was being too optimistic. It was asking the system to unload models, but the ROCm/Ollama backend was taking too long to actually clear the VRAM. I increased the release timeout from 5s to 15s. It’s a heavy-handed fix, but it prevents the race condition where the system tries to load the next model before the previous one has actually left the silicon.

I also patched `llm_interface.py` with a strict safety check. If `unload_model()` fails or times out, the system now aborts the process entirely rather than blindly attempting to load another model and triggering an OOM (Out of Memory) crash. It’s better to have a controlled failure than a system-wide freeze.

## The Pivot: Killing vLLM, Embracing Streaming

The most significant architectural decision today was confirming the death of `vLLM` for this specific setup. We tried to go the high-performance route, but the incompatibility with our current ROCm/RDNA 4 setup is too great. It's not a matter of *if*, but *when* we realize that for local-first, specialized AMD hardware, we need to control the orchestration ourselves.

This led us back to the **Unified Tool Interception (UTI)** strategy.

The current architecture is too bloated. We have a 5-step process:
1. Receptionist (Llama 3.2 1B)
2. Tool Select (DeepSeek 14B)
3. Tool Execution
4. Synthesis (DeepSeek 14B)
5. Persona (Llama 3.2 1B)

It’s too many hops. It’s killing our latency. Every hop is a massive overhead in VRAM management and model loading.

## The Goal: 5 to 3

The vision is to collapse this. We want to move to a 3-step process. By implementing **Streaming** in `llm_interface.py`, we can watch the "thought process" of the DeepSeek model in real-time. We'll use regex to catch JSON tool-calls mid-stream, execute them, and feed the result back to the same model for the final answer.

This isn't just about speed; it's about VRAM stability. One model, one pass. No more constant swapping of the 14B and 1B models that was causing the driver to wedge.

## Summary of Progress

- **Status:** System stabilized. VRAM is behaving.
- **Architecture:** Transitioning from "Three-Mind" (multiple models) to "Unified" (Single-pass streaming).
- **Hardware:** AMD RX 9070 XT is temperamental but capable, provided we respect its VRAM boundaries.

The next step is the real test: implementing the `stream_llm` generator and seeing if we can actually hit that <8s latency target. If we can, Project Apollo moves from a theoretical multi-agent framework to a real-time, responsive intelligence.
