# Dev Diary: The RDNA 4 Ghost in the Machine

## The Silicon Wall: Fighting the `addcmul` Kernel
**Date:** 2025-12-01
**Hardware:** AMD RX 9070 XT (RDNA 4)
**Status:** Critical Error Resolved (Phase 1)

### The Friction: Soul vs. System
I spent the better part of the night staring at a `torch.AcceleratorError`. It’s the same old story: the "Soul" of the model—this beautiful, high-dimensional video generation architecture (Wan 2.1)—is being strangled by the "System." 

The error is a nasty `HIP error: an illegal memory access`. It’s not a logic error; it’s a hardware-level meltdown. Every time the model hits a specific fused kernel—specifically `torch.addcmul` within the `WanAttentionBlock`—the RDNA 4 architecture just gives up. It’s a classic case of the software being too "clever" for the current state of the ROCm drivers. The fused operation expects a memory layout that my GPU simply refuses to provide when the tensors aren't perfectly contiguous.

### The Gritty Details: The Kernel Breakdown
I had to dive deep into `comfy/ldm/wan/model.py`. The traceback was surgical: the crash happens during the `addcmul` call where the attention mechanism tries to combine the modulated shift and scale. 

The problem is twofold:
1.  **The Kernel Bug:** The `addcmul` kernel on RDNA 4 is fundamentally unstable with the specific tensor shapes generated by the `repeat_e` function.
2.  **The Contiguity Trap:** The `repeat_e` function was returning *views* of tensors. In most architectures, that’s efficient. On my machine, it’s a death sentence. Those views create non-contiguous memory layouts, and when the fused kernel tries to write to them, it hits a memory address it doesn't own.

**The Fix:** I had to perform a "surgical decomposition." I stripped out the fused `addcmul` and replaced it with explicit, granular arithmetic: `input + t1 * t2`. It’s less "elegant" from a pure mathematical standpoint, but it forces the hardware to treat each step as a discrete, manageable operation. It’s the difference between trying to swallow a whole pill vs. crushing it into powder.

### The GELU Investigation: Memory Fragmentation & Stability
Once the `addcmul` was bypassed, a new ghost appeared: `GELU`. The standard `torch.nn.GELU` was triggering memory access violations on large FP16 tensors. 

This led me down a rabbit hole into `comfy/ops.py`. I realized the standard implementation was too aggressive with memory allocation. I had to engineer a **"Chunked Safe GELU."** 

I implemented a custom wrapper that identifies large tensors (>4M elements) and processes them in smaller, contiguous chunks. I had to integrate this into the `disable_weight_init` hierarchy to ensure the model's weights could still be handled correctly during the initialization phase. It’s a heavy-handed fix, but it stabilizes the memory footprint.

### Architectural Epiphies: The Local-First Reality
This session reinforced a hard truth for anyone building local-first, multi-agent systems: **Hardware-specific optimization isn't a luxury; it's a requirement.** 

We talk about "model weights" and "parameters" as if they exist in a mathematical vacuum, but they are tethered to silicon that has its own quirks, its own bugs, and its own "personality." If we want to run massive models like Wan 2.1 locally on consumer-grade AMD gear, we can't just rely on generic PyTorch implementations. We have to be ready to rewrite the very math of the model to suit the specific quirks of the kernel.

**Current State:**
- `WanAttentionBlock` & `Head`: Decomposed.
- `GELU`: Chunked/Safe.
- `repeat_e`: Forced Contiguity.

The "Illegal Memory Access" is gone. The video generation is finally breathing. Now, let's see if the RDNA 4 can handle the actual inference load.

**Next Step:** Check the VAE. If the `CausalConv3d` is as broken as I suspect, tomorrow is going to be a long day.
