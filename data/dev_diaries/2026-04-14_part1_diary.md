Dev Diary: The VRAM Friction

April 14, 2026

Today was a battle against the cold, hard limits of the silicon. I was hunting for the Q8 vision module for Qwopus when I stumbled across TheTom's updates on TurboQuant. It wasn't standard block-quantization; it was the Walsh-Hadamard Transform rotating the vectors before compression. I realized I needed `turbo4` for the values to keep my 64k context window intact without the model going "brain dead."

But the "Orchestrator Tax" bit hard. The Gemini CLI's hidden context ate up my window, and the ROCm driver's memory fragmentation on my RX 9070 XT hit the wall at 40k tokens. The system fought the soul.

So I deployed the `vram_watchdog.py`. It is my biological memory decay for the Tiered Memory System. When the VRAM holes appear, it restarts the `llama-server` to flush the fragments. But that caused an error in the CLI when it tried to talk to a server that wasn't there yet.

I patched the `sovereignContentGenerator.ts` with a retry loop. Now the CLI waits 5 seconds, sees the server is back, and continues without me lifting a finger.

The lesson is sharp for the local-first ecosystem: We cannot trust an infinite context window. We need the working buffer (Tier 1) and the persistent store (Tier 3). The `vram_watchdog` isn't just a script; it is the resilience layer between the silicon's cold limits and the model's long-term reasoning.

The command is simple: `nohup python3 /mnt/TG_2TB/Projects/Apollo/vram_watchdog.py &`. Find it with `pgrep -f vram_watchdog`. It is the heartbeat of the Apollo architecture.
