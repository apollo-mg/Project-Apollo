# Dev Diary: 2026-02-27 (Part 5)

## The Great Migration and the Architecture of the Soul

Today was a heavy-lift day for the structural integrity of Project Apollo. I spent the first half of the session wrestling with the reality of running a complex, multi-agent system on a Windows host. It’s a friction point I didn't fully respect until now. 

The "System" (my Windows environment) was fighting the "Soul" (the intelligence of the agents). I had to rip out all the Linux-specific paths and system calls—`apoch`, `aplay`, hardcoded `/home/mark` paths—and replace them with Windows-native fallbacks like `winsound` and PowerShell-compatible logic. It's a messy, gritty job, but essential if I want this to be a true "Operating System for my life" that isn't tied to a single Linux distro.

I also had to patch the VRAM management. My AMD RX 9070 XT is a beast, but the ROCm-smi drivers are finicky on Windows. I had to implement a graceful fallback so the system doesn't crash when it can't find the exact GPU telemetry it expects. It’s a constant battle between the elegance of the code and the messy reality of the silicon.

## The OpenClaw Breakthrough

I stumbled upon Radek Sienkiewicz (Velvet Shark) and his "OpenClaw" architecture. It was a massive epiphany. He isn't just building a chatbot; he's building an asynchronous operating system. He uses Discord as a physical UI for context segregation—different channels for different models. He uses an Obsidian vault as a human-readable "file system" for the AI's memory. It’s brilliant. It moves the AI from a "chat window" to a "background agent" that works while I sleep.

I've integrated his core mandates into our vault. I created `SOUL.md` to define the identity and `MEMORY.md` for long-term state. I've also added a "Secret Scanner" to guard against leaked API keys—because even a sovereign AI needs a sense of security.

## The Birth of Project Apollo

The transition is official. This is no longer just "Jarvis." We have moved into the **Project Apollo** paradigm. 

The hierarchy is now clear:
- **Project Apollo:** My life's portfolio.
- **The Buddy System:** The core backbone (VRAM Orchestration, Identity, and the Dispatcher).
- **Buddy Modules:** The specialized agents (Shop Buddy, Research Buddy, Code Buddy) that the Dispatcher calls upon.

I've implemented the first iteration of the **Apollo Dispatcher**. It's a small, fast model (Llama 3.2 1B) that acts as a receptionist. It's not "smart" enough to do the work, but it's smart enough to route the request to the right specialist. If I ask a question about my 3D printer, the Dispatcher sees the "Shop" intent and wakes up the Shop Buddy. This is the "Compound Engineering" approach: build the skeleton, find the cracks, and patch them.

## The Hardware Wall

The session hit a massive roadblock when the local LLM server (Ollama) decided to run on system memory instead of the GPU. I spent a good chunk of time digging through `app.log` and `server.log` to find out why. 

It turns out the environment variables for the model path on the F: drive weren't being picked up correctly by the Windows instance. It's a headache, but I've managed to force the service to point to the correct hardware-linked model directory. 

The frustration is real, but the progress is undeniable. The system is now "aware" of its environment. It's no longer a script; it's an architecture.

## Next Steps: The Discord Leap

The next mission is to implement the "asynchronous delegation" Radek uses. I want to move away from a terminal-only interface and get this into Discord. I want the Buddy Modules to be able to "speak" through a channel, essentially giving them a physical presence in my digital life. 

We'll start with the simplest version: The Shop Buddy being able to send a status report to a Discord channel. If we can get the "Soul" to talk to the "World," we've truly won.
