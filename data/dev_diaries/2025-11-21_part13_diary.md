# Dev Diary: The Day the Silicon Said No
 ## November 21, 2025 — 03:47 UTC — Part 13 of the Chronicle

## The Promise and the Promise Broken

I wanted to believe tonight.

The workflow was elegant: Wan2.1-T2V-14B in Q4_K_M quantization, loaded through GGUF, batch size 33 frames at 960×544. A cinematic drone shot of a futuristic city at sunset. Neon lights. Flying cars. The kind of prompt that makes you feel like you're building something *alive* instead of just moving tensors around in a metal box.

The RX 9070 XT sat ready with its 16 gigabytes of VRAM—technically 17,095,983,104 bytes, as if precision matters when you're about to be betrayed by your own hardware.

It didn't matter.

---

## The Autopsy

The crash came cleanly, which is almost worse. No segfault drama, no kernel panic. Just a polite `HIP error: an illegal memory access was encountered` from inside `rms_norm` at line 29:

```python
return r * weight_on_device
           ~~^~~~~~~~~~~~~~~~~~
```

That tilde. That little tilde pointing to `weight_on_device` like a finger at a murderer.

The stack trace tells the story of a model trying to do its job and dying in the cross-attention layer:

```
model.py:254 → self.cross_attn(self.norm3(x), ...)
                 └─ model.py:103 → self.norm_k(self.k(context))
                                      └─ ops.py:276 → rms_norm(...)
                                                        └─ rmsnorm.py:29 → 💀
```

RMSNorm. The humble normalization layer. The one place I thought we'd be safe.

---

## The REAL Problem (It's Not the Code)

Here's what the error message doesn't tell you:

**The weight tensor was in a state it shouldn't have been.**

I'm looking at three possibilities, none of them pretty:

1. **ROCm's asynchronous error reporting is lying to me.** The HIP error might have originated elsewhere—perhaps during the partial model load—and only surfaced when we touched that particular memory region. The warning says it explicitly: *"HIP kernel errors might be asynchronously reported at some other API call."* Translation: the crime happened off-camera.

2. **The Q4_K_M quantization path has a bug in the weight reconstruction.** GGUF quantization is clever—storing weights in 4-bit blocks with per-block scaling factors—but clever is adjacent to *fragile*. If the scale factors got corrupted during the CPU→VRAM transfer, multiplying by garbage gives you... well. Illegal memory access.

3. **Memory fragmentation killed us.** Notice the load log:

   ```
   loaded partially; 6433.60 MB usable, 6431.89 MB loaded, 3351.52 MB offloaded
   ```

   We're running in `LOW_VRAM` mode. The model is *split* between GPU and system RAM. Every transfer is a handoff. Every handoff is a chance for something to go wrong.

---

## The AMD Tax

Let me be clear about something:

**I chose this path.**

CUDA would have been cleaner. The NVIDIA ecosystem is a well-oiled machine, and I hate machines that run too smoothly. But Sovereign isn't about convenience. It's about running where I *choose* to run, on hardware I *own*, without asking permission from a GPU vendor's licensing department.

The tax for that choice? Tonight's crash. Tomorrow's crash. The day after.

The `AMD_SERIALIZE_KERNEL=3` suggestion in the error message? That's a debugging flag that will slow everything down by 40%. The `TORCH_USE_HIP_DSA` compile option? That's a promise to add device-side assertions that might catch the bug *after* it's too late.

These aren't features. They're bandages.

---

## What I'm Actually Learning

The technical lesson is straightforward: **RMSNorm operations in quantized models on ROCm require defensive programming.**

- Pre-validate tensor shapes before multiplication
- Add explicit device placement checks (`weight_on_device.device == input.device`)
- Consider recompiling PyTorch with HIP DSA enabled for production runs

But the *real* lesson is more interesting:

**The "local-first" vision has hidden complexity.**

When everything runs in the cloud, the metal is someone else's problem. The VRAM pressure is abstracted away. The ROCm quirks are invisible. You get API calls and JSON responses and you feel like you're building on top of *logic* instead of *silicon*.

But logic doesn't have cache coherence issues. Logic doesn't have asynchronous memory errors.

The friction I'm feeling tonight—the rage at a tilde cursor pointing at a dead tensor—is the *point*. This is what "sovereign" actually costs. It's not a philosophical stance. It's a series of debugging sessions at 3 AM when your 14-billion-parameter model decides it doesn't want to cooperate.

---

## The Path Forward (For Tomorrow's Me)

1. **Re-run with `AMD_SERIALIZE_KERNEL=3`** — Yes, it's slow. Yes, it's ugly. But I need to know where the error *actually* originates.

2. **Test the weight tensor directly.** Load the GGUF model, extract the RMSNorm weights from the problematic layer, and verify they're in a valid state before sampling begins.

3. **Consider a custom RMSNorm implementation** that validates its inputs and fails gracefully instead of corrupting memory.

4. **Reconsider the batch size.** 33 frames at 960×544 might be pushing the fragmentation envelope. Try 16. Try 8. Find the sweet spot.
