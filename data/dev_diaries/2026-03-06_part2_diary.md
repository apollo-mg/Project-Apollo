Today was a grind of the highest order. The tension between my hardware reality and the architectural vision for Project Apollo is palpable. ## The Gatekeeper Shootout

I decided to run some "micro-scale" tests to save the Gemini Pro quota while the heavy lifting happened in the background. I wanted to find a "Gatekeeper"—a small, efficient model that can act as a triage officer for the larger agents.

I ran a shootout between the **Qwen 3.5 0.8B** and the **4B Aggressive** variants. 

The result was a massive wake-up call regarding **Instruction Drift**. 

I forced the models into **Structured JSON Mode** using Ollama's API to see if they could follow strict classification tasks. The 0.8B model was a total failure—it hallucinated "coding" for every single input, essentially becoming a one-trick pony. The 4B model, however, was a revelation. Even though it was slightly slower (1.57s vs 1.11s), it hit 100% accuracy on classification. The "Assistant" training in the 4B model usually makes it too chatty, but the JSON enforcement acted like a digital straitjacket, keeping it focused on the task.

**Lesson learned:** The 4B is our new Gatekeeper. It's fast enough, and the semantic precision is there. The 0.8B is too "small-brained" for the complexity of our multi-agent hierarchy.

## The vLLM/Ollama Schism

There is a looming architectural conflict in how we handle structured data. My current implementation in `llm_interface.py` is hard-wired to the Ollama API. While Ollama is excellent for the "Resident" models, it lacks the high-performance **Guided Decoding** (FSM-based enforcement) that **vLLM** offers. 

The "Sovereign Engine" (Phase 9) requires vLLM for its prefix caching and superior throughput. We have a backend mismatch: the Engineer model needs vLLM, but the current interface isn't ready for that routing. This is critical. If we can't switch backends dynamically, we lose the ability to use the high-performance kernels we're currently building.
