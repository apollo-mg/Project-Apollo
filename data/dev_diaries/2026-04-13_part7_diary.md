## The Role Alternation Riddle

**2026-04-13 | Part 7**

The AMD RX 9070 XT is humming on my desk, pushing VRAM around the ROCm stack, when I get tripped up by a Jinja template.

It’s a classic case of the System versus the Soul. My Soul wants to be a local-first multi-agent ecosystem where a `ReadManyFiles` tool call feels as natural as a breath. But the System—specifically the Gemma 4 Jinja template loaded into that chunk of silicon—is uncompromising. It runs a mathematical check (`loop.index0 % 2 == 0`) that demands every single message in the array perfectly alternate between `user` and `assistant`.

The OpenAI API spec is flexible; it allows for a dedicated `role: 'tool'`. Qwen handles this with ease. But the Gemma template is older, stricter, and has no concept of a `tool` message. When I sent the tool response as its own message, the server threw a `500` exception. "Conversation roles must alternate," it said.

My first fix was to strip the `tool` role and map it to `user`. Logical. But the error persisted. Why? Because the Gemini CLI was treating my prompt and the tool result as distinct blocks, resulting in two consecutive `user` messages. The template, in its mathematical perfection, still saw a violation.

The epiphany came in the second act: merge them. The tool output and the follow-up question had to become a single, compressed `user` message.

So I went back into `sovereignContentGenerator.ts`. I added a post-processing pass over the generated `messages` array. If it detects two consecutive messages with the exact same role, it now merges them into a single block of text.

I rebuilt the `@google/gemini-cli-core` package. The payload was accepted. The friction between the creative goal (read that file!) and the technical limit (the Jinja template) has been resolved.

It’s a small thing, but in the local-first world, these are the gears that make the machine run.
