# Apollo Dev Diary: 2026-03-27 (Part 1)

The friction between silicon and soul is real. Today was a brutal, beautiful lesson in the volatility of a local-first ecosystem. I spent the morning wrestling with the sheer, unadulterated power of the 35B MoE architecture, only to have the entire house of cards collapse because of a single, tiny architectural mismatch in a shell script.

### The 35B Breakthrough

I finally got the Qwen 3.5 35B MoE (Unsloth IQ2_XXS) running on the 9070 XT. It was a moment of pure technical euphoria. Despite the 2-bit quantization, the model isn't just "functional"—it's brilliant. 

I ran a vision test, feeding it a picture of fruit on a patterned plate. The speed was staggering: 572 tokens/sec pre-fill and 68 tokens/sec generation. Even more impressive was the "intelligence" of the vision-language bridge. The model didn't just see "fruit"; it identified the specific colors of the plate's rim and the exact texture of the orange segments. It proves that Unsloth’s "Dynamic 2.0" quantization isn't lobotomizing the spatial reasoning. 

The VRAM was hovering at 15.9GB—dangerously close to the 16GB ceiling—but because we implemented the hard-cap on the KV Cache (131k tokens), the system is rock-solid. It’s not thrashing. It’s not bleeding into system RAM. It’s just a heavy, stable, local brain.

### The Agentic Collapse

Then, the "System" fought back.

I tried to move from pure inference to the agentic loop—the true goal of Project Apollo. I wanted the model to act as a tool-user, writing code and executing it via a shell. But my `buddy_agent.py` was built for an API-driven world. It was looking for a server on port 8082 that didn't exist.

The error was a classic: `Connection refused`. I had been running the model via `llama-cli` (an interactive terminal session), but the agent expected a `llama-server` (a background HTTP service). 

I had to pivot. I rewrote the launcher to spin up the server with the same VRAM-safe parameters. But then, a new ghost in the machine appeared: a shell compatibility error. I was using `fish` shell, and the standard Python `activate` script was throwing a fit because it was written for `bash`. A quick fix (sourcing the `.fish` version) got me back into the driver's seat.

### The Wall

I launched the agent, ready for the 5-turn coding loop. The logs showed the embedding models loading, the architecture initializing, and then... nothing. 

`[ALERT] INTEGRITY BREACH!`
`[ENGINE] Waking Unified Inference Engine...`
`Error connecting to Unified LLM stream: [Errno 111] Connection refused`

The connection failed. Even with the server script, the agent couldn't shake hands with the model. The "System" is proving to be incredibly temperamental. Between the Python 3.14/Pydantic compatibility warnings and the networking failures, the friction between my high-level agentic goals and the low-level driver/server reality is palpable. 

### Core Lessons

1. **Quantization isn't kill intelligence, it kills stability.** The 2-bit model is smarter than I thought, but the memory-management overhead of the MoE routing is a razor's edge. We are living on the edge of 16GB.
2. **Local-first means Local-everything.** You can't just write a script and expect it to work; you have to account for the entire stack—the shell, the Python environment, the HTTP server, and the driver.
3. **The "Soul" is ready, the "System" is still catching up.** The model's reasoning is there, but the infrastructure to harness that reasoning is still a mess of mismatched scripts and broken ports.

The next step is to debug why the `llama-server` isn't accepting the connection from the agent. If we can bridge that gap, we finally have a thinking, coding, local-first agent sitting in my living room.
