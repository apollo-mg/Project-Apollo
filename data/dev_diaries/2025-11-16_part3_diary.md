# Dev Diary: The Day Scripts Learned to Fear Us
## 2025-11-16 | Part 3: A Humbling Education in Windows

---

### The Illusion of Control

We started this session with a problem that should have been trivial.

`ProcessWaitClose()` isn't waiting. The AutoHotkey documentation says it should block execution until a process terminates. The universe says otherwise.

I watched in disbelief as the script marched forward—PowerShell window blooming into existence *while* ffmpeg was still dutifully recording. The keystroke we sent to quit ffmpeg (`q`) was consumed by whichever window happened to be greedy that millisecond. A race condition born from our own overconfidence.

### The Escalation

**Attempt 1:** Replace `ProcessWaitClose()` with a `while (ProcessExist())` loop. 

*More robust*, I told myself. *More explicit.*

**Attempt 2:** The loop fails identically. I add debug message boxes—those humble popups that have saved more developers than I can count. The user reports: *"Key-up event fired, powershell window appeared then disappeared, ffmpeg is still recording."*

The PID message box never appeared. The script believes ffmpeg doesn't exist while we're both staring at it.

**Attempt 3:** A complete architectural rewrite. Single hotkey. `KeyWait`. One continuous thread instead of two separate events fighting over global state.

*"Error: ffmpeg process was not found or already closed."*

The error message arrived like a polite rejection letter.

**Attempt 4:** A temporary file to store the PID. Immutable. Persistent. Immune to whatever ghost was stealing our variables between hotkey threads.

*"FATAL: Could not write PID file. Script cannot continue."*

### The Revelation

That last error was the gift.

After hours of wrestling with threading models and variable scoping and process handles, we discovered the truth: **the environment doesn't care how clever our scripts are.**

We were blocked from writing to the temp directory. Period. Whether it's antivirus theater, permissions paranoia, or something more sinister doesn't matter. The silicon had spoken. We had been playing god with our automation while the OS quietly held a veto.

### The Retreat to v2

We're retreating to a fresh directory—`v2\`. Not because the code was wrong, but because our assumptions were arrogant.

**What we learned:**

- `ProcessWaitClose()` may be a liar in certain Windows configurations
- Global variables in AutoHotkey v2 are not always *global* enough
- Even PID files can be denied
- The difference between "technically correct" and "actually works" is measured in hostile environments

**What we're taking forward:**

- The whisper transcription itself works—we proved that
- The architecture (AHK → ffmpeg → PowerShell → whisper) is sound
- But the handshakes between them are fragile in ways we haven't mapped

---

### The Question for Tomorrow

Do we go command-line native and avoid AutoHotkey entirely? Do we find a Windows audio capture method that doesn't require us to babysit process lifecycles? Or do we accept that some environments are allergic to automation, period?

The `v2\` directory is empty. For now, that's honest.
