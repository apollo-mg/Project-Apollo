# Dev Diary: 2025-11-29 // The RDNA 4 Memory Wall

## The Ghost in the Silicon
Today was a brutal, high-friction battle against the RDNA 4 architecture. I’ve been chasing a phantom—a recurring `HIP error: an illegal memory access` that seems to haunt the `WanAttentionBlock` every time it attempts a complex tensor operation. 

On paper, the math is sound. But the "System"—the cold, hard reality of the ROCm driver and the physical memory layout of the RX 9070 XT—doesn't care about mathematical elegance. It cares about contiguity, alignment, and the sheer audacity of asking it to perform a fused operation across device boundaries.

## The Friction: Soul vs. System
The "Soul" of this project is the Wan 2.1 model—a beautiful, high-dimensional flow of data meant to generate cinematic reality. But the "System" is hitting a wall. I discovered that the issue isn't just a simple bug; it's a fundamental incompatibility in how the current ROCm implementation handles fused kernels. 

When the model tries to perform `(cast_to(...) + e).chunk(...)`, it’s asking the GPU to simultaneously cast a tensor, add it to a time-embedding, and then slice it. On RDNA 4, this sequence triggers a race condition in the memory controller. The driver tries to optimize the operation, fails to manage the non-contiguous memory, and then—*boom*—illegal memory access. The silicon is literally tripping over its own feet.

## The Architectural Epiphany: Decomposition
I realized I couldn't "fix" the driver, so I had to change how the model perceives its own memory. 

The breakthrough was realizing that **contiguity is king**. I couldn't just fix one line; I had to perform a surgical refactoring across the entire `WanModel` implementation. 

**The Strategy:**
I moved away from the elegant, one-line "fused" operations. Instead, I implemented a rigorous, multi-step decomposition:
1. **Isolate the Cast:** I stripped the `cast_to` operations into their own dedicated lines. This forces a synchronization point, ensuring the host-to-device copy is fully realized before the next operation starts.
2. **Enforce Contiguity:** I introduced aggressive `.clone()` calls after addition operations. This forces the engine to materialize the result into a fresh, contiguous block of VRAM, breaking the chain of non-contiguous memory that was crashing the kernels.

## The Gritty Details
It wasn't a simple patch. I had to trace this through:
* `WanAttentionBlock`
* `Head`
* `MLPProj`
* `WanAttentionBlockAudio`
* `CausalAudioEncoder`
* `MotionEncoder_tc`

Each one of these modules was hitting the same memory-layout-trap. I had to rewrite the `forward` passes to be more "verbose" in terms of memory management. It’s less efficient in a theoretical sense—more operations, more memory movement—but it’s the only way to achieve stability on this specific hardware. We are trading a bit of raw throughput for the ability to actually *run* the model without the system collapsing.

## Lessons for the Local-First Ecosystem
This session reinforces a hard truth for the future of local-first AI: **Hardware-agnostic code is a myth.** 

If we want to empower users on consumer-grade AMD hardware, our engines cannot just be math libraries; they must be memory-aware orchestrators. We cannot assume a perfect, unified memory space. Our agents and models must be built with "Hardware Defensive Programming"—anticipating that the driver might fail a complex kernel and providing a "safe path" via explicit memory management.

The engine is now stable. The ghost is gone. Now, let's see if the Soul can finally dance.
