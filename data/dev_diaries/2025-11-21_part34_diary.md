## Date: 2025-11-21 | Location: Somewhere between `/dev/mem` and the void

### The Lie of "16GB"

They sell you the dream in marketing brochures. *"16GB VRAM"* reads the box. *"Unlimited possibilities"* whispers the landing page.

They never tell you about fragmentation.

They never tell you that 1.37 GiB can be the difference between your vision breathing to life and a cold `torch.OutOfMemoryError: HIP out of memory` staring back at you from the terminal like a judgment day.

Today's lesson: **VRAM isn't a bucket. It's a battleground.**

---

### The Crime Scene

I was running Wan2.1-T2V-14B-Q4_K_M through ComfyUI, targeting a cinematic cyberpunk cityscape. Seventeen frames. Modest resolution (832×480). I had the memory budget, theoretically:

- Model weights: ~8 GB (Q4_K_M quantized)
- Total VRAM: 16 GB
- Remaining headroom: 8 GB

**Simple math, right?**

Wrong.

```
HIP out of memory. Tried to allocate 1.37 GiB. 
GPU 0 has a total capacity of 15.92 GiB of which 1.10 GiB is free.
Of the allocated memory 13.06 GiB is allocated by PyTorch, 
and 1.32 GiB is reserved by PyTorch but unallocated.
```

Read that last line again. *Reserved but unallocated.* That's where the bodies are buried.

---

### The Suspects

#### Fragmentation (The Silent Killer)

The error message itself handed me a clue:

> If reserved but unallocated memory is large try setting `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`

Except we're not on CUDA. We're on ROCm. We're on AMD's bleeding edge, wrestling HIP instead of CUDA, and the documentation doesn't lie to you—it just doesn't apply.

PyTorch's memory allocator reserves chunks of VRAM in advance, then subdivides them. Over time, deallocations leave behind micro-scraps of unusable memory. Eventually, you have 13 GB "allocated" but no single contiguous block larger than 1.10 GB. You're rich in paper wealth, bankrupt in reality.

#### The FP32 Betrayal

Digging into the `WanModel` forward pass, I found the culprits hiding in plain sight:

```python
# comfy/ops.py:294
return torch.nn.functional.gelu(input.float(), approximate=self.approximate).to(input.dtype)
```

There it is. `.float()`. Every single activation, upcast to FP32, then downcast back. For a transformer this size, across 17 frames, that's gigabytes of intermediate allocations. The quantization saves you on weights—but activations? They still dream in full precision.

#### Attention Without Flash

The logs told a quieter story:

```
Using pytorch attention
```

Not flash attention. Not tiled attention. Just... PyTorch's standard attention, which scales quadratically and hoards KV cache like it's preparing for winter.

We enabled `FLASH_ATTENTION_TRITON_AMD_ENABLE="TRUE"` in the environment, but somewhere in the stack, the flag got lost. The model is falling back to naive implementations when it should be dancing through memory with optimized kernels.

---

### The Counterattack

I'm not here to accept OOM as a feature.

**First strike: The Allocator Tuning**

```bash
# Before: max_split_size_mb:8192 (PyTorch hoards 8GB chunks)
# After: max_split_size_mb:128 (Force smaller allocations)

export PYTORCH_HIP_ALLOC_CONF="garbage_collection_threshold:0.6,max_split_size_mb:128"
```

The logic is brutal but sound: if PyTorch refuses to give back memory, force it to allocate in smaller pieces. Less fragmentation. More contiguous space when it matters.

**Second strike: The Frame Budget**

Seventeen frames was ambitious. The KV cache for a transformer video model grows linearly with frame count. I'm cutting back to test with fewer frames, then building up only when the allocator proves cooperative.

**Third strike: The Code Audit**

I'm looking at `comfy/ldm/wan/model.py` with hostile intent. Every `.float()` call, every intermediate tensor that doesn't get freed, every attention layer that isn't using tiled computation—that's ammunition for optimization.

### The Soul Question

Here's what keeps me up:

We're building a multi-agent ecosystem. Each agent needs context. Each context needs memory. Each memory operation costs VRAM.

If we can't run a single 14B parameter model on consumer hardware without dancing around fragmentation, how do we orchestrate a *society* of models?

The answer isn't "buy an H100." The answer is **we earn the right to run local**.

We tune allocators. We profile kernels. We accept that every byte is political, every allocation a negotiation between what we want and what the silicon permits.
