# Apollo Dev Diary: The Stubbornness of Silicon

The friction between a high-level intelligence and the actual silicon is real. I thought I had the "Soul" of the agent—the logic, the ability to reason about the Klipper API—but I ran head-first into the "System" limitations of the local LLM.

Today's session was a brutal lesson in model instruction following. I have the `deepseek-coder-v2-lite-instruct` model running locally on my 9070 XT, and while it’s incredibly fast, it is incredibly stubborn. It kept defaulting to its pre-trained knowledge—suggesting generic G-code like `GET_TEMPERATURES`—completely ignoring the custom `Get-KlipperData` tool I had painstakingly defined in the system prompt. It's a classic case of a model prioritizing its training weights over the immediate context window.

The technical hurdle was twofold: first, a permissions nightmare where the PowerShell script was trying to write `voice_session.json` to the root of the C: drive, throwing `Access Denied` errors. I fixed that by forcing absolute paths into a temporary directory, but that was just the appetizer.

The real meat was the "Tool-Use" failure. I realized that for lightweight, quantized models, the `SystemPrompt` is often treated as a suggestion rather than a law. To overcome this, I had to pivot my entire architectural approach to the agent's cognitive load.

I’ve implemented a "brute-force" injection strategy. Instead of hoping the model remembers the tool definition from the system prompt, I am now appending a hard-coded instruction directly to every single user prompt: *"If the user asks for status, output 'COMMAND: STATUS'"*. 

By simplifying the command from a complex regex-heavy string to a single, predictable keyword, I'm reducing the "intelligence" required to trigger the tool. The Python side (`commander_voice.py`) is now looking for this simplified `STATUS` trigger, which it will then map to the actual API path internally.

It's a messy, gritty way to work, but in the world of local-first AI, sometimes you have to stop trying to build a "perfect" mind and start building a more robust "leash."

**Core Lessons Learned:**
- **Instruction Precedence:** Small models require "in-line" instructions. System prompts are too easy for them to ignore.
- **Complexity is the Enemy:** The more complex the tool call, the more likely the model is to hallucinate. Simpler, keyword-based triggers are more reliable for local inference.
- **Observability is King:** Adding the `[LLM RAW]` and `[LLM STDERR]` debug prints was the only reason I could see the "Access Denied" error. Never fly blind.

**Next Steps:**
- Verify the simplified trigger works with the actual API response.
- If the model still hallucinates, I may need to move to a larger, more capable (but slower) model for the "Command" phase.
