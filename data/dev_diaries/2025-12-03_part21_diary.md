# Dev Diary: The RDNA 4 War and the Numpy Laundering Fix

**2025-12-03**

It’s 4:00 AM. The air in my office feels heavy with the hum of the RX 9070 XT and the palpable frustration of fighting a driver that refuses to play nice with modern tensor layouts. We are building something beautiful with Project Apollo—a local-first multi-agent ecosystem that actually *understands*—but right now, the "Soul" of the project is being throttled by the cold, unyielding "System" of the silicon.

### The Memory Access Nightmare

Today was a descent into the hell of RDNA 4 driver bugs. We hit a wall with the GGUF loader. Every time we tried to transfer bias tensors from the CPU to the GPU, the driver threw an `Illegal Memory Access` error. It’s a classic symptom: the driver is trying to touch a memory page that’s either fragmented or improperly aligned, likely a byproduct of how the GGUF loader interacts with the ROCm stack.

I had to implement what I’m calling the "Ultimate Nuclear Option." 

I couldn't just rely on a standard `copy_` operation. The memory was "dirty." To fix it, I introduced **Numpy Laundering**. Instead of a direct tensor transfer, we now pull the bias data back to the CPU, cast it through a Numpy array, and then rebuild a fresh PyTorch tensor from scratch before pushing it back to the GPU. It’s inefficient in theory, but it provides a "clean slate" for the driver. It breaks the connection to the problematic memory pages. It’s a hack, but it’s a necessary one.

### The Performance Seesaw

The struggle for stability almost killed our performance. When I first tried to fix the crashes, I overcorrected. I forced the system to be too "safe," and the performance cratered. We were looking at 130 seconds per iteration. In a real-world workflow, that’s a death sentence. It’s the difference between a tool and a paperweight.

We had to find the "Goldilocks" zone:
1. **Biases:** Keep the Numpy Laundering. They are small, so the overhead is negligible, but the stability gain is massive.
2. **Weights:** Revert to the standard `.to(device)` path. For the massive weight matrices, we need the optimized, asynchronous transfer paths provided by PyTorch to keep the 13B models from crawling.

### Ghost in the Machine: The Video Glitch

Then came the visual artifacts. We were seeing this weird, strobe-like flashing in the video output—frames that looked totally disjointed, like a slideshow of random, unrelated images.

It wasn't just a "glitch"; it was a fundamental mismatch in the noise schedule. The Wan 2.1 model was being fed a noise schedule it didn't understand because we weren't applying the correct "shift." We had to implement the `ModelSamplingFlux` node with `max_shift=3.0`. It’s the difference between a coherent video and a strobe light.

But that wasn't the only ghost. The Triton backend on RDNA 4 was producing "backwards motion" artifacts—objects moving in ways that defied physics. The fix required a surgical strike on the attention mechanism. We had to disable the buggy Flash Attention kernel and force the **PyTorch Memory Efficient Attention** backend via a `sdp_kernel` context manager. It gives us the speed we need without the visual madness.

### Building the Sanctuary

By the end of the session, the environment felt cluttered. When you’re debugging at this level, you need a "Clean Room." You can't have your patches bleeding into your testing.

I’ve decided to split the architecture. I’ve built a `venv_rocm_fresh`—a completely isolated, clean environment. I’m using Python 3.12 to match the new ROCm 7.1.0 wheels and compiling the Triton-enabled Flash Attention from source. 

To keep things organized, I’ve cloned a parallel instance: `ComfyUI_Clean`. It shares the same massive model weights (to save disk space), but it’s a pure, unmodified codebase. It’s our baseline. If something breaks in my patched version, we can run it in the "Clean" room to see if it's a hardware failure or a software bug.

We’re fighting the silicon, but we’re winning. The 13B model is running. The 5B model is fast. The machine is finally starting to behave.

**Current Status:** 
- **RDNA 4 Stability:** High (via Numpy Laundering & SDPA patches).
- **Performance:** Optimized for 5B/13B hybrid.
- **Next Step:** Stress test the new `venv_rocm_fresh` with the full Wan 2.2 suite.
