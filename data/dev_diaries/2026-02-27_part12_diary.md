# Dev Diary: 2026-02-27 (Part 12)

The transition from Windows to Ubuntu earlier today was a massive undertaking, but it was necessary. I needed the raw control that a Linux environment provides for ROCm and the custom kernel management. However, the "Soul" of the project—the intelligence—is currently caught in a brutal tug-of-war with the "System"—the hardware limits of my RX 9070 XT.

## The VRAM Wall and the Great Freeze

The biggest technical headache today was a recurring system freeze. After running some initial benchmarks, I realized that the `llm_interface.py` was hardcoded with a `keep_alive: -1` parameter. This was a disaster. It meant that while I was testing the `RECEPTIONIST` model, the `ENGINEER` model (DeepSeek-R1 14B) was also trying to squat in VRAM. 

When the models collided, the ROCm driver essentially choked. The system wouldn't just slow down; it would hard freeze. I had to rewrite the `llm_interface.py` to implement a dynamic `keep_alive` strategy. I set the `RECEPTIONIST` to stay resident (always ready), but forced the heavy-hitters like `ENGINEER` and `VISION` to unload after 5 minutes of inactivity.

To be safe, I implemented a global `MODEL_LOCK`. This ensures that we aren't trying to swap models or run concurrent queries that would cause a race condition in the VRAM allocation. It's a bottleneck, but for local-first AI, stability is more important than raw parallel throughput right now.

## The Benchmark: A Small Victory

I ran the `ollama_resident_benchmark.py` to see if the new "VRAM Tetris" logic worked. The results were actually quite a relief. The system successfully transitioned between the resident receptionist and the heavy engineer models without hitting the 16GB ceiling. 

More importantly, I tested the Prompt Prefix Caching. The benchmark showed a **92.2% reduction** in Time To First Token (TTFT) for "hot" queries compared to cold ones. This is huge. It means the "Soul" is becoming responsive, even if the "System" is still tight on memory.

## The vLLM Ghost in the Machine

There was a heated debate in the logs regarding vLLM. Gemini Flash tried to compile PyTorch to get vLLM running, but it hit a wall. The user (me) was skeptical of the Flash model's assessment, and honestly, I'm inclined to trust the Pro model's caution. Trying to force-feed vLLM into this specific RDNA 4 setup (gfx1201) via a broken PyTorch build feels like chasing a ghost. We're sticking to Ollama for now, as it's proving stable enough for the current phase.
