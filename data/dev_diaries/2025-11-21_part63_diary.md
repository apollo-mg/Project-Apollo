# Dev Diary: Part 63 — The Ghost in the Quantizer

**Date:** 2025-11-21  
**Session:** Late night, caffeine-fueled descent into ROCm's darkest corridors  
**Target:** AMD Radeon RX 9070 XT (16GB), gfx1201, RDNA4  
**Antagonist:** `HIP error: an illegal memory access was encountered`

---

## The Return of the Villain

It came back. Of course it came back.

The `illegal memory access` error that has haunted this project since week three reappeared tonight, but with a cruel twist: it had moved. My previous patch—forcing contiguity on the `d` (scale) tensor in `dequantize_blocks_Q4_K`—had been a victory. For a moment, I thought I'd won.

How naive.

The new stack trace pointed to the same function, same file, but this time at the *return statement*:

```python
return (d * qs - dm).reshape((n_blocks, QK_K))
```

The inputs were contiguous. The scales were contiguous. But `qs`—the dequantized weights extracted from the packed GGUF representation through a series of bitwise shifts and masks—was not. It was a *view*, a strided phantom of the original tensor, and ROCm does not forgive views the way CUDA pretends to.

---

## The Epiphhanies Between 21:27 and 21:29

**21:27:55** — The crash lands. Stack trace confirms: `dequantize_blocks_Q4_K`, line containing the reshape.

My mind races through the possibilities:
- Is it the reshape itself? Unlikely—PyTorch is paranoid about those.
- Is it the element-wise multiplication `d * qs`? **Yes.**

The bitwise operations that extract the quantized weights:

```python
shift_tensor = get_shift_tensor(...)
qs = qs.reshape((n_blocks, -1, 1, 32)) >> shift_tensor
qs = (qs & 0x0F).reshape((n_blocks, -1, 32))
```

These produce views. Views are cheap. Views are elegant. Views are the enemy of ROCm.

**21:29:05** — The patch lands. I force `.clone()` on `qs` before the final arithmetic:

```python
qs = qs.clone()  # The humility tax
return (d * qs - dm).reshape((n_blocks, QK_K))
```

Victory? Not yet.

---

## The Second Death (21:30:28)

The workflow proceeds further. The dequantization completes. The model begins its forward pass through the Wan2.1 transformer blocks...

And then it dies again.

This time, the error is not in my code. It's in `comfy/model_management.py:1082`, in the function `cast_to`:

```python
r.copy_(weight, non_blocking=non_blocking)
```

A device transfer. A `copy_` operation. The most basic, fundamental operation in GPU computing.

And it failed.

The log shows the model loaded "partially":
- **9252.23 MB usable**, **9251.19 MB loaded**, **84.43 MB offloaded**

Mixed quantization across the model:
- F16: 694 blocks
- Q4_K: 280 blocks  
- Q6_K: 120 blocks
- F32: 1 block

The error suggests the dequantized tensor has a memory layout that ROCm accepts for computation but rejects for transfer. Perhaps a padding issue. Perhaps an alignment problem that only manifests when the kernel tries to copy to a different memory domain.

## The Philosophical Friction

This is the war I fight every night.

**The Soul** wants sovereignty: local models, no API calls, no telemetry, no "Sorry, you've exceeded your monthly credits." The Wan2.1 video model running on bare metal, generating frames from pure mathematical potential.

**The System** is the silicon reality: 16GB of VRAM that vanishes when you actually try to use it, quantization formats designed for CPU inference being shoehorned onto RDNA4 compute units, ROCm drivers that treat memory contiguity as a suggestion rather than a requirement.

The AMD Radeon RX 9070 XT is a beautiful card. On paper, it's everything I wanted. In practice, it's a puzzle where some pieces are missing and others are slightly the wrong shape.

---

## What I Learned Tonight

1. **Contiguity is not transitive.** Making your inputs contiguous does not make your outputs contiguous. Every bitwise operation, every reshape, every stride manipulation creates new opportunities for the GPU to quietly decide your memory is not its memory.

2. **The error moved, which means I'm closer.** The first crash was in dequantization. The second crash is in device transfer. The third will be... somewhere else, probably. But the progression is real.

3. **ROCm's HIP layer is not CUDA.** The errors are similar. The stack traces are similar. But the tolerances, the edge cases, the momentary lapses in validation—these are different. I've been treating ROCm as "CUDA with different branding." That was wrong.

4. **The Wan model's mixed quantization is a feature, not a bug.** 694 blocks in F16, 280 in Q4_K, 120 in Q6_K—this is a model that expects to live in constrained memory. The question is whether I can make it live in *my* constrained memory.

---

## Tomorrow's Battle

The `copy_` failure in `model_management.py` suggests the issue has moved upstream—from my dequantization patches to ComfyUI's core memory management. Either:
- The tensor has metadata (stride, storage order) that confuses ROCm's copy kernels
- There's a race condition in the non-blocking transfer
- The RDNA4 architecture has a quirk with the specific tensor shapes involved

I may need to:
- Force `.contiguous()` on the dequantized weights before returning them
- Disable non-blocking transfers temporarily to isolate the issue
- Add `AMD_SERIALIZE_KERNEL=3` and compile with `TORCH_USE_HIP_DSA` to get actual device-side assertions

The Sovereign Engine will run locally. It will run on AMD. It will run on *my* terms.

Even if I have to rewrite the GGUF loader in C++ to make it happen.
