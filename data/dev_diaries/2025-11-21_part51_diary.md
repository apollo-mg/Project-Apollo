# Project Apollo Dev Diary: Part 51
## The Night the Silicon Said "No"

### 2025-11-21 | 20:21 UTC | The RX 9070 XT Rebellion

---

I don't build things that don't break. If I did, I wouldn't be building anything worth building.

Tonight was no exception.

The stack trace is screaming at me from the terminal: `torch.AcceleratorError: HIP error: an illegal memory access was encountered`. But stack traces don't tell you the story. They just document the corpse.

---

## The Setup That Should Have Worked

I'm running the Wan2.1-T2V-14B model in Q4_K_M quantization on a fresh AMD Radeon RX 9070 XT—16GB of VRAM, gfx1201 architecture, ROCm 7.1.0 bleeding edge. On paper, this is a triumph.

The DisTorch2 virtualization layer is doing its dance:
- **cuda:0**: receiving +10GB virtual allocation (15.92 → 25.92GB)
- **cpu**: donating -10GB (31.26 → 21.26GB)

It's a memory shuffling scheme I'm genuinely proud of. The logs show the choreography:
```
Object   Role   Original(GB) Total(GB)  Virt(GB)
cuda:0   recip      15.92GB   25.92GB  +10.00GB
cpu      donor      31.26GB   21.26GB  -10.00GB
```

But then we hit the wall.

---

## The Autopsy

The crash buries itself deep in the GGUF dequantization pipeline:

```
cast_bias_weight → get_weight → dequantize_tensor → 
dequantize_blocks_Q4_K → get_scale_min
```

And the smoking gun:
```python
sc = torch.empty((n_blocks, 1, 8), dtype=torch.uint8, device=scales.device)
```

Line 173 of `dequant.py`. A simple enough allocation. Except it's not simple when you're dealing with Q4_K blocks on RDNA4 silicon.

**The suspicion**: The `n_blocks` calculation is overflowing or misaligned. The tensor allocation succeeds in PyTorch's eyes, but HIP catches the illegal access when the kernel actually tries to touch that memory.

## Lessons From the Fire

### 1. Q4_K on RDNA4 is not Q4_K on NVIDIA

The dequantization kernels are hand-tuned for specific architectures. The `get_scale_min` function assumes certain memory access patterns that HIP may not honor the same way CUDA does. 

**Next attempt**: Add defensive bounds checking before the `torch.empty` call. Log `n_blocks` and verify the calculation:
```python
expected_blocks = (input_size + block_size - 1) // block_size
if n_blocks > expected_blocks * 1.1:  # 10% tolerance
    raise RuntimeError(f"Block count overflow: {n_blocks} > {expected_blocks}")
```

### 2. DisTorch2 is working too well

The virtual VRAM shuffling completed successfully. The crash happened *after* the model loaded, during actual computation. That means the memory management is clever—but it may be too clever. 

The CPU donor is giving up memory that the GPU then can't actually use because... something in the transfer chain is broken.

**Hypothesis**: The virtual→physical address translation is losing information during the GGUF dequant step.

### 3. The ComfyUI-GGUF node is a black box we're poking with sticks

```
File "/home/mark/gemini/ai/ComfyUI/custom_nodes/ComfyUI-GGUF/dequant.py", line 241
```

That's not my code. That's not even AMD's code. That's a community patch running on bleeding-edge hardware with a bleeding-edge ROCm stack. The probability of *any* one of those four things being stable is roughly 1/256.

We're not building infrastructure. We're building infrastructure on a trampoline while someone else is adjusting the springs.

---

## The Path Forward (For Tomorrow)

1. **Enable HIP serialization** and capture the actual kernel that's failing. The async error reporting is lying to us.

2. **Drop to FP16 weights** temporarily. If Q4_K is the problem, FP16 proves the pipeline works. Then we bisect.

3. **Test without DisTorch2**. Load the model straight to GPU. If it works, the virtualization layer is corrupting something.

4. **The nuclear option**: `TORCH_USE_HIP_DSA` at compile time. Device-side assertions will slow everything to a crawl, but they'll tell us exactly which byte we tried to touch that didn't belong to us.
