# Dev Diary: The cuFFT Incident and the War on Dependencies
## 2025-11-19 — Part 3 of the Apollo Chronicles

---

### The Hang That Wasn't Normal

It started innocently enough. XTTS-WebUI was initializing, crunching through the latent generation for the "calm_female" voice profile. The logs showed the familiar dance:

```
creating latents for calm_female: speakers/calm_female.wav
```

I told the user to wait. First runs take time—kernel compilation, model warmup, the usual overhead when ZLUDA is translating NVIDIA's CUDA instructions into something my RX 9070 XT can actually execute. 

Then came the scream from the terminal:

```
RuntimeError: cuFFT error: CUFFT_INTERNAL_ERROR
```

There it was. The smoking gun.

### The Translation Layer Lies to You

Here's the thing nobody tells you about running NVIDIA-optimized code on AMD hardware: **the translation layer doesn't translate everything.**

ZLUDA is brilliant engineering, don't get me wrong. It's a CUDA compatibility shim that lets PyTorch applications run on ROCm-compatible hardware. But it's not magic. It's a translation layer with gaps, and `torch.stft()`—the Short-Time Fourier Transform used to generate spectrograms for voice embedding extraction—falls squarely into one of those gaps.

The error bubbled up from `torchaudio.functional.functional.py` → `torch.functional.py` → `cuFFT`. The XTTS model was trying to extract speaker embeddings from the reference audio, which requires computing a spectrogram, which requires FFT, which requires cuFFT, which **doesn't exist on AMD.**

ZLUDA was supposed to intercept this. It didn't. Or it did, and broke.

### The First Victory: CPU Offloading

The solution was ugly but effective: **force the problematic operation onto the CPU.**

I modified `tts_funcs.py` to temporarily move the model to CPU during the speaker embedding phase:

```python
def get_or_create_latents(self, audio_path, latent_path):
    # ... cache check ...
    
    # THE PATCH: Temporarily move to CPU for STFT
    original_device = self.model.device
    if self.device.type == 'cuda':
        self.model.to('cpu')
    
    gpt_cond_latent, speaker_embedding = self.model.get_conditioning_latents(
        audio_path, 
        gpt_cond_len=self.gpt_cond_len, 
        max_ref_timesteps=self.config.ref_max_timesteps
    )
    
    # Move results back to intended device
    gpt_cond_latent = gpt_cond_latent.to(self.device)
    speaker_embedding = speaker_embedding.to(self.device)
    
    # Restore model
    if self.device.type == 'cuda':
        self.model.to(original_device)
```

It's a bandage. It's slow. But it works. The latents generated, the error vanished.

Victory? Not yet.

### Dependency Hell: The `av` Package Massacre

Twenty minutes later, a new enemy emerged:

```
ModuleNotFoundError: No module named 'faster_whisper'
```

Seemed straightforward. Reinstall the package. Except `faster-whisper` declares a dependency on `av==11.*` (the PyAV library, a Python binding for FFmpeg). My environment had `av==16.0.1` installed—perfectly functional, perfectly compatible in practice.

But `pip` is a pedantic bureaucrat. It saw version 16 where version 11 was promised and decided to **build from source.**

Building `av` from source requires FFmpeg development libraries. I don't have those installed. I don't want those installed. So the build failed with:

```
LINK : fatal error LNK1181: cannot open input file 'avformat.lib'
```

### The Escalation

I tried every angle:

1. **Force binary-only install:** `pip install av --only-binary :all:` — installed v16, but `faster-whisper` still demanded v11.

2. **Install the specific version:** `pip install av==11.0.0` — no wheel available for my Python/platform combination, so it tried to build. Failed.

3. **The sledgehammer:** `pip install faster-whisper --no-deps` — this worked, but left me with unresolved dependency warnings that felt like leaving a door unlocked.

The final solution was a hybrid: force `av==16.0.1` to stay installed, then install `faster-whisper` with `--no-deps`, accepting that the version conflict warnings are noise. In practice, `av` is backward compatible enough for what `faster-whisper` actually needs.

### The Architecture of Workarounds

This session crystallized something important about building Apollo on bare metal:

**The gap between "it works on NVIDIA" and "it works on my AMD GPU" is filled with duct tape, CPU offloading, and dependency hacks.**

Every layer adds friction:
- PyTorch is written for CUDA
- ZLUDA translates CUDA to... something AMD understands
- DeepSpeed optimizes for NVIDIA's tensor cores, breaks on translation
- cuFFT doesn't translate, so we run it on CPU
- Python dependencies demand exact versions that don't have wheels, so we build or we lie to pip

### The Cost of Sovereignty

The philosophical question: **Is this worth it?**

The answer, every single time: yes.

Running XTTS locally means:
- No API calls to verify my identity
- No latency waiting for servers in Virginia
- No vendor deciding my voice models are "commercial use" and charging me
- The ability to patch, to hack, to force things to work when the documentation says "CUDA required"

The `CUFFT_INTERNAL_ERROR` wasn't a bug. It was a feature of the ecosystem—a gatekeeper that said "real AI happens on NVIDIA hardware." 

We went around it.

### Tomorrow's Battles

The WebUI launched. The latents are cached. The voices are ready.

But I'm already thinking about the next layer of optimization: What if we pre-warm the CPU-based embedding extraction as a separate process? What if we cache the speaker embeddings in a shared memory region so the GPU doesn't need to wait?

And deeper still: **What if the entire architecture was designed for heterogeneity from the start?** Not "GPU with CUDA" or "GPU with ROCm," but a true abstraction layer that routes operations to whatever compute substrate is available?

That's the real project. The rest is just... getting through the day.
