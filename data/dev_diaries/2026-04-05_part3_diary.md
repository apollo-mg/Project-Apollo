### The `MUL_MAT_ID` Nightmare

Overnight, the `llama-server` didn't just crash; it threw a `MUL_MAT_ID failed` error followed by a `ROCm error: unspecified launch failure`.

The log was brutal:
`slot update_slots: ... n_tokens = 1416, batch.n_tokens = 392 ...`

**The Diagnosis:**
The MoE kernel on ROCm is notoriously fragile when dealing with **fractional micro-batches**.
My `start_architect.sh` script was set to `-ub 64` (micro-batch size).
When the server hit the end of a prompt with `1416` tokens, it processed `512` tokens, then `512` tokens, and was left with a remainder of `392`.
`392` is not divisible by `64`. It leaves a fractional remainder (`0.125`).

The GPU's Mixture-of-Experts routing logic panicked. It tried to split that fractional remainder across the expert layers, the matrix math failed, and the kernel dumped core.

### The "Nuclear" Fix

I had to make a hard call. To fix the batch remainder bug, I couldn't just tweak a number. I had to bypass the splitting logic entirely.

I updated `start_architect.sh` to set the micro-batch size equal to the total batch size:
`-b 512 -ub 512`

By forcing `-ub 512`, I told `llama.cpp` to stop splitting the prompt. It now shoves whatever tokens it has (whether it's 512 or 392) directly to the GPU in a single pass. It's ugly, but it works. The fractional remainder is ignored, the kernel panic is gone, and the server stays alive.

**The Cost:**
We lost a bit of theoretical peak efficiency. The prompt processing is slower now because we aren't chunking the input for the memory cache as aggressively. But stability is the price of admission for local inference on RDNA 4.

---

### The `turbo3` Sacrifice

I also had to make a trade-off. The official `llama.cpp` `b8664` branch (which I pulled for the Gemma 4 tokenizer fixes) **does not include** TheTom's `turbo3` custom cache compression.

By upgrading to the official branch, we lost the `turbo3` cache type (`-ctv turbo3`). The server immediately rejected it with: `Unsupported cache type: turbo3`.

I reverted to standard asymmetric caching:
`-ctk q8_0 -ctv q4_0`

This is the next best thing. It uses high precision for Keys (`q8_0`) and aggressive compression for Values (`q4_0`). It frees up enough VRAM to keep our massive **65,536 context window** intact on the 16GB 9070 XT, even without the `turbo3` magic.

We are waiting for TheTom to merge his custom fork on top of the new `b8664` release. Until then, we run standard cache. It works.

### Architectural Epiphanies

While the GPU was crashing, I dug into the **Per-Layer Embeddings (PLE)** concept discussed in the local LLM community. The explanation for the Gemma 4 "E" series is sound: by using sparse embedding lookups at every layer instead of dense weight matrices, the model can store billions of parameters on slow disk/SSD and only stream the active vectors to VRAM.

It's a brilliant "cheat code" for local inference. It shifts the bottleneck from memory bandwidth (RAM/VRAM) to storage speed. This validates why the **Gemma 4 26B-A4B** is the perfect model for us. It's an MoE model with deep reasoning capabilities, and its architecture is designed to be efficient on constrained hardware.

The **Daydream** daemon even proposed a **"Memory-Mapping Shim"** to translate CDNA memory addresses to RDNA ones to fix the ROCm driver spoofing issues. It's a fascinating idea—essentially writing a ZLUDA-style interceptor for AMD—but it's unrelated to the `MUL_MAT_ID` crash. The crash was purely a math remainder bug, not a memory addressing bug.
