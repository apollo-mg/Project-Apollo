### The Failure

Forty-nine seconds. That's how long it took for the universe to remind me who's in charge.

```
!!! Exception during processing !!! HIP error: an illegal memory access was encountered
```

The stack trace is poetry in its brutality. Following the breadcrumbs:

1. `KSampler` → `sample_dpmpp_2m` → `model(x, sigmas[i] * s_in)`
2. Down through the Wan model layers...
3. Into the cross-attention block at line 109 of `model.py`
4. Into the GGUF operations at `/custom_nodes/ComfyUI-GGUF/ops.py`
5. And finally, line 255, where dreams go to die:

```python
out += bias
```

That's it. That's the killer. A simple bias addition in `forward_ggml_cast_weights` triggered a HIP illegal memory access.

---

### The Autopsy

Here's what I think happened—and I'm only partially sure because ROCm's asynchronous error reporting is a philosophical stance at this point:

**The Quantization Trap**

The Q4_K_M quantization scheme packs weights into 4-bit blocks with per-block scaling factors. When ComfyUI-GGUF's custom ops unpack these for computation, they're doing in-place operations that assume perfect alignment. 

The bias tensor—stored in full precision, presumably—needs to be broadcast and added. But something in the shape calculation, the dtype casting, or the memory layout went wrong. On CUDA, this might have been caught. On ROCm with RDNA4's memory controller, it became a segfault masquerading as a HIP error.

**The Memory Fragmentation Theory**

Look at the DisTorch2 logs:

```
cuda:0   recip      15.92GB   25.92GB  +10.00GB
cpu      donor      31.26GB   21.26GB  -10.00GB
```

We're virtualizing across devices. The CLIP model sat at 6.4GB loaded, the Wan2.1 model at 9.7GB. That's 16.1GB of model weights competing with latent space, intermediate activations, and the attention cache for 17 frames at once.

The VRAM wasn't exhausted—the logs showed ~17GB free at startup—but fragmentation is a silent killer. The bias tensor might have been allocated at an address that wrapped, or the in-place addition tried to write beyond a buffer boundary that CUDA's lenient driver would have ignored.

**The AMD Serial Kernel Suggestion**

The error helpfully suggested: `AMD_SERIALIZE_KERNEL=3`

This would force synchronous kernel execution, trading parallelism for debuggability. It's the computational equivalent of holding your breath while walking through a minefield. I haven't run it yet. I'm too afraid of what I'll find.

---

### The Architectural Epiphany

Here's what this crash taught me about the Sovereign Engine's future:

**1. Quantization Is Not a Silver Bullet**

GGUF quantization saves VRAM, yes. But it introduces a new class of failure modes—custom kernel bugs, dtype mismatches, alignment issues that never existed with FP16 tensors. The local-first dream requires robustness across precision levels, not just support for them.

**2. The Multi-Agent Ecosystem Needs Graceful Degradation**

When one node in the agent graph fails with a HIP error, the whole system halts. We need:
- Per-node memory budgets that prevent cascade failures
- Fallback paths (CPU execution, lower precision, reduced batch size)
- Proper error isolation so one crashed sampler doesn't kill the conversation

**3. ROCm Is Not CUDA, and Pretending It Is Will Humble You**

The `cudnn.enabled = False` flag in the logs is a prayer, not a solution. AMD's HIP layer adds translation overhead, different memory semantics, and quirks that only surface under load. The Sovereign Engine needs to be hardware-aware at its core, not just hardware-compatible.

---

### The Path Forward

Three experiments for tomorrow:

1. **Synchronous Debugging:** Run with `AMD_SERIALIZE_KERNEL=3` and `TORCH_USE_HIP_DSA` to catch the exact instruction that trips.

2. **Batch Size Reduction:** Try 4 frames instead of 17. If it works, the issue is memory pressure, not the quantization itself.

3. **FP16 Baseline:** Load the full-precision Wan2.1 model and confirm the crash is GGUF-specific. If it survives, we know where to focus.
