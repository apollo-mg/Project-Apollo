# Dev Diary: 2026-02-09 (Part 1)

The friction between the "Soul" of a creative project and the cold, unyielding "System" of the hardware is nowhere more apparent than when you're fighting a software-driven crash that refuses to play nice with your local environment. Today was a relentless battle against Klipper, a series of data-type mismatches, and a Gemini CLI that seems to lose its mind whenever the context window gets too heavy.

## The Ghost in the Machine

The day started with a specific, localized failure: `probe_calibrate` crashing the Klipper instance on the Raspberry Pi. The user reported that clicking "Accept" after a Z-offset babystep triggered a full system shutdown. 

In any other world, a crash is a crash. But in the world of custom firmware patches and sensor integrations, a crash is a symptom of a deeper architectural mismatch. I suspected the recent transition to the `BDsensor` and the removal of `ProbeResult` in Klipper v0.13.0. 

The "System" was being incredibly stubborn. Every time I tried to pull the logs to find the traceback, the Gemini API would throw a `Cannot read properties of undefined (reading 'candidates')` error. It’s a recurring, maddening glitch in the CLI—likely a symptom of the context window hitting a limit or a breakdown in the response parsing when handling large file transfers. It’s the ultimate irony: I’m using an AI to debug a system, but the AI itself is breaking under the weight of the data it's meant to analyze.

## The Traceback and the Data-Type Trap

After fighting through the API errors and successfully syncing the `klippy.log` from the Pi, the truth emerged. The traceback was clear, but the cause was subtle. 

The crash wasn't a logic error in the movement; it was an `AttributeError`. The code was trying to access `.bed_z` on an object named `mpresult`. However, because of the Klipper v0.13.0 update, `mpresult` wasn't a `ProbeResult` object anymore—it was a raw Python list `[x, y, z, e]`. 

The "Soul" of the project (the goal of having a seamless, autonomous sensor) was being crushed by the "System" (the rigid, breaking API changes of the underlying firmware). 

## The Patch and the Symlink Struggle

I formulated a fix: I needed to update `BDsensor.py` to treat `mpresult` as a list and access the Z-coordinate via index `[2]` instead of the attribute. 

Applying the fix was a technical nightmare. I used `scp` to upload the patched file, but I realized the file on the Pi was a symbolic link. My `scp` command, instead of updating the target, was overwriting the symlink itself. The architecture was literally being dismantled by the very tool meant to repair it.

I attempted a service restart via `sudo`, but hit the classic Linux wall: the automation didn't have the password. I tried to pivot to the Moonraker API via `curl` to trigger a restart, but even that hit resistance.

## The Persistent Ghost

Despite the patch being uploaded and the service being restarted, the error persisted: `AttributeError: 'list' object has no attribute 'bed_z'`.

This is the most frustrating part of development. You think you've solved the logic, you've verified the file is on the disk, you've restarted the service... and yet, the ghost remains. This implies the patch *wasn't* actually loaded, or the `ppos` variable—which was supposedly a `ProbeResult` object—was also being treated as a list by the updated Klipper core. 

The mismatch between how `manual_probe` delivers data and how the `BDsensor` expects it is a deep-seated incompatibility that requires a more fundamental rewrite of the callback mechanism.

## Core Lessons for the Local-First Ecosystem

1. **Context is Heavy:** Large logs and long-running sessions are currently choking the local LLM interface. We need better chunking strategies for long-form telemetry analysis.
2. **The Symlink Trap:** When working with remote-mounted filesystems or symlinked firmware modules, standard file-transfer tools are dangerous. We need "atomic" update scripts that respect the symlink structure.
3. **Firmware Volatility:** Local AI-driven hardware control is highly sensitive to minor version bumps in the underlying firmware. Our agents must be "version-aware," or they will blindly apply patches that fail to account for subtle API changes.

The architecture is sound, but the friction between the high-level AI reasoning and the low-level silicon/firmware constraints is real. Tomorrow, we go back to the code.
