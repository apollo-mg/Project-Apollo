# Dev Diary: When Silicon Betrays Vision

**Date:** November 21, 2025  
**Session:** Part 37 of the Ascent  
**Hardware Under Siege:** AMD Radeon RX 9070 XT (16GB VRAM, gfx1201)

---

## The Crash That Taught Me Everything

It happened at step zero.

I was generating video—seventeen frames at once, a cyberpunk cityscape bleeding neon onto wet pavement, the kind of imagery that makes you forget you're wrestling with silicon—and then the HIP kernel simply refused to obey.

> `HIP error: an illegal memory access was encountered`

The stack trace led me straight to `comfy/ops.py:300`, to a single, innocent-looking line:

```python
out = torch.empty_like(input)
```

*Empty like input.* How hard could that be?

Apparently, infinitely hard when you're asking a 14-billion-parameter quantized model to birth seventeen frames simultaneously on RDNA4 architecture that AMD still considers "experimental" for everything that matters.

---

## The Anatomy of a Betrayal

Let me walk you through the death scene:

**The Victim:** Wan2.1-T2V-14B-Q4_K_M.gguf, quantized to Q4_K/Q6_K/F32, loaded into 9783 MB of my precious 16 GB VRAM.

**The Weapon:** A batch size of 17 frames at 832×480 resolution.

**The Murderer:** Memory fragmentation in the FFN layer, specifically when `forward_comfy_cast_weights` tried to allocate intermediate tensors that ROCm decided were "illegal."

The logs don't lie:
```
Using scaled fp8: fp8 matrix mult: False, scale input: False
gguf qtypes: F32 (695), Q4_K (280), Q6_K (120)
```

I had done everything "right." Quantization? Check. FP8 scaling enabled? Check. Even the GGUF loader was explicitly disabling `torch.compile` for RDNA4 stability. And yet—the kernel screamed and died.

---

## The Soul vs. System Question

Here's what keeps me up at night:

The *Soul* of Project Apollo demands creative freedom without constraints. You should be able to prompt "a dragon eating a cathedral" and not care about batch sizes, VRAM fragmentation, or whether ROCm 7.1 decided your particular tensor shape is "illegal."

The *System*—cold, unfeeling silicon—cares about nothing but page tables and cache lines.

I'm building a multi-agent ecosystem meant to operate autonomously on bare metal, and yet I'm still debugging why `torch.empty_like()` explodes when called from a transformer's feed-forward network.

**This is the gap I'm trying to close.**

## The MultiGPU Gambit

At 19:04, I found myself staring at a GitHub repository: `pollockjj/ComfyUI-MultiGPU`.

The irony wasn't lost on me. I have one GPU. A magnificent, bleeding-edge, *single* GPU. But the node's promise wasn't about parallelism—it was about *memory orchestration*. Layer splitting. Device placement. The kind of surgical control that `accelerate` refuses to give you without a fight.

Even if I never add a second card, understanding how to partition a model across memory boundaries—GPU, CPU, even disk—might be the key to surviving models that refuse to fit.

The question I'm asking myself: *Can I use multi-GPU strategies on a single-GPU system to achieve the same memory flexibility?*

The answer, I suspect, is yes. But at what cost in complexity?

---

## Lessons Carved in Blood (and Stack Traces)

1. **Batch size is a lie.** The "batch size of 17" I thoughtlessly entered wasn't a performance knob—it was a memory bomb waiting to detonate. Video generation at this scale demands batch size 1, period. The rest is hubris.

2. **ROCm is not CUDA.** The HIP error wasn't a bug in my workflow; it was a reminder that AMD's software stack still has jagged edges where NVIDIA's would have silently worked. `AMD_SERIALIZE_KERNEL=3` is now in my startup script. So is `TORCH_USE_HIP_DSA` for device-side assertions.

3. **Quantization isn't a silver bullet.** GGUF quantization saved me from OOM errors at load time, but it doesn't protect you from intermediate tensor explosion during inference. The model fits; the computation does not.

4. **The crash site matters.** The error occurred in the FFN layer, during weight casting. This tells me the fragmentation happened *mid-computation*, not at allocation. Understanding *when* memory dies is as important as understanding *that* it dies.

---

## What Changes Tomorrow

I'm implementing a new memory strategy for the Sovereign Engine:

- **Defensive batching:** All video generation defaults to batch_size=1, with runtime detection that scales up conservatively.
- **Multi-GPU node integration:** Even with one card, the layer-splitting logic might save us from future fragmentation.
- **ROCm-specific error handling:** Catching HIP errors before they cascade and providing human-readable diagnostics.
- **Memory profiling hooks:** I need to know *exactly* where tensors are being allocated before the crash, not after.

---

## A Note on Persistence

The transcript shows I explored the MultiGPU repository at 19:04 but never committed to it. That hesitation is honest.

Every new dependency is a future crash vector. Every new node is a potential incompatibility. But every solved memory crash is a step toward the vision: a local-first, autonomous agent ecosystem that doesn't beg for permission from cloud APIs or silicon vendors.

I choose friction over dependency. Always.
