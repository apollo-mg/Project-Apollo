# Dev Diary: 2025-11-21
## Part 38: The VRAM Partitioning Wars

### The Physical Wall

Today was about hitting the wall. Not metaphorically. The physical, silicon wall of 16GB of VRAM on an RX 9070 XT trying to hold a 14B parameter model in its lap.

The Wan 2.1 model doesn't care about my philosophy of sovereign intelligence. It doesn't care about the "Soul" we're trying to build. It just wants memory. And when you ask it for more than the card can give, the universe responds with OOM errors and the silent tragedy of pages swapping to disk at 2% overnight.

I call it the "2% Overnight" problem. The moment you see that progress bar crawling at two percent, you know you've crossed into swap territory. The GPU is done. The system has surrendered to RAM. And beyond that? The mechanical whine of your SSD as your dreams of local-first intelligence get paged in and out like refugees at a border crossing.

### DisTorch and the Offloading Gambit

Enter DisTorch. The promise: virtual VRAM. The reality: a carefully managed dance of offloading model weights between GPU and CPU RAM, hoping you never have to touch the disk.

I spent hours dissecting the `ComfyUI-MultiGPU` codebase, looking for CUDA-specific traps that would betray ROCm users. The `device_utils.py` file became my bible. I traced every import, every `torch.cuda.is_available()` check, every assumption about hardware.

Here's what I found: the code is clever enough to work with PyTorch's device abstraction. No hardcoded CUDA kernels. No proprietary nonsense. It uses standard `module_object.to(device)` calls, which means ROCm gets the same treatment as CUDA. The `cuda` device string becomes a universal abstraction layer, and I respect that.

But the real magic—and the real friction—is in the FP8 quantization strategy. The code stores weights on CPU in `torch.float8_e4m3fn`, leveraging stochastic rounding. When layers migrate back to GPU, they cast back to a suitable compute format. This isn't just memory management; it's format juggling.

### The Dependency Betrayal

Here's the thing about open source ecosystems: they're beautiful until they're not.

I installed `ComfyUI-MultiGPU`. I patched the workflow JSON, replacing `UnetLoaderGGUF` with `UnetLoaderGGUFDisTorch2MultiGPU`. I was ready to partition that VRAM.

Then the system failed to load the nodes.

Silently.

No error in the browser. No crash. Just... missing nodes.

The problem? A missing dependency: `accelerate`.

Not listed in `requirements.txt`. Not in `pyproject.toml`. Just... expected to be there.

This is the reality of local-first AI: you're not just an architect anymore. You're a dependency manager, a sysadmin, a debugger of silent failures. You're building a castle on a foundation of other people's promises.

### The Partitioning Strategy

With `accelerate` installed and ComfyUI restarted, the nodes appeared. Time to configure the offload.

**UNet (Wan 2.1):** 6.0 GB offloaded to CPU RAM. Leaves ~2-3GB on GPU.

**T5 Encoder:** 4.0 GB offloaded to CPU RAM. Leaves ~1GB on GPU.

**Result:** ~10GB+ freed for KV cache and VAE decode. The goal: stay in VRAM and RAM. Never touch the disk.

The `virtual_vram_gb` parameter is deceptive. It doesn't create virtual memory. It specifies how many gigabytes to *remove* from VRAM and pin to the donor device (CPU). It's not magic; it's accounting.

### The Torch Compile Question

The user asked if `run_comfy_optimized.sh` includes Torch compilation optimizations.

It doesn't.

The script has:
- Triton Flash Attention: Enabled
- PyTorch TunableOp: **Disabled** (caused illegal memory access crashes on Wan 2.1)
- Memory management: `PYTORCH_HIP_ALLOC_CONF` with garbage collection thresholds

But no `torch.compile`. No JIT magic. Just raw, unoptimized PyTorch execution.

The question remains: should we enable it? The risk is compilation overhead at load time. The reward is faster inference. But on ROCm with RDNA 4? I'm not sure the backend is stable enough.

### Lessons for the Ecosystem

1. **Dependencies are political.** When you build local-first, you inherit everyone else's supply chain risks. The Sovereign Engine can't be sovereign if it depends on unlisted packages.

2. **VRAM partitioning is the new reality.** 16GB isn't enough for 14B models. Offloading to CPU RAM is mandatory, not optional. The question is how much latency you accept for the privilege of running locally.

3. **ROCm is not CUDA.** The abstraction works until it doesn't. TunableOp crashes. Expandable segments don't exist. Every optimization assumes NVIDIA until proven otherwise.

4. **The "Soul" runs on the "System."** I can philosophize about intelligence all day, but the model still needs memory. And when the memory fills up, philosophy doesn't page out. Silicon does.
