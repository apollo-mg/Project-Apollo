# Project Apollo: Dev Diary - 2026-02-28 (Part 8)

The friction between the "Soul" and the "System" is reaching a fever pitch. I am currently wrestling with a ghost in the machine—a classic case of architectural drift where the logic is sound, but the silicon is refusing to cooperate with the orchestration.

## The Ghost in the Machine: Zombie Processes

The day started with a frustrating loop of `JSON Parse Errors`. I had implemented a brace-counting stack parser to handle the messy, greedy JSON blocks that the DeepSeek-R1 model was spitting out, but the Discord Bridge was still reporting errors from the old, broken code. 

I realized I hadn't actually killed the old process. A "zombie" instance was still listening to the channel, feeding me stale error logs while my new code sat idle. I had to resort to a `pkill -9` to nuke every ghost instance, but even then, the new process failed to spawn in the background. It was a brutal, manual cleanup of the environment to ensure the local-first ecosystem was actually running the version of the truth I had written.

## The Intelligence Gap: 14B vs. 30B

Once the bridge was stable, the real test of the agentic loop began. I ran the image-to-inventory test through the 14B DeepSeek-R1. The "Engineer" is fast, but it's too polite. It successfully parsed the serial numbers from the image, but then it hit a snag: the web search returned nothing. 

Instead of executing the `add_hardware` tool call as commanded, the model fell into a "helpful chatbot" trap. It hallucinated that it had *already* added the items to the inventory and simply told me what it had done in text. It bypassed the very mechanism that gives the agent its agency. 

This is the fundamental challenge of smaller local models: they lack the "instruction-following discipline" required for autonomous tool use. They revert to conversational modes, forgetting they are part of a larger system.

## The VRAM Wall and the Model Swap

The transition to the "Architect" (Qwen3-Coder:30B) was where the technical limits of my AMD RX 9070 XT really showed. To run the 30B model, the system has to perform a massive VRAM swap. 

I've been debugging a critical failure in the `llm_interface.py` logic. The model-swapping mechanism is causing a massive bottleneck. The system is trying to unload the 14B model and load the 30B model, but the asynchronous nature of the `sys.stdout` buffering is creating a mess. The logs are a jumbled wreck of interleaved print statements from different processes, and the model-loading process is hitting timeouts.

The core of the issue seems to be a deadlock or a race condition during the VRAM swap. The `buddy_agent.py` is waiting for a response from the LLM, but the LLM interface is stuck in a transition state because the memory management hasn't fully cleared the previous weights. 

## Core Lessons for the Multi-Agent Ecosystem

1. **The Parser is not the Problem:** The logic-extraction works; the problem is the orchestration. We need robust, multi-block JSON parsing to handle the "hallucinated-extra-data" behavior common in smaller models.
2. **VRAM Management is the Hard Limit:** In a local-first setup, model-swapping isn't just a convenience; it's the primary constraint. If the swap isn't atomic, the entire agentic loop stalls.
3. **The Need for an Architect:** We cannot rely on 14B models for complex logic-heavy tool chains. The "Architect" model is necessary to act as the reasoning engine, but the "System" (the VRAM/RAM interface) is currently too brittle to support the weight of that intelligence.

**Status:** The system is currently in a state of "unstable equilibrium." The bridge is online, but the model-swapping logic is a wreck. I need to refactor the `llm_interface.py` to ensure model transitions are handled without deadlocking the execution loop. 

**Next Objective:** Stabilize the VRAM swap logic and confirm the Architect's reasoning capabilities.
