# Project Apollo: Dev Diary - 2026-02-19 (Part 6)

The friction between the "Soul" and the "System" reached a boiling point today. I spent hours trying to debug a vision-model hallucination, only to realize I wasn't fighting the AI's logic—I was fighting a hard-coded, cached whitelist in the Gemini CLI's security layer. 

It's a classic case of the silicon getting in the way of the intelligence.

## The Ghost in the Machine: The Whitelist Trap

The agent (DeepSeek-R1) correctly identified a "lampshade" in a webcam capture. I know for a fact there is no lampshade in my workspace. It’s a hallucination, likely born from poor lighting or the C922's sensor noise. I wanted to see the image to debug the vision model's failure, but the `read_file` tool kept throwing "is ignored" errors.

I tried everything to break through:
- Modifying `.gitignore` to whitelist the `tmp/` directory.
- Manually un-ignoring files via `!tmp/*.jpg`.
- Deleting the `.gitignore` entirely.
- Even renaming the `.jpg` to a `.py` extension to trick the parser.

Nothing worked. The CLI was holding onto a cached version of the file-ignore patterns from the start of the session. It was a rigid, unyielding wall of code that refused to acknowledge the new reality of the filesystem. It wasn't matter that the files existed; the "System" simply refused to see them.

## The Corruption: NTFS and the JPEG Overwrite

Then things got weird. I noticed `README.md` and `test_capture.py` had been overwritten. They weren't text files anymore; they were raw JPEG data. 

The culprit appears to be a misconfigured capture script (`webcam_capture.py`) combined with the volatility of the NTFS mount on my infrastructure drive (`/dev/nvme0n1p2`). Because of how the drive is mounted via FUSE, permissions are stuck at `777`, but the file integrity is clearly compromised. The "dirty bit" on that NTFS partition is a constant headache, and it seems the root partition hitting 100% capacity during the model migration may have triggered a cascading failure where the capture script dumped binary data into the wrong file descriptors.

## The Architecture vs. The Environment

We have a massive architectural discrepancy. The `commander.service` is looking for paths in `/home/mark/commander`, but a legacy script (`launch_fix.sh`) is trying to write to `/home/gemini/commander`. This user-context crossover is a nightmare for a multi-agent ecosystem. It’s not just about the models being smart; it's about the environment being stable enough for them to exist.

**Current State of Play:**
- **The System:** The NTFS mount is unstable, the root partition is near capacity, and the CLI's security layer is too rigid for real-time agentic file manipulation.
- **The Soul:** The vision model is capable of high-level identification (even if it's currently hallucinating furniture), but it's effectively "blind" because the file-access layer is broken.

**Next Steps:**
I need to get the `/settings` command to disable the `.geminiignore` filter. Once the "System" lets the "Soul" see the pixels, we can finally figure out if the model is seeing a lampshade or just a very weirdly shaped shadow. 

The path to local-first autonomy isn't just about better weights; it's about the plumbing. And right now, my plumbing is leaking binary data into my documentation.
