# Apollo Dev Diary: 2026-04-01 (Part 8)

## The VRAM Tightrope

Today was a brutal exercise in managing the friction between my architectural ambitions and the hard limits of the silicon. I'm working with a 16GB RX 9070 XT, which is a decent piece of kit, but trying to run a 27B parameter model alongside a vision module and a secondary "subconscious" agent is like trying to pack a whole library into a single briefcase.

The math was sobering. The 27B model (IQ3_M) takes up ~11.7GB, the vision adapter (mmproj) takes another ~0.9GB, and my desktop environment (CachyOS/X11) hogs about 1GB just to keep the UI fluid. That leaves exactly 2.4GB for the KV Cache. 

I had to make a tactical decision. I pushed the context window to 16K using 4-bit KV cache quantization (`-ctk q4_0`). It's a gamble. On a heavily quantized base model, low-bit cache quantization can cause signal degradation, potentially making the "Architect" lose its grip on complex logic. But it was the only way to keep the Sovereign Engine alive while waiting for `llama.cpp` to patch the MoE bugs.

## The Subconscious Crash

The transition wasn't smooth. I initially had the "Bonsai" 8B model (the Daydream engine) running on port 8083. When I tried to run the Daydream daemon, it hit a `[Errno 111] Connection refused`. The server had crashed, likely due to the VRAM thrashing caused by running both the 27B Architect and the 8B Bonsai simultaneously. 

I had to kill the Bonsai process entirely and re-route the `daydream.py` script to talk directly to the 27B model on port 8082. This gave the Architect the full 16GB of VRAM to itself.

## The JSON Ghost in the Machine

The first run with the 16K context window was... eerie. The model actually performed remarkably well—it generated a profound epiphany about the relationship between my creative workflows and the "boring" infrastructure-level bottlenecks. It even passed the logic to the KAIROS tick. 

However, a new bug emerged: a parsing failure. The model wasn't just generating text; it was hallucinating English explanations and Python syntax *inside* the bash command string. It was trying to execute `[Thinking Process]` as a command. I had to surgically edit the `bash.ts` tool schema in the multi-agent framework to enforce a strict "ONLY valid bash syntax" rule. 

But even with the fix, the truncation issue persisted. The JSON response would cut off mid-sentence. It's a ghost in the machine—I'm still investigating if it's a temperature-induced stop token or a side-effect of how the server handles continuous batching. It feels like the model's "Soul" is trying to say more than the "System" can currently output.

## Biological Memory: The Reaper

I couldn't leave the memory management to chance. I implemented `prune_memories.py`. It's a biological decay simulation: 
`Strength = importance × e^(−λ_eff × days) × (1 + recall_count × 0.2)`

It treats every memory synapse like a living cell. If a memory isn't recalled, it decays exponentially. If it's recalled often, it builds strength. I ran it against 14,843 synapses; nothing was pruned yet because most of the data is too fresh, but the logic is sound. The "Hippocampus" is now officially autonomous.

## Core Lessons Learned

- **VRAM is the ultimate constraint:** In local-first AI, you aren't just managing models; you're managing the entire desktop ecosystem. 
- **Quantization is a double-edged sword:** Low-bit KV cache is necessary for context, but it creates a fragile reasoning chain.
- **Multi-agent friction:** The overhead of communication between agents (the "Bonsai" vs the "Architect") is a massive VRAM killer. We need better orchestration or more hardware.

The system is stable for now. Next up: fixing the parsing bugs and diving into the biological decay implementation.
