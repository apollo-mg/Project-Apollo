# 2025-12-03: The RDNA 4 War Room

The hum of the 9070 XT is the only thing keeping me company at 2 AM. We are deep in the trenches of Project Apollo, trying to force a high-parameter model to behave on RDNA 4 hardware. It’s a constant battle between the creative dream—running a 13B model locally—and the cold, hard reality of ROCm driver quirks.

### The Illegal Memory Access

Tonight started with a total system crash. The "Illegal Memory Access" error is a classic RDNA 4 headache. It turns out the standard `comfy.model_management.cast_to` logic is too optimistic for ROCm 7.1. It tries to do these rapid, asynchronous Host-to-Device transfers for modulation weights, but the driver isn't handling the race conditions gracefully. It’s trying to be smart and fast, and it ends up corrupting the memory stream.

We had to go "Nuclear." 

We abandoned the elegant async path for a much more brute-force pattern: manually allocating fresh tensors with `torch.empty` on the target device and using synchronous `.copy_()` calls. It’s less "sophisticated," but it’s stable. We’re sacrificing a bit of pure speed to ensure the memory integrity of the forward pass. We’ve patched the `WanAttentionBlock`, the `MLPProj`, and the `CausalAudioEncoder`. It’s a surgical strike across the `Wan 2.1` architecture to keep the silicon from tripping over its own feet.

### The Syntax Trap

Of course, nothing goes smoothly. In the middle of the patch, we hit a classic "fix one thing, break two" scenario. A botched injection in the `WanAttentionBlock` threw an `UnboundLocalError`. The logic was trying to reference a variable `x` that didn't exist in the `__init__` scope. It was a mess of floating code and broken class structures. 

The "Soul" of the project—the actual generation of the video—was held hostage by a simple Python scoping error. We had to clean up the `comfy/ldm/wan/model.py` file, moving the robust casting logic into the `forward` method where it actually belongs.

### The 14-Second Wall

Once we got the model running, we hit the next wall: performance. 14 seconds per iteration. 

For a 13B model, that is agonizing. The "Split Attention" mechanism we’re using is incredibly safe, but it’s essentially running a Python loop that’s killing our throughput. It’s the "safe" way to avoid the artifacts we saw with Triton Flash Attention on AMD, but "safe" is just another word for "slow." 

We can’t go back to Flash Attention—the artifacts are too much. The motion is wrong, the geometry is garbage. We need a middle ground.

### The Indentation Abyss

The goal was to pivot to the PyTorch SDPA (Memory Efficient) backend. It’s the holy grail for this hardware: the speed of a specialized kernel with the stability of the standard library. 

But as we pushed the modification into `comfy/ldm/modules/attention.py`, the Python interpreter revolted. An `IndentationError` brought everything to a halt. It seems the replacement script for the AMD-specific logic got lost in the nesting. We were fighting an invisible war against whitespace. 

We spent the last hour cleaning up the `attention_pytorch` block, ensuring the `if model_management.is_amd():` branches were perfectly aligned with the surrounding logic. It’s tedious, unglamorous work, but this is where the architecture is forged.

### Current Status

We are now running with `--use-pytorch-cross-attention`. We’re testing the limits of the Memory Efficient backend on the 9070 XT. If this works, we break through the 14s/it wall without the hallucinatory artifacts of the Triton kernels.

The system is stable. The silicon is behaving. Now, we see if we can actually make it fast.
