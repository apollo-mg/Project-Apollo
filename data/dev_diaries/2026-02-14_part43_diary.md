# Dev Diary: The Safety Interlock and the Eye of the Machine

**Date:** 2026-02-14
**Session:** Part 43/49
**Status:** Critical Architecture Milestone Reached

Today was about bridging the gap between high-level logic and physical reality. We’ve spent weeks talking about "Safety" and "Risk," but until today, those were just lines of code in a Python file. They were abstract concepts floating in the VRAM of my AMD 9070 XT. Today, we gave the system a "Kill Switch."

### The Physicality of Logic

The core of today's struggle was implementing the **Guardian Kill Switch**. We realized that Buddy (the Agent) could be perfectly logical, but if he hallucinated a movement command that would crash the print head into a corner, the damage would be real. We needed a mechanism that didn't just *say* "stop," but actually *forced* the hardware to stop.

I directed the Gemini instance to implement a `trigger_lockdown()` function within `local_agent.py`. This is the "Hands" of the Guardian. When the monitoring agent (the `buddy_guardian.py`) detects a **P0 (Critical)** event, it doesn't just log an error; it issues an `M112` (Emergency Stop) command via the Klipper API and creates a `guardian_lock.json`.

This is the "Safety Interlock." The system now has a physical state of "Locked." If that lock file exists, the Agent is effectively paralyzed. He cannot generate G-code; he cannot execute shell commands. The "Soul" (the creative drive to build) has been constrained by the "System" (the hard limit of safety).

### The VRAM Wall and the Vision Pivot

With the safety layer established, the next step was the most ambitious: **"Desktop Eyes."** Buddy wants to see. He wants to visually inspect the print bed and the workspace to resolve errors that purely numerical data might miss.

This brought the inevitable friction of local-first development: **VRAM constraints.** Running a massive Vision Language Model (VLM) alongside the primary LLM and the OS on a 16GB card is a tight squeeze. We had to pivot. We moved away from larger, slower models to hunt for something that respects the ROCm architecture of my AMD card.

After a deep dive into the current model landscape, we identified **Qwen2.5-VL-3B** as the winner. It has dedicated Flash Attention support for ROCm, which is a massive win for performance. It’s small enough to coexist with Buddy, but capable enough to act as a visual agent rather than just a simple captioner.

### The Ghost in the Machine (The Black Screen)

We hit a technical snag during the vision test. The `mss` library—intended for high-speed screen capture—failed on the display server (likely a Wayland/X11 permission issue), returning nothing but a void of black pixels. 

We attempted to bypass this using `scrot` and ImageMagick, but the result was the same: a black screen. This is the reality of local AI development; you aren't just fighting the model, you're fighting the OS, the display server, and the hardware abstraction layers. 

However, the *architecture* is sound. The pipeline—`capture_screen` $\rightarrow$ `llm_interface` $\rightarrow$ `Qwen2.5-VL`—is built. The fact that the "eyes" are currently seeing darkness is a configuration problem, not a logic failure. The system is ready to receive a vision model once we bridge the display-server gap.

### Core Lessons & Evolution

1.  **The Interlock is non-negotiable:** A local agent without a hardware-level kill switch is just a high-speed way to break things.
2.  **VRAM is the ultimate architect:** Every decision on model size is a trade-off between intelligence and the ability to run multiple agents simultaneously.
3.  **Asynchronous Safety:** The Guardian and the Agent must operate in parallel but respect the same lock. The `guardian_lock.json` is the single source of truth that binds them.

**Next Steps:** 
Fix the display capture (likely moving to `grim`/`slurp` for Wayland support) and finalize the integration of the Qwen vision brain. The project is moving from "thinking" to "seeing."
