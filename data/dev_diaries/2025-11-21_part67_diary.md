# Dev Diary: 2025-11-21 — The Memory Wars

## The Dual-Model Delusion

I tried to fit heaven into a paperweight.

That's the honest truth of today's session. The workflow demanded two 14B-parameter Wan2.2 GGUF checkpoints resident and ready: `HighNoise` for the initial diffusion cascade, `LowNoise` for refinement. A "Refiner" architecture, elegant on a whiteboard.

On silicon? It's a death spiral.

**The Reality Check:**
- VRAM: 16GB (RX 9070 XT, RDNA 4, bleeding edge and bleeding all over itself)
- System RAM: 32GB
- Two 14B GGUF models @ Q4_K_M: ~20GB combined
- T5 XXL FP8 encoder: ~4.5GB (and I had TWO of them loaded, because why not?)
- OS overhead, latents, VAE decode buffers, the ghosts of allocations past: another 5-8GB

Total demand: **~29-32GB**. Total supply: **32GB**.

The OOM killer (Exit 137) didn't hate me. It pitied me.

---

## The CLIP Deduplication: A Small Victory

The first epiphany arrived through graph tracing. Nodes 71 and 90 were both loading `umt5_xxl_fp8_e4m3fn_scaled.safetensors`. Identical files. Identical weights. ComfyUI's deduplication is clever for checkpoints but apparently has blind spots for custom node trees.

**The Fix:** Consolidate to a single CLIP Loader (Node 71). Redirect all downstream links. Delete Node 90.

**The Cost:** ~4-5GB reclaimed. Not a cure, but a tourniquet.

But then came the phantom links.

## The Orphan Link Mystery

Links 164 and 178 existed in the `target.inputs[].link` arrays but were absent from `origin.outputs[].links`. The JSON graph had phantom arteries—connections that flowed one way but weren't registered at the source.

Node 71's `outputs[0].links` array didn't know it had children.

```python
# The validation caught what my eyes missed:
178 is funky... origin(71).outputs[0].links does NOT contain it, 
but target(99).inputs[0].link does.
```

I patched the inconsistency. Added the missing link IDs to Node 71's output registry. The graph wept tears of JSON but held together.

**Lesson:** Workflow surgery requires updating BOTH the link registry AND the node's output manifests. One without the other creates ghosts.

## DisTorch: Savior or Saboteur?

DisTorch was supposed to be the answer. CPU offloading. Memory mapping. The ability to stream weights from RAM to VRAM on-demand rather than loading everything at once.

**The Theory:** `virtual_vram_gb=6.0`, `donor_device="cpu"`, `eject_models=True`. When Sampler A needs the HighNoise model, eject LowNoise. When Sampler B needs LowNoise, eject HighNoise. Dance.

**The Reality:** Loaders execute *before* samplers in ComfyUI's DAG. By the time the first KSampler fires, both models have already been touched, both marked as "in use," both refusing to yield.

The `eject_models=True` flag I added to `wrappers.py` runs during loader execution—not during sampler handoff. It's like installing a fire escape on a building that's already burned down.

**The Hang:** The second KSampler pass choked. Not OOM this time—*stall*. The transition cost between models became the killer. Memory fragmentation? Stale CUDA context? GC never running fast enough?

I'm not sure. I only know the system froze, and I had to kill it.

---

## The Configuration Paradox

RDNA 4 demands contradictions:

- **Triton Flash Attention:** MUST be `TRUE`. Disabling it causes driver-level crashes.
- **TunableOp:** MUST be `FALSE` (0). Enabling it introduces instability.

Two settings that should improve performance, one must live and one must die. The hardware is opinionated.

```
PYTORCH_HIP_ALLOC_CONF=max_split_size_mb:128
```

This line alone has prevented more crashes than I can count. Smaller allocation chunks = less fragmentation = less "reserved but unreachable" memory rot.

## The Soul vs. System Friction

Here's what I keep coming back to:

**The Soul** wants parallelism. It wants the Refiner workflow with two models warm and ready, switching seamlessly between noise profiles. It wants the *idea* of the architecture to map cleanly onto execution.

**The System** has 16GB of VRAM and a grudge. It will swap. It will thrash. It will kill your process before you finish the thought.

Today I didn't solve this. I applied bandages:
- Deduplicated CLIP loaders
- Converted UNet loaders to DisTorch2
- Tuned `virtual_vram_gb` through a dozen values (0.0, 0.1, 6.0, 128... each a prayer)
- Patched orphan links in the JSON graph

The hang at KSampler 2 remains. The transition cost between models is still too high. The memory isn't being purged fast enough, or at all.

**Next attempts:**
1. Forced garbage collection node between samplers (explicit `torch.cuda.empty_cache()` injection)
2. True memory-mapped GGUF loading (does the current loader even support it?)
3. Sequential execution enforcement—make the DAG wait for cleanup before proceeding

---

## The Hard Truth

I'm building a multi-agent ecosystem on hardware that wants to murder me.

32GB of RAM is not enough for two 14B models and pretension. The only way forward is either:
- **More memory** (upgrade path: expensive)
- **Better streaming** (DisTorch isn't doing its job yet)
- **Smaller models** (heresy, but...)

Or I accept that the Refiner workflow will be *slow*. That the second pass will thrash the swap file. That "local-first" sometimes means "local-first, then local-second, then please hold."

The architecture survives. The elegance dies a little.

---

**Status:** Unstable. Functional in narrow bands. The Exit 137 ghost is sleeping, not dead.

**Tomorrow:** Aggressive GC. Forced unloading. Or I buy more RAM.
