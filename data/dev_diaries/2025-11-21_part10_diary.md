Not a CUDA error. Not the predictable, well-documented failures of NVIDIA's ecosystem. This is AMD's greeting—a HIP error that arrives asynchronously, unannounced, like a burglar who's already left before the alarm triggers.

Line 146. The Q6_K dequantization routine. A bit-shift operation that should be trivial, mundane even, but on gfx1201 silicon with ROCm 7.1, it's a minefield.

## The Quantization Problem

Here's what I'm trying to do: run Wan2.1-T2V-14B, a 14-billion parameter flow-matching model, quantized to Q4_K_M, through ComfyUI, on a GPU that doesn't officially exist in the driver support matrix yet.

The "M" in Q4_K_M means mixed precision—some layers at Q4_K, some at Q6_K, strategic allocation of bits to preserve fidelity where it matters. The Q6_K layers are the problem. They're more accurate, yes, but they require a dequantization dance that the RDNA 4 architecture apparently hasn't learned to perform gracefully.

The operation at line 146 is reshaping and bit-shifting:
```python
ql.reshape((n_blocks, -1, 1, 64)) >> torch.tensor([0, 4], device=d.device, dtype=torch.uint8).reshape((1, 1, 2, 1))
```

Extracting 6-bit values from packed storage. Elegant in theory. On this hardware, the reshape or the broadcasted shift is touching memory that doesn't belong to it.

## The Soul vs. System Problem

This is the friction I've been documenting since day one.

**The Soul** wants to run 14B parameter models locally, to generate video from text without API calls, to keep the computation—and the intelligence—on bare metal that I own.

**The System** is a GPU that shipped three months ago, drivers that call it "gfx1201" in code that was written for a chip that wouldn't exist when the kernel was drafted, and a ROCm stack that treats RDNA 4 as a footnote to CDNA 3.

The illegal memory access isn't a bug. It's a feature of the relationship between ambitious software and reluctant hardware.

## The Modulation Crash

The error migrated. That's progress, isn't it?

After patching the RoPE encoding to force float32 for the `img_ids` tensor—because bfloat16 is apparently too fragile for coordinate generation on this silicon—the crash moved to line 231 in `WanModel.forward`:

```python
e = (comfy.model_management.cast_to(self.modulation, dtype=x.dtype, device=x.device).unsqueeze(0) + e).unbind(2)
```

The modulation parameters in the Wan architecture. They're supposed to be harmless—just scaling and shifting activations based on timestep. But `cast_to` calls `copy_`, and `copy_` calls something in the HIP runtime that decides this memory doesn't belong to us.

The async nature of HIP errors means the stack trace is a lie. The crash happened elsewhere, and we're just seeing the corpse being discovered.

## Architecture Notes: What I'm Learning

### 1. RDNA 4 Doesn't Play Nice with Certain Memory Patterns

The Q6_K dequantization involves non-contiguous memory access patterns—reshaping tensors in ways that create stride-heavy operations. NVIDIA's memory controller eats this for breakfast. AMD's implementation on gfx1201 apparently has a bug, or a missing optimization, or a guard page that's too aggressive.

### 2. dtype Choices Are Political

Choosing bfloat16 for the RoPE coordinate generation was an optimization. It saved memory, matched the rest of the model's precision. But the RDNA 4 integer units apparently don't handle the coordinate arithmetic correctly in that precision. Float32 is the tax I'm paying for stability.

### 3. The GGUF Format Is Both Savior and Villain

GGUF lets me run 14B parameter models in 16GB of VRAM through aggressive quantization. It's the only way. But the dequantization kernels are written assuming certain hardware behaviors that don't translate cleanly to AMD's implementation of HIP.

### 4. ComfyUI's Architecture Is Beautiful and Fragile

The node-based execution, the way models flow through the pipeline—it's elegant. But every wrapper, every executor, every `patcher_extension.py` layer adds indirection that obscures where the actual failure happens.

---

## The Fix Applied (Temporarily)

I patched `WanModel.rope_encode` to generate `img_ids` in float32 instead of inheriting bfloat16 from the input tensor. The reasoning: if the coordinate generation is stable, the attention patterns will be stable, and the modulation parameters downstream will receive correct inputs.

It's a bandage. The real fix requires either:
- A kernel rewrite that avoids the problematic memory access pattern
- A driver update from AMD that addresses the RDNA 4 edge case
- Acceptance that Q6_K dequantization is off-limits on this hardware

Why do I care? Why not just call an API?
