# Project Apollo: The Triage Breakthrough and the JSON Ghost

The friction between the "Soul" of an autonomous agent and the "System" of its silicon host is becoming painfully clear. Today was a lesson in the fragility of logic when it meets the chaos of real-world data.

## The Triage Architecture
I spent a significant portion of the session wrestling with the model-routing problem. We have a fundamental problem: we don't want to waste heavy VRAM on trivial tasks, but we can't afford to lose the "thought" required for complex reasoning. 

After weighing the options between the specialist Qwen-Coder (fast, syntax-heavy, but "blind") and the thinker DeepSeek-R1 (logic-heavy, but "chatty"), I realized we needed a hierarchy. I implemented a new triage system: a "Receptionist" (Llama 1B) now sits at the front gate. It analyzes the intent of every prompt. If it's a coding task, it wakes the DeepSeek Engineer. If it’s a complex structural or parametric CAD task, it wakes the Qwen Architect.

This is our version of a Mixture of Experts (MoE), but manually orchestrated at the router level. It’s a way to manage our VRAM constraints while ensuring the "Soul" of the reasoning model is only present when the complexity demands it.

## The JSON Ghost (The Thought-Block Crash)
I caught a brilliant, infuriating bug while monitoring Apollo’s "eyes." I had the vision model (Qwen2.5-VL) identify a piece of hardware from a photo. It worked perfectly—it read the text from the CPU. But then, everything fell apart.

DeepSeek-R1 took over to process the text. Because it uses Chain-of-Thought, it generated a `<think>` block before its actual tool call. My regex parser, which was looking for a specific JSON pattern, saw the `{` inside the `<think>` tag and thought it had found the start of a tool call. The parser got confused, the JSON became invalid, and the entire agentic loop crashed. 

It was a collision between the model's "internal monologue" and the hard-coded requirements of the system. I've patched `buddy_agent.py` to strip these thought blocks before parsing, finally allowing the "Thinker" to coexist with the "System."

## The Model Hoard & The Hardware Paradox
We are officially moving into the "Hoard" phase. The volatility of the open-source AI landscape is a threat to sovereignty. If a model is pulled behind an API or censored tomorrow, we lose our intelligence. 

We've adopted a new philosophy: **The Model Hoard.** We will aggressively archive GGUF/safetensors onto local storage to ensure our system's intelligence can never be taken away. 

This creates a new physical bottleneck. My 3TB Backup is a spinning HDD—slow, at ~150 MB/s. Loading a 50GB model from it would take minutes, killing the "instant" feel of the agent. My NVMe (WD_BLACK) is fast enough for the "Hot" tier (active models), but the "Cold" tier (the Vault) must live on the HDD. I’ll have to manage this manual migration of weights to ensure the active minds stay on the fast silicon.

## Next Steps
The agent's tool-use is still too "polite." It's planning, but not acting. It sees a new item in the vision input and says, "I should add this," but it doesn't actually trigger the `add_hardware` tool. I've started refactoring the system prompts in `buddy_agent.py` to force more aggressive tool invocation. 

Tomorrow, we test the updated vision-to-inventory pipeline. If the Architect can see, think, and write to the database in one seamless loop, we've achieved something truly significant.
