# Dev Diary: 2025-11-21 — The Bit That Ate My Dreams

## The Moment Silicon Betrayed Me

The crash came at line 175 of `dequant.py`, in a place so mundane it almost feels like a personal insult.

```python
sc[..., 4:] = (m_d & 0x0F) | ((d >> 2) & 0x30)
```

A bitshift. A bitwise AND. The kind of operation I'd trust to a child's first C++ program. And yet, there it was: `HIP error: an illegal memory access was encountered`.

The RX 9070 XT stared back at me with 16GB of pristine, untouched VRAM—16,997,416,960 bytes of available memory, according to the logs. Plenty of room. The problem wasn't space. It was something more fundamental. Something in the way AMD's ROCm stack interprets "don't crash" versus how the rest of reality does.

## The Architecture That Almost Worked

I had been optimistic. Foolishly, beautifully optimistic.

The Wan2.1-T2V-14B model, quantized to Q4_K_M, was loading through DisTorch2's distributed memory virtualization. The plan was elegant: keep the compute hot path on the GPU, spill the weight layers to CPU memory, and let the magic of model parallelism bridge the gap.

The logs show the ambition clearly:

```

Twenty-five gigabytes of virtual address space. A model that doesn't fit, made to fit through sheer architectural will. It's the kind of hack that becomes a feature when it works.

But the DisTorch2 logs also reveal the fragility:

```

Three times. The system detected its own incompleteness and patched around it, but somewhere in that scaffolding, the foundation was already rotten.

## The Q4_K Autopsy

Here's what I know now:

The Q4_K quantization format stores weights in 4-bit blocks with per-block scales and minimums. The dequantization requires unpacking these compressed values, and the `get_scale_min` function is where the scales and minimums are extracted from packed bytes.

The operation that failed—`((d >> 2) & 0x30)`—is extracting bits 2-3 of a byte. Simple. But on HIP/ROCm, something in the memory access pattern triggered a segfault that CUDA would have silently tolerated.

Three possibilities:

1. **Alignment issues**: AMD's memory controller might be stricter about alignment than NVIDIA's. The tensor operations could be accessing misaligned addresses that ROCm refuses to forgive.

2. **Race conditions**: The error message itself admits: "HIP kernel errors might be asynchronously reported at some other API call." The crash might not have been at the instruction that failed, but at the next synchronization point.

3. **The ComfyUI-GGUF integration**: The stack trace shows `ComfyUI-GGUF/ops.py` calling into the dequantization logic. The quantization-aware operators might not be fully HIP-compatible, despite PyTorch's best efforts.

I'm leaning toward #3. The GGUF format was born in the CPU-first world of llama.cpp. Running it through ComfyUI's node graph, through DisTorch2's virtualization, through ROCm's HIP layer, through AMD's gfx1201 architecture... that's six layers of abstraction between the math and the metal. Somewhere in there, a promise was broken.

## The Soul-System Friction

This is the tension that keeps me awake:

**The Soul** wants to run 14-billion parameter video models on consumer hardware, to create a sovereign AI ecosystem that doesn't phone home to Silicon Valley. It wants the cyberpunk cityscape to render in real-time, neon lights reflecting on wet pavement, the dream of local-first intelligence.

**The System** is 16GB of GDDR6, a ROCm driver that was probably beta-tested by three people, and a quantization format designed for ARM servers.

The crash isn't a bug. It's a feature of this tension. The moment I stop hitting these walls, I've stopped building.

---

## What I'm Changing Tomorrow

1. **AMD_SERIALIZE_KERNEL=3**: The error message suggested it. I'll serialize the HIP kernels and see if the crash becomes deterministic.

2. **TORCH_USE_HIP_DSA**: Device-side assertions might catch the illegal access before it corrupts state.

3. **Fallback to CPU dequantization**: If the GPU can't be trusted with bitwise operations, the CPU will do the dirty work and the GPU can handle what it does best.

4. **Q6_K or FP16**: The Q4_K format might be too aggressive. The extra memory overhead could buy me stability.

5. **A prayer**: Not in any religious sense. But acknowledging that some problems require grace.
