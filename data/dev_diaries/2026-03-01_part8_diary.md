# Project Apollo: Dev Diary - 2026-03-01 (Part 8)

## The Sound of the Machine

Today was a brutal cycle of hardware-level frustration and architectural breakthroughs. I've been wrestling with the "ears" of the system—trying to turn a standard webcam mic into something that can actually function as a sentient agent's input.

### The ALSA Hardware Lock
The first major roadblock was a classic Linux-level friction point. I was trying to bridge the gap between the wake-word listener and the command recording loop. The logic was sound, but the implementation was naive: the script was trying to open a second, simultaneous connection to the microphone. Because I'm running on a Linux/ALSA stack, the hardware driver saw this as a resource conflict. It’s a rigid, "one-owner" architecture that doesn't play nice with dynamic, multi-stage audio loops.

I had to refactor the entire audio pipeline. Instead of closing and re-opening the device (which was causing the `PortAudioError: Device unavailable`), I shifted to a "Persistent Stream" architecture. Now, the microphone remains open continuously, and we simply pass the existing hardware handle from the wake-word listener to the command recorder. It’s cleaner, faster, and—most importantly—it doesn't crash the kernel.

### The Silence Paradox
Once the hardware stabilized, a new problem emerged: the "Silence Threshold." Whisper was being too impatient. The moment the wake-word was detected, the system would see the tiny millisecond of silence before the actual command and immediately assume the user was done. It was cutting off the user before they could even breathe.

I implemented a `has_started` grace period. The system now stays in a `[WAITING]` state for a few seconds after a trigger. Only when it detects actual speech does the silence-detection timer start counting. It’s a small piece of logic, but it's the difference between a tool that feels "broken" and one that feels "patient."

### The Memory Leak and the "Gunshot" Crash
The most technical "aha!" moment came from a crash that looked like it was caused by a loud noise. A sudden spike in input caused the `whisper-server` to die. 

Digging into the Python buffers, I found the culprit: a massive memory leak in the audio buffer management. When I added the "Lookahead" feature (capturing that extra 0.6s of audio), the buffer wasn't being pruned correctly. A loud noise triggered a burst of chunks that ballooned the array size. By the time the script tried to send that massive, bloated chunk to the Whisper server, the RAM was exhausted and the process crashed. It wasn't the noise itself—it was the *size* of the noise. I’ve corrected the slicing logic to ensure the buffer is strictly capped at 3 seconds.

### The Soul vs. The Silicon
It’s funny—after fixing the technical plumbing, we had to address the "Soul." The current voice was too robotic. I spent time running `voice_audition.py` to find a personality. We landed on `bf_lily`—a sophisticated British voice that actually fits the "witty grad student" persona we've built for Zoey. 

The transition from a "voice" to a "character" is much easier when the hardware doesn't fight you every step of the way.

### Current Status & Path Forward
*   **Architecture:** Successfully implemented a continuous-stream, non-blocking, multi-threaded audio loop.
*   **Hardware:** Using the C922 webcam as a "Room Ear" (Wake Word) for now.
*   **Next Step:** Moving into the deep-learning noise reduction territory. We're bypassing the proprietary AMD-only software and going straight to **DeepFilterNet**. This will allow us to clean up the signal before it even reaches the LLM, effectively turning a cheap webcam into a high-fidelity input. 

The friction between the "Soul" (the character) and the "System" (the ALSA/ROCm limits) is narrowing. We're getting closer to a seamless, local-first intelligence.
