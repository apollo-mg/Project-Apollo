## The RDNA 4 Wall: Bypassing the Broken Kernel

### The Ghost in the Silicon
I thought I had it. I thought the native PyTorch RMSNorm kernel was the answer to our performance bottleneck. I was wrong. 

The RX 9070 XT is a beast of a card, but the RDNA 4 architecture (gfx1201) is currently a minefield of unoptimized kernels. I attempted to leverage the native `torch.nn.functional.rms_norm`, but the system threw a catastrophic `torch.AcceleratorError: HIP error: an illegal memory access was encountered`. 

This isn't just a software bug; it's a fundamental friction between the high-level mathematical "Soul" of the model and the "System" of the ROCm driver. The kernel is attempting to access memory addresses that don't exist or are misaligned—likely a Wave32 vs Wave64 alignment issue in the FP8/Mixed Precision path. When the kernel fails, it doesn't just error out; it crashes the entire execution pipeline, leaving us with a cryptic stack trace that points to `torch.zeros_like(input)`—a symptom, not the cause.

### The "Safe" Fallback: Sacrificing Speed for Stability
The realization hit me: We cannot trust the native GPU kernels for this specific math operation on this hardware yet. 

I had to abandon the pursuit of "pure speed" in favor of "guaranteed execution." I implemented a **Safe Python RMSNorm Patch**. 

**The Architectural Shift:**
1. **Forced Upcasting:** Every input is now cast to `.float()` (FP32) before the norm operation.
2. **Enforced Contiguity:** I added `.contiguous()` to the memory layout. On AMD hardware, non-contiguous tensors are a recipe for illegal memory access when passed through certain kernels.
3. **Pure Math Fallback:** By moving the math to a more basic, element-wise operation, we bypass the buggy, optimized kernel entirely.

It was a gamble. I feared the overhead would be massive.

### The Breakthrough
**It is running.** 

The system passed the crash point. The model loaded, processed the first block, and—crucially—it didn't die. 

The CPU usage is spiking at **339%**. This is the "smoking gun." It confirms my hypothesis: the CPU is now handling the heavy lifting for the RMSNorm math, acting as a stabilizer for the GPU. The GPU is still doing the massive Transformer/Attention work in FP8, but the "tricky" normalization is being managed by the CPU. 

It’s not the peak performance we dreamed of, but it is **stable**. In a local-first multi-agent ecosystem, stability is the prerequisite for intelligence. 

### Core Lessons & Next Steps
* **Hardware-Specific Kernel Fragility:** We cannot assume "Native" means "Better." On bleeding-edge RDNA 4, native kernels are currently liabilities.
* **The Cost of Safety:** The CPU overhead is the price we pay for bypassing the broken silicon paths. 
* **The Hybrid Path:** The next objective is to re-enable `SDMA=1` (Fast Swap) while keeping the `Safe Python RMSNorm` patch. If we can decouple the memory transfer speed from the compute stability, we might find a "sweet spot" that allows for production-grade video generation on consumer-grade AMD hardware.
