# Project Apollo: The Silicon War – Log 2025-12-03

The dream is simple: high-fidelity video-gen running locally on my RX 9070 XT. No cloud, no subscription, just pure, raw compute fighting against the limits of VRAM. But today, the silicon actually fought back.

We are pushing the boundaries of the *Wan 14B* model—a beast of a transformer architecture. To fit it, I’m using the GGUF quantization strategy. It’s a clever trick: splitting the model into high/low noise passes to squeeze every drop of utility out of the 16GB of VRAM. It’s a delicate dance of memory fragmentation and mathematical precision.

### The Crash: An Illegal Memory Access

It started with a promise. I was running a `Q6_K` quantization pass—a higher precision, higher memory footprint—trying to balance the the "Soul" (the high-quality video generation) with the "System" (the 16GB cap). 

Then, the terminal screamed.

`torch.AcceleratorError: HIP error: an illegal memory access was encountered.`

In the world of AMD ROCm, that’s the equivalent of a blue screen. It’s a kernel panic at the hardware level. The trace points directly to the `dequantize_blocks_Q6_K` function in the `ComfyUI-GGUF` custom nodes. Specifically, it’s failing during a bitwise operation:

`ql = ql.reshape((n_blocks, -1, 1, 64)) >> torch.tensor([0, 4], device=d.device, dtype=torch.uint8).reshape((1, 1, 2, 1))`

This is where the friction lies. The GGUF dequantization logic is trying to manipulate the bit-level weights of the model to reconstruct the higher-precision values needed for the inference step. On NVIDIA, this might pass unnoticed. On AMD, using the ROCm stack, this specific bit-shifting kernel is hitting an illegal memory address. 

### The Anatomy of a Failure

The error is asynchronous, which is the worst kind of nightmare. The stack trace might be lying to me; the actual crime might have happened several clock cycles before the report. But the culprit seems clear: we are pushing the limits of how the ROCm driver handles non-standard bitwise operations on quantized tensors. 

We are trying to run a massive, 14-billion parameter model using a "low VRAM" strategy, but the overhead of managing those quantized blocks is causing the kernel to step outside the boundaries of the allocated memory. It’s a classic case of the system being too clever for its own good.

### Technical Friction: The ROCm Frontier

The logs also show a mess of missing dependencies—`torchaudio` is missing, which breaks the audio-encoding nodes. It’s a symptom of the chaotic ecosystem we're building in. We're building a multi-agent, local-first ecosystem, but the foundation is still being laid one `pip install` at a time.

But the core issue is the quantization logic. If I want the "Soul" of the video—the fluid motion, the cinematic texture—I need the higher bit-depth of `Q6_K`. But if the "System" can't handle the memory access pattern of that specific kernel, I'm stuck.

### The Path Forward

1.  **The Quantization Pivot:** I might have to drop down to `Q5_K` or even `Q4_K`. It’s a compromise. It’s less "soulful," more compressed, but it’s stable. We need to find the sweet spot where the model is smart enough to be useful but lean enough to not trigger a HIP error.
2.  **Kernel Debugging:** I need to look into `AMD_SERIALIZE_KERNEL=3`. If I can force the driver to serialize the kernels, I can find exactly which operation is killing the process. It’s a slow, tedious way to work, but it’s the only way to stop guessing.
3.  **Memory Management:** The `lowvram` flags and the `reserve-vram` settings are currently fighting a war of attrition against the model’s weight-loading process. I need to optimize the way ComfyUI handles the split-attention and weight-casting.

We are close. The 9070 XT is a monster, but even monsters have limits. We aren't just running code; we are wrestling with physics.
