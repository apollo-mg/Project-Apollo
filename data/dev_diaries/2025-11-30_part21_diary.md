# Dev Diary: The RDNA 4 Wall (Session 21/43)

## The Ghost in the Machine: The Synchronization Deadlock
The pursuit of stability on AMD's RDNA 4 architecture is proving to be less of a straight line and more of a desperate, jagged crawl. Today was a brutal exercise in fighting the friction between the "Soul" (the massive 14B parameter Wan model) and the "System" (the stubborn, non-compliant kernels of the RX 9070 XT).

### The Technical Friction: Synchronization vs. Throughput
I spent the first half of the session chasing a phantom. The system was experiencing a total hang—high VRAM usage, zero progress, and a silent kernel. My initial instinct was a synchronization deadlock. I had introduced aggressive `torch.cuda.synchronize()` calls within the `cast_to` function to prevent "Illegal Memory Access" errors during weight casting. 

The problem? The synchronization was too heavy. On this RDNA 4 hardware, those global sync calls were causing the GPU to stall, potentially creating a race condition with the asynchronous memory copies. I attempted to remove the global synchronization and switch to `non_blocking=False`, but the "Illegal Memory Access" errors simply migrated from the weights to the attention kernels.

### The Architectural Epiphany: The FP32 Safety Net
The breakthrough came when I stopped looking at the *management* of memory and started looking at the *math* inside the kernels. The traceback pointed squarely at `addcmul` within the `WanAttentionBlock`. 

On RDNA 4, the mixed-precision (FP16) operations in the modulation layers were fundamentally broken. The hardware was failing to handle the `addcmul` operation with the specific scale/shift tensors used in the Wan model. 

**The Fix:** I implemented a "Safe Modulation" patch. I forced the `WanAttentionBlock` to perform its modulation arithmetic in **FP32** precision. It’s a heavy-handed approach—it’s computationally expensive and inflates the memory footprint—but it bypasses the faulty FP16 kernel implementation. This is the classic trade-off: sacrificing the "System's" efficiency to preserve the "Soul's" integrity.

### The Flash Attention Failure
I tried to push the boundaries by enabling Triton Flash Attention. I thought it would be the silver bullet for VRAM management. Instead, it was a disaster. The interaction between the Triton kernels and the model's specific modulation requirements caused immediate instability. It turns out the "bleeding edge" is currently too unstable for the current ROCm/Triton stack on this architecture. I've reverted to standard PyTorch SDPA for now.

### Current Status: The Long Wait
The "No Progress" hang is still haunting us. Even with the FP32 safety patches, the KSampler is stalling. 

**My current suspicion:** The `x.contiguous()` calls I added to ensure memory safety are causing massive memory fragmentation. In a 16GB environment, calling `.contiguous()` on large tensors in every attention block is likely triggering a death spiral of memory swapping. The system isn't "crashing"—it's drowning in its own allocations.

**Next Steps:**
1.  Trace the `WanAttentionBlock` execution via debug prints to see exactly which block causes the stall.
2.  Monitor VRAM fragmentation via `monitor_vram.py`.
3.  Determine if the `lowvram` mode is forcing a constant, expensive shuffle of weights that is choking the PCIe bus.

The architecture is stable, but the silicon is uncooperative. We are fighting the hardware to save the model.

***

**Core Lessons for the Local-First Ecosystem:**
*   **Hardware-Specific Kernels are Non-Negotiable:** You cannot treat AMD like "NVIDIA-lite." The kernel-level math (FP16 vs FP32) is a fundamental architectural constraint.
*   **The Cost of Contiguity:** In memory-constrained environments, `.contiguous()` is a luxury we can barely afford.
*   **The Synchronization Paradox:** Over-synchronizing prevents crashes but creates bottlenecks; under-synchronizing creates memory corruption. Finding the "sweet spot" is the true challenge of local-first AI.
