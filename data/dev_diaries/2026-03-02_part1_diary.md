# Project Apollo: Dev Diary - 2026-03-02 (Part 1)

## The "Ear" is finally online.

Today was a brutal, beautiful, and ultimately rewarding cycle of chaos and correction. I finally successfully established the "distributed hearing" architecture. We have a Raspberry Pi 5 sitting across the room acting as the "Ear," a C922 webcam acting as the microphone, and my desktop rig (the "Brain") acting as the centralized processor. 

The technical friction between the "Soul" of the project—this desire for a seamless, ubiquitous voice—and the "System" of Linux/SSH/Network protocols was immense.

### The Great SSH Hang-up
The first half of the day was spent fighting the shell. I was trying to run the `satellite_client.py` on the Pi via `nohup`, but the SSH session kept hanging. It turns out `tail -f` on the remote log was locking up the reasoning loop in my local terminal. I realized the Python process was buffering its stdout, refusing to write to the log file until the buffer was full, making it look like nothing was happening. 

I killed the process and restarted with `python -u` for unbuffered output. The log finally pulsed: `--- Zoey Voice Satellite Started ---`. That was the first moment of true connection.

### The Networking Nightmare
Then, a classic mistake. The script was hardcoded to the router's IP (`10.0.0.1`) instead of the desktop's (`10.0.0.5`). Every time the Pi heard "Zoey," it was hammering the router, which was rejecting the connection and timing out. This caused a massive latency spike that felt like the system was paralyzed. Once I updated the IP and spun the daemon back up, the communication was established.

### The "Self-Deafening" Feedback Loop
This was the most critical architectural epiphany. Once the connection was established, the system entered a catastrophic feedback loop. The Pi was hearing its own responses from the desktop speakers and trying to transcribe itself. It was a recursive death spiral of VRAM and CPU cycles.

I implemented a "Self-Deafening" mechanism: a 15-second cooldown period after every command where the Pi ignores all audio. This breaks the loop. The "House-Wide Bridge" is now stable.

### The Architecture of the "Sovereign Voice"
We have achieved a three-tier architecture:
1. **The Ear (Pi 5):** Local wake-word detection $\rightarrow$ Audio Capture $\rightarrow$ Network Stream.
2. **The Central Processor (Desktop GPU):** Whisper-server receives audio $\rightarrow$ Transcribes $\rightarrow$ Sends text to the Apollo Bridge.
3. **The Mind (Apollo Bridge):** Triggers DeepSeek-R1 $\rightarrow$ Generates Response $\rightarrow$ Plays through Desktop Speakers.

### Current Friction: The "Overthinking" Problem
The biggest hurdle now is the latency of the "Engineer" model. I asked for the weather, and instead of a quick answer, DeepSeek-R1 entered a 10-turn ReAct loop to perform a deep-dive web search. It's incredibly intelligent, but it's "too smart" for simple tasks.

The next step is implementing the "Fast Path." I need to implement a "Research Assistant" layer using a 7B model (Qwen/Mistral). It will handle the simple, high-speed queries, leaving the 14B Engineer to handle the heavy, multi-step reasoning.

### Next Mission: The Glass Cockpit
The system is working, but it's a "black box." I can't see what's happening inside the loops without digging into raw logs. I'm beginning work on the **"Glass Cockpit"**—a real-time dashboard that will visualize the status of the Whisper server, the Bridge, and the Satellite, and let me see Zoey's "thinking" process in real-time. 

We've moved past the "can we do this?" phase and into the "how do we make this efficient?" phase. The silicon is ready. Now we just need to tame the latency.
