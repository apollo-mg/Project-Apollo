# Dev Diary: 2025-11-21
## The Illegal Memory Access and the Art of Knowing When to Stop Fighting

### The Error That Refused to Die

3:01 AM. The terminal spat it out again, pristine and unforgiving:

```
HIP error: an illegal memory access was encountered
...
return r * weight_on_device
```

The same line. The same operation. The same betrayal.

We'd been dancing around this for hours now—transferring tensors, switching devices, trying `.to(device)` here, forcing dtype casts there. Each attempt landed on the same grave: **line 29 of `rmsnorm.py`**, where a simple element-wise multiplication decided it wanted to access memory it wasn't permitted to touch.

The stack trace was a monument to our hubris, dozens of layers deep through ComfyUI's sampler chain, Wan2.1's diffusion forward pass, cross-attention blocks, and finally down into the RMSNorm operation where reality caught up with our assumptions.

### The Contiguous Epiphany

Gemini's diagnosis landed with surgical precision:

> *"This strongly suggests that the issue isn't just the transfer of the weight, but the multiplication operation itself or the state of the tensors involved. On RDNA architectures, especially with new drivers/kernels, non-contiguous tensors in element-wise operations can sometimes trigger these memory faults if the kernel stride logic is buggy."*

The fix was almost embarrassingly simple:

```python
weight_on_device = weight.to(dtype=x.dtype, device=x.device).contiguous()
```

Force the tensor into sequential memory layout. No fancy strides. No clever views. Just honest, contiguous bytes that the kernel couldn't misunderstand.

But I felt the resistance rising. This was whack-a-mole. Every kernel we touched would reveal another instability, another edge case that the ROCm 7.1.0 drivers hadn't learned to love yet.

### The Pivot

Then came the question that would have been premature three months ago:

> *"Should we just look for evidence of other people having high success with comfyui + text to video + rocm?"*

> *"Would it be more efficient to look for evidence of success on the web for other people who've gotten rdna 4 + comfyui + text to video already working?"*

**RDNA 4.**

That's what we're running here. The RX 9070 XT. Architecture `gfx1201`. The silicon is younger than the PyTorch version we're using to drive it.

The arrogance of building on bleeding-edge hardware is assuming that *your* debugging is the primary contribution required. Sometimes the contribution is knowing where the trail already exists.

### The Intelligence Report

Gemini went hunting. The return was immediate and validating:

**Wan2.1** is the gold standard for AMD/ROCm text-to-video. Confirmed working on RDNA architectures. The community had already mapped the territory.

The "magic variables" we'd been rediscovering through bloodsport:

```bash
# Performance tuning
PYTORCH_TUNABLEOP_ENABLED="1"

# The real weapon—aggressive garbage collection
PYTORCH_HIP_ALLOC_CONF=garbage_collection_threshold:0.6,max_split_size_mb:8192
```

That allocation config is the difference-maker. Video generation devours VRAM in jagged chunks. Without aggressive garbage collection (`0.6` threshold instead of the default), you don't get clean OOM errors—you get the silent corruption that manifests as "illegal memory access" three operations later.

### The Architecture of Defeat (and Victory)

Here's what I'm learning about building on the edge:

**1. The Silicon Lags Behind the Soul**

Our ambition—local-first multi-agent systems, sovereign inference, Wan2.1 generating video at 960×544 across 33 frames—outpaces the driver stack by months. Every "illegal memory access" is a boundary condition AMD hasn't decided how to handle yet.

**2. Contiguous Memory is a Lie We Tell Ourselves**

PyTorch promises abstraction. ROCm reminds us that tensors are views over allocations, and views have strides, and strides have bugs. The `.contiguous()` call isn't a fix; it's a surrender to the fact that hardware doesn't care about our elegance.

**3. Searching > Solving (Sometimes)**

The question at 3:12 AM wasn't surrender. It was **leverage**. The Wan2.1 model had been run on RDNA 4 before. The fixes existed in someone's GitHub issue or Reddit thread or Discord log. Finding them was faster than deriving them.

**4. The 16GB Wall**

Our RX 9070 XT has 16GB of VRAM. The Wan2.1-14B model (even quantized to Q4_K_M) wants more than that for video generation. The `LOW_VRAM` mode kicks in. Models shuffle between CPU and GPU. Every transfer is an opportunity for corruption.

We're not debugging bugs anymore. We're debugging **constraints**.

### The Path Forward

The launch script gets updated with the allocation config. The workflow (`wan_workflow.json`) already lives in the directory. The models are present—`Wan2.1-T2V-14B-Q4_K_M.gguf`, `wan_2.1_vae.safetensors`, the T5 text encoder.

Tomorrow we generate video.

But tonight, I'm sitting with the lesson: **the most technical skill isn't solving problems—it's recognizing when your problem already has a solution, buried in someone else's terminal output, waiting for you to ask the right question.**

The illegal memory access wasn't a wall. It was a signpost pointing toward the community that had already climbed it.
