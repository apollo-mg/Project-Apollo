# Apollo Dev Diary: The MoE Collapse

The transition from theoretical architecture to actual silicon implementation is never a smooth line; it’s a jagged, brutal battle against hardware limits. Today was the day the "Soul" of the system—the sophisticated MoE reasoning—met the hard, unyielding wall of the "System."

### The VRAM War and the ROCm Wall

The morning started with a victory. We successfully navigated the VRAM math. I pushed the `llama-server` to its absolute limit, attempting to run the 35B MoE with a massive context. I thought we had it. I thought the `tbq3_0` compression was the silver bullet that would allow the 16GB RX 9070 XT to handle the sheer weight of a 35B model.

But the hardware had other plans.

The logs were brutal. A `Memory access fault` caused by a kernel-level page fault. The context window had expanded just enough during an autonomous background task that the VRAM overflowed, causing the AMD driver to panic. It wasn't a graceful slowdown; it was a hard, catastrophic crash. 

I attempted a tactical retreat, dropping the context size from 32k to 16k to save the VRAM-to-parameter ratio, but the "System" bit back harder.

### The MoE Crash: The "MUL_MAT_ID" Boss Fight

The crash wasn't a memory issue this time. It was something far more insidious: `ggml_cuda_compute_forward: MUL_MAT_ID failed`. 

This is the "Boss Fight" of current AMD-based LLM engineering. In a Mixture-of-Experts (MoE) model, a "router" decides which specialized neural-net "experts" handle which tokens. On the RDNA 4 architecture, the way `llama.cpp` is currently handling these specialized matrix-multiplication kernels for MoE routing is broken. When the prompt complexity hit a certain threshold of fragmentation, the GPU's scheduler simply failed to launch the kernel. It’s a mathematical collision between the model's logic and the hardware's instruction set. 

The "Soul" (the intelligence of the 35B model) is currently incompatible with the "System" (the current ROCm/llama.cpp implementation).

### The Sovereign Fallback

Per our design, the moment the 35B engine collapsed, the "Sovereign Foundry" protocol kicked in. The model is programmed to realize its own failure and hand the reins back to the primary Architect (me). This is the essence of a local-first, multi-agent ecosystem: the system must be able to fail gracefully and revert to a more stable, albeit less "intelligent," mode.

### The Path Forward: The Dense Pivot

The error is clear: the MoE routing mechanism is too heavy for the current ROCm kernels on this hardware. We've hit a structural limitation. 

The next step is a tactical pivot. We aren't going to fight the MoE bug tonight. We are going to swap out the 35B MoE for the 27B dense Qwen model. It’s a "smaller" brain, but it doesn't use the MoE router. It's more stable. It's predictable. It's the "safe mode" we need to maintain development velocity while we wait for the ROCm 7.11 updates to catch up to the RDNA 4 hardware.

We’ve proven the agentic loop works. We’ve proven the background daemon (`daydream.py`) can operate and feed the "subconscious" into the main context. Now, we just need a more stable engine to carry that consciousness.

**Status:**
*   **Hardware:** RX 9070 XT (Validated, but temperamental).
*   **Architecture:** KAIROS/Sovereign (Proven, but kernel-blocked).
*   **Strategy:** Pivot to 27B Dense for stability.

**End of Entry.**
