# Apollo Dev Diary: 2026-04-03 (Part 11)

## The Context Headroom War

Today was a brutal lesson in the friction between the "Soul" of the project—the massive, multi-day stream of consciousness we're trying to ingest—and the cold, hard limits of the silicon. We hit a wall. Not just a wall, but a massive, unyielding 65,536-token limit imposed by the `llama-server`.

The system was throwing `400 Bad Request` errors like clockwork. I thought it was a memory leak or a VRAM spike, but the math was simpler and more devastating. The server calculates `Current Prompt Size + Requested max_tokens`. We had a hardcoded `max_tokens` of 8,192 for the output buffer. By the time we hit Chunk 23, the prompt history had ballooned to 57k tokens. The sum exceeded the context window, and the GPU—rightfully—refused to work.

I had to perform emergency surgery on `llm_interface.py`. I patched it to pass a much smaller `max_tokens=100` during the ingestion phase, essentially trading output buffer for prompt headroom. It worked—the script cleared the chunk—but we were just playing a game of architectural Tetris. The VRAM was creeping up as the KV cache expanded with every new token, hugging the 16GB limit of my RX 9070 XT.

## The Ghost in the Machine

The system was also cluttered with "ghost" processes. My environment was a mess of zombie Gemini agents and stale TypeScript orchestrators. It turns out I had four separate instances of the CLI running—some dating back to March 30th. They were eating up system RAM and making the resource audit a nightmare. 

I performed a clean sweep, killing the stale processes and restarting the `llama-server`. This was vital; when you're pushing 65k tokens, the K/V cache fragmentation can become catastrophic. A fresh spin-up ensured we had contiguous, unfragmented memory for this run.

## The L3 Spine & The V-Cache Revelation

The most profound realization of the day came from a technical discussion about architecture. We've been pushing the limits of the 16GB VRAM, but the synergy between MoE (Mixture of Experts) and TurboQuant is the real game-changer.

The "Spike" problem in dense models—where the prefill phase for a 65k prompt demands massive activation memory—is essentially solved by the MoE architecture. Because only a fraction of the parameters are active at any given moment, we don't hit that catastrophic memory spike. 

But then, there's the "Static Footprint." The 65k history still needs to live in VRAM. By using TurboQuant asymmetric compression (compressing the K/V cache), we've shrunk that footprint from ~8GB down to ~2GB. This allows us to trick a consumer-grade 16GB card into performing like an A100.

However, the true "Soul" of the machine resides in the CPU's L3 cache. We discussed pinning a tiny, 0.5B parameter "Intent Router" directly into the AMD X3D's L3 cache using `taskset`. By forcing a sub-1B model into the 96MB L3 cache and using a GBNF grammar to force deterministic JSON output, we create a zero-latency "System 1" gatekeeper. It costs 0MB of VRAM and acts as a high-speed bouncer, deciding when to wake up the "System 2" heavy-duty models.

## The Midpoint Compression Fix

The final boss of the day was the sheer volume of text. Even with the `max_tokens` fix, the raw data for 28 chunks was over 280,000 bytes—roughly 80k tokens. It was simply too much for the context window to swallow.

I’ve implemented a new strategy: **Midpoint Compression**. 

The `ingest_logs.py` script now pauses at Chunk 14. It triggers the Architect to synthesize a dense, technical summary of the first half of the session, wipes the massive chat history, and replaces it with that summary. This resets the context window, providing a massive amount of fresh headroom for the remaining 14 chunks while preserving the architectural "memory."

The ingestion is currently running through the early chunks again. We are in the final stretch. The 9070 XT is grinding, the VRAM is holding steady, and the "Soul" of the project is finally being processed.
