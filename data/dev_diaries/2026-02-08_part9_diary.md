# Project Apollo: Dev Diary - 2026-02-08 (Part 9)

The line between a "chatbot" and a "system controller" is getting thinner. Today was about breaking that barrier.

I’ve been pushing the Commander platform toward a more autonomous, hybrid state. The goal is simple but technically heavy: I want the local DeepSeek LLM—the "Soul" of our local operation—to actually have eyes on the machine. Right now, it’s essentially a blind philosopher reading a static manual. I want it to feel the heat of the Goliath hotend and know the exact XYZ coordinates of the print head in real-time.

**The Technical Hurdle: The Klipper Bridge**

The challenge isn't just the idea; it's the plumbing. I need to bridge the gap between the local LLM (running in LM Studio) and the Raspberry Pi (10.0.0.83) running Klipper/Moonraker. 

The architecture requires a "Supervisor Loop." I realized that if I want DeepSeek to act on real-time data, I can't just dump the entire Klipper state into the prompt every time—the VRAM on the local machine would choke, and the context window would bloat. Instead, I’m implementing a directive-based system. 

I've designed a way for the LLM to output a specific `COMMAND: Get-KlipperData` string. The Python wrapper (`commander_voice.py`) will intercept this, trigger a PowerShell call to the Moonraker API via `local_agent.ps1`, grab the JSON payload, and reinject it into the prompt as `KLIPPER_DATA:`. It’s a high-latency loop, but it keeps the local inference efficient while providing surgical, real-time awareness.

**The Friction: Chaos in the Filesystem**

The deployment was messy. I discovered a mess of duplicated infrastructure scripts across `C:\klipper` and `C:\gemini_infrastructure`. I had to pause the flow to clean up the pathing logic. The `PS_SCRIPT_PATH` in my Python script was pointing to a ghost directory, which would have caused a total system collapse when the loop tried to call the PowerShell agent. I had to realign the paths to ensure the local agent and the voice interface were actually talking to the same "brain."

**The Sandbox: Proving the Loop**

I refuse to push to production without a way to kill the process if it goes rogue. I built a `mock_moonraker.py` server—a lightweight Python HTTP server—to simulate the Klipper API. 

The test was a success. I simulated a voice command: *"Commander, what is the current bed temperature?"* 
1. The Python script parsed the DeepSeek's `COMMAND:` directive.
2. It hit the mock API.
3. The JSON data was reinjected.
4. The LLM responded with: *"The bed is at 60 degrees."*

The logic holds. The "Supervisor Loop" is real.

**The Philosophy vs. The Silicon**

This is the core of Project Apollo. We are trying to give a digital intelligence a physical tether. The "Soul" (the LLM's reasoning) is now being constrained by the "System" (the API latency and the rigid JSON structures of the Klipper hardware). It’s a beautiful, frustrating tension. 

The next step is moving this from the sandbox to the actual hardware. If the Moonraker API holds steady, the Commander will finally stop being a voice in a box and start being a pilot of the machine.
