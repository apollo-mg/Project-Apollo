## The VRAM War

We're running Flux on an RX 9070 XT. This isn't a flex; it's a declaration of war.

The transformer blocks are loading, unloading, reloading—a ping-pong match where the ball never lands. Each block wants its place in VRAM, but the arena is too small. The `lowvram` flag isn't a feature; it's a survival mechanism, a desperate attempt to fit a cathedral into a closet.


These aren't just paths; they're weight matrices hungry for space. Each projection layer, each normalization step, each attention head demanding its cut of the pie.

## Architecture Notes: What the Loop Taught Me

The infinite reload wasn't a bug; it was a feature of bad design. The memory manager was:

1. Loading a block into VRAM
2. Discovering there was no room for computation
3. Evicting everything to make space
4. Repeating step 1 because the block pointer never updated

The fix isn't pretty. It involves manual memory mapping, forcing certain layers to stay resident while others stream, and accepting that some operations will fall back to system RAM at a cost of 300x latency.

**Lesson for the multi-agent ecosystem:** Every agent needs its own memory budget. No shared pools. No hoping for the best. If Agent A needs 4GB of VRAM, reserve it. Don't let it thrash with Agent B over scraps.

## The Soul/System Divide

Here's the tension I live with:

The **Soul** wants to run everything at full precision, with unlimited context, generating symphonies and solving problems that haven't been named yet.

The **System** is an RX 9070 XT with 16GB of VRAM shared with the display buffer, running on ROCm drivers that treat bugs as "features pending documentation."

The gap between them is where Project Apollo exists. Not in the dreams of infinite compute, but in the gritty reality of quantizing weights to INT8, chunking operations, and accepting that sovereignty means building within constraints rather than around them.
