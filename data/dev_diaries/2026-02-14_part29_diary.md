# Dev Diary: 2026-02-14 (Part 29)

## The Ghost in the Audio Stack

Today was a battle against the friction of a Linux audio subsystem. I’ve been trying to bridge the gap between the "Soul" of the project—the idea of a seamless, voice-driven existence—and the cold, unyielding "System" of PulseAudio. 

The `sounddevice` implementation was hanging indefinitely during calibration. My initial suspicion was a permission issue, but the logs suggested something more insidious: `libportaudio` was connecting to Pulse, but the stream was essentially a void. It was a silent failure. The service would hang for 40 seconds and then just die. I suspect a suspended source or a hardware-level mute on the USB mic, but in the chaos of a local-first setup, the boundary between hardware, driver, and user-space service is often a blurry mess.

I forced a service restart and a reboot to reset the stack, but that just led us into the next rabbit hole: the service came back, but it was dead.

## The Missing Pieces and the Quota Wall

The reboot revealed a massive discrepancy in the environment. The `commander.service` was pointing to a script in `/home/mark/commander`, but my working development was happening in the `infrastructure` directory. Even worse, the TTS engine (Kokoro) was throwing a fit because the `.onnx` model and the `voices.bin` files were missing from the expected path. 

It felt like I was building a house while the foundation was still being delivered by a truck that kept getting lost. I had to hunt down the correct Hugging Face URLs to manually fetch the missing weights. One link returned a 404, then another. It’s frustrating; you want to build an autonomous agent, but you spend 90% of your time just being a glorified download manager for its dependencies.

Then, the dreaded wall: API Quota Exhausted. The model hit its limit mid-diagnostic. I had to pivot to the "Auto" model just to keep the momentum, a reminder that even in a local-first dream, we are still tethered to the cloud-based intelligence that guides our development.

## The Silicon Reality: ROCm and the RX 9070 XT

Once the TTS was finally initialized—"System online"—the battle moved to the GPU. I attempted to trigger the ComfyUI/Flux workflow. This is where the "System" really shows its teeth. 

The startup script for ComfyUI is tuned for RDNA 4 stability, specifically using `HSA_ENABLE_SDMA=0` to mitigate memory errors on the 9070 XT. This is a classic case of the "Soul" (the creative desire for high-end image generation) colliding with the "System" (the current instability of ROCm drivers on cutting-edge hardware). 

The startup failed again. The logs showed a `curl` exit code 7—the server simply wasn't responding. It’s a delicate dance of managing environment variables and virtual environments. I had to manually check the `venv` binaries because the `PATH` export in the shell script was behaving inconsistently, likely trying to hit the system Python instead of the venv's local `python3.12`.

## Current Status and Path Forward

We eventually got ComfyUI to recognize the 9070 XT, but the ComfyUI-Manager is still throwing `pip` errors within the venv, suggesting a fractured environment. 

I’m currently looking at a syntax error in `generate_image.py`—a simple, stupid newline in a print statement—that killed the entire automated testing loop. I’ve fixed the string literal, but the workflow is still brittle. 

**Lessons learned:**
1. **The Audio Problem:** Moving forward, we need a more robust way to handle PulseAudio/PipeWire permissioning in user-level services.
2. **The Dependency Problem:** The orchestration of local models (Kokoro + Flux) requires a more unified "install-all" script that isn't reliant on fragile external URLs.
3. **The Hardware Problem:** The 9070 XT is a beast, but the ROCm/SDMA friction is real. We cannot treat it like a CUDA-stable environment. We have to build for the quirks of the silicon.

I'm going to try to force-start the image generation again. If we can get a single frame out of the voice command, the architecture is proven. If not, I'm going back to the `generate_image.py` source.
