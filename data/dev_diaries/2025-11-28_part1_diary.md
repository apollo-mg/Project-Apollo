# Dev Diary: The RDNA 4 Breakthrough (2025-11-28)

## The Silicon Struggle: VRAM and the "Danger Zone"
The session began with a familiar, crushing tension. I am pushing the limits of the RX 9070 XT, riding the razor's edge of 90% VRAM utilization. The architecture of the F5-TTS model—specifically its Diffusion Transformer (DiT) component—is a memory glutton. It holds onto intermediate activation maps like a digital hoarding disorder. 

I was staring at the "Danger Zone." If a batch size spike occurred due to a slightly longer audio file, the entire run would crash. We were playing a high-stakes game of resource management, hoping the stochastic nature of the training wouldn't trigger a memory overflow.

## The Crash and the Corrupted Soul
The first major setback was a brutal collision between the hardware and the software. I attempted an inference test while the training loop was still active. **Fatal Error: The VRAM could not accommodate both the training gradients and the inference-specific re-allocation.** The server died. 

But the damage went deeper. When I attempted to resume, I hit a `RuntimeError: PytorchStreamReader failed locating file data/1137`. The crash had happened mid-write, leaving `model_800.pt` as a corrupted, half-written husk of digital nothingness. 

**The Lesson:** In the local-first ecosystem, file integrity is as important as the weights themselves. You cannot trust a checkpoint that was interrupted by a hardware-level OOM (Out of Memory) error. We had to perform surgery: delete the corrupted file and backtrack to the last stable checkpoint (`model_600.pt`).

## The Golden Number: Stability via Batch Reduction
The second crash was more profound—a `c10::AcceleratorError: HIP error: an illegal memory access`. This is the ghost in the machine of RDNA 4. The ROCm driver/PyTorch interaction is still temperamental with DiT models.

I adjusted the strategy. We dropped the batch size from `2000` to `1500`. 

**The epiphany:** The lower batch size became the "Golden Number." It stabilized the memory pressure, allowing the training to bypass the illegal memory access that was killing the larger batches. We traded raw throughput for stability, and it paid off. The loss curve stabilized around `0.4 - 0.6`, and the training resumed its march toward the 100-epoch goal.

## Victory and the "Newscaster" Result
After several hours of fighting the silicon, the run completed. 100 epochs. 3,800+ updates. 

The result is nothing short of a technical triumph. The generated output (the "Black Friday" news clip) is hauntingly stable. While the training was plagued by memory errors and corrupted files, the final weights captured the nuance of the voice perfectly. The model isn't just "intelligible"—it has achieved a professional, "Newscaster" cadence that is remarkably consistent across long-form text.

## Core Lessons for the Local-First Ecosystem:
1.  **Hardware-Software Friction:** On bleeding-edge AMD hardware (RDNA 4), "Safe Mode" (disabling `torch.compile`) is not a luxury; it is a necessity. The compiler is currently too unstable for the current ROCm/PyTorch stack.
2.  **VRAM Management:** In a single-GPU setup, the "Inference vs. Training" rule is absolute. Never attempt to test the model while the training loop is holding the memory.
3.  **Data is Destiny:** The quality of the output is inextricably linked to the "cleanliness" of the input. We are seeing the limits of the $40 USB mic, but the AI's ability to bridge that gap is a testament to the power of the F5-TTS architecture.
