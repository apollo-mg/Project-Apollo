## 2025-11-29: The GELU Ghost in the ROCm Machine

The RX 9070 XT was humming, but the terminal turned red. Another `HIP error: an illegal memory access was encountered`. 

It struck during the `KSamplerAdvanced` node, deep in the stack trace at `torch.nn.modules.activation.py`, line 816. Just a simple `F.gelu` call, or so it seemed. But on this RDNA 4 silicon, with the ROCm drivers wrestling the PyTorch backend, "simple" is often a trap. The error was asynchronous, reported late, which means the kernel had already spoken before the warning reached me.

I needed to know why the memory access was illegal. Was it fragmentation? A quantization mismatch? The Soul of Project Apollo wants to run the Wan model locally, fully autonomous, without a cloud crutch. The System, however, reminds me that 16GB of VRAM is not infinite real estate. When you are managing a local-first multi-agent ecosystem, every byte of cache matters.

I drilled into `comfy/ops.py`. The culprit was the dtype handling. The standard `nn.GELU(approximate='tanh')` was fine, but the casting happened *after* the operation in some paths, causing a split in the memory layout between `MLPProj` and `text_embedding`. 

With Gemini watching the logs, we injected a custom `GELU` wrapper. Now the float32 casting happens explicitly before the activation function is invoked. It is a small change, but it unifies the operation. `MLPProj` and `text_embedding` now speak the same dtype language. No more ad-hoc casting. No more silent failures in the activation block.

The lesson is old but always relevant: consistency is the glue of local architecture. If the agents cannot agree on the memory topology, the swarm stalls. We are learning to respect the hardware limits before asking for more intelligence. 

The terminal is green again. The RX 9070 XT is green-lit. Back to generating.
