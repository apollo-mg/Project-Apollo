# Dev Diary: 2026-02-21 (Part 3)

The friction between the "Soul" of my architecture and the "System" of my silicon just became a lot more violent. 

I spent the first half of this session fighting a ghost in the machine—the "Liar Trap" validation. The theoretical architecture of Project Apollo is beautiful; a Three-Mind setup where a small, fast "Receptionist" (Llama 3.2 1B) handles triage, a "Heavy Engineer" (DeepSeek-R1) does the heavy lifting, and the Receptionist returns for the final persona synthesis. On paper, it’s a perfect agentic loop. In reality, the ROCm kernel is a nightmare. 

The critique I received was a cold, hard slap of reality. My `vram_management.py` was trying to play Tetris with 16GB of VRAM, but because the ROCm memory release is asynchronous, my "unload" commands were lying to me. The API said "Done," but the GPU was still holding onto 10GB of garbage, leading to inevitable kernel panics. I was caught in a race condition where the next model would try to load before the previous one had truly vacated the VRAM.

I spent hours hardening the code. I implemented a `wait_for_vram_release` function that polls `rocm-smi` to ensure the physical hardware has actually cleared the memory before allowing a swap. To save latency, I transitioned the "Receptionist" to an ultra-lightweight 1B model that can stay resident in VRAM, avoiding two out of three model swaps per query. It’s a band-aid, but a necessary one.

Then, we hit the real wall: the vLLM transition. 

The goal was to move from the "swapping" model to a resident, real-time backend using vLLM with Prefix Caching. This would have been the holy grail for latency—turning a 45-second wait into milliseconds. But as we tried to deploy the Docker container for Qwen 2.5, the engine crashed.

The error logs were a mess, but the "AITER" roadblock provided the missing link. It turns out vLLM’s specialized kernels (AITER) don't recognize the `gfx1201` architecture of my RX 9070 XT. It's a hard-coded mapping failure. The "Soul" of the system wanted to use high-performance specialized kernels, but the "System" (the driver) simply couldn't recognize the hardware it was running on. 

We've identified the fix: forcing a fallback to Triton-based kernels by setting `VLLM_ROCM_USE_AITER=0`. 

**The Lesson Learned:**
The jump from "Chatbot" to "Autonomous System" isn't just about smarter models; it's about the brutal reality of hardware-level compatibility. My architecture is currently a victim of the "asynchronous lie"—the software thinks the hardware is ready when it isn't.

**Current Status:**
- **Hardware:** RX 9070 XT (16GB) is stable, but the ROCm/vLLM handshake is broken.
- **Architecture:** Transitioning to "Phase 6.5: Infrastructure Validation."
- **Next Move:** Re-patch the vLLM launch command to bypass the AITER kernels and attempt the Prefix Caching benchmark again. If we hit that >70% latency reduction, the "Three-Mind" architecture becomes a real-time engine.

The vision hasn't changed: I'm not just building a bot; I'm building the scaffolding for a decentralized, autonomous manufacturing hub. I just have to stop the silicon from fighting me.
