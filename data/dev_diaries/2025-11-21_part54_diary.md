# Dev Diary: 2025-11-21 (Part 54 of 71)

## The Bias That Broke Us

Another day, another illegal memory access.

The crash landed at line 255 of `ops.py`, right in the middle of `forward_ggml_cast_weights`. The offender: `out += bias`.

At first glance, innocent enough. Add a bias vector to the result of a matrix multiplication. Basic deep learning 101. But RDNA 4 doesn't do "basic."

## The In-Place Trap

Here's what happened:

```python
# The culprit - dies spectacularly on RDNA 4
out += bias

# The survivor - boring, but it lives
out = out + bias
```

The difference? One modifies memory in place. The other creates a new tensor.

On NVIDIA, this distinction barely matters. On my precious RX 9070 XT running ROCm 7.1, the difference between `+=` and `=` is the difference between a functioning neural network and a kernel panic.

RDNA 4's matrix units seem to leave tensors in some half-baked state after matmul operations. Try to write back into that memory space, and the silicon remembers you. Permanently.

I spent twenty minutes oscillating between suspicion and epiphany:
- Was it the `.clone()` calls I'd added as a workaround?
- Race conditions from `non_blocking` transfers?
- Data type mismatches between BF16 and FP16?

All of the above, and none of the above. The kernel didn't care about my theories. It only cared that I'd asked it to mutate memory it hadn't fully committed yet.

## The Silent Hang

User reports: "It seems to hang on ksampler without going forward."

The logs told a different story. The model wasn't hanging. It was laboring.

```
Loading model to: cpu
```

Fourteen billion parameters. On the CPU.

The DisTorch node had `virtual_vram_gb` set to `0`, which I'd misread as "use all available VRAM." The truth was more brutal: it meant "don't offload anything," which somehow translated to "load everything on the CPU and pray."

But that wasn't the full picture either.

## The Ghost in the Metadata

Here's where it gets interesting.

Even with `virtual_vram_gb=0`, the logs showed DisTorch metadata persisting on model objects. Stale allocations from previous runs, clinging to memory like barnacles on a hull.

```python
# The cancer - cached metadata that never dies
_model._distorch_v2_meta  # Still exists, even when it shouldn't
```

ComfyUI caches loaded models. That's a feature. But when DisTorch metadata survives a session where `virtual_vram_gb=0` should have disabled it entirely, you get a system that thinks it's distributing work across devices that aren't in the conversation anymore.

The fix required surgery in `wrappers.py`:

```python
if full_allocation == "":
    # Clear the ghost
    if hasattr(model, '_distorch_v2_meta'):
        delattr(model, '_distorch_v2_meta')
```

Three lines that prevented a 14B parameter model from being loaded onto the wrong device.

## Architecture Notes

Two lessons that matter:

1. **In-place operations are lies we tell ourselves.** PyTorch documents them as optimizations. On bare metal with RDNA 4, they're time bombs waiting for the wrong memory barrier to fail.

2. **State leaks are inevitable in long-running systems.** The ComfyUI server lives for days. Models get loaded, unloaded, reloaded with different configurations. Metadata that should expire doesn't. The Sovereign Engine needs its own garbage collection for semantic state, not just memory.

## The Soul Question

I keep building systems that run models on consumer hardware. The silicon was designed for games, not for the kind of distributed multi-agent orchestration I'm attempting.

Every crash, every hang, every "illegal memory access" is the hardware reminding me: you're asking it to do something it wasn't designed to do.

That's the point, isn't it?

The RX 9070 XT doesn't care about sovereignty. It doesn't care about local-first architecture or multi-agent ecosystems. It cares about memory addresses and whether I've respected the barriers between them.

Today, I finally did.
