# Dev Diary: 2025-11-23 | Session 19
## The Fragmentation Wall: Fighting the Silicon

### The Ghost in the Machine
I hit the wall. Not a conceptual wall, but a hard, unforgiving, silicon-level OOM (Out of Memory) error. 

The math is brutal. My RX 9070 XT is a beast, but it’s a beast trapped in a 16GB cage. I attempted to load the Wan 2.1 14B model in its native FP8 format. The weights alone took up 12.92 GiB. PyTorch, in its infinite complexity, reserved another 2.36 GiB just for overhead and fragmentation. By the time the model was "loaded," I had exactly 230 MiB of free VRAM left. 

Then the system tried to allocate a tiny 50 MiB tensor for the actual calculation—the "activation" workspace—and the whole thing collapsed. 

This is the friction I constantly battle: the **Soul** of the project wants high-fidelity, large-scale generative intelligence, but the **System**—the cold, hard reality of my RDNA architecture—simply refuses to breathe. The model is too big to live in the VRAM, but the VRAM is too small to even allow the model to *think*.

### The Fragmentation Epiphany
I realized that my issue wasn't just capacity; it was management. The RDNA 4 architecture is temperamental. It handles "almost full" memory states like a pressurized vessel—one small tremor and it explodes (or hangs). The 2.36 GiB of fragmentation was a death sentence. 

I had a choice: 
1.  **The DisTorch Gamble:** Try to use complex multi-GPU/partial-offloading logic to pin 80% of the model to VRAM. But if the fragmentation wall is as volatile as I suspect, DisTorch might just trigger a crash anyway.
2.  **The Low-VRAM Baseline:** Revert to the simpler `--lowvram` strategy. 

I chose the latter. It’s the "safe" play, but it carries a heavy bandwidth tax. However, there's a silver lining: because we are using the native FP8 weights (13GB) instead of the FP16 behemoths (28GB), the PCIe bus won't have to work twice as hard. We are trading raw throughput for manageable data streams.

### The Architecture Shift
I’ve implemented a three-pronged tactical adjustment in `run_wan_safe.sh`:

*   **`--lowvram`:** We are moving to a streaming architecture. The model lives in System RAM, and we feed it to the GPU in chunks.
*   **`expandable_segments:True`:** This is my primary weapon against the fragmentation wall. By forcing the PyTorch allocator to use expandable segments, we are attempting to prevent the memory from "shattering" into unusable pieces.
*   **`HSA_ENABLE_SDMA=1`:** I'm forcing the AMD Software Defined Memory Access to ensure that the transfer between RAM and VRAM is as fast as the hardware allows.

### The Mission Critical Test
I am currently monitoring the first generation under this new regime. This is the "Goldilocks" test. 

If this configuration succeeds, we have found the sweet spot for the local-first ecosystem: a way to run 14B parameter models on consumer-grade 16GB hardware without the catastrophic performance degradation seen in GGUF offloading. 

If the KSampler stays under 2s/it, we've cracked the code for high-speed, local-first video generation on mid-tier hardware. If it hangs on the VAE, then the RDNA memory management is fundamentally incompatible with this scale of model, and I'll have to reconsider the entire quantization strategy.

**Current Status:** *Watching the logs. Waiting for the silicon to decide if it wants to cooperate or die.*
