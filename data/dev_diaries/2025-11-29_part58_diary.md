# Dev Diary: 2025-11-29 // The Triton Wall

## The Ghost in the Silicon
I thought I had tamed the RX 9070 XT. I thought the 17GB of VRAM was a wide enough playground for the *Wan* architecture to dance in. I was wrong. 

Today, the "System" fought back with a violence that felt almost sentient. I was pushing the limits of the *Wan* model—a beautiful, complex beast of a transformer—when the kernel hit a wall. Not a software wall, but a hard, physical-feeling limit of the ROCm implementation.

`torch.AcceleratorError: HIP error: an illegal memory access was encountered.`

That error message is the digital equivalent of a seizure. It’s the sound of the hardware losing its grip on reality.

## The Anatomy of the Crash
The stack trace is a graveyard of failed optimizations. I was attempting to leverage `flash_attn_triton_amd`. It’s a high-performance, low-latency dream, designed to make attention mechanisms lightning-fast by bypassing standard memory overhead. But the Triton kernel—the very heart of the speed—is where the "illegal access" lives.

I suspect a fundamental misalignment. The *Wan* model's attention mechanism is producing tensors—`q`, `k`, `v`—that are likely non-contiguous or have strides that the Triton kernel's current AMD-specific implementation cannot map correctly to the hardware's memory addresses. 

The error is persistent. Even when the system tried to fall back to standard `SDPA` (Scaled Dot Product Attention), the kernel-level corruption was already so deep that the GPU context was effectively poisoned. The "System" had locked up.

## Soul vs. Silicon
There is a profound friction here. The "Soul" of this project—the creative potential of the *Wan* model—wants to generate high-fidelity, complex latent spaces. It wants to explore the infinite. But the "System"—the ROCm driver, the Triton kernel, the physical memory layout—is a rigid, unforgiving master. 

The model is ready to create, but the silicon is too brittle to support its complexity. We are trying to build a cathedral of intelligence on a foundation of experimental drivers.

## Architectural Epiphany: The Fragmentation Trap
Looking at the memory logs, I see the shadow of the struggle. The `DisTorch2` layer distribution was attempting to shard the model across CPU and GPU, but the `forced_soft_empty` trigger suggests the memory management system is panicking. 

The VRAM is being fragmented by the constant swapping of weights between the 17GB of VRAM and the system RAM. We are hitting a "Memory Wall" where the overhead of managing the memory is actually consuming more resources than the computation itself. 

The lesson is clear: **Local-first multi-agent ecosystems cannot rely on high-level, monolithic optimizations like Flash Attention if they aren't perfectly aligned with the underlying hardware's memory-stride requirements.**

## The Path Forward
I am pivoting. I need to strip the complexity. 

1.  **De-optimize to Stabilize:** I’m going to disable the Triton Flash Attention backend entirely. I'll force the system to use the default PyTorch SDPA path. It will be slower, but it will be predictable.
2.  **Contiguity Check:** I need to implement a manual `tensor.contiguous()` check before the attention call in the `Wan` model's forward pass. If the issue is indeed a memory stride mismatch, this will be the surgical strike that fixes it.
3.  **Memory Isolation:** I need to rethink the `lowvram` and `reserve-vram` parameters. The current fragmentation is too aggressive.

The engine is stalling, but the blueprints are still sound. I just need to stop trying to run a marathon on a broken track.
