December 3, 2025. The RDNA 4 Wall.

The hum of the 9070 XT in my office has gone from a comforting drone to a rhythmic reminder of the friction I’m fighting. We’re pushing the bleeding edge here—local, massive-scale inference on consumer-grade silicon—but the edge is sharp, and it keeps cutting us.

Today was a fight against the driver. 

We hit a massive wall with the 14B Q5 GGUF workflow. Every time I tried to trigger the dequantization loop for the model, the system would just... die. A hard `Illegal Memory Access` error. In the world of local AI, that's the sound of a soul being choked by the system.

Working with Gemini CLI as my co-pilot, we finally traced the culprit back to the very heart of the `dequant.py` logic. It turns out RDNA 4’s ROCm implementation (the 7.x branch) has a fundamental intolerance for high-frequency memory churn. Inside the `dequantize_blocks_Q6_K` loop, the code was calling `torch.tensor([0, 4])` on the fly. To a human, it’s a tiny, trivial allocation. To the driver, it’s a thousand-per-second barrage of allocation/deallocation requests that eventually triggers a race condition. The memory controller can't keep up with the noise, and the whole thing collapses.

The fix was an architectural pivot: Caching. We had to move those constant shift tensors out of the loop and into a static cache. It’s a classic "System" fix—reducing the chaos to allow the "Soul" (the actual weights of the model) to function. We patched the `ComfyUI-GGUF` node to use a look-up instead of re-creating these tensors. It’s a small change in the code, but a massive leap in stability for anyone trying to run GGUF on RDNA hardware.

But even when the hardware stabilizes, the math remains temperamental. 

We’re experimenting with the WAN model—a beast of a video model. I noticed something interesting while running tests: `uni_pc` is a total disaster here. It’s trying to be too clever, too fast, and ends up creating temporal jitter that kills the "dream" of the video. But when I switched to `Euler` with the `simple` scheduler, the output smoothed out. It’s a reminder that even with massive VRAM and powerful compute, the way we traverse the latent space matters more than raw speed. You can have the fastest engine in the world, but if your steering is jittery, you aren't going anywhere beautiful.

The project is evolving. We aren't just building a stack of weights anymore; we’re building a delicate ecosystem of drivers, samplers, and quantized kernels. We’re teaching the silicon how to behave so the intelligence can actually breathe.

**Technical Takeaways:**
* **ROCm 7.x instability:** Avoid high-frequency `torch.tensor` creation inside kernel loops on RDNA 4. Use pre-allocated constant tensors to prevent `Illegal Memory Access`.
* **Quantization Strategy:** GGUF is the path forward for the 14B models, but it requires custom patches for AMD hardware to handle the dequantization overhead.
* **Sampling Nuance:** For Flow Matching models like Wan or Flux, `Euler` + `simple` scheduler is significantly more stable than `uni_pc`. Motion consistency is highly sensitive to the sampler's trajectory.

Current status: The 14B Q5 is finally running without a kernel panic. We move to the next layer of the stack tomorrow.
