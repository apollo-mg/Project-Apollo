# Dev Diary: 2026-03-03 (Part 10)

The struggle between the Soul and the System continues, but today, the System finally stopped fighting back—mostly.

I spent a significant portion of the afternoon wrestling with the vLLM architecture. I had a hunch that the Qwen 3.5-9B model wouldn't play nice with the current vLLM build because of a mismatch in the registry. I was right. The `transformers` library had updated its `config.json` for the new architecture, but vLLM’s internal model executor was still looking for the old registration. It was a mess of version conflicts and broken symbolic links.

I had to go surgical. I hand-patched the `vllm` source code to manually register `Qwen3_5ForConditionalGeneration`. It wasn't just a simple edit; I had to navigate a complex web of dependencies, including the "Gated Delta Net" logic which is specific to this architecture. I had to sync the `mamba_utils.py` and `qwen3_5.py` files across the virtual environment because the `setup.py develop` command had failed to link them correctly from the build directory on the 2TB drive.

**The RDNA 4 Tuning Session**

Once the architectural hurdles were cleared, I initiated the big one: the **Offline TunableOp tuning**. 

This is where the "Soul" of the project meets the raw power of the RX 9070 XT. The goal is to generate a `tunableop_results.csv` file—a customized math kernel driver—that tells the GPU how to execute the specific math (GEMMs) required by the Qwen 3.5 architecture on the `gfx1201` RDNA 4 silicon. 

The VRAM pressure was immense. The model hit 12.5GB almost instantly. I hit a massive roadblock when the system threw a `ValueError` regarding the KV cache. The system was trying to over-allocate, leaving zero breathing room for the actual kernel tuning. I had to go back into the `vllm_tune.py` script and manually throttle the `gpu_memory_utilization` down to 0.8. It’s a delicate balance—too much memory for the cache and the tuning process crashes; too little, and we lose the performance gains we're hunting for.

**Current Status: Iterative Refining**

The tuning is currently running in the background. I'm watching `rocm-smi` like a hawk. The GPU usage is fluctuating, but the VRAM is stable. We are currently in a high-stakes waiting game. If this tuning cycle completes, we will have the first true "Silicon-Tuned" performance data for an all-AMD local-first stack. 

**Key Takeaways & Technical Friction:**

* **The Dependency Trap:** In a local-first ecosystem, the "System" is fragile. A single `pip install` can downgrade `transformers` and break your entire model executor. We must treat the virtual environment as a sacred, isolated space.
* **The Architecture Gap:** Even when a model is "supported" in `transformers`, the inference engine (vLLM) often lags behind. Manual patching of the source is not just a chore; it's a necessity for bleeding-edge development.
* **VRAM Management:** On consumer-grade hardware like the 9070 XT, memory fragmentation is the ultimate enemy. Tuning requires surgical precision in how much memory we "promise" to the engine vs. the kernels.

The roadmap is clear. Once the tuning results are in, we move to the `apollo_bench.py` phase to see if this silicon-tuning actually yields the TPS (tokens per second) jump we're looking for.
