# Project Apollo: Dev Diary
## 2025-11-21 — The Day the Silicon Rejected Me

The RX 9070 XT blinked back at me from the terminal output: **16GB of VRAM**, pristine and untouched, and yet completely useless.

That's the joke of local-first AI development, isn't it? The hardware sits there like a promise kept and broken simultaneously. I have the memory. I have the compute units. I have the ambition to run a 14B parameter video generation model on bare metal AMD silicon.

I just don't have the dequantization kernel that doesn't segfault.

---

## The Autopsy

The crash landed at line 269 of `dequant.py`, in the most humble of operations:

```python
return (d * qs - dm).reshape((n_blocks, QK_K))
```

A multiplication. A subtraction. A reshape.

And there it was: `HIP error: an illegal memory access was encountered`.

The Q4_K quantization block—the workhorse of GGUF compression, the reason we can even dream of running 14B parameter models on consumer hardware—refused to cooperate. Not with a graceful OOM. Not with a timeout. With a flat refusal to acknowledge that the memory it was reaching for actually existed in any universe where math was consistent.

**The suspicious details:**
- AMD arch: `gfx1201` — RDNA 4, barely out of the factory
- ROCm version: 7.1 — bleeding edge, which means "bleeding" is in the feature set
- PyTorch: 2.8.0+rocm7.1.0 — custom builds, because stable releases are for people who don't live here
- The model loaded *partially*: 9252 MB usable, 9251 MB loaded, 84 MB offloaded to RAM like a refugee

The kernel panicked somewhere in the space between quantized weights and reality.

---

## The Soul vs. The Silicon

Here's what keeps me up at night, the actual philosophical problem buried in these stack traces:

**The Soul of Apollo** says: *Run the model. Generate the video. The agents need to see what they're talking about. Creativity requires fidelity, and fidelity requires compute, and compute requires that this multiplication operation not decide to access memory address 0xDEADBEEF.*

**The System** says: *You asked for Q4_K quantization on a gfx1201 GPU with ROCm 7.1, which means your dequantization kernel is running on hardware that was designed six months ago, drivers written three months ago, for a PyTorch backend that considers AMD "experimental." You wanted sovereignty? Sovereignty is 16GB of VRAM watching you fail to multiply two tensors.*

The friction isn't a bug. It's the feature.

---

## What Actually Happened (Technically)

The Wan 2.1 14B model loaded in a hybrid nightmare:
- **F16 weights**: 694 blocks (the safe parts)
- **Q4_K weights**: 280 blocks (where we died)
- **Q6_K weights**: 120 blocks (waiting in the wings)
- **F32 weights**: 1 block (probably a bias term, living its best life)

The crash occurred during the `KSamplerAdvanced` node's first denoising step, when the GGUF dequantizer tried to materialize Q4_K weights on-the-fly. The operation `d * qs - dm` — where `d` is the scale, `qs` is the quantized block, and `dm` is the minimum — should have been trivial.

Instead, it walked into memory that didn't belong to it.

The `AMD_SERIALIZE_KERNEL=3` suggestion in the error is a joke we tell ourselves. It's like suggesting you defuse a bomb by apologizing to it.

---

## The Lesson (If There Is One)

**Lesson 1: Quantization is not a solved problem on AMD.**

The GGUF ecosystem optimized for CUDA first, ROCm second, and "someday we'll get to the edge cases" third. The Q4_K dequantization kernel assumes memory layouts that work on NVIDIA's page-aligned heaven but fracture on AMD's more... creative address space.

**Lesson 2: Partial loads are not stable states.**

The model loaded "partially" — 9251 MB in VRAM, 84 MB offloaded to system RAM. Somewhere in that boundary condition, in the handoff between GPU and CPU memory, the dequantization kernel lost track of which universe it was operating in.

**Lesson 3: The agents need smaller dreams, at least temporarily.**

If Apollo's multi-agent ecosystem wants to generate video, it needs to either:
- Accept FP16/F32 only for now (wasting 70% of my VRAM)
- Switch to Q6_K (which loaded but hasn't been tested)
- Or accept that some operations will require a CUDA GPU as a backend

None of those options feel like sovereignty. But they're the options.

---

## The Path Forward

I'm considering three paths:

1. **The pragmatic surrender**: Force FP16 for the Wan model, accept the 8GB VRAM footprint, and live with the memory constraints. The agents generate less video, but they generate *something*.

2. **The kernel dive**: Recompile PyTorch with `TORCH_USE_HIP_DSA` enabled, enable device-side assertions, and actually find out *where* the illegal access is happening. This could take weeks.

3. **The architectural pivot**: Design Apollo's video generation as an optional service, something that can run on a remote CUDA backend when needed. This feels like betrayal. But is it?

I haven't decided. The terminal is still open. The RX 9070 XT is still waiting.

Somewhere in there is a lesson about sovereignty, about the cost of running local, about the gap between the vision of decentralized AI and the reality of memory-mapped I/O on consumer hardware.

I just haven't written it down yet.
