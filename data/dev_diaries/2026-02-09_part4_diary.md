# Project Apollo: Dev Diary | 2026-02-09

## The Ghost in the Context

Today was a brutal lesson in the friction between high-level intelligence and low-level silicon constraints. I spent most of the afternoon locked in a recursive loop with the Gemini CLI, battling a persistent, maddening error: `Cannot read properties of undefined (reading 'candidates')`. 

It’s a clinical-sounding error, but in practice, it felt like the system was choking on its own vomit. Every time the model attempted to generate a response or process a large tool output, the client-side rendering would collapse. It turns out the "Soul" of the AI—its reasoning and ability to parse complex instructions—was being strangled by the "System." The context window was being bloated by massive, un-ignored directories like `pi_mirror` and huge log files, creating a massive data footprint that the CLI couldn't handle during the response phase.

I tried every aggressive context-reduction trick in the book. I updated `.geminiignore` to exclude everything from `.onnx` files to massive `.csv` and `.json` dumps. I even tried deleting the `pi_mirror` directory entirely to strip the context back to the bone. But the crash persisted. It was a feedback loop: the model would try to act, the output would be too large, the context would overflow, and the API would return a malformed response that lacked the expected 'candidates' property, triggering the crash.

It’s a sobering reminder: a local-first agentic ecosystem is only as stable as its context management. If you can't prune the environment, the intelligence becomes a liability rather than an asset.

## The BDsensor Mystery

Once I stabilized the CLI by forcing extremely minimal, text-only responses, I was able to pivot back to the primary mission: debugging the probe calibration failure.

The hardware setup is... unconventional. We've swapped out the standard Eddy sensor for the `BDsensor` setup, and it seems we've hit a critical failure point in the Klipper integration. The user reported that the `PROBE_CALIBRATE` command was failing, and after digging into the `printer.cfg` via the agent, the truth became clear.

The `SAVE_CONFIG` block is missing.

In Klipper, when you run a calibration, the system attempts to append the new values to the end of the config file. My analysis of the file timestamps and sizes showed that the `SAVE_CONFIG` operation on the `BDsensor` had likely hung, leaving the main `printer.cfg` truncated or corrupted, while the `.bak` file still held the old, intact configuration. 

The disconnect is glaring: the `BDsensor` is acting as a probe, but it isn't fully support the standard Klipper `PROBE_CALIBRATE` workflow. We're seeing a collision between the new sensor's logic and the legacy command structure. The `collision_calibrate` setting is enabled, but without a proper `[probe]` definition, the system is essentially blind during the homing process.

## Architectural Lessons

The day's chaos taught me two things for the future of Project Apollo:

1. **Context is a finite resource, even in "large window" models.** When working with local-first agents, the "ignore" patterns aren't just suggestions; they are critical system parameters. We need more robust, automated context pruning that doesn't rely on the AI to fix itself.
2. **The Agent-Hardware Gap.** There is a massive, unmapped territory between the AI's high-level command (e.g., "Calibrate the probe") and the messy, stateful reality of hardware firmware. The AI can see the config file, but it can't easily see the "hang" that happens mid-write unless we build better telemetry into the bridge.

The printer is stable, the bed is at 65C, and the CLI is finally breathing again. But the gap between the sensor's logic and the Klipper core is still a chasm. Tomorrow, we dive into the `BDsensor.py` logic to see why it's breaking the `SAVE_CONFIG` routine.
