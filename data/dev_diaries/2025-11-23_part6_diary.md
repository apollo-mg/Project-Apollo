# Dev Diary: The SDMA Sabotage (2025-11-23)

## The Ghost in the Silicon: The RMSNorm Crash
The "Soul" of the project—the creative potential of the Wan model—is currently being strangled by the "System." I was attempting to push the limits of the RX 9070 XT, trying to leverage its native FP8 capabilities to squeeze more intelligence into a smaller VRAM footprint. Instead of progress, I hit a wall of pure, unadulterated digital chaos.

The error: `HIP error: an illegal memory access was encountered`. 

It didn't happen during a heavy compute phase, but right at the onset of the sampling loop, specifically during the `rms_norm` calculation. In the architecture of a transformer, RMSNorm is a fundamental gatekeeper. If the weights are corrupted, the math explodes. If the memory access is illegal, the hardware simply gives up.

## The Forensic Autopsy
I've been staring at the stack trace. The crash is occurring inside `comfy.rmsnorm.rms_norm`. 

I had two suspects:
1.  **The SDMA (System DMA) theory:** I enabled `HSA_ENABLE_SDMA=1` to speed up data transfers. But on RDNA 4 architecture, SDMA is notoriously temperamental with current ROCm drivers. If the DMA transfer corrupted the weight tensors during the `lowvram` offloading/loading cycle, the RMSNorm kernel would be trying to process garbage data, leading to an illegal memory access.
2.  **The Memory Fragmentation theory:** I was using `expandable_segments:True` to fight fragmentation, but combined with `--lowvram`, the memory allocator might be playing a dangerous game of musical chairs with the VRAM, causing the kernel to look for a memory address that no longer exists or has been reallocated.

The logs show the model loading successfully—`10330.69 MB loaded`—but the moment the first kernel tries to touch that data, the whole pipeline collapses. This points heavily toward **data corruption during the load**. The SDMA is likely the saboteur.

## The Friction of Progress
There is a deep, frustrating tension here. To achieve the "Local-First" dream, we need speed. We need SDMA. We need FP8. But the hardware is currently too "unstable" to support the very optimizations that make it useful. 

If I disable SDMA, the model will load at a snail's pace. It will feel like the machine is dying. But if the machine is dying, it can't create. I'd rather have a slow, living engine than a fast, dead one.

## The Architectural Pivot
We are shifting our strategy from **Maximum Throughput** to **Maximum Stability**.

**The Plan:**
*   **Kill SDMA:** Set `HSA_ENABLE_SDMA=0`. We'll trade transfer speed for data integrity.
*   **Increase the Buffer:** Bump `--reserve-vram` from 1.0 to 3.0. We need to give the system more breathing room to prevent the allocator from tripping over itself while the SDMA-less transfer happens.
*   **Maintain `expandable_segments`:** We keep this to manage the fragmentation, even if it's a potential culprit.

## Core Lessons for the Multi-Agent Ecosystem
This isn't just about one model; it's about the entire local-first ecosystem. If we want agents to run on consumer-grade AMD silicon, our orchestration layer must be "hardware-aware." We cannot assume a stable memory environment. Our agent-management logic needs to account for the fact that the driver might lie to us, or the memory might be corrupted mid-flight. 

The "System" is not a constant; it is a volatile, shifting landscape. We must build the "Soul" to be resilient to the "System's" failures.

**Next Step:** Re-run the script with SDMA disabled. Let's see if the ghost is finally exorcised.
