# Dev Diary: The Aluminum Pivot

The transition from "theoretical" to "real-world" is never a straight line. Today was a brutal reminder that physics doesn't care about my elegant code.

I spent the last several hours wrestling with the mechanical instability of the printer. The Carbon Fiber (CF) tube gantry was a nightmare—it was acting like a tuning fork, vibrating at 60 Hz and creating a torsional twist that no amount of software could fix. I realized that while the CF was light, it lacked the structural rigidity to resist the rotational forces of the CoreXY motion. The "Soul" of the machine wanted to be fast, but the "System" (the physical frame) was too flimsy to support it.

The decision to swap to Aluminum 2020 extrusion was a calculated risk. It added mass, and in a world of high-speed motion, mass is usually the enemy.

The data from the EBB36 sensor doesn't lie. The shift was massive. The total vibration energy dropped by 80%. By replacing the hollow CF tube with the rigid aluminum, I killed the torsion. The frequency shifted, but it became a clean, predictable, linear vibration. It’s the classic engineering trade-off: I traded a little bit of theoretical acceleration (dropping from 10.8k to 10.1k mm/s²) for absolute mechanical stability. In local-first robotics, stability is more valuable than a 6% speed boost you can't actually utilize.

Working with Gemini via the CLI today felt different. The friction between the model's reasoning and the raw terminal output was palpable. I had to steer it through a complex workflow: using `scp` to pull remote graph data, then hitting it with `ffmpeg` to resize and compress the images because the VRAM/memory constraints on my local environment make handling raw high-res PNGs a slog. 

We hit some snches with the shell commands—trying to use `&&` in a PowerShell context caused a syntax crash—but we pivoted to using semicolons and separate tool calls. It’s a reminder that even when we're building high-level multi-agent ecosystems, the low-level execution (the "System") still requires a human-like understanding of the environment.

The machine is now a predictable workhorse. The `AXES_MAP_CALIBRATION` is next. If the noise floor stays below 50 mm/s², we have successfully bridged the gap between the digital model and the physical reality.

**Core Lessons:**
- Stiffness > Mass (up to a point).
- Stability is the foundation of speed; without it, high acceleration is just expensive noise.
- The interaction between high-level LLM reasoning and low-level system constraints (VRAM, file formats, shell syntax) is where the real development happens.

**Next Step:** 
Run `VIBRATIONS_CALIBRATION` to find the speed-limit heat map. If the frame is silent at 120mm/s, we are ready for production.
