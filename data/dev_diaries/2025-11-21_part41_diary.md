## The Illusion of Plenty

The terminal greeted me with a lie.

```
VRAM Total: 17095983104 bytes
VRAM Free: 16997416960 bytes
```

Sixteen gigabytes. All of it available. The RX 9070 XT sat there, grinning its synthetic grin, promising me everything.

I wanted to run Wan2.1-T2V-14B through ComfyUI at 832×480, batch size 17, and generate video. Not images—*video*. Moving pictures. The kind of thing that makes people think you're building something alive.

The kind of thing that makes you question what you're doing when the silicon says **no** in the most elegant way possible.

---

## The Error That Broke Me (For About Ten Minutes)

```
torch.AcceleratorError: HIP error: an illegal memory access was encountered
```

Beautiful, isn't it? Not "out of memory." Not "this operation failed." No—*illegal memory access*. The GPU didn't just refuse me; it called security.

The stack trace leads to `/comfy/ops.py:302`:

```python
out = torch.zeros_like(input)
```

A *zeros* operation. The most innocent tensor operation in existence. And yet, somewhere in the dark between the Python interpreter and the RDNA4 compute units, something went wrong. Something fundamental.

The HIP driver doesn't panic. It doesn't yell. It simply returns this polite notification that I've tried to touch memory that doesn't belong to me.

---

## The Architecture That Got Us Here

Let me tell you what I was trying to do, because the ambition itself is half the problem.

**DisTorch2**—my distributed Torch patcher—was doing its dance. The logs show it:

```
DisTorch2 Model Virtual VRAM Analysis
Object   Role   Original(GB)   Total(GB)   Virt(GB)
cuda:0   recip      15.92GB      25.92GB    +10.00GB
cpu      donor      31.26GB      21.26GB    -10.00GB
```

I was creating a *virtual* VRAM layer. Telling the system it had 25.92GB when it physically possessed 15.92GB. Borrowing 10GB from system RAM, pretending the boundary between CPU and GPU memory didn't matter.

It's a lie. A beautiful, necessary lie.

The Wan2.1 model, quantized to Q4_K_M, wanted 9.7GB loaded. The CLIP encoder (umt5_xxl_fp8_e4m3fn_scaled) wanted another 6.4GB. Batch size 17 at 832×480 resolution wanted... well, I don't know what it wanted. It just wanted *things*.

And then the sampler started.

---

## The Friction Point

Here's what I think happened, and it's the kind of thing that keeps me up at night:

The DisTorch2 layering created a memory mapping that *looked* valid at load time. The model loaded. The layers distributed. The logs even said:

```
[MultiGPU DisTorch V2] DisTorch loading completed.
[MultiGPU DisTorch V2] Total memory: 6419.48MB
```

But then the KSampler started iterating. DPM++ 2M, 30 steps, cfg=6. Each step requires forward passes through the UNet, and each forward pass allocates intermediate tensors.

At step 0, everything was fine.

At step... who knows? The HIP error is *asynchronously reported*. The stack trace might be wrong. The kernel that actually failed might have been a different kernel entirely.

```
HIP kernel errors might be asynchronously reported at some other API call,
so the stacktrace below might be incorrect.
```

Even the error message doesn't trust itself.

---

## What I Know Now

1. **The 16GB RX 9070 XT is not enough for Wan2.1-T2V-14B at batch size 17.** I knew this intellectually. I didn't know it *viscerally* until the silicon told me.

2. **DisTorch2's virtual VRAM layer is too optimistic.** It promises mappings that don't survive the stress of actual computation. The model loads because loading is lazy. The model fails because sampling is *eager*.

3. **The `torch.zeros_like()` failure is a symptom, not a cause.** Something earlier corrupted memory, or allocated incorrectly, or tried to use a tensor that had already been freed. The zeros operation just happened to be the first thing that noticed.

4. **ROCm 7.1.0 on RDNA4 is still bleeding edge.** The ComfyUI-GGUF notes say it's "force disabling torch.compile for stability on RDNA 4." I should have read that more carefully.

---

## The Fix (For Tomorrow)

I'm not done with today. I'm not done with this session. I'm just done with *this configuration*.

**Tomorrow's approach:**

- Reduce batch size to 4, then 2, then 1. Find the floor before the ceiling breaks.
- Enable `AMD_SERIALIZE_KERNEL=3` to see if synchronous kernel execution exposes the real failure point.
- Recompile PyTorch with `TORCH_USE_HIP_DSA` for device-side assertions. I want to know *exactly* where memory goes wrong.
- Consider whether DisTorch2's virtualization is compatible with the GGUF loader's own memory management. They might be stepping on each other's toes.

**The philosophical question remains:** How much of this is engineering, and how much of it is hubris?

I wanted to run a 14-billion parameter video generation model on consumer hardware and call it "local-first." I wanted sovereignty. I wanted the silicon to bow.

Instead, I got an illegal memory access error.

And you know what?

*I respect it.*

---

## Notes for the Ecosystem

For anyone else building in this space, reading these logs:

- **The error logs don't lie, but they don't tell you everything either.** The asynchronous nature of HIP errors means the blame can be misattributed. Trust the symptom, investigate the cause.

- **Virtual VRAM is not actual VRAM.** Memory mapping tricks work until they don't. The first production workload that exceeds your physical limits will find you.

- **ROCm is not CUDA.** Not in driver maturity, not in error reporting, not in the way it chooses to break when you push too hard.

- **Batch size is the silent killer.** You can optimize your quantization, your layer distribution, your memory patching—but if your batch size assumes infinite memory, you will fail. Spectacularly.
