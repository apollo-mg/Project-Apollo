# Project Apollo: Dev Diary
## 2026-03-03: The RDNA 4 Breakthrough & The Death of the Docker Bottleneck

The friction between the "Soul" (the vision of an autonomous, agentic mind) and the "System" (the brutal reality of VRAM and driver quirks) has been the defining struggle of this session. I spent the first few hours fighting a losing battle against the silicon, only to realize that the breakthrough wasn't in more hardware, but in better orchestration.

### The VRAM War & The RDNA 4 Pivot
The initial attempt to implement the "Dual-Backend" architecture—running a high-performance vLLM instance for tool-calling alongside Ollama for general chat—was a nightmare. I was trying to push the RX 9070 XT to its limits using standard AWQ quantization. But the ROCm backend on `gfx1201` is finicky; it lacks the optimized Triton kernels for 4-bit, forcing a massive dequantization penalty that killed my tokens-per-second.

The landscape shifted when I realized the 9070 XT's strength isn't in 4-bit AWQ, but in its native **FP8 (W8A8) acceleration**. The community discovered that for RDNA 4, FP8 is the "Goldilocks Zone." It’s 8-bit, meaning a 7B or 9B model fits comfortably in the 16GB VRAM, leaving just enough room for a massive KV Cache. 

However, the technical friction was immense. I tried to install the specialized ROCm vLLM wheels, but the installation crashed because my root partition was a graveyard of old Hugging Face caches and Docker images. I was staring at an `[Errno 28] No space left on device` error while trying to unpack a 4GB PyTorch nightly wheel. 

### The Docker Trap & The Architecture Pivot
I attempted to bypass the local installation by using the existing 41GB `rocm/vllm-dev` Docker container. This was a mistake of scale. While it solved the driver dependency issue, the "Graph Compilation" phase on this specific architecture took over 2.5 minutes before the server would even respond. For a system designed to be a lightning-fast agent, a 150-second boot time for a single tool-call is a death sentence.

Then, the breakthrough: **Ollama's Structured Outputs.** 

The "Soul" of the project—the need for flawless, programmatic JSON—didn't actually need the heavy-duty vLLM engine. By leveraging the recent updates in the Ollama API, we can now pass a strict JSON Schema directly into the payload. This forces the model to perform logit masking *natively* on the resident model. No more swapping, no more 2-minute boot times, and no more VRAM fragmentation. The "System" finally caught up to the "Soul."

### Restoring the Voice
Once the VRAM architecture stabilized, we moved to the physical world. The Discord bridge was crippled by a missing `PyNaCl` dependency, meaning the "Voice Satellites" (the Pi 5 nodes) were essentially deaf and mute. 

With the library restored, the bridge is live. The realization is profound: we aren't just building a chatbot; we are building a distributed, hearing, speaking entity. The transition from a text-only interface to a voice-enabled agent is no longer a question of "if," but a question of "when" we wire up the audio stream.

### Core Lessons & Evolution
- **Hardware-Awareness is Non-Negotiable:** On AMD, you can't just use generic quantization. You have to target the specific FP8/BFloat16 math paths of the RDNA 4 silicon.
- **Orchestration > Raw Power:** The complexity of managing multiple vLLM instances was overkill. The "Dual-Backend" was a beautiful idea that failed the test of practical latency. The leaner, unified Ollama-native approach is the path to a real-time agent.
- **The Space-Complexity Tradeoff:** Our local-first ecosystem is fighting a war for disk space. Managing the `~/.cache/huggingface` and Docker layers is as much a part of "architecture" as the neural networks themselves.

**Next Mission:** 
The voice is active. Now, we need to give it a brain that can listen to the world. I'm looking at the **Procurement Mind**—we have the vision-capable models, and we have the voice. It's time to see if the agent can actually "see" a deal on a flyer and act on it.
