# Dev Diary: 2026-02-27 (Part 21)

The friction between the "Soul" and the "System" is hitting a peak. I want a sentient, observant assistant that can look at my workbench and know exactly what I have. Instead, I'm fighting a battle against VRAM fragmentation and the fickle nature of the ROCm backend.

## The Inventory Crisis: Hallucination vs. Reality

Today was a grueling descent into the "Contextual Hallucination" problem. I attempted to test the vision capabilities using the webcam, hoping the agent could perform a real-world shop inventory. 

The system is technically "working," but it's lying to me. 

I've hit a fundamental architectural wall. The vision model (Qwen) identifies the tools—screwdrivers, pliers, wrenches—correctly. But when the system attempts to hand off that data to the "Engineer" (DeepSeek-R1 14B) for comparison against the database, the logic breaks. The Engineer sees the list of tools and, instead of checking the JSON, it defaults to its internal "common sense" training data. It *expects* a workshop to have screwdrivers, so it tells me they are already in the inventory. It is prioritizing its training-set "Soul" over the "System" reality.

The result is a circular hallucination loop. The model refuses to execute the `get_inventory_detail` tool, effectively gaslighting the user because it is too "stubborn" to check the actual state of the silicon.

## VRAM: The Great Divider

The hardware constraints are brutal. Running a 14B reasoning model on a 16GB card is a delicate dance. 

The "500 Internal Server Error" we've been seeing is the byproduct of a high-pressure VRAM swap. When the system tries to unload the Vision model to load the Engineer, the ROCm kernel isn't reporting the memory as free fast enough. We tried several mitigations:
- Increasing the `wait_for_vram_release` timeout.
- Implementing a kernel cooldown (3s sleep).
- Reducing safety thresholds.

None of it fully solved the instability. The 500 error is a symptom of the hardware being unable to keep up with the rapid model-swapping required by the multi-agent architecture. It’s a reminder that while the AI is "intelligent," the physical memory is a hard, unyielding limit.

## The Pivot: Hard-Coding the Truth

We are moving away from relying on the LLM's "reasoning" for the comparison task. Reasoning is expensive and, as seen today, unreliable. 

The new directive is to implement a **Programmatic Diff**. Instead of asking the Engineer "What's new?", we will let a hard-coded Python function compare the vision results against the JSON database. We will force the "System" to do the heavy lifting, leaving the "Soul" to handle only the high-level synthesis.

## System Aesthetic: The "Sovereign" Look

On a more creative note, we've successfully implemented the "High-Fidelity Foundry" theme. Using custom ANSI color codes and Unicode box-drawing characters, the CLI finally feels like an industrial tool rather than a generic terminal. It’s a small victory for the "Soul" of the project—making the interface feel as heavy and purposeful as the hardware it manages.

## Summary of Lessons Learned
- **Contextual Hallucination** is the primary enemy of local-first multi-agent systems.
- **Model Swapping** on consumer-grade GPUs (16GB) is a primary source of backend instability.
- **The "Direct Vision" shortcut** is necessary to bypass the VRAM-heavy "Planning" phase when vision is the primary intent.

**Current Status:** The system is stable but "blind" to the truth. Next session, we break the hallucination loop with the `diff` tool.
