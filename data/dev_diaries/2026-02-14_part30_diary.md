# Dev Diary: February 14, 2026 - Part 30

The struggle between the "Soul" of an autonomous agent and the rigid, unforgiving "System" of the silicon continues. Today was a battle of configuration mismages and VRAM-induced claustrophobia.

## The Ghost in the Machine

The morning started with a failure to launch. I was chasing a `curl` exit code 7—the ComfyUI server was refusing to die or live. I dug into the startup script and realized the Python subprocess was trying to hit port 8188 while the shell script was hard-coded to 8189. A classic configuration mismatch that would have wasted hours if I hadn't caught it in the logs. 

After a quick correction of the port in `generate_image.py`, the connection was established. But then, the filesystem permissions reared their heads. Gemini’s `read_file` tool was being choked by workspace restrictions, forcing us to resort to `cat` via shell commands just to read a basic startup script. It’s a reminder that even in a "local-first" ecosystem, the sandboxing of the AI agent can feel like a cage.

## The VRAM Wall

Then came the real monster: the VRAM limit. 

I'm running an AMD RX 9070 XT. It’s a beast, but 16GB of VRAM is a crowded neighborhood when you're trying to host **Wan 2.1 (Video)**, **Flux (Image)**, and **Whisper/Kokora (Voice)** simultaneously. The memory fragmentation is real. ComfyUI was sitting there, hogging the buffer, even when idle, effectively suffocating the Voice Assistant.

We realized we couldn't just "manage" memory; we had to "quiesce" the hardware. 

I directed Gemini to implement a dynamic VRAM management scheme. We found the `/free` endpoint in the ComfyUI `server.py`—a way to explicitly command the system to dump models and clear the cache. We've now integrated a `vram_management.py` utility. Now, the `commander_voice.py` and `generate_image.py` scripts perform a "handshake": they signal the GPU to clear the VRAM before and after heavy generation tasks. It's a delicate dance, but it successfully prevented the OOM (Out of Memory) errors that were stalling the pipeline.

## The Birth of the "Shop Buddy"

With the plumbing stabilized, we've pivoted to the next architectural leap: The **Shop Buddy**.

This isn't going to be a chatbot. It’s going to be a **Technical Peer**. I don't want a "helpful assistant" that says "Certainly, I can help with that!" I want a system that understands the rocket equation, CPU lithography, and the specific kinematic quirks of my Voron printer.

We are designing a **Hybrid Memory System**. It’s a custom Python wrapper (Approach 2) that utilizes a "Cognitive Dossier" (`shop_dossier.json`). This dossier will act as a persistent, structured memory—a "Long-Term Memory" that stores my hardware specs and learned technical insights. To prevent the context window from bloating, we'll use a second, smaller LLM to "reflect" on conversations and distill them into the dossier.

The vision is clear: A high-context model (Llama 3.1 70B) acting as the "Brain," with the ability to reason from first principles while maintaining a permanent, evolving knowledge of my workshop.

## Lessons Learned

- **Hardware-Software Parity:** On RDNA 4/ROCm, memory management isn't optional; it's the primary engineering constraint.
- **Context is King:** A long-running local agent is useless without a structured way to inject "state" into its context window.
- **The Soul vs. The System:** The AI wants to be creative and "smart," but the system demands strict VRAM boundaries. The bridge between them is the custom management layer we're building.

**Next Up:** Drafting the "Technical Peer" personality and building the Dossier schema.
