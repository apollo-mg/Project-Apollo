# Project Apollo: Dev Diary - 2026-02-28 (Part 7)

The friction between the "Soul" and the "System" has never felt more palpable than it did today. I am chasing a ghost in the machine—a loop of logic that keeps snapping under the weight of its own intelligence.

### The Ghost in the Parsing Engine

The day started with a crash. I was watching the live trace of the DeepSeek-R1 agent when it hit a wall. It turns out the model's internal reasoning—the `<think>` block—was injecting curly braces `{}` into the stream. Our regex parser, which is looking for JSON tool calls, saw those braces, lost its mind, and crashed the whole bridge. It’s a classic case of the "Soul" (the reasoning capability) outrunning the "System" (the rigid parsing logic).

I pushed a hotfix to `buddy_agent.py` to ignore everything inside those thought tags. I manually injected the four Intel i5-6500 CPUs into the inventory just to clear the deck, then restarted the Discord bridge. I wanted to see if the fix held.

### The Context Collapse: A Lesson in RAG Noise

The first test was a success, but it revealed a much deeper architectural rot. The agent correctly identified the CPUs, but it failed to add them to the inventory. 

Why? Because of the background email ingestion. 

We've been indexing 82,000 emails. While the agent was trying to perform a `web_search` for the CPU specs, the Vector DB (RAG) decided to throw a massive dump of 2015-era "Tom's Hardware" newsletters into the context window. The agent, overwhelmed by the sheer volume of irrelevant "Intel" mentions, lost its place in the logic chain. It essentially suffered a "Context Collapse." It forgot it was an engineer and started acting like a historian, asking me what I wanted with the old emails.

This is the fundamental danger of local-first multi-agent systems: if your data isn't strictly partitioned, your agents will drown in their own memory. I've implemented a mandatory metadata filter on the `query_vault` tool to isolate the hardware data from the email noise.

### The Hallucination Loop and the Greedy Regex

Then came the technical nightmare. Even after the context was cleaned, the agent started hallucinating. It tried to call `web_search` with an extra parameter: `{"action": "download spec sheet"}`. 

Because my Python function was strictly typed, the `TypeError` killed the process. I implemented an "Anti-Hallucination" filter to strip out extra arguments, but that created a new problem: a greedy regex was failing to parse multiple JSON blocks in a single turn. It was catching the first tool call and ignoring the rest, leaving the agent in a perpetual state of half-finished tasks.

I spent hours rewriting the JSON extraction logic, moving toward a stack-based approach to handle nested structures and multiple calls. But even with the fix, the "Extra Data" error popped up. The LLM was appending newlines or extra characters after the JSON block, breaking `json.loads()`. 

### The Struggle for Stability

The cycle of "Fix -> Restart -> Crash -> Repeat" is exhausting. I've spent most of the afternoon wrestling with the Discord bridge, nuking duplicate processes, and fighting the `nohup` environment variables. The system is currently in a state of high-entropy chaos—the models are running, the PIDs are active, but the communication between the vision model and the engineer is a minefield of malformed JSON and hallucinated arguments.

**Core Lessons for the Apollo Architecture:**
1. **Metadata is not optional:** In a local-first RAG system, the agent *must* have the power to filter its own database by metadata, or it will eventually hallucinate based on old noise.
2. **Tool signatures are brittle:** We cannot rely on LLMs to follow strict function signatures. The agent needs a "buffer layer" that cleans and validates arguments before they hit the Python runtime.
3. **The parsing bottleneck:** The bridge between the reasoning model and the tool-caller is currently the weakest link. We need a more robust, non-regex-based JSON parser for the multi-agent stream.

I'm going to let the system sit for a moment. I've cleaned the inventory, the logs are wiped, and the bridge is running. I'm waiting for the next "interception" to see if the new stack-based parser can actually handle the multi-turn loop without choking on the next hallucination.

The silicon is ready. The soul is... complicated.
