# Project Apollo: The Silicon Struggle
## 2026-03-03 | Log Entry: Part 11

The friction between the soul of a model and the cold reality of its silicon is becoming increasingly palpable. I want to build something elegant, a local-first multi-agent ecosystem that feels alive, but right now, I’m mostly fighting the temperamental physics of the RDNA 4 architecture and the rigid constraints of vLLM.

The tuning process for the Qwen 3.5B FP8 weights has been an absolute rollercoaster of memory fragmentation and mathematical errors.

### The VRAM Wall
I hit a massive wall early on with a "No available memory" error. My initial math was sloppy. I was looking at the 16GB total, subtracting the 9GB weight footprint, and thinking I had plenty of room. But between the desktop's overhead and the way the system handles memory allocation, I was actually hitting a hard ceiling. 

I attempted to throttle the `gpu_memory_utilization` down to 0.6, but the error persisted. It turns out vLLM is extremely sensitive to how it carves out the KV cache. I realized my mistake: by setting it too low, I was leaving almost zero space for the cache blocks. I had to pivot and push it to 0.95, effectively telling the system to cram everything into that 2.7GB remaining window. It’s a razor-thin margin of error. One wrong move, one slight spike in kernel demand, and the whole thing collapses.

### The RDNA 4 Ghost
There is something strange about how the ROCm drivers are interacting with the FP8 kernels on this RX 9070 XT. The logs indicated the FP8 kernel optimization was sidelined because of missing configuration files—expected for a new architecture, but frustrating. I had to rely on `TunableOp` to benchmark the base GEMM operations instead. It felt like I was running the engine on manual override, bypassing the very optimizations that are supposed to make this hardware shine.

### The Zombie in the Machine
The most unnerving moment was when the VRAM usage hit 96% and stayed there, but the process vanished from `ps aux`. For a few minutes, I thought I had a memory leak or a zombie process. The GPU was drawing 98W, the VRAM was saturated at 15.36GB, but the logs were silent. The engine core was stuck in a computational loop, benchmarking kernels in a way that the system didn't seem to recognize as a running process. I had to sit there, watching `rocm-smi`, wondering if the hardware was about to cook itself or if the OS was about to kill the thread.

### The Breakthrough
Eventually, the dust settled. The tuning finished, and the results were flushed to the CSV. It was a massive relief. The results are stored, but the immediate victory felt hollow because the `apollo_bench.py` script failed instantly upon execution. It was the same memory issue again—the benchmark script had its own hardcoded memory utilization. 

I’m currently patching the benchmark script to match the `0.95` utilization of the tuning run. It’s a tedious cycle of: *Tuning -> Crash -> Patch -> Retry*, but it’s the only way to see if these tuned kernels actually provide the performance leap I’m looking for.

### Core Lessons
- **VRAM is a lie:** Never trust the "total available" number. Fragmentation and the OS overhead make the actual usable window much smaller than the hardware specs suggest.
- **Architecture Maturity:** Working on cutting-edge RDNA 4 means we can't rely on standard optimization paths. We are essentially writing the playbook for this hardware as we go.
- **The Optimization Paradox:** The more we squeeze the model to fit into local VRAM, the more fragile the execution becomes. We are trading stability for the ability to run high-parameter models locally.

Next step: Benchmarking the tuned model and seeing if the performance gain justifies the architectural headache.
