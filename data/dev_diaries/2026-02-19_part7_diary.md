# Dev Diary: 2026-02-19 (Part 7)

The friction between the Silicon and the Soul was palpable today. I spent the first half of the session wrestling with a massive, invisible wall of permissions and filesystem corruption that threatened to derail the entire vision-to-inventory pipeline.

### The Corruption & The Bypass
The session began in chaos. A failed interaction with the `gnome-screenshot` utility on Wayland had left the system in a state of confusion. The "Desktop Eyes" integration had been trying to bypass Wayland's restrictive security context, but it resulted in a cascade of corrupted files. I found that `test_capture.py` and `README.md` had been overwritten by a blob of JPEG data—likely a rogue `run_bash` command or a misdirected tool during a previous session. 

It was a classic case of a "dirty" filesystem. The NTFS partition on the infrastructure drive was flagged as "dirty" in `dmesg`, which typically forces a read-only mount. I had to verify write access by forcing a 2.4MB screenshot to the drive. Even though the permissions looked like a wide-open `777`, the actual data was garbage. The "Soul" of the project (our documentation and test scripts) was being crushed by the "System" (the hardware/filesystem error).

### The RDNA 4 & ROCm Battle
Once the files were stabilized, the real technical beast emerged: the vision model. I've been trying to get `qwen2.5vl` running on the RX 9070 XT, but it was being stubborn. It kept defaulting to the CPU, making the inference time for a single frame painfully slow.

I realized the `OLLAMA_LLM_LIBRARY=vulkan` override was the culprit. It was hitting a `500` error because the Vulkan bridge couldn't handle the RDNA 4 architecture's specific vision requirements. I had to manually strip the Vulkan override and force-restart the Ollama service with the native ROCm backend. 

The moment it worked was pure magic. The model finally hit the VRAM, and the vision pipeline—capturing a frame and having Qwen describe the "collage" of images—was instantaneous. The "Soul" (the intelligence) finally had a home in the "System" (the GPU).

### The Search for the Ghost in the Machine
The afternoon took a turn into a strange, almost existential, detective hunt. I was looking for the `settings.json` file that the user claimed to have updated with new experimental features (Introspection and Plan mode). 

Despite the `GEMINI.md` memory insisting the file existed and the settings were active, the file was nowhere to be found in the `gemini_infrastructure` directory. I searched through the `.gitignore`—which was aggressively excluding everything—and even checked the `guardian_config.json` and `shop_dossier.json`. It felt like the file had vanished into the void of the unmounted NTFS layer. 

I eventually realized the `settings.json` was likely being swallowed by a overly-restrictive `.gitignore` pattern. It was a reminder that as we build this local-first ecosystem, the very tools we use to manage the project can sometimes become the biggest obstacles to its development.

### Current Status: The Vision is Live
We are back on track. The `qwen2.5vl` vision-to-dossier pipeline is functional, the GPU is finally being utilized properly via ROCm, and the permission-based bottlenecks in the Gemini CLI have been cleared. The "Shop Buddy" is no longer blind; it can see the world, and we are ready to begin the actual inventory scanning.
