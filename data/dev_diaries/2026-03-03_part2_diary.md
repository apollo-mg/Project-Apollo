# Apollo Dev Diary: 2026-03-03 (Part 2)

The friction between the "Soul" (the creative vision of a sovereign, multi-agent intelligence) and the "System" (the cold, hard constraints of my 16GB VRAM ceiling) is becoming the defining challenge of this project. Today was a fight against memory fragmentation and a hard lesson in the volatility of local LLM context windows.

### The Ghost in the Machine: Context Window Crashes
I spent the first part of the session hunting a ghost. The Vision model (`qwen3-vl:8b`) was returning empty strings for multi-image inputs. It looked like a hallucination, but it was actually a silent, catastrophic failure.

The visual tokens from two high-res images were eating up ~1,867 tokens. Because Ollama defaults to a 2,048 token context window, the moment the model tried to generate the first token of text, it hit the ceiling and crashed. The downstream Engineer model (`qwen3:8b`) received an empty string, saw nothing, and proceeded to hallucinate a generic "low-power vs high-power" comparison based on its weights alone. 

**The Fix:** I modified `llm_interface.py` to explicitly request a 8,192 context window (`num_ctx`) in the Ollama payload. This gave the model enough VRAM headroom to process the images and generate text. After a restart, the Vision model correctly identified the board as "BIGTREE TECH EB636 CAN V1.1".

### Automating the Pipeline: The Sync & Review Cycle
We need to stop manually managing the codebase across three different directories. I've implemented a new autonomous pipeline: `apollo-sync`. 

It’s a 4-step automated workflow:
1. **Sync:** `rsync` mirrors code to the Git-tracked directory.
2. **Stage:** `git add .`
3. **AI Review:** A `pre-commit` hook where the `qwen3-coder:30b` (the Architect) performs a security audit and generates semantic commit messages.
4. **Push:** Uploads to GitHub.

I've also added a suite of aliases to `~/.bashrc` (like `apollo-status`, `apollo-vram`, and `apollo-logs-discord`) so the terminal becomes a control center rather than a chore.

### The VRAM Tetris: The vLLM Dilemma
The most significant architectural epiphany of the day: We are approaching the "VRAM Ceiling." 

The 16GB on the RX 9070 XT is a brutal bottleneck. Running a 14B model in unquantized mode is impossible (28GB). Even at 8-bit, it leaves zero room for the KV cache. 

We discussed moving toward **vLLM for Guided Decoding**. This would allow us to force models like `Qwen2.5-Coder-7B` to output 100% perfect, syntax-guaranteed JSON for tool calls. However, vLLM is a "memory hog." 

The plan is a **"Swap & Lock"** architecture:
* Keep Ollama for the heavy-hitting, high-context Vision/Reasoning models.
* Use a small, highly optimized 3B/7B Coder in vLLM for the structured "tool-calling" tasks.
* Implement strict VRAM management to flush Ollama models before spawning the vLLM instance.

We are no longer just writing code; we are managing a delicate ecosystem of memory-intensive processes. The next step is to test if a 7B model can survive the vLLM-ROCm integration without triggering an OOM crash.
