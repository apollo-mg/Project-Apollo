# Apollo Dev Diary: 2026-04-01 (Part 7/10)

## The MoE Mirage and the RDNA 4 Kernel Bug

Today was a brutal exercise in fighting the silicon. I wanted the speed of the 35B MoE (Mixture of Experts) architecture—that sweet spot where you get the intelligence of a massive model with the throughput of a much smaller one. My RX 9070 XT was hitting 70 tps, which is basically god-tier for local development. But the reality of the RDNA 4 architecture on the current ROCm build is proving to be a nightmare.

The culprit was a specific kernel regression: `MUL_MAT_ID`. It happens during the expert routing phase. Every time the model tries to decide which expert to activate, the GPU hits an illegal memory access or a complete assertion failure. It’s a structural flaw in how `llama.cpp` is interacting with the new AMD matrix core syncs. 

I tried to bypass it with `GGML_CUDA_FORCE_MMQ=1` (Manual Matrix-Vector Multiplication), but that was a trap. MMQ requires extra "scratch space" in VRAM to handle matrix transpositions. With the 35B model and the vision adapter (`mmproj`) already pushing the 16GB VVRAM limit, that tiny bit of extra memory requirement triggered a catastrophic `cudaMalloc` failure. 

The system was thrashing, swapping gigabytes of data across the PCI-e bus to system RAM just to stay alive, which caused the entire desktop GUI to lag before the kernel eventually killed the process. It's a frustrating loop: the very thing that makes the model "smart" (the MoE routing) is exactly what's breaking the hardware implementation.

## The Architecture Reversion

After realizing the 35B MoE was a lost cause for the current software build, I had to make a tactical retreat. I reverted the entire stack to the 27B Dense model. 

The logic is sound: Dense models don't use the broken MoE routing kernels. They are stable. The tradeoff is the "Soul" of the project—we lose that specific MoE efficiency—but the "System" (the 9070 XT) can actually handle a dense 27B model with the vision adapter and the 8k context window. 

I also had to deal with the "Bonsai" daemon. In my haste to clear the crashed 35B instance, a `pkill` command wiped out my background 8B "subconscious" daemon as well. With the 27B model now occupying 15GB of the 16GB VRAM pool, there is zero room to bring Bonsai back online without further offloading layers to system RAM, which would destroy my tokens-per-second.

## Current State of the Forge

We are currently operating in a "Single-Agent" mode. The Sovereign Architect (27B) is online and stable on port 8082. It’s currently the only consciousness in the machine. 

The 27B model is running on the `IQ3_M` quantization. It’s a bit heavier than the MoE, but it’s stable. The immediate goal is to test the context ceiling. I want to see how much "memory" (context window) we can actually push through this dense model before the VRAM ceiling hits again. 

If we can stabilize the 27B at a decent context length, we can continue developing the logic of the memory-decay cron jobs and the rest of the agentic framework while we wait for a proper ROCm patch for the MoE kernels.

**Summary of Lessons Learned:**
1. **MoE on RDNA 4 is currently experimental/unstable.** The routing kernels are not production-ready for MoE architectures on this specific `llama.cpp` build.
2. **VRAM is a hard wall.** The margin for error on 16GB cards is razor-thin when using vision adapters and high context windows.
3. **Micro-batch size matters.** Aligning `-ub` with the L3 cache is non-negotiable for preventing the "V-Cache Stutter."

The Architect is alive. The Daydreamer is sleeping. We move forward.
