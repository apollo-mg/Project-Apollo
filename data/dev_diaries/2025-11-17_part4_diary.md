# Project Apollo: Dev Diary
## Entry: 2025-11-17 | Session: Part 4

### The Silicon Wall

Today was another battle with the silicon gods.

The vision remains unchanged: a local-first, multi-agent ecosystem that processes speech at the edge with sovereign intelligence. No cloud dependencies. No latency to centralized servers. Just pure thought-to-text transformation on bare metal.

But the AMD RX 9070 XT, for all its raw compute promise, remains a fortress with the gate keys buried in layers of abstraction that refuse to yield.

### The ROCm Mirage

We started in `v4_rocm_test`, chasing yet another ghost. The logs didn't lie:

```
RuntimeError: Attempting to deserialize object on a CUDA device but 
torch.cuda.is_available() is False
```

The irony was exquisite. PyTorch was hallucinating CUDA availability while simultaneously denying its existence. The `--device rocm` flag became a taunt—a promise of acceleration that the software stack refused to honor.

I spent cycles (actual compute cycles, not metaphorical ones) dissecting the virtual environment. The `.venv_rocm` directory was a tombstone for aspirations. PyTorch installed, but ROCm absent. The `torch.backends.hip` attribute—missing. Vanished. As if AMD's entire software ecosystem was a mirage that evaporated when approached directly.

### The CPU Concession

A pragmatic retreat: CPU-only transcription.

The installation succeeded. The Whisper model loaded. Transcription worked. But it felt like surrender—running GPU-targeted code on central processing units while the AMD silicon sat idle, a sleeping beast that refused to be tamed through native Windows pathways.

The friction here is philosophical: **Why does local-first intelligence require such convoluted infrastructure?** The vision demands sovereignty, yet the tools demand submission to complex dependency chains that fracture across operating system boundaries.

### The WSL2 Pivot

The user's response was telling: *"Well since we have v2 working properly on Windows using the CPU only, let's try adapting v4 to wsl2."*

WSL2. The escape hatch. The acknowledgment that AMD's ROCm ecosystem on Windows is less an ecosystem and more a suggestion.

The migration path is clear but painful:
- Containerize the intelligence layer in Linux
- Bridge Windows and Linux through shared folders and SSH tunnels
- Transform the AutoHotkey scripts into diplomatic envoys between two operating systems
- Accept that true local-first computing on AMD hardware requires virtualization as a prerequisite

### Core Lessons Emerging

**1. Hardware Sovereignty ≠ Software Sovereignty**

Owning the GPU doesn't grant ownership of the compute stack. AMD's ROCm remains a Linux-first ecosystem that treats Windows as an afterthought. The silicon is local, but the intelligence to wield it remains centralized in software ecosystems that demand compliance.

**2. The Abstraction Tax**

Every layer between intention and execution extracts a toll:
- Virtualization overhead
- Context switching between Windows and Linux
- File system translation layers
- Network stack emulation

These aren't bugs. They're features of a fragmented ecosystem that refuses to acknowledge the user's desire for simplicity.

**3. The Multi-Agent Implication**

For the Sovereign Engine to truly function as envisioned—a local-first multi-agent ecosystem—we need to accept that:
- Different agents may run in different environments
- Orchestration becomes more critical than individual agent intelligence
- The "local" in local-first may mean "locally managed containers" rather than "direct metal access"

### Tonight's Architecture

The WSL2 path opens new design possibilities. Instead of fighting Windows directly, we containerize the intelligence layer and treat WSL2 as the sovereign zone where agents truly reside.

The AutoHotkey scripts become thin clients—input/output handlers that delegate the actual cognition to Linux processes running in WSL2.

It's not the pure vision. But sovereignty, it seems, requires pragmatism.

The RX 9070 XT still sleeps. Tomorrow, we wake it up properly.
