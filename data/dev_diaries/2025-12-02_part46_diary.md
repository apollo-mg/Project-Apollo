# Dev Diary: The Precision War

**Date:** 2025-12-02
**Session:** Part 46
**Hardware:** AMD Radeon RX 9070 XT | ROCm 7.1.1 | 16GB VRAM

The dream of local video generation is hitting the wall of silicon reality. 

Tonight was supposed to be the breakthrough for the WanVideo integration. I was pushing the limits of the 9070 XT, trying to see if we could actually dance with these massive video models using the GGUF quantization strategy. We’re trying to squeeze high-fidelity temporal consistency into a 16GB VRAM footprint—it’s a tight squeeze, a digital claustrophobia that defines everything we do in Project Apollo.

Then, the sampler died.

The terminal spat out a classic, soul-crushing `RuntimeError`: 
`self and mat2 must have the same dtype, but got Half and Float`.

It’s a precision mismatch. A fundamental disagreement between the math and the machine.

Looking at the stack trace, the culprit is lurking in the interaction between the `ComfyUI-GGUF` node and the `WanVideo` forward pass. We are using `lowvram` mode and `split-cross-attention` to keep the system from choking, which is the right move for the hardware, but the precision logic is breaking. Specifically, during the `forward_comfy_cast_weights` call, the model is trying to perform a linear operation where the input tensor is `Half` (FP16) but the weights being fed into the layer are somehow still `Float` (FP32).

It’s a byproduct of our attempt to be clever with quantization. We are trying to use GGUF to save VRAM, which is the only way these models will ever run locally without a server farm, but the "System" is punishing us for it. The ROCm driver and PyTorch are being incredibly pedantic about dtype consistency. One single layer, one single mismatched weight matrix, and the whole architectural stack collapses.

This is the friction I talk about. The "Soul" of the project is this beautiful, fluid motion we're trying to extract from the WanVideo weights. But the "System" is this cold, uncompromising matrix multiplication. If the precision doesn't match, the motion doesn't exist.

The trace points directly to `comfy/ops.py` and the way `ComfyUI-GGUF` handles weight casting. It seems the `forward_comfy_cast_weights` function is failing to enforce a uniform `Half` dtype across the entire operation. We’re getting a "leak" where FP32 precision is staying alive in a pipeline that should be strictly FP16.

**The technical roadmap for the next session:**

1.  **Audit the GGUF Cast Logic:** I need to dig into how `ComfyUI-GGUF` is interacting with the `ModelPatcher`. We need to ensure that when we are in `lowvram` mode, the cast to `Half` is absolute and irreversible for all weights in that layer.
2.  **ROCm Precision Profiling:** I need to see if `torch.backends.cudnn.enabled = False` is helping or hurting here. We disabled it for better AMD performance, but we might be seeing weird side effects in how `linear` operations are dispatched.
3.  **Quantization Strategy Refinement:** If we can't get the `Half/Float` mismatch solved, we might need to move to a more aggressive quantization scheme that forces everything into a unified dtype from the moment it leaves the disk.

We’re close. The fact that the sampler even got to the first step without a massive OOM (Out of Memory) error means the memory management is working. The VRAM is holding. We just need to fix the math.

The machine is stubborn, but we’ll make it sing.
