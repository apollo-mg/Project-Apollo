# Dev Diary: 2025-11-30 (Part 43)
## The Ghost in the Memory Map

The struggle between the "Soul" of the creative model and the "System" of the silicon has never felt more visceral. Today was a brutal fight against the RDNA 4 architecture and the current state of ROCm 7.x. We are trying to push the Wan 2.1 Video model through a 16GB bottleneck, and the hardware is fighting back with illegal memory access errors that feel less like software bugs and more like a rebellion of the driver.

### The MMap Ghost
The session began with a recurring crash at `cpu_weight = weight.cpu()`. It was a ghost in the machine—the tensor was corrupted or inaccessible before the copy could even begin. 

My analysis pointed to a fundamental friction in how ROCm 7.x handles memory-mapped (`mmap`) tensors from `safetensors`. It seems the driver is failing to handle non-contiguous memory-mapped views during the transition from disk to RAM. 

**The Fix:** I implemented a "Nuclear Option" in `lora.py`. By forcing a `.clone().detach()`, we break the file-backed association and force the tensors into fresh, writable RAM. It was a brute-force way to bypass the driver's inability to manage the file descriptors, but it worked. The crash at the loading stage vanished.

### The Flash Attention Paradox
With the loading crash resolved, we hit the next wall: the KSampler. The system was "running" (100% GPU load, 96% VRAM saturation), but it was effectively a zombie process—no progress, just a heavy, compute-locked stall.

I suspected the experimental Flash Attention Triton kernels on RDNA 4 were either deadlocking or causing massive memory thrashing. I reverted to "Safe Mode"—disabling Flash Attention and falling back to `split_cross_attention`.

The result was a temporary victory: the system actually began to process. The desktop became sluggish, a sign that the GPU was finally crunching numbers. But then, the inevitable: a crash during the KSampler loop. 

The conclusion was inescapable: **The memory efficiency of Flash Attention is not optional.** For a model of this scale, standard attention is a memory hog. We need the linear complexity of Flash Attention to survive, but the current Triton implementation is unstable on this hardware.

### The Current Architecture
We are currently caught in a loop of trying to find the "Goldilocks" zone of stability. We have implemented:
1. **Deep Copy Patches:** To ensure weights are in RAM, not just mapped from disk.
2. **Memory Allocator Tuning:** Using `PYTORCH_HIP_ALLOC_CONF` to manage fragmentation.
3. **Flash Attention Re-enabled:** Because we need its efficiency, even if it's temperamental.

### Core Lessons & The Path Forward
- **Local-First Reality:** Running 14B parameter video models on consumer-grade AMD hardware is not a matter of "plug and play." It is a matter of constant, granular memory management. 
- **The Driver Gap:** The gap between the cutting-edge model architecture (Wan 2.1) and the stable driver stack (ROCm) is massive. We are essentially writing the glue that holds them together.
- **The VRAM Ceiling:** 16GB is the hard limit. The success of the next run depends entirely on whether the `VAEDecodeTiled` implementation can handle the output without triggering an OOM during the final step.

**Status:** *Optimistic, but cautious. The system is currently configured with the most aggressive stability patches we have. Now, we wait for the silicon to prove us right.*
