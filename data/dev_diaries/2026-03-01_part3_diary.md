# Project Apollo Dev Diary: 2026-03-01 (Part 3)

The friction between high-performance silicon and the software that tries to tame it is real. Today was a battle against the "Soul" of my local intelligence—the desire for massive, reasoning-capable models—and the cold, hard reality of a 16GB VRAM ceiling.

### The Silicon Struggle: VRAM and the vLLM Wall

I spent much of the afternoon wrestling with the vLLM engine on the RX 9070 XT. I was running a benchmark for a DeepSeek-R1 distillation, trying to push the limits of the RDNA 4 architecture. The problem is that vLLM is a "greedy" beast; it wants to own every byte of VRAM for its `PagedAttention` cache. 

I hit a wall where the driver couldn't even submit command buffers because the memory was so tightly packed. It wasn't a crash, but a deadlock. The GPU was drawing 334W—working hard, but doing nothing. I had to pivot and throttle the `gpu_memory_utilization` down to 70%. It felt counter-intuitive to "limit" my hardware, but it gave the ROCm driver the 4.8GB of breathing room it needed to manage the system and the command queues. The result? Stable, high-speed token generation. It’s a lesson: in local-first AI, managing the *overhead* is just as important as managing the *model*.

### The Breakthrough: MoE and RDNA 4

The most exciting moment was seeing the telemetry for the `Qwen3.5-35B-A3B` model. It's a Mixture-of-Experts (MoE) architecture. This is the "Golden Ratio" for my current hardware. The model has 35B parameters, but only 3B are active during inference. 

On the RX 9070 XT, this is pure magic. The 35B weights are sitting in VRAM, but the actual computation throughput matches a 3B model. The RDNA 4 L3/Infinity Cache handles the expert-switching with almost zero latency. It's the only way to get "Pro-grade" reasoning on consumer-grade silicon without a massive workstation card. 

### The "Foundry" Strategy

I've realized we can't just download and play. We need a "Foundry." I've implemented a new profiling agent, `foundry_profile.py`. Since these high-performance optimizations (like the AOT-compiled kernels and HIP Graphs) are sensitive to the exact math-shape of the model, they need to be "pre-baked." 

The plan is to treat the local drive like a factory:
1. **Hoard:** Download the model.
2. **Profile:** Run the Foundry overnight to generate the `MXFP4` or `TunableOp` math libraries.
3. **Deploy:** Use the primed model with blazing speeds.

### Digital Housekeeping: The Storage Crisis

The desktop is a mess. My fastest NVMe (the WD Black) is choked by a "Ghost" Windows partition that's holding 465GB of data. The `AppData` folder alone is a 162GB bloat-fest of caches. 

The architectural decision is clear: I need to move the "Cold" data (old user profiles, massive game installs like *Mass Effect*) to the mechanical HDDs. I need to clear the high-speed NVMe for the actual "Mind" (the active models and their KV caches). We're going to prune the Windows junk and move the user profiles to the 2TB game drive tonight.

**Current Status:**
The system is currently in the "Graph Capture" phase for the DeepSeek benchmark. It's currently drawing 353W—the card is screaming—but it's recording the optimal execution paths. Once this finishes, we'll have the most optimized local reasoning engine on the market.

**Next Step:** Automating the Foundry. If we can automate the "baking" of models, the distinction between a consumer PC and a server-grade node disappears.
