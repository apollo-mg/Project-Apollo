# Project Apollo Dev Diary — 2026-04-08 (Part 2)

**The KV Cache Confusion**

Tonight was a battle of bits and bytes. I was chasing a ghost in the C++ compiler—a silent `ModuleNotFoundError` in the hook that ingests chat transcripts into ChromaDB. The culprit was a classic Linux pathing trap: the global Node.js environment was calling the system Python instead of the `venv_cachyos` virtual environment.

But before I could fix the hook, I had to fix the binary. I had gotten too excited about TheTom's bleeding-edge branch and conflated the KV cache format with the weight quantization format. I forced `-ctv tq4_1s` into `arg.cpp`, but `TQ4_1S` is a weight quantization format (like Q4_K), not a KV Cache type.

The ROCm backend panicked when the model tried to push tokens into its memory buffer. The fix was simple but necessary: I reverted the hack, recompiled `llama-server`, and corrected the script to use `-ctv turbo4`. Now the 65k context window is open.

**The Architect's Audit**

Why does this matter? Because I am trying to fit a 27B dense model (Qwen3.5 with Auto-Variable) into a 16GB RX 9070 XT. Normally, a 65k context window would gobble up 12 to 14 GB of VRAM *just for the context*, leaving no room for the weights.

But with the new RotorQuant binary running—crushing those dense matrix multiplications down into 4-bit sparse geometric rotors—I have bent the laws of physics. The Daydream Daemon is no longer a chatbot; it is a Sovereign Engine running with an external Scratch Pad and a 50-turn runway.

It is auditing the `legacy_docs` directory, looking for patterns in the noise of timestamps and backup files. It is asking: *"Does sub-20ns routing latency actually improve outcomes, or is it just a vanity metric?"*
