# Dev Diary: The Silicon Wall and the Contiguity War
**Date:** 2025-12-03
**Project:** Apollo (Local-First Multi-Agent Video Ecosystem)
**Hardware:** AMD RX 9070 XT | 16GB VRAM | ROCm 7.1

Today was a brutal lesson in why "local-first" is a war of attrition. We aren't just fighting for creative expression; we are fighting the very way the silicon handles memory. 

### The GGUF Kernel Deadlock
We’ve been trying to run the Wan 2.1 14B model using GGUF quantization. On paper, it’s the holy grail: high intelligence, lower VRAM footprint. In practice, the RDNA 4 architecture seems to have a fundamental beef with how `ComfyUI-GGUF` handles bitwise math.

We kept hitting `gfxhub page faults`. That’s not a software bug; that’s the GPU screaming because it tried to access memory that wasn't there. Every time the dequantization kernel tried to perform a bitwise shift on a tensor slice, the driver lost its mind. 

The initial fix was to cache the tensors to prevent re-allocation crashes, but that wasn't enough. The "Soul" of the project—the desire to see high-fidelity video—was being strangled by the "System." I had to go nuclear. 

I’m implementing a contiguity patch in `dequant.py`. The problem is that `torch.split` returns *views*. On RDNA 4, these views are apparently too "messy" for the driver's bitwise vectorization. I’m forcing `.contiguous()` calls immediately after every split. It’s technically "expensive" because it forces physical memory copies, but on a bleeding-edge driver like ROCm 7.1, breaking the memory dependency chain is the only way to stop the page faults. It’s the difference between a fast, broken system and a stable, slightly slower one.

### The VRAM Tightrope
Then there’s the "Step 2 Hang." 

We ran the 14B Q5_K_M model, and it worked—until it didn't. It would start the sampling process, the fans would ramp up to a deafening roar (the hardware actually working), and then... silence. A total hang. 

This is the classic VRAM thrashing wall. The 14B model plus the VAE and the KV cache is pushing right up against that 16GB limit. One wrong allocation, one slightly larger intermediate buffer, and the system starts swapping to system RAM over the PCIe bus. The speed drops from 4 seconds per frame to 100 seconds per frame, and the whole process looks dead.

To fight this, I’ve had to turn the memory allocator into a precision instrument. We're using `max_split_size_mb:128` and `expandable_segments:True`. We are essentially micro-managing every single byte of the 16GB VRAM to prevent fragmentation from killing the run. It’s claustrophobic, but it’s the only way to keep the 14B model alive.

### The Safety Lock: Attention & Artifacts
We also had to implement a "Safety Lock" on the attention mechanism. The Flash Attention kernel on RDNA 4 is fast, but it’s "hallucinogenic"—it produces visual artifacts and weird temporal wobbles that ruin the immersion. 

We’ve patched `attention.py` to force the `MemEfficient` backend by default. It’s slower, but it’s clean. I’ve added an environment variable `RDNA4_DISABLE_FLASH_SDP` so we can toggle it. If we find a driver update that fixes the Flash artifacts, we can flip the switch. For now, we prioritize the "Soul"—we want the video to look like a simulation, not a fever dream.

### The Result: A Slow, Beautiful Simulation
We finally got a stable run on the 5B model. It’s slow—500 seconds for a 5-second clip—but it’s *stable*. 

There is a massive semantic gap between the 5B and 14B models. The 5B model is a "dream"—it’s okay for simple motion, but it lacks the physics of the world. The 14B model is a "simulation." It understands how water splashes and how light hits a surface. 

Watching the first prompts—the deep-sea leviathans and the naval battles—render through the fog of these patches feels like winning a war. We are building a bridge between the chaos of the prompt and the rigid, unforgiving limits of the RDNA 4 silicon. 

**Current Status:**
- **GGUF:** Patched for contiguity (working).
- **Attention:** Forced Safe Mode (stable).
- **VRAM:** Aggressive management active (on the edge).
- **Next Step:** Optimizing the `torch.compile` path to claw back some of that lost speed without breaking the kernel.

*The silicon is stubborn. But we're getting there.*
