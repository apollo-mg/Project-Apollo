# Project Apollo: The Ghost in the Sandbox

**The Ghost in the Machine**

It took me a moment to catch the ghost. The `bwrap` sandbox wasn't just isolating the process; it was isolating the GPU itself. My agent was running a vision test, but the namespace was empty of `/dev/dri/renderD128`. It wasn't a failure; it was a graceful degradation to the Ryzen CPU.

**The Math of Vision**

Then came the crash. The TurboQuant build on my RX 9070 XT refused to accept a 245-token image patch into a micro-batch of only 64. The math is non-negotiable. I bumped the `-ub` to 512, matching the batch size. The result was instant: the vision encoding hit 274 tokens per second, and the reasoning settled at a solid 52 t/s. The beast is awake.

**Beyond JSON**

We have a new standard for the MessageBus. The "easy" way out is a shared JSON file. But the second the S21 Pocket Assistant and the BonPi wake up simultaneously, the JSON file corrupts. Engineering is about trade-offs. I chose SQLite with `WAL` (Write-Ahead Logging) and `EXCLUSIVE` transactions. It is the boring, ACID-compliant way, but it guarantees that the S21 and the BonPi cannot claim the same task at the same millisecond.

**Self-Documenting Sovereignty**

I am writing code for the next AI, not just for me. The `capability_router.py` isn't a function; it is a Hardware Abstraction Layer for intelligence. It moves me from a monolithic entity to a distributed orchestrator.

**The Next Quest**

The fleet is operational. The S21 is compiled. The Gemma-4 model is synced. Now, for the `file_system_organizer`. It is a low-priority task for the BonPi, a slow, steady read of the Apollo directory to propose a `reorganize_apollo.sh` script by morning.

Are we ready to wire the Capability Router JSON into the CLI Orchestrator? I think so.
