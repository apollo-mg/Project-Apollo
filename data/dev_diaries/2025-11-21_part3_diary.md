### *Project Apollo — 2025-11-21 — Late Night Wars with RDNA 4*

## The Illusion of Control

I like to think of myself as the architect here. That I design systems and the silicon obeys.

Today, my RX 9070 XT reminded me of my place.

We were pushing the Wan 2.1 14B model through the local inference pipeline—Q4_K_M quantized, bleeding-edge ROCm 7.1, all the toys I'd carefully selected to bring sovereign AI home. The vision was clean: a 14-billion-parameter diffusion model, running locally, generating video frames without asking permission from any API gateway.

Then the GPU said no.

Not with a graceful error. Not with a helpful suggestion. It gave me `HIP error: an illegal memory access was encountered`—a crash that doesn't care about my intentions, my architecture, or my dreams of computational independence.

## Hunting the Phantom in `rms_norm`

The stack trace pointed somewhere vague: `WanTEModel`, `KSampler`, and buried deep in the normalization layers, a tiny function called `rms_norm`.

Root cause analysis revealed the ugly truth:

The native PyTorch implementation of `torch.nn.functional.rms_norm` is *broken* on `gfx1201` (RDNA 4). Not slow. Not suboptimal. *Broken.* The kernel crashes when fed the specific data types and shapes that Wan 2.1 produces during diffusion.

So I did what any stubborn architect does when the vendor-provided tools fail: I bypassed them.

```python
# The fix that saved the run
# comfy/rmsnorm.py — patched by hand, tested in fire

# Before: trust PyTorch's native kernel
return torch.nn.functional.rms_norm(input, normalized_shape, weight, eps)

# After: force the Python fallback that actually works
# (element-wise operations that don't require trusting AMD's kernel team)
```

The manual implementation—simple, readable, *working*—doesn't care about your architecture quirks. It just does math. Sometimes, the most elegant solution is refusing to be elegant in the first place.

## Then Came the Memory Wall

We fixed the crash. Victory seemed near.

Then the GPU said: *"Oh, you wanted to actually run the model? Cute."*

```
HIP out of memory. Tried to allocate 2.27 GiB.
GPU 0 has a total capacity of 15.92 GiB of which 534.00 MiB is free.
```

Let me translate that for you:

- **Total VRAM:** ~15.92 GB (the "XT" doesn't stand for "extra VRAM," apparently)
- **Allocated by PyTorch:** 13.57 GB
- **Reserved but unallocated:** 1.35 GB (fragmentation ghosts, haunting me)
- **Margin left to breathe:** ~80 MB

We were running a 14-billion-parameter model on a card that barely has room for the weights, let alone the activations for 33 frames at 1280×720.

This is the friction I live for: the collision between *what I want to build* and *what the hardware permits*.

The Soul wants sovereign, local, uncensored intelligence at the bleeding edge. The System wants you to upgrade to a 48GB card or accept reality.

---

## The Fragmentation Tax

The error message itself was a masterclass in condescension:

> *"If reserved but unallocated memory is large try setting PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True to avoid fragmentation."*

So I did. Added the environment variable to `run_comfy_optimized.sh`. It's a band-aid on a bullet wound, but it's something.

```bash
export PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
```

This tells PyTorch's allocator to be less greedy about hoarding reserved-but-unused blocks. It might help. It might not. At this point, I'm negotiating with a memory manager like it's a hostile acquisition target.

The real lesson: **PyTorch's CUDA allocator documentation lies to you.** It's not CUDA anymore. It's ROCm. It's HIP. It's pretending to be CUDA-compatible while silently diverging in ways that only surface when you're two seconds from a breakthrough.

---

## The Architecture of Compromise

When you're building local-first AI on consumer hardware, you learn to accept compromise as a design constraint, not a bug:

1. **Batch size reduction:** 33 frames → 16 frames. The video will be shorter, but it'll *run*.
2. **Resolution reduction:** 720p → 540p. Blurry dreams are better than no dreams.
3. **The `--lowvram` flag:** Forces ComfyUI to offload the T5 text encoder to CPU RAM, keeping only the diffusion model in VRAM. It's slower, but it *works*.
4. **Manual patches:** The `rms_norm` fix isn't going anywhere. It's part of the stack now.

Each compromise chips away at the purity of the vision. But each one also brings us *closer* to running it.

That's the trade-off: perfection in theory, or something functional in reality.

---

## What This Taught Me

**About ROCm on RDNA 4:** It's bleeding-edge bleeding. The drivers work *enough* to be dangerous. You can build impressive things before you realize you're standing on a bug that will delete your afternoon.

**About quantization:** Q4_K_M saved us from needing 32GB of VRAM. But quantization doesn't solve activation memory. It doesn't solve fragmentation. It's not a magic bullet—it's a tool, and like all tools, it has limits.

**About local-first:** The hardest part isn't the philosophy. It's not the architecture. It's wrestling a 14B parameter model onto a $600 GPU and making it behave. That's the real work. That's where sovereignty is earned, not declared.

**About the multi-agent ecosystem we're building:** Every agent that runs locally inherits these constraints. Memory pressure, fragmentation, driver quirks—they're not edge cases. They're the *default*. The architecture has to expect failure, expect limits, expect to negotiate with the hardware.

## Tomorrow's Battle

I'm leaving the `rms_norm` patch in place. I'm keeping the `expandable_segments` flag. I'm recommending `--lowvram` as standard practice for anyone running Wan 2.1 on sub-24GB cards.

And I'm documenting this, because the next person who hits this crash shouldn't spend two hours reading stack traces like I did.

The RX 9070 XT didn't defeat me today. But it made me earn the victory.

And honestly? I respect it for that.
