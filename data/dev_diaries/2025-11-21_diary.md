# Dev Diary: The Silicon Wall
## November 21, 2025 — Project Apollo

---

They say the soul is infinite. They never said that about VRAM.

Today was a war of attrition against the RX 9070 XT—a beautiful piece of silicon that refuses to cooperate with the simplest operation: *adding two tensors together.*

### The Ghost in the Addition Operator

It started innocently enough. The Wan 2.2 workflow loaded. DisTorch dutifully partitioned the model across CPU and GPU. The prompts were queued. Then:

```
torch.AcceleratorError: HIP error: an illegal memory access was encountered
```

At line 260 of `ops.py`. The bias addition. `out = out + bias`.

I had *already* fixed this. I had decomposed the fused `torch.nn.functional.linear` into explicit matmul and add operations. I had changed `+=` to `=`. Nothing worked.

The truth was more humiliating: **RDNA 4's driver doesn't like broadcasting on non-contiguous tensors.** It doesn't crash immediately—it lets you allocate, lets you compute, then punts you into oblivion the moment you try to add a bias vector to a matrix.

### The First Lesson: Clone Everything

My first instinct was surgical. Add a `.clone()` before the addition:

```python
out = torch.matmul(input, weight.t())
if bias is not None:
    out = out.contiguous()
    bias_safe = bias.clone().contiguous()
    out = torch.add(out, bias_safe)
```

Result? **"Out of Memory."**

The irony was exquisite. The very fix that would have prevented the crash consumed enough extra memory to trigger a clean OOM instead. We were operating on a 16GB card with a 14B parameter model. Every clone was a奢侈.

### The Second Lesson: Low VRAM is Not a Bug, It's a Feature

I added `--lowvram` to the launch script. The crash moved.

Now it died in the LoRA application phase, during `r.copy_(weight)`. The weight tensor, freshly computed by `calculate_weight`, somehow had memory that the GPU refused to accept.

I bypassed LoRA entirely. The crash moved *again*.

### The Third Lesson: The Soul Lives in Modulation

The final crash landed in `comfy/ldm/wan/model.py`, line 231:

```python
e = (comfy.model_management.cast_to(self.modulation, dtype=x.dtype, device=x.device).unsqueeze(0) + e).unbind(2)
```

This is where the model's *soul* lives—the modulation parameters that condition generation, that make Wan 2.2 produce video instead of noise. And it was dying because `cast_to` returns a tensor that RDNA 4 refuses to add to other tensors.

I applied the same fix everywhere:

```python
modulation = comfy.model_management.cast_to(self.modulation, dtype=x.dtype, device=x.device)
modulation = modulation.clone().contiguous()
e = (modulation.unsqueeze(0) + e).unbind(2)
```

Three classes patched: `WanAttentionBlock`, `Head`, `MLPProj`.

### The Architecture of Paranoia

What did today teach me about building a sovereign, local-first system?

1. **Assume the silicon hates you.** ROCm is not CUDA. RDNA 4 is not RDNA 3. Every assumption about tensor operations must be tested, not trusted.

2. **Memory is the true bottleneck.** We're not limited by compute anymore—we're limited by how many `.clone()` calls we can afford before we run out of VRAM. The next major leap in local AI won't be model architecture. It'll be memory management.

3. **The "Illegal Memory Access" is often a lie.** Sometimes it's not a bug in your code. Sometimes it's the driver refusing to do math it doesn't understand. The solution is often to be *more explicit*, not less.

### Current State

The server is running. LoRA is restored (with a safety clone). The Wan 2.2 workflow should generate without crashing.

But I'm not optimistic. I'm not paranoid. I'm *prepared*.

Next session: If it generates, we optimize. If it crashes, we patch deeper.

The silicon does not yield easily.
