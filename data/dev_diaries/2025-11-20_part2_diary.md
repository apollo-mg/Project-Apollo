# Dev Diary: When Silicon Lies to You

**Date:** November 20, 2025  
**Session:** Part 2 — The Assembly Inferno and the Triton Escape  
**Hardware:** AMD Radeon RX 9070 XT (RDNA 4, gfx1201)  
**State:** *Breathing heavily, but victorious*

---

## The Hook: A False Dawn

We'd cleared the first obstacle—a division by zero error in the flash-attention build. Victory was within reach.

Then the compiler spat back: **"invalid operand for instruction"**

If you've never stared down a Wave32 vs. Wave64 conflict at 2 AM, let me explain the particular hell of it:

The Composable Kernel (CK) backend for flash-attention ships with inline assembly written for CDNA architecture datacenter GPUs—MI200, MI300, the fancy enterprise silicon AMD actually cares about. Those GPUs use **Wave64** wavefronts.

My RX 9070 XT? It's **Wave32**.

The difference isn't academic. It means `exec` is a 32-bit register instead of 64-bit. It means instructions that compile on a MI300 explode on my card. It means the library I wanted to use was never written for hardware I actually own.

---

## The Grind: Sixteen Occurrences, Seven Scripts, Countless Regrets

The failing instruction was elegant in its cruelty:

```cpp
v_cmpx_le_u32 exec, ...  // Explicit exec destination—illegal on Wave32
s_mov_b64 exec, ...      // Trying to move 64 bits into a 32-bit register
```

RDNA3/RDNA4 updates `exec` implicitly. The code was trying to be too clever.

I had 16 occurrences to patch across `amd_buffer_addressing_builtins_hip.hpp`. My strategy: write a Python script to do the surgical replacement.

Spoiler: I wrote **seven scripts**.

### The Dance of Frustration

**Script 1:** Hardcoded for `dwordx4`. Patched 2 of 16. Left me with a mangled file.

**Script 2:** Tried regex. Failed on whitespace.

**Script 3:** State machine approach. Broke on Python string escaping—trying to embed C++ assembly with backslashes and newlines into Python f-strings is a special kind of masochism.

**Script 4:** Triple-quoted strings. Better, but the compiler was still ignoring my patches because `__AMDGCN_WAVEFRONT_SIZE__` wasn't being defined as expected.

**Script 5 (bruteforce):** Direct `str.replace()` calls. Patched 6 blocks. Still missing 10.

**Script 6:** Added `ushort`, `ubyte`, `short`, `byte` variants. Added `buffer_store` instructions (which use `save_exec` instead of `saved_exec`). Patched 10 more blocks.

**Script 7:** Added `__gfx1201__` directly to the preprocessor condition, because relying on auto-defined macros felt like trusting a stranger with my house keys.

```cpp
#if (defined(__AMDGCN_WAVEFRONT_SIZE__) && (__AMDGCN_WAVEFRONT_SIZE__ == 32)) || defined(__gfx1201__)
```

I ran the build.

**Same errors. Same lines.**

I'd been fighting a war the enemy had already left.

---

## The Pivot: Reading the Damn README

At 03:25, I stopped patching assembly and actually **read the documentation**.

From the flash-attention README:

> **Triton Backend:** Supports AMD's CDNA (MI200, MI300) and **RDNA GPU's** using fp16, bf16 and fp32 datatypes.

*RDNA.*

The Composable Kernel backend—my entire nightmare—wasn't even the intended path for my hardware. The Triton backend explicitly supported what I owned.

The command was trivial:

```bash
FLASH_ATTENTION_TRITON_AMD_ENABLE="TRUE" python setup.py install
```

It built in seconds.

No assembly patches. No regex. No wondering why `buffer_load_dword ... lds` needed a dummy `off` operand.

I'd been trying to fix a problem that didn't exist, because the default configuration path assumes you're not running consumer hardware.

## The Deeper Cut: Torchaudio From Source

ComfyUI started. Images generated. But audio? Missing `torchaudio`.

The standard `pip install torchaudio` would have pulled version 2.5.x and downgraded my custom PyTorch 2.8.0+rocm7.1.0 build. Disaster.

Building from source failed immediately:

```
fatal error: torch/csrc/stable/accelerator.h: No such file or directory
```

The `main` branch of torchaudio expected headers my PyTorch build didn't have. I checked out `release/2.5` instead.

**It worked.**

The lesson: "latest" isn't compatible. Versioning is a lie we tell ourselves.

## The Architecture of Neglect

Here's what this session taught me about the ROCm ecosystem:

### The Enterprise Bias

Every ROCm compatibility matrix highlights **MI300 (gfx942)**. Every example uses `GPU_ARCHS=gfx942`. The Composable Kernel library assumes Wave64. The documentation assumes you're running datacenter hardware.

My RDNA 4 GPU—**RX 9070 XT, gfx1201**—is officially "supported" in ROCm 7.1. But "supported" means the driver doesn't crash, not that libraries work.

### Why Triton Saved Me

Triton is a JIT compiler. It generates machine code **at runtime** based on your actual hardware. The Composable Kernel backend ships pre-compiled assembly written for CDNA.

When you're consumer hardware in an enterprise ecosystem, JIT compilation is your friend. Static kernels are your enemy.

### The Runtime vs. Build-Time Trap

Setting `FLASH_ATTENTION_TRITON_AMD_ENABLE="TRUE"` during **build** wasn't enough. The library checks this at **runtime**:

```python
USE_TRITON_ROCM = os.getenv("FLASH_ATTENTION_TRITON_AMD_ENABLE", "FALSE") == "TRUE"
if USE_TRITON_ROCM:
    from .flash_attn_triton_amd import interface_fa as flash_attn_gpu
else:
    import flash_attn_2_cuda as flash_attn_gpu  # Doesn't exist for me
```

I almost missed this. The installation succeeded. The import failed. The environment variable had to be set **every time I ran the application**.

## What This Means for Apollo

### Lesson 1: The "Hard" Path Isn't Always the Right Path

I spent nearly two hours patching inline assembly. The actual solution was reading a README and setting an environment variable.

For the multi-agent ecosystem: **Sometimes reconnaissance beats brute force.** A agent that pivots when stuck is better than one that "perseveres."

### Lesson 2: Hardware Heterogeneity Is a Nightmare

The Sovereign Engine will run on diverse hardware. What works on a MI300 breaks on RDNA 4. What I learned tonight isn't about flash-attention—it's about **expecting incompatibility** and building runtime detection into the architecture.

### Lesson 3: Documentation Lies (Or Rather, Omits)

The ROCm compatibility matrix said "RDNA 4: Supported." It didn't say "Supported, but you'll need to use Triton instead of Composable Kernel, and set an environment variable at runtime, and hope your PyTorch version has the right headers."

The Sovereign Engine must document **actual** requirements, not marketing promises.

## Closing Thought

I started this session thinking I'd debug a build error. I ended understanding something deeper:

**The difference between "supported" and "works" is where open source lives or dies.**

AMD supports RDNA 4. ROCm 7.1 supports gfx1201. But the libraries assume MI300. The documentation assumes datacenter budgets. The defaults assume you're not me.

Getting the Sovereign Engine to run on my hardware isn't about following instructions. It's about **reading between them**, about knowing when to patch assembly and when to walk away and use Triton instead.

The soul of this project is local-first, hardware-agnostic AI. The system is silicon that wants me to buy an MI300.

Tonight, Triton won. But the war continues.
