### The Memory Corruption That Taught Me Everything

The crash was inevitable. I just didn't expect it to arrive wearing such polite packaging.

A `torch.AcceleratorError` claiming "an illegal memory access was encountered" — as if the GPU had simply forgotten where it was allowed to live.

---

## The Setup That Should Have Worked

Let's walk through the theater of operations:

The RX 9070 XT reports 16GB of VRAM. PyTorch sees it. ROCm 7.1 acknowledges it. Everything nods politely at one another. The DisTorch2 virtualization layer does its accounting dance:

```
cuda:0   recip      15.92GB   25.92GB  +10.00GB  ← Virtually extended
cpu      donor      31.26GB   21.26GB  -10.00GB  ← RAM as backup
```

The math is beautiful. The poetry is elegant. We're borrowing 10GB of virtual capacity from system RAM and presenting it as if the GPU itself had grown new muscle.

Then we load Wan2.1-T2V-14B, quantized to Q4_K_M. A 14-billion parameter text-to-video model that wants to live in my living room.

And here's where the first lie reveals itself:

```
Device             Layers   Memory (MB)   % Total
cuda:0 (<0.01%)        73          0.48      0.0%
cpu                   169       6419.00    100.0%
```

**Almost the entire model is sitting in system RAM.**

The DisTorch2 allocator decided that the GPU was too precious to burden with weights. It would stream layers in as needed. It would be efficient. It would be clever.

It was lying to itself.

---

## Where Silicon Betrayed Me

The crash happens at line 247 of `ComfyUI-GGUF/ops.py`:

```python
return torch.nn.functional.linear(input, weight, bias)
```

A simple linear layer. The most fundamental operation in the entire transformer architecture. And yet, somewhere in that `forward_ggml_cast_weights` function, something reaches for memory it doesn't own.

The warning fires first:
```
HIP warning: an illegal memory access was encountered
```

Then the kernel surrenders.

The question isn't whether the code is wrong. The question is *whose fault it is to be right*.

---

## Three Suspects

**Suspect #1: The GGUF Casting Path**

The weights arrive quantized — Q4_K blocks compressed into oblivion. They must be dequantized on-the-fly, cast to fp16, then fed to the compute units. The GGUF ops layer is doing all of this in custom kernels that I didn't write and can't fully see.

When `forward_ggml_cast_weights` touches memory that ROCm refuses to bless, the question becomes: did the quantization metadata corrupt? Did the dequantization routine overshoot its buffer? Or is there a precision mismatch between what the kernel expects and what PyTorch handed it?

The warning mentions a specific file path in PyTorch's HIP implementation:
```
/pytorch/aten/src/ATen/hip/impl/HIPGuardImplMasqueradingAsCUDA.h:83
```

"MasqueradingAsCUDA" — the name itself is a confession.

**Suspect #2: DisTorch2's Virtual Memory Theater**

The DisTorch2 logs show a model that's 100% resident on CPU RAM but *virtually* attached to the GPU. When the sampler needs layer weights, it must stream them across PCIe, cast them, compute, then evict.

But look at the allocation string:
```
cuda:0,0.0000;cpu,0.3199
```

Almost nothing on the GPU. The streaming layer must be fetching weights on demand. If that fetch path has a race condition — if metadata arrives before weights do, if a pointer dereferences before the PCIe transfer completes — the HIP kernel will scream exactly this error.

**Suspect #3: The AMD Tax**

The transcript mentions environment variables I hadn't considered:
- `AMD_SERIALIZE_KERNEL=3` — forces synchronous kernel execution
- `TORCH_USE_HIP_DSA` — enables device-side assertions

HIP errors are *asynchronously reported*. The stack trace might be incorrect. The error might have happened three kernels ago and only manifested when the GPU decided to tell me about it.

This is the AMD tax: you don't own your own errors. They belong to the hardware now, and the hardware will return them when convenient.

## The Philosophical Problem

Here's what keeps me up at night:

The Sovereign Engine is supposed to be *sovereign*. Local-first. Running on consumer hardware that I actually own. But every layer of this stack is an abstraction someone else built, patched, extended, and then patched again.

- ComfyUI wraps the diffusion pipeline
- ComfyUI-GGUF wraps the quantization
- DisTorch2 wraps the memory management
- PyTorch-ROCm wraps the GPU
- HIP wraps the silicon

When memory corruption happens, *none of us know whose abstraction failed first*.

The error is real. The symptoms are measurable. But the causal chain is lost in wrappers.

---

## The Fix I'm Actually Going to Try

Tomorrow's experiments, in order of increasing desperation:

1. **Serialize everything**: `AMD_SERIALIZE_KERNEL=3` and see if the error vanishes. If it does, I've found a race condition. If it doesn't, the race was a red herring.

2. **Force GPU residency**: Disable DisTorch2's clever layer-splitting. Load the entire Q4_K model into VRAM even if it means batch_size=1 and praying. If that works, the streaming path is broken.

3. **Bypass GGUF**: Load the full fp16 checkpoint and quantize at runtime. Brutally expensive. But if GGUF's dequantization kernels are the culprit, this proves it.

4. **The nuclear option**: Rebuild PyTorch from source with `TORCH_USE_HIP_DSA` enabled. Get device-side assertions. Let the GPU tell me *exactly* which pointer it hated.

---

## What This Means for the Ecosystem

The local-first multi-agent vision survives on one assumption: that consumer hardware can run sophisticated models predictably.

This crash proves that assumption is naive.

The path forward isn't "more abstraction." It's the opposite. I need to understand the memory model deeply enough to predict where the abstractions will leak. I need to know when to trust DisTorch2 and when to tell it to get out of the way.

The Sovereign Engine doesn't need to be perfect today. But it needs to fail *understandably*. And right now, "HIP error: an illegal memory access was encountered" isn't understandable — it's a shrug.
