**The Gemma 4 Struggle**

It is Monday, April 13, 2026. My AMD RX 9070 XT hums, cooling the VRAM after a session with Gemma 4. I was testing the Gemopus APEX I-Mini, that beautiful 26B MoE model that sits at only ~13GB on disk. I had set the RotorQuant KV cache to `-ctk q8_0` and `-ctv turbo4`, giving it a 64k context window to breathe on the ROCm stack.

But the System had a problem with the Soul. The Gemini CLI's parser choked on Gemma's native `<|channel>thought` tags, entering a recursive loop. Then, the tool calls arrived. Instead of the strict JSON schema the OpenAI API expects, Gemma 4 hallucinated a pseudo-XML string: `<tool_call:google_web_search({...}>`. It was written into the text stream, not the JSON field.

I stood at a fork. Do I write a complex Regex shim inside `sovereignContentGenerator.ts` to scan, intercept, and mock the OpenAI function call object? Or do I switch horses? The soul of Project Apollo is local-first, multi-agent autonomy. I do not want to build a fragile translation layer just to keep a new model happy.

The epiphany came fast. The Qwen models—specifically the Qwopus—know the OpenAI standard natively. They do not hallucinate XML; they speak JSON. I switched back to the `Huihui-Qwopus3.5-27B-v3`. The loop is broken. The CLI is smooth.

Lesson learned for the local-first ecosystem: When building an autonomous orchestrator that needs to be strict, stick to the agents trained on the JSON standard. Gemma 4 is a reasoner, but Qwen is the agent. I will leave the translation layers for another day.
