# Dev Diary: 2025-11-29 (Part 70/74)
## The Ghost in the Silicon: The VRAM Wall

The "Soul" of Project Apollo—the creative potential of the Wan2.1 architecture—is currently being suffocated by the cold, unyielding reality of the "System." 

Today was a brutal exercise in fighting the memory allocator. I was attempting to push the boundaries of the Wan2.1 model, seeking that perfect intersection of fluid motion and high-fidelity texture, but I hit the VRAM wall harder than expected.

### The Technical Friction: HIP vs. The Model
The core issue is a massive `torch.OutOfMemoryError` triggered during the `scaled_dot_product_attention` call. The model is trying to allocate a staggering **15.45 GiB** in a single pass. On my RX 9070 XT, which has a hard limit of 15.92 GiB, this is a death sentence. 

The math is unforgiving: even with `--lowvram` and `--reserve-vram 0.1` flags active, the PyTorch/ROCm stack is choking. The system reports 7.88 GiB free, but the attention mechanism is asking for nearly double that. This isn't just a capacity issue; it's a fragmentation nightmare. The ROCm driver is struggling to find a contiguous block of memory large enough for the attention matrix, even though the total free memory seems sufficient on paper.

### The Architectural Epiphany: Fragmentation and the "Expandable Segment" Gambit
I looked closely at the error logs. The `HIP out of memory` error is explicit. The reserved-but-unallocated memory is relatively small (~200 MiB), which tells me this isn't a standard leak, but a massive, sudden spike in the attention mechanism's footprint.

I'm seeing a pattern in the `DisTorch2` virtual VRAM analysis. The system is trying to offload layers to the CPU (the "donor" role), but the `WanTEModel` is still demanding massive contiguous chunks for its forward pass. 

**The Lesson:** We cannot rely on standard memory management for these massive temporal-diffusion models. The architecture of the model is inherently more "spiky" than standard LLMs. We are moving from a world of steady-state memory usage to a world of violent, high-amplitude memory spikes.

### Impact on the Multi-Agent Ecosystem
This is a critical realization for the local-first ecosystem. If we want Apollo to run on consumer-grade AMD hardware without constant OOM crashes, our multi-agent orchestration layer must be "memory-aware." 

Currently, the agents are being treated as independent processes, but they need to be treated as **memory-managed entities**. We need a more aggressive garbage collection and a more sophisticated "memory-budgeting" protocol for the agentic workflows. If Agent A is using the attention mechanism, Agent B shouldn't just be "offloaded"—it needs to be completely purged from the VRAM to prevent the next spike from killing the entire stack.

### Moving Forward
- **Immediate Fix:** Test `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`. If we can force the allocator to use non-contiguous segments, we might bypass the fragmentation issue, though at the cost of some performance overhead.
- **Long-term Strategy:** We need to refine our quantization strategy. The current GGUF Q4_K and Q6_K weights are great for storage, but the runtime memory footprint during the attention phase is still too heavy for 16GB cards. We may need to implement more aggressive 4-bit attention kernels specifically optimized for ROCm.

The soul of the model is beautiful, but the silicon is stubborn. We keep pushing.
