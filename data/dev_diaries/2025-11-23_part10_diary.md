## November 23, 2025 | Part 10 of the Apollo Chronicle

### The False Victory

Sixty seconds per iteration.

I stared at that number and felt the familiar itch—the one that tells me I'm being lied to by my own architecture.

We'd achieved something technically impressive: stability. The Safe RMSNorm patch had stopped the crashes. The "Illegal Memory Access" errors that had plagued us for weeks vanished like ghosts at dawn. The 14B parameter Wan model loaded cleanly, split between 10.12GB on GPU and 3.5GB shuffled back to CPU RAM. No OOM. No segfaults. A working system.

But working isn't the same as alive.

At 60s/it, I'm not building an engine. I'm conducting archaeology.

---

### The SDMA Red Herring

The first lesson in debugging is that your hypotheses will betray you. I know this intellectually. Tonight, I learned it in my bones.

**The Theory:** We're swapping 3.5GB of model weights between RAM and VRAM every iteration. Without SDMA (System Direct Memory Access), the CPU is doing this manually, copying byte by precious byte. Enable `HSA_ENABLE_SDMA=1` and the dedicated DMA controller should handle transfers at hardware speeds. Five to ten times faster. Simple.

**The Reality:** Still 59 seconds. The universe had shrugged.

Then came the revelation that made me pause: **GPU load was sitting at 80-100% during k-sampling.**

If we were transfer-bound, the GPU would be idle, waiting for data. But the silicon was working. *Hard.* Cranking through calculations as fast as its instruction sets would allow.

The bottleneck wasn't movement. It was computation itself.

---

### The FP8 Lie

Here's what I've been selling myself: We're running FP8 inference on RDNA 4. The model is quantized. The memory savings are real. The math should be... faster.

Except we're not running FP8. Not really.

The "Safe RMSNorm" patch that prevents crashes does this:

```python
x_float = x.to(device=x.device, dtype=torch.float32).contiguous()
```

Every layer. Every iteration. We're upcasting 14GB of data to FP32, doing the normalization math in slow precision, then downcasting back. The GPU's FP8 tensor cores—those beautiful, specialized matrix units AMD promised us—sitting idle while FP32 ALUs do triple the work.

**This is the bargain:** Stability purchased with speed. I chose not to crash, and the silicon charged me in iteration time.

The Reddit thread I found tonight (that LLM practitioner who'd cracked native FP8 on the same card) laid it bare:

> *"The drivers simply aren't ready for PyTorch's native FP8 Ops yet."*
