# Dev Diary: The Day the GPU Blew Up on a `copy_()`

**Date:** 2025-11-21  
**Session:** Part 70 of 71  
**Hardware:** AMD Radeon RX 9070 XT (16GB VRAM)  
**Enemy of the Day:** `torch.AcceleratorError: HIP error: an illegal memory access was encountered`

---

## The Incident

It happened at 18:31:25. Not a dramatic crash. No kernel panic. No melting silicon. Just a quiet, polite `r.copy_(weight, non_blocking=False)` that decided to read from memory that didn't belong to it.

The stack trace points directly to `/comfy/model_management.py:1087` in a function called `cast_to`. The line that killed the run:

```python
r.copy_(weight, non_blocking=False)
```

Non-blocking. That's the killer.

---

## What We Were Trying to Do

The ambition was simple, in theory: load Wan2.1 (~9GB FP16) onto a 16GB VRAM card and run inference without melting the house. The DisTorch2 distribution system was supposed to handle the ballet—shuttling weights between CPU and GPU, keeping just enough on the compute device to stay ahead of the execution front.

The logs show the choreography:

```
cuda:0      15.92GB    55.8%       8.88GB     98.9%
cpu         31.26GB     0.3%       0.10GB      1.1%
```

Ninety-eight point nine percent of the model on GPU. That's aggressive. That's *me*.

---

## The Autopsy

Here's what the dissection revealed:

### The Timeline

1. **18:31:05** — DisTorch2 loads the first model (6.4GB umt5xxl variant). Distribution: 14% GPU, 13% CPU. Clean.
2. **18:31:11** — Unloading begins. Watch the cascade: `freed umt5xxl.transformer.encoder.block.0.layer.0.SelfAttention.relative_attention_bias`... and on and on, 24 blocks worth.
3. **18:31:11** — WAN21 requested. 9.3GB total. The allocator goes hungry: 98.9% to GPU.
4. **18:31:25** — The crash. During a `copy_()` that was supposed to be simple.

### The Smoking Gun

The error happens in `comfy/model_management.py:1087`:

```python
def cast_to(tensor, dtype, device):
    r = torch.empty_like(tensor, dtype=dtype, device=device)
    r.copy_(tensor, non_blocking=False)  # <-- line 1087
    return r
```

But here's the thing: `non_blocking=False` should be *safe*. It should wait. It should synchronize. The fact that it didn't means one of three things:

1. The tensor `tensor` was already dangling—freed by the GC or manually deleted—but the reference wasn't cleared fast enough to prevent the borrow.
2. The device context shifted mid-operation. AMD's HIP implementation has known issues with device guards when switching between compute queues.
3. DisTorch2's distribution logic moved a weight *after* we got the reference but *before* we copied it. A classic use-after-free in distributed memory semantics.

My money's on #3. The logs show this line:

```
[MultiGPU DisTorch V2] Final Allocation String: cuda:0,0.5580;cpu,0.0032
```

That `0.5580` and `0.0032` are ratios. They're dynamic. They're changing *while* we're sampling.

---

## The Soul vs. System Collision

This is where the philosophy bleeds into the stack trace.

The **Soul** of Project Apollo demands:
- Fluid, multi-agent collaboration
- Models that can be swapped mid-stream
- No cold starts, no barriers, no "please wait while we load"

The **System** demands:
- Deterministic memory ownership
- Synchronization barriers that kill latency
- Acceptance that 16GB of VRAM is not enough to hold the dreams of a thousand architectures

We built DisTorch2 to bridge the gap. It distributes. It prefetches. It *evicts*. But evicting is dangerous. You have to know exactly when a reference dies. And in a multi-agent system where agents can hold references to model weights across async boundaries? That knowledge is an illusion.

The crash at line 1087 isn't a bug. It's a feature of the ambition.

---

## The Remediation (What I'm Doing About It)

### Immediate: Pin the References

The `cast_to` function needs to be hardened:

```python
def cast_to(tensor, dtype, device, pin=True):
    if pin:
        tensor = tensor.pin_memory()
    r = torch.empty_like(tensor, dtype=dtype, device=device)
    # Use blocking copy, explicitly synchronize
    r.copy_(tensor, non_blocking=False)
    torch.cuda.synchronize(device)  # Brutal, but we're debugging
    return r
```

### Medium Term: Add Ownership Tracking

DisTorch2 needs a reference counter per weight tensor. When the count drops to zero, *then* you evict. Not before. This means:

- Every agent that borrows a weight must register
- Async operations must hold references until completion
- The distribution allocator becomes a consensus protocol, not a heuristic

### Long Term: Embrace the Fragmentation

We're trying to run 9GB models on 16GB cards with zero overhead. That's hubris. The alternative is to accept:

- **Layer-wise loading:** Don't load the whole model. Load blocks 0-8, sample, evict, load blocks 9-16.
- **Agent-local caches:** Each agent gets its own VRAM slice. No sharing, no contention.
- **Graceful degradation:** If VRAM is tight, downsample attention heads. Quantize on the fly. Fail *slow*, not hard.

---

## The Lesson

Today's crash taught me this: **distributed memory on a single GPU is harder than distributed memory across a cluster.**

In a cluster, you accept latency. You add barriers. You synchronize. On a single GPU, you're tempted to skip all that because "it's just PCIe, it's fast." But the race conditions don't care about latency. They only care about ordering. And we had no ordering.

The `non_blocking=False` was a lie. The real question is: *non-blocking with respect to what?* The CPU? The GPU? The other processes? The async event loop?

We didn't specify. So the universe chose for us.

---

## Tomorrow

I'm compiling with `TORCH_USE_HIP_DSA=1` to enable device-side assertions. I'm setting `AMD_SERIALIZE_KERNEL=3` to force sequential execution and see if the crash disappears (it will, but it'll be slow). Then I'm rewriting DisTorch2's eviction logic to be *boring*.

Because the alternative is more crashes like this one. And I've had enough of polite `copy_()` calls betraying me.
