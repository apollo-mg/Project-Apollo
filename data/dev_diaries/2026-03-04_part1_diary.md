# Apollo Dev Diary: 2026-03-04 (Part 1)

## The Silicon Ceiling and the Death of Eager Mode

Today was a brutal lesson in the friction between software elegance and the hard reality of RDNA 4 memory management. I spent most of the morning chasing a phantom in the VRAM, only to realize I was fighting the very architecture I was trying to optimize.

We attempted to benchmark the Qwen 3.5 9B FP8 on the RX 9070 XT. The initial run was a disaster—a total system freeze. I had enabled `enforce_eager=True` to bypass the instability of ROCm's graph compilation, but I didn't account for the massive memory footprint of the vision-language encoder combined with the 8-bit weights. 

The math was unforgiving: 12.5 GB for the weights, plus the overhead of the desktop environment (KDE Plasma), plus the memory required for the graph capture... it all pushed the 16GB card past the breaking point. The OS was starved of VRAM, causing a catastrophic lockup.

The realization was sobering: **Eager Mode is the performance killer.** While it's "safe," it forces a CPU-intensive round-trip for every single token. We saw a pathetic 13 TPS. It’s essentially like trying to run a race where you have to stop and check your pulse after every single step. The GPU is so fast it's sitting idle, waiting for Python to tell it what to do next.

## The GGUF Revelation

We've hit a critical divergence point in the local-first ecosystem. 

While vLLM is the "correct" way to do high-performance inference, our tests showed it is currently being crushed by Ollama's GGUF implementation. On this specific hardware, the unoptimized FP8 kernels in vLLM were lagging behind GGUF by a factor of 10x. The GGUF stack is far more efficient at maximizing bandwidth on this new RDNA 4 frontier. This changes how we prioritize the model hoard. If we want speed, we use GGUF; if we want pure, raw-metal tensor math, we have to wait for better FP8 kernel support.

## Infrastructure & Cold Storage

Despite the turbulence, the "Model Hoard" is stabilizing. I spent time debugging the sequential download worker, which was choking on a 404 error caused by a single space and a special character in a filename (`GLM-4.7-Flash...`). Once fixed, the worker is back online. 

The 80B Architect giant (Qwen3-Coder-Next) is currently crawling across the HDD, nearing completion. It's a slow burn, but it's a critical piece of the long-term intelligence archive.

## Lessons Learned & Next Steps

* **The VRAM/Desktop Conflict:** We cannot run high-performance Graph Mode (the high-speed "tape" mode) on a 16GB card while running a graphical desktop. The memory overhead is too high. To get the true 100+ TPS, we'll either need to move to a headless server or use smaller, 4-bit quantized models that leave room for the OS.
* **The Quantization Divide:** The 14B models worked before because they were 4-bit. This 9B model was 8-bit. The difference in VRAM pressure is non-linear.
