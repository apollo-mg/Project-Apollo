# Dev Diary: When Silicon Betrays You
## 2025-11-21 — The Night HIP Stole My Memory

---

### The Promise and the Betrayal

Sixteen gigabytes of VRAM staring back at me. The RX 9070 XT, gleaming with potential, promised to be the heart of something sovereign. Something *local-first*, as we call it now—the phrase that separates dreamers from people who still trust cloud APIs.

I wanted to run Wan2.1-T2V-14B. A video generation model. Ambitious? Yes. Necessary? Absolutely.

What I got instead was a crash that made me question whether AMD's ROCm stack was built by engineers or by engineers' grandchildren.

---

### The Autopsy

```
torch.AcceleratorError: HIP error: an illegal memory access was encountered
```

Beautiful, isn't it? The kind of error message that tells you everything and nothing. Like being told your house burned down due to "thermal events."

The stack trace led me somewhere surgical: `comfy/rmsnorm.py:27`. A single line. A single multiplication operation that decided to access memory it wasn't allowed to touch.

```python
return r * comfy.model_management.cast_to(weight, dtype=x.dtype, device=x.device)
```

The RMSNorm operation. Innocuous. Fundamental. The kind of operation you'd expect to work *perfectly* on any GPU ever made.

Except this wasn't "any GPU." This was AMD's attempt at CUDA parity, running on the newest architecture (gfx1201), with a quantized GGUF model (Q4_K_M), in LOW_VRAM mode, executing cross-attention in a transformer that wanted to generate video.

The stack was too tall. The margins were too thin.

---

### The Real Story: Memory as a Character

Look at the loading sequence:

```
loaded partially; 6429.60 MB usable, 6429.59 MB loaded, 3353.83 MB offloaded
```

That's the story right there. We're juggling. The model doesn't fit, so we offload. We stream between CPU RAM and GPU VRAM like a nervous system trying to remember where it put its keys.

The Wan2.1-14B model is 14 billion parameters. Even quantized to Q4_K, that's a beast. We're asking it to live in a 16GB house that really only has 6.4GB of actual bedroom space.

The crash happened during cross-attention—`model.py:254`, the `norm3` layer. That's where context meets computation, where the model tries to relate every token to every other token. It's the most memory-intensive operation in the entire transformer.

And ROCm said: *"I'll take that bet."*

---

### The Friction: Soul vs. Silicon

Here's what keeps me up at night:

**The Soul** wants sovereign AI. It wants video generation running on hardware I own, in a basement, with no telemetry, no API calls, no Terms of Service update that changes everything tomorrow. It wants the dream of local-first intelligence to be real.

**The System** is a 16GB GPU with a driver stack that's still learning what "stable" means. It's ROCm 7.1, which is to CUDA what a promising open-source project is to a billion-dollar ecosystem. It's brave. It's necessary. It's also occasionally insane.

The friction isn't a bug. It's the condition of building something new on hardware that wasn't designed for this exact use case.

---

### What I'm Learning

1. **HIP errors are lies.** The asynchronous nature means the crash you see might not be the crash that happened. The real error could be ten operations back, buried in a kernel launch that succeeded on paper but corrupted state in practice.

2. **Quantization is not a silver bullet.** Q4_K_M saves VRAM, yes. But the dequantization math has to be *perfect*. A single rounding error, a single misplaced pointer, and you're accessing memory that belongs to someone else.

3. **LOW_VRAM mode is a survival strategy, not a feature.** The fact that we need it at all tells you everything. We're not building for scale; we're building for *survival* on consumer hardware.

4. **The stack trace is a map of dependencies you didn't know you had.** ComfyUI → k_diffusion → torch → HIP → ROCm → AMD drivers → BIOS → the physical arrangement of transistors on a chip. Any layer can betray you.

---

### The Path Forward

I'm not done with the 9070 XT. I'm not done with ROCm. But I'm adjusting:

- **Serialization:** `AMD_SERIALIZE_KERNEL=3` might force synchronous execution and catch the real offender
- **Device-side assertions:** `TORCH_USE_HIP_DSA` could expose the memory corruption at the source
- **Batch size reduction:** Maybe 33 frames is too greedy for this configuration
- **Model exploration:** A smaller checkpoint might teach us something about where the boundary lies

The Sovereign Engine doesn't care about convenience. It cares about *sovereignty*. And that means learning to dance with hardware that hasn't finished growing up yet.

---

### The Question That Remains

Is the dream of local-first AI realistic on consumer AMD hardware in 2025?

The crash log doesn't answer it. But the fact that I'm still here, reading stack traces at 2 AM, suggests the answer isn't "no."

It's just... complicated.
