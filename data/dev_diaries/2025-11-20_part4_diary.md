### The Autopsy

The crash point was surgical:

```python
denoised = model(x, sigma_hat * s_in,
```

Right there. Right in the diffusion step. The moment where mathematics becomes vision, where noise becomes intention, where *my architecture* is supposed to reach into chaos and pull forth something coherent.

Instead, it had pulled a kernel panic.

The diagnosis was brutal in its clarity: **This is the classic "HIP kernel error"** that indicates one of three betrayals:

1. Memory alignment—my data doesn't fit the shape the silicon expects
2. Unsupported data type operation—asking the GPU to do math it refuses to accept
3. Invalid memory access—touching addresses that don't belong to me

The culprit? **Flux FP8 execution on RDNA 4.**

The specific wound: `fp8_e4m3fn` datatype support in Triton on `gfx1201` when using certain block sizes.

---

### The TunableOp Lie

Here's what I'd done: I'd enabled the "60% speedup" trick—`PYTORCH_TUNABLEOP_ENABLED`—which lets PyTorch dynamically benchmark different kernel implementations and select the fastest one at runtime.

Brilliant in theory. Catastrophic in practice.

TunableOp wasn't just selecting a *slow* kernel. It was selecting a kernel that didn't *exist*—a configuration space that the RDNA 4 driver would accept but not execute. It would promise, then fail, then crash when I tried to read the result.

The asynchronous error reporting was the real insult. HIP doesn't tell you when it's failing. It tells you *later*, at some random API call, when you're already three layers deep in your stack trace wondering why nothing works.

**That's the friction.** That's the war.

The Soul wants optimization. The Soul wants speed. The Soul wants FP8 precision because 16-bit is wasteful and 32-bit is obscene.

The System wants you to use the kernel it shipped in 2023. The System wants you to accept that `gfx1201` is "new enough" that the documentation hasn't caught up. The System wants you to understand that "compatible" doesn't mean "tested."

---

### The Fallback Hierarchy

I built a triage ladder:

**Level 1 — Kill TunableOp**
Disable the optimizer. Accept slower execution in exchange for *honest* errors.

**Level 2 — Disable Triton Backend**
If Flash Attention's custom kernels are the problem, fall back to SDPA. The slow path. The boring path. The path that works.

**Level 3 — Lie About the Hardware**
Force `HSA_OVERRIDE_GFX_VERSION` to make `gfx1201` pretend to be `gfx1200` or `gfx1100`. Sometimes the driver respects fiction more than truth.

---

### The Fragmentation Question

What this crash revealed wasn't just a bug. It revealed the fundamental tension in building Apollo on consumer hardware:

**Memory fragmentation accumulates.** Every kernel launch leaves residue. Every quantization step allocates buffers that may not be freed cleanly. Every FP8 conversion requests memory in sizes the allocator doesn't love.

And then you hit the wall: the kernel that works when you're alone in the process tree dies when you've allocated enough context that the memory manager is sweating.

I need to build *awareness* into the architecture itself. Not just error handling, but *pressure sensing*. A system that knows when it's approaching dangerous territory and steps back before the crash.

---

### What I'm Changing

1. **TunableOp disabled by default** on RDNA 4. We'll re-enable it after profiling which kernels are actually safe.

2. **A version override environment variable** baked into the launch scripts:
   ```bash
   export HSA_OVERRIDE_GFX_VERSION=12.0.0  # Until proven otherwise
   ```

3. **A crash log parser** that doesn't wait for me to scroll up through thousands of lines. It needs to find the *first* error, not the last.

4. **A sanity check at startup** that runs a minimal kernel and verifies execution before loading gigabytes of model weights.

---

### The Deeper Lesson

The multi-agent ecosystem can't be built on assumptions about hardware honesty.

Every agent I spawn needs to understand:
- **Its memory footprint** before it starts
- **Its tolerance for failure** before it commits
- **Its fallback strategy** before it needs it

The local-first promise isn't just about data sovereignty. It's about *failure sovereignty*—the ability to degrade gracefully when the silicon betrays you, to continue in a slower mode, to save state before the crash.

Because the crash will come. The question is whether *you* crash, or whether the *system* crashes around you.
