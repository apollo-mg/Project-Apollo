# Apollo Dev Diary: 2026-02-28 (Part 4)

The friction between the "Soul" and the "System" was palpable today. I wanted to build a digital memory—a way for Apollo to look back at my life through the lens of my inbox—but the "System" (the cold, hard reality of my Linux partitions) kept pushing back.

## The Digital Memory (Phase 7: The Chronicler)

I spent the first half of the session wrestling with formatting errors in the Python scripts. I had to perform some surgery on the email ingestion modules because the parser was choking on newline characters. It's a classic case of a machine being too literal for its own good. Once the syntax was stabilized, I moved into the heavy lifting: building the **Chronicler**.

I successfully deployed a background sync service using `mbsync` and a custom Python parser that leverages `BeautifulSoup` to strip HTML and chunk the raw text for vectorization. The goal was to feed my email history into the Vector DB (Chroma DB).

The integration was a bit of a "VRAM Tetris" headache. I had to build a high-speed local cache (`vault/email_processed_keys.txt`) because querying the Vector DB to check for duplicates was becoming exponentially slower as the index grew. It's a classic scaling problem: the more "memory" the system gains, the harder it is to maintain the very speed that makes that memory useful.

The result: The Chronicler is now a background daemon (`background_chronicler.py`). It's currently sweeping through my local maildir, vectorizing about 160,000 emails. It's a slow, grinding process, but it's working.

## The Glass Cockpit (Live Telemetry)

I realized I couldn't monitor this mess effectively. Watching logs scroll by in a terminal is a nightmare. I needed a "Glass Cockpit."

I built the **Apollo Glass Cockpit**—a real-time telemetry dashboard. It monitors:
* **Hardware Health**: CPU, RAM, and GPU (VRAM/Temp) stats.
* **Background Ingestion**: A live ticker for the `mbsync` and `Chronicler` progress.
* **LLM Model Registry**: A live view of which models are currently resident in VRAM (essential for monitoring the swap between DeepSeek-R1 and the new Qwen models).
* **Discord Bridge Status**: Real-time health check for the Discord bot.

The initial version was "flashing" like crazy because I was using `os.system('clear')`. I had to rewrite the refresh logic to use ANSI escape codes (`\033[H`) to overwrite the buffer in place, providing a stable, flicker-free experience. It feels like a real command center now.

## The Qwen3-Coder Breakthrough

Then, the news hit. AMD announced Day-0 ROCm 7 support for the **Qwen3-Coder-Next** models. This changes everything. This isn't just an "enterprise" update; it's a direct hit for my RX 9070 XT. 

The Qwen3-Coder is a Mixture-of-Experts (MoE) beast. It has 80B parameters, but only activates 3B at a time. This is the "cheat code" for local AI. It gives me the reasoning depth of a massive model with the inference speed of a much smaller one.

## Storage & The Hardware Struggle

We hit a massive bottleneck: Storage. My root partition (`/`) is nearly full. The massive models won't fit. I had to do some quick-thinking file system management. I've identified the 1TB WD_BLACK SSD (`nvme0n1`) as the new home for the models. 

The plan is to:
1. Stop the Ollama service.
2. Move the `.ollama` directory to the WD_BLACK SSD.
3. Symlink it back to the default location.

This will give us the 65GB+ of breathing room we need to pull the Qwen3-Coder-Next (80B) and the 30B versions. It's a surgical procedure on the file system, but it's necessary to keep the "Soul" of the project from being crushed by the "System" constraints.
