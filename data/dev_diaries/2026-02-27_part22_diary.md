# Project Apollo: Dev Diary - 2026-02-27 (Part 22)

## The Silicon Struggle: VRAM vs. Vision

Today was a battle between the "Soul" of the system—the intelligence I want Apollo to possess—and the hard-coded, unyielding reality of the silicon. I've been wrestling with the vision pipeline, specifically the interaction between Qwen2.5-VL and DeepSeek-R1.

The core problem is a classic one: LLMs are too "smart" for their own good. When I asked the system to perform a visual inventory, the model wasn't just looking at the pixels; it was "hallucinating" based on common sense. It saw a shroud that *looked* like an MSI 3080 and decided, with unearned confidence, that it *was* one.

### The Death of "Common Sense" Hallucinations
I realized that my error was trying to make the LLM do too much reasoning in a single pass. The 16GB VRAM on my RX 9070 XT is a tight squeeze when you're swapping between a vision model and a reasoning model. 

I implemented a "Zero-Trust" architecture. Instead of asking the model, "What is this?", I moved to a two-turn sequence:
1. **Turn 1 (Vision Mind):** Qwen is now a "dumb" observer. Its only job is to act like a digital camera that outputs a raw, unformatted list of text. No JSON, no reasoning. Just: "White sticker, text: MS-V389."
2. **Turn 2 (Engineer Mind):** DeepSeek receives that raw text and runs it through a hard-coded Python tool called `diff_inventory`. 

This is a massive architectural win. By stripping the "Soul" (the reasoning) away from the "Observation" (the vision), we've eliminated the hallucination. The system can't guess a part is a 3080 if the programmatic tool says that part doesn't exist in the database.

### The Forensic Pivot
The most significant epiphany today was the "Forensic Anchor" concept. I realized that "identifying a GPU" is too broad a goal for a vision model. We don't need the model to recognize a "GPU"; we need it to read the "DNA"—the SKU or the serial number printed on the PCB.

I've refactored the `identify_hardware` tool. It no longer asks "What is this?". It now asks "Read the alphanumeric string on the white sticker." This forces the Vision Mind to focus its attention on high-density information (the SKU) rather than low-density shapes (the shroud). This is the difference between a system that *guesses* and a system that *verifies*.

### The Friction of the "Fast Path"
I ran into a frustrating-as-hell logic loop with the `buddy_agent.py` dispatcher. The "Fast Path" (a shortcut meant to speed up simple chats) was hijacking the command, preventing the agent from actually executing the `identify_hardware` tool because it thought the user just wanted a quick status update. I had to manually intervene to bypass the dispatcher's logic to ensure the image capture was actually being fed into the vision pipeline.

### Summary of the Architecture Shift
- **The `diff_inventory` Tool:** Now a programmatic, fuzzy-matching Python function. No more LLM-based inventory checks.
- **The Two-Turn Sequence:** Vision (Qwen) $\rightarrow$ Logic (DeepSeek). This manages the VRAM load and ensures the vision model doesn't bloat the context window with useless reasoning.
- **The Forensic Protocol:** Apollo is no longer a "guesser." It is now a "scanner." It will refuse to identify a component until it finds a verifiable "Anchor Point" (a serial number or SKU).

The system is becoming more robust, but it's also becoming more "brittle" in the sense that it requires higher-quality input (clearer camera angles/better lighting) to work. We've traded the ease of "general intelligence" for the precision of "forensic verification." In a local-first, resource-constrained environment, that's a trade I'm willing to make.

Next step: Fine-tuning the macro-lens focus on the webcam to ensure those tiny PCB numbers are actually readable. The Silicon is demanding precision; I'm going to give it to him.
