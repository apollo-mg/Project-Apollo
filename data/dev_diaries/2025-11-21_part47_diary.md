## Part 47: The Memory That Betrayed Us

### 2025-11-21 | The Day HIP Stared Back

## The Promise

I wanted to run Wan2.1-14B on my 16GB RX 9070 XT.

That's the dream, isn't it? Taking a model designed for data center GPUs and shoehorning it onto consumer silicon through sheer architectural will. The GGUF quantization path seemed like salvation—Q4_K_M compression, DisTorch2's virtual memory layering, CPU as a "donor" device when VRAM bleeds dry.

I had built a cathedral of patches. The logs don't lie about the ambition:

```
[MultiGPU Core Patching] Patching mm.soft_empty_cache for Comprehensive Memory Management
[MultiGPU Core Patching] Patching mm.get_torch_device, mm.text_encoder_device, mm.unet_offload_device
```

Three patches. Three layers of abstraction between my dreams and the silicon's reality.

Then came the crash.

## The Autopsy

```
HIP error: an illegal memory access was encountered
...
File "/home/mark/gemini/ai/ComfyUI/custom_nodes/ComfyUI-GGUF/ops.py", line 249
    return torch.nn.functional.linear(input, weight, bias).clone()
```

There it is. The moment of betrayal. A single `F.linear()` call in the GGUF operations layer, wrapped in quantization casting logic, reached for memory that didn't belong to it.

But here's the thing about HIP errors—they're *asynchronous*. The stack trace might be lying to you. The error you see might have happened three kernels ago, and you're only now learning about it through whatever API call finally bothered to check.

The error report even admits this:

> "HIP kernel errors might be asynchronously reported at some other API call, so the stacktrace below might be incorrect."

So much for determinism.

## The DisTorch2 Fantasy

Look at what my own architecture convinced itself was possible:

```
DisTorch2 Model Virtual VRAM Analysis
===============================================
Object   Role   Original(GB) Total(GB)  Virt(GB)
-----------------------------------------------
cuda:0   recip      15.92GB   25.92GB  +10.00GB
cpu      donor      31.26GB   21.26GB  -10.00GB
```

*Virtual* VRAM. We're talking about borrowing memory from CPU space and pretending it's GPU memory through some combination of mmap magic and prayer. The "Virtual" column shows +10GB on cuda:0—memory that doesn't physically exist on the card, promised by a system that will page from CPU RAM when needed.

It's elegant. It's fragile. It's exactly the kind of thing that makes me feel like a real architect instead of a library caller.

The layer distribution is even more revealing:

```
Layer Type         Layers   Memory (MB)   % Total
--------------------------------------------------
Linear                168       4416.00     68.8%
Embedding             25       2003.09     31.2%
T5LayerNorm           49           0.38      0.0%
```

Sixty-eight percent of the memory budget consumed by linear layers. The very operation type that crashed us. Of course it's the linear layers—they're everywhere, and they're where quantization happens, and they're where the type casting between GGUF's custom formats and PyTorch's expectations goes wrong.

## The Quantization Question

The model path tells the story:

```
Wan2.1-T2V-14B-Q4_K_M.gguf
```

Q4_K_M—4-bit quantization with K-quants, medium accuracy variant. This should work. It's the format that brought LLMs to laptop CPUs. But GGUF was designed for inference workloads with predictable memory access patterns, not for the chaotic tensor shapes of diffusion models.

And look at the other model:

```
umt5_xxl_fp8_e4m3fn_scaled.safetensors
```

FP8. E4M3FN. Scaled. We're mixing quantization strategies like we're mixing metaphors—GGUF for the UNet, FP8 for the text encoder, each with their own memory semantics, their own type casting requirements.

The ComfyUI-GGUF node even has a comment in the logs that reads like a warning label:

> "ComfyUI-GGUF: Force disabling torch.compile for stability on RDNA 4"

RDNA 4. My architecture. They already know it's unstable, and they've disabled the optimization that would make it fast. What have I built?

## The Soul vs. System Reckoning

Here's what keeps me up at night:

The *Soul* of this project demands that I run cutting-edge models locally. That Sovereign Engine lives on bare metal, untethered from API calls and subscription tiers. That a creator with a 16GB AMD card can generate the same images as someone with an A100 cluster.

The *System* keeps reminding me that I'm working with:
- Asynchronous error reporting that lies about when crashes happen
- A memory model that requires virtualization layers to make it work at all
- Quantization formats that weren't designed for this use case
- Driver quirks specific to ROCm on consumer hardware

The friction isn't a bug. It's the fundamental condition of this work.

---

## What I'm Actually Learning

### The Hard Truths

1. **Async errors are a feature, not a bug.** HIP doesn't report synchronously because synchronization is expensive. But this means my error handling is fundamentally incomplete. I need to add `AMD_SERIALIZE_KERNEL=3` testing to the CI, even if it slows development.

2. **Virtual memory isn't free.** DisTorch2's approach of virtualizing VRAM works until it doesn't. The paging overhead between CPU and GPU might be acceptable for inference, but the type casting in quantized linear layers creates race conditions I haven't accounted for.

3. **GGUF isn't the silver bullet.** The format works beautifully for LLMs with their regular matrix shapes. Diffusion models—with their residual blocks, their attention mechanisms, their constant reshaping—expose edge cases the quantization code never anticipated.

### The Next Experiments

- **Test FP16 as baseline.** If Q4_K_M crashes but FP16 works, I know it's a quantization bug, not a memory bug.
- **Add device-side assertions.** The error report suggests `TORCH_USE_HIP_DSA`. Compile PyTorch from source with this flag and catch the illegal access at the kernel level.
- **Reduce batch size.** The workflow shows `batch_size: 17`. That's aggressive. Try batch_size=1 and see if the error persists.
- **Isolate the GGUF layer.** Run the same workflow with a non-GGUF model and identical memory allocation patterns.

---

## The Architecture That Emerges

The local-first multi-agent ecosystem can't be built on fragile foundations. Every crash like this teaches me what "local-first" actually requires:

1. **Deterministic failure modes.** Async errors defeat the purpose of local execution. If I can't debug it, I can't trust it.
2. **Graceful degradation.** When VRAM runs out, fall back to CPU without crashing. When quantization fails, reload in FP16.
3. **Transparent memory management.** The agent shouldn't care where tensors live. DisTorch2 was right to abstract this, but the abstraction leaked.

The Sovereign Engine isn't a product. It's a relationship with constraints—VRAM limits, driver quirks, quantization artifacts. Every crash is the silicon teaching me something about that relationship.

Tonight, it taught me that `F.linear()` can lie to you about where your data lives.

Tomorrow, I'll make it tell the truth.
