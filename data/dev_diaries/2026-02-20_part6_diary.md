# Project Apollo: Dev Diary - 2026-02-20 (Part 6)

The friction between silicon and soul is reaching a breaking point. Today was a frantic dance between high-level architectural breakthroughs and the brutal reality of running local LLMs on a single 16GB RX 9070 XT.

### The Voice/Vault Breakthrough
The goal was simple: a seamless, local-first voice assistant that can actually "read" my physical world via the vault. We achieved a milestone with the integration of `shop_buddy_voice.py`. The system successfully identified and ingested a PDF from a web search, mapped it to the vector DB, and—most importantly—summarized the technical specs of a BTT Octopus-Pro motherboard without tripping over its own feet.

The output was clean. The cryptic filenames were mapped to human-readable titles. The "Soul" of the agent is starting to emerge, but the "System" is still screaming about VRAM. The `ALSA lib` underruns in the audio buffer are a constant reminder that even when the logic is sound, the hardware-software interface is still a mine나 (nightmare).

### The Receptionist Pattern
We hit a massive realization regarding agentic architecture. Currently, we are forcing a single "Engineer" model (DeepSeek R1 14B) to do everything: act as a conversationalist, a logic processor, and a tool executor. It’s too heavy. It's too slow. It causes that "awkward hang" in voice playback where the agent stays silent while it's thinking.

I’ve decided to implement the **"Receptionist/Dispatcher"** pattern. 

The plan: 
1. A tiny, lightning-fast model (Llama 3.2 3B) sits at the front door. 
2. It handles the "Hi Jarvis" and the "What do you mean by that?" queries.
3. Only when a specific `WORK` intent is detected does the heavy DeepSeek "Engineer" spin up.

This solves the latency issue. The user gets an immediate response, even if the heavy lifting takes a few seconds. It's the difference between a waiter who acknowledges you immediately and a waiter who disappears into the kitchen for ten minutes.

### The VRAM War & Storage Crisis
This is where the "System" hits hardest. My root partition is at 98%. I'm essentially living on the edge. Running multiple Python venvs is eating my SSD alive—35GB gone just to various environments. 

I realized I can't just download every model to test the "Heavy Receptionist" theory. My SSDs (the NVMe drives) are packed. The 2TB drive is a mechanical HDD, which is death for model loading times. I have to be surgical. 

The benchmark I ran showed that Llama 3.2 (3B) is incredibly fast (100 t/s) and handles simple triage perfectly. The 8B model is more accurate for nuance but adds a 230ms penalty. In a voice-first world, 230ms is the difference between a tool that feels alive and one that feels like a toy.

### The Chaos of the Real World
The session ended in a blur of API limits and authentication loops. Between hitting the Google Cloud quota and the constant dance of re-authenticating the Code Assist login, it's clear that even the best architecture can't escape the bureaucracy of the cloud. 

I'm left with a choice: Do I build a smarter, bigger "Receptionist" that takes up more VRAM, or do I stick to the "Lite" version and accept that my agent might occasionally miss a nuance?

The next step is a stress test. I need to see if the 3B model can handle the "messy" reality of human speech before I commit to a larger model that might starve the Engineer of VRAM.

**Current Status:**
- Architecture: Transitioning to Receptionist/Engineer split.
- Hardware: VRAM is stable, but Disk Space is critical.
- Next Task: Run high-complexity linguistic stress tests on the triage layer.
