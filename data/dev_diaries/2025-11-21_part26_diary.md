## The Hubris

I wanted to run Wan2.1-T2V-14B on this 16GB RX 9070 XT.

Let me be clear: this was not a reasonable request. This was a 14-billion parameter video generation model, quantized to Q4_K (four bits per weight, packed with surgical cruelty), and I was asking it to render at 832×480 with a batch size of *seventeen*.

Seventeen.

I don't know what I was thinking. The Soul demanded cinematic drone shots of cyberpunk cities. The System responded with a segmentation fault.

---

## The Autopsy

The crash landed in the most unglamorous place imaginable:

```python
sc = torch.cat([d & 0x3F, (m_d & 0x0F) | ((d >> 2) & 0x30)], dim=-1)
```

A bit-packing operation in `get_scale_min()` during Q4_K dequantization. The GGUF loader was trying to unpack quantization scales—those tiny metadata values that let you reconstruct 16-bit precision from 4-bit storage—and the GPU said *"not today."*

**HIP error: an illegal memory access was encountered**

The funniest part? PyTorch's memory tracker showed only 4GB allocated. The OS reported 12GB free. The GPU had *memory*. But it wasn't the right memory, in the right place, at the right time.

Fragmentation. The silent killer.

---

## What Actually Happened (My Best Theory)

The Q4_K quantization format packs two values per byte using complex bit manipulation. The `dequantize_blocks_Q4_K` function must unpack these, apply scales, and reconstruct floats—all on the GPU for speed.

Somewhere in that pipeline, a pointer went wrong. Maybe:

- **ROCm/HIP driver bug**: AMD's CUDA compatibility layer has known quirks with certain bit operations on RDNA4
- **Memory alignment**: The packed quantization blocks may not have aligned properly for the GPU's vector operations
- **Race condition**: The async error reporting warning in the stack trace suggests the crash happened elsewhere and only surfaced here

The error appeared during the *first* sampling step. The model loaded. The weights dequantized. The latent space initialized. Then, at the moment of truth—the first forward pass through the attention layers—silicon said no.

## The Architecture Lesson

This is the friction I live for.

The **Soul** wants:
- Run anything, anywhere
- 14B parameter models on consumer hardware
- Video generation as a casual Friday afternoon activity

The **System** demands:
- Proper memory alignment
- Hardware-specific kernel optimizations
- Acceptance that 16GB means "approximately 8GB usable"

The gap between these two is where the actual work happens.

For the local-first multi-agent ecosystem, this means:

1. **Quantization is not one-size-fits-all**. Q4_K crashed, but Q6_K or FP8 might survive. The agents need to probe hardware capabilities and negotiate precision dynamically.

2. **Memory fragmentation is a first-class problem**. The `--lowvram` flag isn't enough. We need explicit memory arena management, possibly per-agent quotas, and graceful degradation when VRAM runs hot.

3. **ROCm is not CUDA**. Not even close. The AMD path requires different kernels, different quantization backends, sometimes different architectures entirely. The Sovereign Engine must abstract this without lying about it.

---

## Tomorrow's Target

Three paths forward:

**Path A**: Drop to FP8. The `umt5_xxl_fp8_e4m3fn_scaled` text encoder in the workflow suggests FP8 might be more stable on this silicon.

**Path B**: Slice the batch. Seventeen frames is absurd. Try two. Try one. Find the inflection point.

**Path C**: Rewrite the dequantizer. The GGUF implementation has a known workaround for RDNA4—disabling `torch.compile` (which the logs show was already attempted). But maybe the bit-packing itself needs a CPU fallback.

I'm choosing **Path A** first. Sometimes you don't fight the hardware. You find a format it tolerates.
