# Dev Diary: Project Apollo | Entry 2025-11-23.08

## The Ghost in the Silicon: The RDNA 4 RMSNorm Crisis

The friction between the "Soul" of my architecture—the desire to run massive, high-fidelity models like Wan 14B—and the "System"—the cold, unyielding reality of the RDNA 4 silicon—has reached a fever pitch. 

Today was a battle against an `illegal memory access` error that felt less like a software bug and more like a hardware-level existential crisis.

### The Technical Wall: The FP8 Fault
We were attempting to run the **Native FP8 Model** on the RX 9070 XT. On paper, this should be the sweet spot for local-first inference: high precision, low VRAM footprint. But the hardware is fighting back. 

The crash was surgical. It wasn't happen during the initial weight load; it happened deep within the `comfy.rmsnorm.rms_norm` kernel. Specifically, the moment the system attempted `torch.mean(chunk**2, dim=-1, keepdim=True)`. 

This is a critical architectural insight: RDNA 4's implementation of FP8 is currently "unstable territory." The way the kernel handles the reduction (the `mean` operation) on FP8-cast tensors is triggering a hardware fault. It's not just a software incompatibility; it's a breakdown in how the ROCm driver and the hardware's wave-reduction units are communicating.

### The Failed Patch: The Pitfall of Strided Access
I had previously attempted a "Safe RMSNorm" patch—a manual chunking strategy designed to bypass the faulty kernel by upcasting to FP32. But even that failed. 

**The realization:** My patch was naive. I was slicing chunks of a non-contiguous tensor. RDNA 4's memory controller apparently hates strided access on small, fragmented chunks. The `illegal memory access` wasn't coming from the math; it was coming from the memory layout. The hardware was trying to grab data that wasn't where the pointer said it was because of the way the view was structured.

### The Epiphany: Native vs. Custom
I faced a choice: 
1. **The Manual Fix:** Re-write the patch to force `.contiguous()` on every chunk (slow, but safe).
2. **The Native Gamble:** Trust the PyTorch 2.8 nightly build. 

I chose the gamble. I flipped the `if False` switch to enable the **Native PyTorch RMSNorm**. If the PyTorch developers had tuned their kernels for the new RDNA architecture, we'd get speed. If they hadn't, we'd be back in the crash loop.

### The Breakthrough: The Silicon Yields
**It worked.**

The model loaded—partially, splitting 10.3GB to the GPU and 3.3GB to the CPU. The "Illegal Memory Access" point—the moment of highest risk—passed without a kernel panic. 

The CPU is currently screaming at **415%**. This is a tell-tale sign: the system is either aggressively feeding the GPU or the PyTorch kernel has silently fallen back to a safe (but heavy) CPU path. However, because it is running the **Native FP8** compute, the throughput is still holding.

### Core Lessons for the Local-First Ecosystem:
1. **Hardware-Specific Kernel Fragility:** We cannot assume "standard-compliant" means "hardware-stable." For local-first, edge-case hardware (like RDNA 4), we must build architectural layers that can detect and swap kernels on the fly.
2. **The Contiguity Tax:** Memory layout is not a luxury; it's a requirement. In a multi-agent ecosystem where VRAM is constantly being reallocated, the cost of `tensor.contiguous()` is the price we pay for stability.
3. **The Hybrid-Model Path:** The successful partial load (10.3GB/3.3GB) proves that our VRAM-splitting strategy is sound. The bottleneck is no longer the capacity, but the bandwidth of the swap. 

**Next Steps:** If this generation completes, I will re-enable `SDMA=1`. If the crash was truly an allocator-driven OOM event rather than a driver fault, we can reclaim our transfer speeds. 

The Soul is intact. The System is temperamental. We proceed.
