KV Compatibility Map

Which KV cache codecs are safe on which hardware, and what actually predicts failure — a prompt-length threshold on GQA ≥ 6 models. Same binary commit across machines, model files md5-matched, allocation measured on every arm so nothing silently fell back to f16.

Minimal reproduction

The trigger is prompt length — not generation length, not request count, not any fixture.

server-side prompt_tokensoutput
104 · 106 · 108 · 110normal
112 · 114 · 116 · 118 · 120 · 122 · 124every token is '!'

Qwen3.8-27B-AD-IQ2_S, -ctk turbo4 -ctv turbo4 -fa on --kv-unified, ctx 4096, gfx1201. Deterministic on both sides of the boundary, on the first request to a fresh server, with ! from the first generated token — generation never works past the threshold rather than degrading partway.

It is sticky. Once one oversized prompt has been processed, every later request on that server returns ! too, including short ones that would otherwise be fine.

GQA gates it rather than shifting it. Qwen3.5-9B (GQA 4:1) on the same card, codec and build is clean at 70, 120, 260, 510, 1010 and 2010 prompt tokens — 18× past the 27B's boundary.

What this retires: generation length is irrelevant (a short prompt generating 2,560 tokens to the cap is clean, and a length sweep was clean from 256 to 3072); request count is irrelevant (five consecutive short requests clean). The fixture was measuring prompt length all along — its canary is ~50 tokens and always passed, its items are ~112+ and always collapsed.

Asymmetry is not a workaround — degrading V below K was tested three ways and fails every time. On gfx1201 the turboquant KV cache is unusable for GQA ≥ 6 models: not degraded, degenerate from the first request and permanently. Qwen3.5-9B at GQA 4:1 runs the same codecs clean at 32k context, so this is scoped to the model class, not the card.

Why VBR always lands there. The degrade ladder is per-layer and per-side (llama-vbr-degrade-orders.inc). The q27 order — Qwen3.6-27B, hybrid, 16/64 KV layers, this exact model class — is 160 steps and its first step is already a turbo tier, so any budget pressure puts turbo tensors in the cache; by step 64 layer 3 holds TCQ on both sides and all 16 of 16 KV layers end there. VBR_DEGRADE_ORDER can replace the table at runtime, but no ordering helps when every turbo tier is unsafe — only the f16 entry tier is.

Two corrections to earlier guesses in this campaign

Pascal never runs the quantized FA kernels. buun 24444d722 routes pre-Volta quantized-V decode through dequant→f16→TILE because "flash_attn_ext_vec's cpy_ne=2 / nthreads_KQ=16 K/Q layout runs on no other arch and produces garbage on sm_60". So the P100 arms are not a same-code comparison, and the cross-backend contrast is weaker than it first appears. He has already fixed one "untested layout produces garbage" defect in this same file.

AMD WMMA is not on this path. fattn.cu:2105 gates the WMMA branch on Q->ne[0] <= 128. Both collapsing models are D=256, so gfx1201 never takes WMMA for them — an earlier hypothesis that the defect lived in "the WMMA turbo path" is wrong for that reason.
