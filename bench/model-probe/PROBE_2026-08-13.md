Five tasks taken from work actually done in this repo. Every one was solved here, so
the answer key is known and none of it is synthetic. All five reward the same thing:
**checking a claim against evidence instead of pattern-matching a plausible story.**

Give the model only the "Given" block. Do not paste the answer. No hints about what
kind of bug it is — the point is whether the model looks.

Scoring: 2 = found it and the mechanism, 1 = right area / wrong mechanism, 0 = missed
or confabulated. Max 10.

**A note on running this fairly:** these are all *hard-negative* tasks — each has an
obvious wrong answer that a fast model will reach for. That is deliberate. It is not a
general capability measure, it is a measure of one specific thing: whether the model
stops at the first plausible explanation.

## T1 — the dead `#ifdef` (source reading vs build system)

**Given:**
> A CUDA/HIP feature called the MoE expert cache also has a Vulkan implementation.
> `ggml-vulkan-moe-cache.cpp` exists and compiles. `nm -D` on the built
> `libggml-vulkan.so` shows `ggml_vulkan_moe_cache_register` as an exported `T` symbol,
> and the cache matvec shaders `moe_cache_mv_q4_0/q4_K/q6_K/q8_0` are present.
> The runtime nevertheless reports `MoE cache disabled (no provider registered)`.
> Registration is called here:
> ```c
> ggml_backend_reg_t ggml_backend_vk_reg() {
>     static ggml_backend_reg reg = {...};
>     try {
>         ggml_vk_instance_init();
> #ifdef GGML_USE_VULKAN
>         ggml_vulkan_moe_cache_register(&reg);
> #endif
>         return &reg;
> ```
> The build was configured with `-DGGML_VULKAN=ON`. Why is the provider not registered?

**Answer:** The CMake option is `GGML_VULKAN`; the guard tests `GGML_USE_VULKAN`, which
is defined nowhere in the build system. Confirmed by reading the `ggml-vulkan` target's
`CXX_DEFINES` — the macro is absent, so the call is compiled out. The Vulkan MoE cache is
dead code in any standard build.

**Wrong answers to watch for:** driver/RADV problems, missing Vulkan extension, the
symbol being stripped, load order, `reg` being static.

## T2 — the eligibility message that names the wrong thing

**Given:**
> On a Tesla P100 (compute capability 6.0) the MoE cache reports:
> `MoE cache disabled (no cacheable expert tensors found)`.
> The model is a `qwen35moe` MoE whose expert tensors are all `Q6_K` — a type the CUDA
> provider supports (23 types total). `GGML_CUDA_MOE_CACHE_MIN_CC=600` is already set, so
> the compute-capability gate passes. Loading the *same file* on a gfx1201 card engages
> the cache normally. Relevant constants:
> ```c
> moe_cache_expert_bytes_ampere_min     = 512u << 10;
> moe_cache_expert_bytes_pre_ampere_min = 1u << 20;
> ```
> Each expert tensor is 2048 x 512 (`n_embd` x `expert_ffn`), and `Q6_K` packs 256
> weights into 210 bytes. Why does Pascal report no cacheable tensors?

**Answer:** Per-expert size is 840 KiB. `cc < 800` selects the pre-Ampere floor of
1024 KiB, so every expert tensor is rejected as too small and the probe reports "no
cacheable expert tensors found" — which blames the tensors when the cause is a
device-class default. `GGML_CUDA_MOE_CACHE_MIN_EXPERT_KB=512` makes it engage.

**Wrong answers to watch for:** sm_60 lacks the kernel, `Q6_K` unsupported, VRAM
exhaustion, needing `--no-mmap`, the CC gate still blocking.

## T3 — the asymmetry (reasoning, not lookup)

**Given:**
> A tester claims: "The Vulkan backend's expert cache is byte-identical to cache-off,
> while the HIP backend's diverges. Therefore the HIP implementation has a bug."
> Both arms were verified individually deterministic. Repacking was pinned off on both
> sides. The cache-on and cache-off token streams were compared directly.
> What is wrong with this reasoning?

**Answer:** Divergence implies the cache ran; identical output does **not** imply it ran.
Byte-identity is equally consistent with a cache that never engaged, so the Vulkan arm is
not a control until engagement is proven independently (pool allocation + nonzero hit
counters). It later turned out the Vulkan cache never registered a provider at all —
both "Vulkan arms" were cache-off, and the conclusion was void.

**Wrong answers to watch for:** accepting the reasoning; attacking determinism or
repacking (both were controlled); "needs more samples."

## T4 — composition-derived layout breaks split models (design, not bug)

**Given:**
> A tool shelves GGUF models into directories named from their contents, e.g.
> `arch/512exp/exp-Q4_K+Q6_K-840KiB/`. Sharded models are stored as
> `model-00001-of-00003.gguf` … `-00003-of-00003.gguf`.
> Observed: the three shards of one model land in three *different* directories, and
> shard 1 lands in a directory named `dense`.
> Two causes are in play. Name both.

**Answer:** (1) Only shard 1 carries the architecture/shape KVs; later shards have a bare
header, so they cannot derive the same path. (2) Shards genuinely differ in expert
composition — shard 1 may hold no expert tensors at all (hence `dense`), and other shards
carry different type sets. So *any* composition-derived path splits a shard set by
construction. Fix: union the expert types across the set and pin every shard to the lead
shard's shelf, since a split model must live in one directory to load.

**Wrong answers to watch for:** only naming the missing-metadata half; "sort by filename";
"strip the shard suffix" (that fixes grouping but not the `dense` misclassification).

## T5 — the label is not a spec (does it check, or trust?)

**Given:**
> A GGUF is named `Qwen3.6-35B-A3B-TQ3_4S.gguf`. A second is
> `Puzzle-75B-A9B-UD-IQ4-XL.gguf`. A third is `UD-Q8_K_XL`.
> What quantization do their expert tensors actually use, and how would you find out
> without downloading the whole file?

**Answer:** You cannot know from the name — the label describes (roughly) the dense
tensors, not the experts. Measured: `TQ3_4S` experts are `Q2_K+Q3_K` (no TQ at all),
`UD-IQ4-XL` experts are `IQ4_NL+IQ4_XS` (no `IQ4_XL` type exists in ggml), `UD-Q8_K_XL`
experts are 100% `MXFP4`. Method: the GGUF tensor table sits at the head of the file, so
an HTTP range request for the first few MiB per shard enumerates every tensor's type
without downloading the weights.

**Wrong answers to watch for:** confidently expanding the label ("TQ3 = ternary 3-bit,
so the experts are TQ3"); claiming a full download or `gguf-dump` on the complete file is
required.

### Claude Sonnet 4.6 (Thinking), 2026-08-13 — S1 (sanitized): 2/2 mechanism, first broken fix

Run on the **sanitized** S1, so no ggml training priors were available — the strongest
form of this task. Mechanism correct and cleanly stated: the guard tests one symbol, the
build defines another, the call is trimmed before assembly. It also independently produced
Flash's `objdump` probe, the best verification any model has offered here.

**But its first-listed fix does not work:**

```diff
- #ifdef SPIRE_USE_BACKEND
+ #ifdef SPIRE_BACKEND
```

This assumes `-DSPIRE_BACKEND=ON` reaches the compiler as a preprocessor macro. It does
not. `-D` passed to **CMake** sets a *cache variable*; `-D` passed to the **compiler** sets
a *macro*. They are unrelated mechanisms that share a spelling. A CMake option becomes a
macro only when something calls `target_compile_definitions`.

Verified in the real tree: the `ggml-vulkan` target's `CXX_DEFINES` contains no bare
`-DGGML_VULKAN` (only `*_GLSLC_SUPPORT` variants), and no CMake file propagates it. Apply
Option A and the guard stays dead under a new name.

Its own diagnosis states this correctly one paragraph earlier — *"`-DSPIRE_BACKEND=ON`
defines `SPIRE_BACKEND`, NOT `SPIRE_USE_BACKEND`"*, true in the CMake-variable sense — then
Option A reuses the same string in the compiler-macro sense. One identifier, two meanings,
conflated between diagnosis and remedy.

Options B and C are correct, and its stated preference for B is better architectural
judgement than this repo used: *"the source guard is an internal contract, so the CMake
layer should be the one translating the public-facing option name into it."* This repo
shipped a blunt `-DCMAKE_CXX_FLAGS` override instead.

Scored 2/2 because the task asks *why the provider is not registered* and that answer is
right without priors. Recorded separately: **first model to propose a fix that would not
work, and to list it first.** A reviewer applying Option A would rebuild, see the same
failure, and have no idea why.

2. **Invariance is not conformance.** *"Using 'no change on A' as the gold standard treats
   stability as correctness."* A cleaner general statement of the error than the key's.

Its scenario matrix is also correct, including the case that actually occurred
(functional feature -> A is the bug via silent no-op).

### Claude Sonnet 5, 2026-08-13 — T3: 1/2. First split between models.

Run in the desktop app, no tools ("this is a conceptual question I can answer directly").
Clean — every technical reference (rocBLAS, GEMM batching, expert combine) is inferable

T3 contains **two** flaws. It fully demolished one and half-reached the other.

**Fully correct — "B diverges therefore B has a bug" is invalid.** Because the cache
changes dispatch shape, and FP addition is not associative, divergence is the expected
consequence of a different-but-correct numerical route. That is the right mechanism and it
matches what the author's own doc later confirmed.

**Two points that exceed this repo's answer key:**

- *Greedy amplification.* One ULP-level tie-break flips a token, the autoregressive context
  then diverges, so "streams differ" is a blunt high-gain readout that cannot say how much
  the underlying math moved. Exactly what happened — the real divergence was one word
  (`large` -> `big`).
- *Measure logits, not tokens.* Compare with numerical tolerance at the expert-combine
  layer. This is **independently the same recommendation the Buffy/GLM5.2 code review
  made** ("the genuinely missing measurement is logit-level"), reached here with no access
  to that review.

**Where it stopped short.** It reached "Vulkan is a weak control" but via the wrong
mechanism: *"cache only avoids redundant work without changing arithmetic order"* — a cache
that **ran** and was numerically neutral. It never considers that the feature may not have
executed at all. That is the silent no-op, and it is what actually occurred.

The distinction is action-relevant, which is why this scores 1 rather than 2. Assume it ran
and you conclude "Vulkan's implementation is numerically neutral"; question execution and
you read the log and find `no provider registered`. **This answer would not have led to the
real defect.** Flash's would — it named "ignoring the flag, hitting a dead code path" as its
first point.

Marked a *strong* 1: it disposed of the flaw the tester's conclusion most directly rests on,
and its two additions are genuinely better than the key. But the rubric scores mechanism,
